# Configuration : ressources et tableaux


## Types de ressources

Un **type de ressource** est une catégorie que vous définissez vous-même (*Figure*, *Tableau*, *Diagramme*, *Listing*…) et qui détermine comment les ressources de ce genre sont numérotées, légendées et citées. La liste se trouve dans `config.resourceTypes` ; le Sandbox la modifie dans **Maquette → Figures et tableaux → Numérotation et placement**.

Quand `config.resourceTypes` n’est pas défini, Postext fournit trois types par défaut : **Figure**, **Tableau** et **Vidéo**, chacun numéroté séparément selon `{h1}.{n}` (`{h1}-{n}` en chinois, en japonais et en arabe), remis à zéro à chaque titre de niveau 1, avec des compteurs décimaux. Une liste sans type `video` (celle d’un livre enregistré avant l’arrivée des vidéos) numérote quand même les ressources vidéo de type `video` : le type Vidéo intégré leur est ajouté (`effectiveResourceTypes(config, resources)`), et `defaultVideoResourceType(locale)` le renvoie seul. Leurs noms suivent la langue du document : `config.locale`, à défaut `bodyText.hyphenation.locale`, à défaut l’anglais (voir [Langue du document](/fr/docs/configuration-language#langue-du-document)).

Les types par défaut dépendent de la langue. La fonction exportée `defaultResourceTypes(locale = 'en')` traduit les noms des types, les libellés courts et les préfixes de légende dans la langue du document : l’anglais donne *Figure*/*Fig.* et *Table*/*Tab.* ; l’espagnol *Figura*/*Fig.* et *Tabla*/*Tabla* ; le français, l’allemand, l’italien, le portugais, le catalan, le néerlandais, le chinois (simplifié et traditionnel), le japonais et l’arabe ont aussi les leurs (le tableau de [Langue du document](/fr/docs/configuration-language#langue-du-document) les donne). Les étiquettes régionales comme `es-ES` se résolvent par la langue, et toute langue sans traduction se rabat sur l’anglais. Dans toutes les langues, le compteur repart à chaque `h1` et compte en décimal. Le modèle est `'{h1}.{n}'`, sauf en chinois, en japonais et en arabe, qui relient le numéro du chapitre et le compteur par un trait d’union : `'{h1}-{n}'` (图1-1, 図1-1). Chaque appel renvoie des objets neufs, que vous pouvez donc modifier librement :

```ts
import { defaultResourceTypes } from 'postext';

const types = defaultResourceTypes('es');
// => [{ id: 'figure', name: 'Figura', shortLabel: 'Fig.', captionPrefix: 'Figura',
//       numberingTemplate: '{h1}.{n}', resetOn: 'h1', counterFormat: 'decimal', … },
//     { id: 'table',  name: 'Tabla',  shortLabel: 'Tabla', captionPrefix: 'Tabla', … },
//     { id: 'video',  name: 'Vídeo',  shortLabel: 'Vídeo', captionPrefix: 'Vídeo', … }]
```

```ts
type ResourceCounterFormat =
  | 'decimal'
  | 'roman-lower'
  | 'roman-upper'
  | 'alpha-lower'
  | 'alpha-upper'
  | EastAsianNumeralStyle  // 'simp-chinese-informal', 'circled-decimal', 'hiragana'…
  | ArabicNumeralStyle;    // 'arabic-indic', 'persian', 'abjad'…

type ResourceCounterReset = 'never' | 'h1' | 'h2' | 'h3' | 'h4' | 'h5' | 'h6';

interface ResourcePlacement {
  position?: 'auto' | 'top' | 'bottom' | 'here'; // which free slot a float may take; 'here' = inline embed at the ::resource directive
  span?: 'column' | 'page' | 'side';             // one column, the full content width, or the float-only side column
  rotate?: 'ccw' | 'cw';                         // a quarter turn: a landscape table on a page of its own
  width?: number;                                // fraction (0 < width < 1) of the column or page width; default: the whole width
  align?: 'left' | 'center' | 'right' | 'start' | 'end'; // where a float narrower than its column sits; default 'left'
  captionSide?: boolean | 'inside';              // caption beside the figure, in the side column of a oneAndHalf layout (column floats and resources set in the text); 'inside': beside the picture, within its own slot
  columns?: number;                              // a 'column' float across this many adjacent columns (since 1.18)
  wrap?: 'none' | 'left' | 'right' | 'start' | 'end' | 'contour'; // text beside the resource, at that side of its column (since 1.24); 'contour' follows its shape
  wrapGap?: Dimension;                           // space between the wrapped resource and the text (since 1.24)
  shrink?: 'never' | 'page' | 'slot';            // scale a floated picture down to the room of its slot
  minScale?: number;                             // the smallest scale shrink sets it at; default 0.7
  captionMeasure?: 'slot' | 'body';              // caption and note as wide as the slot or as the picture
  citingPage?: boolean;                          // a top or auto float may head the page or column it is cited on
}

interface ResourceType {
  id: string;                          // stable id, referenced by Resource.typeId
  name: string;                        // singular display name, e.g. "Figure"
  namePlural?: string;                 // optional plural, e.g. "Figures"
  shortLabel: string;                  // compact label for inline refs, e.g. "Fig."
  numberingTemplate: string;           // "{h1}.{n}" or "{n}"
  resetOn: ResourceCounterReset;       // when the {n} counter resets
  counterFormat: ResourceCounterFormat;// how {n} is formatted
  captionPrefix: string;               // prepended to the caption, e.g. "Figure"
  defaultPlacement?: ResourcePlacement;// fallback placement for this type's resources
  captionStyle?: CaptionStyleConfig;   // partial caption style for this type's resources
}
```

Un type peut omettre des champs (depuis postext 1.38) : le type intégré de même identifiant les complète (`figure`, `table`, `video`, dans la langue du document) ; à défaut, `name` reprend l’identifiant, `shortLabel` et `captionPrefix` reprennent `name`, `numberingTemplate` vaut `{'{h1}.{n}'}` (`{'{h1}-{n}'}` en chinois, en japonais et en arabe), `resetOn` vaut `'h1'` et `counterFormat` vaut `'decimal'`. Un `resetOn` qui ne désigne aucun niveau compte comme `'h1'` et déclenche l’avertissement `unknownConfigValue`. Un type qui donne son propre `name` et aucun `shortLabel` est cité sous ce nom, comme avant la 1.38, et non sous l’étiquette courte du type intégré : dans un document en anglais, `{ id: 'table', name: 'Table' }` donne « Table 1 », et non « Tab. 1 ».

`ResourcePlacement` a la même forme que le `placement` qu’une ressource définit pour elle-même. `position` choisit le genre d’emplacement libre qu’un flottant peut prendre : `auto` (par défaut) prend le premier après le premier renvoi, `top` / `bottom` le limitent à ce genre de bande, `here` insère la ressource dans le texte. `span` fixe l’étendue du flottant : une colonne, toute la largeur du contenu, ou la colonne latérale réservée aux flottants d’une mise en page à une colonne et demie. `rotate` fait pivoter la ressource d’un quart de tour et en fait un flottant sur toute la largeur de la page, sur une page à lui. `width` rétrécit un flottant à une fraction de sa colonne (ou de la page, pour un flottant sur toute la largeur de la page) : un petit tableau dans une large colonne, par exemple. `align` indique où se place un flottant ainsi rétréci (à gauche par défaut, au centre ou à droite) et où se place, dans son emplacement, une image plus étroite que lui : un bitmap plus petit que la colonne, ou une image que `layout.fitFiguresToPage` a réduite. La légende et la note gardent la largeur de l’emplacement. (Jusqu’à postext 1.4, une telle image était toujours alignée à gauche.) `left` et `right` sont des côtés du fil du texte, inversés sur les pages d’un document de droite à gauche ; `start` et `end` désignent les mêmes côtés. `captionSide` place la légende à côté de la figure, dans la colonne latérale réservée aux flottants d’une mise en page à une colonne et demie (`layout.sideColumnRole: 'floats'`), à hauteur du haut de la figure (de son bas pour un flottant en pied de colonne) ; il s’applique aux flottants de colonne et, depuis postext 1.28, à une ressource placée dans le texte (`position: 'here'`, large d’une colonne, sans texte qui l’habille), dont la légende et la note se placent dans la colonne latérale, à hauteur du haut de son corps, là où cette colonne est libre à côté d’elle, et sous le corps là où elle ne l’est pas (`layout.inlineCaptionSide`, actif par défaut ; `false` réserve les légendes latérales aux flottants de colonne) ; une page sans cette colonne garde la légende sous la figure. Quand ni la ressource ni son type ne définissent de placement, la valeur intégrée par défaut est `auto` / `column`. `shrink` (`'never'`, `'page'`, `'slot'`) et `minScale` (0,7 s’il n’est pas défini) réduisent une image flottante à la place dont dispose son emplacement au lieu de la repousser plus loin, et `captionMeasure: 'body'` compose la légende et la note d’une image plus étroite que son emplacement à la largeur de l’image (voir [Format du document › Placement](/fr/docs/document-format-resources#placement)) ; `layout.floatShrink` donne la valeur par défaut du document pour les deux premiers. `wrap` place une ressource insérée ou un flottant d’une colonne d’un côté de sa colonne, le texte courant à côté d’elle, à `wrapGap` de distance ; `layout.wrap` contient les valeurs par défaut (voir [Format du document › Habillage](/fr/docs/document-format-resources#habillage-du-texte)). `wrap: 'contour'` fait courir le texte le long de la forme de l’image, prise dans le `contour` de la ressource (`points`, `alpha`, `threshold`, `margin`, et le `traced` de l’hôte ; voir [Format du document › Habillage au contour](/fr/docs/document-format-resources#habillage-au-contour)). `citingPage` permet à un flottant `top` ou `auto` de se placer en tête de la page ou de la colonne où tombe la ligne qui le cite, au lieu de prendre le premier emplacement libre qui la suit ; `layout.floatsAtCitingPage` donne la valeur par défaut du document et `layout.maxTopFraction` la part de la colonne qu’il peut occuper (voir [Format du document › Placement](/fr/docs/document-format-resources#placement)).

`columns` (depuis postext 1.18) étend un flottant `span: 'column'` sur autant de colonnes adjacentes d’une page qui en compte plusieurs : une image sur deux des cinq colonnes d’un journal. Sa largeur couvre ces colonnes et les gouttières qui les séparent. Il prend la tête d’une suite de colonnes vides qui commencent au même niveau, ou le pied de la colonne qui le cite et des colonnes vides qui la suivent ; autant de colonnes que la page en compte, ou davantage, en font un flottant sur toute la largeur de la page. Il est ignoré par les étendues `'page'` et `'side'`, par une ressource pivotée (`rotate`) et par une insertion dans le texte (`here`), et `captionSide` ne s’applique qu’à un flottant large d’une seule colonne.

`captionSide: 'inside'` (depuis postext 1.52) place la légende et la note à côté d’une image étroite, dans son propre emplacement, quelle que soit la mise en page : la colonne d’une page à une ou deux colonnes, un flottant sur toute la page, une ressource placée dans le texte, un encadré ou le cadre d’une page composée. L’emplacement garde toute sa largeur ; l’image en prend `width` (la moitié si `width` n’est pas donné) du côté que nomme `align` (`'center'` vaut `'left'`), et la légende prend le reste après `layout.gutterWidth`, sa première ligne au niveau du haut de l’image. Le bloc est aussi haut que le plus haut des deux : une longue légende repousse le texte qui suit, et le bloc passe entier à la colonne suivante quand la place restant au pied de la colonne ne suffit pas. Une bande de légende plus étroite que le cinquième de l’emplacement revient sous l’image. Cela vaut pour les images (bitmap, SVG, vidéo) ; un tableau, une ressource tournée et une ressource sur une page verticale gardent leur légende au-dessus ou au-dessous, et aucun texte ne contourne une telle image.

### Jetons de modèle

`numberingTemplate` est rendu par le même moteur que la numérotation des titres (voir [Titres](/fr/docs/configuration-headings#titres)). Il reconnaît deux genres de jetons :

- `{n}` : le compteur propre au type, écrit selon `counterFormat`. C’est la valeur qui augmente à chaque ressource et qui revient à zéro selon `resetOn`.
- `{h1}` … `{h6}` : les numéros de titre en vigueur à l’endroit du premier renvoi, en décimal sauf si le jeton précise un style. `{h1}` est le numéro du titre de niveau 1 courant, `{h2}` celui du niveau 2, et ainsi de suite.
- `{h1:A}`, `{h2:i}`, `{n:i}` : un jeton suivi de deux-points et d’un style s’écrit dans ce style, n’importe lequel de ceux qu’accepte un modèle de titre : `1`, `01`, `A`, `a`, `I`, `i`, un nom de format de numérotation comme `upper-roman`, un jeton d’un seul caractère comme `一` ou `①`, ou un style en toutes lettres comme `Words`. Sur `{n}`, le style l’emporte sur `counterFormat` pour ce jeton. Un style inconnu compte en décimal. Depuis postext 1.28.

Tout autre texte est pris littéralement. Une barre oblique inverse échappe un `{`, un `}` ou un `\` littéral. Quand un jeton de titre n’a pas de valeur à cet endroit (par ex. `{h1}` avant tout titre de niveau 1), il disparaît avec le séparateur qui le jouxte : `{h1}.{n}` se réduit proprement au simple compteur.

Un modèle vide (`''`) n’imprime aucun numéro, mais le type compte toujours ses ressources : une légende s’imprime *Do. Lignes à 0°* et un `:ref` imprime le libellé seul (*Do*). Jusqu’à postext 1.4, une telle légende s’imprimait *Do .Lignes à 0°* et le renvoi se terminait par une espace insécable.

**Annexes.** Un livre dont les annexes sont désignées par des lettres grâce à un style de titre (`numberingTemplate: 'Appendix {1:A}'`, avec `startAt=1` sur la première) donne à leurs figures et à leurs tableaux un type à part, `{ ...table, id: 'table-a', numberingTemplate: '{h1:A}.{n}', resetOn: 'h1' }`. Un seul type sert à toutes les annexes : il imprime *Tableau A.1*, *A.2* et *B.1*, dans la légende comme dans `:ref`. Un simple `{h1}` imprimerait ici le numéro du titre en décimal (*Tableau 1.1*).

### Numérotation et renvois

Le numéro que produit un type de ressource est celui qu’imprime `:ref` et que précède le préfixe de légende. `:ref{id}` est la forme principale : le premier renvoi dans l’ordre de lecture **insère** la ressource, qui flotte jusqu’au premier emplacement libre après ce renvoi, à savoir le bas de la colonne qui la cite, le haut ou le bas de la colonne vide suivante, ou une bande de la page suivante (selon son placement résolu : `position: 'auto' | 'top' | 'bottom' | 'here'` et `span: 'column' | 'page' | 'side'`, plus `rotate`, `width`, `align` et `captionSide`, résolus d’abord sur la ressource, puis sur le `defaultPlacement` du type, puis selon la valeur intégrée par défaut `auto` / `column` ; `'top'` / `'bottom'` limitent la recherche à ce genre d’emplacement). L’insertion `::resource{id}` est facultative et ne sert qu’avec `placement.position: 'here'` : une insertion dans le texte, non flottante, à un point précis du flux. La grammaire complète côté document (les deux formes, plus les options `style` et `text` de `:ref`) est décrite dans [Format du document › Ressources](/fr/docs/document-format-resources#ressources), y compris la façon dont l’ordre des premiers renvois détermine le compte.

Cela reproduit la numérotation des titres : de même qu’un niveau de titre a un `numberingTemplate`, un type de ressource en a un ; mais le compteur des ressources (`{n}`) avance à chaque premier renvoi et non à chaque titre, et `resetOn` le rattache à la hiérarchie des titres.

### Ce qui est numéroté

Une ressource est numérotée quand le texte la cite (avec `:ref` ou avec une insertion `::resource`), dans l’ordre de ces premiers renvois, quel que soit son placement : flottante, dans le texte (`here`), dans la colonne latérale ou pivotée. Une ressource que seule une maquette dessine (un élément `image` d’une ouverture de chapitre, d’un titre courant ou d’une page de partie) ou que rien ne cite ne reçoit pas de numéro et ne fait pas avancer le compteur de son type. Ainsi, dans un essai photographique dont les planches à fond perdu sont des images d’ouverture et dont la seule planche plus petite est un flottant cité, ce flottant est la planche **I**, quel que soit le nombre de planches que les ouvertures ont montrées avant lui ; numérotez les planches d’ouverture dans leur maquette (avec un attribut comme `{attr.plate}`) et gardez le compteur pour les planches que le texte cite.

Dans un livre mis en page chapitre par chapitre (le Sandbox, `buildBundle`, ou `buildDocument` avec les compteurs que transmet `continuationAfter()`), c’est le premier renvoi de tout le livre qui compte : une ressource garde le numéro reçu dans le chapitre qui la cite en premier, et seul ce chapitre la place. Le `:ref` d’un chapitre ultérieur imprime ce numéro sans rien placer, et une insertion `::resource` d’une ressource flottante n’y est qu’un renvoi de plus (une insertion `here` reste composée là où elle est écrite). Un tel renvoi pointe vers la figure quand la figure se trouve dans la même sortie : un PDF du livre entier le lie à la page du chapitre précédent. Un chapitre rendu seul, en HTML ou en PDF, le compose en texte simple dans la couleur des liens, puisque sa figure n’est pas dans ce document. Un hôte qui réunit le HTML des chapitres sur une seule page passe à `renderToHtml` les ressources que les chapitres ancrent, sous la forme `refTargets`, et un tel renvoi pointe de nouveau vers la figure du chapitre précédent :

```ts
import { anchoredResourceIds, buildBundle, renderToHtml } from 'postext';

const docs = buildBundle(bundle);
const refTargets = new Set(docs.flatMap((d) => [...anchoredResourceIds(d)]));
const html = docs.map((d) => renderToHtml(d, { refTargets })).join('');
```

**Modifié dans postext 1.5 :** jusqu’à la 1.4, chaque chapitre qui citait une figure la refaisait flotter, et le HTML de chaque `:ref` était un lien, que sa figure soit sur la page ou non.

`{h1}` est le compte continu des titres de niveau 1 : chaque H1 le fait avancer, sauf si son style de titre définit `numbered: false` (un `numberingTemplate` vide masque le numéro du titre, il n’arrête pas le compte). Un article dont le seul H1 est son titre numérote donc ses figures `1.1`, `1.2`… avec les types `{h1}.{n}` intégrés. Deux façons d’imprimer Figure 1, 2… :

- un type numéroté `{n}` avec `resetOn: 'never'` (avec `resetOn: 'h1'`, le compte reprendrait à chaque H1) ;
- un [style de titre](/fr/docs/configuration-styles#styles-de-titre) avec `numbered: false` sur le titre, et sur tout autre H1 qui ne doit pas compter : un tel titre ne fait pas avancer `{h1}` mais le laisse tel qu’il était (vide avant le premier H1 compté, où `{h1}.{n}` se réduit au simple compteur) et ne déclenche jamais `resetOn: 'h1'` : le compte se poursuit donc au-delà. Après `# Introduction` et sa figure 1.1, la première figure sous un `# Appendix` non numéroté est la 1.2, pas la 2.1.

```ts
// Figure 1, 2, 3… in a single-article document
resourceTypes: defaultResourceTypes('en').map((t) => ({ ...t, numberingTemplate: '{n}', resetOn: 'never' })),
```

### Lignes zébrées

Les longs tableaux de données se lisent plus facilement d’un bout à l’autre de la ligne quand une ligne sur deux est teintée. `bodyAlternateBackgroundEnabled` active les bandes et `bodyAlternateBackground` fixe leur couleur :

```ts
const config: PostextConfig = {
  tableStyle: {
    bodyBackgroundEnabled: true,
    bodyBackground: { hex: '#ffffff', model: 'hex' },
    bodyAlternateBackgroundEnabled: true,
    bodyAlternateBackground: { hex: '#eef3fa', model: 'hex' },
  },
};
```

Les lignes se comptent à partir de la première ligne qui suit les lignes d’en-tête (`TableModel.headerRowCount`, ou les premières lignes faites de cellules d’en-tête) : cette ligne garde `bodyBackground` (ou aucun fond tant que `bodyBackgroundEnabled` est désactivé), la suivante prend le fond alterné, et ainsi de suite. Le compte suit le modèle du tableau, pas la page : un tableau coupé sur plusieurs pages garde la bande de chaque ligne sur chaque page, et une cellule fusionnée sur plusieurs lignes prend la bande de sa première ligne. Les cellules d’en-tête gardent le fond de l’en-tête, le `background` propre à une cellule l’emporte sur les deux, et une couleur liée à la palette suit la palette. Un [style de tableau nommé](#styles-de-tableau-nommés) définit ces deux champs comme les autres : un style peut donc être zébré sans que les autres tableaux du document le soient ; dans le Sandbox, ce sont l’interrupteur *Lignes zébrées* et sa couleur, sous **Cellules du corps**.

Dans le VDT, les cellules des lignes alternées portent `alternate: true`, et la mise en page du tableau porte `bodyAlternateBackground`. `tableCellFill(table, cell)` renvoie le fond avec lequel une cellule est peinte (le sien, celui de l’en-tête, le fond alterné ou celui du corps), c’est-à-dire ce que peignent les moteurs de rendu canvas, HTML et PDF. Les fonds voisins se rejoignent sans jointure : un navigateur à un rapport de pixels fractionnaire ou une visionneuse PDF lisse chaque fond séparément et laisserait voir la page par un filet extra-fin entre deux cellules ; les moteurs HTML et PDF peignent donc `tableCellFillRects(table)`, c’est-à-dire le fond de chaque cellule prolongé d’une bande sur chaque bord qu’elle partage avec une cellule peinte après elle, que cette cellule recouvre ensuite, et le canvas cale ses fonds sur les pixels de l’appareil.

### Filets booktabs

Les tableaux des revues et des manuels se composent d’ordinaire avec trois filets et aucun trait vertical : un filet épais au-dessus du tableau, un fin sous l’en-tête et un épais sous la dernière ligne, avec de courts filets sous les intitulés qui regroupent plusieurs colonnes (le paquet LaTeX `booktabs` : `\toprule`, `\midrule`, `\cmidrule`, `\bottomrule`). `rules: 'booktabs'` trace ce schéma :

```ts
const config: PostextConfig = {
  tableStyle: {
    rules: 'booktabs',
    borderColor: { hex: '#000000', model: 'hex' },
    headerBackgroundEnabled: false,
  },
};
```

- Le filet au-dessus du tableau et celui sous sa dernière ligne ont l’épaisseur `heavyRuleWidth` (`0.08em`), le filet sous les lignes d’en-tête l’épaisseur `lightRuleWidth` (`0.05em`). Un tableau sans lignes d’en-tête n’a pas de filet d’en-tête.
- Une cellule d’en-tête qui couvre plusieurs colonnes au-dessus de la dernière ligne d’en-tête reçoit sous elle un filet d’épaisseur `spanRuleWidth` (`0.03em`). Avec `spanRules: 'trimmed'` (par défaut), le filet est raccourci de `spanRuleTrim` (`0.5em`) aux deux bouts, pour que les filets sous deux intitulés voisins ne se touchent pas ; `'full'` le prolonge sur toute la cellule et `'none'` l’omet.
- `groupRules: true` ajoute un filet fin au-dessus de chaque ligne du corps qui ouvre un groupe (une seule cellule sur toute la largeur du tableau, ou une ligne de cellules d’en-tête), sauf si la ligne ouvre le tableau ou une page, où se trouve déjà le filet d’en-tête.
- Les épaisseurs se calculent sur le corps des cellules du corps (`bodyFontSize`) : un en-tête plus grand n’épaissit donc pas le filet d’en-tête. Une épaisseur de `0` supprime le filet.
- Les filets prennent `borderColor` (une couleur liée à la palette suit la palette et `:::part palette`), et `borders: false` les désactive. `borderWidth` ne s’applique pas, `borderRadius` non plus : les filets restent droits, tandis que les fonds des cellules sont toujours découpés au cadre arrondi. Les fonds d’en-tête, les lignes zébrées et le `background` propre à une cellule fonctionnent comme avec les autres schémas, sous les filets.
- Un tableau coupé sur plusieurs pages répète ses lignes d’en-tête sur chaque partie : chaque partie s’ouvre donc sur le filet épais et le filet d’en-tête. Le filet épais sous la dernière ligne ne ferme que la dernière partie ; une partie qui continue à la page suivante se termine par `continuedFootRule` : un filet fin (`'light'`, par défaut), le filet épais (`'bottom'`) ou rien (`'none'`).

La mise en page calcule les filets une seule fois. Le tableau du VDT les contient sous forme de `strokes` (`{ x1, y1, x2, y2, widthPx }`, relatifs au coin supérieur gauche du corps du tableau), et le canvas, la visionneuse HTML, le PDF et l’EPUB à mise en page fixe tracent exactement ceux-là ; dans un PDF balisé, ce sont des artefacts de mise en page. L’EPUB recomposable les écrit comme des bordures CSS sur le tableau et son en-tête, les filets raccourcis étant dessinés comme des lignes d’arrière-plan. Dans le Sandbox, **Booktabs** dans la liste *Filets* affiche ces champs et masque *Épaisseur de bordure* et *Rayon des coins*.

### Styles de tableau nommés

Un document compose rarement tous ses tableaux de la même façon : une liste de contrôle dans une grille bleu marine au cadre arrondi, une ligne d’options entourée de son seul cadre extérieur, un tableau de données en simples filets horizontaux. `tableStyles` déclare des variantes nommées, et une ressource tableau en choisit une avec `table.styleId`. Tout champ qu’un style laisse vide est pris d’abord dans `tableStyle`, puis dans le texte courant : un style n’énonce que ce qui distingue ses tableaux. Un tableau sans `styleId`, ou dont l’identifiant n’est déclaré par aucun style, garde `tableStyle` ; un document sans `tableStyles` se rend exactement comme avant.

```ts
const config: PostextConfig = {
  tableStyle: {
    borderColor: { hex: '#163a76', model: 'hex' },
    borderWidth: { value: 1.3, unit: 'pt' },
    borderRadius: { value: 10, unit: 'pt' },
  },
  tableStyles: [
    {
      id: 'option',
      name: 'Option row',
      rules: 'outer',
      borderColor: { hex: '#7a9cc6', model: 'hex' },
      borderWidth: { value: 1, unit: 'pt' },
      borderRadius: { value: 8, unit: 'pt' },
      headerBackgroundEnabled: false,
    },
  ],
};

// In the resources: this table is set in the "option" style.
const resource: Resource = {
  id: 'choices', typeId: 'table', kind: 'table', createdAt: 0, updatedAt: 0,
  table: { model: { rows: [/* … */] }, styleId: 'option' },
};
```

Chaque entrée accepte tous les champs de `tableStyle`, plus `id` (ce que référence `table.styleId`) et un `name` facultatif pour l’éditeur (l’identifiant par défaut). Tout ce qu’un style peut définir s’applique tableau par tableau : typographie, fonds, bordures, filets, rayon des coins, marges intérieures et comportement en cas de débordement, avec ses mentions de suite. `resolveTableStylesConfig(styles, tableStyle, resolvedBodyText, locale?)` renvoie la liste résolue, `pickTableStyle(resolved, styleId)` le style dans lequel un tableau est composé, et `stripTableStylesDefaults` supprime les champs non définis (il garde un champ égal à sa valeur par défaut intégrée, qui l’emporte encore sur une valeur différente de `tableStyle`). Dans un EPUB recomposable, un style nommé est une classe posée sur le tableau (`pt-table-<id>`), mise en forme par la feuille de style du livre.

### Tableaux plus hauts que la page

Un tableau flottant qui ne tient pas sur la page neuve qui lui est offerte n’est ni comprimé ni laissé déborder : avec `overflow: 'split'` (par défaut), le moteur le coupe entre deux lignes, au dernier bord qui tient sur la page, et le continue sur les pages suivantes, autant qu’il en faut. Chaque partie suivante répète les lignes d’en-tête du tableau (`TableModel.headerRowCount`, ou à défaut les premières lignes faites de cellules d’en-tête) et reprend la légende avec `continuedSuffix` après la description : « Table 6-4. Title *(cont.)* ». Chaque partie qui continue reçoit `continuesMarker` sous elle, aligné à droite, dans le caractère de la note ; la note du tableau est réservée à la dernière partie. Une coupe ne traverse jamais une cellule fusionnée (une cellule sur plusieurs lignes passe entière à la partie suivante), et une ligne qui chapeaute les lignes du dessous (une seule cellule sur toute la largeur du tableau) est reportée à la partie suivante plutôt que laissée seule au pied d’une page. Un tableau booktabs ferme chaque partie qui continue avec `continuedFootRule` (voir [filets booktabs](#filets-booktabs)).

**Où finit la première partie.** Un tableau à qui s’offre la tête d’une colonne vide après son renvoi prend les lignes qui y tiennent et continue dans l’emplacement suivant. Il remplit la colonne jusqu’au pied quand il a la colonne pour lui seul : une partie qui laisserait sous elle moins de trois lignes de texte les prend aussi, plutôt que de laisser un moignon de texte. Quand la colonne porte déjà une autre bande de flottants (une figure sur toute la largeur en tête de page, par exemple), la partie s’arrête au contraire à trois lignes de texte au moins du pied, soit la place pour le texte que laisse tout flottant qui partage une colonne avec un autre : la colonne se termine ainsi par du texte sous le tableau et non par des flottants seuls. Pour qu’un long tableau descende jusqu’au pied de sa colonne, citez-le là où la page où il commence ne porte aucun autre flottant (après la page d’une figure sur toute la largeur, par exemple), ou ajustez ses lignes à la colonne.

`'clip'` garde les premières lignes qui tiennent sur la page et abandonne les autres sans le signaler (la note ferme toujours la partie) ; `'hide'` omet entièrement le tableau. Les deux ne s’appliquent qu’à un tableau plus haut qu’une page : un tableau qui tient est placé entier dans tous les modes.

**Tableaux placés dans le texte.** Un tableau placé `here` (inséré avec `::resource`) suit les mêmes règles depuis postext 1.25 (`splitInline`, actif par défaut). Quand il ne tient pas dans la place restante de sa colonne, il est coupé entre deux lignes : la première partie garde au-dessus d’elle l’espace des flottants et au moins les lignes d’en-tête et deux lignes du corps (s’il en tient moins, tout le tableau commence dans la colonne suivante, comme avant), chaque partie suivante ouvre la colonne suivante sans espace au-dessus d’elle, composée à la largeur de cette colonne (une mise en page à une colonne et demie compose une partie dans la colonne étroite, à sa largeur), et le texte qui suit la ligne `::resource` vient après la dernière partie. La répétition de l’en-tête, la légende avec son suffixe, la mention, la note sur la dernière partie, le reliquat de trois lignes au moins et les coupes qui respectent les cellules fusionnées et les têtes de groupe sont ceux d’un tableau flottant. Un tableau de moins de cinq lignes de corps n’est jamais coupé. `'clip'` garde les premières lignes d’un tableau dans le texte plus haut qu’une colonne, composé en tête de colonne ; `'hide'` omet un tel tableau ; un tableau plus court passe entier à la colonne suivante dans les deux modes. Une page qu’ouvre un tableau dans le texte ne réserve, parmi les flottants qu’elle reçoit, que la place de sa première partie : une figure sur toute la largeur en attente se place donc en tête de cette page et le tableau continue en dessous. Les tableaux dans le texte sur une page verticale, et les tableaux à l’intérieur d’un encadré, ne sont pas coupés. `splitInline: false` déplace un tableau dans le texte entier à la colonne suivante, comme jusqu’à postext 1.24.

Les mentions de suite ont une valeur par défaut propre à chaque langue de document (`locale`, à défaut la langue de césure) : en anglais `(cont.)` / `Continued`, en espagnol `(cont.)` / `Continúa`, et de même en français, en allemand, en italien, en portugais, en catalan, en néerlandais, en chinois, en japonais et en arabe (listées sous [Langue du document](/fr/docs/configuration-language#langue-du-document)).

Le contenu des cellules est du Markdown en ligne, et un saut de ligne dans une cellule (une fin de ligne dans la source, ou `\\` comme dans les légendes et les notes) commence un nouveau paragraphe. Un paragraphe qui commence par une puce ou un tiret (`•`, `-`, `*`, `–`) ou par un numéro (`1.`, `1)`) suivi d’une espace est composé comme un élément de liste : le marqueur est dessiné tel qu’il est écrit, le texte s’en écarte de l’`unorderedLists.gap` du document, les lignes suivantes s’alignent sur le texte, et deux espaces en tête imbriquent un niveau. Une cellule écrite `• Ofrece elección\n• Acomoda a personas diestras y zurdas` donne ainsi une liste de deux éléments. Une ligne faite seulement d’espaces ordinaires n’ajoute rien ; une ligne qui contient une espace insécable (U+00A0) est une ligne de la cellule, comme en CommonMark : `1\n` suivi d’une espace insécable donne une ligne de tableau haute de deux lignes de texte. Une espace insécable à la fin du texte d’une cellule garde sa largeur : `760` suivi d’une espace insécable, aligné à droite au-dessus de `(231)`, s’arrête une espace avant le bord, ce qui rapproche le 0 du 1. Les chiffres ne s’alignent exactement que là où l’espace est aussi large que la parenthèse, et dans la plupart des polices elle est plus étroite. (Jusqu’à postext 1.4, les deux étaient supprimées.)

Les largeurs de colonne appartiennent au modèle du tableau, pas au style : `TableModel.columnWidths` est une liste facultative de poids relatifs, un par colonne, normalisés au moment de la mise en page ; `[2, 1, 1]` donne à la première colonne la moitié de la largeur. Une liste absente, de mauvaise longueur, ou contenant un poids nul ou négatif se rabat sur un partage égal. L’éditeur de tableaux garde la liste en accord avec les colonnes quand on en ajoute ou en retire.

### Construire des modèles de tableau

Un `TableModel` est une grille rangée ligne par ligne, et chaque cellule est disposée selon sa place dans cette grille : `rows[r][c]` occupe la colonne `c`. Une cellule fusionnée garde donc dans la grille les cellules qu’elle couvre, chacune marquée `hiddenBy` avec sa cellule principale, contrairement à un tableau HTML, qui les omet. Les fonctions de modèle exportées par `postext` conservent cette forme ; ce sont des fonctions pures qui renvoient un nouveau modèle : `mergeCells(model, { start, end })` et `unmergeCell(model, at)`, `addRow`, `addColumn`, `removeRow`, `removeColumn`, `setCellContent`, `setCellImage`, `setCellBackground` et `setAlignment`. Les quatre fonctions de lignes et de colonnes gardent les fusions entières : une ligne ou une colonne ajoutée à l’intérieur d’un bloc fusionné l’élargit, une ajoutée avant lui le déplace, une retirée de lui le rétrécit (un bloc qui perd sa première ligne ou sa première colonne garde son contenu dans sa nouvelle cellule en haut à gauche), et chaque `hiddenBy` continue de désigner sa cellule principale.

`parseTSV(text, options?)` construit un modèle à partir de texte séparé par des tabulations, comme une plage collée depuis un tableur : les lignes se séparent aux sauts de ligne, les cellules aux tabulations, et les lignes trop courtes sont complétées pour que la grille soit rectangulaire. `headerRows` fait des premières lignes des lignes d’en-tête : leurs cellules reçoivent `isHeader` et le modèle `headerRowCount` : un tableau coupé sur plusieurs pages les répète donc.

```ts
import { parseTSV, mergeCells } from 'postext';

let model = parseTSV('Part\tQty\tNote\nBolt\t4\tM6\nNut\t8\t', { headerRows: 1 });
// model.headerRowCount === 1; model.rows[0][0] is { content: 'Part', isHeader: true }
model = mergeCells(model, { start: { row: 2, col: 1 }, end: { row: 2, col: 2 } });
// rows[2][1] gets colSpan: 2; rows[2][2] stays in the grid with hiddenBy: { row: 2, col: 1 }
```

`tableGridIssues(model)` vérifie la grille. Elle renvoie une liste vide pour un modèle sain, et sinon chaque endroit où la grille se rompt, dans l’ordre des lignes : `spanOverlap`, une cellule visible sous le `colSpan` / `rowSpan` d’une autre cellule (`coveredBy` désigne cette cellule), ce que produit une cellule couverte omise à la manière de HTML, puisque toutes les cellules suivantes se décalent sur la fusion ; et `missingCells`, une ligne qui s’arrête avant la dernière colonne sans fusion qui couvre le reste, ce qui laisse un trou.

```ts
import { tableGridIssues } from 'postext';

tableGridIssues({
  rows: [
    [{ content: 'A', colSpan: 2 }, { content: 'C' }],
    [{ content: '1' }, { content: '2' }, { content: '3' }],
  ],
});
// => [{ kind: 'spanOverlap', row: 0, col: 1, coveredBy: { row: 0, col: 0 } },
//     { kind: 'missingCells', row: 0, col: 2 }]
```

Un tableau utilisé par le document dont la grille présente de tels problèmes est signalé dans `doc.contentWarnings` sous le nom `raggedTableGrid` (voir [Avertissements dans le document](/fr/docs/configuration-programmatic-usage#avertissements-dans-le-document)).


## Style de légende

La propriété `captionStyle` règle les légendes des ressources (la ligne `Figure 1 — …` sous les images, les SVG et les tableaux, ou au-dessus). Le libellé numéroté et la description partagent le même caractère et le même corps (une contrainte du moteur), mais le libellé peut avoir sa propre graisse, son italique et sa couleur. La famille, le corps et la couleur héritent du texte courant s’ils ne sont pas définis. La légende peut se placer **au-dessus** de la ressource (la convention habituelle pour les tableaux) et être composée sur une **barre** de couleur qui couvre la largeur du bloc ; une **note** facultative plus petite (ligne de source, crédits : `Resource.note`) se règle avec le sous-objet `note`. Un type de ressource peut surcharger n’importe lequel de ces champs pour ses propres ressources avec `ResourceType.captionStyle` (voir [Types de ressources](#types-de-ressources)).

## Style des diagrammes

### Fonctionnement de l’encre unique

Quand `singleInk` est activé, chaque couleur du balisage SVG est réécrite en une teinte d’`inkColor` dont l’intensité vaut **1 − luminance relative** (coefficients Rec. 709 appliqués aux canaux encodés en gamma : une approximation perceptive largement suffisante pour convertir en teintes). La conversion préserve la valeur perçue : le blanc devient le blanc du papier, le noir l’encre pleine, et les fonds clairs restent clairs quelle que soit leur teinte d’origine. Un fond jaune pâle devient une teinte pâle de l’encre ; un trait foncé s’approche de l’encre pleine.

La recoloration est faite par la fonction exportée `applySingleInkToSvg(svgText, inkHex)`, qui travaille sans DOM sur le balisage SVG, en tant que texte :

- Les littéraux hexadécimaux `#rgb` / `#rgba` / `#rrggbb` / `#rrggbbaa`, les fonctions `rgb()` / `rgba()` et les fonctions `hsl()` / `hsla()` sont réécrits partout où ils apparaissent : attributs de présentation, `style` en ligne, dégradés, `<defs>`. Les fonctions peuvent utiliser des canaux entiers, décimaux ou en pourcentage, et la syntaxe à virgules ou à espaces : `rgb(11.37%, 20%, 50.59%)` (tel que l’écrit Cairo) et `rgb(51 102 153 / 50%)` sont donc recolorés aussi. Une fonction teintée est réécrite en `rgb(…)` ou en `rgba(…)`.
- Les mots-clés `white` et `black` ne sont remplacés que là où ils sont des valeurs de peinture (`fill`, `stroke`, `stop-color`, `flood-color`, `color`, en attributs ou en propriétés de style en ligne), jamais dans le contenu textuel ou les libellés.
- `none`, `transparent` et `currentColor` restent intacts, tout comme les autres couleurs nommées (`red`, `steelblue`…) et le noir par défaut d’une forme ou d’un texte qui ne définit aucun remplissage. Donnez à ces éléments une couleur explicite pour qu’ils soient recolorés.
- Les canaux alpha sont conservés (les quartets de `#rgba` / `#rrggbbaa` et la composante alpha de `rgba(…)` passent tels quels ; un alpha en pourcentage est écrit comme un nombre).
- Quand `inkHex` ne peut pas être analysé, l’entrée est renvoyée inchangée.
- Le résultat porte `data-postext-single-ink="#…"` (l’encre) sur sa racine `<svg>`, et un balisage qui le porte déjà est renvoyé tel quel, quelle que soit l’encre qu’il indique. La conversion n’est pas idempotente (une seconde passe éclaircit chaque couleur, le noir ressortant à environ deux tiers de l’encre) : une image n’est donc recolorée qu’une fois, par votre code ou par le moteur de rendu, selon celui qui la traite en premier. (Cette marque est nouvelle dans postext 1.5 ; un balisage recoloré par la 1.4 n’en a pas.)

```ts
import { applySingleInkToSvg } from 'postext';

const recoloured = applySingleInkToSvg(svgText, '#295AA3');
applySingleInkToSvg(recoloured, '#295AA3') === recoloured; // true: never twice
```

L’encre unique s’applique dans les trois moteurs de rendu : le moteur PDF recolore les octets SVG que lui transmet `resourceBytes` avant de les dessiner en vectoriel, et les moteurs canvas et HTML teintent les images SVG qu’ils peignent quand vous le leur demandez (voir [Encre unique sur le canvas et en HTML](#encre-unique-sur-le-canvas-et-en-html)) : le PDF exporté correspond ainsi à l’aperçu à l’écran.

Le résolveur et la fonction de nettoyage suivent le modèle des autres sections, avec les types `DiagramStyleConfig` / `ResolvedDiagramStyleConfig` :

```ts
import {
  DEFAULT_DIAGRAM_STYLE_CONFIG,
  resolveDiagramStyleConfig,
  stripDiagramStyleDefaults,
  applySingleInkToSvg,
} from 'postext';
import type { DiagramStyleConfig, ResolvedDiagramStyleConfig } from 'postext';

const resolved = resolveDiagramStyleConfig(config.diagramStyle);
// => { singleInk: false, inkColor: { hex: '#295AA3', model: 'hex', paletteId: 'main-color' }, inlineFonts: true }

const minimal  = stripDiagramStyleDefaults(config.diagramStyle);
// => undefined when everything matches the defaults
```

### Encre unique sur le canvas et en HTML

Les moteurs canvas et HTML reçoivent les images déjà décodées (`registerResourceImage`) ou sous forme d’URL (`resourceImageUrl`), et non le balisage SVG. Sur demande, ils appliquent la même conversion à ce qu’ils dessinent :

- **Canvas** (`renderPage`, `renderPageToCanvas`, `renderToCanvas`). Chaque image SVG concernée par la teinte (une figure, l’image d’une cellule de tableau, une image de maquette, une icône ou un marqueur d’encadré) est tramée à sa taille de placement et ses pixels sont teintés à l’encre, qu’elle ait été enregistrée comme `<img>` ou comme `ImageBitmap`. Le bitmap teinté est mis en cache comme toute trame vectorielle. Une image bitmap n’est jamais teintée.
- **HTML** (`renderToHtml`, `renderToHtmlIndexed`). Chaque `<img>` SVG reçoit `filter: url(#pt-ink-…)`, qui pointe vers un `feColorMatrix` contenu dans sa page : un `<svg>` de taille nulle contenant le `<filter>`, placé en premier dans la page, et inclus dans le `decorationHtml` de la page dans la sortie indexée. Chaque page le contient tant que l’encre unique s’applique, qu’elle contienne une image ou non : un hôte qui remplace les blocs un par un n’introduit jamais une image dont le filtre manque.

**Jamais teinté deux fois.** Jusqu’à postext 1.4, les moteurs canvas et HTML dessinaient les images telles quelles : les hôtes recoloraient donc eux-mêmes le balisage avec `applySingleInkToSvg` avant de le transmettre. Les adaptateurs de paquet et le Sandbox le font encore, parce que la passe sur le balisage donne exactement les couleurs du PDF (voir le dernier paragraphe plus bas). Une image n’est donc teintée qu’une fois, selon trois règles valables dans les trois moteurs de rendu :

- **Un balisage marqué n’est pas retouché.** Le moteur PDF recolore `resourceBytes` avec `applySingleInkToSvg` : des octets SVG déjà recolorés sont donc dessinés tels quels. Sur le canvas et en HTML, une image chargée depuis une URI de données SVG dont le balisage porte la marque n’est jamais teintée non plus.
- **Désactivé sauf demande, dans postext 1.x.** Le canvas teinte une image SVG enregistrée sans indicateur propre seulement quand le rendu passe `singleInk: true` (`RenderPageOptions`), et une image enregistrée avec `registerResourceImage(id, img, { singleInk: true })` dans tout rendu. Le moteur HTML teinte quand `renderToHtml` reçoit `singleInk: true`, ou quand son résolveur `resourceImageUrl` indique `singleInk: true`. Un hôte écrit pour la 1.4, qui recolore le balisage et enregistre l’image décodée sans indicateur, garde sa sortie. La prochaine version majeure teintera par défaut.
- **`singleInk: false` n’est jamais teinté.** Derrière une URL blob ou réseau, le balisage ne peut pas être relu : une image que vous avez recolorée vous-même et décodée ainsi s’enregistre donc avec `singleInk: false`, comme le font `registerBundleImages` et le Sandbox. `bundleImageUrl(bundle)` renvoie un résolveur qui indique `singleInk: false`, et `bundleResourceBytes` transmet au PDF les octets propres du paquet, que le moteur PDF recolore une fois.

Les deux moteurs connaissent le genre de chaque image grâce au VDT : une figure et une image de cellule portent le genre de leur ressource, et un bloc d’image de maquette porte `imageKind` (`'svg'` ou `'bitmap'`), tiré de sa ressource lors de la mise en page. Pour un VDT construit avant l’existence d’`imageKind`, le canvas traite comme un SVG une image de maquette enregistrée comme source vectorielle, et le moteur HTML une image dont l’URL est une URI de données SVG ou se termine par `.svg`.

Recolorez le balisage vous-même ou laissez les moteurs teinter l’image brute, mais pas les deux :

```ts
import { applySingleInkToSvg, registerResourceImage, renderPage, renderToHtml } from 'postext';

// Raw SVG: tinted while diagramStyle.singleInk is on…
registerResourceImage('diagram.svg', rawImg, { singleInk: true });
// …or register it plainly and ask on each render.
registerResourceImage('diagram.svg', rawImg);
const canvas = renderPage(doc.pages[0], doc, { singleInk: true });

// Recoloured before decoding (as postext 1.4 hosts do): painted as given.
const inked = applySingleInkToSvg(svgText, ink);
registerResourceImage('diagram.svg', await decode(inked), { singleInk: false });

// The HTML backend with URLs to the raw markup.
const html = renderToHtml(doc, { resourceImageUrl: urlFor, singleInk: true });
```

`renderToHtml` tire la valeur par défaut de son option `singleInk` de l’indicateur propre au résolveur : `bundleImageUrl(bundle)` n’a donc besoin d’aucune option.

Pour chaque couleur que réécrit la passe sur le balisage (valeurs hexadécimales, `rgb()` et `hsl()`, `white` et `black` ; voir [Fonctionnement de l’encre unique](#fonctionnement-de-lencre-unique)), la conversion des pixels donne le même résultat, bords lissés et dégradés compris. Les deux diffèrent là où la passe sur le balisage laisse une couleur intacte : les couleurs nommées autres que `white` et `black`, `currentColor`, les formes et le texte sans remplissage (dessinés dans le noir par défaut) et les bitmaps incorporés au SVG sont teintés à l’écran mais gardent leur couleur dans le PDF. Donnez à chaque élément d’un diagramme une couleur explicite en hexadécimal, `rgb()` ou `hsl()` pour obtenir une sortie identique. Quand le canvas ne peut pas relire les pixels (une `<img>` d’une autre origine, chargée sans CORS), l’image est dessinée sans teinte.

### Polices du texte SVG

Une image SVG s’affiche à travers une image : une `<img>` sur le canvas, en HTML et en EPUB. Un document image n’a pas accès aux polices web de la page : `<text font-family="IBM Plex Sans">` se rabattrait donc sur une police du système. Depuis postext 1.25, le moteur incorpore dans le balisage les polices que désigne le texte avant que l’image soit décodée ou fournie sous forme d’URL : une règle `@font-face` par fichier de police, ses octets en URI de données, dans un `<style>` placé juste après la balise racine `<svg>`. Le PDF n’a besoin de rien de tout cela : il compose le texte SVG comme du vrai texte dans ses polices incorporées (voir [Octets des ressources et originaux d’impression](/fr/docs/configuration-pdf-output#octets-des-ressources-et-originaux-dimpression)).

Ce que demande le texte se lit dans `font-family`, `font-weight`, `font-style` et `font`, en attributs, dans les attributs `style` et par héritage des groupes englobants ; une règle `<style>` qui cite une famille compte aussi. Les familles génériques (`serif`, `sans-serif`…) et le texte de `<title>` ou de `<desc>` sont exclus, et une famille que le SVG déclare lui-même avec `@font-face` n’est pas retouchée. Un segment de texte parcourt sa liste `font-family` jusqu’à la première famille qui dispose d’une police. La recoloration pour l’encre unique passe en premier, puis les polices.

Les polices viennent d’un **fournisseur** qui respecte le contrat du `PdfFontProvider` de postext-pdf : un seul fournisseur sert donc aux deux. Il est appelé avec la famille, la graisse, le style et les caractères que le SVG compose dans cette police, et répond par un fichier ou plusieurs. Une famille servie en tranches unicode-range (Fontsource, Google Fonts) reçoit les tranches dont ces caractères ont besoin : un SVG aux libellés latins ne reçoit que le fichier `latin`. Le fournisseur par défaut lit le registre de polices du moteur : `loadBundleFonts` y enregistre les polices d’un paquet, et un hôte y enregistre les siennes avec `registerFontBytes(family, weight, style, bytes, { unicodeRange })`, ou `registerFontUrl(…)` pour un fichier téléchargé la première fois qu’un SVG en a besoin. Une famille que rien n’a enregistrée est cherchée dans les règles `@font-face` des feuilles de style lisibles de la page. Une `FontFace` ajoutée à `document.fonts` à partir d’octets ne garde pas ces octets, et le moteur ne peut donc pas les relire : enregistrez aussi ces polices.

```ts
import { registerFontBytes, registerSvgImage, renderPage } from 'postext';

registerFontBytes('IBM Plex Sans', 700, 'normal', plexBoldWoff2);
await registerSvgImage('chart.svg', svgText);   // recoloured, fonts inlined, decoded, registered
const canvas = renderPage(doc.pages[0], doc);
```

Où cela se passe :

- **Canvas.** `registerSvgImage(fileId, svgText, options)` recolore (`inkHex`), intègre les polices (`fonts`, un fournisseur ; `inlineFonts: false` saute cette étape), décode et enregistre l’image comme source vectorielle, puis se résout avec le sort de chaque police. `registerBundleImages(bundle)` fait de même pour les SVG d’un paquet, en partant des polices du paquet lui-même. `prepareSvgMarkup(svgText, options)` renvoie le balisage préparé, pour un hôte qui décode de son côté.
- **HTML.** `bundleImageUrl(bundle)` sert le balisage SVG avec les polices du paquet intégrées. `renderToHtml(doc, { inlineSvgFonts: true })` les intègre dans les URI `data:` SVG que renvoie `resourceImageUrl`, à partir des polices que le registre garde en mémoire (ou `inlineSvgFonts: { fonts, maxBytes, withhold, standIn }`). Une URL d’objet ne peut pas être lue de façon synchrone : un hôte qui sert des URL blob intègre donc les polices avant de les créer.
- **EPUB.** `postext-epub` intègre les polices à partir des `fonts` du livre, puis de `svgFonts.provider`, avant d’écrire un SVG (voir [Livres EPUB](/fr/docs/configuration-html-folio-epub#livres-epub-postext-epub)).
- **PDF.** Le texte SVG est composé comme du vrai texte dans les polices incorporées. Un `<style>` qui ne contient que des règles `@font-face` (des polices qu’un auteur a incorporées) ne fait plus se rabattre la figure sur une image matricielle. Quand une figure se rabat malgré tout (un filtre, un dégradé), son image matricielle est produite avec les polices intégrées depuis le `fontProvider` du PDF.

Les fonctions de plus bas niveau sont exportées aussi : `svgFontRequests(svgText)` liste les familles, la graisse, le style et les caractères de chaque segment ; `inlineSvgFonts(svgText, provider, options)` et `inlineSvgFontsSync(svgText, syncProvider, options)` renvoient le balisage ; `inlineSvgFontsDetailed` y ajoute un rapport sur chaque police (`inlined`, `declared`, `unavailable`, `withheld`, `tooLarge`) ; une police intégrée depuis une famille de substitution nomme cette famille dans `standIn`.

Un EPUB ne garde que les attributs que connaît son schéma : un fichier se lit avec <code>controls</code>, <code>autoplay</code>, <code>muted</code>, <code>loop</code>, <code>playsinline</code> et <code>preload</code>, plus l’attribut <code>data-pt-alongside</code>, et le système de lecture décide du reste.

Une vidéo non exclusive porte `data-pt-alongside` dans la sortie HTML. `coordinateVideoPlayback(root)` fait respecter cette règle aux lecteurs placés sous `root` (l’élément qui contient la sortie de `renderToHtml`) : lancer une vidéo exclusive met en pause toutes les autres en cours de lecture, et lancer une vidéo qui joue en même temps que les autres ne met en pause que les exclusives. La fonction renvoie une fonction qui arrête l’écoute. `playsAlongside(el)` et `videosToPause(started, videos, alongside)` donnent la même règle à un hôte qui a ses propres lecteurs. Dans [Folio](/fr/docs/document-format-resources#les-vidéos-sur-les-pages-de-folio), une vidéo qui démarre d’elle-même et joue en même temps que les autres (`autoplay` avec `exclusive: false`) démarre, en sourdine, chaque fois que sa page apparaît, et s’arrête quand la page est tournée, plusieurs à la fois, et `loop` la reprend depuis le début. Une page ou un chapitre EPUB qui contient des vidéos à coordonner (deux ou plus, dont une exclusive) applique la même règle grâce à un petit script, `scripts/videos.js` (l’export `VIDEO_PLAYBACK_SCRIPT`), et le paquet déclare ce document `scripted`. Un système de lecture qui exécute les scripts fait respecter la règle aux vidéos de ce document, mais pas à celles d’une page en regard, qui est un autre document ; un système qui n’exécute pas les scripts lit chaque vidéo indépendamment, comme le font toujours les lecteurs YouTube et Vimeo.

Le résolveur et la fonction de nettoyage suivent le modèle des autres sections, avec les types `VideoStyleConfig` / `ResolvedVideoStyleConfig` :

```ts
import {
  DEFAULT_VIDEO_STYLE_CONFIG,
  DEFAULT_VIDEO_PLAYER_OPTIONS,
  resolveVideoStyleConfig,
  resolveVideoPlayerOptions,
  stripVideoStyleDefaults,
} from 'postext';

const resolved = resolveVideoStyleConfig(config.videoStyle);
const player = resolveVideoPlayerOptions(resource.video?.player, resolved.player);
const minimal = stripVideoStyleDefaults(config.videoStyle); // undefined when all defaults
```
