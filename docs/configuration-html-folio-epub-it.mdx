# Uso programmatico: HTML, Folio, EPUB e SCORM


## Integrare il visualizzatore HTML

Il visualizzatore HTML è il renderer di Postext pensato prima di tutto per lo schermo. Invece di rasterizzare le pagine in una bitmap emette nodi DOM posizionati in modo assoluto, la cui geometria è determinata dalla stessa pipeline che produce l’output di stampa. Per questo è la scelta giusta quando vuoi in un browser una tipografia leggibile, selezionabile e sensibile al ridimensionamento (un’app di lettura, un’anteprima dentro un prodotto o una superficie di documentazione incorporata) senza dover includere un visualizzatore PDF.

I pezzi principali dell’API pubblica:

- **`buildDocument(content, config, cache?)`**: esegue l’intera pipeline di impaginazione e restituisce un `VDTDocument`.
- **`renderToHtmlIndexed(doc, options)`**: trasforma il VDT in un’unica stringa HTML più una scomposizione per pagina e per blocco. La scomposizione permette di aggiornare il DOM a basso costo quando tra due rendering cambiano solo pochi blocchi.
- **`resolveHtmlViewerConfig(partial)`**: completa i valori predefiniti del visualizzatore HTML (`maxCharsPerLine`, `columnGap`, `optimalLineBreaking`).
- **`buildFontString` + `measureGlyphWidth` + `dimensionToPx`**: primitive di misurazione usate per ricavare una larghezza di colonna reale in pixel da un numero di caratteri desiderato.
- **`createMeasurementCache` / `clearMeasurementCache`**: cache intercambiabili che ti permettono di riutilizzare le misure tra un’impaginazione e l’altra.
- **`prepareFonts` / `buildDocumentWithFonts` / `watchFonts` / `onFontsChanged`**: caricano i caratteri del documento prima dell’impaginazione e impaginano di nuovo quando i caratteri arrivano (vedi [Caricare i font prima dell’impaginazione](/it/docs/configuration-programmatic-usage#caricare-i-font-prima-dellimpaginazione)).

### Esempio dal vivo: una stringa HTML

L’intero percorso in JavaScript semplice, prima dell’integrazione con React più sotto: costruisci il documento, passa il `VDTDocument` a `renderToHtml` e inserisci la stringa in un contenitore. `mode: 'single'` impila le pagine in verticale; `background` dà loro un colore, perché per impostazione predefinita le pagine sono trasparenti. Il pen stampa anche il markup generato, così puoi vedere le righe posizionate in modo assoluto che il renderer emette: il browser le disegna ma non le reimpagina mai.

### Integrazione minima

Il frammento qui sotto è l’integrazione utile più breve: costruisce il documento alla dimensione attuale della finestra, lo inserisce in un contenitore e ripete il tutto a ogni ridimensionamento.

```tsx
import { useEffect, useRef } from 'react';
import {
  buildDocument,
  renderToHtmlIndexed,
  resolveHtmlViewerConfig,
  buildFontString,
  measureGlyphWidth,
  dimensionToPx,
  createMeasurementCache,
  watchFonts,
  onFontsChanged,
} from 'postext';
import type { PostextConfig, MeasurementCache } from 'postext';

// Screen-friendly DPI: at 144 DPI, an 8pt body size resolves to 16 px.
const HTML_DPI = 144;
const PADDING_PX = 24;

// Prose sample used to measure the target column width. Proportional fonts
// make "N × average width" unreliable, so we measure a representative string.
const SAMPLE =
  'The quick brown fox jumps over the lazy dog. Sphinx of black quartz, judge my vow.';

function sampleForChars(n: number): string {
  let s = SAMPLE;
  while (s.length < n) s += ' ' + SAMPLE;
  return s.slice(0, n);
}

export function PostextHtmlViewer({
  markdown,
  config,
  mode = 'multi',
}: {
  markdown: string;
  config: PostextConfig;
  mode?: 'single' | 'multi';
}) {
  const hostRef = useRef<HTMLDivElement | null>(null);
  const cacheRef = useRef<MeasurementCache>(createMeasurementCache());

  useEffect(() => {
    const host = hostRef.current;
    if (!host) return;

    const relayout = () => {
      const rect = host.getBoundingClientRect();
      if (rect.width === 0 || rect.height === 0) return;

      const viewer = resolveHtmlViewerConfig(config.htmlViewer);
      const fontFamily = config.bodyText?.fontFamily ?? 'EB Garamond';
      const fontWeight = config.bodyText?.fontWeight ?? 400;
      const fontSize = config.bodyText?.fontSize ?? { value: 8, unit: 'pt' as const };
      const fontSizePx = dimensionToPx(fontSize, HTML_DPI);

      // Measure the *actual* column width for N characters of body prose.
      const targetColumnPx = measureGlyphWidth(
        sampleForChars(viewer.maxCharsPerLine),
        buildFontString(fontFamily, fontSizePx, String(fontWeight), 'normal'),
      );

      const inner = Math.max(rect.width - PADDING_PX * 2, 100);
      let columnWidthPx: number;
      if (mode === 'single') {
        columnWidthPx = Math.min(targetColumnPx, inner);
      } else {
        // Fit as many columns as we can at the target width.
        const count = Math.max(
          1,
          Math.floor((inner + viewer.columnGap) / (targetColumnPx + viewer.columnGap)),
        );
        columnWidthPx = (inner - viewer.columnGap * (count - 1)) / count;
      }
      columnWidthPx = Math.max(Math.floor(columnWidthPx), 80);

      // Single mode uses one very tall page; multi mode uses the viewport
      // height so each VDT "page" becomes one column.
      const pageHeightPx =
        mode === 'single' ? Math.max(rect.height * 20, 200_000) : Math.max(rect.height - PADDING_PX * 2, 400);

      const override: PostextConfig = {
        ...config,
        page: {
          ...config.page,
          dpi: HTML_DPI,
          width: { value: columnWidthPx, unit: 'px' },
          height: { value: pageHeightPx, unit: 'px' },
          margins: {
            top: { value: 0, unit: 'px' },
            bottom: { value: 0, unit: 'px' },
            left: { value: 0, unit: 'px' },
            right: { value: 0, unit: 'px' },
          },
        },
        layout: { ...config.layout, layoutType: 'single' },
        bodyText: {
          ...config.bodyText,
          optimalLineBreaking: viewer.optimalLineBreaking,
        },
      };

      const doc = buildDocument({ markdown }, override, cacheRef.current);
      const { html } = renderToHtmlIndexed(doc, {
        mode,
        columnGap: viewer.columnGap,
        padding: PADDING_PX,
        background: 'transparent',
      });

      host.innerHTML = html;
    };

    relayout();

    const ro = new ResizeObserver(() => relayout());
    ro.observe(host);

    // Re-measure when web fonts land so glyph widths aren't taken from fallbacks.
    const stopWatching = watchFonts();
    const off = onFontsChanged(() => relayout());

    return () => {
      ro.disconnect();
      off();
      stopWatching();
    };
  }, [markdown, config, mode]);

  return <div ref={hostRef} style={{ width: '100%', height: '100%', overflow: 'auto' }} />;
}
```

Qualche nota su che cosa fa questo esempio:

- **Misurare la colonna, non stimarla.** Poiché `maxCharsPerLine` è un *obiettivo* espresso in caratteri, la larghezza reale in pixel dipende dal font del testo corrente. `measureGlyphWidth` fornisce una misura reale con il font scelto, il che mantiene coerente la giustezza quando cambi font.
- **Riscrivere la pagina.** Il visualizzatore HTML tratta ogni «pagina» del VDT come una colonna sullo schermo. L’esempio sostituisce `page.width` con la larghezza di colonna misurata, azzera i margini (il padding sta fuori dalla pagina, nel div `.pt-doc` che la avvolge) e usa `HTML_DPI = 144` perché un testo corrente di `8pt` diventi `16px`.
- **Attenzione al caricamento dei font.** `watchFonts` ascolta `document.fonts` e, una volta per frame, scarta ciò che era stato misurato nelle famiglie i cui caratteri sono arrivati; `onFontsChanged` impagina poi di nuovo la colonna. Senza la nuova impaginazione, il primo rendering usa le metriche di un font di ripiego e il testo salta quando arriva il font vero.
- **Riutilizzare la cache delle misure.** Creare la cache una volta per componente significa che i ridimensionamenti e i cambi di scala del font riutilizzano le misure del rendering precedente invece di rimisurare ogni paragrafo.

### Andare oltre

L’esempio qui sopra è volutamente essenziale. Le integrazioni in produzione di solito aggiungono:

- **Isolamento con Shadow DOM**: esegui il rendering dentro `host.attachShadow({ mode: 'open' })` così che niente della pagina esterna possa far trapelare CSS nel visualizzatore.
- **Aggiornamento incrementale**: `renderToHtmlIndexed` restituisce `pages[i].blocks`, ognuno con un `id` stabile e l’HTML esterno del blocco. Quando tra due rendering differiscono solo pochi blocchi puoi sostituire sul posto quei contenitori di blocco invece di ricostruire `innerHTML`.
- **Sovrapposizioni**: un SVG posizionato in modo assoluto sopra ogni `.pt-page` per cursori, selezioni o griglie della linea di base.
- **Link**: le parole di un link Markdown sono avvolte in `<a href="…" rel="noopener noreferrer">`, che prende il colore del testo e non ha sottolineatura; vedi [Formato del documento › Link](/it/docs/document-format-inline#link). In un visualizzatore simile a un editor, intercetta i clic sugli `a[href]` che non cominciano con `#` e aprili in una nuova scheda (le ancore di `:ref` puntano dentro il documento).
- **Esercizi da risolvere**: l’HTML di un documento con blocchi `:::exercise` contiene i loro dati in uno `<script type="application/json" class="pt-exercises">`, ma nessun codice per rispondere: i controlli li aggiunge la pagina che lo mostra. Quando il markup è al suo posto, chiama `attachExercises(root, options?)` da `postext` sull’elemento (o sulla shadow root) che lo contiene, e chiama la funzione che restituisce prima di sostituire il markup. `attachExercises` dispone sulle pagine i campi, le opzioni da selezionare e la barra con «Verifica», «Mostra la soluzione» e «Ricomincia», e aggiunge un proprio foglio di stile. `storageKey` indica il libro e il capitolo sotto cui si conservano le risposte, `store` le tiene altrove invece che in `localStorage` (qualsiasi oggetto con `getItem`, `setItem` e `removeItem`), e `onResult(result)` riceve ogni verifica, ogni nuovo tentativo e ogni soluzione mostrata, con il punteggio (`right` su `total`) e ogni risposta valutata. Un host che sostituisce i blocchi uno per uno a partire da `renderToHtmlIndexed` passa gli `exercises` dell’indice come `data`. `EXERCISE_SCRIPT` è lo stesso codice come script autonomo, per un file HTML senza una pagina host che lo chiami. Vedi [Esercizi in HTML ed EPUB](/it/docs/exercises#esercizi-in-html-ed-epub).
- **Immagini a un solo inchiostro**: con `diagramStyle.singleInk` attivo, gli `<img>` SVG ricevono un filtro CSS, a meno che tu non passi `singleInk: false` per URL già ricolorati; vedi [Un solo inchiostro su canvas e in HTML](/it/docs/configuration-resources#inchiostro-unico-sul-canvas-e-in-html).
- **Pagine composte e di fumetto su un foglio di stampa**: su una pagina larga quanto lo schermo e alta quanto lo scorrimento, una cornice ancorata al piede di una pagina composta (`::::page{template}`) finirebbe al piede dello scorrimento. Passa `composedViewerLeaf: { width, height, margins? }` (formato e margini della pagina stampata) nella configurazione che impagini: ogni pagina composta viene impaginata su una pagina di quel formato, con la sua geometria di stampa, e tu la scali allo schermo (da postext 1.47); `comics.viewerLeaf` fa lo stesso con le pagine di fumetto, scalate a `fitWidth` px (vedi [Fumetti](/it/docs/configuration-comics)). Entrambe sono per gli host: le imposta il visualizzatore HTML del Sandbox e non vengono mai salvate con un documento.

Il componente `HtmlPreview` della Sandbox (`packages/postext-sandbox/src/viewport/html/HtmlPreview/index.tsx`) implementa tutto questo sopra la stessa API mostrata qui e può servire da riferimento. Inoltre fa passare ogni build da un worker di impaginazione condiviso (vedi [Eseguire l’impaginazione in un Web Worker](/it/docs/configuration-programmatic-usage#eseguire-limpaginazione-in-un-web-worker)), così le modifiche dal vivo e i ridimensionamenti non bloccano mai il thread principale: sostituisci la chiamata diretta `buildDocument(...)` del frammento qui sopra con `layoutWorker.build(...)` quando sei pronto a spostare l’impaginazione fuori dal thread principale.

La pagina trasparente conta su un sito scuro: un’anteprima senza `background` mostra testo nero sullo sfondo scuro del sito. Passa `renderToHtml(doc, { background: '#ffffff' })`, oppure dai al documento un `page.backgroundColor`.

**Gli stili di testo della pagina ospite restano fuori.** Ogni riga è composta alle larghezze misurate dal motore, quindi un `letter-spacing`, `word-spacing`, `text-transform` o `font-variant` che l’output ereditasse dalla pagina circostante allargherebbe le sequenze di glifi e farebbe sovrapporre le righe. Per questo la radice `.pt-doc` reimposta le proprietà di testo ereditate (spaziatura tra lettere e tra parole, maiuscole e minuscole, rientro, spazi bianchi, stile, variante, peso ed estensione del font, funzioni OpenType e crenatura, interlinea, allineamento, ombra ed enfasi del testo, sillabazione, direzione, modo di scrittura, contorno e riempimento del testo, e l’ingrandimento automatico del testo su mobile) prima delle proprie dichiarazioni di impaginazione, così l’output appare uguale dentro una shadow root o sotto un elemento con stili propri. L’elenco è esportato come `HTML_TEXT_RESET`, una stringa di dichiarazioni CSS: un’applicazione ospite che monta l’`innerHtml` delle pagine (da `renderToHtmlIndexed`) in contenitori propri la imposta sulla loro radice. Fino a postext 1.4 la radice non reimpostava nulla; la soluzione era un contenitore con `all: initial`.


## Un libro in 3D (`postext-folio`)

`postext-folio` presenta sullo schermo un documento impaginato come un libro stampato aperto su una scrivania: doppie pagine secondo la regola del recto, e fogli che chi legge gira con i pulsanti ‹ ›, i tasti freccia, uno swipe, un clic su una pagina, oppure prendendo una pagina per il bordo e trascinandola. Ogni foglio si incurva in three.js secondo la sua carta e proietta un’ombra vera sulle pagine sottostanti. Il canvas WebGL disegna il libro allo stesso modo sia fermo sia mentre si gira, quindi una pagina non cambia mai aspetto quando si posa. È il visualizzatore delle ricette del Ricettario e della scheda **Folio** della Sandbox.

```bash
npm install postext postext-folio three
```

```ts
import { buildDocument } from 'postext';
import { createFolioFromDocument } from 'postext-folio';

const doc = buildDocument({ markdown }, config);
const book = createFolioFromDocument(document.getElementById('book')!, doc, {
  onChange: ({ pages }) => console.log('showing pages', pages),
});

// After an edit: the same viewer, on the same page.
book.setDocument(buildDocument({ markdown: edited }, config));
```

- **Le pagine si disegnano quando servono.** `createFolioFromDocument` disegna ogni pagina con `renderPageToCanvas` esattamente ai pixel del dispositivo di uno slot di pagina (WebGL poi la mostra un texel per pixel, nitida come l’anteprima canvas), e solo le doppie pagine attorno a quella aperta (`window`, tre per lato per impostazione predefinita). Le pagine che escono da quella finestra vengono liberate, quindi un libro di mille pagine costa la memoria di poche. Un salto a una pagina lontana disegna per prima quella doppia pagina. Fino a dieci pagine di distanza i fogli si girano uno per uno; oltre, il blocco di pagine intermedie si solleva come un’unica lastra, spessa quanto quelle pagine (la somma dei loro spessori), e si posa dall’altra parte. `setDocument` conserva l’immagine già disegnata di ogni pagina che nella nuova impaginazione risulta uguale (`{ repaint: true }` le ridisegna tutte, dopo l’arrivo di un’immagine).
- **Il documento definisce il libro.** La sua prima pagina si apre da sola a destra quando è un recto (`pageIndexOffset` pari), un libro rilegato a destra (`page.binding: 'right'`, o un documento verticale) si presenta specchiato e si gira verso sinistra, le pagine bianche prendono il colore di sfondo della pagina, e la larghezza del formato rifilato della pagina (`pageWidthMm`) scala lo spessore della carta e i piatti. Un capitolo impaginato con una `continuation` conta le altre pagine del libro (`pageIndexOffset` prima, `bookPageCount` dopo) nello spessore dei due blocchi di pagine senza disegnarle (`extraPages`).
- **Il documento definisce l’aspetto.** La carta, la rilegatura, la scrivania e la luce sono le [impostazioni `folio`](/it/docs/configuration-fonts-colors-viewers#visualizzatore-folio-configurazione) del documento (`doc.config.folio`). Una pagina composta dentro una sequenza `:::paper` porta la propria carta (`VDTPage.paper`), e il suo foglio viene disegnato con il colore, la superficie, lo spessore e la rigidità di quella carta. Con `binding.cover: 'pages'` la prima pagina è il piatto anteriore e l’ultima, quando è un verso, il piatto posteriore (`covers`). Un formato da quotidiano (`'broadsheet'`, `'berliner'`, `'tabloid'`, `'compact'`) le cui impostazioni non indicano né carta né rilegatura si presenta come carta da giornale piegata, anche quando l’applicazione ospite passa un proprio `folio`.
- **Il contenitore definisce la dimensione.** Il libro lo riempie, con i pulsanti e il conteggio delle pagine nei margini, quindi dai un’altezza al contenitore; un ridimensionamento ridisegna le pagine alla nuova dimensione. Sotto i 560 px di larghezza mostra una pagina alla volta (`mode: 'auto'`; `'single'` e `'double'` forzano l’una o l’altra modalità): il dorso corre lungo il bordo interno della pagina e il foglio gli si gira sopra, un trascinamento verso il dorso va avanti, uno swipe in direzione opposta torna indietro, un tocco gira la pagina.
- **Che cosa fa il puntatore.** `interaction` (e poi `setInteraction`) stabilisce che cosa fanno sul libro il tasto sinistro, un dito o una penna: `'hand'` (il valore predefinito) prende e gira le pagine, `'orbit'` ruota la vista come fa un trascinamento con il tasto destro (per trackpad e tablet), `'select'` lascia il puntatore all’applicazione ospite, per esempio per selezionare il testo. `pageAt(event)` restituisce la pagina sotto un puntatore e il punto su di essa (`{ page, x, y }`, frazioni della pagina a partire dal suo angolo in alto a sinistra), sul libro così come lo si vede, inclinato o ruotato; `pointOnScreen(point)` fa il percorso inverso, per disegnare un cursore o una selezione sopra la pagina. `refreshPage(src)` mostra di nuovo un canvas di pagina che l’applicazione ospite ha ridisegnato sul posto. La Sandbox li usa tutti per selezionare il testo e seguire il cursore dell’editor sulle pagine 3D.
- **Una lente d’ingrandimento per i caratteri piccoli.** `interaction: 'magnify'` tiene una lente rotonda con un bordo nero sopra il libro dove si trova il puntatore (un dito la tiene sopra di sé mentre tocca lo schermo). Mostra il libro come lo vede l’occhio di chi legge, illuminato e curvo come giace, ingrandito al massimo al centro e incurvato verso il bordo. La rotellina, `+` e `−` cambiano l’ingrandimento (`setMagnification(zoom)`, da 1,5 a 10; il valore predefinito mostra la pagina a circa 5,5 px CSS per millimetro) ed Esc la ripone; `magnifier: { zoom, diameter }` imposta entrambi fin dall’inizio. `createFolioFromDocument` ridisegna le pagine sotto la lente, abbastanza nitide per il suo centro, così il testo corrente di un quotidiano si legge; `createFolio` prende queste immagini da `detail: { paint(index, deviceWidth), release() }`. La Sandbox la mette sul pulsante **Lente d’ingrandimento** (M). La lente seleziona anche il testo: sopra le pagine il cursore è un cursore di testo, `pageAt` restituisce il punto sotto il centro della lente (sopra il dito su uno schermo tattile), e nella Sandbox un clic lì colloca il cursore e un trascinamento seleziona.
- **Chi legge può guardarci intorno.** Un trascinamento con il tasto destro fa ruotare la vista attorno al libro (fino a 70° dalla verticale), anche mentre i fogli si girano; `resetView()` la riporta dolcemente al `tilt` e allo `yaw` delle impostazioni, e `getView()` restituisce la vista così come la si vede ora (`{ tilt, yaw }`, in gradi) da memorizzare come quelle impostazioni. La Sandbox li mette su due pulsanti, **Reimposta la vista** e **Salva come vista predefinita**.
- **I video si riproducono sulle pagine.** Un clic sul poster di un video lo riproduce sulla pagina, in ogni modalità di `interaction`, e la riproduzione continua mentre il suo foglio si gira; un altro clic lo mette in pausa, e il video si ferma quando il libro si posa su una doppia pagina che non lo mostra. Un video con `player.autoplay` parte da solo la prima volta che viene mostrata la sua doppia pagina; uno che si riproduce anche insieme agli altri (`player.exclusive: false`) parte, senza audio, ogni volta che viene mostrata la sua doppia pagina e si ferma quando la pagina viene girata; più video possono riprodursi insieme. Opzioni `videos`, `videoUrl` e `onVideo`, e `stopVideo()` sul visualizzatore; vedi [Formato del documento › Video sulle pagine di Folio](/it/docs/document-format-resources#video-sulle-pagine-di-folio).
- **Prima i font e le immagini.** Come per `renderPage`, i font che il documento usa devono essere caricati in `document.fonts` e le sue immagini delle risorse registrate con `registerResourceImage` prima che le pagine vengano disegnate.
- **Accessibile.** Il visualizzatore è un gruppo che può ricevere il focus e accetta ←/→ (specchiati per un libro rilegato a destra), Pagina su/giù, Home e Fine; i suoi pulsanti e il conteggio delle pagine hanno un’etichetta (`labels` li traduce), e ogni canvas di pagina porta un testo `alt` (`alt: (index) => …`).
- **Senza WebGL2**, o quando chi legge chiede di ridurre il movimento, le doppie pagine semplicemente cambiano. I libri WebGL sono pesanti per un telefono (una texture per ogni lato di pagina): la Sandbox offre la scheda Folio solo dove WebGL2 è disponibile e il lato corto dello schermo è di almeno 600 px. `canFlip()` dice se qui i fogli si gireranno in 3D: WebGL2, e nessuna riduzione del movimento.

## Libri EPUB (`postext-epub`)

`postext-epub` scrive un libro impaginato come file EPUB 3.3, nel browser o in Node, senza server. Legge gli stessi documenti di capitolo che `renderToPdf` riceve per un libro, quindi numeri di pagina, note, citazioni, rimandi, indice e indice analitico arrivano già risolti, e restituisce il file come byte. È il generatore dietro la scheda **EPUB 3** della Sandbox.

```bash
npm install postext postext-epub
```

`postext` è una dipendenza peer, come per `postext-pdf`: aggiorna i due pacchetti insieme e, su una CDN, fissali alla stessa versione.

### Scrivere un libro

```ts
import { openBundle, buildBundle } from 'postext';
import { renderToEpub } from 'postext-epub';

const bundle = await openBundle(fileBytes);
const docs = buildBundle(bundle); // one VDTDocument per chapter, in book order

const bytes = await renderToEpub(docs, {
  layout: 'reflowable',
  metadata: { title: 'Lantern', creators: ['Ada Lovelace'], language: 'en' },
  fonts: bundle.fonts.map((f) => ({ family: f.family, weight: f.weight, style: f.style, bytes: new Uint8Array(f.bytes), format: f.format })),
  resourceBytes: (fileId) => {
    const data = bundle.files.get(fileId);
    return data ? { bytes: data, mediaType: '' } : undefined;
  },
  onWarning: (w) => console.warn(w),
});
```

Un singolo documento è un libro di un capitolo: `renderToEpub([doc], options)`.

- **`renderToEpub(docs, options): Promise<Uint8Array>`** scrive il file. `options` è `{ layout, metadata, fonts?, svgFonts?, resourceBytes?, cover?, onProgress?, onWarning?, signal?, kindlePanelView? }`.
- **`metadata`**: `title` e `language` (un tag BCP 47) sono obbligatori; `subtitle`, `creators`, `identifier`, `date`, `publisher`, `rights`, `description` e `modified` sono facoltativi. Un ISBN nudo diventa `urn:isbn:…`. Senza un `identifier` il libro riceve un `urn:uuid:` derivato dal titolo, dagli autori e dalla lingua, così una nuova versione dello stesso libro mantiene il suo posto nella biblioteca di chi legge. Passa anche `modified` per ottenere un output identico byte per byte.
- **`fonts`**: i font da incorporare, `{ family, weight, style, bytes, format, unicodeRange? }` con `format` tra `woff2`, `woff`, `ttf`, `otf`. Ogni font diventa un file e una regola `@font-face`; più file con il loro `unicodeRange` formano un unico font (le porzioni di Google Fonts). Una famiglia, un peso o uno stile usati dalle pagine senza un font incorporato vengono segnalati come `missingFont`, e i sistemi di lettura li sostituiscono con i propri. Incorpora solo font la cui licenza lo consente: un font con `redistributable: false` non viene mai scritto nel file (il libro può essere composto con esso, ma il suo file resta fuori, anche dalle immagini SVG). Un’applicazione ospite può fornire invece gli stili della famiglia libera con il nome della famiglia con licenza (sono stili ordinari), ed è ciò che fanno la Sandbox e `postext` per una famiglia che indica un `fallback` (da postext 1.43).
- **`resourceBytes(fileId)`**: le immagini che le pagine collocano, in modo sincrono o asincrono, come `{ bytes, mediaType }`; un `mediaType` vuoto viene ricavato dai byte. Fornisci le bitmap come sono conservate e gli SVG come sorgente, non il master di stampa PDF (`svg.pdfFileId`). Ogni immagine viene conservata una sola volta. In un libro a un solo inchiostro (`diagramStyle.singleInk`) gli SVG vengono ricolorati nel file. Un SVG riceve incorporati i font usati dal suo testo, perché un sistema di lettura lo mostra come un’immagine che non vede i font del libro (vedi [Font nel testo SVG](/it/docs/configuration-resources#font-nel-testo-svg)): da `fonts` (le porzioni che contengono i suoi caratteri), poi da **`svgFonts.provider`** per una famiglia che il testo del libro non usa. Le famiglie di font marcati `redistributable: false`, e quelle indicate da `svgFonts.withhold(family)`, restano fuori e vengono segnalate una volta ciascuna come `fontWithheld`; una famiglia senza font viene segnalata come `svgFontUnavailable`, i font oltre `svgFonts.maxBytes` (2 MiB) come `svgFontsTooLarge`. `svgFonts.inline: false`, `diagramStyle.inlineFonts: false` e il `svg.inlineFonts: false` di una risorsa conservano i byte così come sono forniti. Un’immagine senza byte viene segnalata come `missingImage` e lasciata come cornice vuota. `svgFonts.standIn(family)` (da postext 1.43) indica una famiglia libera da usare al posto di una di esse: a `svgFonts.provider` si chiede lo stile di quella famiglia con lo stesso peso e la stessa inclinazione, che entra nell’immagine con il nome della famiglia esclusa; se il provider non ce l’ha, la famiglia resta fuori e viene segnalata.
- **`cover`**: `{ bytes, mediaType, alt?, showsFirstPage? }`, un’immagine JPEG, PNG, WebP o SVG. Il libro si apre allora su un documento di copertina che la contiene, ed essa diventa il `cover-image` del pacchetto (la miniatura in una biblioteca). Senza copertina, il layout fisso indica la sua prima pagina come copertina e il libro a layout fluido non ha un’immagine di copertina. `showsFirstPage: true` indica che l’immagine è una cattura della prima pagina stampata: il layout fisso la usa allora solo come `cover-image` e si apre su quella pagina, che altrimenti verrebbe mostrata due volte; il libro a layout fluido si apre sul documento di copertina come prima.
- **`kindlePanelView`**: per un layout fisso con pagine a fumetti, aggiunge Kindle Panel View, una zona da toccare su ogni vignetta che la mostra ingrandita, con i metadati che Kindle richiede. Ogni zona contiene una copia del fumetto della sua pagina, quindi ogni pagina cresce di una copia per vignetta; riservalo ai libri destinati a Kindle. Valore predefinito `false`. La navigazione per regioni, che qualsiasi sistema di lettura può usare, viene scritta in ogni caso (vedi [Output dei fumetti](/it/docs/comics#output-dei-fumetti)).
- **`onProgress({ phase, done, total })`**: `resources` (font e immagini), `documents` (pagine per un layout fisso, capitoli per uno fluido), poi `package`. **`signal`** interrompe tra un passo e l’altro.
- **`readEpub(bytes)`** rilegge un file per un visualizzatore, senza `DOMParser`: layout, metadati, direzione di lettura, ogni file per percorso, il manifest, lo spine, l’indice, l’elenco delle pagine, il viewport del layout fisso e la copertina. Il lettore della Sandbox si basa su questa funzione.

Entrambe le rese contengono i metadati di EPUB Accessibility 1.1 (modalità di accesso, funzionalità come l’indice e i numeri delle pagine stampate, rischi e un riepilogo) e per impostazione predefinita non dichiarano alcuna conformità WCAG. L’elenco completo delle opzioni e i limiti si trovano nel [README del pacchetto](https://www.npmjs.com/package/postext-epub).

### Verificare un file con EPUBCheck

[W3C EPUBCheck](https://www.w3.org/publishing/epubcheck/) è il validatore di riferimento per EPUB; i negozi di ebook lo usano per verificare i file che ricevono. Una volta installato (`brew install epubcheck`, oppure la versione Java), `epubcheck book.epub` elenca errori, avvisi e note d’uso; le note d’uso che l’output di Postext genera (`CSS-028`, `OBS-001`, `HTM_062`) sono solo informative. Nel repository di Postext, `pnpm --filter postext-epub epubcheck` verifica i libri di esempio della suite di test, `node packages/postext-epub/scripts/epubcheck.mjs book.postext --layout both` impagina un file `.postext` o una cartella di preset e verifica entrambe le rese, e `pnpm --filter postext-epub validate` esegue l’intera matrice di libri (la guida, i preset della vetrina, i libri cinesi, arabi e del Ricettario), ciascuno dei quali passa senza errori né avvisi.

## Pacchetti SCORM (`postext-scorm`)

`postext-scorm` scrive un libro, o i capitoli e le sezioni scelti, come pacchetto SCORM: lo zip che un sistema di gestione dell’apprendimento (Moodle, Canvas, Blackboard, SCORM Cloud e la maggior parte degli altri) importa come corso. Il contenuto è quello del generatore EPUB, pagine fisse o testo fluido, come pagine HTML5; ogni parte che l’LMS segue si apre in un piccolo player, e gli esercizi che contiene inviano all’LMS il punteggio, il completamento e l’esito (superato o non superato). È il generatore dietro la scheda **SCORM** della Sandbox.

```bash
npm install postext postext-epub postext-scorm
```

`postext` e `postext-epub` sono dipendenze peer: aggiorna i tre pacchetti insieme.

### Scrivere un pacchetto

```ts
import { openBundle, buildBundle } from 'postext';
import { renderToScorm, scormTree, scormOrganization, treeLeaves } from 'postext-scorm';

const bundle = await openBundle(fileBytes);
const docs = buildBundle(bundle);

// The book's spine: chapters and their headings down to the third level.
const tree = scormTree(bundle.chapters.map((c) => ({ markdown: c.markdown, title: c.title })));
// Chapter 1 whole, and two sections of chapter 2.
const picked = new Set([tree[0]!, tree[1]!.children[0]!, tree[1]!.children[2]!].flatMap(treeLeaves).map((n) => n.id));

const zip = await renderToScorm(docs, {
  version: '1.2',
  layout: 'fixed',
  items: scormOrganization(tree, picked),
  metadata: { title: 'Lantern', language: 'en' },
  fonts, resourceBytes, // as for renderToEpub
});
```

- **`renderToScorm(docs, options): Promise<Uint8Array>`** scrive lo zip. `docs` sono i documenti di capitolo che riceve `renderToEpub`. `options` è `{ version, layout, items?, metadata, fonts?, svgFonts?, resourceBytes?, cover?, passingScore?, onProgress?, onWarning?, signal? }`; `metadata`, `fonts`, `svgFonts`, `resourceBytes` e `cover` sono quelli del generatore EPUB.
- **`version`**: `'1.2'` o `'2004'` (SCORM 2004 4ª edizione). Ogni LMS accetta SCORM 1.2. SCORM 2004 tiene distinti completamento e superamento, dà un punteggio in scala e conserva fino a 64.000 caratteri di risposte salvate, dove SCORM 1.2 ne conserva 4.096; sceglilo quando l’LMS lo accetta e queste differenze contano.
- **`layout`**: `'fixed'`, ogni pagina stampata adattata alla finestra, o `'reflowable'`, il testo ricomposto per la finestra, come in [Layout fisso e fluido](#layout-fisso-e-fluido).
- **`items`**: l’organizzazione che l’LMS mostra, un albero di `{ title, doc?, range?, children? }`. Un elemento con `children` li raggruppa; uno senza è uno SCO, una parte che l’LMS avvia, segue e valuta a sé: il capitolo `doc` intero, o il suo `range` (`{ start, end? }`, posizioni nel Markdown del capitolo così come è scritto, front matter compreso). Senza `items`, ogni capitolo è uno SCO.
- **`scormTree(chapters, config?)`** elenca i capitoli e i loro titoli dei livelli da 1 a 3, ciascuno con l’intervallo che rappresenta: dalla sua riga al titolo successivo del suo livello o di uno superiore. Il primo titolo sotto un capitolo o un titolo prende anche il testo che lo precede, così il titolo e i paragrafi di apertura di un capitolo vanno con la sua prima sezione. **`scormOrganization(tree, picked)`** trasforma un insieme di id di foglie scelte in `items`: un nodo scelto per intero è uno SCO, un nodo scelto in parte raggruppa gli elementi dei suoi figli. `treeLeaves(node)` e `pickState(node, picked)` (`'all'`, `'some'`, `'none'`) aiutano a costruire un albero con caselle di controllo.
- **`passingScore`**: la percentuale di risposte valutate giuste che basta per superare, al di sopra del `exercises.digital.passingScore` dei documenti. `0` o assente: nessun esito.

Uno SCO a layout fisso contiene ogni pagina stampata che la sua parte tocca, così una pagina condivisa da due parti compare in entrambe. Uno SCO a layout fluido contiene esattamente il testo della sua parte, tagliato ai suoi titoli. I link dalle pagine di uno SCO a quelle di un altro vengono tolti, perché un LMS segue uno SCO in base a ciò che apre. Il player mostra un documento alla volta, con ← e → (o Pag su e Pag giù sulle pagine fisse), l’indice dello SCO e la posizione; un libro rilegato a destra gira le pagine verso sinistra.

### Che cosa arriva all’LMS

Il player trova l’API dell’LMS come chiede SCORM (`API` per SCORM 1.2, `API_1484_11` per SCORM 2004, risalendo la catena delle finestre madri, poi nella finestra che l’ha aperto) e comunica:

- **Punteggio.** Un esercizio conta la sua ultima verifica: le risposte valutate giuste sul totale delle risposte valutate, il punteggio che mostra la sua barra. Il punteggio di uno SCO è la somma delle risposte giuste divisa per la somma delle risposte valutate dei suoi esercizi, così un cruciverba di venti caselle pesa più di un vero o falso; un esercizio mai verificato non conta nessuna risposta giusta. SCORM 1.2 lo riceve come percentuale (`cmi.core.score.raw`, da 0 a 100); SCORM 2004 come frazione (`cmi.score.scaled`) con le risposte come `raw` e `max`. Un esercizio appartiene alla parte in cui si trova il suo blocco: solo quello SCO lo conta, anche dove la sua pagina compare pure in uno SCO vicino.
- **Completamento.** Uno SCO è completato quando tutte le sue pagine o i suoi documenti sono stati mostrati e ogni esercizio che conta è stato verificato (o non ha più verifiche). Fino ad allora è incompleto, e l’LMS conserva il punto in cui il lettore era arrivato per la visita successiva.
- **Superamento.** Con una soglia di superamento, uno SCO completato risulta superato o non superato rispetto a essa. Il manifest la contiene (`adlcp:masteryscore` in SCORM 1.2, un obiettivo primario con `minNormalizedMeasure` in SCORM 2004), e il player prende il valore che l’LMS restituisce, così un LMS che fissa la propria soglia prevale.
- **Interazioni.** Ogni verifica scrive l’esercizio come interazione: un id ricavato dalla sua ancora o dal suo numero, un tipo ricavato dal suo genere (`true-false`, `choice`, `fill-in`, `other`), la risposta del lettore, quella giusta, il risultato e un peso pari alle sue risposte valutate; SCORM 2004 aggiunge una descrizione e tiene un’interazione per esercizio, SCORM 1.2 ne aggiunge una a ogni verifica.
- **Aggregazione.** SCORM 2004 pesa nel manifest la misura di ogni SCO in base alle sue risposte valutate, così il punteggio del corso è il totale delle risposte giuste sul totale delle risposte valutate. SCORM 1.2 non ha un’aggregazione propria: decide il metodo di valutazione dell’LMS (Moodle offre il punteggio più alto, la media o la somma dei punteggi degli SCO).
- **Risposte.** Vanno in `cmi.suspend_data` con le verifiche usate e le volte in cui si è ricominciato, così i limiti di un tentativo ([Valutazione](/it/docs/configuration-exercises#valutazione)) valgono da una visita all’altra e da un dispositivo all’altro. Oltre i 4.096 caratteri di SCORM 1.2, i conteggi arrivano comunque all’LMS e le risposte restano nel browser del lettore.

Fuori da un LMS (la sola pagina di avvio, o il pacchetto su un server web) il player non trova nessuna API: il libro si legge allo stesso modo e gli esercizi conservano le risposte nel browser, come quelli di un libro HTML o EPUB.

### Verificare un pacchetto

La suite di test convalida i manifest di entrambe le versioni rispetto agli schemi IMS e ADL con `xmllint`. Per provare un pacchetto, importa lo zip in un LMS (l’attività SCORM di Moodle accetta entrambe le versioni) o in [SCORM Cloud](https://cloud.scorm.com/). Funziona anche un sostituto locale: [scorm-again](https://github.com/jcputney/scorm-again) fornisce le API di SCORM 1.2 e 2004 in una pagina che carica la pagina di avvio in un riquadro, e rifiuta ogni valore che il modello di dati non ammette.
