# Configuració: ús programàtic


## Ús programàtic

> **Camí recomanat: fes servir el Web Worker.** Al navegador, compon a través de `createLayoutWorker()` de `postext/worker` en lloc de cridar `buildDocument` al fil principal. El worker manté la pàgina receptiva mentre compon, conserva les mesures del text d'una composició a la següent i cancel·la la que està en curs quan en comença una de més recent, de manera que una pulsació mai no espera que es compongui un text anterior. La recepta és a [Executar la composició en un Web Worker](#executar-la-composició-en-un-web-worker). La resta d'aquesta secció (`buildDocument` directe, resolutors, funcions de neteja, memòries cau) continua sent vàlida: el worker rep les mateixes entrades i retorna les mateixes sortides. Crida `buildDocument` al fil principal només per a exportacions puntuals, renderització al servidor (Node) o proves.

### Construir un document

La funció `buildDocument` executa tot el procés de composició i retorna un arbre de document virtual (VDT) amb coordenades precises per a cada element. És el punt d'entrada de més baix nivell; el codi d'una interfície hauria de fer servir preferentment l'[embolcall Web Worker](#executar-la-composició-en-un-web-worker), que crida `buildDocument` dins d'un fil worker dedicat amb els mateixos arguments.

```ts
import { buildDocument } from 'postext';

const content = {
  markdown: '# Capítol u\n\nLa història comença aquí...',
};

const config = {
  page: { sizePreset: '17x24' },
  layout: { layoutType: 'double' },
  bodyText: { fontFamily: 'EB Garamond', fontSize: { value: 9, unit: 'pt' } }, // 9 pt sobreescriu el valor per defecte de 8 pt
};

// Construir la composició — produeix un VDT amb una entrada per pàgina a `vdt.pages`
const vdt = buildDocument(content, config);
console.log(`El document té ${vdt.pages.length} pàgines`);
```

### Avisos del document

`buildDocument` no s'atura davant d'una referència errònia o d'un estil desconegut: aplica una alternativa i registra el que ha fet a `doc.contentWarnings`. Les caixes que la maquetació ha hagut de forçar són a `doc.warnings`, que conserva la forma que tenia a postext 1.4: cada entrada és un `calloutOverflow` amb el `pageIndex`, el `columnIndex` i l'`overflowPx`. Si no hi ha res a notificar, el camp no hi és. Cada entrada té un `kind`. Els avisos de contingut porten l'interval del text font on hi ha l'element (`sourceStart` / `sourceEnd`, posicions dins del Markdown que has passat, frontmatter inclòs) i, quan l'element ha anat a parar a una pàgina, el `pageIndex`.

La taula enumera els tipus que pot generar qualsevol document. Els tipus d'una funció concreta es descriuen amb ella: els dels còmics (`comicPanelCount`, `comicBalloonOverflow`…) a la pàgina [Còmics](/ca/docs/comics), els dels vídeos (`videoWithoutUrl`, `videoUrlInvalid`, `videoWithoutPoster`) a [Recursos](/ca/docs/document-format-resources), els de les citacions i l'índex (`unknownCitationKey`, `referencesUnreadable`, `indexMark`…) a [Notes i referències](/ca/docs/document-format-notes-references), els del text xinès, japonès i àrab (`cjkLooseLine`, `rubyExceedsLeading`, `arabicMarksExceedLeading`…) a les pàgines d'aquestes escriptures, i els del separador de línies (`raggedLine`, `unbreakableWordOverflow`, `wordDividedByCharacter`, `wordDividedBySyllable`) a [Justificació](/ca/docs/justification).

Els avisos sobre un recurs (l'estil de taula, la graella, una referència dins del peu, de la nota o de les cel·les) apunten a la primera inserció o referència del recurs al text, i cadascun es registra una sola vegada per recurs. Només es comproven els recursos que fa servir el document: un capítol d'un llibre notifica les taules que cita, no totes les taules del llibre.

```ts
import { buildDocument, formatWarning } from 'postext';

const doc = buildDocument({ markdown: 'Vegeu :ref{id="fig-map"}.\n\n:::sidebar\nNotes.' }, config);
for (const w of [...(doc.warnings ?? []), ...(doc.contentWarnings ?? []), ...(doc.configWarnings ?? [])]) console.warn(formatWarning(w));
// Unknown resource id "fig-map" in :ref — it prints "?" (or its text= label), with no number or link (page 1, offset 6)
// Unknown directive ":::sidebar" — the line is set as text (page 1, offset 27)

// Estreny per `kind` per llegir els camps d'un tipus.
const missing = (doc.contentWarnings ?? []).flatMap((w) => (w.kind === 'unknownResourceId' ? [w.resourceId] : []));
```

`formatWarning(w)` retorna una descripció en anglès d'una línia. Un amfitrió que tradueix els missatges els distingeix per `kind`, i ha de conservar una branca per defecte, perquè les versions menors poden afegir tipus nous. `collectContentWarnings(markdown, config, resources)` retorna els avisos de contingut sense maquetar res (la mateixa llista que afegeix la composició, sense `pageIndex`), per a un editor que revisa el text mentre s'escriu. `collectHeadingDesignCuts(doc)` revisa una maquetació acabada a la recerca de dissenys d'encapçalament amb un text que passa del peu de la seva pàgina o de la seva columna (`kind: 'headingDesignCut'`; vegeu [Alçada reservada](/ca/docs/configuration-headings#alçada-reservada)), que la maquetació mateixa no avisa, i `formatWarning` també en descriu els resultats. El tauler **Revisió** del Sandbox els mostra tots.

Els renderitzadors comuniquen el que no poden pintar com s'ha demanat amb una opció `onWarning`: `renderPageToCanvas`, `renderPage` i `renderToCanvas` (`RenderPageOptions`), `renderToHtml` i `renderToHtmlIndexed` (`RenderHtmlOptions`), i `renderToPdf` (`RenderToPdfOptions`, també a través del worker de PDF). El principal tipus d'avís de renderitzat és `missingImage`: una imatge (una figura, la imatge d'una cel·la de taula, la icona d'un requadre, una imatge de disseny) sense res a dibuixar es pinta com un requadre buit neutre i es notifica, una vegada per `fileId` i crida de renderitzat, amb el seu `pageIndex`, el `resourceId` quan el renderitzador el coneix (figures i imatges de cel·la) i, al PDF, el `documentIndex` d'un renderitzat de diversos documents. Res a dibuixar vol dir: cap `registerResourceImage` per al `fileId` al canvas, cap URL de `resourceImageUrl` en HTML, i cap byte de `resourceBytes` (o bytes que no es poden descodificar) al PDF. Un recurs de mapa de bits o SVG que no indica cap `fileId` no té res a demanar: es dibuixa com a requadre buit sense cap avís. Dos tipus més vénen dels amfitrions que incrusten fonts a les imatges SVG (`registerSvgImage`, `registerBundleImages`, `bundleImageUrl`, `renderToHtml` amb `inlineSvgFonts`, postext-epub; consulta [Fonts al text dels SVG](/ca/docs/configuration-resources#fonts-al-text-dels-svg)), amb el `fileId` i el `resourceId` de la imatge: `svgFontUnavailable` (`family`, `weight`, `style`), una família que fa servir el text però que no té cap variant per incrustar, de manera que la imatge compon aquest text amb una font de reserva; i `svgFontsTooLarge` (`bytes`, `maxBytes`), variants per sobre del límit de mida, de les quals no se n'incrusta cap. Els avisos de renderitzat no es desen al VDT: el que un amfitrió pot aportar pot canviar després de la maquetació.

```ts
import { buildDocument, renderPage, type RenderWarning, type Resource } from 'postext';

const map: Resource = {
  id: 'fig-map', typeId: 'figure', kind: 'bitmap', caption: 'La ruta.', createdAt: 0, updatedAt: 0,
  bitmap: { fileId: 'map-file', format: 'png', width: 1200, height: 800 },
};
const doc = buildDocument({ markdown: 'Vegeu :ref{id="fig-map"}.', resources: [map] }, config);

const warnings: RenderWarning[] = [];
const canvas = renderPage(doc.pages[0], doc, { onWarning: (w) => warnings.push(w) });
// Fins que 'map-file' es registri amb registerResourceImage:
// [{ kind: 'missingImage', fileId: 'map-file', resourceId: 'fig-map', pageIndex: 0 }]
```

### Renderitzar una pàgina en un mapa de bits

Cada pàgina es pot rasteritzar de manera independent. Fes servir `renderPage(page, doc)` per obtenir un `HTMLCanvasElement` a partir del número de pàgina: el canvas és un mapa de bits amb la mida exacta de la pàgina en píxels (amb els dpi configurats), de manera que el pots mostrar, exportar o passar a qualsevol procés de tractament d'imatges:

```ts
import { buildDocument, renderPage } from 'postext';

const vdt = buildDocument(content, config);

// Renderitzar la pàgina 3 (índex de base 0) com a bitmap
const pageNumber = 2;
const page = vdt.pages[pageNumber];
if (!page) throw new Error(`La pàgina ${pageNumber} no existeix`);

const canvas = renderPage(page, vdt);
// canvas.width / canvas.height són la mida del bitmap de la pàgina en píxels

// Mostrar-lo al DOM
document.body.appendChild(canvas);

// …o exportar-lo com a PNG data URL
const pngDataUrl = canvas.toDataURL('image/png');

// …o obtenir un Blob per baixar o pujar
canvas.toBlob((blob) => {
  if (blob) saveAs(blob, `pagina-${pageNumber + 1}.png`);
}, 'image/png');

// …o accedir als píxels RGBA en brut
const ctx = canvas.getContext('2d')!;
const imageData = ctx.getImageData(0, 0, canvas.width, canvas.height);
```

Si prefereixes pintar sobre un canvas que ja tens (per exemple un de muntat al DOM amb una disposició concreta), fes servir `renderPageToCanvas(page, doc, canvas)`: redimensiona i dibuixa al canvas que li passis en lloc de crear-ne un de nou.

Per renderitzar totes les pàgines, itera sobre `vdt.pages`:

```ts
const bitmaps = vdt.pages.map((page) => renderPage(page, vdt));
```

### React

`postext/react` exporta `createLayout(content, config?)`: un component que compon el document una sola vegada, en muntar-se, i mostra cada pàgina com un `<canvas>` dins d'un `<div>`.

```tsx
import { createLayout } from 'postext/react';

const Article = createLayout(
  { markdown: '# Hola\n\nEl primer paràgraf de l\'article.' },
  { page: { sizePreset: '17x24' } },
);

export function ArticlePage() {
  return <Article className="pages" style={{ maxWidth: 480 }} />;
}
```

- **Al fil principal, una vegada.** Les pàgines es pinten a la resolució del document i s'escalen a l'amplada del contenidor. `content` i `config` queden fixats en cridar `createLayout`; crea un altre component per mostrar una altra cosa. Per a una previsualització en viu, compon al [Web Worker](#executar-la-composició-en-un-web-worker) i pinta amb `renderPageToCanvas`, com a l'exemple de React d'aquella secció.
- **Primer, fonts i imatges.** Carrega les fonts web del document abans que el component es munti i registra'n les imatges amb `registerResourceImage`. Si el Markdown conté un `$`, el component arrenca el [motor de fórmules](/ca/docs/configuration-lists-math#arrencar-el-motor-de-fórmules) pel seu compte.
- **React es queda fora de l'entrada principal.** `postext` no importa mai React; només ho fa `postext/react`. `createLayout` encara s'exporta des de `postext` perquè el codi existent continuï funcionant, però està obsolet: carrega `postext/react` quan el crides, i el component queda suspès fins que arriba (React el torna a renderitzar tot sol). Importa'l des de `postext/react`.
- **El component obsolet se suspèn.** Fins que arriba `postext/react`, el `createLayout` de `postext` necessita una arrel concurrent (`createRoot`) o un límit `<Suspense>` per sobre. En una arrel antiga de `ReactDOM.render`, o a `renderToString`, sense aquest límit, React dona un error. `react` continua sent una *peer dependency* obligatòria, perquè els empaquetadors puguin resoldre aquesta importació diferida.

### Resoldre valors per defecte

Les funcions de resolució omplen els valors per defecte per a objectes de configuració parcials. Això és útil quan necessites una configuració completa per a inspecció o comparació:

```ts
import { resolvePageConfig, resolveBodyTextConfig } from 'postext';

const fullPage = resolvePageConfig({ sizePreset: '21x28' });
// => { sizePreset: '21x28', width: { value: 21, unit: 'cm' }, height: { value: 28, unit: 'cm' },
//      margins: { top: { value: 2, unit: 'cm' }, ... }, dpi: 300, cutLines: { enabled: false, ... }, ... }

const fullBody = resolveBodyTextConfig({ fontFamily: 'Inter' });
// => { fontFamily: 'Inter', fontSize: { value: 8, unit: 'pt' }, lineHeight: { value: 1.5, unit: 'em' }, ... }
```

Funcions de resolució disponibles, una per secció de primer nivell: `resolvePageConfig`, `resolveLayoutConfig`, `resolveBodyTextConfig`, `resolveHeadingsConfig`, `resolveHeadingStylesConfig`, `resolveTocConfig`, `resolvePartsConfig`, `resolveUnorderedListsConfig`, `resolveOrderedListsConfig`, `resolveMathConfig`, `resolveTableStyleConfig`, `resolveCaptionStyleConfig`, `resolveDiagramStyleConfig`, `resolveParagraphStylesConfig`, `resolveCalloutStylesConfig`, `resolveHeaderFooterConfig`, `resolveDebugConfig`, `resolveHtmlViewerConfig`, `resolvePdfGenerationConfig` i, a més, `resolveDesignSlot` per a una sola zona de disseny. Les paletes de colors s'apliquen per separat amb `applyPaletteToConfig(config)`, `applyPaletteToResolvedConfig(resolved, palette)` i `resolveColorValue(value, palette, fallback)`; vegeu [Paleta de colors](/ca/docs/configuration-fonts-colors-viewers#paleta-de-colors).

Les funcions de resolució amb valors per defecte heretats d'una altra secció reben aquesta secció, ja resolta, com a argument addicional. `resolveUnorderedListsConfig` i `resolveOrderedListsConfig` reben el cos de text resolt, perquè les llistes n'hereten `fontFamily` i `color`; `resolveCalloutStylesConfig` rep el cos de text, els encapçalaments i les llistes no ordenades resolts (vegeu l'exemple a [Estils de requadre](/ca/docs/configuration-callouts#estils-de-requadre)), i `resolveHeadingStylesConfig` la pàgina, el cos de text i les dues seccions de llistes resoltes. Consulta les declaracions de tipus del paquet per a la signatura exacta de cadascun:

```ts
import { resolveBodyTextConfig, resolveUnorderedListsConfig } from 'postext';

const body = resolveBodyTextConfig({ fontFamily: 'Inter' });
const lists = resolveUnorderedListsConfig({ bulletChar: '—' }, body);
// => lists.fontFamily === 'Inter' (heretat)
```

També s'exporten els conjunts de valors per defecte estàtics, els que es fan servir quan no hi ha herència: `DEFAULT_PAGE_CONFIG`, `DEFAULT_CUT_LINES`, `DEFAULT_PAGE_NUMBERING`, `PAGE_SIZE_PRESETS`, `DEFAULT_LAYOUT_CONFIG`, `DEFAULT_COLUMN_RULE`, `DEFAULT_COLUMN_BALANCING`, `DEFAULT_BODY_TEXT_CONFIG`, `DEFAULT_HYPHENATION_CONFIG`, `DEFAULT_HEADINGS_CONFIG`, `DEFAULT_UNORDERED_LISTS_STATIC`, `DEFAULT_ORDERED_LISTS_STATIC`, `DEFAULT_PARAGRAPH_STYLES`, `DEFAULT_CALLOUT_STYLES`, `DEFAULT_CALLOUT_STYLE_STATIC`, `DEFAULT_PARTS_CONFIG`, `DEFAULT_HEADING_STYLES`, `DEFAULT_TOC_CONFIG`, `DEFAULT_MATH_CONFIG`, `DEFAULT_DIAGRAM_STYLE_CONFIG`, `DEFAULT_DEBUG_CONFIG`, `DEFAULT_HTML_VIEWER_CONFIG`, `DEFAULT_PDF_GENERATION_CONFIG`, `DEFAULT_COLOR_PALETTE`, `DEFAULT_MAIN_COLOR`, `DEFAULT_MAIN_COLOR_ID`, `DEFAULT_MAIN_COLOR_NAME`, `DEFAULT_MAIN_COLOR_HEX`, a més dels valors per defecte dels elements de capçalera/peu (`DEFAULT_HEADER_FOOTER_SLOT`, `DEFAULT_HEADER_SLOT`, `DEFAULT_FOOTER_SLOT`, `DEFAULT_TEXT_ELEMENT`, `DEFAULT_RULE_ELEMENT`, `DEFAULT_BOX_ELEMENT`) i la funció sensible a la llengua `defaultResourceTypes(locale)` (vegeu [Tipus de recurs](/ca/docs/configuration-resources#tipus-de-recurs)).

### Eliminar valors per defecte

Quan desis la configuració (per exemple, a localStorage o en un fitxer), fes servir `stripConfigDefaults` per eliminar els valors que coincideixen amb els valors per defecte. Així, les configuracions desades són tan petites com és possible: només s'hi desen els canvis fets a propòsit:

```ts
import { stripConfigDefaults } from 'postext';

const minimal = stripConfigDefaults(fullConfig);
// Només hi romanen les propietats que difereixen dels valors per defecte
```

També hi ha funcions individuals, una per cada funció de resolució: `stripPageDefaults`, `stripLayoutDefaults`, `stripBodyTextDefaults`, `stripHeadingsDefaults`, `stripHeadingStylesDefaults`, `stripTocDefaults`, `stripPartsDefaults`, `stripUnorderedListsDefaults`, `stripOrderedListsDefaults`, `stripMathDefaults`, `stripTableStyleDefaults`, `stripCaptionStyleDefaults`, `stripDiagramStyleDefaults`, `stripParagraphStylesDefaults`, `stripCalloutStylesDefaults`, `stripHeaderFooterDefaults`, `stripDesignSlotDefaults`, `stripDebugDefaults`, `stripHtmlViewerDefaults`, `stripPdfGenerationDefaults`.

Alguns valors per defecte depenen de la resta de la configuració: l'equilibratge de columnes està desactivat en una retícula de caràcters i en el text vertical, `bodyText.avoidWidows` està desactivada en una retícula de caràcters (i `bodyText.avoidOrphans` també a la regió `japan`), i les notes a peu de pàgina, els peus de recurs i l'índex analític segueixen la llengua del document. `stripConfigDefaults` compara cada valor amb el valor per defecte de la configuració que rep, de manera que `headings.balancing.enabled: true` es conserva on l'equilibratge està desactivat per defecte, i `false` s'hi elimina. `bodyText.avoidWidows: true` es conserva de la mateixa manera en una retícula de caràcters. Una funció cridada per separat rep aquest context com a arguments: `stripHeadingsDefaults(headings, balancingOnByDefault(config))`, `stripIndexDefaults(index, locale)`, `stripCaptionStyleDefaults(captionStyle, locale)`, `stripFootnotesDefaults(footnotes, locale, writingMode)`, `stripBodyTextDefaults(bodyText, locale, avoidWidowsByDefault(config), avoidOrphansByDefault(config))`.

Un valor que diu «res» es conserva allà on res no és el valor per defecte. Un estil d'encapçalament pren la capçalera i el peu de pàgina del document quan no en fixa de propis, de manera que l'estil que els buida (`footer: { elements: [] }` en una coberta) conserva el buit, i els seus `margins`, `layout` i `bodyStyle` es conserven encara que estiguin buits. Un nivell d'encapçalament que torna al valor per defecte mentre els valors generals dels encapçalaments són diferents conserva el valor. `calloutStyles: []` i `chipStyles: []` continuen sent llistes buides: si s'ometessin, tornaria l'estil integrat. En tots els casos `resolveAllConfig(stripConfigDefaults(config))` es resol igual que `resolveAllConfig(config)`.

### Anàlisi

El motor ofereix el seu tokenitzador de Markdown i el lector de frontmatter. Fes-los servir per inspeccionar un document abans de construir-lo, o per alimentar altres eines amb la mateixa estructura de blocs que veu Postext:

```ts
import { parseMarkdown, extractFrontmatter } from 'postext';

const source = '---\ntitle: Capítol u\n---\n\n# Obertura\n\nLa història comença aquí.';

const { metadata, content } = extractFrontmatter(source);
// metadata.title === 'Capítol u'

const blocks = parseMarkdown(content);
// => [ { type: 'heading', level: 1, text: 'Obertura', … },
//      { type: 'paragraph', text: 'La història comença aquí.', … } ]
```

Consulta la pàgina de [Format del document](/ca/docs/document-format) per veure la llista completa de construccions de Markdown que reconeix Postext.
### Mapa de procedència d'un document compaginat

`sourceAt(doc, pageIndex, x, y, options?)` retorna el que mostra un punt d'una pàgina, de dins cap a fora, cada element amb el seu `id` estable, el seu `source` (un tram del Markdown, un punter JSON de la configuració, un atribut de la línia d'obertura de la pàgina o un recurs) i el seu `rect`. `elementsForSource(doc, start, end, options?)` retorna el que ha sortit d'un tram del Markdown, pàgina a pàgina, i `findElement(doc, id)` torna a trobar un element després de recompondre. Llegeixen el que la compaginació ha deixat marcat al VDT i no compaginen res. `composedPagePaintKey(page)` diu si una pàgina composta pinta el mateix que va pintar abans. Els tipus de procedència, els identificadors i com es recompon una pàgina composta només on ha canviat són a [Pàgines compostes › Mapa de procedència](/ca/docs/composed-pages#mapa-de-procedència).

### Carregar les fonts abans de compondre

La composició mesura el text amb les variants que té el conjunt de fonts en el moment en què s'executa. `prepareFonts` carrega abans de la primera construcció totes les variants que necessiten una configuració i el seu text: el cos, els encapçalaments, les llistes, els títols i els cossos dels requadres, les taules, els textos dels elements de disseny, les capçaleres, l'índex general, el codi i la retolació dels còmics, en cada pes i inclinació que fixa la configuració (les quatre de la família del cos, perquè `**` i `*` hi componen la negreta i la cursiva). Cada variant es carrega per als caràcters que compon el document, de manera que una família servida en trams de `unicode-range` (llatí estès, grec, àrab, els trams CJK de Google Fonts i Fontsource) porta els fitxers que el text necessita.

```ts
import { prepareFonts, buildDocument, buildDocumentWithFonts } from 'postext';

// Els fitxers de l'amfitrió: el contracte del proveïdor de fonts del PDF, així que una mateixa funció serveix per a tots dos.
async function resolve(family: string, weight: number, style: 'normal' | 'italic') {
  const id = family.toLowerCase().replace(/\s+/g, '-');
  return `https://cdn.jsdelivr.net/npm/@fontsource/${id}@5/files/${id}-latin-${weight}-${style}.woff2`;
}

const report = await prepareFonts(content, config, { resolve });
// report.loaded, report.missing, report.synthesized: { family, weight, style }[]
const doc = buildDocument(content, config);

// O en una sola crida: preparar, compondre, carregar les cares que han fet servir les pàgines i no hi eren, i tornar a compondre.
const same = await buildDocumentWithFonts(content, config, { resolve });
```

- **Les variants que declara la pàgina** (una regla `@font-face`, un `FontFace` ja afegit) es carreguen a través del conjunt de fonts (`document.fonts.load`, o `self.fonts` en un worker). **Les que no declara** es demanen a `resolve(family, weight, style, { text, codePoints })`, que respon amb un fitxer (bytes o una URL), amb diversos (els trams d'una variant), amb `{ source, unicodeRange, weight, style }` per a un tram o un interval variable, o amb `null`. El motor les afegeix com a `FontFace` quan s'han carregat totes, en l'ordre de la configuració i de cada resposta (latin, després latin-ext, després greek si el resolutor respon així), de manera que el conjunt de fonts queda igual sigui quin sigui l'ordre en què arribin els fitxers. També les inscriu al registre de fonts que llegeixen les [imatges SVG](/ca/docs/configuration-resources#fonts-al-text-dels-svg) i els workers de composició. Un resolutor pot declarar la variant pel seu compte (afegint un full d'estils) i respondre `null`.
- **L'informe** llista a `loaded` les variants que cobreix una variant carregada (o una família instal·lada); a `missing`, les que encara falten, i a `synthesized`, les que el navegador generaria a partir d'un altre pes o d'una altra inclinació; `added` compta els `FontFace` afegits a partir dels fitxers del resolutor. `timeoutMs` (10 000 per defecte) limita l'espera; una variant que en aquell moment encara s'estigui carregant compta com a absent. On no hi ha conjunt de fonts (Node), `prepareFonts` no fa res i dona totes les variants per carregades.
- **`buildDocumentWithFonts(content, config, options)`** prepara les fonts, maqueta amb `buildDocumentAsync`, llegeix les variants amb què les pàgines han compost realment text, carrega les que el conjunt de fonts no podia proporcionar (un pes que només revelen les pàgines es demana a `resolve` encara que un altre pes de la família pogués respondre per ell) i torna a maquetar (dues vegades més com a màxim). `withLoadedFonts(build, options)` fa el mateix al voltant de qualsevol funció de composició, per a un llibre que es maqueta capítol a capítol o per a un paquet (`buildBundle`) que retorna diversos documents. `options.onFonts` rep l'informe final.
- **Després de la construcció**, cada variant amb què s'ha compost el text i que el conjunt de fonts no ha pogut proporcionar apareix a `doc.contentWarnings` com a `fontFallback` (vegeu [Avisos del document](#avisos-del-document)).

**Estils de xifres.** Un estil amb [`figureStyle`](/ca/docs/configuration-fonts-colors-viewers#estils-de-xifres) compon el text en una família amb funcions: el nom de la família base seguit de les funcions OpenType després de `@` (`EB Garamond@onum`). A `prepareFonts` i a `resolve` se'ls demana la família base, i el motor declara les variants de la família amb funcions a partir dels mateixos fitxers, amb el descriptor `featureSettings`. El `FontPayload` d'un worker de maquetació admet un `featureSettings` opcional per a aquesta font, amb `family` igual a la família amb funcions i la memòria intermèdia del fitxer de la família base. `configFeatureFamilies(config)` enumera les famílies amb funcions en què una configuració compon text. Un amfitrió que compon text en fonts de les quals no té fitxers nomena amb `setFigureStyleFamilies((family) => boolean)` les famílies que poden prendre funcions; les altres conserven les seves xifres. `baseFontFamily` i `featureFamilyParts` descomponen aquest nom, `withFigureStyle(fontFamily, figureStyle)` el construeix i `freezeFontFeatures(bytes, features)` retorna una còpia d'un fitxer TrueType o OpenType el `cmap` de la qual porta els caràcters als glifs que donen les substitucions simples de les funcions, per a un canvas que no aplica funcions (Skia a Node).

Les variants que arriben més tard es detecten soles. El motor anota, per a cada conjunt de fonts, quines variants de cada família hi havia carregades l'última vegada que el va consultar; una construcció hi torna a mirar en començar (només si el conjunt ha crescut o s'ha reduït, o està carregant o ha acabat de carregar una variant) i descarta el que s'havia mesurat en les famílies amb variants canviades. `watchFonts(fontSet)` fa el mateix a mesura que es carreguen les variants, com a molt una vegada per fotograma d'animació, per molts trams que arribin alhora, i `onFontsChanged(listener)` diu a l'amfitrió quines famílies han canviat, perquè torni a compondre les pàgines:

```ts
import { watchFonts, onFontsChanged } from 'postext';

const stop = watchFonts();                         // document.fonts per defecte
const off = onFontsChanged((families) => relayout());
```

`prepareFonts` engega la vigilància sobre el conjunt on carrega (`watch: false` la deixa apagada).

### Memòria cau de mesures

La mesura del text és el pas més costós del procés de composició. Hi ha dues menes de memòria cau que en redueixen el cost:

- **Una memòria cau de blocs que és teva.** `createMeasurementCache()` retorna una `MeasurementCache` que recorda cada paràgraf mesurat, fent servir com a clau el text, les fonts, l'amplada, les opcions de tall de línies i el diccionari de partició de mots actiu. Passa-la com a tercer argument de `buildDocument` (o de `buildDocumentAsync`) per reutilitzar les mesures entre les passades de col·locació d'una composició i entre composicions: un editor que recompon el document a cada pulsació mesura llavors només els paràgrafs que han canviat. Sense ella, cada passada torna a mesurar tots els blocs. Un paràgraf llegit de la memòria cau és igual que un de mesurat de nou, de manera que una composició amb memòria cau talla cada línia igual que una sense; a postext 1.4.1, un paràgraf desat a la memòria cau perdia la marca d'última línia massa curta, i la correcció d'aquestes línies i l'equilibratge de columnes el podien tallar d'una altra manera. La memòria cau porta la generació de mesures amb què es va omplir: quan arriben o desapareixen variants d'una família, la consulta següent descarta els blocs compostos en aquella família, de manera que una memòria cau que es conserva mentre es carreguen les fonts mai no serveix línies mesurades amb la de reserva.
- **Memòries cau globals d'amplades.** Les amplades de paraula es desen per cadena de font en un estat de mòdul que comparteixen totes les composicions de la pàgina, i pretext té la seva pròpia memòria cau. El motor descarta les amplades d'una família quan en canvien les variants (en començar una construcció, des de `watchFonts`, des de `prepareFonts` i des de `loadBundleFonts`); la memòria cau de pretext no té índex per família i es buida sencera.

```ts
import { buildDocument, createMeasurementCache, evictFontFamilies, clearMeasurementCache } from 'postext';

const cache = createMeasurementCache();
let doc = buildDocument(content, config, cache);

// S'ha afegit a document.fonts una cara d'"EB Garamond": el build següent la veu,
// amb la mateixa memòria cau, i torna a mesurar aquella família.
doc = buildDocument(content, config, cache);

// Un amfitrió que canvia cares que el motor no pot veure (un conjunt de fonts propi) ho avisa:
evictFontFamilies(['EB Garamond']);   // les amplades i els blocs desats d'aquella família
clearMeasurementCache();              // totes les famílies
```

Per a aplicacions que mesuren el text peça a peça, `cachedMeasureBlock(text, font, maxWidthPx, lineHeightPx, options, cache)` i `cachedMeasureRichBlock(spans, normalFont, boldFont, italicFont, boldItalicFont, maxWidthPx, lineHeightPx, options, cache)` reben els arguments de `measureBlock` i `measureRichBlock` més la memòria cau, al final.

### El separador de línies (WebAssembly)

Els paràgrafs es parteixen en línies amb Knuth–Plass. Des de postext 1.33, el motor l'executa en un separador de línies escrit en Rust i compilat a WebAssembly (30 KB, inclòs al paquet). Tria els mateixos talls que el separador en TypeScript, amb la mateixa aritmètica en el mateix ordre, i un llibre sencer es maqueta un 15 % més de pressa, aproximadament. No cal configurar res:

- En un worker, a Node i a Bun, el mòdul es compila al primer paràgraf.
- Al fil principal d'una pàgina, on el navegador només compila un mòdul d'aquesta mida de manera asíncrona, es compila en segon pla i fins aleshores respon el separador en TypeScript. `await initLineBreaker()` abans de la primera composició el posa a treballar des del primer paràgraf; retorna `false` on no hi ha WebAssembly.
- On falta WebAssembly, o una política de seguretat de contingut el rebutja (`script-src` sense `'wasm-unsafe-eval'`), el separador en TypeScript respon a tots els paràgrafs.

Tots dos trien els mateixos talls, de manera que el resultat no canvia mai segons quin respongui. `useWasmLineBreaker(false)` manté el separador en TypeScript, per comparar-los.

```ts
import { initLineBreaker, buildDocument } from 'postext';

await initLineBreaker(); // opcional: la primera composició ja l'usa
const doc = buildDocument({ markdown }, config);
```


### Estat global compartit en una pàgina

Part de l'estat de Postext és en variables de mòdul. Tot el que importa `postext` en el mateix context de JavaScript (*realm*) el comparteix: una pàgina i els seus scripts comparteixen una còpia, mentre que cada iframe i cada worker tenen la seva. Amb un document per pàgina no es nota. Amb diversos documents a la mateixa pàgina (dues previsualitzacions en directe, una galeria d'exemples), sí:

- **Imatges dels recursos.** `registerResourceImage(fileId, image)` omple un únic registre indexat per `fileId`, que llegeixen `renderPage` i `renderPageToCanvas`. Dos documents que registren `figure.svg` comparteixen aquesta entrada: preval l'últim registre, per a tots dos. Posa als identificadors de fitxer un prefix per document, i crida `unregisterResourceImage(fileId)` o `clearResourceImages()` quan un document desapareix. Els ràsters que desa a la memòria cau el backend de canvas fan servir la mateixa clau i es descarten amb la imatge.
- **Mesures del text.** Les amplades mesurades es desen a la memòria cau per cadena de font i text per a tot el context. Quan arriben o desapareixen variants d'una família, el motor descarta les amplades d'aquella família per a tots els documents (vegeu [Carregar les fonts abans de compondre](#carregar-les-fonts-abans-de-compondre)); `clearMeasurementCache()` les descarta totes.
- **Configuracions resoltes.** Cada objecte de configuració es resol una vegada i el resultat queda a la memòria cau associat a aquest objecte. Abans de res, cada construcció compara l'objecte amb el text que tenia quan es va resoldre (un `JSON.stringify`, uns 0,1 ms per a una configuració de llibre de 55 KB i 1,5 ms per a una de 240 KB), de manera que una configuració modificada al lloc, a qualsevol profunditat (`config.bodyText.fontSize = …`, un color de la paleta), es torna a resoldre. `invalidateConfig(config)` descarta la resolució a mà. `stableStringify` i `hashString` donen una clau de contingut que no depèn de l'ordre de les claus, per als amfitrions que desen composicions a la memòria cau per configuració.
- **Llengua de la partició de mots.** Cada construcció fixa la llengua de partició de mots de tot el procés al `bodyText.hyphenation.locale` del seu document. Les funcions exportades `hyphenateText(text)` i `layoutDesignSlot` fan servir la llengua de l'última construcció tret que els en passis una: crida `hyphenateText(text, 'es')`.
- **Motor de fórmules.** Hi ha un únic motor MathJax i una única memòria cau de fórmules renderitzades per context; `initMathEngine()` l'engega per a tots.
- **Separador de línies.** Hi ha un únic separador de línies WebAssembly per context, compilat una vegada; `useWasmLineBreaker(false)` el desactiva per a tots.

L'aïllament més senzill és un context per document: un iframe per exemple en directe (una inserció de CodePen ho és), o un [worker de composició](#executar-la-composició-en-un-web-worker) per document per a les mesures i la partició de mots (les imatges es continuen registrant a la pàgina).

### Documents de Word (`postext/word`)

El subcamí `postext/word` llegeix i escriu documents de Word (`.docx`) sense DOM. La importació i l'exportació de Word del Sandbox i les ordres `import-docx` i `docx` de la línia d'ordres s'hi basen (vegeu [Línia d'ordres › docx i import-docx](/ca/docs/command-line#docx-i-import-docx)).

```ts
import { readDocx, parseTemplate, emptyTemplate, analyzeDocx, wordToPostext, postextToDocx } from 'postext/word';

const word = readDocx(bytes);                                    // un Uint8Array o un ArrayBuffer
const template = parseTemplate(word.embeddedTemplate) ?? emptyTemplate();
const report = analyzeDocx(word, template, config);              // report.verdict, report.findings
const { chapters, pictures, tables } = wordToPostext(word, {
  template, config, chapters: 'split', existingIds: new Set(), untitledChapter: 'Sense títol',
});

const docx = postextToDocx(chapters, { template, config, book: chapters.length > 1, title: 'Notes de camp' });
```

- **`readDocx(bytes)`** llegeix el fitxer en un model de Word: els estils, els paràgrafs, les notes i les imatges, el `title` del document i la plantilla d'importació que porta una exportació de Postext (`embeddedTemplate`). Un fitxer que no és un document de Word llança un `DocxReadError`.
- **`wordToPostext(word, settings)`** converteix el model en capítols (`{ title, markdown }`), imatges i taules. La plantilla fa correspondre cada estil de Word a un títol, un estil de paràgraf, un requadre, una cita o un peu de la configuració. `chapters: 'split'` obre un capítol a cada títol de nivell 1, i `'single'` en conserva un de sol. Les imatges (`id`, `media.bytes`, `caption`, `alt`) i les taules (`id`, `model`, `caption`) les ha de desar l'amfitrió com a recursos; `skippedPictures` enumera les imatges EMF, WMF i TIFF que s'han deixat fora.
- **`analyzeDocx(word, template, config)`** és l'informe de qualitat que mostra el Sandbox abans d'una importació: els estils en ús, quants paràgrafs tenen estil i observacions com `directFormatting`, `manualHeadings` i `typedNumbering`, cadascuna amb un recompte i exemples.
- **`postextToDocx(chapters, settings)`** escriu els capítols com un `.docx` (un `Uint8Array`) amb estils de Word per als títols, els paràgrafs, els requadres, les cites, les llistes i les notes. El que Word no pot expressar es conserva tal com està escrit amb els estils *Postext Markup*, i la plantilla va dins del fitxer, de manera que el document es torna a importar sense canvis. `book: true` obre cada capítol amb un paràgraf `Postext Chapter`, a partir del qual la importació reconstrueix els capítols.
- **`wordStyleTracking(word, template, config)`** i **`applyStyleTracking(config, tracking)`** passen l'espaiat entre caràcters dels estils de Word als estils de la configuració que no en defineixen cap.


## Executar la composició en un Web Worker

**Aquesta és la manera recomanada de fer servir Postext al navegador.** Si construeixes alguna cosa interactiva (una previsualització en directe, un editor, un visor que es redimensiona o un entorn de proves com el Sandbox), executa la composició amb `createLayoutWorker()` de `postext/worker`. No cridis `buildDocument` directament al fil principal en el codi d'una interfície.

Si crides `buildDocument` al fil principal, tot el procés (anàlisi, mesura, col·locació i cada repetició de la passada de col·locació que necessiti la composició) s'executa al fil que crida la funció. Per a una exportació puntual està bé. Per a una interfície interactiva és el fil equivocat: una composició de 150 ms bloqueja els esdeveniments d'entrada, les pulsacions de teclat s'encuen i el desplaçament va a batzegades. El worker trasllada cadascun d'aquests mil·lisegons a un fil secundari.

Postext inclou un punt d'entrada específic per a Web Worker, `postext/worker`, que treu la composició del fil principal. És el camí que esperem que segueixin la majoria de les integracions: les tres previsualitzacions del Sandbox (Canvas, HTML i PDF) comparteixen el mateix objecte de `createLayoutWorker()` a través d'un sol hook `useLayoutWorker` (`packages/postext-sandbox/src/worker/useLayoutWorker.ts`) i el controlen amb cancel·lació *last-wins*: una pulsació nova atura la construcció en curs fins i tot abans que acabi.

D'un cop d'ull, la integració recomanada és aquesta:

1. **Crea** un worker una vegada per vista amb `createLayoutWorker()`.
2. **Registra les fonts** una vegada per família enviant `ArrayBuffer`s transferibles via `registerFonts(payloads)`.
3. **Maqueta** amb `build(content, config, { signal })`, i passa un `AbortSignal` nou a cada crida per poder cancel·lar les construccions obsoletes.
4. **Substitueix** qualsevol construcció anterior avortant-ne el senyal *abans* de començar la següent: és el patró *last-wins*.
5. **Allibera** (*dispose*) el worker quan es desmunta el component que l'ha creat.

El mateix `VDTDocument` que retorna `build(...)` alimenta cada renderitzador posterior: `renderPage`/`renderPageToCanvas` per a canvas, `renderToHtmlIndexed` per a HTML i `renderToPdf` (de `postext-pdf`) per a PDF. Maquetes una vegada al worker i rasteritzes al fil principal tantes vegades com necessiti la interfície.

### Què t'aporta el worker

- **El fil principal queda lliure.** L'anàlisi, la mesura i totes les passades de col·locació s'executen dins del worker. El fil principal només es toca quan es publica de tornada el `VDTDocument` acabat.
- **Cancel·lació *last-wins*.** `build(content, config, { signal })` passa un `AbortSignal` al worker. Si s'avorta abans que acabi, el fil principal rep un `AbortError`; dins del worker, la composició llança un `BuildCancelledError` al punt de comprovació següent (n'hi ha un per bloc) i s'atura immediatament.
- **Memòria cau de mesures per worker.** El worker manté una sola `MeasurementCache` durant tota la seva vida. Les construccions posteriors que comparteixen font, text i amplada reutilitzen les mesures desades: si escrius un sol caràcter en un document llarg, només es tornen a mesurar els blocs que han canviat realment.
- **Mètriques idèntiques al fil principal.** Les fonts s'envien al worker com a `ArrayBuffer`s transferibles i es registren mitjançant `new FontFace(...)` al `FontFaceSet` propi del worker. Les mesures fan servir les mateixes mètriques de font del canvas que faria servir el fil principal, de manera que els talls de línia i les alçades de les columnes són idèntics byte a byte.
- **La memòria cau de fórmules rasteritzades es conserva d'una construcció a l'altra.** El renderitzador de fórmules té una memòria cau de ràsters indexada per contingut, a més de la indexada per identitat: si només hi hagués la memòria cau per identitat, fallaria en clonar estructuralment un `MathRender` per passar-lo al worker o del worker.
- **Les mateixes línies que a la pàgina.** Un canvas creat en un worker no té cap pàgina d'on prendre una llengua, i una font respon amb altres glifs segons la llengua. El motor fixa la llengua del document (`locale`) a cada context amb què mesura, al worker igual que a la pàgina, de manera que `build()` retorna les línies que `buildDocument` dona en una pàgina en qualsevol llengua ([`bodyText.shapingLanguage: 'document'`](/ca/docs/configuration-text#text-de-cos), el valor per defecte des de postext 1.30). Amb `'host'`, que conserva una configuració desada abans de la 1.30, un worker mesura sense llengua i una pàgina amb la seva, com fins a postext 1.28.

### API pública

El client del worker és al subcamí `postext/worker` i té pocs noms:

- **`createLayoutWorker(opts?): LayoutWorkerHandle`**: crea un worker dedicat (o n'embolcalla un que passis amb `opts.worker`, o engega l'entrada del worker que hi ha a `opts.url`) i retorna un objecte tipat per controlar-lo. Consulta [Carregar el worker des d'una CDN](#carregar-el-worker-des-duna-cdn).
- **`LayoutWorkerHandle.registerFonts(faces: FontPayload[]): Promise<void>`**: envia bytes de font al worker. Els buffers es transfereixen, així que desa'n una còpia nova al fil principal si després els necessites.
- **`LayoutWorkerHandle.unregisterFonts(families: string[]): Promise<void>`**: descarta les variants d'aquestes famílies que té el worker, perquè el `registerFonts` següent d'una família tingui efecte en lloc de comparar-se amb la variant que ja té.
- **`LayoutWorkerHandle.build(content, config?, options?): Promise<VDTDocument>`**: executa la composició. `options` és `{ signal?, onProgress?, onStats?, resourcesKey?, cacheKey? }`. Si avortes `signal`, es cancel·la la construcció en curs. `onProgress({ pass, blocks, totalBlocks, pages })` es crida a mesura que avança la col·locació; `onStats({ passes, totalMs, cached?, missingFonts? })` rep els temps de cada passada de la construcció acabada. `resourcesKey` és una empremta de `content.resources`: les construccions consecutives amb la mateixa clau envien la llista una sola vegada, i el worker la conserva. `cacheKey` és una empremta de tota la construcció: el worker hi associa els seus últims documents i respon des d'aquesta memòria cau una construcció amb una clau que ja té.
- **`LayoutWorkerHandle.warm(content, config, { cacheKey, … }): Promise<void>`**: construeix dins de la memòria cau de documents del worker sense tornar el document, per a un capítol que el lector pot obrir tot seguit; el `build` següent amb aquest `cacheKey` es respon des de la memòria cau.
- **`LayoutWorkerHandle.prepareFonts(content, config?, options?)`**: `prepareFonts` a la pàgina i, després, l'enviament al worker de les variants que ha trobat; vegeu [Carregar el worker des d'una CDN](#carregar-el-worker-des-duna-cdn).
- **`LayoutWorkerHandle.dispose(): void`**: tanca el worker i rebutja qualsevol construcció pendent amb `AbortError`.
- **`FontPayload`**: `{ family, weight, style, unicodeRange?, buffer: ArrayBuffer }`. `weight` és un pes CSS en forma de cadena (`'700'`, `'bold'`); `registerFonts` també l'accepta com a nombre (`700`). El `buffer` es transfereix al worker quan crides `registerFonts`.
- **`BuildCancelledError`** (reexportat des de `postext`): el que llança `buildDocument` internament quan `options.shouldCancel` retorna `true`. Normalment no el veus al fil principal: el protocol del worker el converteix en un `AbortError` abans d'arribar al teu codi.

El paquet també publica el camí `postext/worker/entry`, que apunta a l'script compilat del worker. `createLayoutWorker()` resol aquest URL automàticament; només cal que hi facis referència explícitament quan el teu empaquetador exigeix una crida manual a `new Worker(new URL(...), { type: 'module' })`, o quan serveixes l'entrada tu mateix (`opts.url`).

### Integració mínima

```ts
import { createLayoutWorker } from 'postext/worker';
import type { FontPayload, LayoutWorkerHandle } from 'postext/worker';
import type { PostextConfig, VDTDocument } from 'postext';

// 1. Crea el worker una sola vegada i conserva el handle durant tota la vida de la teva vista.
const layout: LayoutWorkerHandle = createLayoutWorker();

// 2. Registra les fonts una vegada per família (ArrayBuffers transferibles).
//    getConfigFontFamilies(config) és un helper que llista les famílies que la teva config renderitzarà.
const payloads: FontPayload[] = await collectFontPayloadsForFamilies([
  'EB Garamond',
  'Open Sans',
]);
await layout.registerFonts(payloads);

// 3. Dirigeix els builds amb cancel·lació last-wins: avorta el signal anterior
//    abans d'iniciar-ne un de nou. Un build obsolet es descarta dins del worker.
let pending: AbortController | null = null;

async function rebuild(
  markdown: string,
  config: PostextConfig,
): Promise<VDTDocument | null> {
  pending?.abort();
  pending = new AbortController();
  try {
    return await layout.build({ markdown }, config, { signal: pending.signal });
  } catch (err) {
    if ((err as { name?: string } | null)?.name === 'AbortError') return null;
    throw err;
  }
}

// 4. Allibera (dispose) quan el component propietari del worker es desmunta.
//    Els builds pendents es rebutgen amb AbortError.
layout.dispose();
```

Embolcallat en un component React, la forma és:

```tsx
import { useEffect, useRef } from 'react';
import { createLayoutWorker } from 'postext/worker';
import type { LayoutWorkerHandle } from 'postext/worker';
import { renderPageToCanvas } from 'postext';
import type { PostextConfig } from 'postext';

export function CanvasPreview({
  markdown,
  config,
}: {
  markdown: string;
  config: PostextConfig;
}) {
  const canvasRef = useRef<HTMLCanvasElement | null>(null);
  const workerRef = useRef<LayoutWorkerHandle | null>(null);
  const pendingRef = useRef<AbortController | null>(null);

  // Muntatge: engega el worker i envia les fonts una sola vegada.
  useEffect(() => {
    const handle = createLayoutWorker();
    workerRef.current = handle;
    (async () => {
      const payloads = await collectFontPayloadsForFamilies(
        getConfigFontFamilies(config),
      );
      await handle.registerFonts(payloads);
    })();
    return () => {
      pendingRef.current?.abort();
      handle.dispose();
    };
  }, []); // les fonts es registren una vegada; torna-les a registrar només quan canviï el conjunt de famílies

  // A cada tecla o canvi de config: substitueix el build en curs i llança'n un de nou.
  useEffect(() => {
    const handle = workerRef.current;
    if (!handle) return;
    pendingRef.current?.abort();
    const ac = new AbortController();
    pendingRef.current = ac;
    (async () => {
      try {
        const vdt = await handle.build({ markdown }, config, { signal: ac.signal });
        const canvas = canvasRef.current;
        if (!canvas || !vdt.pages[0]) return;
        renderPageToCanvas(vdt.pages[0], vdt, canvas); // rasteritza al fil principal
      } catch (err) {
        if ((err as { name?: string } | null)?.name !== 'AbortError') throw err;
      }
    })();
  }, [markdown, config]);

  return <canvas ref={canvasRef} />;
}
```

El patró sempre és el mateix: **crea una vegada, registra les fonts una vegada, maqueta amb AbortSignal tantes vegades com calgui i allibera en desmuntar.**

### Carregar el worker des d'una CDN

L'script d'un worker ha de venir del mateix origen que la pàgina, així que una còpia de `postext/worker` servida per una CDN no pot engegar el fitxer `layout.worker.js` que té al costat. `createLayoutWorker()` ho resol:

- **esm.sh, sense opcions.** Quan `postext/worker` mateix s'ha carregat des d'esm.sh (la URL del seu mòdul té la forma `https://esm.sh/postext@1.5.0/es2022/worker.mjs`), el client engega l'entrada corresponent, `https://esm.sh/postext@1.5.0/worker/entry`, a través d'un mòdul blob d'una línia, del mateix origen, que la importa. El mateix val per a les importacions que afegeixen `?deps=`, `?external=` o `?alias=`, i per a la forma `https://esm.sh/*postext@1.5.0/worker`. El worker rep sempre la compilació normal d'aquesta versió, perquè un worker no té *import map* amb què resoldre dependències externes.
- **Qualsevol altre servidor, amb `url`.** Les altres CDN, com jsDelivr (`/+esm`) o unpkg, no es detecten. `createLayoutWorker({ url })` engega el mòdul d'entrada del worker que hi ha a `url`: directament si és del mateix origen, i a través del mateix embolcall blob si és d'un altre. Aquest servidor ha de permetre peticions d'altres orígens (CORS).
- **Amb un empaquetador no canvia res.** Amb Vite, webpack o Next.js, continua cridant `createLayoutWorker()` sense opcions: ells emeten el worker com un fragment més de la teva aplicació.

```js
import { createLayoutWorker } from 'https://esm.sh/postext/worker';

const layout = createLayoutWorker();
const face = async (weight, style) => ({
  family: 'EB Garamond',
  weight,
  style,
  buffer: await (await fetch(`https://cdn.jsdelivr.net/npm/@fontsource/eb-garamond@5/files/eb-garamond-latin-${weight}-${style}.woff2`)).arrayBuffer(),
});
await layout.registerFonts(await Promise.all([face(400, 'normal'), face(700, 'normal'), face(400, 'italic')]));
const doc = await layout.build({ markdown }, { bodyText: { fontFamily: 'EB Garamond' } });
```

**Un worker no veu les fonts de la pàgina.** Té el seu propi conjunt de fonts, que només conté les variants enviades amb `registerFonts` i les fonts instal·lades al sistema. Quan una construcció compon text en una família que el worker no troba, aquest text es mesura amb una font de reserva, així que els seus talls de línia no coincidiran amb els de la pàgina. El client imprimeix llavors un avís a la consola per família (`"EB Garamond" is not available inside the layout worker…`) i enumera les famílies a `BuildStats.missingFonts`, que rep el callback `onStats` de `build`. El mateix document inclou aquestes variants com a avisos de contingut `fontFallback`.

`handle.prepareFonts(content, config, options)` executa [`prepareFonts`](#carregar-les-fonts-abans-de-compondre) a la pàgina i després envia al worker els fitxers de cada variant trobada que conté el registre de fonts (els fitxers del resolutor, les variants d'un paquet, les regles `@font-face` llegibles de la pàgina), i d'aquests, només els trams que contenen caràcters del document. Quan arriben variants al worker, aquest descarta només les mesures d'aquelles famílies, a més de la seva memòria cau de documents acabats.

Les variants també poden arribar al worker després d'una composició: un pes que les pàgines resulten necessitar, un altre tram `unicode-range` d'un tall, un fitxer pujat de nou amb el mateix nom de família. La composició següent hi mesura. El canvas d'un worker no ho faria tot sol: a Chrome resol una font la primera vegada que se li assigna una declaració abreujada de font i no torna a mirar el conjunt de fonts per a aquella declaració, de manera que el text conservaria les amplades de la variant que va respondre primer. Per això el worker repeteix el nom de la família a les declaracions que assigna quan una variant d'aquesta família ha arribat tard (`Geist, Geist`): una altra llista de famílies per al canvas, la mateixa font i les mateixes amplades. Els documents que retorna conserven les cadenes de font tal com les escriu el motor, i un worker que té les variants abans de la primera composició assigna cada declaració tal com és.

### Recollir els bytes de les fonts (Fontsource / Google Fonts)

`registerFonts` pren bytes de font en brut. El fil principal és el lloc adequat per obtenir-los, perquè una memòria cau centralitzada permet que diverses instàncies del worker comparteixin els mateixos bytes.

`collectFontPayloadsForFamilies` del Sandbox (`packages/postext-sandbox/src/controls/fontLoader.ts`) és una implementació de referència. El que fa:

1. Consulta `https://api.fontsource.org/v1/fonts/{id-de-familia}` per saber quins pesos i estils té la família.
2. Llegeix els subconjunts de la família i el seu `unicode-range` al seu paquet de jsDelivr (`@fontsource/{id-de-familia}@5/400.css`), una vegada per família. Els fitxers es demanen després a la versió exacta des de la qual es va servir aquest full d'estils (`x-jsd-version` de jsDelivr), de manera que una família no arriba mai de dues versions del seu paquet.
3. Baixa tots els fitxers de la rodona, la negreta i les seves cursives de cada família (`files/{id-de-familia}-{subconjunt}-{pes}-{estil}.woff2`); `collectFontPayloadsForConfig(config, markdown)` pren, en canvi, els pesos i estils que demana una configuració. Són fitxers estàtics, els que incrusta el PDF, de manera que el worker mesura amb allò que el PDF dibuixa. Un fitxer variable dona altres avanços entre dos dels seus màsters, i una línia que se'n desvia una fracció de píxel es pot tallar en un altre lloc.
4. Retorna un `FontPayload[]` on `buffer` és un `ArrayBuffer` nou a cada crida, cosa important perquè `registerFonts` transfereix el buffer i deixa inutilitzada la còpia de qui l'envia.

Els fitxers d'un tall van en l'ordre en què els declara un pen del Receptari (un exemple de CodePen), `latin` primer i els propis de l'escriptura al final (`arabic`, els trams numerats d'una família xinesa o japonesa), perquè el fitxer afegit en darrer lloc respon per un caràcter que tenen dos fitxers. Una família de la qual Fontsource no té fitxers es llegeix del full d'estils CSS2 de Google, que només retorna WOFF2 a User-Agents amb aspecte de navegador.

Combina-ho amb `getConfigFontFamilies(config)` per obtenir la llista de famílies que renderitzarà una `PostextConfig` concreta (cos, encapçalaments, vinyetes de llistes, números de llistes ordenades).

### Cancel·lació cooperativa dins del motor

Si controles `buildDocument` tu mateix (per exemple, dins d'un worker personalitzat), la composició ofereix un hook `shouldCancel` que pots fer servir directament:

```ts
import { buildDocument, BuildCancelledError } from 'postext';

let superseded = false;
try {
  const vdt = buildDocument(content, config, cache, {
    shouldCancel: () => superseded,
  });
} catch (err) {
  if (err instanceof BuildCancelledError) return; // un build més nou ha pres el relleu
  throw err;
}
```

`shouldCancel` s'invoca una vegada per cada bloc de nivell superior durant la col·locació. El hook és cooperatiu a propòsit: no pot aturar a mitja línia la crida de maquetació de Pretext, però manté la cancel·lació prou fina (mil·lisegons) perquè un usuari que escriu de pressa no hagi d'esperar mai una construcció obsoleta.

### Exportar PDF des del worker

El generador de PDF pren un `VDTDocument` ja acabat i el converteix en bytes PDF. **No** torna a executar la composició. Això vol dir que el flux recomanat per al PDF al navegador encaixa perfectament amb el worker: construeix el VDT al worker (fora del fil principal, cancel·lable, reutilitzant la memòria cau), i després crida `renderToPdf` al fil principal sobre aquest mateix VDT.

```ts
import type { LayoutWorkerHandle } from 'postext/worker';
import { renderToPdf } from 'postext-pdf';
import type { PostextConfig } from 'postext';
import { createPdfFontProvider } from './pdfFontProvider';

const fontProvider = createPdfFontProvider();

export async function exportPdf(
  layout: LayoutWorkerHandle,
  markdown: string,
  config: PostextConfig,
): Promise<Uint8Array> {
  // 1. Construeix el VDT al worker — la UI continua responent durant les passades de composició.
  const vdt = await layout.build({ markdown }, config);

  // 2. Rasteritza a PDF al fil principal. renderToPdf és ràpid un cop existeix el VDT
  //    perquè recorre coordenades precalculades, no torna a mesurar text.
  return renderToPdf(vdt, {
    fontProvider,
    // La config `pdfGeneration` de `vdt.config` es respecta automàticament.
  });
}
```

Si ja tens un worker per a la previsualització en directe, reutilitza'l per a l'exportació en lloc d'engegar-ne un altre: gràcies a la memòria cau de mesures del worker, una exportació a PDF després d'una previsualització en pantalla gairebé no costa res.

En un llibre llarg, escriure el PDF mateix també porta segons; `postext-pdf/worker` executa aquest pas en un worker propi (consulta [Renderitzar el PDF en un worker](/ca/docs/configuration-pdf-output#renderitzar-el-pdf-en-un-worker)).

### Quan fer servir el worker i quan no

Fes servir el worker per a:

- **Previsualitzacions en directe, editors i entorns de proves.** Qualsevol situació en què el document es torna a maquetar cada vegada que l'usuari hi escriu.
- **Visors HTML que es redimensionen** i tornen a executar la composició a cada canvi del `ResizeObserver`.
- **Exportació a PDF des del navegador** des d'una interfície que ja té previsualització en directe: reutilitza el worker existent per aprofitar la memòria cau de mesures.
- **Diverses pestanyes de previsualització** que necessiten el mateix VDT (les previsualitzacions Canvas / HTML / PDF del Sandbox comparteixen un worker per cada muntatge).

Salta-te'l per a:

- **Generació al servidor**: Node no té el `FontFaceSet` del navegador, i de tota manera el fil és teu.
- **Exportacions puntuals aïllades** (una línia d'ordres, un script d'exportació sense interfície, una Cloud Function), on no hi ha cap interfície interactiva que es pugui bloquejar. Cridar `buildDocument` directament és més simple i evita el cost de la transferència inicial de fonts.
