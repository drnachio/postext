# Uso programmatico: file PDF


## Generare PDF

L’output PDF vive in un pacchetto separato, **`postext-pdf`**, così che le integrazioni solo web non paghino il costo di `pdf-lib` e `@pdf-lib/fontkit`. Il backend PDF non rimisura il testo: usa esattamente lo stesso `VDTDocument` che passeresti a `renderToCanvas` o `renderToHtml` e traduce le sue coordinate in pixel in punti PDF. Per questo i tre output concordano sempre su a capo, altezze delle colonne e collocazione delle risorse.

> **Nel browser, costruisci il VDT tramite il [Web Worker](/it/docs/configuration-programmatic-usage#eseguire-limpaginazione-in-un-web-worker).** `renderToPdf` in sé è veloce una volta che il VDT esiste: la parte costosa è la pipeline di impaginazione che lo ha prodotto. Eseguire quella pipeline nel worker mantiene reattiva l’interfaccia e permette a un’esportazione PDF di riutilizzare la stessa cache delle misure che l’anteprima dal vivo ha già riempito. Vedi [Guidare l’esportazione PDF dal worker](/it/docs/configuration-programmatic-usage#guidare-lesportazione-pdf-dal-worker) per il flusso consigliato. Gli esempi sul thread principale qui sotto sono il riferimento per *che cosa significano gli argomenti*: per il codice dell’interfaccia, costruisci prima il VDT nel worker e chiama direttamente solo `renderToPdf`.

### Installazione

```bash
npm install postext postext-pdf
```

`postext` è una peer dependency di `postext-pdf`. Ogni release di `postext-pdf` richiede il `postext` con cui è stata pubblicata, o uno successivo della stessa major (il suo intervallo peer è un intervallo `^` su quella versione: `^1.5.0` per la 1.5.0), perché importa funzioni di supporto che `postext` ha aggiunto in quella release. Aggiorna i due pacchetti insieme e, su una CDN, fissali alla stessa versione.

### API pubblica

Il pacchetto espone un unico punto di ingresso e una manciata di tipi:

- **`renderToPdf(doc, options): Promise<Uint8Array>`**: prende un `VDTDocument` (o i capitoli di un libro come array di documenti) e restituisce i byte grezzi del PDF.
- **`PdfFontProvider`**: la firma della callback `(family, weight, style, request?) => Promise<Uint8Array | Uint8Array[]>` che `renderToPdf` usa per chiedere i byte di un font quando deve incorporare una nuova combinazione di famiglia, peso e stile. `request.codePoints` contiene i caratteri che le pagine compongono in quel font; la risposta è un file, o più file che insieme formano il font (vedi [Font cinesi, giapponesi e coreani](#font-cinesi-giapponesi-e-coreani)).
- **`declaredFontFile(bytes, { unicodeRange?, order? }): PdfFontFile`**: un file di font che registra come la pagina lo ha dichiarato: l’`unicode-range` della sua regola `@font-face` e la sua posizione nell’ordine di dichiarazione. Un `PdfFontFile` è un `Uint8Array` con queste due proprietà facoltative (vedi [Font cinesi, giapponesi e coreani](#font-cinesi-giapponesi-e-coreani)). Da postext-pdf 1.30.
- **`RenderToPdfOptions`**: `{ fontProvider, forms?, resourceBytes?, previewBytes?, outlines?, accessible?, colorSpace?, pageNegative?, characterGrid?, baselineGrid?, onProgress?, onWarning?, rasterizeSvg?, harfbuzzWasm?, print?, outputProfile?, profileBaseUrl?, date? }`. `forms` stabilisce come i campi dei moduli scrivono i numeri (valuta, il lato in cui va, separatori) e il font in cui mostrano i valori (`font`; vedi [Campi dei moduli](#campi-dei-moduli)). `outlines`, `accessible` e `colorSpace` ricadono sul `pdfGeneration` del documento quando sono omessi (vedi [Generazione del PDF (configurazione)](/it/docs/configuration-fonts-colors-viewers#generazione-del-pdf-configurazione)). `resourceBytes` è descritto in [Byte delle risorse e master di stampa](#byte-delle-risorse-e-master-di-stampa); `onWarning` in [Quali font vengono chiesti al provider](#quali-font-vengono-chiesti-al-provider) e in [Avvisi nel documento](/it/docs/configuration-programmatic-usage#avvisi-nel-documento). `characterGrid: true` stampa la griglia che `cjk.grid.show` disegna sullo schermo e che altrimenti il PDF tralascia (vedi [Griglia di caratteri](/it/docs/configuration-east-asian#griglia-di-caratteri)). `harfbuzzWasm` indica da dove caricare `harfbuzz.wasm` di HarfBuzz (un URL, relativo alla pagina, o i byte del file) per un documento con testo da destra a sinistra o con lettere legate; se è omesso, postext-pdf prova la copia accanto al proprio modulo, poi la stessa release di harfbuzzjs da jsDelivr ed esm.sh. `print` prende le impostazioni di produzione per la stampa (standard PDF/X, profilo di output, nero, preflight), con ripiego sul `print` del documento; con uno standard PDF/X, o con `colorSpace: 'cmyk'`, ogni colore viene separato tramite il profilo ICC di output, i cui byte sono dati da `outputProfile` (altrimenti viene scaricato da `profileBaseUrl`, per impostazione predefinita la copia sulla CDN di npm della cartella `icc/` di postext). `date` (un `Date`, un istante in millisecondi o una stringa di data, come il `mtime` di `createBundle`) è la data di creazione e di modifica del file e, in un file PDF/X, le date del suo pacchetto XMP e l’origine del suo identificatore di documento: lo stesso documento prodotto due volte con la stessa `date` dà gli stessi byte. Se è omessa, il file riporta l’ora della chiamata. Una data non valida solleva un’eccezione.
- **`PdfWarning`**: un problema non bloccante segnalato tramite `onWarning`; si distingue per `kind`: `'fontFallback'` (`PdfFontFallbackWarning`), un font sostituito da un’altra variante della sua famiglia; `'missingGlyph'` (`PdfMissingGlyphWarning`), caratteri per cui nessun file di un font ha un glifo; `'variableFontDefaultInstance'` (`PdfVariableFontWarning`), un font variabile chiesto a un peso diverso dalla sua istanza predefinita; `'cffEmbeddedWhole'` (`PdfCffEmbeddedWholeWarning`), un font CFF di oltre 2 MB incorporato per intero; `'complexShapingUnavailable'` (`PdfComplexShapingWarning`), testo da destra a sinistra o con lettere legate disegnato senza HarfBuzz, che non è stato possibile caricare (`reason` elenca dove è stato cercato), per cui i segni dell’arabo sono fuori posto; `'outputProfileUnavailable'` (`PdfPrintWarning`), un rendering CMYK il cui profilo di output non si è potuto caricare, convertito con la formula semplificata; `'pageNegativeIgnored'` (`PdfPrintWarning`), il negativo della pagina escluso da un file PDF/X-1a; `'spotTintsExhausted'` (`PdfPrintWarning`), un render che ha esaurito i codici per le tinte distinte degli inchiostri piatti (circa 25 milioni) e ha stampato le restanti in quadricromia; `'spotInkRenamed'` (`PdfPrintWarning`), un inchiostro la cui lastra viene scritta con un altro nome (vedi [Tinte piatte](#tinte-piatte)); `'imageProfileUnavailable'` (`PdfPrintWarning`), il profilo assegnato alle immagini RGB non si è potuto caricare e sono stati usati i loro profili; `'pictureOriginalUnreadable'` (`PdfPrintWarning`), un originale TIFF o Photoshop che non si è potuto decodificare, stampato dalla sua anteprima (`previewBytes`) o come segnaposto; `'plateMixesApproximated'` e `'artworkOffPlates'` (`PdfPrintWarning`), un lavoro su poche lastre (`print.plates`) che ha esaurito i codici e ha composto i colori restanti come la miscela già codificata più vicina, o che ha collocato una pagina PDF o un'immagine non decodificabile con i propri inchiostri; oppure `'missingImage'`, un’immagine senza byte disegnata come segnaposto (segnalato solo a un `onWarning` che passi tu; gli avvisi sui font, in sua assenza, vanno a `console.warn`).
- **`inspectPrintMaster(bytes): Promise<PrintMasterReport>`**: legge la prima pagina di un master di stampa PDF e segnala i font che usa senza incorporarli (`nonEmbeddedFonts`), se dipinge in RGB (`rgb`) e se usa la trasparenza (`transparency`), per il [preflight](/it/docs/configuration-pdf-output#preflight).
- **`inspectPrintPdf(bytes): Promise<PrintPdfReport>`**: rilegge un PDF finito come farebbe il preflight di una tipografia, tutte le pagine: la versione e il numero di pagine, l’identificazione PDF/X e l’intento di output (e se il profilo è incorporato), il formato rifilato e l’abbondanza minima, le pagine con un altro formato, senza TrimBox o con un riquadro di pagina che non è fatto di quattro numeri (`malformedBoxPages`, letto come mancante), i font (`fonts`: nome, incorporato o no, tipo; un font usato sia incorporato sia non incorporato compare una volta per ciascun modo), in cosa dipinge (CMYK, grigio, tinte piatte per nome, registro, e RGB diviso in `deviceRgb`, senza profilo, e `iccRgb`, con profilo, ciascuno in pittura `vector` o in `images`), trasparenze, sovrastampa, annotazioni, un modulo interattivo e se è taggato. Oltre alle pagine legge gli aspetti delle annotazioni, i campi e le risorse predefinite del modulo, i pattern, i glifi Type 3 e le immagini inline. Legge ciò che dice il file, non ciò che chiedeva la configurazione, e non legge la risoluzione delle immagini, l’inchiostro totale, i filetti troppo sottili né il trapping. Percorre le pagine come `inspectPrintMaster`, che segnala anche l’RGB in sfumature, pattern e glifi Type 3.
- **`decompressWoff2(bytes): Uint8Array`**: funzione di supporto che trasforma un file WOFF2 in byte TTF, il formato che `pdf-lib` può incorporare direttamente.
- **`createPdfWorker(options?)`**, da `postext-pdf/worker`: lo stesso rendering in un Web Worker; vedi [Generare il PDF in un worker](#generare-il-pdf-in-un-worker).

### Esempio minimo

```ts
import { buildDocument } from 'postext';
import { renderToPdf } from 'postext-pdf';

const vdt = buildDocument(
  { markdown: '# Chapter One\n\nThe story begins here…' },
  {
    page: { sizePreset: '17x24' },
    layout: { layoutType: 'double' },
    bodyText: { fontFamily: 'EB Garamond', fontSize: { value: 9, unit: 'pt' } }, // 9 pt overrides the 8 pt default
  },
);

const pdfBytes = await renderToPdf(vdt, {
  fontProvider: async (family, weight, style) => {
    // Return TTF bytes for this family/weight/style.
    // See the "Font provider" section below for a real implementation.
    const res = await fetch(`/fonts/${family}-${weight}${style === 'italic' ? 'i' : ''}.ttf`);
    return new Uint8Array(await res.arrayBuffer());
  },
});

// `pdfBytes` is a Uint8Array — save, download, or stream it.
const blob = new Blob([pdfBytes], { type: 'application/pdf' });
const url = URL.createObjectURL(blob);
window.open(url);
```

### Perché un provider di font?

`pdf-lib` incorpora nel PDF file di font veri: i font installati nel browser non sono disponibili al momento del rendering, e un font che hai caricato solo per la misurazione a schermo non basta, da solo, a produrre un PDF autonomo. `renderToPdf` scorre le pagine alla ricerca di ogni font che usano (uno per combinazione `family|weight|style`; vedi [Quali font vengono chiesti al provider](#quali-font-vengono-chiesti-al-provider)) e chiama il tuo provider una volta per ogni combinazione distinta. Il provider restituisce un `Uint8Array` di byte **TTF o OTF**, o un elenco di essi per un font servito in più file (vedi [Font cinesi, giapponesi e coreani](#font-cinesi-giapponesi-e-coreani)); `pdf-lib` crea un sottoinsieme dei contorni TrueType e incorpora per intero i file CFF (`.otf`). Un font CFF viene dichiarato come tale, cioè come font `CIDFontType0` con il programma CFF in `FontFile3` (`CIDFontType0C`), che `pdffonts` elenca come `CID Type 0C` e che il preflight di stampa si aspetta. Un font CFF con chiavi CID (Source Han, i file `.otf` di Noto CJK) mantiene la dichiarazione TrueType, perché la sua numerazione dei glifi non corrisponde a quella con cui è scritto il testo; per la stampa usa le versioni TrueType di queste famiglie. I font a cui il provider risponde con lo stesso file, come una variante regular che fa le veci del grassetto che manca a una famiglia, condividono un unico font incorporato. Un font che alla fine nessuna pagina usa, come il font del testo di una figura SVG quando la figura è disegnata come immagine, viene lasciato fuori dal file.

**Usa font statici per ogni peso, non un unico font variabile.** Google Fonts serve spesso un solo WOFF2 variabile per famiglia, che copre l’intero asse dei pesi. `pdf-lib` può incorporare da un file variabile solo l’istanza predefinita, quindi un paragrafo in grassetto uscirebbe con il peso regular. Fontsource pubblica file WOFF2 statici per ogni peso che risolvono il problema in modo pulito: è lo schema che usa la Sandbox. Un file variabile chiesto a un peso diverso dalla sua istanza predefinita viene segnalato con un avviso `variableFontDefaultInstance`.

**Ogni parola del testo finisce dove l’ha messa l’impaginazione.** Nei paragrafi, nelle voci di elenco, nelle citazioni, nei riquadri e nel resto del testo che scorre, ogni parola comincia nella posizione misurata dal VDT, quindi una differenza tra le larghezze del browser e quelle del font incorporato non si accumula mai lungo una riga. Una riga senza formattazione in linea viene disegnata come un unico oggetto di testo che sposta la penna tra le parole; le righe giustificate, quelle centrate e quelle con formattazione vengono disegnate parola per parola. Un carattere per cui il font non ha glifo, che il browser ha misurato in un altro font e che il PDF disegna come il riquadro del glifo mancante del font, non sposta nessuna delle parole che lo seguono, e viene segnalato una volta per font con un avviso `missingGlyph`. Uno spazio che manca al font, come uno spazio unificatore stretto o uno spazio cifra, prende la larghezza che gli ha dato il browser, e i caratteri invisibili come il word joiner e lo spazio a larghezza zero non vengono disegnati. Un trattino unificatore (U+2011) che manca al font viene disegnato con il trattino del font (U+2010), o con il suo trattino-meno quando non ha nemmeno il trattino, come lo mostra il browser; Open Sans e Outfit, tra gli altri, non hanno né l’uno né l’altro. Nessuno dei due casi conta come glifo mancante. Ci sono due eccezioni. Una riga con lettere da destra a sinistra viene comunque disegnata come un’unica sequenza (vedi [Lingue e scritture](/it/docs/configuration-language#lingue-e-scritture)). Il testo collocato dalla grafica (testatine e piè di pagina, aperture, titoli dei riquadri e altri elementi grafici) viene composto con le larghezze proprie del font incorporato, quindi lì un glifo che manca al font sposta comunque il resto della riga.

### Quali font vengono chiesti al provider

`renderToPdf` percorre le pagine nello stesso modo in cui le disegna e chiede al provider solo i font che disegnano:

- il font regular di un blocco che compone almeno una riga, e il grassetto, corsivo o grassetto corsivo di ogni sequenza composta effettivamente in quel modo;
- le sequenze dei chip, i segni degli elenchi e il testo degli slot della grafica (testatine, numeri di pagina, fasce di apertura e di parte);
- il testo di didascalie, note e celle di tabella di ogni risorsa;
- i font indicati dal `<text>` di una figura SVG, quando la figura è incorporata. Una famiglia che il provider non riesce a fornire affatto passa alla famiglia successiva dell’elenco `font-family` dell’SVG.

Così a una famiglia dei titoli mai composta in corsivo non viene mai chiesto il corsivo, e una figura senza nota non ha mai bisogno dei font delle note.

Quando il provider rifiuta un font, il rendering continua. Al suo posto viene incorporato un altro font della stessa famiglia, e viene segnalato un `PdfWarning`. Il sostituto è il primo font che si carica, provando i nove pesi standard (da 100 a 900) nell’ordine usato dalla selezione dei font del CSS, che è anche il font che il browser mostra nell’anteprima:

1. prima lo stesso stile. Per un peso da 400 a 500, vengono prima i pesi fino a 500, poi quelli più leggeri dal più vicino in giù, poi quelli più pesanti da 600 in su. Per un peso sotto 400, vengono prima i pesi più leggeri, dal più vicino in giù, poi quelli più pesanti. Per un peso sopra 500, vengono prima i pesi più pesanti, poi quelli più leggeri;
2. poi l’altro stile, corsivo per il tondo e tondo per il corsivo, al peso richiesto e agli altri pesi nello stesso ordine.

Una famiglia senza corsivi compone quindi in tondo le sue sequenze in corsivo, una famiglia che fornisce solo 400 e 700 prende un 600 come 700, e una famiglia che fornisce una sola variante compone tutto in quella. Al provider viene chiesto un font alla volta, in quell’ordine, e mai due volte lo stesso font, quindi un font che nessuno usa non viene mai incorporato. A una famiglia che il provider non riesce a servire affatto vengono chiesti tutti e 18 quei font prima che il rendering fallisca.

```ts
const bytes = await renderToPdf(doc, {
  fontProvider,
  onWarning: (w) => {
    // { kind: 'fontFallback', family: 'Oswald', weight: 700, style: 'italic',
    //   fallback: { weight: 700, style: 'normal' }, reason: '…', message: '…' }
    console.info(w.message);
  },
});
```

Senza `onWarning`, il messaggio va a `console.warn`. Il testo mantiene le sue posizioni, che vengono dal VDT e sono state misurate con i font che aveva il browser, quindi un sostituto con larghezze diverse può apparire troppo stretto o troppo largo. Fornisci il font vero per correggerlo. Un rendering fallisce ancora (`postext-pdf: failed to load font(s): …`) solo quando il provider non riesce a fornire nessun font di una famiglia a un peso standard, né in tondo né in corsivo.

### Provider di font per il browser (Fontsource + WOFF2)

La Sandbox include `createPdfFontProvider()` (`packages/postext-sandbox/src/viewport/pdf/pdfFontProvider.ts`), che puoi copiare in qualsiasi app per browser. L’essenziale:

```ts
import type { PdfFontProvider } from 'postext-pdf';
import { decompressWoff2 } from 'postext-pdf';

const bytesCache = new Map<string, Promise<Uint8Array>>();

function fontsourceId(family: string): string {
  return family.toLowerCase().replace(/\s+/g, '-');
}

function fontsourceWoff2Url(
  family: string,
  weight: number,
  style: 'normal' | 'italic',
): string {
  const id = fontsourceId(family);
  return `https://cdn.jsdelivr.net/npm/@fontsource/${id}@5/files/${id}-latin-${weight}-${style}.woff2`;
}

export function createPdfFontProvider(): PdfFontProvider {
  return async (family, weight, style) => {
    const key = `${family}|${weight}|${style}`;
    const cached = bytesCache.get(key);
    if (cached) return cached;

    const promise = (async (): Promise<Uint8Array> => {
      const url = fontsourceWoff2Url(family, weight, style);
      const res = await fetch(url, { mode: 'cors' });
      if (!res.ok) throw new Error(`font fetch failed: ${res.status} ${url}`);
      // pdf-lib needs TTF bytes, so decompress the WOFF2 wrapper client-side.
      return decompressWoff2(new Uint8Array(await res.arrayBuffer()));
    })();

    bytesCache.set(key, promise);
    return promise;
  };
}
```

Una versione per la produzione dovrebbe anche:

- **Interrogare i pesi disponibili** (tramite `https://api.fontsource.org/v1/fonts/{id}`) e arrotondare il peso richiesto a quello più vicino che la famiglia fornisce davvero, così una richiesta di `weight: 600` per una famiglia che ha solo `{400, 700}` va comunque a buon fine.
- **Ripiegare dal corsivo al tondo** quando una famiglia non ha una variante corsiva per il peso richiesto, invece di far fallire tutto il rendering.
- **Riutilizzare la cache tra un rendering e l’altro** (tieni `bytesCache` a livello di modulo, non per chiamata) così rigenerare il PDF dopo una modifica della configurazione non costa praticamente nulla.

### Font cinesi, giapponesi e coreani

Un font CJK non arriva come un unico file piccolo. Fontsource fornisce Noto Serif SC come un centinaio di file per peso, ognuno con una parte dei caratteri e dichiarato nel foglio di stile della famiglia con il suo `unicode-range` (`@fontsource/noto-serif-sc/400.css`); il browser scarica i file toccati dal testo di una pagina. Il file `latin` che scarica il provider qui sopra non contiene alcun carattere Han, e i sottoinsiemi con nome sono incompleti: `chinese-simplified` di Noto Serif SC non ha 釵, e `chinese-traditional` di Noto Serif TC non ha nessuno dei segni a larghezza piena （），！？：；.

Per questo un provider può fornire un font in più file. `renderToPdf` gli passa i caratteri che le pagine compongono in quel font (`request.codePoints`), raccolti da ogni capitolo prima di disegnare qualsiasi cosa, e il provider restituisce i file che li contengono, nell’ordine in cui il browser li consulta. Ogni file viene incorporato come sottoinsieme a sé e ogni carattere viene disegnato dal primo file che ha un glifo per esso: un capitolo che tocca 60 porzioni incorpora 60 piccoli sottoinsiemi. A un font chiesto di nuovo, per esempio per il testo di una figura SVG, vengono chiesti solo i caratteri che mancano ai suoi file. Un provider che restituisce un solo `Uint8Array` funziona come prima. Il provider della Sandbox legge il foglio di stile di Fontsource del peso e dello stile e scarica i file i cui intervalli contengono il testo; il nucleo:

```ts
import type { PdfFontProvider } from 'postext-pdf';
import { decompressWoff2 } from 'postext-pdf';

type Slice = { url: string; ranges: Array<[number, number]> };

async function fontsourceSlices(family: string, weight: number, style: 'normal' | 'italic'): Promise<Slice[]> {
  const id = family.toLowerCase().replace(/\s+/g, '-');
  const cssUrl = `https://cdn.jsdelivr.net/npm/@fontsource/${id}@5/${weight}${style === 'italic' ? '-italic' : ''}.css`;
  const css = await (await fetch(cssUrl)).text();
  return [...css.matchAll(/@font-face\s*{([^}]*)}/g)].map(([, rule]) => ({
    url: new URL(/url\(\.?\/?([^)]+\.woff2)\)/.exec(rule)![1], cssUrl).href,
    ranges: /unicode-range:\s*([^;]+);/.exec(rule)![1].split(',').map((part) => {
      const [lo, hi = lo] = part.trim().slice(2).split('-');
      return [parseInt(lo, 16), parseInt(hi, 16)] as [number, number];
    }),
  }));
}

export const sliceFontProvider: PdfFontProvider = async (family, weight, style, request) => {
  // Where ranges overlap, the browser tries the last rule first.
  const slices = (await fontsourceSlices(family, weight, style)).reverse();
  const picked = new Set<Slice>();
  for (const cp of request?.codePoints ?? []) {
    const slice = slices.find((s) => s.ranges.some(([lo, hi]) => cp >= lo && cp <= hi));
    if (slice) picked.add(slice);
  }
  if (picked.size === 0) picked.add(slices[0]!);
  return Promise.all(slices.filter((s) => picked.has(s)).map(async (s) =>
    decompressWoff2(new Uint8Array(await (await fetch(s.url)).arrayBuffer()))));
};
```

Una famiglia latina passa per lo stesso codice: un testo inglese riceve solo il suo file `latin`, uno ceco riceve `latin` e `latin-ext`.

Un browser non si ferma al primo file con un glifo. Compone un carattere nel file dichiarato per ultimo tra quelli il cui `unicode-range` lo contiene, e i file di una famiglia si sovrappongono: Fontsource ripete le lettere ASCII di Noto Serif JP nel suo file `latin` e nelle sue porzioni numerate. Due caratteri composti in due file diversi non hanno crenatura tra loro, quindi è il file a decidere la larghezza: Chrome 154 compone `Shift_JIS` largo 4,25 em con le porzioni dichiarate dopo `latin`, mentre il solo file `latin`, che applica la crenatura a `t_` e `_J`, lo compone largo 4,32 em. Da postext-pdf 1.30 un provider può indicare come la pagina ha dichiarato ogni file: `declaredFontFile(bytes, { unicodeRange, order })` restituisce gli stessi byte con l’`unicode-range` della regola del file, come lo scrive il CSS, e la posizione di quella regola tra le regole del font, un numero qualsiasi che cresce con l’ordine di dichiarazione (il più grande è dichiarato per ultimo).

```ts
import { declaredFontFile } from 'postext-pdf';

declaredFontFile(bytes, { unicodeRange: 'U+0000-00FF,U+0131,U+0152-0153', order: 0 });
```

Quando i file di un font riportano i loro intervalli, in un documento modellato nella propria lingua ([`bodyText.shapingLanguage: 'document'`](/it/docs/configuration-text#testo-corrente), il valore predefinito), un carattere viene disegnato dal file dichiarato per ultimo il cui intervallo lo contiene e che ha un glifo per esso, come un browser sceglie tra le regole `@font-face`, e una lettera e i suoi segni combinanti restano in un solo file. Un carattere che nessun intervallo contiene viene disegnato dal primo file con un glifo. I file semplici, e ogni file in un documento con `'host'`, vengono letti nell’ordine dato, come prima, quindi un provider che descrive i suoi file elenca comunque per primo quello dichiarato per ultimo. A un font descritto in questo modo vengono chiesti di nuovo tutti i caratteri che non gli erano stati chiesti prima, perché un file dichiarato più tardi potrebbe contenerli. Il provider della Sandbox descrive i suoi file.

I caratteri per cui nessun file del font ha un glifo vengono disegnati con il glifo `.notdef` del font (un riquadro vuoto nella maggior parte dei font), e `renderToPdf` li segnala una volta per font dopo aver disegnato le pagine:

```ts
// { kind: 'missingGlyph', family: 'Noto Serif TC', weight: 400, style: 'normal',
//   characters: ['，', '！', '？'], message: '…' }
```

La Sandbox li elenca, insieme ai due avvisi qui sotto, nel suo pannello Verifiche dopo ogni PDF che genera. Quando il libro, le sue impostazioni o le sue risorse cambiano, vengono contrassegnati come provenienti da un PDF precedente finché il successivo non li sostituisce; aprire un altro libro li cancella.

- **Il grassetto richiede un file statico per peso.** Fontsource serve ogni peso di Noto Serif SC e TC come file statici separati, quindi nella Sandbox il grassetto funziona. I file di Google Fonts (`NotoSerifSC[wght].ttf`, 25 MB) sono font variabili: pdf-lib ne incorpora l’istanza predefinita, quindi un font 700 viene stampato a 400, e `renderToPdf` lo segnala come `variableFontDefaultInstance`. Per un pacchetto, ricava con fontTools un’istanza statica per peso (`fonttools varLib.instancer NotoSerifSC[wght].ttf wght=700`) e riducila ai caratteri del libro con `pyftsubset`.
- **Usa le versioni TrueType.** Source Han Serif e i file `.otf` di Noto Serif CJK hanno contorni CFF, che postext-pdf incorpora per intero, da 8 a 25 MB per peso; un font CFF di oltre 2 MB viene segnalato come `cffEmbeddedWhole`. Delle versioni TrueType (Google Fonts, Fontsource) si incorpora solo il sottoinsieme dei glifi usati. Per il giapponese, Noto Serif JP e Noto Sans JP (Google Fonts, o le porzioni numerate di Fontsource), Shippori Mincho, Zen Old Mincho e BIZ UDMincho sono in TrueType; Source Han Serif JP e i file `.otf` `JP` di Noto Serif CJK sono CFF.
- **Forme giapponesi di un font pan-CJK.** Uno stesso code point, che sia un carattere Han, un segno di punteggiatura o una virgoletta, può essere disegnato in un modo in Giappone e in un altro in Cina, e un font pan-CJK (Source Han, Noto CJK) li contiene entrambi. Il PDF modella un documento giapponese (`locale: 'ja'`), e un isolamento in giapponese (`:ltr[…]{lang=ja}`) in qualsiasi documento, con il sistema linguistico OpenType `JAN `, così la funzione `locl` del font stampa le forme giapponesi che il canvas e l’HTML stampano tramite `lang`. Un isolamento in un’altra lingua dentro un libro giapponese viene modellato con le forme di quella lingua (quelle predefinite del font per il cinese con `'host'`) e taggato come `Span` con il suo `/Lang`. Con [`bodyText.shapingLanguage: 'document'`](/it/docs/configuration-text#testo-corrente), il valore predefinito da postext 1.30, ogni documento e ogni isolamento è modellato nella propria lingua (`ZHS` per il cinese semplificato), come l’ha misurato l’impaginazione; con `'host'`, i documenti cinesi e gli altri sono modellati con le forme predefinite del font, come prima. Un font fatto per il giapponese come Noto Serif JP ha forme predefinite giapponesi; compone comunque le “ ” del testo giapponese nelle loro forme `JAN `.

Un carattere che manca in una famiglia non viene preso da un’altra: Noto Serif TC non prende in prestito da Noto Serif SC. Risolvi la copertura quando costruisci i file dei font; la vetrina 红楼梦 copia dal font SC i glifi che mancano ai suoi sottoinsiemi TC.

### Provider di font lato server (Node, file locali)

In Node puoi saltare del tutto il passaggio WOFF2 e leggere i file TTF/OTF dal disco:

```ts
import { readFile } from 'node:fs/promises';
import { join } from 'node:path';
import type { PdfFontProvider } from 'postext-pdf';

const FONT_DIR = '/path/to/fonts';

function filename(family: string, weight: number, style: 'normal' | 'italic'): string {
  const slug = family.replace(/\s+/g, '');
  const styleSuffix = style === 'italic' ? 'Italic' : '';
  const weightName =
    weight >= 700 ? 'Bold'
    : weight >= 600 ? 'SemiBold'
    : weight >= 500 ? 'Medium'
    : weight >= 300 ? 'Light'
    : 'Regular';
  return `${slug}-${weightName}${styleSuffix}.ttf`;
}

export const localFontProvider: PdfFontProvider = async (family, weight, style) => {
  const buf = await readFile(join(FONT_DIR, filename(family, weight, style)));
  return new Uint8Array(buf);
};
```

### Byte delle risorse e master di stampa

`resourceBytes(fileId)` restituisce i byte grezzi di un’immagine, e il backend ne riconosce il formato:

- PNG, JPEG, GIF e WebP vengono incorporati come immagini;
- il markup SVG viene disegnato come tracciati vettoriali, con il suo `text` composto come testo vero nei font incorporati del documento, oppure rasterizzato a 600 dpi nel browser quando usa funzioni fuori dal sottoinsieme vettoriale. Uno `<style>` che contiene solo regole `@font-face` (font incorporati da un autore) viene saltato e mantiene vettoriale la figura (da postext-pdf 1.25); qualsiasi altro foglio di stile la trasforma in un raster, disegnato con i font indicati dal suo testo, inseriti in linea tramite `fontProvider` (a meno che `diagramStyle.inlineFonts` o lo `svg.inlineFonts` della risorsa non sia `false`);
- i TIFF e i documenti Photoshop (PSD, PSB) si stampano dai propri pixel: scala di grigi, RGB o CMYK, a 8 o 16 bit, con il profilo ICC e la risoluzione che contengono. Uno CMYK mantiene i propri inchiostri così come sono; la scala di grigi e l’RGB seguono `print.imageColor`. Di un documento Photoshop si legge l’immagine composita che salva con «Massimizza compatibilità»; i TIFF con compressione JPEG non vengono letti;
- di un PDF viene incorporata così com’è la prima pagina, come form XObject.

Ogni immagine viene memorizzata nel file una sola volta, per quante volte venga disegnata. Un SVG disegnato come tracciati vettoriali diventa un form XObject che ogni pagina disegna, quindi una cornice o un logo nella grafica della pagina di un documento di trenta pagine viene scritto una volta, non trenta; ogni pagina in più aggiunge qualche centinaio di byte. Fino a postext-pdf 1.4 ogni pagina portava la propria copia dei tracciati.

Una figura SVG può indicare un **master di stampa** in `svg.pdfFileId`: un PDF di una sola pagina della stessa figura, di solito l’originale da cui l’SVG è stato esportato. `renderToPdf` chiede prima a `resourceBytes` i byte dell’id del master. Incorpora quella pagina al posto dell’SVG, con i suoi font, sfumature e spazi colore intatti, ovunque l’SVG venga disegnato: come figura, come immagine di una cella di tabella (`TableCell.image`), come immagine grafica o come icona di un riquadro (anche il suo `marker`). Il VDT riporta l’id del master in ognuno di questi usi (`svg.pdfFileId` sulla risorsa della figura, `pdfFileId` su un’immagine di cella e su un blocco di immagine grafica), così in un libro ogni capitolo riceve il master. I backend canvas e HTML continuano a disegnare l’SVG. Si usano invece i byte dell’SVG stesso in tre casi: il master manca, non è un PDF, oppure è attivo l’inchiostro unico (`diagramStyle.singleInk` ricolora solo il markup SVG).

```ts
const resources: Resource[] = [{
  id: 'map', typeId: 'figure', kind: 'svg', createdAt: 0, updatedAt: 0,
  svg: { fileId: 'map.svg', width: 800, height: 600, pdfFileId: 'map.pdf' },
}];
const files = new Map([['map.svg', svgBytes], ['map.pdf', masterPdfBytes]]);
const pdf = await renderToPdf(buildDocument({ markdown, resources }, config), {
  fontProvider,
  resourceBytes: (fileId) => files.get(fileId),
});
```

Un’applicazione host può anche restituire i byte del master per l’id dell’SVG stesso, come fa `bundleResourceBytes`; funzionano entrambi i modi.

Un browser non può mostrare un TIFF né un documento Photoshop, quindi una risorsa bitmap creata da uno di questi conserva due file: `bitmap.fileId` è un’anteprima PNG, che mostrano il canvas, l’HTML e l’EPUB, e `bitmap.printFileId` (con `printFormat: 'tiff' | 'psd'`) è l’originale. Un’applicazione host restituisce i byte dell’originale per `bitmap.fileId`, come fanno `bundleResourceBytes` e la Sandbox, e il PDF stampa da quello. Passa anche l'anteprima, come `previewBytes` (`bundlePreviewBytes` per un pacchetto): un originale che non si riesce a decodificare si stampa dalla sua anteprima, con un avviso `pictureOriginalUnreadable`, e senza anteprima resta un segnaposto. `decodePrintRaster(bytes)` e `rasterToRgba(raster)` di `postext` leggono l’originale e creano l’anteprima; la Sandbox la crea quando il file viene importato, e un pacchetto memorizza l’originale come `resources/<nome>.tif` o `.psd` accanto all’anteprima.

Un file di Adobe Illustrator salvato con «Crea file compatibile PDF» è un PDF, e può essere un master di stampa come qualsiasi altro (`.ai`). I suoi campioni sono le sue lastre: il preflight elenca quelle che la tabella degli inchiostri rinomina, quelle che nessun colore del libro definisce e, in un lavoro sulle proprie lastre (`print.plates`), quelle che il lavoro non stampa, perché un file collocato si stampa così com’è.

### Testo verticale nel PDF

Una pagina verticale (`layout.writingMode: 'vertical-rl'`) viene disegnata tramite un sistema di riferimento ruotato di un quarto di giro, come fa il canvas, e il suo testo è composto lungo la colonna:

- **I caratteri in piedi** sono mostrati tramite un secondo font Type0 dello stesso file incorporato: lo stesso CIDFont, le stesse larghezze e la stessa mappa ToUnicode, con `Encoding /Identity-V` (modo verticale). Una sequenza di caratteri è un unico oggetto di testo i cui glifi avanzano da soli di un em lungo la colonna (`DW2 [880 −1000]`), così i lettori selezionano ed estraggono una colonna come un’unica riga. I glifi sono modellati con le funzioni OpenType `vert` e `fwid`, che danno le loro forme verticali a parentesi, virgolette, segni di pausa della Cina continentale, ellissi e lineette; un carattere che sta già in piedi così com’è mantiene il suo glifo orizzontale. Niente del font viene incorporato due volte.
- **Le parole latine e i numeri lunghi** scorrono ruotate di lato con il font orizzontale; **un numero in una sola cella** sta in piedi, compresso trasversalmente fino a un em quando è più largo; un segno per cui il font non ha forma verticale viene ruotato o spostato, come sul canvas.
- **La spaziatura** tra i caratteri (tracking) è scritta come numeri `TJ`, che in modo verticale spostano la penna lungo la colonna.
- **Ogni riga verticale** è contrassegnata con un `/ActualText` del suo testo, così la copia e l’estrazione del testo la leggono come è scritta. `pdftotext` e pdf.js leggono le colonne dall’alto in basso, da destra a sinistra; pdf.js comincia una nuova riga a un numero composto in una sola cella.
- **Link, segnalibri e destinazioni** sono riportati sul foglio: un link su una riga verticale è un rettangolo alto e stretto, e un segnalibro apre la pagina in cima alla colonna del suo titolo.
- **Un PDF taggato** dichiara il modo di scrittura sul suo elemento `Document` (l’attributo di layout `WritingMode /TbRl`, che ogni elemento eredita); la validazione PDF/UA-1 (veraPDF) passa su un capitolo verticale.
- **Visualizzatori:** Acrobat, Anteprima, Chrome (PDFium), pdf.js e Poppler visualizzano correttamente i font verticali. Un libro rilegato a destra (`page.binding`) chiede anche ai visualizzatori di disporre le sue doppie pagine da destra a sinistra (`/Direction /R2L`, `/PageLayout /TwoPageRight`); Acrobat e Foxit lo seguono, Chrome no.

Un capitolo di 43 pagine composto in Noto Serif TC (i caratteri del libro, TrueType) pesa circa 820 KB, di cui la maggior parte sono i due sottoinsiemi di font.

### Campi dei moduli

Un chip con l’attributo `field` è un campo di modulo compilabile (AcroForm). Il chip si compone e dipinge il suo riquadro come qualsiasi chip: lo stile ne dà l’aspetto e la larghezza minima (`minWidth`), le sue parole sono il valore predefinito del campo. Il PDF mette un campo interattivo sopra il riquadro; un nome usato due volte è un solo campo con due widget.

```md
Quantità :chip[ ]{style="field" field="pos.a.qty" kind="number"}
Prezzo :chip[120]{style="field" field="pos.a.price" format="currency"}
Totale :chip[ ]{style="field" field="pos.a.total" format="currency" calc="product(pos.a.qty, pos.a.price)"}
Servizio :chip[ ]{style="box" field="pkg.a" kind="checkbox" on="1"}
Totale dell’ordine :chip[ ]{style="field" field="order.total" format="currency" calc="sum(pos.a.total, product(pkg.a, 161.75))"}
Taglia :chip[M]{style="field" field="size" kind="choice" options="S|M|L"}
```

- `kind`: `text` (predefinito), `number`, `checkbox`, `choice` (con `options`, separate da `|`). Un chip con `format` o `calc` e senza `kind` è un campo numerico.
- `on` (una casella di controllo): il nome dello stato attivo della casella, cioè il valore che leggono i suoi script quando è spuntata. Con `on="1"` una casella spuntata conta 1 in un calcolo, così `product(pkg.a, 161.75)` aggiunge un prezzo fisso quando la casella è spuntata. Il valore predefinito è `Yes`, che un calcolo conta 0.
- `format`: `currency`, `decimal` (due decimali), `integer`. Viene scritto con `AFNumber_Format` e `AFNumber_Keystroke` di Acrobat, con i separatori della lingua del documento (`1.234,56` in tedesco e in italiano) a meno che `RenderToPdfOptions.forms.separatorStyle` non indichi altro; la valuta è `forms.currency` (predefinita `€`), prima del numero a meno che `forms.currencyBefore` non sia `false`. Un valore predefinito viene disegnato già formattato.
- `calc`: `sum(…)`, `product(…)`, `min(…)`, `max(…)` o `avg(…)`. Gli argomenti sono altri campi indicati per nome, numeri (con il punto come separatore decimale, `161.75`) e calcoli annidati: `sum(pos.a.total, pos.b.total, product(pkg.a, 161.75))`. Un calcolo solo su campi viene scritto come `AFSimple_Calculate`. Uno con numeri o calcoli annidati diventa un breve script Calculate a sé, che legge ogni campo allo stesso modo (`AFMakeNumber` del suo valore; ciò che non è un numero conta 0) e arrotonda il risultato a sei decimali. Un campo calcolato è di sola lettura, e l’ordine di calcolo tiene conto di tutti i campi che legge, anche quelli dei calcoli annidati. Producono un avviso `formField`: un calcolo che legge un campo sconosciuto (conta 0), un ciclo, un nome usato per due tipi e una casella di controllo in un calcolo il cui valore `on` non è un numero (conta sempre 0).
- `readonly`, `required`, `multiline`, `tooltip` fanno quello che dice il nome.

Un campo mostra il suo valore, e ciò che vi si digita, nel font del suo chip (`forms.font: 'chip'`, il predefinito) o in un font del documento indicato da `forms.font` (`{ family, weight?, style? }`, chiesto al `fontProvider` come qualsiasi altro). Quel font viene incorporato **per intero**, non come sottoinsieme, perché a un sottoinsieme mancherebbero i glifi dei caratteri digitati in seguito; viene incorporato una sola volta, quanti che siano i campi che lo usano, nominato nelle risorse predefinite del modulo (`/DR`) e nell’aspetto predefinito di ogni campo (`/DA`), e i valori predefiniti vengono disegnati con esso. Un font intero aggiunge al PDF il suo file completo (un font latino da testo pesa in genere 50–300 KB, uno CJK diversi MB), oltre al sottoinsieme usato dal testo delle pagine. Il provider può rispondere con TrueType, OpenType o WOFF2 (decompresso prima dell’incorporazione). I campi ripiegano su Helvetica, con un avviso `formField`, quando il font non si può incorporare per intero: la licenza lo vieta (`fsType` della tabella OS/2 ristretto o solo bitmap), il provider lo fornisce in più file (un font suddiviso) oppure il formato è WOFF o una raccolta. Con `forms.font: 'helvetica'` si usa Helvetica senza incorporare nulla. Alcuni visualizzatori (Anteprima di macOS, per esempio) disegnano il testo mentre lo si digita in un font proprio; il valore è lo stesso.

Acrobat, Foxit, pdf.js (Firefox) e la maggior parte dei visualizzatori eseguono questi script. Uno standard di stampa (PDF/X) non ammette campi interattivi: lì i valori sono dipinti come testo, e quello di un campo numerico come lo mostra il modulo (formattato, allineato alla fine del riquadro entro il `paddingX` dello stile, nel colore del chip).

Il canvas dipinge un campo numerico allo stesso modo, così l’anteprima corrisponde al PDF: passa a `renderPageToCanvas` (o a `renderPage`, `renderToCanvas`) la stessa opzione `forms` che passi a `renderToPdf`; in entrambi i casi i separatori derivano per impostazione predefinita dal `locale` del documento (altrimenti dalla sua lingua di sillabazione). Una sola regola scrive i numeri ovunque, e postext la esporta per altri generatori di output: `formNumberStyle(forms, lang)` risolve le opzioni, `formatFieldNumber(value, format, style)` formatta un valore (undefined per un testo che non è un numero) e `numberFieldText(field, words, style)` restituisce ciò che mostra un campo numerico dipinto. La lista di visualizzazione porta il campo sul segmento del chip (`inline.field`, con `sizePx` e `padPx` dell’impaginazione).

Un libro può tenere queste opzioni nella sua configurazione: `pdfGeneration.forms` accetta gli stessi campi (`currency`, `currencyBefore`, `separatorStyle`, `font`). `renderToPdf` e il canvas prendono ciascuno prima dalla propria opzione `forms`, poi dal `pdfGeneration.forms` del primo documento, infine dai valori predefiniti. Non cambia l’impaginazione, solo come i campi vengono scritti e dipinti. Nel Sandbox è il gruppo **Campi modulo** della sezione PDF.

```ts
pdfGeneration: {
  forms: { currency: 'USD', currencyBefore: true, separatorStyle: 0, font: { family: 'Lora', weight: 400 } },
}
```

**Da esm.sh in un browser**, importa `https://esm.sh/postext-pdf?bundle`. La build predefinita di pdf-lib su esm.sh mette le classi delle annotazioni in un modulo a parte, e pdf-lib rifiuta allora il widget di ogni campo: il PDF conserva le caselle, ma perde formati, calcoli e attributi, con un avviso `formField` per campo. `?bundle` compila pdf-lib in un solo modulo e lascia fuori `postext`, condiviso con la pagina. Un bundler (Vite, webpack, Next.js) e Node non ne sono toccati.

L’esportazione IDML scrive gli stessi campi come campi di modulo di InDesign (vedi [Uso programmatico › Pacchetti InDesign](/it/docs/configuration-programmatic-usage#pacchetti-indesign-postext-idml)).

### Link nel PDF

Le parole di un link Markdown (vedi [Formato del documento › Link](/it/docs/document-format-inline#link)) diventano annotazioni di link URI, una per ogni sequenza di parole collegate su una riga. Ognuna copre il riquadro della riga e non ha bordo. In un rendering accessibile, ogni sequenza è un elemento `Link` il cui `/Contents` è il suo testo. Vengono collegate solo le destinazioni assolute `http:`, `https:`, `mailto:`, `tel:` e `ftp:`, perché un URL relativo non ha una base dentro un PDF. I caratteri fuori dall’ASCII stampabile vengono codificati con la codifica percentuale. I rimandi `:ref` e le righe dell’indice mantengono i loro link dentro il documento.

### Esempio completo per il browser: costruire, generare, scaricare

Mettendo tutto insieme: costruisci il VDT, producine il PDF e avvia un download dal browser:

```tsx
import { buildDocument, createMeasurementCache } from 'postext';
import { renderToPdf } from 'postext-pdf';
import { createPdfFontProvider } from './pdfFontProvider';

const fontProvider = createPdfFontProvider();

export async function downloadPdf(markdown: string, config: PostextConfig) {
  const cache = createMeasurementCache();
  const vdt = buildDocument({ markdown }, config, cache);

  const bytes = await renderToPdf(vdt, { fontProvider });

  const blob = new Blob([bytes.slice().buffer], { type: 'application/pdf' });
  const url = URL.createObjectURL(blob);
  const a = document.createElement('a');
  a.href = url;
  a.download = 'document.pdf';
  document.body.appendChild(a);
  a.click();
  a.remove();
  setTimeout(() => URL.revokeObjectURL(url), 1000);
}
```

**Importante:** chiama `ensureConfigFontsLoaded(config)` (o un equivalente) *prima* di `buildDocument` quando la tua configurazione fa riferimento a web font. L’impaginazione viene misurata con le metriche che il browser ha in quel momento per quella famiglia: se il font vero non è ancora arrivato, il VDT viene misurato con un font di ripiego e il PDF non corrisponderà all’output canvas o HTML. La Sandbox lo fa esplicitamente prima di ogni rendering (vedi `packages/postext-sandbox/src/viewport/pdf/PdfViewport.tsx`).

### Esempio dal vivo: un PDF nel browser

Il flusso completo qui sopra, in esecuzione nel browser: il pen importa `postext` e `postext-pdf` da una CDN, carica i web font, costruisce il documento, incorpora le varianti di Fontsource tramite il provider di font e passa i byte a un link che apre il file in una nuova scheda e a un link di download. Il PDF che ottieni ha gli stessi a capo dell’output canvas e HTML, veri font incorporati e segnalibri di struttura.

### Generare il PDF in un worker

`postext-pdf/worker` sposta `renderToPdf` fuori dal thread principale. Il worker scrive il testo, le figure vettoriali, l’albero della struttura e il file stesso. Due compiti richiedono la pagina, quindi il worker li chiede al thread principale: scaricare i font e rasterizzare un SVG tramite un `<img>`. Per un libro di centinaia di pagine, il rendering richiede secondi che altrimenti bloccherebbero la pagina; per poche pagine, chiamare direttamente `renderToPdf` è più semplice.

```ts
import { createPdfWorker } from 'postext-pdf/worker';

const pdfWorker = createPdfWorker();
const bytes = await pdfWorker.render(docs, {
  fontProvider,                                     // runs on this thread
  resourceBytes: new Map([['map.svg', svgBytes]]),  // a Map; its buffers move to the worker
  onProgress: ({ phase, pages, totalPages }) => showProgress(phase, pages, totalPages),
  onWarning: (w) => console.info(w.message),
});
pdfWorker.dispose();
```

- `render(docs, options)` prende un documento o l’array dei documenti dei capitoli di un libro. Accetta le opzioni di `renderToPdf`, con due differenze. `resourceBytes` (e `previewBytes`) è una `Map<string, Uint8Array>` i cui buffer vengono trasferiti, quindi passa copie dei byte che vuoi conservare. `rasterizeSvg`, se è fornito, viene eseguito sul thread principale; per impostazione predefinita se ne occupano l’`Image` e il canvas della pagina stessa.
- Un handle produce un documento alla volta. `dispose()` termina il worker e rifiuta qualsiasi rendering ancora in sospeso con un `AbortError` (`DOMException`), da trattare come un annullamento. Se il provider risponde con un font o un’immagine dopo `dispose()`, la risposta viene scartata.
- `inspect(bytes)` rilegge un PDF finito nel worker (`inspectPrintPdf`) e si risolve col suo rapporto, o con `undefined` se i byte non si leggono come PDF. I byte vengono copiati, quindi i tuoi restano utilizzabili. Non si legge nulla se non lo chiami.
- `createPdfWorker({ worker })` accetta un `Worker` creato da te, per gli strumenti di build che controllano gli URL dei worker. Quel worker deve eseguire `postext-pdf/worker/entry`.

**Da una CDN.** Per impostazione predefinita lo script del worker viene caricato dall’URL del pacchetto stesso (`new URL('./pdf.worker.js', import.meta.url)`). Una pagina su un’altra origine potrebbe non riuscire ad avviarlo: importato da `esm.sh`, `createPdfWorker()` solleva `Failed to construct 'Worker': Script at 'https://esm.sh/postext-pdf@…/pdf.worker.js' cannot be accessed from origin …`. Avvia invece un module worker della stessa origine che importa l’entry (se fissi una versione, fissa la stessa in entrambi gli URL):

```js
import { createPdfWorker } from 'https://esm.sh/postext-pdf/worker';

const entry = URL.createObjectURL(new Blob(
  ["import 'https://esm.sh/postext-pdf/worker/entry';"],
  { type: 'text/javascript' },
));
const pdfWorker = createPdfWorker({ worker: new Worker(entry, { type: 'module' }) });
```

Il worker di impaginazione di `postext/worker` non ne ha bisogno: `createLayoutWorker()` avvia il proprio punto d’ingresso da esm.sh senza opzioni, e da qualsiasi altro server con la sua opzione `url` (vedi [Caricare il worker da una CDN](/it/docs/configuration-programmatic-usage#caricare-il-worker-da-una-cdn)).

### PDF pronti per la stampa

Per i flussi di lavoro di stampa in produzione, regola queste opzioni di configurazione prima del rendering:

- **`page.cutLines.enabled: true`**: aggiunge l’abbondanza e i segni di taglio attorno al formato rifilato, e dà a ogni pagina un TrimBox e un BleedBox. Vedi [Segni di taglio](/it/docs/configuration-page-layout#segni-di-taglio).
- **`print: { standard: 'pdfx4', outputProfile: 'fogra51' }`** (o `'pdfx1a'`): un file PDF/X con l’output intent, l’identificazione e i box di pagina che una tipografia controlla; ogni colore e ogni immagine RGB separati tramite il profilo ICC, sovrastampa del 100 % K e grandi aree nere in nero ricco. Vedi [Produzione di stampa (configurazione)](/it/docs/configuration-fonts-colors-viewers#produzione-di-stampa-configurazione).
- **`colorSpace: 'cmyk'`** (o `pdfGeneration: { forceColorSpace: true, colorSpace: 'cmyk' }`): la stessa separazione senza l’identificazione PDF/X (i segni di taglio sono sempre in colore di registro). I master di stampa PDF vengono incorporati così come sono.
- **`page.dpi: 300`**: i px per pollice dell’impaginazione: una bitmap senza una risoluzione propria viene stampata a questa risoluzione alla sua dimensione naturale. Il [preflight](/it/docs/configuration-pdf-output#preflight) segnala le immagini sotto i 300 ppi alla dimensione di stampa.
- **`ColorValue.cmyk`**: un colore definito in CMYK viene stampato con i suoi valori esatti.
- **`{ pageNegative: true }`** in `RenderToPdfOptions`: inverte l’area del formato rifilato con un metodo di fusione Differenza (i segni di taglio restano non invertiti). Utile per i controlli di preflight sul testo scuro su fondo chiaro.
- **`print.dieLine`**: la linea di fustella di un libro con fustelle, tracciata su una lastra propria che la macchina non inchiostra mai (`Die` per impostazione predefinita, in un gruppo di contenuto opzionale fuori da PDF/X-1a). Vedi [La linea di fustella nel PDF](/it/docs/special-inks-die-cuts#la-linea-di-fustella-nel-pdf).

### Tinte piatte

Una tinta piatta (un Pantone, un inchiostro aziendale, una vernice) si stampa su una propria lastra. Un colore con `model: 'spot'` porta il suo inchiostro in `ColorValue.spot`: `name` è il nome della lastra come lo conosce lo stampatore, `cmyk` l’aspetto dell’inchiostro al 100 % (il sostituto che il PDF dà a chi non ha l’inchiostro), `tint` la forza in percentuale (100 per impostazione predefinita), `overprint` fa sovrastampare l’inchiostro su ciò che sta sotto invece di risparmiarlo, come una vernice, e `finish` dice che cos’è un inchiostro speciale: metallizzato, lamina a caldo, fluorescente, bianco coprente o vernice. `hex` è la sua resa a schermo. [Inchiostri speciali e fustelle](/it/docs/special-inks-die-cuts#finiture) spiega come si stampa e come si vede ogni finitura.

Un PDF CMYK o PDF/X scrive ogni inchiostro come uno spazio colore `Separation` con il suo nome, e dipinge ogni colore di quell’inchiostro alla sua tinta: i colori con lo stesso `name` condividono una lastra. Questo copre i lavori abituali: due colori (il nero e una tinta piatta), la quadricromia con alcuni elementi in una tinta piatta, e una vernice sovrastampata su aree scelte. Quando `diagramStyle.singleInk` usa una tinta piatta, i diagrammi SVG si stampano in tinte di quella lastra. Un PDF RGB e lo schermo dipingono l’`hex` del colore.

**Tinte piatte dentro un SVG.** Vedi [Come funziona l’inchiostro unico](/it/docs/configuration-resources#come-funziona-linchiostro-unico).

```ts
colorPalette: [
  { id: 'brand', name: 'Brand', value: { hex: '#1f3f99', model: 'spot', spot: { name: 'PANTONE 286 C', cmyk: { c: 100, m: 66, y: 0, k: 2 } } } },
  { id: 'brand-40', name: 'Brand 40 %', value: { hex: '#a5b6dd', model: 'spot', spot: { name: 'PANTONE 286 C', cmyk: { c: 100, m: 66, y: 0, k: 2 }, tint: 40 } } },
  { id: 'varnish', name: 'Varnish', value: { hex: '#f4f4ee', model: 'spot', spot: { name: 'Varnish', cmyk: { c: 0, m: 0, y: 10, k: 0 }, finish: { kind: 'varnish', sheen: 'gloss' } } } },
],
diagramStyle: { singleInk: true, inkColor: { hex: '#1f3f99', model: 'spot', paletteId: 'brand' } },
```

Il preflight conta una tinta piatta come un solo inchiostro, la tiene fuori dal limite di copertura ed elenca le tinte piatte del lavoro (`spotInks`), compresi gli inchiostri che nominano le immagini SVG. Avverte quando uno stesso inchiostro è definito due volte con valori diversi (`spotInkConflict`; il PDF usa il primo), quando un SVG nomina un inchiostro che nessun colore della tavolozza né alcuna voce della tabella degli inchiostri con `cmyk` definisce (`spotInkUndefined`; si stampa su una lastra propria, con il CMYK del colore dell’SVG come sostituto, una lastra per nome), quando il PDF deve scrivere il nome di una lastra in un altro modo (`spotInkName`, vedi sotto), e quando due nomi di lastra differiscono solo per maiuscole o spazi (`spotInkSimilar`: `PANTONE 185 C` e `Pantone  185 C` sarebbero due lastre). `preflightDocument` sa quali inchiostri nomina un SVG da `svgInks(fileId)`, una funzione che restituisce i nomi che `svgSpotInks(markup)` trova nel file; il pannello **Verifiche** del Sandbox e `postext check` gliela passano.

**Nomi delle lastre.** Il nome si scrive così come lo si digita: gli accenti, i simboli e `#` arrivano al PDF in UTF-8 (`Rojo Médica` è `/Rojo#20M#C3#A9dica`), che è come lo leggono Acrobat, un RIP e il preflight dello stampatore. Un nome che una lastra non può portare si scrive con un altro: `All`, `None`, `Cyan`, `Magenta`, `Yellow` e `Black`, in maiuscolo o minuscolo, ricevono dopo di sé la parola ink (`All ink`); i caratteri di controllo si tolgono, e un nome oltre i 127 byte in UTF-8 si taglia tra due caratteri e finisce con un breve hash, così due nomi lunghi che cominciano allo stesso modo restano due lastre. Lo `spotInkName` del preflight dice il motivo (`problem`: `reserved`, `process`, `control` o `tooLong`) e il nome che il PDF scrive (`written`), e il render segnala ogni cambio tramite `onWarning` (`spotInkRenamed`). Per scegliere tu il nome, dai all’inchiostro un `pdfName` nella tabella degli inchiostri.

**Un inchiostro per colore.** Un render di stampa riconosce un colore dal suo hex a schermo, quindi due colori che fissano i propri valori di stampa (due inchiostri, oppure un inchiostro e un colore definito in CMYK) non possono condividerlo. Se lo condividono, il secondo passa all’hex libero più vicino, a un passo di distanza e invisibile a schermo, e ciascuno si stampa sulla propria lastra. Un semplice colore a schermo (`model: 'hex'`) con l’hex di una tinta piatta si stampa come quella tinta piatta; collegalo alla voce della tavolozza per renderlo esplicito. Il colore che si sposta cambia anche a schermo, di un passo (1/255) in un solo canale, prima il blu, in tutte le uscite (canvas, HTML, EPUB e PDF RGB). È molto al di sotto di ciò che l’occhio distingue, ed è il prezzo di un render di stampa che legge gli inchiostri dall’hex dipinto. La configurazione salvata non cambia.

#### La tabella degli inchiostri

`print.inks` dice come gli inchiostri del lavoro arrivano allo stampatore, comunque li chiamino i colori, gli SVG e i file importati. Un inchiostro che la tabella non elenca si stampa come lo definiscono i suoi colori.

```ts
interface PrintInk {
  name: string;                    // L’inchiostro come lo nomina spot.name o un SVG.
  aliases?: string[];              // Altri nomi dello stesso inchiostro: si stampano su questa lastra.
  pdfName?: string;                // Il nome della lastra nel PDF. Predefinito: name.
  output?: 'spot' | 'process';     // 'process' stampa l’inchiostro in CMYK, dal suo sostituto.
  cmyk?: CmykPercent;              // Il sostituto al 100 %, prevale su quello dei colori.
  overprint?: boolean;             // Prevale su quello dei colori.
  finish?: InkFinish;              // Metallizzato, lamina, fluorescente, bianco o vernice; prevale su quella dei colori.
}
```

Nomi e alias si confrontano ignorando le maiuscole e gli spazi ripetuti. Rinominare richiede una riga, per quanti colori usino l’inchiostro; un alias riunisce su una lastra i nomi che un campione del grafico, un SVG (`data-spot`, `icc-named-color`) o una tavolozza precedente davano allo stesso inchiostro; `output: 'process'` stampa un inchiostro in CMYK quando la macchina non ha un gruppo per esso, tutte le sue tinte comprese; e `finish` rende speciale un inchiostro da qualunque parte venga il suo nome, compreso un SVG o un file importato che nomina `Gold`.

Nel Sandbox la tabella si trova in **Grafica › Esportazione › Preparazione per la stampa › Tabella degli inchiostri**: una scheda per inchiostro con **Nome dell’inchiostro**, **Alias**, **Nome della lastra nel PDF**, **Si stampa come**, **CMYK alternativo**, **Sovrastampa**, **Finitura** e **Lucentezza**. **Inchiostri usati dai colori** elenca gli inchiostri dei colori del libro che mancano nella tabella, ciascuno con un pulsante che lo aggiunge.

```ts
print: {
  standard: 'pdfx4',
  inks: [
    { name: 'Azul corporativo', pdfName: 'PANTONE 286 C', aliases: ['Pantone 286C', 'Azul'] },
    { name: 'Varnish', output: 'process' },
  ],
},
```

#### Stampa a due inchiostri

`print.plates` nomina le lastre su cui si stampa il lavoro, e nient’altro viene stampato: un libro in nero e una tinta piatta, in due tinte piatte o solo in nero. Le lastre di quadricromia sono `Cyan`, `Magenta`, `Yellow` e `Black`; una lastra di tinta piatta si nomina come la nomina il PDF, o con un nome o un alias della tabella degli inchiostri.

```ts
interface PrintPlatesConfig {
  inks?: string[];                                // Le lastre. Vuoto: tutte, come sempre.
  images?: string[];                              // Le lastre delle immagini: una o due.
  curves?: Record<string, Array<[number, number]>>; // La curva di una lastra d’immagine: [tono, inchiostro] in percentuale.
}
```

- Un colore di un inchiostro che il lavoro stampa, o un colore CMYK di cui stampa i canali, viene impostato così com’è.
- Qualsiasi altro colore viene proiettato: si stampa come la miscela di una o due lastre il cui aspetto, attraverso il profilo di output, gli si avvicina di più. Una miscela di due inchiostri è uno spazio colore `DeviceN` nel PDF, e un grigio resta solo su `Black`. Il nero ricco viene scartato, a meno che il lavoro non stampi tutti e quattro gli inchiostri di quadricromia.
- Le immagini si stampano in monotono su una lastra, o in bicromia su due: il tono di ogni pixel (la sua luminosità) passa per la curva di ciascuna lastra. `images` è per impostazione predefinita `Black`, o la prima lastra quando il lavoro non stampa il nero. La curva di un monotono è una retta; una bicromia mette la sua prima lastra sulle ombre e la seconda sui mezzitoni. `curves` sostituisce l’una o l’altra.

```ts
print: {
  standard: 'pdfx4',
  plates: {
    inks: ['Black', 'PANTONE 286 C'],
    images: ['Black', 'PANTONE 286 C'],
    curves: { 'PANTONE 286 C': [[0, 0], [50, 35], [100, 70]] },
  },
},
```

Il preflight elenca le lastre del lavoro e ogni colore che la proiezione sposta. Una tinta piatta o un colore CMYK che il lavoro non stampa è un'informazione quando la sua miscela cade entro ΔE 6, e un avviso oltre o finché il profilo di uscita non è caricato (`offPlateInk`, `offPlateCmyk`); anche un colore di schermo che cade oltre ΔE 6 è un avviso (`offPlateColor`). Una lastra di tinta piatta che nessun colore e nessuna voce della tabella degli inchiostri definisce è un avviso: si stampa e appare nera nella prova. In un lavoro così l'originale di stampa di una figura viene messo da parte e il suo SVG è composto sulle lastre; una pagina PDF collocata, o un'immagine non decodificabile, mantiene i propri inchiostri e il rendering avverte (`artworkOffPlates`). Nel Sandbox le lastre si scelgono in Preparazione per la stampa → Lastre. Le sue anteprime e l'anteprima di stampa mostrano i colori come li definisce il libro, non come li stampano le lastre: guarda il PDF, dove Verifica per la stampa elenca gli inchiostri che usa.

### Colore delle immagini

Un’immagine viene separata a partire dai colori in cui è stata creata. `print.imageColor` dice come si leggono i suoi pixel:

```ts
interface PrintImageColorConfig {
  embeddedProfile?: 'use' | 'ignore';                  // A picture's own ICC profile. Default 'ignore'.
  assignedRgbProfile?: { name: string; fileId: string }; // Read every RGB picture through this .icc instead.
  grayDotGain?: 'profile' | 'none' | number;           // Greyscale pictures on black. Default 'none'.
  cmykProfile?: 'convert' | 'keep';                    // A CMYK picture of another press. Default 'keep'.
}
```

I valori predefiniti lasciano le immagini come le stampavano le versioni precedenti: ogni immagine RGB è letta come sRGB (`'ignore'`), le immagini in scala di grigi sono separate come le altre (`'none'`) e un’immagine CMYK conserva i suoi valori (`'keep'`). Ogni comportamento dell’elenco si attiva con il suo campo.

- **Il suo profilo.** Un PNG (`iCCP`) o un JPEG (`ICC_PROFILE`) che incorpora un profilo viene letto attraverso di esso, così una fotografia in Adobe RGB o Display P3 si separa come appare e non come se fosse sRGB. Un’immagine senza profilo, o con profilo sRGB, viene letta come sRGB, come finora. `'ignore'` legge tutte le immagini come sRGB.
- **Un profilo assegnato.** `assignedRgbProfile` indica un `.icc` salvato attraverso cui si legge ogni immagine RGB, qualunque profilo incorpori: per esempio, per un lotto di fotografie che hanno perso il loro. I suoi byte arrivano da `resourceBytes`; se mancano, si usano i profili delle immagini, con un avviso `imageProfileUnavailable`.
- **Mantenuta per il RIP.** In PDF/X-4 con `convertImages: false`, un’immagine con un profilo diverso da sRGB viene scritta nei suoi colori, marcata `ICCBased` con quel profilo, ed è il RIP della tipografia a convertirla.
- **Scala di grigi.** Un’immagine in scala di grigi (un PNG o un JPEG in grigio, o una con profilo di grigio) si stampa con il solo nero, mai come un grigio in quadricromia. I suoi toni, letti attraverso il suo profilo (altrimenti come li mostra lo schermo), vengono adattati alla macchina: `'profile'` attraverso il nero del profilo di output, la cui crescita del punto è già inclusa nella condizione; un numero è la crescita del punto della macchina al tono del 50 %, in percentuale (di solito tra 10 e 30), che viene invece compensata; `'none'` scrive i valori così come sono, come finora.

```ts
print: {
  standard: 'pdfx4',
  imageColor: { grayDotGain: 20 },
},
```

- **Un’immagine CMYK di un’altra macchina.** Un’immagine CMYK il cui profilo è un’altra condizione di stampa (una fotografia separata per SWOP o per carta da giornale in un libro per FOGRA) viene separata di nuovo per quella di output (`cmykProfile: 'convert'`), e il solo nero resta solo nero: un TIFF o un file Photoshop a partire dai suoi pixel; un JPEG CMYK, i cui pixel non vengono decodificati, viene marcato `ICCBased` con il suo profilo in PDF/X-4 perché lo converta il RIP, e passa così com’è in PDF/X-1a, che non ammette questa marcatura; lì il preflight lo segnala (`cmykImageForeign`) quando l’host gli fornisce il profilo dell’immagine (`imageProfile`). In PDF/X-4 con `convertImages: false`, un TIFF o un file Photoshop viene marcato allo stesso modo. `'keep'` stampa i valori di ogni immagine CMYK così come sono.

**Le impostazioni di una sola immagine.** Il `printColor` di una risorsa accetta gli stessi campi di `print.imageColor` del libro e li applica solo a quell’immagine: una fotografia il cui profilo va ignorato, un’altra letta attraverso un profilo assegnato, un’immagine in grigio con un’altra crescita del punto. Nella Sandbox, la scheda di un’immagine indica se viene letta attraverso il suo profilo («Colore in stampa»), come i suoi grigi si adattano alla macchina («Grigi in stampa») e quale profilo le è assegnato («Profilo assegnato», un file `.icc`); un pacchetto porta i profili assegnati, quello del libro e quelli delle immagini, nella sua cartella `profiles/`. Le impostazioni del libro sono in Preparazione per la stampa → Immagini.

```ts
{ id: 'archive-photo', kind: 'bitmap', bitmap: { fileId: 'photo.jpg', format: 'jpeg', width: 2400, height: 1600 },
  printColor: { embeddedProfile: 'ignore' } }
```


### Colori definiti in CMYK

Un colore scritto in CMYK mantiene i suoi valori esatti: `ColorValue.cmyk` (in percentuale) viene impostato così com’è in un rendering di stampa, e `hex` è la sua resa a schermo. Una voce della tavolozza definita in CMYK copre ogni colore collegato a essa.

```ts
colorPalette: [
  { id: 'brand', name: 'Brand', value: { hex: '#00a0e3', model: 'cmyk', cmyk: { c: 100, m: 0, y: 0, k: 0 } } },
],
```

### Colori in sovrastampa

Qualsiasi colore può andare in sovrastampa in un rendering di stampa: `overprint: true` su un `ColorValue` fa stampare tutto ciò che si disegna con esso (testo, filetti, riquadri, fondi) sopra ciò che sta sotto invece di risparmiarlo. Un colore di quadricromia si scrive così come si separa, sotto uno stato grafico di sovrastampa; una tinta piatta va in sovrastampa sulla lastra del suo inchiostro, anche dove lo stesso inchiostro in un altro colore va in risparmio. Un nero al 100 % K in sovrastampa mantiene il trattamento del nero: le grandi superfici escono comunque in nero ricco (`black.richBlack`). Un PDF RGB e lo schermo lo ignorano. Impostalo sulla voce della tavolozza perché vada in sovrastampa ogni colore collegato a essa, comprese le sue tinte; un colore collegato prende l’impostazione della voce e non ne ha una propria. La tavolozza di una parte o di una sezione la mantiene: anche il testo nel colore della parte va in sovrastampa.

```ts
colorPalette: [
  { id: 'title', name: 'Title', value: { hex: '#c00020', model: 'cmyk', cmyk: { c: 0, m: 100, y: 80, k: 10 }, overprint: true } },
],
```

Un rendering di stampa riconosce un colore dall’hex che la composizione dipinge, quindi un colore in sovrastampa non condivide mai l’hex con uno che va in risparmio. Quando coincidono, quello in sovrastampa si sposta di un passo (1/255 in un canale), come fanno le tinte piatte; il colore di una parte per una voce in sovrastampa si allontana allo stesso modo da qualsiasi colore del libro che va in risparmio. Un colore in sovrastampa che non deposita inchiostro (il bianco della carta, un inchiostro allo 0 %) scompare in stampa: il preflight lo segnala come critico (`overprintWhite`). Un rendering con più colori distinti dei codici di cui dispone (circa 25 milioni) manda in risparmio il resto e avvisa (`overprintsExhausted`). Nella Sandbox lo imposta l’interruttore «Sovrastampa in tipografia» del selettore di colore.

`preflightDocument(doc, options)` esegue le verifiche su un documento impaginato e restituisce una lista di problemi, ognuno con un `kind`, una `severity` (`'critical'`, `'warning'` o `'info'`), il `pageIndex` assoluto nel libro, il `rect` incriminato (px della pagina) e, quando l’elemento ce l’ha, il suo intervallo nella sorgente. I tipi sono `lowImageResolution`, `declaredPixelsMismatch`, `rgbImage`, `thinRule`, `smallProcessText`, `inkLimit`, `safeZone` e `nearTrim`. Senza un `transform` un neutro conta come un inchiostro e qualsiasi altro colore come tre, e la copertura non viene verificata; con un `transform`, i conteggi e la copertura sono esatti. La risoluzione di un’immagine si ricava dai pixel che la sua risorsa dichiara, o da quelli del file stesso quando `imageSize(fileId)` li fornisce (`bitmapInfo` sui byte, o l’immagine decodificata): una dichiarazione che si discosta dal file di più di un pixel viene segnalata una volta come `declaredPixelsMismatch`, un avviso quando dichiara più pixel di quanti ne abbia il file. `placedImageResolutions(doc, { resources, imageSize })` elenca ogni bitmap collocata con i suoi ppi effettivi, che il preflight sia attivo o no. Le etichette di una figura contano come testo per `smallProcessText`, `inkLimit` e `safeZone`.

```ts
import { bitmapInfo, outputTransform, parseIccProfile, preflightDocument, resolvePrintConfig } from 'postext';
import { inspectPrintMaster } from 'postext-pdf';

const print = resolvePrintConfig(config.print);
const transform = outputTransform(parseIccProfile(fogra51Bytes), { intent: print.renderingIntent });
const issues = preflightDocument(doc, {
  print,
  transform,
  resources,                                    // pixel sizes of the bitmaps
  imageSize: (fileId) => bitmapInfo(bytesOf(fileId)),  // the files' real pixels
  imageColor: (fileId) => colourOf(fileId),     // 'rgb' | 'cmyk' | 'gray', from the file
});
if (issues.some((i) => i.severity === 'critical')) process.exit(1);

const master = await inspectPrintMaster(masterBytes);
// => { nonEmbeddedFonts: ['Helvetica'], rgb: true, transparency: false }
```

### Implementazione di riferimento

Il componente `PdfViewport` della Sandbox (`packages/postext-sandbox/src/viewport/pdf/PdfViewport.tsx`) collega i pezzi descritti sopra in un’anteprima dal vivo con i pulsanti per rigenerare, scaricare e stampare, ed è un buon punto di partenza per qualsiasi integrazione PDF nel browser. Costruisce il VDT tramite il worker di impaginazione condiviso (vedi [Eseguire l’impaginazione in un Web Worker](/it/docs/configuration-programmatic-usage#eseguire-limpaginazione-in-un-web-worker)), così un clic su *Ricalcola* non blocca l’interfaccia mentre la pipeline è in esecuzione: il thread principale gestisce solo `renderToPdf` (che è già veloce una volta che il VDT esiste).
