# Utilisation programmatique : fichiers PDF


## Générer des PDF

La sortie PDF se trouve dans un paquet séparé, **`postext-pdf`**, afin que les intégrations purement web ne paient pas le coût de `pdf-lib` et de `@pdf-lib/fontkit`. Le moteur PDF ne remesure pas le texte : il consomme exactement le même `VDTDocument` que celui que vous passeriez à `renderToCanvas` ou à `renderToHtml`, et convertit ses coordonnées en pixels en points PDF. Les trois sorties s’accordent donc forcément sur les coupures de lignes, les hauteurs de colonnes et la position des ressources.

> **Dans le navigateur, construisez le VDT au moyen du [Web Worker](/fr/docs/configuration-programmatic-usage#mise-en-page-dans-un-web-worker).** `renderToPdf` est rapide une fois le VDT disponible : la partie coûteuse est le pipeline de mise en page qui l’a produit. Exécuter ce pipeline dans le worker garde l’interface réactive et permet à un export PDF de réutiliser le cache de mesures que l’aperçu en direct a déjà rempli. Voir [Piloter l’export PDF depuis le worker](/fr/docs/configuration-programmatic-usage#piloter-lexport-pdf-depuis-le-worker) pour la démarche recommandée. Les exemples sur le fil principal ci-dessous servent de référence pour *ce que signifient les arguments* : dans le code d’interface, construisez d’abord le VDT dans le worker et n’appelez directement que `renderToPdf`.

### Installation

```bash
npm install postext postext-pdf
```

`postext` est une dépendance de pair (peer dependency) de `postext-pdf`. Chaque version de `postext-pdf` a besoin du `postext` avec lequel elle est sortie, ou d’une version ultérieure de la même version majeure (sa plage de pair est `^` suivi de cette version, `^1.5.0` pour la 1.5.0), car elle importe des fonctions que `postext` a ajoutées dans cette version. Mettez les deux à jour ensemble et, sur un CDN, épinglez-les à la même version.

### API publique

Le paquet expose un seul point d’entrée et quelques types :

- **`renderToPdf(doc, options): Promise<Uint8Array>`** : prend un `VDTDocument` (ou les chapitres d’un livre sous forme de tableau de documents) et renvoie les octets bruts du PDF.
- **`PdfFontProvider`** : la signature de rappel `(family, weight, style, request?) => Promise<Uint8Array | Uint8Array[]>` que `renderToPdf` utilise pour demander les octets d’une police quand il doit incorporer une nouvelle combinaison famille/graisse/style. `request.codePoints` contient les caractères que les pages composent dans cette fonte ; la réponse est un fichier, ou plusieurs qui forment ensemble la fonte (voir [Polices chinoises, japonaises et coréennes](#polices-chinoises-japonaises-et-coréennes)).
- **`declaredFontFile(bytes, { unicodeRange?, order? }): PdfFontFile`** : un fichier de fonte qui indique comment la page l’a déclaré, c’est-à-dire l’`unicode-range` de sa règle `@font-face` et sa place dans l’ordre des déclarations. Un `PdfFontFile` est un `Uint8Array` doté de ces deux propriétés facultatives (voir [Polices chinoises, japonaises et coréennes](#polices-chinoises-japonaises-et-coréennes)). Depuis postext-pdf 1.30.
- **`RenderToPdfOptions`** : `{ fontProvider, forms?, resourceBytes?, previewBytes?, outlines?, accessible?, colorSpace?, pageNegative?, characterGrid?, baselineGrid?, onProgress?, onWarning?, rasterizeSvg?, harfbuzzWasm?, print?, outputProfile?, profileBaseUrl?, date? }`. `forms` règle la façon dont les champs de formulaire écrivent les nombres (devise, côté où elle se place, séparateurs) et la fonte dans laquelle ils affichent leurs valeurs (`font` ; voir [Champs de formulaire](#champs-de-formulaire)). Omis, `outlines`, `accessible` et `colorSpace` reprennent le `pdfGeneration` du document (voir [Génération PDF (configuration)](/fr/docs/configuration-fonts-colors-viewers#génération-pdf-configuration)). `resourceBytes` est décrit dans [Octets des ressources et originaux d’impression](#octets-des-ressources-et-originaux-dimpression) ; `onWarning` dans [Quelles fontes sont demandées au fournisseur](#quelles-fontes-sont-demandées-au-fournisseur) et dans [Avertissements dans le document](/fr/docs/configuration-programmatic-usage#avertissements-dans-le-document). `characterGrid: true` imprime la grille que `cjk.grid.show` dessine à l’écran et que le PDF omet sinon (voir [Grille de caractères](/fr/docs/configuration-east-asian#grille-de-caractères)). `harfbuzzWasm` indique où charger le `harfbuzz.wasm` de HarfBuzz (une URL, relative à la page, ou les octets du fichier) pour un document contenant du texte de droite à gauche ou à liaisons ; omis, c’est la copie placée à côté du module de postext-pdf, puis la même version de harfbuzzjs sur jsDelivr et esm.sh. `print` reçoit les réglages de production pour l’impression (norme PDF/X, profil de sortie, noir, contrôle en amont) et reprend sinon le `print` du document ; avec une norme PDF/X, ou `colorSpace: 'cmyk'`, chaque couleur est séparée au moyen du profil ICC de sortie, dont `outputProfile` fournit les octets (sinon il est téléchargé depuis `profileBaseUrl`, par défaut la copie du dossier `icc/` de postext sur le CDN de npm). `date` (une `Date`, un temps en millisecondes ou une chaîne de date, comme le `mtime` de `createBundle`) est la date de création et de modification du fichier et, dans un fichier PDF/X, la date de son paquet XMP et la source de son identifiant de document : le même document rendu deux fois avec une même `date` donne les mêmes octets. Sans elle, le fichier prend l’heure de l’appel. Une date invalide lève une exception.
- **`PdfWarning`** : un problème non bloquant signalé par `onWarning` ; distinguez-le par `kind` : `'fontFallback'` (`PdfFontFallbackWarning`), une fonte composée dans une autre coupe de sa famille ; `'missingGlyph'` (`PdfMissingGlyphWarning`), des caractères pour lesquels aucun fichier d’une fonte n’a de glyphe ; `'variableFontDefaultInstance'` (`PdfVariableFontWarning`), une police variable demandée à une graisse autre que son instance par défaut ; `'cffEmbeddedWhole'` (`PdfCffEmbeddedWholeWarning`), une fonte CFF de plus de 2 Mo incorporée en entier ; `'complexShapingUnavailable'` (`PdfComplexShapingWarning`), du texte de droite à gauche ou à liaisons dessiné sans HarfBuzz, qui n’a pas pu être chargé (`reason` liste où il a été cherché) : les signes diacritiques arabes sont alors mal placés ; `'outputProfileUnavailable'` (`PdfPrintWarning`), un rendu CMJN dont le profil de sortie n’a pas pu être chargé, converti avec la formule naïve ; `'pageNegativeIgnored'` (`PdfPrintWarning`), la page en négatif omise d’un fichier PDF/X-1a ; `'spotTintsExhausted'` (`PdfPrintWarning`), un rendu à court de codes pour des teintes de ton direct distinctes (quelque 25 millions), qui a imprimé le reste en quadrichromie ; `'spotInkRenamed'` (`PdfPrintWarning`), une encre dont la plaque est écrite sous un autre nom (voir [Tons directs](#tons-directs)) ; `'imageProfileUnavailable'` (`PdfPrintWarning`), le profil attribué aux images RVB n’a pas pu être chargé et leurs propres profils ont servi ; `'pictureOriginalUnreadable'` (`PdfPrintWarning`), un original TIFF ou Photoshop qui n’a pas pu être décodé, imprimé depuis son aperçu (`previewBytes`) ou comme espace réservé ; `'plateMixesApproximated'` et `'artworkOffPlates'` (`PdfPrintWarning`), un travail sur quelques plaques (`print.plates`) à court de codes, qui a composé les couleurs restantes comme le mélange déjà codé le plus proche, ou qui a placé une page PDF ou une image impossible à décoder avec leurs propres encres ; ou `'missingImage'`, une image sans octets dessinée sous forme d’emplacement vide (signalé uniquement à un `onWarning` que vous passez ; sans lui, les avertissements de polices vont à `console.warn`).
- **`inspectPrintMaster(bytes): Promise<PrintMasterReport>`** : lit la première page d’un original d’impression PDF et indique les polices qu’il utilise sans les incorporer (`nonEmbeddedFonts`), s’il peint en RVB (`rgb`) et s’il utilise de la transparence (`transparency`), pour le [contrôle en amont](/fr/docs/configuration-pdf-output#contrôle-en-amont).
- **`inspectPrintPdf(bytes): Promise<PrintPdfReport>`** : relit un PDF terminé comme le ferait le contrôle en amont d’un imprimeur, toutes ses pages : la version et le nombre de pages, l’identification PDF/X et le mode de sortie (et si son profil est incorporé), le format rogné et le plus petit fond perdu, les pages d’un autre format, sans TrimBox ou dont une boîte de page n’est pas faite de quatre nombres (`malformedBoxPages`, lue comme absente), les polices (`fonts` : nom, incorporée ou non, type ; une police employée à la fois incorporée et non incorporée figure une fois sous chaque forme), ce dans quoi il peint (CMJN, gris, tons directs par leur nom, repérage, et RVB séparé en `deviceRgb`, sans profil, et `iccRgb`, avec profil, chacun en peinture `vector` ou en `images`), la transparence, la surimpression, les annotations, un formulaire interactif et s’il est balisé. Outre les pages, il lit les apparences des annotations, les champs et les ressources par défaut du formulaire, les motifs, les glyphes Type 3 et les images en ligne. Il lit ce que dit le fichier, non ce que demandait la configuration, et ne lit ni la résolution des images, ni l’encrage total, ni les filets trop fins, ni le grossi-maigri (*trapping*). Il parcourt les pages comme `inspectPrintMaster`, qui signale aussi le RVB dans les dégradés, les motifs et les glyphes Type 3.
- **`decompressWoff2(bytes): Uint8Array`** : fonction utilitaire qui transforme un fichier WOFF2 en octets TTF, le format que `pdf-lib` sait incorporer directement.
- **`createPdfWorker(options?)`**, depuis `postext-pdf/worker` : le même rendu dans un Web Worker ; voir [Rendre le PDF dans un worker](#rendre-le-pdf-dans-un-worker).

### Exemple minimal

```ts
import { buildDocument } from 'postext';
import { renderToPdf } from 'postext-pdf';

const vdt = buildDocument(
  { markdown: '# Chapter One\n\nThe story begins here…' },
  {
    page: { sizePreset: '17x24' },
    layout: { layoutType: 'double' },
    bodyText: { fontFamily: 'EB Garamond', fontSize: { value: 9, unit: 'pt' } }, // 9 pt overrides the 8 pt default
  },
);

const pdfBytes = await renderToPdf(vdt, {
  fontProvider: async (family, weight, style) => {
    // Return TTF bytes for this family/weight/style.
    // See the "Font provider" section below for a real implementation.
    const res = await fetch(`/fonts/${family}-${weight}${style === 'italic' ? 'i' : ''}.ttf`);
    return new Uint8Array(await res.arrayBuffer());
  },
});

// `pdfBytes` is a Uint8Array — save, download, or stream it.
const blob = new Blob([pdfBytes], { type: 'application/pdf' });
const url = URL.createObjectURL(blob);
window.open(url);
```

### Pourquoi un fournisseur de polices ?

`pdf-lib` incorpore de vrais fichiers de polices dans le PDF : les polices installées dans le navigateur ne sont pas disponibles au moment du rendu, et une police chargée uniquement pour la mesure à l’écran ne suffit pas, à elle seule, à produire un PDF autonome. `renderToPdf` parcourt les pages à la recherche de chaque fonte qu’elles peignent (une par combinaison `family|weight|style` ; voir [Quelles fontes sont demandées au fournisseur](#quelles-fontes-sont-demandées-au-fournisseur)) et appelle votre fournisseur une fois par combinaison distincte. Le fournisseur renvoie un `Uint8Array` d’octets **TTF ou OTF**, ou une liste de ceux-ci pour une fonte servie en plusieurs fichiers (voir [Polices chinoises, japonaises et coréennes](#polices-chinoises-japonaises-et-coréennes)) ; `pdf-lib` réduit les fontes TrueType aux glyphes utilisés et incorpore les fichiers CFF (`.otf`) en entier. Une fonte CFF est déclarée comme telle, sous la forme d’une police `CIDFontType0` dont le programme CFF se trouve dans `FontFile3` (`CIDFontType0C`), que `pdffonts` liste comme `CID Type 0C` et qu’attendent les contrôles en amont des imprimeurs. Une fonte CFF à clés CID (Source Han, les fichiers `.otf` de Noto CJK) garde la déclaration TrueType, car sa numérotation des glyphes ne correspond pas à celle dans laquelle le texte est écrit ; pour l’impression, utilisez les versions TrueType de ces familles. Les fontes auxquelles le fournisseur répond avec le même fichier, par exemple une coupe romaine qui remplace le gras dont une famille est dépourvue, partagent une seule police incorporée. Une fonte qu’aucune page n’utilise finalement pour dessiner, comme celle du texte d’une figure SVG quand la figure est dessinée sous forme d’image, est laissée hors du fichier.

**Utilisez des polices statiques par graisse, pas une seule police variable.** Google Fonts sert souvent un unique WOFF2 variable par famille, qui couvre tout l’axe des graisses. `pdf-lib` ne peut incorporer que l’instance par défaut d’un fichier variable : un paragraphe en gras serait donc rendu en graisse normale. Fontsource publie des fichiers WOFF2 statiques par graisse qui règlent proprement le problème : c’est la méthode qu’utilise le Sandbox. Un fichier variable demandé à une graisse autre que son instance par défaut est signalé par un avertissement `variableFontDefaultInstance`.

**Chaque mot du texte arrive là où la mise en page l’a placé.** Dans les paragraphes, les éléments de liste, les citations, les encadrés et les autres textes courants, chaque mot commence à la position mesurée par le VDT : un écart entre les largeurs du navigateur et celles de la fonte incorporée ne s’accumule donc jamais le long d’une ligne. Une ligne sans mise en forme en ligne est peinte comme un seul objet texte qui déplace la plume entre les mots ; les lignes justifiées, centrées ou comportant de la mise en forme sont peintes mot par mot. Un caractère pour lequel la fonte n’a pas de glyphe, que le navigateur a mesuré dans une autre police et que le PDF peint avec la boîte de glyphe manquant de la fonte, ne déplace aucun des mots qui le suivent, et il est signalé une fois par fonte par un avertissement `missingGlyph`. Une espace absente de la fonte, comme une espace fine insécable ou une espace tabulaire, prend la largeur que le navigateur lui a donnée, et les caractères invisibles comme le gluon de mots (word joiner) et l’espace sans chasse ne sont pas dessinés. Un trait d’union insécable (U+2011) absent de la fonte est dessiné avec le trait d’union de la fonte (U+2010), ou avec son trait d’union-signe moins quand elle n’a pas non plus de trait d’union, comme l’affiche le navigateur ; Open Sans et Outfit, entre autres, n’ont ni l’un ni l’autre. Aucun de ces deux cas ne compte comme un glyphe manquant. Il y a deux exceptions. Une ligne qui contient des lettres de droite à gauche est toujours peinte d’un seul tenant (voir [Langues et écritures](/fr/docs/configuration-language#langues-et-écritures)). Le texte placé par une maquette (titres courants et pieds de page, ouvertures, titres d’encadrés et autres éléments de maquette) est composé avec les largeurs propres de la fonte incorporée : un glyphe absent de la fonte y décale donc toujours le reste de sa ligne.

### Quelles fontes sont demandées au fournisseur

`renderToPdf` parcourt les pages comme il les peint et ne demande au fournisseur que les fontes qu’elles dessinent :

- la fonte romaine d’un bloc qui compose au moins une ligne, et la fonte grasse, italique ou grasse italique de chaque suite de texte réellement composée ainsi ;
- les suites de pastilles, les puces et numéros de liste, et le texte des zones de maquette (titres courants, folios, bandeaux d’ouverture et de partie) ;
- le texte des légendes, des notes et des cellules de tableau de chaque ressource ;
- les fontes que désigne le `<text>` d’une figure SVG, quand la figure est incorporée. Une famille que le fournisseur ne peut pas fournir du tout cède la place à la famille suivante de la liste `font-family` du SVG.

Une famille de titres que personne ne met en italique n’est donc jamais demandée en italique, et une figure sans note n’a jamais besoin des fontes des notes.

Quand le fournisseur refuse une fonte, le rendu continue. Une autre fonte de la même famille est incorporée à sa place et un `PdfWarning` est signalé. La remplaçante est la première fonte qui se charge, en essayant les neuf graisses standard (100 à 900) dans l’ordre qu’utilise la correspondance des polices CSS, qui est aussi la fonte que le navigateur affiche dans l’aperçu :

1. d’abord le même style. Pour une graisse de 400 à 500, les graisses jusqu’à 500 passent en premier, puis les plus maigres de la plus proche vers le bas, puis les plus grasses à partir de 600. Pour une graisse inférieure à 400, les graisses plus maigres passent en premier, de la plus proche vers le bas, puis les plus grasses. Pour une graisse supérieure à 500, les graisses plus grasses passent en premier, puis les plus maigres ;
2. ensuite l’autre style, italique pour le romain et romain pour l’italique, à la graisse demandée puis aux autres graisses dans le même ordre.

Une famille sans italique compose donc ses suites italiques en romain, une famille qui ne propose que 400 et 700 prend un 600 pour un 700, et une famille qui n’a qu’une coupe compose tout dans celle-ci. Le fournisseur est sollicité une fonte à la fois, dans cet ordre, et jamais deux fois pour la même fonte : une fonte que rien n’utilise n’est donc jamais incorporée. Une famille que le fournisseur ne peut pas servir du tout est demandée pour chacune de ces 18 fontes avant que le rendu échoue.

```ts
const bytes = await renderToPdf(doc, {
  fontProvider,
  onWarning: (w) => {
    // { kind: 'fontFallback', family: 'Oswald', weight: 700, style: 'italic',
    //   fallback: { weight: 700, style: 'normal' }, reason: '…', message: '…' }
    console.info(w.message);
  },
});
```

Sans `onWarning`, le message va à `console.warn`. Le texte garde ses positions, qui viennent du VDT et ont été mesurées avec les fontes dont disposait le navigateur : une remplaçante aux largeurs différentes peut donc paraître serrée ou lâche. Fournissez la vraie fonte pour corriger cela. Un rendu n’échoue encore (`postext-pdf: failed to load font(s): …`) que lorsque le fournisseur ne peut fournir aucune fonte d’une famille à une graisse standard, en romain ou en italique.

### Fournisseur de polices dans le navigateur (Fontsource + WOFF2)

Le Sandbox fournit `createPdfFontProvider()` (`packages/postext-sandbox/src/viewport/pdf/pdfFontProvider.ts`), que vous pouvez copier dans n’importe quelle application web. L’essentiel :

```ts
import type { PdfFontProvider } from 'postext-pdf';
import { decompressWoff2 } from 'postext-pdf';

const bytesCache = new Map<string, Promise<Uint8Array>>();

function fontsourceId(family: string): string {
  return family.toLowerCase().replace(/\s+/g, '-');
}

function fontsourceWoff2Url(
  family: string,
  weight: number,
  style: 'normal' | 'italic',
): string {
  const id = fontsourceId(family);
  return `https://cdn.jsdelivr.net/npm/@fontsource/${id}@5/files/${id}-latin-${weight}-${style}.woff2`;
}

export function createPdfFontProvider(): PdfFontProvider {
  return async (family, weight, style) => {
    const key = `${family}|${weight}|${style}`;
    const cached = bytesCache.get(key);
    if (cached) return cached;

    const promise = (async (): Promise<Uint8Array> => {
      const url = fontsourceWoff2Url(family, weight, style);
      const res = await fetch(url, { mode: 'cors' });
      if (!res.ok) throw new Error(`font fetch failed: ${res.status} ${url}`);
      // pdf-lib needs TTF bytes, so decompress the WOFF2 wrapper client-side.
      return decompressWoff2(new Uint8Array(await res.arrayBuffer()));
    })();

    bytesCache.set(key, promise);
    return promise;
  };
}
```

Une version de production devrait aussi :

- **Interroger les graisses disponibles** (via `https://api.fontsource.org/v1/fonts/{id}`) et ramener la graisse demandée à la plus proche que la famille propose réellement, afin qu’une demande de `weight: 600` sur une famille qui n’a que `{400, 700}` aboutisse quand même.
- **Se rabattre de l’italique sur le romain** quand une famille n’a pas de coupe italique pour la graisse demandée, au lieu de faire échouer tout le rendu.
- **Réutiliser le cache d’un rendu à l’autre** (garder `bytesCache` au niveau du module, pas par appel), de sorte que régénérer le PDF après un changement de configuration ne coûte pratiquement rien.

### Polices chinoises, japonaises et coréennes

Une fonte CJK ne se présente pas comme un seul petit fichier. Fontsource livre Noto Serif SC en une centaine de fichiers par graisse, chacun contenant une partie des caractères et déclaré dans la feuille de style de la famille avec son `unicode-range` (`@fontsource/noto-serif-sc/400.css`) ; le navigateur télécharge les fichiers que touche le texte d’une page. Le fichier `latin` que télécharge le fournisseur ci-dessus ne contient aucun caractère han, et les sous-ensembles nommés sont incomplets : le `chinese-simplified` de Noto Serif SC n’a pas 釵, et le `chinese-traditional` de Noto Serif TC n’a aucun des signes pleine chasse （），！？：；.

Un fournisseur peut donc répondre pour une fonte avec plusieurs fichiers. `renderToPdf` lui passe les caractères que les pages composent dans cette fonte (`request.codePoints`), rassemblés dans tous les chapitres avant que quoi que ce soit ne soit dessiné, et le fournisseur renvoie les fichiers qui les contiennent, dans l’ordre où le navigateur les consulte. Chaque fichier est incorporé en sous-ensemble distinct, et chaque caractère est dessiné à partir du premier fichier qui a un glyphe pour lui : un chapitre qui touche 60 tranches incorpore 60 petits sous-ensembles. Une fonte demandée à nouveau, pour le texte d’une figure SVG par exemple, n’est demandée que pour les caractères qui manquent à ses fichiers. Un fournisseur qui renvoie un seul `Uint8Array` fonctionne comme avant. Le fournisseur du Sandbox lit la feuille de style Fontsource de la graisse et du style, et télécharge les fichiers dont les plages contiennent le texte ; en voici le cœur :

```ts
import type { PdfFontProvider } from 'postext-pdf';
import { decompressWoff2 } from 'postext-pdf';

type Slice = { url: string; ranges: Array<[number, number]> };

async function fontsourceSlices(family: string, weight: number, style: 'normal' | 'italic'): Promise<Slice[]> {
  const id = family.toLowerCase().replace(/\s+/g, '-');
  const cssUrl = `https://cdn.jsdelivr.net/npm/@fontsource/${id}@5/${weight}${style === 'italic' ? '-italic' : ''}.css`;
  const css = await (await fetch(cssUrl)).text();
  return [...css.matchAll(/@font-face\s*{([^}]*)}/g)].map(([, rule]) => ({
    url: new URL(/url\(\.?\/?([^)]+\.woff2)\)/.exec(rule)![1], cssUrl).href,
    ranges: /unicode-range:\s*([^;]+);/.exec(rule)![1].split(',').map((part) => {
      const [lo, hi = lo] = part.trim().slice(2).split('-');
      return [parseInt(lo, 16), parseInt(hi, 16)] as [number, number];
    }),
  }));
}

export const sliceFontProvider: PdfFontProvider = async (family, weight, style, request) => {
  // Where ranges overlap, the browser tries the last rule first.
  const slices = (await fontsourceSlices(family, weight, style)).reverse();
  const picked = new Set<Slice>();
  for (const cp of request?.codePoints ?? []) {
    const slice = slices.find((s) => s.ranges.some(([lo, hi]) => cp >= lo && cp <= hi));
    if (slice) picked.add(slice);
  }
  if (picked.size === 0) picked.add(slices[0]!);
  return Promise.all(slices.filter((s) => picked.has(s)).map(async (s) =>
    decompressWoff2(new Uint8Array(await (await fetch(s.url)).arrayBuffer()))));
};
```

Une famille latine passe par le même code : un texte anglais reçoit son seul fichier `latin`, un texte tchèque reçoit `latin` et `latin-ext`.

Un navigateur ne s’arrête pas au premier fichier qui a un glyphe. Il compose un caractère dans le fichier déclaré en dernier parmi ceux dont l’`unicode-range` le contient, et les fichiers d’une famille se chevauchent : Fontsource répète les lettres ASCII de Noto Serif JP dans son fichier `latin` et dans ses tranches numérotées. Deux caractères composés dans deux fichiers ne sont pas crénés entre eux : c’est donc le fichier qui détermine la largeur. Chrome 154 compose `Shift_JIS` sur 4,25 em avec les tranches déclarées après `latin`, et sur 4,32 em avec le seul fichier `latin`, qui crène `t_` et `_J`. Depuis postext-pdf 1.30, un fournisseur peut indiquer comment la page a déclaré chaque fichier : `declaredFontFile(bytes, { unicodeRange, order })` renvoie les mêmes octets accompagnés de l’`unicode-range` de la règle du fichier, tel que l’écrit le CSS, et de la place de cette règle parmi les règles de la fonte, n’importe quel nombre qui croît avec l’ordre de déclaration (le plus grand est déclaré en dernier).

```ts
import { declaredFontFile } from 'postext-pdf';

declaredFontFile(bytes, { unicodeRange: 'U+0000-00FF,U+0131,U+0152-0153', order: 0 });
```

Quand les fichiers d’une fonte indiquent leurs plages, dans un document façonné dans sa propre langue ([`bodyText.shapingLanguage: 'document'`](/fr/docs/configuration-text#texte-courant), la valeur par défaut), un caractère est dessiné à partir du fichier déclaré en dernier dont la plage le contient et qui a un glyphe pour lui, comme un navigateur choisit parmi les règles `@font-face`, et une lettre et ses signes diacritiques combinants restent dans un même fichier. Un caractère qu’aucune plage ne contient est dessiné à partir du premier fichier qui a un glyphe. Les fichiers simples, et tous les fichiers d’un document en `'host'`, sont lus dans l’ordre donné, comme avant : un fournisseur qui décrit ses fichiers place donc toujours en tête celui déclaré en dernier. Une fonte décrite ainsi est sollicitée à nouveau pour chaque caractère qui ne lui avait pas encore été demandé, puisqu’un fichier déclaré plus tard peut le contenir. Le fournisseur du Sandbox décrit ses fichiers.

Les caractères pour lesquels aucun fichier de la fonte n’a de glyphe sont dessinés avec le glyphe `.notdef` de la police (une boîte vide dans la plupart des polices), et `renderToPdf` les signale une fois par fonte après avoir dessiné les pages :

```ts
// { kind: 'missingGlyph', family: 'Noto Serif TC', weight: 400, style: 'normal',
//   characters: ['，', '！', '？'], message: '…' }
```

Le Sandbox les liste, ainsi que les deux avertissements ci-dessous, dans son panneau Vérifications après chaque PDF qu’il génère. Quand le livre, ses réglages ou ses ressources changent, ils sont marqués comme provenant d’un PDF antérieur jusqu’à ce que le suivant les remplace ; ouvrir un autre livre les efface.

- **Le gras exige un fichier statique par graisse.** Fontsource sert chaque graisse de Noto Serif SC et TC sous forme de fichiers statiques distincts : le gras fonctionne donc dans le Sandbox. Les fichiers de Google Fonts (`NotoSerifSC[wght].ttf`, 25 Mo) sont des polices variables : pdf-lib incorpore leur instance par défaut : une fonte 700 s’imprime donc en 400, et `renderToPdf` le signale par `variableFontDefaultInstance`. Pour un paquet, découpez une instance statique par graisse avec fontTools (`fonttools varLib.instancer NotoSerifSC[wght].ttf wght=700`) et réduisez-la aux caractères du livre avec `pyftsubset`.
- **Utilisez les versions TrueType.** Les fichiers `.otf` de Source Han Serif et de Noto Serif CJK ont des contours CFF, que postext-pdf incorpore en entier, de 8 à 25 Mo par graisse ; une fonte CFF de plus de 2 Mo est signalée par `cffEmbeddedWhole`. Les versions TrueType (Google Fonts, Fontsource) sont réduites aux glyphes utilisés. Pour le japonais, Noto Serif JP et Noto Sans JP (Google Fonts, ou les tranches numérotées de Fontsource), Shippori Mincho, Zen Old Mincho et BIZ UDMincho existent en TrueType ; Source Han Serif JP et les fichiers `.otf` `JP` de Noto Serif CJK sont en CFF.
- **Formes japonaises d’une fonte pan-CJK.** Un même point de code han, de ponctuation ou de guillemet peut se dessiner d’une façon au Japon et d’une autre en Chine, et une fonte pan-CJK (Source Han, Noto CJK) contient les deux. Le PDF façonne un document japonais (`locale: 'ja'`), et un isolat en japonais (`:ltr[…]{lang=ja}`) dans n’importe quel document, avec le système de langue OpenType `JAN ` : la fonctionnalité `locl` de la fonte imprime ainsi les formes japonaises que le canvas et le HTML impriment grâce à `lang`. Un isolat dans une autre langue à l’intérieur d’un livre japonais est façonné avec les formes de cette langue (les formes par défaut de la police pour le chinois en `'host'`) et balisé comme un `Span` avec son `/Lang`. Avec [`bodyText.shapingLanguage: 'document'`](/fr/docs/configuration-text#texte-courant), la valeur par défaut depuis postext 1.30, chaque document et chaque isolat est façonné dans sa propre langue (`ZHS` pour le chinois simplifié), comme la mise en page l’a mesuré ; avec `'host'`, les documents chinois et les autres sont façonnés avec les formes par défaut de la police, comme avant. Une fonte conçue pour le japonais comme Noto Serif JP a des formes par défaut japonaises ; elle compose tout de même les “ ” d’un texte japonais dans leurs formes `JAN `.

Un caractère absent d’une famille n’est pas pris dans une autre : Noto Serif TC n’emprunte rien à Noto Serif SC. Réglez la couverture au moment de construire les fichiers de polices ; la vitrine 红楼梦 copie les glyphes qui manquent à ses sous-ensembles TC depuis la fonte SC.

### Fournisseur de polices côté serveur (Node, fichiers locaux)

Sous Node, vous pouvez sauter entièrement l’étape WOFF2 et lire des fichiers TTF/OTF sur le disque :

```ts
import { readFile } from 'node:fs/promises';
import { join } from 'node:path';
import type { PdfFontProvider } from 'postext-pdf';

const FONT_DIR = '/path/to/fonts';

function filename(family: string, weight: number, style: 'normal' | 'italic'): string {
  const slug = family.replace(/\s+/g, '');
  const styleSuffix = style === 'italic' ? 'Italic' : '';
  const weightName =
    weight >= 700 ? 'Bold'
    : weight >= 600 ? 'SemiBold'
    : weight >= 500 ? 'Medium'
    : weight >= 300 ? 'Light'
    : 'Regular';
  return `${slug}-${weightName}${styleSuffix}.ttf`;
}

export const localFontProvider: PdfFontProvider = async (family, weight, style) => {
  const buf = await readFile(join(FONT_DIR, filename(family, weight, style)));
  return new Uint8Array(buf);
};
```

### Octets des ressources et originaux d’impression

`resourceBytes(fileId)` renvoie les octets bruts d’une image, et le moteur en détecte le format :

- PNG, JPEG, GIF et WebP sont incorporés comme images ;
- le balisage SVG est dessiné en tracés vectoriels, son `text` composé en texte réel dans les polices incorporées du document, ou bien rastérisé à 600 dpi dans le navigateur lorsqu’il emploie des fonctions hors du sous-ensemble vectoriel. Un `<style>` qui ne contient que des règles `@font-face` (des fontes qu’un auteur a incorporées) est ignoré et laisse la figure vectorielle (depuis postext-pdf 1.25) ; toute autre feuille de style en fait une image matricielle, produite avec les fontes que désigne son texte, insérées depuis `fontProvider` (sauf si `diagramStyle.inlineFonts` ou le `svg.inlineFonts` de la ressource vaut `false`) ;
- les TIFF et les documents Photoshop (PSD, PSB) s’impriment à partir de leurs propres pixels : niveaux de gris, RVB ou CMJN, 8 ou 16 bits, avec le profil ICC et la résolution qu’ils portent. Un document CMJN garde ses encres telles quelles ; les niveaux de gris et le RVB suivent `print.imageColor`. D’un document Photoshop, on lit l’image composite qu’il enregistre avec « Maximiser la compatibilité » ; les TIFF à compression JPEG ne sont pas lus ;
- un PDF voit sa première page incorporée telle quelle, sous forme de XObject de formulaire.

Chaque image est stockée une seule fois dans le fichier, quel que soit le nombre de fois où elle est dessinée. Un SVG dessiné en tracés vectoriels devient un XObject de formulaire que chaque page peint : un cadre ou un logo dans la maquette de page d’un document de trente pages est écrit une fois, et non trente ; chaque page supplémentaire ajoute quelques centaines d’octets. Jusqu’à postext-pdf 1.4, chaque page contenait sa propre copie des tracés.

Une figure SVG peut désigner un **original d’impression** dans `svg.pdfFileId` : un PDF d’une page de la même figure, en général l’original dont le SVG a été exporté. `renderToPdf` demande d’abord à `resourceBytes` l’identifiant de l’original. Il incorpore cette page à la place du SVG, avec ses polices, ses dégradés et ses espaces colorimétriques intacts, partout où le SVG est dessiné : comme figure, comme image d’une cellule de tableau (`TableCell.image`), comme image de maquette ou comme icône d’encadré (son `marker` aussi). Le VDT transmet l’identifiant de l’original à chacun de ces usages (`svg.pdfFileId` sur la ressource de la figure, `pdfFileId` sur une image de cellule et sur un bloc d’image de maquette) : dans un livre, chaque chapitre reçoit donc l’original. Les moteurs canvas et HTML continuent de dessiner le SVG. Les octets du SVG lui-même sont utilisés à la place dans trois cas : l’original est absent, ce n’est pas un PDF, ou l’encre unique est activée (`diagramStyle.singleInk` ne recolore que le balisage SVG).

```ts
const resources: Resource[] = [{
  id: 'map', typeId: 'figure', kind: 'svg', createdAt: 0, updatedAt: 0,
  svg: { fileId: 'map.svg', width: 800, height: 600, pdfFileId: 'map.pdf' },
}];
const files = new Map([['map.svg', svgBytes], ['map.pdf', masterPdfBytes]]);
const pdf = await renderToPdf(buildDocument({ markdown, resources }, config), {
  fontProvider,
  resourceBytes: (fileId) => files.get(fileId),
});
```

Un hôte peut aussi renvoyer les octets de l’original pour l’identifiant propre du SVG, comme le fait `bundleResourceBytes` ; les deux façons fonctionnent.

Un navigateur ne sait pas afficher un TIFF ni un document Photoshop, si bien qu’une ressource bitmap créée à partir de l’un d’eux garde deux fichiers : `bitmap.fileId` est un aperçu PNG, qu’affichent le canvas, le HTML et l’EPUB, et `bitmap.printFileId` (avec `printFormat: 'tiff' | 'psd'`) est l’original. Un hôte renvoie les octets de l’original pour `bitmap.fileId`, comme le font `bundleResourceBytes` et le Sandbox, et le PDF s’imprime à partir de lui. Il passe aussi l’aperçu, comme `previewBytes` (`bundlePreviewBytes` pour un paquet) : un original qui ne se décode pas s’imprime depuis son aperçu, avec un avertissement `pictureOriginalUnreadable`, et sans aperçu il reste un espace réservé. `decodePrintRaster(bytes)` et `rasterToRgba(raster)` de `postext` lisent l’original et produisent l’aperçu ; le Sandbox le produit à l’importation du fichier, et un paquet stocke l’original sous `resources/<nom>.tif` ou `.psd` à côté de l’aperçu.

Un fichier Adobe Illustrator enregistré avec « Créer un fichier compatible PDF » est un PDF, et il peut être un original d’impression comme un autre (`.ai`). Ses nuances sont ses propres plaques : le contrôle en amont énumère celles que la table des encres renomme, celles qu’aucune couleur du livre ne définit et, dans un travail sur ses propres plaques (`print.plates`), celles que le travail n’imprime pas, car un fichier placé s’imprime tel quel.

### Texte vertical dans le PDF

Une page verticale (`layout.writingMode: 'vertical-rl'`) est dessinée dans un repère tourné d’un quart de tour, comme sur le canvas, et son texte est composé de haut en bas de la colonne :

- **Les caractères debout** sont affichés au moyen d’une seconde police Type0 tirée du même fichier incorporé : même CIDFont, mêmes largeurs et même table ToUnicode, avec `Encoding /Identity-V` (mode vertical). Une suite de caractères forme un seul objet texte dont les glyphes avancent d’eux-mêmes d’un cadratin vers le bas de la colonne (`DW2 [880 −1000]`) : les visionneuses sélectionnent et extraient donc une colonne comme une seule ligne. Les glyphes sont façonnés avec les fonctionnalités OpenType `vert` et `fwid`, qui donnent leurs formes verticales aux parenthèses, aux guillemets, aux virgules d’énumération du continent, aux points de suspension et aux tirets ; un caractère qui se tient debout tel quel garde son glyphe horizontal. Rien de la police n’est incorporé deux fois.
- **Les mots latins et les nombres longs** sont couchés sur le côté avec la police horizontale ; **un nombre dans une cellule** se tient debout, comprimé en largeur jusqu’au cadratin s’il est plus large ; un signe pour lequel la police n’a pas de forme verticale est tourné ou déplacé, comme sur le canvas.
- **L’approche** entre les caractères est écrite sous forme de nombres `TJ`, qui, en mode vertical, déplacent la plume vers le bas de la colonne.
- **Chaque ligne verticale** est marquée d’un `/ActualText` contenant son texte : la copie et l’extraction de texte la restituent ainsi telle qu’elle est écrite. `pdftotext` et pdf.js lisent les colonnes de haut en bas et de droite à gauche ; pdf.js commence une nouvelle ligne à chaque nombre composé dans une cellule.
- **Les liens, signets et destinations** sont reportés sur la feuille : un lien sur une ligne verticale est un rectangle haut et étroit, et un signet ouvre la page en haut de la colonne de son titre.
- **Un PDF balisé** déclare le mode d’écriture sur son élément `Document` (l’attribut de mise en page `WritingMode /TbRl`, dont hérite chaque élément) ; la validation PDF/UA-1 (veraPDF) réussit sur un chapitre vertical.
- **Visionneuses :** Acrobat, Aperçu, Chrome (PDFium), pdf.js et Poppler affichent les polices verticales. Un livre relié à droite (`page.binding`) demande aussi aux visionneuses de disposer ses doubles pages de droite à gauche (`/Direction /R2L`, `/PageLayout /TwoPageRight`) ; Acrobat et Foxit le suivent, Chrome non.

Un chapitre de 43 pages composé en Noto Serif TC (les caractères du livre, en TrueType) pèse environ 820 Ko, dont la plus grande partie revient aux deux sous-ensembles de polices.

### Champs de formulaire

Une pastille dotée d’un attribut `field` est un champ de formulaire à remplir (AcroForm). La pastille se compose et peint son cadre comme toute pastille : son style lui donne son aspect et sa largeur minimale (`minWidth`), ses mots sont la valeur par défaut du champ. Le PDF pose un champ interactif sur le cadre ; un nom employé deux fois donne un seul champ à deux widgets.

```md
Quantité :chip[ ]{style="field" field="pos.a.qty" kind="number"}
Prix :chip[120]{style="field" field="pos.a.price" format="currency"}
Total :chip[ ]{style="field" field="pos.a.total" format="currency" calc="product(pos.a.qty, pos.a.price)"}
Prestation :chip[ ]{style="box" field="pkg.a" kind="checkbox" on="1"}
Total de la commande :chip[ ]{style="field" field="order.total" format="currency" calc="sum(pos.a.total, product(pkg.a, 161.75))"}
Taille :chip[M]{style="field" field="size" kind="choice" options="S|M|L"}
```

- `kind` : `text` (par défaut), `number`, `checkbox`, `choice` (avec `options`, séparées par `|`). Une pastille avec `format` ou `calc` et sans `kind` est un champ numérique.
- `on` (une case à cocher) : le nom de l’état coché de la case, c’est-à-dire la valeur que lisent ses scripts quand elle est cochée. Avec `on="1"`, une case cochée compte 1 dans un calcul, et `product(pkg.a, 161.75)` ajoute ainsi un prix fixe quand la case est cochée. La valeur par défaut est `Yes`, qu’un calcul compte pour 0.
- `format` : `currency`, `decimal` (deux décimales), `integer`. Écrit avec `AFNumber_Format` et `AFNumber_Keystroke` d’Acrobat, avec les séparateurs de la langue du document (`1.234,56` en allemand) sauf si `RenderToPdfOptions.forms.separatorStyle` en décide autrement ; la devise est `forms.currency` (par défaut `€`), placée avant le nombre sauf si `forms.currencyBefore` vaut `false`. Une valeur par défaut est dessinée déjà mise en forme.
- `calc` : `sum(…)`, `product(…)`, `min(…)`, `max(…)` ou `avg(…)`. Les arguments sont d’autres champs désignés par leur nom, des nombres (avec un point comme séparateur décimal, `161.75`) et des calculs imbriqués : `sum(pos.a.total, pos.b.total, product(pkg.a, 161.75))`. Un calcul qui ne porte que sur des champs s’écrit avec `AFSimple_Calculate`. Un calcul qui contient des nombres ou des calculs imbriqués devient un court script Calculate à part, qui lit chaque champ de la même manière (`AFMakeNumber` de sa valeur ; ce qui n’est pas un nombre compte pour 0) et arrondit le résultat à six décimales. Un champ calculé est en lecture seule, et l’ordre de calcul tient compte de tous les champs qu’il lit, ceux des calculs imbriqués compris. Donnent un avertissement `formField` : un calcul qui lit un champ inconnu (il compte pour 0), un cycle, un nom employé pour deux types de champ, et une case à cocher dans un calcul dont la valeur `on` n’est pas un nombre (elle compte toujours pour 0).
- `readonly`, `required`, `multiline`, `tooltip` font ce que dit leur nom.

Un champ affiche sa valeur, et ce qu’on y tape, dans la fonte de sa pastille (`forms.font: 'chip'`, par défaut) ou dans une fonte des polices du document que désigne `forms.font` (`{ family, weight?, style? }`, demandée au `fontProvider` comme toute autre). Cette fonte est incorporée **en entier**, et non en sous-ensemble, car un sous-ensemble n’aurait pas les glyphes des caractères tapés plus tard ; elle n’est incorporée qu’une fois, quel que soit le nombre de champs qui l’utilisent, nommée dans les ressources par défaut du formulaire (`/DR`) et dans l’apparence par défaut de chaque champ (`/DA`), et les valeurs par défaut sont dessinées avec elle. Une fonte entière ajoute tout son fichier au PDF (une fonte de texte latine pèse en général de 50 à 300 Ko, une fonte CJK plusieurs Mo), en plus du sous-ensemble qu’utilise le texte des pages. Le fournisseur peut répondre en TrueType, OpenType ou WOFF2 (décompressé avant l’incorporation). Les champs reviennent à Helvetica, avec un avertissement `formField`, quand la fonte ne peut pas être incorporée en entier : sa licence l’interdit (`fsType` de la table OS/2 restreint ou bitmap seulement), le fournisseur la livre en plusieurs fichiers (une fonte découpée), ou son format est WOFF ou une collection. Avec `forms.font: 'helvetica'`, les champs utilisent Helvetica sans rien incorporer. Certains lecteurs (Aperçu sur macOS, par exemple) affichent le texte en cours de saisie dans une fonte à eux ; la valeur reste la même.

Acrobat, Foxit, pdf.js (Firefox) et la plupart des lecteurs exécutent ces scripts. Une norme d’impression (PDF/X) n’admet aucun champ interactif : les valeurs y sont peintes comme du texte, celle d’un champ numérique telle que le formulaire l’affiche (mise en forme, calée à la fin du cadre à l’intérieur du `paddingX` du style, dans la couleur de la pastille).

Le canvas peint un champ numérique de la même façon, si bien que l’aperçu correspond au PDF : passez à `renderPageToCanvas` (ou à `renderPage`, `renderToCanvas`) la même option `forms` qu’à `renderToPdf` ; dans les deux cas, les séparateurs suivent par défaut le `locale` du document (à défaut, sa langue de césure). Une seule règle écrit les nombres partout, et postext l’exporte pour d’autres générateurs de sortie : `formNumberStyle(forms, lang)` résout les options, `formatFieldNumber(value, format, style)` met en forme une valeur (undefined pour un texte qui n’est pas un nombre) et `numberFieldText(field, words, style)` donne ce qu’affiche un champ numérique peint. La liste d’affichage porte le champ sur le segment de la pastille (`inline.field`, avec le `sizePx` et le `padPx` de la mise en page).

Un livre peut garder ces options dans sa configuration : `pdfGeneration.forms` prend les mêmes champs (`currency`, `currencyBefore`, `separatorStyle`, `font`). `renderToPdf` et le canvas prennent chacun d’abord dans leur propre option `forms`, puis dans le `pdfGeneration.forms` du premier document, puis dans les valeurs par défaut. Cela ne change pas la mise en page, seulement la façon d’écrire et de peindre les champs. Dans le Sandbox, c’est le groupe **Champs de formulaire** de la section PDF.

```ts
pdfGeneration: {
  forms: { currency: 'USD', currencyBefore: true, separatorStyle: 0, font: { family: 'Lora', weight: 400 } },
}
```

**Depuis esm.sh dans un navigateur**, importez `https://esm.sh/postext-pdf?bundle`. La compilation par défaut de pdf-lib sur esm.sh place ses classes d'annotation dans un module à part, et pdf-lib refuse alors le widget de chaque champ : le PDF garde les cases, mais perd formats, calculs et attributs, avec un avertissement `formField` par champ. `?bundle` compile pdf-lib en un seul module et laisse `postext` à l'extérieur, partagé avec la page. Un bundler (Vite, webpack, Next.js) et Node ne sont pas concernés.

L’export IDML écrit les mêmes champs en champs de formulaire InDesign (voir [Utilisation programmatique › Paquets InDesign](/fr/docs/configuration-programmatic-usage#paquets-indesign-postext-idml)).

### Liens dans le PDF

Les mots d’un lien Markdown (voir [Format du document › Liens](/fr/docs/document-format-inline#liens)) deviennent des annotations de lien URI, une par suite de mots liés sur une ligne. Chacune couvre la boîte de la ligne et n’a pas de bordure. Dans un rendu accessible, chaque suite est un élément `Link` dont le `/Contents` est son texte. Seules les cibles absolues `http:`, `https:`, `mailto:`, `tel:` et `ftp:` sont liées, car une URL relative n’a pas de base à l’intérieur d’un PDF. Les caractères hors de l’ASCII imprimable sont encodés en pourcentage. Les renvois `:ref` et les lignes de la table des matières gardent leurs liens à l’intérieur du document.

### Exemple complet dans le navigateur : construire, rendre, télécharger

Tout assembler : construire le VDT, le rendre en PDF et déclencher un téléchargement depuis le navigateur :

```tsx
import { buildDocument, createMeasurementCache } from 'postext';
import { renderToPdf } from 'postext-pdf';
import { createPdfFontProvider } from './pdfFontProvider';

const fontProvider = createPdfFontProvider();

export async function downloadPdf(markdown: string, config: PostextConfig) {
  const cache = createMeasurementCache();
  const vdt = buildDocument({ markdown }, config, cache);

  const bytes = await renderToPdf(vdt, { fontProvider });

  const blob = new Blob([bytes.slice().buffer], { type: 'application/pdf' });
  const url = URL.createObjectURL(blob);
  const a = document.createElement('a');
  a.href = url;
  a.download = 'document.pdf';
  document.body.appendChild(a);
  a.click();
  a.remove();
  setTimeout(() => URL.revokeObjectURL(url), 1000);
}
```

**Important :** appelez `ensureConfigFontsLoaded(config)` (ou l’équivalent) *avant* `buildDocument` quand votre configuration fait référence à des polices web. La mise en page est mesurée avec les métriques dont dispose le navigateur à ce moment pour la famille : si la vraie police n’est pas encore arrivée, le VDT est mesuré avec une police de secours et le PDF ne correspondra pas à la sortie canvas ou HTML. Le Sandbox le fait explicitement avant chaque rendu (voir `packages/postext-sandbox/src/viewport/pdf/PdfViewport.tsx`).

### Rendre le PDF dans un worker

`postext-pdf/worker` sort `renderToPdf` du fil principal. Le worker écrit le texte, les figures vectorielles, l’arbre de structure et le fichier lui-même. Deux tâches ont besoin de la page, et le worker les demande donc au fil principal : télécharger les polices et rastériser un SVG au moyen d’un `<img>`. Pour un livre de plusieurs centaines de pages, le rendu prend des secondes qui figeraient sinon la page ; pour quelques pages, appeler directement `renderToPdf` est plus simple.

```ts
import { createPdfWorker } from 'postext-pdf/worker';

const pdfWorker = createPdfWorker();
const bytes = await pdfWorker.render(docs, {
  fontProvider,                                     // runs on this thread
  resourceBytes: new Map([['map.svg', svgBytes]]),  // a Map; its buffers move to the worker
  onProgress: ({ phase, pages, totalPages }) => showProgress(phase, pages, totalPages),
  onWarning: (w) => console.info(w.message),
});
pdfWorker.dispose();
```

- `render(docs, options)` prend un document, ou le tableau des documents de chapitres d’un livre. Il accepte les options de `renderToPdf`, avec deux différences. `resourceBytes` (et `previewBytes`) est une `Map<string, Uint8Array>` dont les tampons sont transférés : passez des copies des octets que vous conservez. `rasterizeSvg`, s’il est fourni, s’exécute sur le fil principal ; par défaut, ce sont l’`Image` et le canvas de la page qui s’en chargent.
- Un même objet ne rend qu’un document à la fois. `dispose()` termine le worker et rejette tout rendu encore en attente avec une erreur `AbortError` (`DOMException`), à traiter comme une annulation. Si votre fournisseur répond avec une police ou une image après `dispose()`, la réponse est ignorée.
- `inspect(bytes)` relit un PDF terminé dans le worker (`inspectPrintPdf`) et se résout avec son rapport, ou `undefined` si les octets ne se lisent pas comme un PDF. Les octets sont copiés : les vôtres restent utilisables. Rien n’est lu si vous ne l’appelez pas.
- `createPdfWorker({ worker })` accepte un `Worker` que vous créez vous-même, pour les outils de build qui contrôlent les URL des workers. Ce worker doit exécuter `postext-pdf/worker/entry`.

**Depuis un CDN.** Par défaut, le script du worker est chargé depuis l’URL propre du paquet (`new URL('./pdf.worker.js', import.meta.url)`). Une page d’une autre origine peut ne pas pouvoir le démarrer : importé depuis `esm.sh`, `createPdfWorker()` lève `Failed to construct 'Worker': Script at 'https://esm.sh/postext-pdf@…/pdf.worker.js' cannot be accessed from origin …`. Démarrez plutôt un worker de module de même origine qui importe le point d’entrée (si vous épinglez une version, épinglez la même dans les deux URL) :

```js
import { createPdfWorker } from 'https://esm.sh/postext-pdf/worker';

const entry = URL.createObjectURL(new Blob(
  ["import 'https://esm.sh/postext-pdf/worker/entry';"],
  { type: 'text/javascript' },
));
const pdfWorker = createPdfWorker({ worker: new Worker(entry, { type: 'module' }) });
```

Le worker de mise en page de `postext/worker` n’en a pas besoin : `createLayoutWorker()` démarre lui-même son point d’entrée depuis esm.sh sans option, et depuis tout autre serveur avec son option `url` (voir [Charger le worker depuis un CDN](/fr/docs/configuration-programmatic-usage#charger-le-worker-depuis-un-cdn)).

### PDF prêts pour l’impression

Pour une chaîne de production imprimée, réglez ces options de configuration avant le rendu :

- **`page.cutLines.enabled: true`** : ajoute la zone de fond perdu et les traits de coupe autour du format rogné, et donne à chaque page une TrimBox et une BleedBox. Voir [Traits de coupe](/fr/docs/configuration-page-layout#traits-de-coupe).
- **`print: { standard: 'pdfx4', outputProfile: 'fogra51' }`** (ou `'pdfx1a'`) : un fichier PDF/X avec l’intention de sortie (output intent), l’identification et les boîtes que vérifie un imprimeur ; chaque couleur et chaque image RVB séparées au moyen du profil ICC, le noir 100 % K en surimpression et les grands aplats noirs en noir enrichi. Voir [Production pour l’impression (configuration)](/fr/docs/configuration-fonts-colors-viewers#production-pour-limpression-configuration).
- **`colorSpace: 'cmyk'`** (ou `pdfGeneration: { forceColorSpace: true, colorSpace: 'cmyk' }`) : la même séparation sans l’identification PDF/X (les traits de coupe sont toujours en couleur de repérage). Les originaux d’impression PDF sont incorporés tels quels.
- **`page.dpi: 300`** : les px par pouce de la mise en page ; un bitmap sans résolution propre s’imprime à cette résolution à sa taille naturelle. Le [contrôle en amont](/fr/docs/configuration-pdf-output#contrôle-en-amont) signale les images de moins de 300 ppp à leur taille imprimée.
- **`ColorValue.cmyk`** : une couleur définie en CMJN s’imprime avec ses valeurs exactes.
- **`{ pageNegative: true }`** dans `RenderToPdfOptions` : inverse la zone rognée au moyen d’un mode de fusion Différence (les traits de coupe ne sont pas inversés). Utile pour les contrôles en amont d’une typographie sombre sur fond clair.
- **`print.dieLine`** : le tracé de découpe d’un livre avec des découpes, tracé sur sa propre plaque, que la presse n’encre jamais (`Die` par défaut, dans un groupe de contenu optionnel hors PDF/X-1a). Voir [Le tracé de découpe dans le PDF](/fr/docs/special-inks-die-cuts#le-tracé-de-découpe-dans-le-pdf).

### Tons directs

Un ton direct (un Pantone, une encre d’entreprise, un vernis) s’imprime sur sa propre plaque. Une couleur avec `model: 'spot'` porte son encre dans `ColorValue.spot` : `name` est le nom de la plaque tel que l’imprimeur le connaît, `cmyk` l’aspect de l’encre à 100 % (la couleur de substitution que le PDF donne à qui n’a pas l’encre), `tint` la force en pourcentage (100 par défaut), `overprint` fait surimprimer l’encre sur ce qui est dessous au lieu de le défoncer, comme un vernis, et `finish` dit ce qu’est une encre spéciale : métallisée, dorure, fluorescente, blanc opaque ou vernis. `hex` est son rendu à l’écran. [Encres spéciales et découpes](/fr/docs/special-inks-die-cuts#finitions) explique comment chaque finition s’imprime et s’affiche.

Un PDF CMJN ou PDF/X écrit chaque encre comme un espace colorimétrique `Separation` qui porte son nom, et peint chaque couleur de cette encre à sa teinte : les couleurs de même `name` partagent une plaque. Cela couvre les travaux habituels : deux couleurs (le noir et un ton direct), la quadrichromie avec quelques éléments dans un ton direct, et un vernis surimprimé sur des zones choisies. Quand `diagramStyle.singleInk` utilise un ton direct, les diagrammes SVG s’impriment en teintes de cette plaque. Un PDF RVB et l’écran peignent le `hex` de la couleur.

**Tons directs dans un SVG.** Voir [Fonctionnement de l’encre unique](/fr/docs/configuration-resources#fonctionnement-de-lencre-unique).

```ts
colorPalette: [
  { id: 'brand', name: 'Brand', value: { hex: '#1f3f99', model: 'spot', spot: { name: 'PANTONE 286 C', cmyk: { c: 100, m: 66, y: 0, k: 2 } } } },
  { id: 'brand-40', name: 'Brand 40 %', value: { hex: '#a5b6dd', model: 'spot', spot: { name: 'PANTONE 286 C', cmyk: { c: 100, m: 66, y: 0, k: 2 }, tint: 40 } } },
  { id: 'varnish', name: 'Varnish', value: { hex: '#f4f4ee', model: 'spot', spot: { name: 'Varnish', cmyk: { c: 0, m: 0, y: 10, k: 0 }, finish: { kind: 'varnish', sheen: 'gloss' } } } },
],
diagramStyle: { singleInk: true, inkColor: { hex: '#1f3f99', model: 'spot', paletteId: 'brand' } },
```

Le contrôle en amont compte un ton direct comme une seule encre, le laisse hors de la limite d’encrage et énumère les tons directs du travail (`spotInks`), y compris les encres que nomment les images SVG. Il avertit quand une même encre est définie deux fois avec des valeurs différentes (`spotInkConflict` ; le PDF utilise la première), quand un SVG nomme une encre qu’aucune couleur de la palette ni aucune entrée de la table des encres avec `cmyk` ne définit (`spotInkUndefined` ; elle s’imprime sur une plaque à elle, avec le CMJN de la couleur du SVG comme couleur de substitution, une plaque par nom), quand le PDF doit écrire un nom de plaque autrement (`spotInkName`, voir plus bas), et quand deux noms de plaque ne diffèrent que par la casse ou les espaces (`spotInkSimilar` : `PANTONE 185 C` et `Pantone  185 C` feraient deux plaques). `preflightDocument` apprend quelles encres un SVG nomme par `svgInks(fileId)`, une fonction qui renvoie les noms que `svgSpotInks(markup)` trouve dans le fichier ; le panneau **Vérifications** du Sandbox et `postext check` la lui passent.

**Noms de plaque.** Le nom est écrit tel qu’il est saisi : les accents, les symboles et `#` arrivent dans le PDF en UTF-8 (`Rojo Médica` devient `/Rojo#20M#C3#A9dica`), et c’est ainsi que le lisent Acrobat, un RIP et le contrôle en amont de l’imprimeur. Un nom qu’une plaque ne peut pas porter est écrit sous un autre : `All`, `None`, `Cyan`, `Magenta`, `Yellow` et `Black`, quelle que soit la casse, reçoivent le mot ink à leur suite (`All ink`) ; les caractères de contrôle sont retirés, et un nom de plus de 127 octets en UTF-8 est coupé entre deux caractères et se termine par un court hachage, si bien que deux noms longs qui commencent pareil restent deux plaques. Le `spotInkName` du contrôle en amont dit pourquoi (`problem` : `reserved`, `process`, `control` ou `tooLong`) et quel nom le PDF écrit (`written`), et le rendu signale chaque changement par `onWarning` (`spotInkRenamed`). Pour choisir le nom vous-même, donnez à l’encre un `pdfName` dans la table des encres.

**Une encre par couleur.** Un rendu pour l’impression reconnaît une couleur à son hex d’écran : deux couleurs qui fixent leurs valeurs d’impression (deux encres, ou une encre et une couleur définie en CMJN) ne peuvent donc pas le partager. Si elles le partagent, la seconde passe au hex libre le plus proche, à un pas de distance et invisible à l’écran, et chacune s’imprime sur sa propre plaque. Une simple couleur d’écran (`model: 'hex'`) qui a le hex d’un ton direct s’imprime comme ce ton direct ; liez-la à l’entrée de la palette pour le rendre explicite. La couleur qui se déplace change aussi à l’écran, d’un pas (1/255) sur un seul canal, le bleu d’abord, dans toutes les sorties (canvas, HTML, EPUB et PDF RVB). C’est bien en dessous de ce que l’œil distingue, et c’est le prix d’un rendu pour l’impression qui lit les encres dans le hex peint. La configuration enregistrée ne change pas.

#### La table des encres

`print.inks` indique comment les encres du travail arrivent chez l’imprimeur, quel que soit le nom que leur donnent les couleurs, les SVG et les fichiers importés. Une encre absente de la table s’imprime comme ses couleurs la définissent.

```ts
interface PrintInk {
  name: string;                    // L’encre telle que la nomme spot.name ou un SVG.
  aliases?: string[];              // Autres noms de la même encre : ils s’impriment sur cette plaque.
  pdfName?: string;                // Le nom de la plaque dans le PDF. Par défaut, name.
  output?: 'spot' | 'process';     // 'process' imprime l’encre en CMJN, d’après sa substitution.
  cmyk?: CmykPercent;              // La substitution à 100 %, prioritaire sur celle des couleurs.
  overprint?: boolean;             // Prioritaire sur celui des couleurs.
  finish?: InkFinish;              // Métallisée, dorure, fluorescente, blanc ou vernis, prioritaire sur celle des couleurs.
}
```

Les noms et les alias sont comparés sans tenir compte de la casse ni des espaces répétés. Renommer tient en une ligne, quel que soit le nombre de couleurs qui utilisent l’encre ; un alias réunit sur une seule plaque les noms qu’un nuancier du graphiste, un SVG (`data-spot`, `icc-named-color`) ou une palette antérieure donnaient à la même encre ; `output: 'process'` imprime une encre en CMJN quand la presse n’a pas de groupe pour elle, toutes ses teintes comprises ; et `finish` fait d’une encre une encre spéciale d’où que vienne son nom, y compris d’un SVG ou d’un fichier importé qui nomme `Gold`. L’ordre des entrées est l’ordre sous presse de deux vernis qui se rencontrent : à l’écran et dans Folio, une entrée plus loin dans la table passe sur une entrée antérieure (voir [Finitions](/fr/docs/special-inks-die-cuts#finitions)).

Dans le Sandbox, la table se trouve dans **Maquette › Export › Préparation pour l’impression › Table des encres** : une carte par encre avec son **Nom de l’encre**, ses **Alias**, le **Nom de la plaque dans le PDF**, **S’imprime en**, le **CMJN de substitution**, la **Surimpression**, la **Finition** et la **Brillance**. **Encres utilisées par les couleurs** énumère les encres des couleurs du livre absentes de la table, chacune avec un bouton qui l’ajoute.

```ts
print: {
  standard: 'pdfx4',
  inks: [
    { name: 'Azul corporativo', pdfName: 'PANTONE 286 C', aliases: ['Pantone 286C', 'Azul'] },
    { name: 'Varnish', output: 'process' },
  ],
},
```

#### Impression à deux encres

`print.plates` nomme les plaques sur lesquelles le travail s’imprime, et rien d’autre n’est imprimé : un livre en noir et un ton direct, en deux tons directs, ou en noir seul. Les plaques de quadrichromie sont `Cyan`, `Magenta`, `Yellow` et `Black` ; une plaque de ton direct se nomme comme la nomme le PDF, ou par un nom ou un alias de la table des encres.

```ts
interface PrintPlatesConfig {
  inks?: string[];                                // Les plaques. Vide : toutes, comme d’habitude.
  images?: string[];                              // Les plaques des images : une ou deux.
  curves?: Record<string, Array<[number, number]>>; // La courbe d’une plaque d’image : [ton, encre] en pourcentage.
}
```

- Une couleur d’une encre que le travail imprime, ou une couleur CMJN dont il imprime les couches, est appliquée telle quelle.
- Toute autre couleur est projetée : elle s’imprime comme le mélange d’une ou deux plaques dont l’aspect, à travers le profil de sortie, s’en approche le plus. Un mélange de deux encres est un espace colorimétrique `DeviceN` dans le PDF, et un gris reste sur `Black` seul. Le noir enrichi est abandonné, sauf si le travail imprime les quatre encres de quadrichromie.
- Les images s’impriment en monotone sur une plaque, ou en bichromie sur deux : le ton de chaque pixel (sa luminosité) passe par la courbe de chaque plaque. `images` vaut par défaut `Black`, ou la première plaque quand le travail n’imprime pas de noir. La courbe d’un monotone est une droite ; une bichromie met sa première plaque dans les ombres et la seconde dans les tons moyens. `curves` remplace l’une ou l’autre.

```ts
print: {
  standard: 'pdfx4',
  plates: {
    inks: ['Black', 'PANTONE 286 C'],
    images: ['Black', 'PANTONE 286 C'],
    curves: { 'PANTONE 286 C': [[0, 0], [50, 35], [100, 70]] },
  },
},
```

Le contrôle en amont énumère les plaques du travail et chaque couleur que la projection déplace. Un ton direct ou une couleur CMJN que le travail n'imprime pas est une information quand son mélange tombe à moins de ΔE 6, et un avertissement au-delà ou tant que le profil de sortie n'est pas chargé (`offPlateInk`, `offPlateCmyk`) ; une couleur d'écran qui tombe au-delà de ΔE 6 est aussi un avertissement (`offPlateColor`). Une plaque de ton direct qu'aucune couleur ni aucune entrée de la table des encres ne définit est un avertissement : elle s'imprime et apparaît en noir sur l'épreuve. Dans un tel travail, l'original d'impression d'une figure est mis de côté et son SVG est composé sur les plaques ; une page PDF placée, ou une image impossible à décoder, garde ses propres encres et le rendu avertit (`artworkOffPlates`). Dans le Sandbox, les plaques se choisissent dans Préparation pour l’impression → Plaques. Ses aperçus et l'aperçu d'impression montrent les couleurs telles que le livre les définit, non telles que les plaques les impriment : regardez le PDF, où Vérifier pour l'impression liste les encres qu'il utilise.

### Couleurs des images

Une image est séparée à partir des couleurs dans lesquelles elle a été créée. `print.imageColor` indique comment ses pixels sont lus :

```ts
interface PrintImageColorConfig {
  embeddedProfile?: 'use' | 'ignore';                  // A picture's own ICC profile. Default 'ignore'.
  assignedRgbProfile?: { name: string; fileId: string }; // Read every RGB picture through this .icc instead.
  grayDotGain?: 'profile' | 'none' | number;           // Greyscale pictures on black. Default 'none'.
  cmykProfile?: 'convert' | 'keep';                    // A CMYK picture of another press. Default 'keep'.
}
```

Les valeurs par défaut laissent les images telles que les imprimaient les versions précédentes : toute image RVB est lue comme sRGB (`'ignore'`), les images en niveaux de gris sont séparées comme les autres (`'none'`) et une image CMJN garde ses valeurs (`'keep'`). Chaque comportement de la liste s’active avec son champ.

- **Son propre profil.** Un PNG (`iCCP`) ou un JPEG (`ICC_PROFILE`) qui intègre un profil est lu à travers celui-ci, si bien qu’une photographie en Adobe RGB ou en Display P3 se sépare telle qu’elle apparaît et non comme si elle était en sRGB. Une image sans profil, ou avec un profil sRGB, est lue en sRGB, comme jusqu’ici. `'ignore'` lit toutes les images en sRGB.
- **Un profil attribué.** `assignedRgbProfile` désigne un `.icc` enregistré à travers lequel toute image RVB est lue, quel que soit le profil qu’elle intègre : pour un lot de photographies qui ont perdu le leur, par exemple. Ses octets viennent de `resourceBytes` ; s’ils manquent, les profils propres aux images sont utilisés, avec un avertissement `imageProfileUnavailable`.
- **Conservée pour le RIP.** En PDF/X-4 avec `convertImages: false`, une image dont le profil n’est pas sRGB est écrite dans ses propres couleurs, étiquetée `ICCBased` avec ce profil, et le RIP de l’imprimeur la convertit.
- **Niveaux de gris.** Une image en niveaux de gris (un PNG ou un JPEG en gris, ou une image avec un profil de gris) s’imprime avec la seule encre noire, jamais en gris quadrichrome. Ses tons, lus à travers son propre profil (sinon tels que l’écran les affiche), sont ajustés à la presse : `'profile'` par le noir du profil de sortie, dont la condition inclut déjà l’engraissement ; un nombre est l’engraissement de la presse au ton de 50 %, en pourcentage (10 à 30 en général), qui est alors compensé ; `'none'` écrit les valeurs telles quelles, comme jusqu’ici.

```ts
print: {
  standard: 'pdfx4',
  imageColor: { grayDotGain: 20 },
},
```

- **Une image CMJN d’une autre presse.** Une image CMJN dont le profil propre est une autre condition d’impression (une photographie séparée pour SWOP ou pour le papier journal dans un livre pour FOGRA) est séparée de nouveau pour celle de la sortie (`cmykProfile: 'convert'`), le noir seul restant noir seul : une image TIFF ou Photoshop à partir de ses pixels ; un JPEG CMJN, dont les pixels ne sont pas décodés, est étiqueté `ICCBased` avec son propre profil en PDF/X-4 pour que le RIP le convertisse, et passe tel quel en PDF/X-1a, qui n’admet pas cette étiquette ; le contrôle en amont l’y signale (`cmykImageForeign`) quand l’hôte lui donne le profil de l’image (`imageProfile`). En PDF/X-4 avec `convertImages: false`, une image TIFF ou Photoshop est étiquetée de la même façon. `'keep'` imprime telles quelles les valeurs de toute image CMJN.

**Les réglages d’une seule image.** Le `printColor` d’une ressource accepte les mêmes champs que le `print.imageColor` du livre, pour cette seule image : une photographie dont le profil doit être ignoré, une autre lue à travers un profil attribué, une image en gris avec un autre engraissement. Dans le Sandbox, la fiche d’une image indique si elle est lue à travers son propre profil (« Couleur à l’impression »), comment ses gris s’accordent à la presse (« Gris à l’impression ») et quel profil lui est attribué (« Profil attribué », un fichier `.icc`) ; un paquet porte les profils attribués, celui du livre et ceux des images, dans son dossier `profiles/`. Les réglages du livre sont dans Préparation pour l’impression → Images.

```ts
{ id: 'archive-photo', kind: 'bitmap', bitmap: { fileId: 'photo.jpg', format: 'jpeg', width: 2400, height: 1600 },
  printColor: { embeddedProfile: 'ignore' } }
```


### Couleurs définies en CMJN

Une couleur écrite en CMJN garde ses valeurs exactes : `ColorValue.cmyk` (en pourcentage) est appliqué tel quel dans un rendu d’impression, et `hex` est son rendu à l’écran. Une entrée de palette définie en CMJN couvre toutes les couleurs qui lui sont liées.

```ts
colorPalette: [
  { id: 'brand', name: 'Brand', value: { hex: '#00a0e3', model: 'cmyk', cmyk: { c: 100, m: 0, y: 0, k: 0 } } },
],
```

### Couleurs en surimpression

Toute couleur peut être en surimpression dans un rendu d’impression : `overprint: true` sur un `ColorValue` imprime tout ce qui est peint avec elle (texte, filets, boîtes, fonds) par-dessus ce qui est dessous au lieu de le défoncer. Une couleur quadri s’écrit telle qu’elle se sépare, sous un état graphique en surimpression ; un ton direct surimprime sur la plaque de son encre, même là où la même encre dans une autre couleur défonce. Un noir à 100 % K en surimpression garde le traitement du noir : les grands aplats passent toujours en noir enrichi (`black.richBlack`). Un PDF RVB et l’écran l’ignorent. Placez-le sur l’entrée de palette pour que toute couleur qui lui est liée soit en surimpression, ses teintes comprises ; une couleur liée prend le réglage de l’entrée et n’a pas le sien. La palette d’une partie ou d’une section le garde : le texte dans la couleur de la partie est lui aussi en surimpression.

```ts
colorPalette: [
  { id: 'title', name: 'Title', value: { hex: '#c00020', model: 'cmyk', cmyk: { c: 0, m: 100, y: 80, k: 10 }, overprint: true } },
],
```

Un rendu d’impression reconnaît une couleur au hex que peint la mise en page, si bien qu’une couleur en surimpression ne partage jamais son hex avec une couleur qui défonce. Quand elles coïncident, celle en surimpression se décale d’un cran (1/255 sur un canal), comme le font les tons directs ; la couleur d’une partie pour une entrée en surimpression s’écarte de la même façon de toute couleur du livre qui défonce. Une couleur en surimpression qui ne dépose aucune encre (le blanc du papier, une encre à 0 %) disparaît à l’impression : le contrôle en amont la signale comme critique (`overprintWhite`). Un rendu qui compte plus de couleurs distinctes qu’il n’a de codes (quelque 25 millions) défonce les autres et avertit (`overprintsExhausted`). Dans le Sandbox, l’interrupteur « Surimprimer à l’impression » du sélecteur de couleur l’active.

`preflightDocument(doc, options)` exécute les contrôles sur un document mis en page et renvoie une liste de problèmes, chacun avec un `kind`, une `severity` (`'critical'`, `'warning'` ou `'info'`), l’index de page `pageIndex` absolu dans le livre, le `rect` fautif (en px de page) et, quand l’élément en a une, sa position dans la source. Les types sont `lowImageResolution`, `declaredPixelsMismatch`, `rgbImage`, `thinRule`, `smallProcessText`, `inkLimit`, `safeZone` et `nearTrim`. Sans `transform`, un neutre compte pour une encre et toute autre couleur pour trois, et l’encrage n’est pas vérifié ; avec une transformation, les décomptes et l’encrage sont exacts. La résolution d’une image est calculée à partir des pixels que déclare sa ressource, ou de ceux du fichier lui-même quand `imageSize(fileId)` les fournit (`bitmapInfo` sur les octets, ou l’image décodée) : une déclaration qui s’écarte de plus d’un pixel du fichier est signalée une fois comme `declaredPixelsMismatch`, un avertissement quand elle annonce plus de pixels que le fichier n’en a. `placedImageResolutions(doc, { resources, imageSize })` liste chaque image matricielle placée avec sa résolution effective en ppi, que le contrôle en amont soit activé ou non. Les étiquettes d’une figure comptent comme du texte pour `smallProcessText`, `inkLimit` et `safeZone`.

```ts
import { bitmapInfo, outputTransform, parseIccProfile, preflightDocument, resolvePrintConfig } from 'postext';
import { inspectPrintMaster } from 'postext-pdf';

const print = resolvePrintConfig(config.print);
const transform = outputTransform(parseIccProfile(fogra51Bytes), { intent: print.renderingIntent });
const issues = preflightDocument(doc, {
  print,
  transform,
  resources,                                    // pixel sizes of the bitmaps
  imageSize: (fileId) => bitmapInfo(bytesOf(fileId)),  // the files' real pixels
  imageColor: (fileId) => colourOf(fileId),     // 'rgb' | 'cmyk' | 'gray', from the file
});
if (issues.some((i) => i.severity === 'critical')) process.exit(1);

const master = await inspectPrintMaster(masterBytes);
// => { nonEmbeddedFonts: ['Helvetica'], rgb: true, transparency: false }
```

### Implémentation de référence

Le composant `PdfViewport` du Sandbox (`packages/postext-sandbox/src/viewport/pdf/PdfViewport.tsx`) relie les pièces ci-dessus dans un aperçu en direct doté de boutons de régénération, de téléchargement et d’impression, et constitue un bon point de départ pour toute intégration PDF dans le navigateur. Il construit le VDT au moyen du worker de mise en page partagé (voir [Exécuter la mise en page dans un Web Worker](/fr/docs/configuration-programmatic-usage#mise-en-page-dans-un-web-worker)) : un clic sur *Recalculer* ne fige donc pas l’interface pendant l’exécution du pipeline : le fil principal ne s’occupe que de `renderToPdf` (déjà rapide une fois le VDT disponible).
