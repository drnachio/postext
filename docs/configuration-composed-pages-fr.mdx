# Configuration : pages composées


## Gabarits de page

Une page composée est une page dont la forme vient d’un **gabarit** de la configuration et dont le contenu vient du Markdown placé sous un délimiteur de page `::::page{template="…"}`. Le gabarit définit des rectangles nommés, appelés **blocs** ; le Markdown envoie chaque morceau de contenu vers un bloc d’après son nom (son emplacement, attribut `slot`). La géométrie n’apparaît jamais dans le Markdown, et le texte du contenu n’apparaît jamais dans le gabarit. La propriété `pageTemplates` contient les gabarits du livre :

```ts
const config: PostextConfig = {
  calloutStyles: [{ id: 'caja-azul' }, { id: 'tab-titulo' }],
  pageTemplates: [
    {
      id: 'tema-cajas',
      decoration: {
        elements: [
          { kind: 'image', id: 'fondo', resourceId: '{attr.fondo}', decorative: true,
            placement: { anchor: { to: 'bleed', edge: 'top-left' }, size: { width: 'fill', height: 'fill' } } },
        ],
      },
      frames: [
        { name: 'titulo', takes: 'h1', style: 'tab-titulo' },
        { name: 'texto', flow: true },
        { name: 'dinero', style: 'caja-azul', padding: { right: { value: 62, unit: 'mm' } } },
        { name: 'dinero-fotos', layer: 2, width: { value: 60, unit: 'mm' },
          placement: { anchor: { to: '#dinero', edge: 'top-right' } } },
      ],
      groups: [
        { name: 'pagina', kind: 'stack', gap: { value: 6, unit: 'mm' }, frames: ['titulo', 'texto', 'dinero'] },
      ],
    },
  ],
};
```

### Blocs

Un bloc est un rectangle nommé qui reçoit du contenu composé. Son `name` est l’emplacement qu’indique le Markdown, et il est unique dans son gabarit (un groupe ne peut pas non plus prendre le nom d’un bloc, puisque les ancrages les désignent tous deux de la même façon).

Un bloc se place par sa cellule `grid` quand le gabarit a une grille, sinon par son `placement`, qui fonctionne comme celui d’un élément de maquette : un ancrage (`'container'` est la zone, `'page'`, `'bleed'`, ou `'#name'` pour un autre bloc ou groupe), un bord, un décalage et une taille. Un bloc ancré à un autre se déplace avec lui. Sans l’un ni l’autre, le bloc commence au coin supérieur gauche de la zone, sur toute sa largeur, et aussi haut que le prévoit sa règle de hauteur. La façon dont le contenu est versé dans les blocs, chaîné et rogné est décrite dans [Pages composées › Comment la page est composée](/fr/docs/composed-pages#comment-la-page-est-composée).

### Groupes

Un groupe est une pile (de haut en bas) ou une rangée (du début à la fin) de blocs qui se partagent l’espace et se déplacent ensemble. Dans un groupe, la position propre des blocs dans le sens du groupe est ignorée : le groupe les dispose dans l’ordre, avec `gap` entre eux. Quand le texte d’un bloc s’allonge, les blocs qui le suivent se décalent. Un groupe est une boîte à laquelle les blocs et le décor peuvent s’ancrer (`'#pagina'`).

### Comment les groupes se partagent l’espace

Un bloc déclare sa taille : une `height` fixe, ou `'auto'`, la hauteur de ce qu’il contient, maintenue entre `minHeight` et `maxHeight`. Pour un gabarit relevé sur une page imprimée, donnez à chaque boîte comme `minHeight` la hauteur qu’elle a sur la page : avec un texte court, la boîte reste telle qu’elle est dessinée, et un texte plus long l’agrandit. La page est mise en page deux fois au cours du même passage, une fois telle que le gabarit la déclare, une fois selon ce que demande son contenu, et les différences entre les deux forment le [journal de recomposition](/fr/docs/composed-pages#journal-de-recomposition).

**Pile.** Les blocs d’une pile se placent les uns sous les autres, chacun à sa hauteur, séparés par `gap`. Chacun garde sa position horizontale et sa largeur ; sa position verticale propre est ignorée.

- Un groupe sans `placement` ni `grid` à lui commence là où son premier bloc est placé (son `placement`, ou sa cellule `grid` dans un gabarit à grille) et descend aussi loin que ses blocs l’exigent, jusqu’au pied de la zone du gabarit. Quand un bloc grandit, les blocs qui le suivent descendent d’autant.
- Un groupe qui a sa propre boîte y dispose ses blocs. Quand ils demandent plus de place que la boîte n’en offre, les blocs dont le `shrink` dépasse 0 rendent de l’espace, ceux de plus basse `priority` en premier ; à priorité égale, chacun cède en proportion de son `shrink`, et aucun ne descend sous son `minHeight`. L’espace libre va aux blocs dont le `grow` dépasse 0, en proportion de cette valeur, jusqu’à leur `maxHeight` ; s’il n’y en a aucun, `align` place les blocs (`'end'` en pied, `'center'`, `'space-between'`). Un bloc du groupe sans placement propre prend la boîte du groupe pour zone.
- Quand plus rien ne peut céder, les blocs les plus proches du pied du groupe cèdent les premiers, chacun jusqu’à son `minHeight` ; un bloc de hauteur fixe la garde : un espace de réponse vide ou la place d’une image sous une boîte qui grandit reste donc sur la page, et c’est le texte de la boîte qui cède. Aucun bloc ne dépasse le pied du groupe : le bloc dont le contenu ne tient pas passe par les étapes d’ajustement (voir [Quand le contenu ne tient pas](#quand-le-contenu-ne-tient-pas)), et ce qui ne tient toujours pas y est coupé et signalé par `frameOverflow`. Un bloc réduit sous son `minHeight` ou sa hauteur fixe est signalé lui aussi, qu’il ait du contenu ou non.
- Un bloc en `height: 'fill'` demande son `minHeight` et prend l’espace libre comme s’il avait `grow: 1`.

**Rangée.** Les blocs d’une rangée se placent côte à côte à leurs largeurs déclarées, tous à la hauteur de la rangée : celle de la boîte du groupe ou, si le groupe n’a pas de boîte à lui, la plus grande des hauteurs que déclarent ses blocs : une `height` fixe, sinon un `minHeight` (un bloc `'auto'` n’en déclare pas plus), ou, s’ils n’en déclarent aucune, celle du contenu le plus haut (un bloc de hauteur fixe garde la sienne). Quand le texte d’un bloc dépasse la hauteur de la rangée, le bloc s’élargit : d’abord sur la largeur libre de la rangée, puis sur celle des autres blocs dont le `shrink` dépasse 0, ceux de plus basse `priority` en premier, sans jamais rendre l’un d’eux plus étroit que la largeur où son propre texte tient encore. La largeur prise est le plus petit nombre de millimètres entiers qui fait tenir le texte ; si toute la place disponible n’y suffit pas, le bloc n’en prend aucune, et une rangée sans boîte à elle gagne en hauteur. Des cartes en `height: 'auto'` avec un `minHeight` se partagent donc la largeur à cette hauteur, et la rangée ne grandit que si aucune n’a de largeur à céder. La largeur libre va aux blocs dont le `grow` dépasse 0, puis à `align`. Les rangées vont de gauche à droite.

**Blocs épinglés.** Un bloc en `pin: true` garde la boîte que le gabarit lui déclare, même quand le bloc auquel il est ancré grandit ou se déplace : une boîte dessinée pour tomber juste sur l’illustration y reste. Dans un groupe, un bloc épinglé garde sa place et les autres blocs passent au-delà, avec `gap` conservé de part et d’autre ; un bloc épinglé hors du groupe fait de même pour les blocs du groupe qu’il chevaucherait.

**Décor.** Un élément de décor ancré à un bloc (`anchor: { to: '#dinero' }`) suit le bloc quand celui-ci grandit ou se déplace. Un élément en `pin: true` reste là où le gabarit dessine ce bloc.

Le résultat ne dépend que du contenu de la page, du gabarit et de la typographie : la même entrée donne la même page, mesurée dans le même ordre, par les mêmes étapes. La négociation ne lit jamais une autre page ; modifier une page composée laisse donc toutes les autres telles qu’elles étaient, tant que le contenu reste sur sa page.

**Tenir des blocs au pied d’une carte (depuis postext 1.42).** Un bloc ancré sous le texte qui le surmonte suit ce texte : dans une édition où le texte compte une ligne de moins ou de plus, les blocs situés dessous montent ou descendent, tandis que ce que dessine le gabarit (une carte, un bandeau, le pied) reste en place. Pour que des blocs restent au pied d’une carte, là où le gabarit les met, réunissez les blocs de la carte en une pile dotée d’une boîte de la hauteur de la carte. Les blocs placés au-dessus de ceux qu’on retient prennent l’espace en trop (`grow: 1`) et le rendent (`shrink: 1`) ; les blocs retenus déclarent un `minHeight`. Un texte plus court laisse les blocs retenus où ils étaient. Un texte plus long est comprimé au-dessus d’eux : ils gardent leur `minHeight`, le texte du dessus est réduit et, si cela ne suffit pas, la mise en page signale `frameOverflow` et le journal de recomposition note `textScaled` et `overflow` pour le bloc du dessus. Un bloc ancré au pied du conteneur (`bottom-left`) garde aussi sa place, mais rien ne le lie aux blocs qui le surmontent : un texte plus long le recouvre, rien n’est comprimé pour lui et le chevauchement n’est pas signalé.

```json
{
  "frames": [
    { "name": "texto", "grow": 1, "shrink": 1 },
    { "name": "mapa", "minHeight": { "value": 60, "unit": "mm" } }
  ],
  "groups": [{
    "name": "tarjeta", "frames": ["texto", "mapa"], "gap": { "value": 4, "unit": "mm" },
    "placement": {
      "anchor": { "to": "container", "edge": "top-left" },
      "size": { "width": "fill", "height": { "value": 140, "unit": "mm" } }
    }
  }]
}
```

Le bloc qui grandit est aussi haut que la place disponible, quoi qu’il contienne ; un style à fond visible le remplirait donc tout entier : dessinez la carte dans le décor du gabarit et laissez sans style le bloc qui reçoit le texte.

### Grilles qui répètent un jeu de blocs

Une page de cartes photo, une page de fiches d’activité ou une page de portraits avec un nom sous chacun, c’est la même carte dessinée de nombreuses fois. Un groupe en grille avec `repeat` la dessine une seule fois dans le gabarit : les blocs d’une carte, appelés jeu de blocs, que la grille pose une fois par élément que lui donne le Markdown de la page. Le nombre de cartes d’une page dépend alors du Markdown, et une traduction qui ajoute une carte n’a pas besoin d’un nouveau gabarit. Depuis postext 1.48.

```ts
frames: [
  { name: 'titulo', takes: 'h1' },
  { name: 'foto', style: 'marco', placement: { anchor: { to: '#titulo', edge: 'below' }, offset: { y: { value: 6, unit: 'mm' } } } },
  { name: 'pie', style: 'pastilla', width: 'auto', layer: 2, overlap: 'allow',
    placement: { anchor: { to: '#foto', edge: 'bottom' }, offset: { y: { value: 4, unit: 'mm' } } } },
],
groups: [{
  name: 'fotos', kind: 'grid', columns: 3,
  columnGap: { value: 6, unit: 'mm' }, rowGap: { value: 10, unit: 'mm' },
  repeat: { frames: ['foto', 'pie'] },
}],
```

- **Le jeu.** Le premier bloc de `repeat.frames` est le bloc **principal** de la cellule : il prend la largeur de la cellule et garde sa propre règle de hauteur (`'auto'` est la hauteur de son contenu, entre `minHeight` et `maxHeight`). Les autres blocs du jeu sont posés comme le gabarit les dessine, ancrés au bloc principal ou les uns aux autres : ici, la pastille de légende est suspendue au pied de la photo. Un bloc du jeu ancré à un bloc extérieur au jeu reste là où le met cet ancrage.
- **Éléments.** Chaque morceau `:::frame{slot="foto"}` de la page est un élément : les morceaux d’un emplacement répété ne sont pas réunis. Dans le morceau, un élément qui désigne un membre du jeu (`:::frame{slot="pie"}`, `::resource{… slot="pie"}`) va dans ce membre de la même carte ; le reste va dans le bloc principal. Voir [Pages composées › Emplacements répétés](/fr/docs/composed-pages#emplacements-répétés).
- **Instances.** Les blocs de chaque carte s’appellent `<frame>[n]`, numérotés à partir de 1 : `foto[2]` et `pie[2]` forment la deuxième carte. Les avertissements, le journal de recomposition, la carte des sources et le Sandbox utilisent ces noms, les identifiants des blocs sont `cp<n>:foto[2]`, et un élément de décor ou un connecteur peut s’ancrer à `'#foto[2]'`. Le `to: '#foto[*]'` d’un connecteur atteint toutes les cartes de la page. Un élément ancré à `'#foto'` lit la boîte de la grille.
- **Cellules.** Les cellules remplissent les rangées depuis le côté de début : sur une page de droite à gauche, la première carte est donc à droite. Une rangée est aussi haute que sa plus haute cellule, en comptant ce qui dépasse au-dessus du bloc principal (un onglet) et au-dessous (une pastille) ; `rowAlign` place les cellules moins hautes. La boîte de la grille est son propre `placement` ou sa cellule de `grid` ; sans l’un ni l’autre, elle commence là où le gabarit dessine le bloc principal et va jusqu’au bord droit et au pied de la zone.
- **Quand les cartes ne tiennent pas.** Une rangée qui dépasse le pied de la grille y est coupée, chaque carte passe seule par les étapes d’ajustement, et la dernière carte coupée signale `frameOverflow`. Avec `overflow.continueIn` sur le bloc principal (`'next-page'`, `'template:<id>'`), la grille se poursuit **par rangées entières** : la première rangée qui ne tient pas, et toutes celles qui la suivent, sont posées sur la page ajoutée, dans la grille d’un gabarit qui répète le même jeu de blocs. Une cellule plus haute que la grille entière déclenche un avertissement au lieu de se poursuivre sans fin.
- **`max`.** Les éléments au-delà de `repeat.max` vont dans le bloc de flux, ou après la page quand le gabarit n’en a pas, et chacun déclenche `repeatOverflow`.

Une grille sans `repeat` pose les blocs qu’elle liste, un par cellule, dans l’ordre d’écriture. Un bloc d’un jeu répété listé dans un autre groupe y est sauté (`groupFrameTwice`), et un nom que le gabarit n’a pas est un `groupFrameUnknown`. `grow` et `shrink` ne s’appliquent pas aux rangées d’une grille, ni `redistribute` à ses cartes.

### Modules

Une page de manuel empile souvent des blocs qui reviennent dans tout le livre, dans un autre ordre : un encadré avec une photo à côté, un arbre de trois idées, une grille de quatre photos sous un titre. Dessiner un gabarit pour chaque ordre multiplie les gabarits. Un **module** est l’un de ces blocs dessiné une seule fois : un gabarit avec `role: 'module'`, qui contient des blocs, des groupes et un décor (connecteurs compris), et pas de page à lui. Un gabarit de page prend des modules dans un groupe avec `modules: true` ; le Markdown de la page indique quels modules il contient et dans quel ordre (voir [Pages composées › Modules dans une page](/fr/docs/composed-pages#modules-dans-une-page)). Depuis postext 1.48.

```ts
pageTemplates: [
  { id: 'tema', frames: [{ name: 'titulo', takes: 'h1' }],
    groups: [{ name: 'cuerpo', modules: true, gap: { value: 8, unit: 'mm' },
      placement: { anchor: { to: '#titulo', edge: 'below' }, offset: { y: { value: 6, unit: 'mm' } },
        size: { width: 'fill', height: 'fill' } } }] },
  { id: 'arbol', role: 'module',
    frames: [
      { name: 'raiz', style: 'nodo', width: { value: 56, unit: 'mm' }, placement: { anchor: { to: 'container', edge: 'top' } } },
      { name: 'izq', style: 'nodo', width: { value: 56, unit: 'mm' },
        placement: { anchor: { to: '#raiz', edge: 'below' }, offset: { x: { value: -44, unit: 'mm' }, y: { value: 10, unit: 'mm' } } } },
      { name: 'der', style: 'nodo', width: { value: 56, unit: 'mm' },
        placement: { anchor: { to: '#raiz', edge: 'below' }, offset: { x: { value: 44, unit: 'mm' }, y: { value: 10, unit: 'mm' } } } },
    ],
    decoration: { elements: [
      { kind: 'connector', id: 'ramas', routing: 'tree', from: { to: '#raiz' }, to: [{ to: '#izq' }, { to: '#der' }] },
    ] } },
],
```

- **Ce que contient un module.** Des blocs, des groupes (y compris une grille qui répète), un décor et des connecteurs. Il n’a ni `area`, ni `header`, ni `footer`, ni `variants`, ni `spread`, ni `gutter`, ni `overflowTemplate` : chacun d’eux est signalé comme `unknownConfigValue` et ignoré. `extends` fonctionne entre modules (un gabarit qui étend un module est un module).
- **Sa boîte.** Un module est aussi large que son groupe et aussi haut que ses blocs vont loin ; le groupe empile les modules depuis son haut, avec `gap` entre eux. Dans un module, `'container'` est la boîte du module, pour ses blocs (`'fill'` et les pourcentages aussi) et pour son décor : un fond dimensionné à `{ to: 'container', edge: 'bottom' }` couvre le module, quelle que soit la hauteur que lui donnent ses mots.
- **Noms.** Les blocs, groupes et éléments d’un module sont rangés sous le nom de l’instance du module : `<name>.<frame>`, avec le nom que donne le Markdown (`name="ramas"`) ou, à défaut, `<template>[n]`, le rang du module parmi les modules de ce gabarit sur la page (`arbol[2].raiz`). Les ancrages, `next`, `continueIn: '#x'` et les connecteurs d’un module sont réécrits vers ses propres blocs : deux arbres sur une même page ne se relient donc jamais l’un à l’autre. L’identifiant d’un bloc s’écrit `cp0:arbol[2].raiz`.
- **Quand les modules ne tiennent pas.** Un module qui dépasse le pied du groupe y est coupé et ses blocs passent par les étapes d’ajustement ; `frameOverflow` est déclenché une fois pour le groupe. Avec `overflow.continueIn` sur le groupe de modules (`'next-page'` ou `'template:<id>'`), le premier module qui ne tient pas et tous ceux qui le suivent se poursuivent **entiers** sur la page ajoutée, sous les mêmes noms, en haut du groupe de modules de cette page. Dans une rangée ou une grille de modules, une rangée continue entière : ses modules ne sont jamais partagés entre deux pages.
- **Côte à côte.** Un groupe de modules avec `kind: 'row'` pose ses modules du début à la fin, chacun à la `width` de son gabarit (une longueur, `{ percent: 48 }`, ou `'fill'`, une part égale de ce qui reste), la rangée aussi haute que son module le plus haut ; `kind: 'grid'` les pose en `columns` colonnes égales, rangée après rangée. `rowAlign` place un module moins haut que sa rangée. Les rangées partent du côté où commence la ligne : une page de droite à gauche pose le premier module à droite. Depuis postext 1.50.
- **Groupes dans la pile.** Un groupe de modules avec `within: '<pile>'` se place dans la pile de modules de la page, et `templates` dit quels modules il reçoit : chaque suite de ces modules dans le Markdown forme une rangée ou une grille de la pile, là où vient son premier module. Avec les groupes ci-dessous, deux blocs `aviso` suivis de quatre blocs `tarjeta` donnent une rangée de deux encadrés sur une grille de 2 × 2 cartes, et le Markdown ne contient que des blocs `:::module`.
- **Des groupes dans des groupes.** Depuis postext 1.51 `within` peut nommer n’importe quel groupe de modules, une rangée ou une grille aussi, à n’importe quelle profondeur. Avec `banda` une rangée dans `cuerpo` et `columna` une pile dans `banda`, un encadré suivi de deux cartes se pose à côté d’une colonne des deux cartes. Un bloc de la page ancré à `#banda` est posé après les modules.
- **Partager une rangée.** Depuis postext 1.51 la place qu’une rangée de modules laisse se partage selon le `grow` de chaque module, et une rangée plus large que son groupe cède de la largeur selon `shrink`.
- **Pas encore.** Un module dans un module (`moduleNested`) et des cellules `grid` de gabarit dans un module.

```ts
groups: [
  { name: 'cuerpo', modules: true, gap: { value: 8, unit: 'mm' } },
  { name: 'par', modules: true, within: 'cuerpo', kind: 'row', templates: ['aviso'], gap: { value: 6, unit: 'mm' } },
  { name: 'tarjetas', modules: true, within: 'cuerpo', kind: 'grid', columns: 2, templates: ['tarjeta'], gap: { value: 6, unit: 'mm' } },
],
```

### Quand le contenu ne tient pas

Quand le contenu d’un bloc est plus haut que la place que lui donne son groupe, la mise en page essaie dans l’ordre les [étapes d’ajustement](/fr/docs/composed-pages#quand-le-contenu-ne-tient-toujours-pas) et s’arrête à la première qui le fait tenir : l’espace libre jusqu’à `maxHeight`, le groupe qui pousse et qui cède, des images plus petites, les autres blocs du groupe ramenés à leur minimum, un texte plus petit, la suite sur une autre page. Ces réglages du bloc fixent jusqu’où chaque étape peut aller :

- `maxHeight` sur un bloc de `height` fixe : le bloc peut grandir jusque-là avant toute réduction.
- `minHeight` sur les autres blocs du groupe : jusqu’où ils rendent de l’espace ; un bloc ne descend jamais sous ce que demande son propre contenu.
- `fit.scaleImages` et `fit.imageMinScale` : si les images du bloc et de son groupe peuvent être réduites, et jusqu’à quelle échelle (80 % par défaut).
- `fit.shrinkText` et `fit.minScale` : si le texte du bloc peut être réduit, et jusqu’à quelle échelle (90 % par défaut). L’échelle est la même pour le corps, l’interlignage et les espacements ; le bloc garde sa taille.
- `overflow.continueIn` : où le contenu se poursuit quand rien de tout cela ne suffit, soit un autre bloc, soit une autre page (`'next-page'`, `'template:<id>'`, `'page:<id>'`), où le texte reprend à sa taille normale après l’`overflow.mark` du morceau. Un bloc qui peut continuer sur une autre page le fait avant que ses images et son texte ne soient réduits, sauf si son `fit.preferContinue` vaut `false`.

Les échelles vont par paliers de 2,5 % et la mise en page prend la plus grande qui convient : un texte trop long d’une ligne est composé à 97,5 %, pas au minimum. Un encadré qui doit garder son corps prend `fit: { shrinkText: false }` ; une page dont les images doivent garder leur taille met `fit: { scaleImages: false }` sur les blocs de son groupe :

```ts
{ name: 'recuadro', style: 'recuadro', height: { value: 63, unit: 'mm' }, maxHeight: { value: 75, unit: 'mm' },
  fit: { minScale: 0.85, imageMinScale: 0.9 } }
```

Ce qui ne tient toujours pas est signalé par `frameOverflow`, avec les étapes essayées et des propositions qui indiquent leurs valeurs : voir [L’avertissement et ses propositions](/fr/docs/composed-pages#lavertissement-et-ses-propositions).

### Héritage et variantes

Un gabarit doté d’`extends` part du gabarit qu’il désigne (qui peut lui-même en étendre un autre) et ne change que ce qu’il précise :

- Un champ comme `area`, `header` ou `overflowTemplate` remplace celui du parent. `grid` se fusionne clé par clé. `spread`, `gutter` et `role` sont hérités aussi ; `id`, `name` et `extends` sont propres au gabarit.
- `frames` et `groups` se fusionnent **par nom** : une entrée qui porte le nom d’une entrée héritée change les champs qu’elle précise et garde les autres (`fit`, `overflow` et `padding` se fusionnent clé par clé ; `placement` est remplacé en entier) ; `remove: true` la supprime ; un nom nouveau s’ajoute après les entrées héritées.
- Les éléments du décor se fusionnent par `id` de la même façon ; un élément avec un identifiant nouveau, ou sans identifiant, s’ajoute. Depuis postext 1.42, `{ id: 'tete-paire', remove: true }` dans `decoration.elements` d’un gabarit enfant ou d’une variante retire l’élément hérité portant cet `id`, comme `remove: true` le fait pour un bloc ; un `id` que le gabarit n’hérite pas ne change rien. Un nouvel élément du même `id` peut suivre le retrait dans la même liste.

`variants.recto` et `variants.verso` s’écrivent comme un gabarit et se fusionnent de la même façon, sur une page de droite ou de gauche. Elles s’appliquent après toute la chaîne d’`extends`, la variante de la racine en premier. Une double page a les deux côtés : aucune variante ne s’y applique.

Un élément de `variants.recto` avec `parity: 'even'`, ou de `variants.verso` avec `'odd'`, n’est jamais dessiné : `unknownConfigValue`.

```ts
pageTemplates: [
  { id: 'tema', frames: [{ name: 'texto', flow: true }, { name: 'margen', width: { value: 30, unit: 'mm' },
      placement: { anchor: { to: 'container', edge: 'top-left' } } }],
    variants: { recto: { frames: [{ name: 'margen', placement: { anchor: { to: 'container', edge: 'top-right' } } }] } } },
  { id: 'tema-sin-margen', extends: 'tema', frames: [{ name: 'margen', remove: true }] },
]
```

Une valeur égale à une valeur par défaut n’est jamais abandonnée quand le Sandbox enregistre un gabarit : dans un gabarit qui en étend un autre, ou dans une variante, elle remplace la valeur du parent.

Depuis le code, `resolvePageTemplate(config, id, { parity })` renvoie un gabarit avec sa chaîne fusionnée, la variante du côté appliquée, toutes les valeurs par défaut remplies et chaque référence réglée comme le décrivent les avertissements ci-dessous ; `validatePageTemplates(config)` renvoie les avertissements.

### Dessiné quand la page le dit

Un élément de la décoration, et un élément du `header` ou du `footer` du gabarit, peut porter `when` ou `unless`, chacun nommant un attribut du délimiteur de la page. `when: 'folio'` ne dessine l’élément que sur les pages dont le délimiteur pose `folio` ; `unless: 'frontmatter'` le retire des pages dont le délimiteur pose `frontmatter`. Un délimiteur pose un attribut quand il l’écrit seul (`::::page{template="pagina" frontmatter}`) ou avec une valeur autre que `false`. Un même gabarit sert alors aux pages liminaires, sans folio ni bandeau, et aux pages du corps, qui portent les deux : le Markdown dit ce qu’est la page, le gabarit garde le dessin. Depuis postext 1.50.

```ts
decoration: { elements: [
  { kind: 'box', id: 'band', unless: 'frontmatter',
    placement: { anchor: { to: 'page', edge: 'top-left' }, size: { width: 'fill', height: { value: 12, unit: 'mm' } } },
    style: { backgroundColor: { hex: '#2a6f97' } } },
  { kind: 'text', id: 'folio', when: 'folio', content: '{pageNumber}',
    placement: { anchor: { to: 'page', edge: 'bottom-center' }, offset: { y: { value: -8, unit: 'mm' } } } },
] }
```

- Un élément ancré à un élément retiré, ou dont la taille va jusqu’à lui, est retiré aussi.
- Avec les deux clés, l’élément est dessiné là où le délimiteur pose l’attribut de `when` et pas celui de `unless`.
- Les titres courants du document et ceux d’une section les lisent aussi. Une page qui n’est pas composée n’a pas de délimiteur et ne pose rien. Les dessins de titre, de partie et d’encadré les ignorent.
- Une valeur qui n’est pas un texte non vide, ou une valeur écrite dans un dessin de titre, de partie ou d’encadré, est signalée par `unknownConfigValue`, et l’élément est dessiné comme s’il n’en avait pas. `postext check` ajoute une note, `conditionNeverMet`, pour un `when` ou un `unless` sur un attribut qu’aucune page du livre ne pose : cet élément n’est jamais dessiné, ou toujours. De même pour un `{attr.x}` que rien ne définit : il reste vide.
- Une fois le livre mis en page, une page qui ne dessine rien d’un folio ou d’un titre courant (un texte de `header` ou de `footer`, un texte du décor qui lit `{pageNumber}`, un nom courant ou `{attr.x}`) que dessinent la plupart des pages de son gabarit et de son côté est signalée par `folioMissing`, avec la page, le gabarit et l’élément. Une page dont le délimiteur coupe l’élément, ou dont le gabarit n’a pas cet élément, n’entre pas dans le compte. Depuis postext 1.53.
- Dans le Sandbox, chaque fiche d’élément d’un titre courant et de la décoration d’un gabarit a les champs **Dessiné quand la page le dit** et **Pas dessiné quand la page le dit**, dont les choix sont les attributs des délimiteurs du livre.

### Ce que la mise en page applique

La mise en page applique le placement et les tailles de chaque bloc (grille, ancrages, `min`/`max`, `verticalAlign`), son style et son `padding`, `columns`, `rules`, `layer`, `rotate`, `exclude` (et son `wrap`), `flow`, `takes`, `next`, `overflow.continueIn` (`"#frame"`, `"next-page"`, `"template:<id>"`, `"page:<id>"`) avec `overflow.mark` et `overflow.fromMark`, et son `fit` (la réduction du texte et des images des étapes d’ajustement, voir [Quand le contenu ne tient pas](#quand-le-contenu-ne-tient-pas)) ; la négociation de l’espace dans un groupe (`grow`, `shrink`, `priority`, `pin`, et le `gap` et l’`align` du groupe, voir [Comment les groupes se partagent l’espace](#comment-les-groupes-se-partagent-lespace)) ; et l’`area`, la `grid`, le `decoration`, le `header`, le `footer`, les `variants`, `spread` et l’`overflowTemplate` du gabarit. Depuis postext 1.42, elle applique aussi la `palette` du gabarit, le `look` d’un bloc et la largeur `'auto'` (celle de la plus longue ligne du bloc). Le `writingMode` et la `direction` d’un bloc sont appliqués depuis postext 1.39. Depuis postext 1.48, elle applique les groupes en grille et leur `repeat`, les groupes de modules et les gabarits de module, les connecteurs et les éléments tracé du décor, et l’`overlap` d’un bloc. Est lu et vérifié, mais pas encore appliqué : le `bodyStyle` du gabarit.

### Doubles pages

Dans un gabarit de double page, toutes les coordonnées portent sur la feuille de ses deux pages, le dos au milieu : `area`, `grid`, les ancrages à `container`, `page` et `bleed` et les tailles `fill` se rapportent à la double largeur. `bleed` atteint la tête, le pied et les deux bords extérieurs, jamais le dos. La frise chronologique en double page d’un manuel tient en un seul gabarit :

```ts
pageTemplates: [{
  id: 'linea-tiempo',
  spread: true,
  gutter: { value: 10, unit: 'mm' },
  grid: { columns: 6, rows: 12, columnGap: { value: 12, unit: 'mm' }, rowGap: { value: 3, unit: 'mm' } },
  frames: [
    { name: 'titulo', takes: 'h1', style: 'tab-titulo' },
    { name: 'texto', flow: true, width: { value: 196, unit: 'mm' },
      placement: { anchor: { to: '#titulo', edge: 'below' } } },
    { name: 'recuadro', style: 'recuadro', grid: { col: 4, row: 1, cols: 3, rows: 4 }, height: 'auto' },
    { name: 'banda-1', style: 'banda', grid: { col: 1, row: 5, cols: 3 }, height: { value: 8, unit: 'mm' } },
    { name: 'banda-2', style: 'banda', crossGutter: true, width: 'fill', height: { value: 8, unit: 'mm' },
      placement: { anchor: { to: '#banda-1', edge: 'right-of' }, offset: { x: { value: 2, unit: 'mm' } } } },
    { name: 'era-1', style: 'era', grid: { col: 1, row: 6, rows: 2 }, height: 'auto' },
    // … de era-2 à era-6, une colonne de la grille chacune, et les notes sous la frise
    { name: 'tira', crossGutter: true, grid: { col: 1, row: 8, cols: 6, rows: 3 } },
  ],
}]
```

Un écart entre colonnes plus large que le `gutter` tient les fiches d’une grille symétrique à l’écart du dos : aucune n’est déplacée. Le second bandeau et la frise d’images ont `crossGutter` pour le traverser : chacun appartient à la page qui contient son centre et est dessiné sur les deux. Tous les mots de la page, y compris les noms des époques sur les onglets, restent dans le Markdown.

Dans un livre vertical (`vertical-rl`), la double page se compose dans le repère du flux des pages, comme ses pages composées seules : le haut d’une page est le bord droit de la feuille et les lignes descendent : le `x` du gabarit descend donc le long de la feuille et son `y` va du bord droit de la feuille vers le gauche. La feuille est la page de droite suivie de celle de gauche le long de `y`, le dos est une ligne qui traverse le gabarit, et `gutter`, `crossGutter` et la coupe entre les pages se rapportent à cet axe ; le décor se compose toujours sur la feuille physique et se coupe au dos. Une frise horizontale dessinée pour un livre horizontal sort tournée dans un livre vertical : écrivez le gabarit d’un livre vertical dans le repère de son flux. Depuis postext 1.38. Une fiche qui doit se lire dans la largeur de la feuille prend `writingMode: 'horizontal-tb'` : elle est composée à l’horizontale et se tient droite sur la page verticale (depuis postext 1.39).

### Connecteurs

Un connecteur est une ligne du décor qui relie des blocs : les branches d’un arbre, un organigramme, les descentes d’une frise chronologique, les flèches d’un logigramme, le trait par lequel une note désigne un endroit d’une carte. Il est posé une fois que les blocs ont leur boîte définitive : il suit donc un texte qui s’allonge, une édition aux mots plus longs ou un groupe qui déplace ses blocs, et il est dessiné comme une ligne vectorielle dans toutes les sorties, si bien que le gabarit n’a besoin d’aucune image des lignes. Les connecteurs sont des éléments du `decoration` d’un gabarit de page ou d’un module ; les titres courants et les maquettes de titre n’ont pas de blocs à relier, et un connecteur placé là est signalé (`unknownConfigValue`) et n’est pas dessiné. Depuis postext 1.48.

```ts
decoration: {
  elements: [
    { kind: 'connector', id: 'ramas', routing: 'tree', radius: { value: 2, unit: 'mm' },
      width: { value: 1.25, unit: 'pt' }, from: { to: '#raiz' }, to: [{ to: '#a' }, { to: '#b' }], endCap: 'arrow' },
  ],
},
```

**Extrémités absentes.** Une extrémité sur un bloc que la page ne montre pas (replié, facultatif et vide, une carte au-delà des éléments de la page, un point de l’image que son bloc coupe) est laissée de côté : un arbre garde ses autres enfants, et le journal de recomposition de la page le note (`connectorDropped`). S’il ne reste ni `from` ni `to`, rien n’est dessiné.

**Peinture.** Les connecteurs sont peints comme des tracés vectoriels : sur le canvas, dans le PDF, dans la visionneuse HTML et l’EPUB à mise en page fixe, et comme un artefact de mise en page dans un PDF balisé ; l’EPUB recomposable les omet avec le reste du décor. Un connecteur avec une extrémité `anchor` est peint sur tous les blocs de la page, si bien qu’une ligne qui pointe dans une image se voit sur le bloc de l’image sans `layer` ; les autres connecteurs restent avec le décor, sous les blocs. `over: true` fait passer une ligne entre blocs au-dessus, `over: false` garde dessous une ligne qui pointe. Sur une double page, un connecteur entre des blocs des deux pages traverse le dos et y est coupé comme le reste du décor ; sur une page de droite à gauche, `start` et `end` suivent le flux en miroir.

```ts
frames: [
  { name: 'mapa', width: { value: 118, unit: 'mm' } },
  { name: 'nota', style: 'nota', width: { value: 44, unit: 'mm' } },
],
decoration: { elements: [
  { kind: 'connector', id: 'a-lago', from: { to: '#nota', side: 'end' },
    to: { to: '#mapa', anchor: 'lago', gap: { value: 1.2, unit: 'mm' } }, endCap: 'dot' },
] },
```

**Vérifications.** Une extrémité dont le `to` ne désigne rien est un `frameAnchorUnknown` (sur `…/from/to` ou `…/to/<k>/to`) et est laissée de côté ; `[*]` n’est valable que dans `to` et sur un bloc répété. Une `anchor` qu’aucune image du bloc n’a est un `labelAnchorUnknown`, avec l’identifiant du connecteur. Un mot hors des choix de `routing`, `startCap`, `endCap` ou `side`, et un `at` hors de l’intervalle 0 à 1, sont des `unknownConfigValue`. Une `opacity` qui n’est pas un nombre de 0 à 1 est aussi un `unknownConfigValue` (un nombre hors de l’intervalle y est ramené).

## Apparences de bloc

Une grille de cartes photo dont les pastilles ne diffèrent que par la couleur, ou une page d’encadrés en une douzaine de teintes, garde un seul style d’encadré et un seul gabarit : les couleurs vont dans `frameLooks`, une liste d’apparences nommées, et le Markdown en désigne une sur chaque morceau qui la porte. Depuis postext 1.50.

```ts
frameLooks: [
  { id: 'rojo', name: 'Red pill', background: { hex: '#e63946', model: 'hex' }, body: { color: { hex: '#ffffff', model: 'hex' } } },
  { id: 'verde', background: { hex: '#6a994e', model: 'hex' } },
  { id: 'marino', border: { color: { hex: '#264653', model: 'hex' } } },
]
```

## Styles d’étiquette

La propriété `labelStyles` définit des apparences nommées pour les étiquettes posées sur une image : les mers et les villes d’une carte, les parties d’un schéma. Une étiquette se place sur une ancre de l’image (un point enregistré avec la ressource, comme les locuteurs de la bande dessinée) et prend le style que désigne l’ancre ou l’étiquette. Dans le Sandbox, ils se modifient sous **Maquette › Figures et tableaux › Styles d’étiquette** (depuis postext 1.42). Renommer un style à cet endroit réécrit les ancres et les lignes `::label` qui le nomment (depuis postext 1.43).

```ts
labelStyles: [
  { id: 'mar', fontStyle: 'italic', textTransform: 'uppercase', letterSpacing: 0.12,
    color: { hex: '#2b6ca3', model: 'hex' } },
  { id: 'ciudad', fontWeight: 600, halo: { color: { hex: '#ffffff', model: 'hex' }, width: { value: 0.6, unit: 'pt' } } },
]
```

`start` et `end` suivent la direction de l’étiquette : dans une étiquette arabe, `start` est son bord droit. Une ancre partagée par les éditions de gauche à droite et de droite à gauche d’une même carte se lit mieux avec l’étiquette centrée au-dessus ou au-dessous du point. Une étiquette avec une `width` se coupe entre les mots ; un mot plus large que la justification réduit toute l’étiquette, jusqu’au `minScale` de son style. La façon dont les étiquettes sont dessinées est décrite dans [Pages composées](/fr/docs/composed-pages).

Un trait de rappel quitte l’étiquette par le côté de sa boîte (son fond, sinon ses lignes) qui fait face au point en travers du plus large écart, depuis le milieu de ce côté : la ligne ne traverse donc jamais les mots de l’étiquette, même tournée. Un point situé sous la boîte de l’étiquette, ou un trait plus court que sa marque d’extrémité, ne dessine rien. Les traits de rappel sont peints sous les étiquettes, avec l’image, dans toutes les sorties qui dessinent les étiquettes, et ils suivent l’image quand elle est recadrée, mise à l’échelle, mise en miroir ou posée sur une double page.

```ts
anchors: [
  { id: 'peaks', x: 0.42, y: 0.8, labelAt: { x: 0.62, y: 0.6 }, style: 'name', leader: true },
  { id: 'lake', x: 0.531, y: 0.865, labelAt: { x: 0.76, y: 0.93 }, style: 'name', leader: { routing: 'elbow' } },
],
```

## Avertissements des gabarits de page

Ailleurs, le moteur ignore une clé qu’il ne connaît pas. Les gabarits de page et les styles d’étiquette sont au contraire vérifiés, et chaque problème devient un avertissement de configuration dans `postext check` et dans le panneau Vérifications du Sandbox. Le `path` de ces avertissements est un pointeur JSON vers le champ en cause : `/pageTemplates/3/frames/2/style`, `/pageTemplates/0/variants/recto/frames/1/next`, `/resources/4/anchors/0/style`. Quand le champ a été hérité, le pointeur désigne le gabarit qui l’a défini. Un avertissement qui cite un identifiant ou un nom inexistant propose aussi le plus proche qui existe.

Une clé mal orthographiée d’un gabarit, d’un bloc, d’un groupe, d’une grille, de `fit`, d’`overflow`, d’une variante ou d’un style d’étiquette est un `unknownConfigKey` ; un mot hors des choix d’un réglage (`area`, `verticalAlign`, `exclude`, `wrap`, `takes`, `kind`, `align`, `writingMode`, `direction`, `fontStyle`, `textTransform`, `overlap`, `rowAlign`, le `routing`, les extrémités et le `side` d’un connecteur, les extrémités et le `routing` d’un trait de rappel) est un `unknownConfigValue`, et le réglage garde sa valeur par défaut. Un gabarit sans `id`, ou un bloc ou un groupe sans `name`, est ignoré avec un `unknownConfigValue` sur ce champ. Les apparences de bloc (`frameLooks`) sont vérifiées de la même façon : une apparence sans `id` est ignorée, et une clé que le `look` d’un bloc n’a pas est un `unknownConfigKey`.
