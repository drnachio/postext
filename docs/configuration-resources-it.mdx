# Configurazione: risorse e tabelle


## Tipi di risorsa

Un **tipo di risorsa** è una categoria definibile dall’utente (*Figura*, *Tabella*, *Diagramma*, *Listato*…) che stabilisce come le risorse di quel tipo vengono numerate, come si scrive la loro didascalia e come vi si rimanda. L’elenco si trova in `config.resourceTypes`; la Sandbox lo modifica in **Grafica → Figure e tabelle → Numerazione e posizione**.

Quando `config.resourceTypes` non è impostato, Postext fornisce tre tipi predefiniti integrati: **Figura**, **Tabella** e **Video**, ciascuno numerato per conto suo con `{h1}.{n}` (`{h1}-{n}` in cinese, giapponese e arabo), che riparte a ogni titolo di livello 1, e contatori decimali. Un elenco senza un tipo `video` (un libro salvato prima che esistessero i video) numera comunque le risorse video di tipo `video`: per loro viene aggiunto il tipo Video integrato (`effectiveResourceTypes(config, resources)`), e `defaultVideoResourceType(locale)` lo restituisce da solo. I nomi sono nella lingua del documento: `config.locale`, altrimenti `bodyText.hyphenation.locale`, altrimenti l’inglese (vedi [Lingua del documento](/it/docs/configuration-language#lingua-del-documento)).

I tipi predefiniti integrati tengono conto della lingua. La funzione esportata `defaultResourceTypes(locale = 'en')` localizza i nomi dei tipi, le etichette brevi e i prefissi delle didascalie nella lingua del documento: l’inglese dà *Figure*/*Fig.* e *Table*/*Tab.*; lo spagnolo dà *Figura*/*Fig.* e *Tabla*/*Tabla*; anche francese, tedesco, italiano, portoghese, catalano, olandese, cinese (semplificato e tradizionale), giapponese e arabo hanno i loro (la tabella in [Lingua del documento](/it/docs/configuration-language#lingua-del-documento) li elenca). I tag regionali come `es-ES` valgono per la loro lingua, e qualsiasi lingua senza traduzioni ripiega sull’inglese. In ogni lingua il contatore riparte a ogni `h1` e conta in decimale. Il modello è `'{h1}.{n}'`, tranne in cinese, giapponese e arabo, che uniscono il numero del capitolo e il contatore con un trattino: `'{h1}-{n}'` (图1-1, 図1-1). Ogni chiamata restituisce oggetti nuovi, quindi puoi modificare liberamente il risultato:

```ts
import { defaultResourceTypes } from 'postext';

const types = defaultResourceTypes('es');
// => [{ id: 'figure', name: 'Figura', shortLabel: 'Fig.', captionPrefix: 'Figura',
//       numberingTemplate: '{h1}.{n}', resetOn: 'h1', counterFormat: 'decimal', … },
//     { id: 'table',  name: 'Tabla',  shortLabel: 'Tabla', captionPrefix: 'Tabla', … },
//     { id: 'video',  name: 'Vídeo',  shortLabel: 'Vídeo', captionPrefix: 'Vídeo', … }]
```

```ts
type ResourceCounterFormat =
  | 'decimal'
  | 'roman-lower'
  | 'roman-upper'
  | 'alpha-lower'
  | 'alpha-upper'
  | EastAsianNumeralStyle  // 'simp-chinese-informal', 'circled-decimal', 'hiragana'…
  | ArabicNumeralStyle;    // 'arabic-indic', 'persian', 'abjad'…

type ResourceCounterReset = 'never' | 'h1' | 'h2' | 'h3' | 'h4' | 'h5' | 'h6';

interface ResourcePlacement {
  position?: 'auto' | 'top' | 'bottom' | 'here'; // which free slot a float may take; 'here' = inline embed at the ::resource directive
  span?: 'column' | 'page' | 'side';             // one column, the full content width, or the float-only side column
  rotate?: 'ccw' | 'cw';                         // a quarter turn: a landscape table on a page of its own
  width?: number;                                // fraction (0 < width < 1) of the column or page width; default: the whole width
  align?: 'left' | 'center' | 'right' | 'start' | 'end'; // where a float narrower than its column sits; default 'left'
  captionSide?: boolean | 'inside';              // caption beside the figure, in the side column of a oneAndHalf layout (column floats and resources set in the text); 'inside': beside the picture, within its own slot
  columns?: number;                              // a 'column' float across this many adjacent columns (since 1.18)
  wrap?: 'none' | 'left' | 'right' | 'start' | 'end' | 'contour'; // text beside the resource, at that side of its column (since 1.24); 'contour' follows its shape
  wrapGap?: Dimension;                           // space between the wrapped resource and the text (since 1.24)
  shrink?: 'never' | 'page' | 'slot';            // scale a floated picture down to the room of its slot
  minScale?: number;                             // the smallest scale shrink sets it at; default 0.7
  captionMeasure?: 'slot' | 'body';              // caption and note as wide as the slot or as the picture
  citingPage?: boolean;                          // a top or auto float may head the page or column it is cited on
}

interface ResourceType {
  id: string;                          // stable id, referenced by Resource.typeId
  name: string;                        // singular display name, e.g. "Figure"
  namePlural?: string;                 // optional plural, e.g. "Figures"
  shortLabel: string;                  // compact label for inline refs, e.g. "Fig."
  numberingTemplate: string;           // "{h1}.{n}" or "{n}"
  resetOn: ResourceCounterReset;       // when the {n} counter resets
  counterFormat: ResourceCounterFormat;// how {n} is formatted
  captionPrefix: string;               // prepended to the caption, e.g. "Figure"
  defaultPlacement?: ResourcePlacement;// fallback placement for this type's resources
  captionStyle?: CaptionStyleConfig;   // partial caption style for this type's resources
}
```

Un tipo può omettere dei campi (da postext 1.38): li completa il tipo integrato con lo stesso id (`figure`, `table`, `video`, nella lingua del documento); in mancanza, `name` prende l’id, `shortLabel` e `captionPrefix` prendono `name`, `numberingTemplate` vale `{'{h1}.{n}'}` (`{'{h1}-{n}'}` in cinese, giapponese e arabo), `resetOn` vale `'h1'` e `counterFormat` vale `'decimal'`. Un `resetOn` che non indica alcun livello vale `'h1'` e viene segnalato con `unknownConfigValue`. Un tipo che dà un proprio `name` e nessun `shortLabel` viene citato con quel nome, come prima della 1.38, e non con l’etichetta breve del tipo integrato: in un documento in inglese `{ id: 'table', name: 'Table' }` dà «Table 1», non «Tab. 1».

`ResourcePlacement` ha la stessa forma del `placement` che una risorsa imposta per conto proprio. `position` sceglie il tipo di spazio libero che un elemento flottante può occupare: `auto` (il valore predefinito) prende il primo dopo il primo rimando, `top` / `bottom` lo limitano a quel tipo di fascia, `here` inserisce la risorsa nel testo. `span` imposta l’estensione dell’elemento flottante: una colonna, l’intera larghezza del contenuto o la colonna laterale riservata agli elementi flottanti di un’impaginazione a colonna e mezza. `rotate` ruota la risorsa di un quarto di giro e ne fa un elemento flottante a tutta larghezza, su una pagina a sé. `width` restringe un elemento flottante a una frazione della sua colonna (o della pagina, per un elemento a tutta larghezza): per esempio una tabella piccola in una colonna larga. `align` indica dove si colloca un elemento flottante più stretto (a sinistra per impostazione predefinita, al centro o a destra) e dove si colloca nel suo spazio un’immagine più stretta di quello spazio: una bitmap più piccola della colonna, o un’immagine ridotta da `layout.fitFiguresToPage`. La didascalia e la nota mantengono la giustezza dello spazio. (Fino a postext 1.4 un’immagine del genere veniva sempre allineata a sinistra.) `left` e `right` sono lati del flusso del testo, invertiti nelle pagine di un documento da destra a sinistra; `start` ed `end` indicano gli stessi lati. `captionSide` colloca la didascalia accanto alla figura nella colonna laterale riservata agli elementi flottanti di un’impaginazione a colonna e mezza (`layout.sideColumnRole: 'floats'`), all’altezza del bordo superiore della figura (di quello inferiore, per un elemento flottante in basso); si applica agli elementi flottanti di colonna e, da postext 1.28, a una risorsa composta nel testo (`position: 'here'`, larga una colonna, senza testo che le scorra attorno), la cui didascalia e la cui nota stanno nella colonna laterale, all’altezza del bordo superiore della risorsa, dove la colonna laterale accanto è libera, e sotto la risorsa dove non lo è (`layout.inlineCaptionSide`, attivo per impostazione predefinita; `false` riserva le didascalie laterali agli elementi flottanti di colonna); una pagina senza una colonna del genere tiene la didascalia sotto la figura. Quando né la risorsa né il suo tipo impostano un posizionamento, vale il valore predefinito integrato `auto` / `column`. `shrink` (`'never'`, `'page'`, `'slot'`) e `minScale` (0.7 se non impostato) riducono un’immagine flottante allo spazio del suo posto invece di spostarla più avanti, e `captionMeasure: 'body'` compone la didascalia e la nota di un’immagine più stretta del suo spazio alla larghezza dell’immagine (vedi [Formato del documento › Collocazione](/it/docs/document-format-resources#collocazione)); `layout.floatShrink` dà il valore predefinito del documento per i primi due. `wrap` colloca una risorsa inserita nel testo o un elemento flottante largo una colonna su un lato della sua colonna, con il testo che scorre accanto a distanza `wrapGap`; `layout.wrap` contiene i valori predefiniti (vedi [Formato del documento › Testo intorno alle immagini](/it/docs/document-format-resources#testo-intorno-alle-immagini)). `wrap: 'contour'` fa scorrere il testo attorno alla forma dell’immagine, letta dal `contour` della risorsa (`points`, `alpha`, `threshold`, `margin` e il `traced` dell’host; vedi [Formato del documento › Testo lungo il contorno](/it/docs/document-format-resources#testo-lungo-il-contorno)). `citingPage` permette a un elemento flottante `top` o `auto` di andare in testa alla pagina o alla colonna in cui cade la riga che lo richiama, invece di prendere il primo spazio libero successivo; `layout.floatsAtCitingPage` dà il valore predefinito del documento e `layout.maxTopFraction` la frazione della colonna che può occupare (vedi [Formato del documento › Posizionamento](/it/docs/document-format-resources#collocazione)).

`columns` (da postext 1.18) estende un elemento flottante `span: 'column'` su quel numero di colonne adiacenti in una pagina che ne ha diverse: un’immagine su due delle cinque colonne di un quotidiano. La sua giustezza è data da quelle colonne e dalle intercolonne tra l’una e l’altra. Occupa la testa di una serie di colonne vuote che cominciano alla stessa altezza, oppure il piede della colonna che la cita e delle colonne vuote successive; tante colonne quante ne ha la pagina, o più, ne fanno un elemento flottante a tutta larghezza. Non ha effetto con gli span `'page'` e `'side'`, con una risorsa ruotata (`rotate`) e con una risorsa inserita nel testo (`here`), e `captionSide` si applica solo a un elemento flottante largo una colonna.

`captionSide: 'inside'` (da postext 1.52) mette didascalia e nota accanto a un’immagine stretta, nel suo stesso spazio, in qualunque impaginazione: la colonna di una pagina a una o due colonne, un flottante a tutta pagina, una risorsa composta nel testo, un riquadro o la cornice di una pagina composta. Lo spazio conserva tutta la sua larghezza; l’immagine ne occupa `width` (metà se `width` non è indicato) sul lato indicato da `align` (`'center'` vale come `'left'`), e la didascalia il resto dopo `layout.gutterWidth`, con la prima riga all’altezza del bordo superiore dell’immagine. Il blocco è alto quanto il più alto dei due: una didascalia lunga spinge in basso il testo che segue, e il blocco passa intero alla colonna successiva quando lo spazio rimasto al piede della colonna non basta. Una fascia di didascalia più stretta di un quinto dello spazio torna sotto l’immagine. Vale per le immagini (bitmap, SVG, video); una tabella, una risorsa ruotata e una risorsa su una pagina verticale tengono la didascalia sopra o sotto, e nessun testo scorre attorno a un’immagine così.

### Token del modello

`numberingTemplate` viene elaborato dallo stesso motore della numerazione dei titoli (vedi [Titoli](/it/docs/configuration-headings#titoli)). Riconosce due tipi di token:

- `{n}`: il contatore del tipo, formattato secondo `counterFormat`. È il valore che aumenta a ogni risorsa e si azzera secondo `resetOn`.
- da `{h1}` a `{h6}`: i numeri dei titoli in vigore nel punto del primo rimando, in decimale a meno che il token non indichi uno stile. `{h1}` è il numero del titolo di livello 1 corrente, `{h2}` quello di livello 2, e così via.
- `{h1:A}`, `{h2:i}`, `{n:i}`: un token seguito da due punti e da uno stile viene scritto in quello stile, uno qualsiasi di quelli accettati da un modello di titolo: `1`, `01`, `A`, `a`, `I`, `i`, il nome di un formato di numerazione come `upper-roman`, un token di un carattere come `一` o `①`, o uno stile in lettere come `Words`. Su `{n}` lo stile prevale su `counterFormat` per quel token. Uno stile sconosciuto conta in decimale. Da postext 1.28.

Qualsiasi altro testo è letterale. Una barra rovesciata rende letterale un `{`, un `}` o un `\`. Quando un token di titolo non ha un valore disponibile (ad esempio `{h1}` prima di qualsiasi titolo di livello 1), sparisce insieme al separatore adiacente: così `{h1}.{n}` si riduce senza problemi al semplice contatore.

Un modello vuoto (`''`) non stampa alcun numero, anche se il tipo continua a contare le sue risorse: una didascalia appare come *Do. Lines at 0°* e un `:ref` stampa la sola etichetta (*Do*). Fino a postext 1.4 una didascalia del genere appariva come *Do .Lines at 0°* e il rimando terminava con uno spazio indivisibile.

**Appendici.** Se in un libro le appendici sono contrassegnate da lettere grazie a uno stile di titolo (`numberingTemplate: 'Appendix {1:A}'`, con `startAt=1` sulla prima), dai alle loro figure e tabelle un tipo a sé, `{ ...table, id: 'table-a', numberingTemplate: '{h1:A}.{n}', resetOn: 'h1' }`. Un solo tipo basta per tutte le appendici: stampa *Table A.1*, *A.2* e *B.1*, nella didascalia e nel `:ref`. Un semplice `{h1}` in quella posizione stampa il numero del titolo in decimale (*Table 1.1*).

### Numerazione e rimandi

Il numero prodotto da un tipo di risorsa è quello che `:ref` stampa e che, nella didascalia, segue il prefisso. `:ref{id}` è la forma principale: il primo rimando in ordine di lettura **inserisce** la risorsa, che flotta nel primo spazio libero dopo quel rimando, cioè il piede della colonna che la richiama, la testa o il piede della colonna vuota successiva, o una fascia della pagina successiva (secondo il posizionamento risolto: `position: 'auto' | 'top' | 'bottom' | 'here'` e `span: 'column' | 'page' | 'side'`, più `rotate`, `width`, `align` e `captionSide`, cercati prima nella risorsa, poi nel `defaultPlacement` del tipo e infine nel valore predefinito integrato `auto` / `column`; `'top'` / `'bottom'` limitano la ricerca a quel tipo di spazio). L’inserimento di blocco `::resource{id}` è facoltativo e serve solo per `placement.position: 'here'`, cioè per inserire la risorsa nel testo, senza farla flottare, in un punto preciso del flusso. La grammatica completa lato documento (entrambe le forme più le opzioni `style` e `text` di `:ref`) è documentata in [Formato del documento › Risorse](/it/docs/document-format-resources#risorse), compreso il modo in cui l’ordine dei primi rimandi determina il conteggio.

È lo stesso schema della numerazione dei titoli: come un livello di titolo ha un proprio `numberingTemplate`, così lo ha anche un tipo di risorsa; ma il contatore delle risorse (`{n}`) avanza a ogni primo rimando anziché a ogni titolo, e `resetOn` lo ricollega alla gerarchia dei titoli.

### Che cosa viene numerato

Una risorsa viene numerata quando il testo la richiama (con `:ref` o con un inserimento `::resource`), nell’ordine di quei primi rimandi, qualunque sia il suo posizionamento: flottante, nel testo (`here`), nella colonna laterale o ruotata. Una risorsa disegnata solo da un elemento grafico (un elemento `image` di un’apertura di capitolo, di una testatina o di una pagina di parte) o che nessuno richiama non riceve un numero e non fa avanzare il contatore del suo tipo. Così, in un saggio fotografico in cui le tavole al vivo sono immagini delle aperture e l’unica tavola più piccola è un elemento flottante richiamato nel testo, quella tavola è la **I**, per quante tavole abbiano mostrato prima le aperture; numera le tavole delle aperture nel loro progetto grafico (con un attributo come `{attr.plate}`) e lascia il contatore alle tavole citate dal testo.

In un libro impaginato capitolo per capitolo (la Sandbox, `buildBundle` o `buildDocument` con i contatori passati da `continuationAfter()`), conta il primo rimando dell’intero libro: una risorsa mantiene il numero ricevuto nel capitolo che la richiama per primo, e solo quel capitolo la colloca. Il `:ref` di un capitolo successivo stampa quel numero e non colloca nulla, e lì un inserimento `::resource` di una risorsa flottante è solo un altro rimando (un inserimento nel testo con `here` si compone comunque dove è scritto). Un rimando del genere è un link alla figura quando la figura si trova nello stesso output: un PDF dell’intero libro lo collega alla pagina del capitolo precedente. Un capitolo generato da solo, in HTML o PDF, lo compone come testo semplice nel colore dei link, perché la sua figura non è in quel documento. Un host che riunisce l’HTML dei capitoli in una sola pagina passa a `renderToHtml` le risorse ancorate dai capitoli, come `refTargets`, e un rimando del genere torna a essere un link alla figura del capitolo precedente:

```ts
import { anchoredResourceIds, buildBundle, renderToHtml } from 'postext';

const docs = buildBundle(bundle);
const refTargets = new Set(docs.flatMap((d) => [...anchoredResourceIds(d)]));
const html = docs.map((d) => renderToHtml(d, { refTargets })).join('');
```

**Cambiato in postext 1.5:** fino alla 1.4 ogni capitolo che richiamava una figura la faceva flottare di nuovo, e l’HTML di ogni `:ref` era un link, che la sua figura fosse nella pagina oppure no.

`{h1}` è il conteggio progressivo dei titoli di livello 1: ogni H1 lo fa avanzare, a meno che il suo stile di titolo non imposti `numbered: false`; un `numberingTemplate` vuoto nasconde il numero del titolo, ma non ferma il conteggio. Un articolo il cui unico H1 è il titolo numera quindi le sue figure `1.1`, `1.2`… con i tipi integrati `{h1}.{n}`. Due modi per stampare Figura 1, 2…:

- un tipo numerato `{n}` con `resetOn: 'never'` (con `resetOn: 'h1'` il conteggio ripartirebbe a ogni H1);
- uno [stile di titolo](/it/docs/configuration-styles#stili-dei-titoli) con `numbered: false` sul titolo, e su ogni altro H1 che non deve contare: un titolo del genere non fa avanzare `{h1}` ma lo lascia com’era (vuoto prima del primo H1 contato, dove `{h1}.{n}` si riduce al semplice contatore) e non fa mai scattare `resetOn: 'h1'`, così il conteggio prosegue oltre. Dopo `# Introduction` e la sua Figura 1.1, la prima figura sotto un `# Appendix` non numerato è la 1.2, non la 2.1.

```ts
// Figure 1, 2, 3… in a single-article document
resourceTypes: defaultResourceTypes('en').map((t) => ({ ...t, numberingTemplate: '{n}', resetOn: 'never' })),
```

### Righe alternate

Nelle tabelle di dati lunghe è più facile seguire ogni riga se una riga su due è colorata. `bodyAlternateBackgroundEnabled` attiva le strisce e `bodyAlternateBackground` ne imposta il colore:

```ts
const config: PostextConfig = {
  tableStyle: {
    bodyBackgroundEnabled: true,
    bodyBackground: { hex: '#ffffff', model: 'hex' },
    bodyAlternateBackgroundEnabled: true,
    bodyAlternateBackground: { hex: '#eef3fa', model: 'hex' },
  },
};
```

Le righe si contano dalla prima riga dopo le righe d’intestazione (`TableModel.headerRowCount`, o le righe iniziali fatte di celle d’intestazione): quella riga mantiene `bodyBackground` (o nessun fondo finché `bodyBackgroundEnabled` è disattivato), la successiva prende il fondo alternato, e così via. Il conteggio segue il modello della tabella, non la pagina, così una tabella divisa tra più pagine mantiene la striscia di ogni riga su ogni pagina, e una cella unita su più righe prende la striscia della sua prima riga. Le celle d’intestazione mantengono il fondo dell’intestazione, il `background` proprio di una cella prevale su entrambi, e un colore collegato alla tavolozza segue la tavolozza. Uno [stile di tabella con nome](#stili-di-tabella-con-nome) imposta i due campi come qualsiasi altro, così uno stile può essere a strisce mentre le altre tabelle del documento no; nella Sandbox sono l’interruttore *Righe alternate* e il suo colore, sotto **Celle del corpo**.

Nel VDT le celle delle righe alternate hanno `alternate: true`, e l’impaginazione della tabella contiene `bodyAlternateBackground`. `tableCellFill(table, cell)` restituisce il fondo con cui viene disegnata una cella (il suo, quello dell’intestazione, quello alternato o quello del corpo), ed è ciò che disegnano tutti i backend canvas, HTML e PDF. I fondi vicini si incontrano senza giunture: un browser con un rapporto di pixel frazionario o un visualizzatore PDF applica l’antialiasing a ogni fondo separatamente e lascerebbe trasparire la pagina in un filo sottilissimo tra due celle, per questo i backend HTML e PDF disegnano `tableCellFillRects(table)` (il fondo di ogni cella con una striscia su ogni lato che condivide con una cella disegnata dopo, che quella cella poi copre) e il canvas allinea i suoi fondi ai pixel del dispositivo.

### Filetti booktabs

Le tabelle delle riviste scientifiche e dei manuali si compongono di solito con tre filetti e nessuna linea verticale: un filetto spesso sopra la tabella, uno sottile sotto l’intestazione e uno spesso sotto l’ultima riga, con filetti corti sotto le intestazioni che raggruppano più colonne (il pacchetto LaTeX `booktabs`: `\toprule`, `\midrule`, `\cmidrule`, `\bottomrule`). `rules: 'booktabs'` traccia questo schema:

```ts
const config: PostextConfig = {
  tableStyle: {
    rules: 'booktabs',
    borderColor: { hex: '#000000', model: 'hex' },
    headerBackgroundEnabled: false,
  },
};
```

- Il filetto sopra la tabella e quello sotto la sua ultima riga sono spessi `heavyRuleWidth` (`0.08em`), il filetto sotto le righe d’intestazione `lightRuleWidth` (`0.05em`). Una tabella senza righe d’intestazione non ha il filetto d’intestazione.
- Una cella d’intestazione che copre più colonne sopra l’ultima riga d’intestazione riceve sotto di sé un filetto spesso `spanRuleWidth` (`0.03em`). Con `spanRules: 'trimmed'` (il valore predefinito) il filetto viene accorciato di `spanRuleTrim` (`0.5em`) alle due estremità, così i filetti sotto due intestazioni vicine non si toccano; `'full'` lo estende a tutta la cella e `'none'` lo omette.
- `groupRules: true` aggiunge un filetto sottile sopra ogni riga del corpo che apre un gruppo (una cella unica su tutta la tabella, o una riga di celle d’intestazione), a meno che la riga non apra la tabella o una pagina, dove c’è già il filetto d’intestazione.
- Gli spessori si risolvono rispetto al corpo delle celle del corpo (`bodyFontSize`), così un corpo d’intestazione più grande non ingrossa il filetto d’intestazione. Uno spessore di `0` elimina quel filetto.
- I filetti prendono `borderColor` (un colore collegato alla tavolozza segue la tavolozza e `:::part palette`), e `borders: false` li disattiva. `borderWidth` non si applica, e nemmeno `borderRadius`: i filetti restano dritti, mentre i fondi delle celle vengono comunque ritagliati sulla cornice arrotondata. I fondi dell’intestazione, le righe alternate e il `background` proprio di una cella funzionano come con gli altri schemi, sotto i filetti.
- Una tabella divisa tra più pagine ripete le righe d’intestazione su ogni parte, così ogni parte si apre con il filetto spesso e il filetto d’intestazione. Il filetto spesso sotto l’ultima riga chiude solo l’ultima parte; una parte che prosegue alla pagina successiva termina con `continuedFootRule`: un filetto sottile (`'light'`, il valore predefinito), il filetto spesso (`'bottom'`) o niente (`'none'`).

L’impaginazione calcola i filetti una volta sola. La tabella del VDT li contiene come `strokes` (`{ x1, y1, x2, y2, widthPx }`, relativi all’angolo superiore sinistro del corpo della tabella), e il canvas, il visualizzatore HTML, il PDF e l’EPUB a layout fisso tracciano esattamente quelli; in un PDF con tag sono artefatti di impaginazione. L’EPUB a layout fluido li scrive come bordi CSS sulla tabella e sulla sua intestazione, con i filetti accorciati disegnati come linee di sfondo. Nella Sandbox, **Booktabs** nel menu *Filetti* mostra questi campi e nasconde *Spessore del bordo* e *Raggio degli angoli*.

### Stili di tabella con nome

Raramente un documento compone tutte le tabelle allo stesso modo: una lista di controllo in una griglia blu notte con la cornice arrotondata, una riga di opzioni racchiusa solo dalla cornice esterna, una tabella di dati con semplici filetti orizzontali. `tableStyles` dichiara varianti con nome, e una risorsa tabella ne sceglie una con `table.styleId`. Ogni campo che uno stile non imposta viene letto prima da `tableStyle` e poi dal testo corrente, così uno stile dichiara solo ciò che distingue le sue tabelle. Una tabella senza `styleId`, o con un id che nessuno stile dichiara, mantiene `tableStyle`: un documento senza `tableStyles` viene composto esattamente come prima.

```ts
const config: PostextConfig = {
  tableStyle: {
    borderColor: { hex: '#163a76', model: 'hex' },
    borderWidth: { value: 1.3, unit: 'pt' },
    borderRadius: { value: 10, unit: 'pt' },
  },
  tableStyles: [
    {
      id: 'option',
      name: 'Option row',
      rules: 'outer',
      borderColor: { hex: '#7a9cc6', model: 'hex' },
      borderWidth: { value: 1, unit: 'pt' },
      borderRadius: { value: 8, unit: 'pt' },
      headerBackgroundEnabled: false,
    },
  ],
};

// In the resources: this table is set in the "option" style.
const resource: Resource = {
  id: 'choices', typeId: 'table', kind: 'table', createdAt: 0, updatedAt: 0,
  table: { model: { rows: [/* … */] }, styleId: 'option' },
};
```

Ogni voce accetta tutti i campi di `tableStyle` più `id` (ciò a cui fa riferimento `table.styleId`) e un `name` facoltativo per l’editor (per impostazione predefinita è l’id). Tutto ciò che uno stile può impostare si applica tabella per tabella: tipografia, fondi, bordi, filetti, raggio degli angoli, spaziatura interna e il comportamento quando la tabella non entra (`overflow`), con i testi di continuazione. `resolveTableStylesConfig(styles, tableStyle, resolvedBodyText, locale?)` restituisce l’elenco risolto, `pickTableStyle(resolved, styleId)` lo stile con cui viene composta una tabella, e `stripTableStylesDefaults` elimina i campi non impostati (ma conserva un campo uguale al valore predefinito integrato, perché continua a prevalere su un valore diverso di `tableStyle`). In un EPUB a layout fluido uno stile con nome diventa una classe sulla tabella (`pt-table-<id>`), il cui aspetto dipende dal foglio di stile del libro.

### Tabelle più alte della pagina

Una tabella flottante che non entra nella pagina nuova che le viene offerta non viene schiacciata né lasciata uscire dalla pagina: con `overflow: 'split'` (il valore predefinito) il motore la taglia tra due righe, all’ultimo bordo di riga che entra nella pagina, e la fa proseguire nelle pagine successive, per quante ne servono. Ogni parte successiva ripete le righe d’intestazione della tabella (`TableModel.headerRowCount`, o le righe iniziali fatte di celle d’intestazione quando non è impostato) e riporta la didascalia con `continuedSuffix` dopo la descrizione: «Tabella 6-4. Titolo *(cont.)*». Ogni parte che prosegue riceve sotto di sé `continuesMarker`, allineato a destra, con il carattere delle note; la nota della tabella si rimanda all’ultima parte. Un taglio non attraversa mai una cella unita (un rowspan passa intero alla parte successiva), e una riga che fa da intestazione alle righe sottostanti (una cella unica su tutta la tabella) viene portata alla parte successiva invece di restare isolata al piede di una pagina. Una tabella booktabs chiude ogni parte che prosegue con `continuedFootRule` (vedi [filetti booktabs](#filetti-booktabs)).

**Dove finisce la prima parte.** Una tabella a cui viene offerta la testa di una colonna vuota dopo il suo rimando prende le righe che entrano lì e prosegue nello spazio successivo. Riempie la colonna fino al piede quando ha la colonna tutta per sé: una parte che lascerebbe sotto di sé meno di tre righe di testo prende anche quelle, piuttosto che lasciare un moncone di testo. Quando la colonna contiene già un’altra fascia di elementi flottanti (per esempio una figura a tutta larghezza in testa alla pagina), la parte si ferma invece almeno tre righe di testo prima del piede, lo spazio per il testo che ogni elemento flottante lascia quando condivide una colonna con un altro, così la colonna termina con un po’ di testo sotto la tabella invece che con soli elementi flottanti. Perché una tabella lunga arrivi fino al piede della sua colonna, richiamala in un punto in cui la pagina dove comincia non ha altri elementi flottanti (dopo la pagina di una figura a tutta larghezza, per esempio), oppure adatta le sue righe alla colonna.

`'clip'` tiene le righe iniziali che entrano nella pagina e scarta il resto in silenzio (la nota chiude comunque la parte); `'hide'` omette del tutto la tabella. Entrambi si applicano solo quando la tabella è più alta di una pagina: una tabella che entra viene collocata intera in qualsiasi modalità.

**Tabelle composte nel testo.** Una tabella collocata `here` (inserita con `::resource`) segue le stesse regole da postext 1.25 (`splitInline`, attivo per impostazione predefinita). Quando non entra nello spazio rimasto nella sua colonna, viene tagliata tra due righe: la prima parte mantiene sopra di sé la distanza prevista per gli elementi flottanti e almeno le righe d’intestazione e due righe del corpo (se sono meno, l’intera tabella comincia nella colonna successiva, come prima), ogni parte successiva apre la colonna seguente senza spazio sopra, impaginata alla larghezza di quella colonna (in un’impaginazione a colonna e mezza, una parte che cade nella colonna stretta si compone alla larghezza di quella colonna), e il testo dopo la riga `::resource` segue l’ultima parte. La ripetizione dell’intestazione, la didascalia con il suffisso, l’indicatore, la nota sull’ultima parte, la coda di tre righe e i tagli che rispettano le celle unite e le intestazioni di gruppo sono quelli di una tabella flottante. Una tabella con meno di cinque righe del corpo non viene mai tagliata. `'clip'` tiene le righe iniziali di una tabella nel testo più alta di una colonna, composte in testa a una colonna; `'hide'` omette una tabella del genere; una più bassa passa intera alla colonna successiva in entrambe le modalità. Una pagina aperta da una tabella nel testo tiene libero dagli elementi flottanti solo lo spazio della prima parte, così una figura a tutta larghezza in attesa apre quella pagina e la tabella prosegue sotto. Le tabelle nel testo su una pagina verticale, e le tabelle dentro un riquadro, non vengono tagliate. `splitInline: false` sposta una tabella nel testo intera alla colonna successiva, come fino a postext 1.24.

Le stringhe di continuazione hanno valori predefiniti per lingua del documento (`locale`, altrimenti la lingua di sillabazione): inglese `(cont.)` / `Continued`, spagnolo `(cont.)` / `Continúa`, e analogamente in francese, tedesco, italiano, portoghese, catalano, olandese, cinese, giapponese e arabo (elencate in [Lingua del documento](/it/docs/configuration-language#lingua-del-documento)).

Il contenuto delle celle è Markdown in linea, e un a capo dentro una cella (un carattere di nuova riga, o `\\` come nelle didascalie e nelle note) comincia un nuovo paragrafo. Un paragrafo che si apre con un punto elenco o un trattino (`•`, `-`, `*`, `–`) o con un numero (`1.`, `1)`) seguito da uno spazio viene composto come voce di elenco: il segno viene disegnato come è scritto, il testo segue il segno alla distanza `unorderedLists.gap` del documento, con rientro sporgente, le righe a capo si allineano al testo, e due spazi iniziali annidano un livello. Così una cella scritta come `• Ofrece elección\n• Acomoda a personas diestras y zurdas` diventa un elenco di due voci. Una riga fatta solo di spazi normali non aggiunge nulla; una riga che contiene uno spazio indivisibile (U+00A0) è una riga della cella, come in CommonMark, quindi `1\n` seguito da uno spazio indivisibile rende la riga alta due righe di testo. Uno spazio indivisibile alla fine del testo di una cella mantiene la sua larghezza: `760` e uno spazio indivisibile, allineati a destra sopra `(231)`, terminano uno spazio prima del bordo, il che avvicina lo 0 all’1. Le cifre si allineano esattamente solo dove lo spazio è largo quanto la parentesi, e nella maggior parte dei caratteri è più stretto. (Fino a postext 1.4 venivano eliminati entrambi.)

Le larghezze delle colonne appartengono al modello della tabella, non allo stile: `TableModel.columnWidths` è un array facoltativo di pesi relativi, uno per colonna, normalizzati al momento dell’impaginazione; `[2, 1, 1]` dà alla prima colonna metà della larghezza. Un array mancante, di lunghezza sbagliata o con un peso non positivo ripiega su una divisione in parti uguali. L’editor di tabelle mantiene l’array allineato quando si aggiungono o si rimuovono colonne.

### Costruire i modelli di tabella

Un `TableModel` è una griglia ordinata per righe, e ogni cella viene impaginata in base alla sua posizione: `rows[r][c]` sta nella colonna `c`. Una cella unita mantiene quindi nella griglia le celle che copre, ciascuna marcata `hiddenBy` con la sua cella principale, a differenza di una tabella HTML, che le omette. Le funzioni di supporto per il modello esportate da `postext` mantengono questa forma; sono funzioni pure che restituiscono un nuovo modello: `mergeCells(model, { start, end })` e `unmergeCell(model, at)`, `addRow`, `addColumn`, `removeRow`, `removeColumn`, `setCellContent`, `setCellImage`, `setCellBackground` e `setAlignment`. Le quattro funzioni per righe e colonne mantengono intere le unioni: una riga o una colonna aggiunta dentro un blocco unito lo allarga, una aggiunta prima lo sposta, una rimossa da esso lo restringe (un blocco che perde la sua prima riga o colonna mantiene il contenuto nella sua nuova cella in alto a sinistra) e ogni `hiddenBy` continua a puntare alla sua cella principale.

`parseTSV(text, options?)` costruisce un modello da un testo separato da tabulazioni, come un intervallo incollato da un foglio di calcolo: le righe si separano agli a capo, le celle alle tabulazioni, e le righe corte vengono completate perché la griglia sia rettangolare. `headerRows` trasforma le righe iniziali in righe d’intestazione: le loro celle ricevono `isHeader` e il modello `headerRowCount`, così una tabella divisa tra più pagine le ripete.

```ts
import { parseTSV, mergeCells } from 'postext';

let model = parseTSV('Part\tQty\tNote\nBolt\t4\tM6\nNut\t8\t', { headerRows: 1 });
// model.headerRowCount === 1; model.rows[0][0] is { content: 'Part', isHeader: true }
model = mergeCells(model, { start: { row: 2, col: 1 }, end: { row: 2, col: 2 } });
// rows[2][1] gets colSpan: 2; rows[2][2] stays in the grid with hiddenBy: { row: 2, col: 1 }
```

`tableGridIssues(model)` controlla la griglia. Restituisce un elenco vuoto per un modello corretto, e altrimenti ogni punto in cui la griglia si rompe, in ordine di riga: `spanOverlap`, una cella visibile sotto il `colSpan` / `rowSpan` di un’altra cella (`coveredBy` indica quella cella): è ciò che succede quando si omette una cella coperta come in HTML, perché ogni cella successiva slitta sull’unione; e `missingCells`, una riga che termina prima dell’ultima colonna senza un’unione che copra il resto, il che lascia un buco.

```ts
import { tableGridIssues } from 'postext';

tableGridIssues({
  rows: [
    [{ content: 'A', colSpan: 2 }, { content: 'C' }],
    [{ content: '1' }, { content: '2' }, { content: '3' }],
  ],
});
// => [{ kind: 'spanOverlap', row: 0, col: 1, coveredBy: { row: 0, col: 0 } },
//     { kind: 'missingCells', row: 0, col: 2 }]
```

Una tabella usata dal documento la cui griglia presenta problemi del genere viene segnalata in `doc.contentWarnings` come `raggedTableGrid` (vedi [Avvisi nel documento](/it/docs/configuration-programmatic-usage#avvisi-nel-documento)).


## Stile delle didascalie

La proprietà `captionStyle` controlla le didascalie delle risorse (la riga `Figure 1 — …` sotto, o sopra, immagini, SVG e tabelle). ### Come funziona l’inchiostro unico

Quando `singleInk` è attivo, ogni colore nel markup SVG viene riscritto come una tinta di `inkColor` la cui intensità è **1 − luminanza relativa** (coefficienti Rec. 709 applicati ai canali con codifica gamma: un’approssimazione percettiva più che sufficiente per la mappatura delle tinte). La mappatura conserva il valore percepito: il bianco diventa il bianco della carta, il nero diventa l’inchiostro pieno, e i riempimenti chiari restano chiari qualunque sia la loro tonalità originale. Uno sfondo giallo pallido diventa una tinta pallida dell’inchiostro; un tratto scuro si avvicina all’inchiostro pieno.

La ricolorazione viene eseguita dalla funzione esportata `applySingleInkToSvg(svgText, inkHex)`, che lavora senza DOM sul markup SVG come testo:

- I valori esadecimali `#rgb` / `#rgba` / `#rrggbb` / `#rrggbbaa`, le funzioni `rgb()` / `rgba()` e le funzioni `hsl()` / `hsla()` vengono riscritti ovunque compaiano: attributi di presentazione, `style` in linea, gradienti, `<defs>`. Le funzioni possono usare canali interi, decimali o in percentuale e la sintassi con virgole o con spazi, quindi vengono ricolorati anche `rgb(11.37%, 20%, 50.59%)` (come lo scrive Cairo) e `rgb(51 102 153 / 50%)`. Una funzione tinta viene riscritta come `rgb(…)` o `rgba(…)`.
- Le parole chiave `white` e `black` vengono sostituite solo dove compaiono come valori di colorazione (`fill`, `stroke`, `stop-color`, `flood-color`, `color`, come attributi o proprietà di stile in linea), mai dentro il contenuto testuale o le etichette.
- `none`, `transparent` e `currentColor` restano invariati, come pure gli altri colori con nome (`red`, `steelblue`…) e il nero predefinito di una forma o di un testo che non imposta alcun riempimento. Assegna a questi elementi un colore esplicito perché vengano ricolorati.
- I canali alfa vengono conservati (i nibble di `#rgba` / `#rrggbbaa` e le componenti alfa di `rgba(…)` passano invariati; un’alfa in percentuale viene scritta come numero).
- Quando `inkHex` non si può interpretare, l’input viene restituito invariato.
- Il risultato ha `data-postext-single-ink="#…"` (l’inchiostro) sul suo `<svg>` radice, e un markup che lo ha già viene restituito così com’è, qualunque inchiostro indichi. La mappatura non è idempotente (un secondo passaggio schiarisce ogni colore, e il nero esce a circa due terzi dell’inchiostro), quindi un’immagine viene ricolorata una sola volta, da chiunque arrivi prima tra il tuo codice e i backend. (Il marcatore è nuovo in postext 1.5; il markup ricolorato dalla 1.4 non lo ha.)

```ts
import { applySingleInkToSvg } from 'postext';

const recoloured = applySingleInkToSvg(svgText, '#295AA3');
applySingleInkToSvg(recoloured, '#295AA3') === recoloured; // true: never twice
```

L’inchiostro unico si applica in tutti e tre i backend: il backend PDF ricolora i byte SVG che `resourceBytes` gli passa prima di disegnarli come vettori, e i backend canvas e HTML tingono le immagini SVG che disegnano, se lo chiedi (vedi [Inchiostro unico sul canvas e in HTML](#inchiostro-unico-sul-canvas-e-in-html)), così il PDF esportato corrisponde all’anteprima a schermo.

Le funzioni di risoluzione e di pulizia funzionano come quelle delle altre sezioni, insieme ai tipi `DiagramStyleConfig` / `ResolvedDiagramStyleConfig`:

```ts
import {
  DEFAULT_DIAGRAM_STYLE_CONFIG,
  resolveDiagramStyleConfig,
  stripDiagramStyleDefaults,
  applySingleInkToSvg,
} from 'postext';
import type { DiagramStyleConfig, ResolvedDiagramStyleConfig } from 'postext';

const resolved = resolveDiagramStyleConfig(config.diagramStyle);
// => { singleInk: false, inkColor: { hex: '#295AA3', model: 'hex', paletteId: 'main-color' }, inlineFonts: true }

const minimal  = stripDiagramStyleDefaults(config.diagramStyle);
// => undefined when everything matches the defaults
```

### Inchiostro unico sul canvas e in HTML

I backend canvas e HTML ricevono le immagini già decodificate (`registerResourceImage`) o come URL (`resourceImageUrl`), non come markup SVG. Su richiesta applicano la stessa mappatura a ciò che disegnano:

- **Canvas** (`renderPage`, `renderPageToCanvas`, `renderToCanvas`). Ogni immagine SVG a cui si applica la tinta (una figura, l’immagine di una cella di tabella, l’immagine di un elemento grafico, l’icona o il marcatore di un riquadro) viene rasterizzata alla dimensione con cui è collocata e i suoi pixel vengono tinti con l’inchiostro, sia che sia stata registrata come `<img>` sia come `ImageBitmap`. La bitmap tinta finisce in cache come qualsiasi raster vettoriale. Un’immagine bitmap non viene mai tinta.
- **HTML** (`renderToHtml`, `renderToHtmlIndexed`). Ogni `<img>` SVG riceve `filter: url(#pt-ink-…)`, che punta a un `feColorMatrix` contenuto nella sua pagina: un `<svg>` di dimensione zero che contiene il `<filter>`, collocato per primo nella pagina, e parte del `decorationHtml` della pagina nell’output indicizzato. Ogni pagina lo contiene finché l’inchiostro unico è attivo, che contenga o no un’immagine, così un host che aggiorna i blocchi uno per uno non introduce mai un’immagine a cui manca il filtro.

**Mai tinta due volte.** Fino a postext 1.4 i backend canvas e HTML dipingevano le immagini così come le ricevevano, quindi gli host ricoloravano da sé il markup con `applySingleInkToSvg` prima di passarlo. Gli adattatori dei pacchetti e la Sandbox lo fanno ancora, perché il passaggio sul markup dà esattamente i colori del PDF (vedi l’ultimo paragrafo qui sotto). Un’immagine viene quindi tinta una volta sola, secondo tre regole valide in tutti e tre i backend:

- **Il markup marcato non viene toccato.** Il backend PDF ricolora `resourceBytes` con `applySingleInkToSvg`, quindi i byte SVG già ricolorati vengono disegnati così come sono. Sul canvas e in HTML, non si tinge mai nemmeno un’immagine caricata da un data URI SVG il cui markup ha il marcatore.
- **Disattivato salvo richiesta, in postext 1.x.** Il canvas tinge un’immagine SVG registrata senza un proprio flag solo quando il rendering passa `singleInk: true` (`RenderPageOptions`), e una registrata con `registerResourceImage(id, img, { singleInk: true })` in qualsiasi rendering. Il backend HTML tinge quando `renderToHtml` riceve `singleInk: true`, o quando il suo resolver `resourceImageUrl` ha `singleInk: true`. Un host scritto per la 1.4, che ricolora il markup e registra l’immagine decodificata senza flag, mantiene il suo output. La prossima versione major tingerà per impostazione predefinita.
- **`singleInk: false` non viene mai tinto.** Dietro un URL blob o di rete il markup non si può rileggere, quindi un’immagine che hai ricolorato da te e decodifichi in quel modo va registrata con `singleInk: false`, come fanno `registerBundleImages` e la Sandbox. `bundleImageUrl(bundle)` restituisce un resolver con `singleInk: false`, e `bundleResourceBytes` passa al PDF i byte originali del pacchetto, che il backend PDF ricolora una volta.

Entrambi i backend conoscono il tipo di ogni immagine dal VDT: una figura e un’immagine di cella hanno il tipo della loro risorsa, e il blocco immagine di un elemento grafico ha `imageKind` (`'svg'` o `'bitmap'`), preso dalla sua risorsa durante l’impaginazione. Per un VDT costruito prima che esistesse `imageKind`, il canvas tratta come SVG l’immagine di un elemento grafico registrata come sorgente vettoriale, e il backend HTML una il cui URL è un data URI SVG o termina in `.svg`.

O ricolori da te il markup o lasci che i backend tingano l’immagine grezza, non entrambe le cose:

```ts
import { applySingleInkToSvg, registerResourceImage, renderPage, renderToHtml } from 'postext';

// Raw SVG: tinted while diagramStyle.singleInk is on…
registerResourceImage('diagram.svg', rawImg, { singleInk: true });
// …or register it plainly and ask on each render.
registerResourceImage('diagram.svg', rawImg);
const canvas = renderPage(doc.pages[0], doc, { singleInk: true });

// Recoloured before decoding (as postext 1.4 hosts do): painted as given.
const inked = applySingleInkToSvg(svgText, ink);
registerResourceImage('diagram.svg', await decode(inked), { singleInk: false });

// The HTML backend with URLs to the raw markup.
const html = renderToHtml(doc, { resourceImageUrl: urlFor, singleInk: true });
```

`renderToHtml` prende il valore predefinito di `singleInk` dal flag del resolver, quindi `bundleImageUrl(bundle)` non ha bisogno di opzioni.

Per ogni colore che il passaggio sul markup riscrive (valori esadecimali, `rgb()` e `hsl()`, `white` e `black`; vedi [Come funziona l’inchiostro unico](#come-funziona-linchiostro-unico)), la mappatura sui pixel dà lo stesso risultato, bordi con antialiasing e gradienti compresi. I due metodi differiscono dove il passaggio sul markup non tocca un colore: i colori con nome diversi da `white` e `black`, `currentColor`, forme e testi senza riempimento (disegnati nel nero predefinito) e le bitmap incorporate nell’SVG vengono tinti a schermo ma mantengono il loro colore nel PDF. Assegna a ogni elemento di un diagramma un colore esplicito esadecimale, `rgb()` o `hsl()` per ottenere un output identico. Quando il canvas non può rileggere i pixel (un `<img>` di un’altra origine, caricato senza CORS), l’immagine viene dipinta senza tinta.

### Font nel testo SVG

Un’immagine SVG si mostra attraverso un elemento immagine: un `<img>` sul canvas, in HTML e in EPUB. Un documento immagine non vede i web font della pagina, quindi `<text font-family="IBM Plex Sans">` ripiegherebbe su un carattere di sistema. Da postext 1.25 il motore incorpora nel markup i caratteri che il testo richiede, prima che l’immagine venga decodificata o fornita come URL: una regola `@font-face` per ogni file di font, con i suoi byte come data URI, in uno `<style>` subito dopo il tag `<svg>` radice. Il PDF non ha bisogno di nulla di tutto questo: compone il testo SVG come testo vero nei suoi font incorporati (vedi [Byte delle risorse e master di stampa](/it/docs/configuration-pdf-output#byte-delle-risorse-e-master-di-stampa)).

Ciò che il testo richiede viene letto da `font-family`, `font-weight`, `font-style` e `font`, come attributi, negli attributi `style` ed ereditato dai gruppi che lo contengono; conta anche una regola `<style>` che nomina una famiglia. Le famiglie generiche (`serif`, `sans-serif`…) e il testo in `<title>` o `<desc>` vengono esclusi, e una famiglia che l’SVG dichiara da sé con `@font-face` non viene toccata. Un tratto di testo scorre il suo elenco `font-family` fino alla prima famiglia che ha un carattere disponibile. Prima viene la ricolorazione per l’inchiostro unico, poi i font.

I caratteri provengono da un **provider** con il contratto del `PdfFontProvider` di postext-pdf, così un solo provider serve entrambi: viene chiamato con la famiglia, il peso e lo stile, e i caratteri che l’SVG compone in quel carattere, e risponde con uno o più file. A una famiglia servita come porzioni per unicode-range (Fontsource, Google Fonts) risponde con le porzioni di cui quei caratteri hanno bisogno, così un SVG con etichette latine contiene solo il file `latin`. Il provider predefinito legge il registro dei font del motore: `loadBundleFonts` vi registra i caratteri di un pacchetto, e un host registra i propri con `registerFontBytes(family, weight, style, bytes, { unicodeRange })`, o `registerFontUrl(…)` per un file scaricato la prima volta che un SVG ne ha bisogno. Una famiglia che nessuno ha registrato viene cercata nelle regole `@font-face` dei fogli di stile leggibili della pagina. Un `FontFace` aggiunto a `document.fonts` da byte non conserva i byte, quindi il motore non può rileggerlo: registra anche quei caratteri.

```ts
import { registerFontBytes, registerSvgImage, renderPage } from 'postext';

registerFontBytes('IBM Plex Sans', 700, 'normal', plexBoldWoff2);
await registerSvgImage('chart.svg', svgText);   // recoloured, fonts inlined, decoded, registered
const canvas = renderPage(doc.pages[0], doc);
```

Dove avviene:

- **Canvas.** `registerSvgImage(fileId, svgText, options)` ricolora (`inkHex`), incorpora i font (`fonts`, un provider; `inlineFonts: false` salta il passaggio), decodifica e registra l’immagine come sorgente vettoriale, e restituisce che cosa è stato di ogni carattere. `registerBundleImages(bundle)` fa lo stesso per gli SVG di un pacchetto, cominciando dai caratteri del pacchetto stesso. `prepareSvgMarkup(svgText, options)` restituisce il markup preparato per un host che decodifica per conto proprio.
- **HTML.** `bundleImageUrl(bundle)` serve il markup SVG con i caratteri del pacchetto incorporati. `renderToHtml(doc, { inlineSvgFonts: true })` incorpora i font nei data URI `data:` SVG che `resourceImageUrl` restituisce, a partire dai caratteri che il registro tiene in memoria (oppure `inlineSvgFonts: { fonts, maxBytes, withhold, standIn }`). Un object URL non si può leggere in modo sincrono, quindi un host che serve URL blob incorpora i font prima di crearli.
- **EPUB.** `postext-epub` incorpora i font dai `fonts` del libro, poi da `svgFonts.provider`, prima di scrivere un SVG (vedi [Libri EPUB](/it/docs/configuration-html-folio-epub#libri-epub-postext-epub)).
- **PDF.** Il testo SVG viene composto come testo vero nei font incorporati. Uno `<style>` che contiene solo regole `@font-face` (caratteri incorporati dall’autore) non fa più ripiegare la figura su un raster. Quando una figura ripiega comunque (un filtro, un gradiente), il suo raster viene creato con i caratteri incorporati dal `fontProvider` del PDF.

Sono esportate anche le funzioni di livello più basso: `svgFontRequests(svgText)` elenca per ogni tratto le famiglie, il peso, lo stile e i caratteri; `inlineSvgFonts(svgText, provider, options)` e `inlineSvgFontsSync(svgText, syncProvider, options)` restituiscono il markup; `inlineSvgFontsDetailed` aggiunge un resoconto di ogni carattere (`inlined`, `declared`, `unavailable`, `withheld`, `tooLarge`); un carattere incorporato da una famiglia sostitutiva nomina quella famiglia in `standIn`.

Un EPUB conserva solo gli attributi che il suo schema conosce: un file si riproduce con <code>controls</code>, <code>autoplay</code>, <code>muted</code>, <code>loop</code>, <code>playsinline</code> e <code>preload</code>, più il marcatore <code>data-pt-alongside</code>, e il resto lo decide il sistema di lettura.

Un video non esclusivo ha `data-pt-alongside` nell’output HTML. `coordinateVideoPlayback(root)` fa rispettare la regola ai player sotto `root` (l’elemento che contiene l’output di `renderToHtml`): quando si avvia un video esclusivo, tutti gli altri in riproduzione vanno in pausa; quando se ne avvia uno che si riproduce insieme agli altri, vanno in pausa solo quelli esclusivi. Restituisce una funzione che smette di ascoltare. `playsAlongside(el)` e `videosToPause(started, videos, alongside)` offrono la stessa regola a un host con player propri. In [Folio](/it/docs/document-format-resources#video-sulle-pagine-di-folio) un video che parte da solo e si riproduce insieme agli altri (`autoplay` con `exclusive: false`) si avvia, senza audio, ogni volta che la sua pagina entra in vista e si ferma quando la pagina viene girata, più d’uno in contemporanea, e `loop` lo fa ripartire dall’inizio. Una pagina o un capitolo EPUB con video da coordinare (due o più, di cui uno esclusivo) include la stessa regola come piccolo script, `scripts/videos.js` (l’esportazione `VIDEO_PLAYBACK_SCRIPT`), e il pacchetto dichiara quel documento `scripted`. Un sistema di lettura che esegue gli script fa rispettare la regola ai video di quel documento, ma non a quelli della pagina a fronte, che è un altro documento; uno che non esegue script riproduce ogni video secondo le sue regole, come fanno sempre i player di YouTube e Vimeo.

Le funzioni di risoluzione e di pulizia funzionano come quelle delle altre sezioni, insieme ai tipi `VideoStyleConfig` / `ResolvedVideoStyleConfig`:

```ts
import {
  DEFAULT_VIDEO_STYLE_CONFIG,
  DEFAULT_VIDEO_PLAYER_OPTIONS,
  resolveVideoStyleConfig,
  resolveVideoPlayerOptions,
  stripVideoStyleDefaults,
} from 'postext';

const resolved = resolveVideoStyleConfig(config.videoStyle);
const player = resolveVideoPlayerOptions(resource.video?.player, resolved.player);
const minimal = stripVideoStyleDefaults(config.videoStyle); // undefined when all defaults
```
