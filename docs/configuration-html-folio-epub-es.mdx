# Uso programático: HTML, Folio, EPUB y SCORM


## Integrar el visor HTML

El visor HTML es el renderizador de Postext pensado para la pantalla. En lugar de convertir las páginas en un mapa de bits, genera nodos DOM con posición absoluta cuya geometría sale del mismo proceso que produce la salida impresa. Es la opción adecuada cuando quieres en el navegador una tipografía legible, seleccionable y que responda a los cambios de tamaño (una aplicación de lectura, una vista previa dentro de un producto o un espacio de documentación integrado) sin tener que incluir un visor de PDF.

Las piezas clave de la API pública:

- **`buildDocument(content, config, cache?)`**: ejecuta el proceso completo de maquetación y devuelve un `VDTDocument`.
- **`renderToHtmlIndexed(doc, options)`**: convierte el VDT en una única cadena HTML, más un desglose por página y por bloque. El desglose permite actualizar el DOM con poco coste cuando solo han cambiado algunos bloques entre dos renderizados.
- **`resolveHtmlViewerConfig(partial)`**: completa los valores predeterminados del visor HTML (`maxCharsPerLine`, `columnGap`, `optimalLineBreaking`).
- **`buildFontString` + `measureGlyphWidth` + `dimensionToPx`**: primitivas de medida que sirven para calcular el ancho real de la columna en píxeles a partir de un número objetivo de caracteres.
- **`createMeasurementCache` / `clearMeasurementCache`**: cachés intercambiables para reutilizar las medidas de una maquetación a otra.
- **`prepareFonts` / `buildDocumentWithFonts` / `watchFonts` / `onFontsChanged`**: cargan las fuentes del documento antes de maquetar y vuelven a maquetar cuando llegan fuentes nuevas (véase [Cargar las fuentes antes de componer](/es/docs/configuration-programmatic-usage#cargar-las-fuentes-antes-de-componer)).

### Ejemplo en vivo: una cadena HTML

El recorrido completo en JavaScript sin más, antes de la integración con React que se describe más abajo: construir el documento, pasar el `VDTDocument` a `renderToHtml` y volcar la cadena en un contenedor. `mode: 'single'` apila las páginas en vertical; `background` les da un color, porque por defecto las páginas son transparentes. El pen también muestra el marcado generado, para que veas las líneas con posición absoluta que genera el renderizador: el navegador las pinta, pero nunca las vuelve a componer.

### Integración mínima

El fragmento siguiente es la integración útil más breve: construye el documento al tamaño actual de la ventana, lo dibuja en un contenedor y lo vuelve a maquetar cuando cambia el tamaño.

```tsx
import { useEffect, useRef } from 'react';
import {
  buildDocument,
  renderToHtmlIndexed,
  resolveHtmlViewerConfig,
  buildFontString,
  measureGlyphWidth,
  dimensionToPx,
  createMeasurementCache,
  watchFonts,
  onFontsChanged,
} from 'postext';
import type { PostextConfig, MeasurementCache } from 'postext';

// DPI adecuado para pantalla: a 144 DPI un tamaño de cuerpo de 8pt resuelve a 16 px.
const HTML_DPI = 144;
const PADDING_PX = 24;

// Muestra de prosa usada para medir el ancho objetivo de columna. Las fuentes
// proporcionales hacen poco fiable "N × ancho medio", así que medimos una
// cadena representativa.
const SAMPLE =
  'The quick brown fox jumps over the lazy dog. Sphinx of black quartz, judge my vow.';

function sampleForChars(n: number): string {
  let s = SAMPLE;
  while (s.length < n) s += ' ' + SAMPLE;
  return s.slice(0, n);
}

export function PostextHtmlViewer({
  markdown,
  config,
  mode = 'multi',
}: {
  markdown: string;
  config: PostextConfig;
  mode?: 'single' | 'multi';
}) {
  const hostRef = useRef<HTMLDivElement | null>(null);
  const cacheRef = useRef<MeasurementCache>(createMeasurementCache());

  useEffect(() => {
    const host = hostRef.current;
    if (!host) return;

    const relayout = () => {
      const rect = host.getBoundingClientRect();
      if (rect.width === 0 || rect.height === 0) return;

      const viewer = resolveHtmlViewerConfig(config.htmlViewer);
      const fontFamily = config.bodyText?.fontFamily ?? 'EB Garamond';
      const fontWeight = config.bodyText?.fontWeight ?? 400;
      const fontSize = config.bodyText?.fontSize ?? { value: 8, unit: 'pt' as const };
      const fontSizePx = dimensionToPx(fontSize, HTML_DPI);

      // Mide el ancho *real* de columna para N caracteres de prosa del cuerpo.
      const targetColumnPx = measureGlyphWidth(
        sampleForChars(viewer.maxCharsPerLine),
        buildFontString(fontFamily, fontSizePx, String(fontWeight), 'normal'),
      );

      const inner = Math.max(rect.width - PADDING_PX * 2, 100);
      let columnWidthPx: number;
      if (mode === 'single') {
        columnWidthPx = Math.min(targetColumnPx, inner);
      } else {
        // Encaja tantas columnas como se pueda al ancho objetivo.
        const count = Math.max(
          1,
          Math.floor((inner + viewer.columnGap) / (targetColumnPx + viewer.columnGap)),
        );
        columnWidthPx = (inner - viewer.columnGap * (count - 1)) / count;
      }
      columnWidthPx = Math.max(Math.floor(columnWidthPx), 80);

      // El modo single usa una página muy alta; el modo multi usa la altura
      // del viewport, de modo que cada "página" VDT se convierte en una columna.
      const pageHeightPx =
        mode === 'single' ? Math.max(rect.height * 20, 200_000) : Math.max(rect.height - PADDING_PX * 2, 400);

      const override: PostextConfig = {
        ...config,
        page: {
          ...config.page,
          dpi: HTML_DPI,
          width: { value: columnWidthPx, unit: 'px' },
          height: { value: pageHeightPx, unit: 'px' },
          margins: {
            top: { value: 0, unit: 'px' },
            bottom: { value: 0, unit: 'px' },
            left: { value: 0, unit: 'px' },
            right: { value: 0, unit: 'px' },
          },
        },
        layout: { ...config.layout, layoutType: 'single' },
        bodyText: {
          ...config.bodyText,
          optimalLineBreaking: viewer.optimalLineBreaking,
        },
      };

      const doc = buildDocument({ markdown }, override, cacheRef.current);
      const { html } = renderToHtmlIndexed(doc, {
        mode,
        columnGap: viewer.columnGap,
        padding: PADDING_PX,
        background: 'transparent',
      });

      host.innerHTML = html;
    };

    relayout();

    const ro = new ResizeObserver(() => relayout());
    ro.observe(host);

    // Vuelve a medir cuando cargan las web fonts para que los anchos de glifo no
    // queden tomados a partir de las fuentes de reserva.
    const stopWatching = watchFonts();
    const off = onFontsChanged(() => relayout());

    return () => {
      ro.disconnect();
      off();
      stopWatching();
    };
  }, [markdown, config, mode]);

  return <div ref={hostRef} style={{ width: '100%', height: '100%', overflow: 'auto' }} />;
}
```

Algunas notas sobre lo que hace el ejemplo:

- **Se mide la columna, no se aproxima.** Como `maxCharsPerLine` es un *objetivo* expresado en caracteres, el ancho real en píxeles depende de la fuente del texto base. `measureGlyphWidth` da una medida real con la fuente elegida, y así la medida se mantiene al cambiar de fuente.
- **Se reescribe la página.** El visor HTML trata cada «página» del VDT como una columna en pantalla. El ejemplo sustituye `page.width` por el ancho medido de la columna, pone los márgenes a cero (el relleno está fuera de la página, en el `div` `.pt-doc` que la envuelve) y usa `HTML_DPI = 144` para que un texto base de `8pt` resulte en `16px`.
- **Atento a la carga de fuentes.** `watchFonts` escucha `document.fonts` y, una vez por fotograma, descarta lo medido en las familias cuyas fuentes acaban de llegar; `onFontsChanged` vuelve entonces a maquetar la columna. Sin esa nueva maquetación, el primer renderizado usa las métricas de una fuente de reserva y el texto salta cuando llega la fuente real.
- **Se reutiliza la caché de medidas.** Si la caché se crea una sola vez por componente, los cambios de tamaño y de escala de letra reutilizan las medidas del renderizado anterior en lugar de volver a medir cada párrafo.

### Siguiente paso

El ejemplo anterior es deliberadamente sencillo. Las integraciones en producción suelen añadir:

- **Aislamiento con Shadow DOM**: renderiza en `host.attachShadow({ mode: 'open' })` para que ningún CSS de la página exterior se filtre al visor.
- **Actualización incremental**: `renderToHtmlIndexed` devuelve `pages[i].blocks`, cada uno con un `id` estable y el HTML externo del bloque. Si solo unos cuantos bloques cambian entre dos renderizados, puedes sustituir esos envoltorios donde están en lugar de reconstruir todo el `innerHTML`.
- **Capas superpuestas**: coloca un SVG con posición absoluta sobre cada `.pt-page` para cursores, selecciones o la rejilla base.
- **Enlaces**: las palabras de un enlace Markdown se envuelven en `<a href="…" rel="noopener noreferrer">`, que toma el color del texto y no lleva subrayado; consulta [Formato del documento › Enlaces](/es/docs/document-format-inline#enlaces). En un visor que funcione como editor, intercepta los clics en los `a[href]` que no empiecen por `#` y ábrelos en una pestaña nueva (las anclas de `:ref` enlazan dentro del documento).
- **Imágenes a una sola tinta**: con `diagramStyle.singleInk` activado, los `<img>` SVG reciben un filtro CSS, salvo que pases `singleInk: false` para URL que ya están recoloreadas; consulta [Tinta única en canvas y en HTML](/es/docs/configuration-resources#tinta-única-en-canvas-y-en-html).
- **Páginas compuestas y de cómic sobre una hoja impresa**: en una página tan ancha como la pantalla y tan alta como el desplazamiento, un marco anclado al pie de una página compuesta (`::::page{template}`) quedaría al pie del desplazamiento. Pasa `composedViewerLeaf: { width, height, margins? }` (el tamaño y los márgenes de la página impresa) en la configuración que maquetas, y cada página compuesta se maqueta en una página de ese tamaño, con su geometría de imprenta, para que la escales a la pantalla (desde postext 1.47); `comics.viewerLeaf` hace lo mismo con las páginas de cómic, escaladas a `fitWidth` px (consulta [Cómics](/es/docs/configuration-comics)). Las dos son para anfitriones: las pone el visor HTML del Sandbox y nunca se guardan con un documento.

El componente `HtmlPreview` del Sandbox (`packages/postext-sandbox/src/viewport/HtmlPreview/index.tsx`) implementa todo esto sobre la misma API que se muestra aquí y puede servirte de referencia. Además, envía cada compilación a un worker de maquetación compartido (consulta [Ejecutar la composición en un Web Worker](/es/docs/configuration-programmatic-usage#ejecutar-la-composición-en-un-web-worker)) para que las ediciones en vivo y los cambios de tamaño nunca bloqueen el hilo principal: cuando quieras sacar la maquetación del hilo principal, sustituye la llamada directa a `buildDocument(...)` del fragmento anterior por `layoutWorker.build(...)`.

La página transparente importa en un sitio con tema oscuro: una vista previa sin `background` muestra texto negro sobre el fondo oscuro del sitio. Pasa `renderToHtml(doc, { background: '#ffffff' })`, o da al documento un `page.backgroundColor`.

**Los estilos de texto de la página anfitriona se quedan fuera.** Cada línea se compone con los anchos que midió el motor, así que un `letter-spacing`, un `word-spacing`, un `text-transform` o un `font-variant` que la salida heredara de la página que la contiene ensancharía los tramos de glifos y las líneas se montarían unas sobre otras. Por eso la raíz `.pt-doc` restablece las propiedades de texto heredables —espaciado entre letras y entre palabras, caja, sangría, espacios en blanco, estilo, variante, peso, anchura, rasgos y kerning de la fuente, interlineado, alineación, sombra y énfasis del texto, guiones, dirección, modo de escritura, trazo y relleno del texto y el agrandado del texto en móviles— antes de sus propias declaraciones de maquetación, de modo que la salida se ve igual dentro de una *shadow root* o bajo un elemento con estilos. La lista se exporta como `HTML_TEXT_RESET`, una cadena de declaraciones CSS: un anfitrión que monta el `innerHtml` de las páginas (de `renderToHtmlIndexed`) en contenedores propios la aplica a su raíz. Hasta postext 1.4 la raíz no restablecía nada; el remedio era un envoltorio con `all: initial`.


## Un libro en 3D (`postext-folio`)

`postext-folio` presenta en pantalla un documento maquetado como un libro impreso abierto sobre una mesa: dobles páginas que respetan la regla de las páginas impares y hojas que el lector pasa con los botones ‹ ›, las flechas del teclado, deslizando el dedo, con un clic en una página o tomando la página por su borde y arrastrándola. Cada hoja se curva en three.js según su papel y proyecta una sombra real sobre las páginas que tiene debajo. El canvas WebGL dibuja el libro tanto en reposo como al pasar las hojas, así que una página nunca cambia de aspecto al posarse. Es el visor de las recetas del Recetario y de la pestaña **Folio** del Sandbox.

```bash
npm install postext postext-folio three
```

```ts
import { buildDocument } from 'postext';
import { createFolioFromDocument } from 'postext-folio';

const doc = buildDocument({ markdown }, config);
const book = createFolioFromDocument(document.getElementById('book')!, doc, {
  onChange: ({ pages }) => console.log('páginas a la vista', pages),
});

// Tras una edición: el mismo visor, en la misma página.
book.setDocument(buildDocument({ markdown: edited }, config));
```

- **Las páginas se pintan a medida que hacen falta.** `createFolioFromDocument` pinta cada página con `renderPageToCanvas` exactamente a los píxeles de dispositivo de su hueco (WebGL la muestra entonces téxel a píxel, tan nítida como en la vista previa del canvas), y solo las dobles páginas cercanas a la abierta (`window`, tres a cada lado por defecto). Las páginas que salen de esa ventana se liberan, así que un libro de mil páginas ocupa la memoria de unas pocas. Un salto a una página lejana pinta primero esa doble página. Hasta diez páginas, las hojas pasan una a una; más allá, el bloque de páginas intermedio se levanta como una sola pieza, tan gruesa como esas páginas (la suma de sus calibres), y se posa al otro lado. `setDocument` conserva lo pintado de cada página que queda igual en la nueva maquetación (`{ repaint: true }` las vuelve a pintar todas, por ejemplo cuando acaba de llegar una imagen).
- **El documento define el libro.** Su primera página aparece sola a la derecha cuando es impar (`pageIndexOffset` par), un libro encuadernado por la derecha (`page.binding: 'right'`, o un documento vertical) aparece en espejo y pasa las páginas hacia la izquierda, las páginas en blanco toman el color de fondo de la página, y el ancho de corte de la página (`pageWidthMm`) escala el grosor del papel y las tapas. Un capítulo maquetado con una `continuation` suma las demás páginas del libro (`pageIndexOffset` antes, `bookPageCount` después) al grosor de los dos bloques de páginas sin dibujarlas (`extraPages`).
- **El documento define el aspecto.** El papel, la encuadernación, la mesa y la luz son los [ajustes `folio`](/es/docs/configuration-fonts-colors-viewers#visor-folio-configuración) del documento (`doc.config.folio`). Una página compuesta dentro de una tanda `:::paper` lleva su propio papel (`VDTPage.paper`), y su hoja se dibuja con el color, la superficie, el grosor y la rigidez de ese papel. Con `binding.cover: 'pages'`, la primera página es la tapa delantera y la última, si es par, la trasera (`covers`). Un formato de periódico (`'broadsheet'`, `'berliner'`, `'tabloid'`, `'compact'`) cuyos ajustes no indican papel ni encuadernación aparece como papel prensa doblado, también cuando el anfitrión pasa su propio `folio`.
- **El contenedor define el tamaño.** El libro lo ocupa entero, con los botones y el contador de páginas en los márgenes, así que dale una altura; al cambiar de tamaño, las páginas se vuelven a pintar al nuevo. Por debajo de 560 px de ancho muestra una página cada vez (`mode: 'auto'`; `'single'` y `'double'` fuerzan una u otra): el lomo va por el borde interior de la página y la hoja gira sobre él; arrastrar hacia el lomo avanza, deslizar en sentido contrario retrocede, y un toque pasa la página.
- **Qué hace el puntero.** `interaction` (y después `setInteraction`) fija qué hace el botón izquierdo, un dedo o un lápiz sobre el libro: `'hand'` (por defecto) toma las páginas y las pasa, `'orbit'` gira la vista como al arrastrar con el botón derecho (para trackpads y tabletas), `'select'` deja el puntero al anfitrión, por ejemplo para seleccionar texto. `pageAt(event)` da la página bajo un puntero y el punto de ella (`{ page, x, y }`, fracciones de la página desde su esquina superior izquierda), sobre el libro tal como se ve, inclinado o girado; `pointOnScreen(point)` hace el camino inverso, para dibujar un cursor o una selección sobre la página. `refreshPage(src)` vuelve a mostrar el canvas de una página que la aplicación anfitriona ha repintado en su sitio. El Sandbox los usa todos para seleccionar texto y seguir el cursor del editor sobre las páginas en 3D.
- **Una lupa para la letra pequeña.** `interaction: 'magnify'` sostiene sobre el libro, donde está el puntero, un cristal redondo con aro negro (un dedo la sostiene por encima de sí mientras toca la pantalla). Muestra el libro como lo ve el ojo del lector, iluminado y curvado como está, con más aumento en el centro y curvándose hacia el aro. La rueda, `+` y `−` cambian el aumento (`setMagnification(zoom)`, de 1,5 a 10; por defecto, la página a unos 5,5 px CSS por milímetro) y Esc la retira; `magnifier: { zoom, diameter }` fija ambos desde el principio. `createFolioFromDocument` vuelve a pintar las páginas bajo el cristal con nitidez suficiente para su centro, de modo que se puede leer el texto de un periódico; `createFolio` obtiene esas imágenes de `detail: { paint(index, deviceWidth), release() }`. El Sandbox la pone en el botón **Lupa** (M). La lupa también selecciona texto: sobre las páginas el cursor es el de texto, `pageAt` devuelve el punto bajo el centro de la lupa (encima del dedo en una pantalla táctil) y en el Sandbox un clic coloca ahí el cursor de edición y un arrastre selecciona.
- **El lector puede rodear el libro.** Arrastrar con el botón derecho gira la vista alrededor del libro (hasta 70° desde la vertical), también mientras pasan hojas; `resetView()` la devuelve con suavidad a la `tilt` y el `yaw` de los ajustes, y `getView()` da la vista tal como se ve ahora (`{ tilt, yaw }`, en grados) para guardarla en esos ajustes. El Sandbox los ofrece en dos botones, **Restablecer la vista** y **Guardar como vista por defecto**.
- **Los vídeos se reproducen en las páginas.** Un clic en la portada de un vídeo lo reproduce en la página, en cualquiera de los modos de `interaction`, y el vídeo sigue en marcha mientras pasa su hoja; otro clic lo pausa, y se detiene cuando el libro se queda quieto en una doble página que no lo muestra. Un vídeo con `player.autoplay` arranca solo la primera vez que se muestra su doble página; si además se reproduce junto a otros (`player.exclusive: false`), arranca sin sonido cada vez que se muestra su doble página y se detiene al pasarla, y pueden reproducirse varios a la vez. Las opciones son `videos`, `videoUrl` y `onVideo`, y el visor tiene `stopVideo()`; consulta [Formato del documento › Vídeos en las páginas de Folio](/es/docs/document-format-resources#vídeos-en-las-páginas-de-folio).
- **Antes, fuentes e imágenes.** Como con `renderPage`, las fuentes del documento deben estar cargadas en `document.fonts` y sus imágenes registradas con `registerResourceImage` antes de pintar las páginas.
- **Accesible.** El visor es un grupo enfocable que responde a ←/→ (en espejo para un libro encuadernado por la derecha), Re Pág/Av Pág, Inicio y Fin; sus botones y el contador de páginas llevan etiqueta (`labels` las traduce), y cada canvas de página lleva texto alternativo (`alt: (index) => …`).
- **Sin WebGL2**, o cuando el lector pide movimiento reducido, las dobles páginas simplemente cambian. Un libro en WebGL pesa demasiado para un móvil (una textura por cada cara de página): el Sandbox ofrece su pestaña Folio solo donde hay WebGL2 y el lado corto de la pantalla mide al menos 600 px. `canFlip()` dice si las hojas pasarán en 3D en ese entorno: con WebGL2 y sin preferencia de movimiento reducido.

## Libros EPUB (`postext-epub`)

`postext-epub` escribe un libro maquetado como un archivo EPUB 3.3, en el navegador o en Node, sin servidor. Lee los mismos documentos por capítulo que `renderToPdf` recibe para un libro, así que los números de página, las notas, las citas, las referencias cruzadas, el índice general y el analítico llegan resueltos, y devuelve el archivo como bytes. Es el escritor que usa la pestaña **EPUB 3** del Sandbox.

```bash
npm install postext postext-epub
```

`postext` es una dependencia *peer*, como en `postext-pdf`: actualiza los dos a la vez y, desde un CDN, fíjalos en la misma versión.

### Escribir un libro

```ts
import { openBundle, buildBundle } from 'postext';
import { renderToEpub } from 'postext-epub';

const bundle = await openBundle(fileBytes);
const docs = buildBundle(bundle); // un VDTDocument por capítulo, en el orden del libro

const bytes = await renderToEpub(docs, {
  layout: 'reflowable',
  metadata: { title: 'Linterna', creators: ['Ada Lovelace'], language: 'es' },
  fonts: bundle.fonts.map((f) => ({ family: f.family, weight: f.weight, style: f.style, bytes: new Uint8Array(f.bytes), format: f.format })),
  resourceBytes: (fileId) => {
    const data = bundle.files.get(fileId);
    return data ? { bytes: data, mediaType: '' } : undefined;
  },
  onWarning: (w) => console.warn(w),
});
```

Un documento suelto es un libro de un capítulo: `renderToEpub([doc], options)`.

- **`renderToEpub(docs, options): Promise<Uint8Array>`** escribe el archivo. `options` es `{ layout, metadata, fonts?, svgFonts?, resourceBytes?, cover?, onProgress?, onWarning?, signal?, kindlePanelView? }`.
- **`metadata`**: `title` y `language` (una etiqueta BCP 47) son obligatorios; `subtitle`, `creators`, `identifier`, `date`, `publisher`, `rights`, `description` y `modified` son opcionales. Un ISBN sin prefijo pasa a `urn:isbn:…`. Sin `identifier`, el libro recibe un `urn:uuid:` derivado del título, los autores y el idioma, de modo que una versión nueva del mismo libro conserva su sitio en la biblioteca del lector. Pasa también `modified` para obtener un archivo idéntico byte a byte.
- **`fonts`**: las variantes que se incrustan, `{ family, weight, style, bytes, format, unicodeRange? }`, con `format` uno de `woff2`, `woff`, `ttf`, `otf`. Cada variante pasa a ser un archivo y una regla `@font-face`; varios archivos con su `unicodeRange` forman una sola variante (los tramos de Google Fonts). Una familia, un peso o un estilo que las páginas usan sin variante incrustada se avisa como `missingFont`, y los lectores ponen una suya. Incrusta solo las fuentes cuya licencia lo permita: una variante con `redistributable: false` nunca se escribe en el archivo (el libro puede componerse con ella, pero su archivo queda fuera, también de las imágenes SVG). Una aplicación anfitriona puede dar en su lugar las variantes de la familia abierta con el nombre de la familia con licencia (son variantes corrientes), que es lo que hacen el Sandbox y `postext` con una familia que indica un `fallback` (desde postext 1.43).
- **`resourceBytes(fileId)`**: las imágenes que colocan las páginas, de forma síncrona o asíncrona, como `{ bytes, mediaType }`; un `mediaType` vacío se lee de los bytes. Da los mapas de bits tal como están guardados y los SVG como su código fuente, no el máster PDF de imprenta (`svg.pdfFileId`). Cada imagen se guarda una vez. En un libro a una tinta (`diagramStyle.singleInk`) los SVG se recolorean en el archivo. Cada SVG lleva incrustadas las variantes que nombra su texto, porque un lector lo muestra como una imagen que no ve las fuentes del libro (consulta [Fuentes en el texto de los SVG](/es/docs/configuration-resources#fuentes-en-el-texto-de-los-svg)): desde `fonts` (los tramos que contienen sus caracteres) y después desde **`svgFonts.provider`** para una familia que el texto del libro no usa. Las familias de variantes marcadas con `redistributable: false`, y las que nombre `svgFonts.withhold(family)`, quedan fuera y se avisan una vez cada una como `fontWithheld`; una familia sin variante se avisa como `svgFontUnavailable`, y las variantes que superan `svgFonts.maxBytes` (2 MiB), como `svgFontsTooLarge`. `svgFonts.inline: false`, `diagramStyle.inlineFonts: false` y el `svg.inlineFonts: false` de un recurso conservan los bytes tal como se dan. Una imagen sin bytes se avisa como `missingImage` y queda como un marco vacío. `svgFonts.standIn(family)` (desde postext 1.43) indica una familia abierta que sustituye a una de ellas: a `svgFonts.provider` se le pide la cara de esa familia con el mismo peso e inclinación, que entra en la imagen con el nombre de la familia retenida; si no la tiene, la familia queda fuera y se avisa.
- **`cover`**: `{ bytes, mediaType, alt?, showsFirstPage? }`, una imagen JPEG, PNG, WebP o SVG. El libro se abre entonces con un documento de cubierta que la contiene, y es la `cover-image` del paquete (la miniatura en una biblioteca). Sin ella, la maquetación fija toma su primera página como cubierta, y el libro de maquetación fluida no tiene imagen de cubierta. `showsFirstPage: true` indica que la imagen es una captura de la primera página impresa: la maquetación fija la usa entonces solo como `cover-image` y se abre en esa página, que si no se vería dos veces; el libro de maquetación fluida se abre en el documento de cubierta, como siempre.
- **`kindlePanelView`**: en una maquetación fija con páginas de cómic, añade Kindle Panel View, una zona táctil sobre cada viñeta que la muestra ampliada, con los metadatos que pide Kindle. Cada zona contiene una copia del cómic de su página, así que cada página crece una copia por viñeta; resérvalo para los libros destinados a Kindle. Por defecto, `false`. La navegación por regiones, que puede usar cualquier sistema de lectura, se escribe en los dos casos (véase [Salida de los cómics](/es/docs/comics#salida-de-los-cómics)).
- **`onProgress({ phase, done, total })`**: `resources` (fuentes e imágenes), `documents` (páginas en la maquetación fija, capítulos en la fluida) y después `package`. **`signal`** interrumpe entre pasos.
- **`readEpub(bytes)`** lee un archivo para un visor, sin `DOMParser`: maquetación, metadatos, sentido de lectura, cada archivo por su ruta, el manifiesto, el spine, el índice, la lista de páginas, el viewport de la maquetación fija y la cubierta. El lector del Sandbox se apoya en ella.

Las dos maquetaciones llevan los metadatos de EPUB Accessibility 1.1 (modos de acceso, prestaciones como el índice y los números de página impresos, riesgos y un resumen) y no declaran conformidad con WCAG por omisión. La lista completa de opciones y las limitaciones están en el [README del paquete](https://www.npmjs.com/package/postext-epub).

### Comprobar un archivo con EPUBCheck

[W3C EPUBCheck](https://www.w3.org/publishing/epubcheck/) es el validador de referencia de EPUB; las tiendas de libros electrónicos comprueban con él los archivos que reciben. Con él instalado (`brew install epubcheck`, o la versión Java), `epubcheck libro.epub` enumera errores, avisos y notas de uso; las notas de uso que deja la salida de Postext (`CSS-028`, `OBS-001`, `HTM_062`) son informativas. En el repositorio de Postext, `pnpm --filter postext-epub epubcheck` comprueba los libros de muestra de las pruebas, `node packages/postext-epub/scripts/epubcheck.mjs libro.postext --layout both` maqueta un archivo `.postext` o una carpeta de preset y comprueba las dos maquetaciones, y `pnpm --filter postext-epub validate` recorre toda la matriz de libros (la guía, los libros de ejemplo de la portada y libros en chino, en árabe y del Recetario), que pasan todos sin errores ni avisos.

## Paquetes SCORM (`postext-scorm`)

`postext-scorm` escribe un libro, o los capítulos y secciones que se elijan de él, como un paquete SCORM: el zip que un sistema de gestión del aprendizaje (Moodle, Canvas, Blackboard, SCORM Cloud y casi todos los demás) importa como un curso. El contenido es el del escritor de EPUB, páginas fijas o texto fluido, en forma de páginas HTML5; cada parte que sigue el LMS lleva alrededor un pequeño reproductor, y sus ejercicios envían al LMS la puntuación, si se ha completado y si se ha aprobado. Es el escritor que usa la pestaña **SCORM** del Sandbox.

```bash
npm install postext postext-epub postext-scorm
```

`postext` y `postext-epub` son dependencias *peer*: actualiza los tres a la vez.

### Escribir un paquete

```ts
import { openBundle, buildBundle } from 'postext';
import { renderToScorm, scormTree, scormOrganization, treeLeaves } from 'postext-scorm';

const bundle = await openBundle(fileBytes);
const docs = buildBundle(bundle);

// El esquema del libro: los capítulos y sus encabezados hasta el tercer nivel.
const tree = scormTree(bundle.chapters.map((c) => ({ markdown: c.markdown, title: c.title })));
// El capítulo 1 entero y dos secciones del capítulo 2.
const picked = new Set([tree[0]!, tree[1]!.children[0]!, tree[1]!.children[2]!].flatMap(treeLeaves).map((n) => n.id));

const zip = await renderToScorm(docs, {
  version: '1.2',
  layout: 'fixed',
  items: scormOrganization(tree, picked),
  metadata: { title: 'Linterna', language: 'es' },
  fonts, resourceBytes, // como en renderToEpub
});
```

- **`renderToScorm(docs, options): Promise<Uint8Array>`** escribe el zip. `docs` son los documentos por capítulo que recibe `renderToEpub`. `options` es `{ version, layout, items?, metadata, fonts?, svgFonts?, resourceBytes?, cover?, passingScore?, onProgress?, onWarning?, signal? }`; `metadata`, `fonts`, `svgFonts`, `resourceBytes` y `cover` son los del escritor de EPUB.
- **`version`**: `'1.2'` o `'2004'` (SCORM 2004, 4.ª edición). Todos los LMS admiten SCORM 1.2. SCORM 2004 separa la finalización del éxito, da una puntuación escalada y guarda hasta 64.000 caracteres de respuestas, donde SCORM 1.2 guarda 4.096; elígelo cuando el LMS lo admita y eso importe.
- **`layout`**: `'fixed'`, cada página impresa ajustada a la ventana, o `'reflowable'`, el texto recompuesto para la ventana, como en [Maquetación fija y maquetación fluida](#maquetación-fija-y-maquetación-fluida).
- **`items`**: la organización que muestra el LMS, un árbol de `{ title, doc?, range?, children? }`. Un elemento con `children` los agrupa; uno sin ellos es un SCO, una parte que el LMS abre, sigue y califica por separado: el capítulo `doc` entero o su tramo `range` (`{ start, end? }`, posiciones en el Markdown del capítulo tal como está escrito, con el *front matter* incluido). Sin `items`, cada capítulo es un SCO.
- **`scormTree(chapters, config?)`** enumera los capítulos y sus encabezados de los niveles 1 a 3, cada uno con el tramo que representa: desde su línea hasta el siguiente encabezado de su nivel o superior. El primer encabezado bajo un capítulo o bajo otro encabezado se lleva también el texto que lo precede, de modo que el título y los párrafos iniciales de un capítulo van con su primera sección. **`scormOrganization(tree, picked)`** convierte un conjunto de ids de hojas elegidas en `items`: un nodo elegido entero es un SCO; uno elegido en parte agrupa los elementos de sus hijos. `treeLeaves(node)` y `pickState(node, picked)` (`'all'`, `'some'`, `'none'`) ayudan a montar un árbol con casillas.
- **`passingScore`**: el porcentaje de respuestas calificadas correctas con el que se aprueba, por encima del `exercises.digital.passingScore` de los documentos. `0` o sin valor: ni aprobado ni suspenso.

Un SCO de maquetación fija contiene todas las páginas impresas que toca su parte, así que una página que comparten dos partes aparece en las dos. Un SCO de maquetación fluida contiene exactamente el texto de su parte, cortado en sus encabezados. Los enlaces de las páginas de un SCO a las de otro se quitan, porque un LMS sigue un SCO por lo que abre. El reproductor muestra un documento cada vez, con ← y → (o Re Pág y Av Pág en las páginas fijas), el índice del SCO y la posición; un libro encuadernado por la derecha pasa las páginas hacia la izquierda.

### Qué llega al LMS

El reproductor busca la API del LMS como pide SCORM (`API` en SCORM 1.2, `API_1484_11` en SCORM 2004, subiendo por la cadena de ventanas padre y después en la ventana que lo abrió) y le envía:

- **Puntuación.** Un ejercicio cuenta su última comprobación: las respuestas calificadas correctas sobre el total de respuestas calificadas, la puntuación que muestra su barra. La puntuación de un SCO es la suma de las respuestas correctas sobre la suma de las respuestas calificadas de sus ejercicios, así que un crucigrama de veinte casillas pesa más que un verdadero o falso; un ejercicio que no se ha comprobado nunca no suma ninguna respuesta correcta. SCORM 1.2 la recibe como porcentaje (`cmi.core.score.raw`, de 0 a 100); SCORM 2004, como fracción (`cmi.score.scaled`), con las respuestas como `raw` y `max`. Un ejercicio pertenece a la parte en la que está su contenedor: solo ese SCO lo cuenta, aunque su página aparezca también en un SCO vecino.
- **Finalización.** Un SCO queda completado cuando se han mostrado todas sus páginas o documentos y se han comprobado todos los ejercicios que cuenta (o ya no les quedan comprobaciones). Hasta entonces está incompleto, y el LMS guarda el punto de lectura para la siguiente visita.
- **Éxito.** Con una nota para aprobar, un SCO completado queda aprobado o suspenso según ella. El manifiesto la lleva (`adlcp:masteryscore` en SCORM 1.2, un objetivo principal con `minNormalizedMeasure` en SCORM 2004), y el reproductor toma el valor que le devuelve el LMS, así que, si el LMS fija la suya, manda la del LMS.
- **Interacciones.** Cada comprobación escribe el ejercicio como una interacción: un id sacado de su ancla o de su número, un tipo de interacción según el tipo de ejercicio (`true-false`, `choice`, `fill-in`, `other`), la respuesta del lector, la correcta, el resultado y un peso según sus respuestas calificadas; SCORM 2004 añade una descripción y guarda una interacción por ejercicio, y SCORM 1.2 añade una por comprobación.
- **Agregación.** SCORM 2004 pondera en el manifiesto la medida de cada SCO por sus respuestas calificadas, de modo que la puntuación del curso es el total de respuestas correctas sobre el total de respuestas calificadas. SCORM 1.2 no tiene agregación propia: decide el método de calificación del LMS (Moodle ofrece la más alta, la media o la suma de las puntuaciones de los SCO).
- **Respuestas.** Van en `cmi.suspend_data` con las comprobaciones y los reinicios gastados, de modo que los límites de un intento ([Evaluación](/es/docs/configuration-exercises#evaluación)) se mantienen entre visitas y dispositivos. Si pasan de los 4.096 caracteres de SCORM 1.2, los recuentos siguen llegando al LMS y las respuestas se quedan en el navegador del lector.

Abierto fuera de un LMS (la página de inicio sola, o el paquete en un servidor web), el reproductor no encuentra ninguna API: el libro se lee igual y los ejercicios guardan las respuestas en el navegador, como en un libro HTML o EPUB.

### Comprobar un paquete

Las pruebas validan con `xmllint` los manifiestos de las dos versiones contra los esquemas de IMS y ADL. Para probar un paquete, importa el zip en un LMS (la actividad SCORM de Moodle admite las dos versiones) o en [SCORM Cloud](https://cloud.scorm.com/). También sirve un sustituto local: [scorm-again](https://github.com/jcputney/scorm-again) ofrece las API de SCORM 1.2 y 2004 en una página que enmarca la página de inicio, y rechaza los valores que el modelo de datos no admite.
