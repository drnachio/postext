# Configuración: uso programático


## Uso programático

> **La opción recomendada: usa el Web Worker.** En el navegador, maqueta a través de `createLayoutWorker()` de `postext/worker` en lugar de llamar a `buildDocument` en el hilo principal. El worker mantiene la página receptiva durante la maquetación, conserva las medidas del texto entre una maquetación y la siguiente, y cancela la que esté en curso cuando empieza otra más reciente, de modo que una pulsación nunca espera a que se maquete un texto anterior. La receta está en [Ejecutar la composición en un Web Worker](#ejecutar-la-composición-en-un-web-worker). El resto de esta sección (`buildDocument` directo, resolvedores, funciones de limpieza, cachés) sigue valiendo: el worker recibe las mismas entradas y devuelve las mismas salidas. Llama a `buildDocument` en el hilo principal solo para exportaciones puntuales, renderizado en servidor (Node) o pruebas.

### Construir un documento

La función `buildDocument` ejecuta todo el proceso de composición y devuelve un árbol virtual del documento (VDT, *Virtual Document Tree*) con las coordenadas exactas de cada elemento. Es el punto de entrada de más bajo nivel; el código de la interfaz debería usar preferentemente el [envoltorio del Web Worker](#ejecutar-la-composición-en-un-web-worker), que llama a `buildDocument`, con los mismos argumentos, dentro de un hilo de worker dedicado.

```ts
import { buildDocument } from 'postext';

const content = {
  markdown: '# Capítulo uno\n\nLa historia comienza aquí...',
};

const config = {
  page: { sizePreset: '17x24' },
  layout: { layoutType: 'double' },
  bodyText: { fontFamily: 'EB Garamond', fontSize: { value: 9, unit: 'pt' } }, // 9 pt sobrescribe el valor por defecto de 8 pt
};

// Construir la composición — produce un VDT con una entrada por página en `vdt.pages`
const vdt = buildDocument(content, config);
console.log(`El documento tiene ${vdt.pages.length} páginas`);
```

### Avisos del documento

`buildDocument` no se detiene ante una referencia errónea o un estilo desconocido: aplica una alternativa y registra lo que ha hecho en `doc.contentWarnings`. Los recuadros que la maquetación ha tenido que forzar están en `doc.warnings`, que conserva la forma que tenía en postext 1.4: todas sus entradas son de tipo `calloutOverflow`, con su `pageIndex`, su `columnIndex` y su `overflowPx`. Cada campo falta si no hay nada que comunicar. Todas las entradas tienen un `kind`. Los avisos de contenido incluyen el rango de origen de la construcción (`sourceStart` / `sourceEnd`, posiciones en el Markdown que pasaste, frontmatter incluido) y, si la construcción ha quedado en una página, su `pageIndex`.

Los avisos sobre un recurso (su estilo de tabla, su estructura, una referencia dentro de su pie, de su nota o de sus celdas) apuntan a la primera inserción o referencia del recurso en el texto, y cada uno se registra una sola vez por recurso. Solo se comprueban los recursos que usa el documento: un capítulo de un libro avisa de las tablas que cita, no de todas las tablas del libro.

```ts
import { buildDocument, formatWarning } from 'postext';

const doc = buildDocument({ markdown: 'Véase :ref{id="fig-map"}.\n\n:::sidebar\nNotas.' }, config);
for (const w of [...(doc.warnings ?? []), ...(doc.contentWarnings ?? []), ...(doc.configWarnings ?? [])]) console.warn(formatWarning(w));
// Unknown resource id "fig-map" in :ref — it prints "?" (or its text= label), with no number or link (page 1, offset 6)
// Unknown directive ":::sidebar" — the line is set as text (page 1, offset 27)

// Estrecha por `kind` para leer los campos de un tipo.
const missing = (doc.contentWarnings ?? []).flatMap((w) => (w.kind === 'unknownResourceId' ? [w.resourceId] : []));
```

`formatWarning(w)` devuelve una descripción de una línea en inglés. Una aplicación que traduce sus mensajes debe distinguir los casos por `kind` y mantener una rama por defecto, porque las versiones menores pueden añadir tipos nuevos. `collectContentWarnings(markdown, config, resources)` devuelve los avisos de contenido sin maquetar nada (la lista que añade la compilación, sin `pageIndex`), para un editor que revise el texto a medida que se escribe. `collectHeadingDesignCuts(doc)` busca, en una maquetación terminada, diseños de encabezado cuyo texto sobrepasa el pie de su página o de su columna (`kind: 'headingDesignCut'`; véase [Altura reservada](/es/docs/configuration-headings#altura-reservada)), algo de lo que la maquetación por sí misma no avisa, y `formatWarning` también describe sus resultados. El panel **Revisión** del Sandbox los muestra todos.

Los renderizadores comunican lo que no pueden pintar como se les pide mediante una opción `onWarning`: `renderPageToCanvas`, `renderPage` y `renderToCanvas` (`RenderPageOptions`), `renderToHtml` y `renderToHtmlIndexed` (`RenderHtmlOptions`), y `renderToPdf` (`RenderToPdfOptions`, también a través del worker de PDF). El principal aviso de renderizado es `missingImage`: una imagen (una figura, la imagen de una celda de tabla, el icono de un recuadro, una imagen de diseño) que no tiene nada que dibujar se pinta como un marcador de posición neutro y se comunica una vez por cada `fileId` y llamada de renderizado, con su `pageIndex`, el `resourceId` si quien pinta lo conoce (figuras e imágenes de celda) y, en el PDF, el `documentIndex` de un renderizado de varios documentos. «Nada que dibujar» significa que no hay ningún `registerResourceImage` para el `fileId` en el canvas, ninguna URL de `resourceImageUrl` en HTML y ningún byte de `resourceBytes` (o bytes que no se pueden decodificar) en el PDF. Un recurso de mapa de bits o SVG que no indica ningún `fileId` no tiene nada que pedir: se dibuja como marcador de posición, sin aviso. Hay otros dos tipos que proceden de las funciones que incrustan fuentes en las imágenes SVG (`registerSvgImage`, `registerBundleImages`, `bundleImageUrl`, `renderToHtml` con `inlineSvgFonts`, postext-epub; véase [Fuentes en el texto de los SVG](/es/docs/configuration-resources#fuentes-en-el-texto-de-los-svg)), con el `fileId` y el `resourceId` de la imagen: `svgFontUnavailable` (`family`, `weight`, `style`), una familia que usa su texto y de la que no hay ningún estilo que incrustar, de modo que la imagen compone ese texto con una fuente de reserva, y `svgFontsTooLarge` (`bytes`, `maxBytes`), estilos que superan el límite de tamaño y de los que no se incrusta ninguno. Los avisos de renderizado no se guardan en el VDT: lo que puede aportar una aplicación cambia después de la maquetación.

```ts
import { buildDocument, renderPage, type RenderWarning, type Resource } from 'postext';

const map: Resource = {
  id: 'fig-map', typeId: 'figure', kind: 'bitmap', caption: 'La ruta.', createdAt: 0, updatedAt: 0,
  bitmap: { fileId: 'map-file', format: 'png', width: 1200, height: 800 },
};
const doc = buildDocument({ markdown: 'Véase :ref{id="fig-map"}.', resources: [map] }, config);

const warnings: RenderWarning[] = [];
const canvas = renderPage(doc.pages[0], doc, { onWarning: (w) => warnings.push(w) });
// Hasta que 'map-file' se registre con registerResourceImage:
// [{ kind: 'missingImage', fileId: 'map-file', resourceId: 'fig-map', pageIndex: 0 }]
```

### Renderizar una página como mapa de bits

Cada página se puede rasterizar por separado. Usa `renderPage(page, doc)` para obtener un `HTMLCanvasElement` de un número de página dado: el canvas es un mapa de bits con el tamaño exacto de la página en píxeles (a la resolución configurada), así que puedes mostrarlo, exportarlo o pasarlo a cualquier proceso de tratamiento de imágenes:

```ts
import { buildDocument, renderPage } from 'postext';

const vdt = buildDocument(content, config);

// Renderizar la página 3 (índice base 0) como bitmap
const pageNumber = 2;
const page = vdt.pages[pageNumber];
if (!page) throw new Error(`La página ${pageNumber} no existe`);

const canvas = renderPage(page, vdt);
// canvas.width / canvas.height son el tamaño del bitmap de la página en píxeles

// Mostrarlo en el DOM
document.body.appendChild(canvas);

// …o exportarlo como PNG data URL
const pngDataUrl = canvas.toDataURL('image/png');

// …o obtener un Blob para descargar o subir
canvas.toBlob((blob) => {
  if (blob) saveAs(blob, `pagina-${pageNumber + 1}.png`);
}, 'image/png');

// …o acceder a los píxeles RGBA crudos
const ctx = canvas.getContext('2d')!;
const imageData = ctx.getImageData(0, 0, canvas.width, canvas.height);
```

Si prefieres pintar en un canvas que ya tienes (por ejemplo, uno insertado en el DOM con una maquetación concreta), usa `renderPageToCanvas(page, doc, canvas)`: cambia el tamaño del canvas que le pases y pinta en él, en lugar de crear uno nuevo.

Para renderizar todas las páginas, itera sobre `vdt.pages`:

```ts
const bitmaps = vdt.pages.map((page) => renderPage(page, vdt));
```

### React

`postext/react` exporta `createLayout(content, config?)`: un componente que maqueta el documento una sola vez, al montarse, y muestra cada página como un `<canvas>` dentro de un `<div>`.

```tsx
import { createLayout } from 'postext/react';

const Article = createLayout(
  { markdown: '# Hola\n\nEl primer párrafo del artículo.' },
  { page: { sizePreset: '17x24' } },
);

export function ArticlePage() {
  return <Article className="pages" style={{ maxWidth: 480 }} />;
}
```

- **En el hilo principal, una sola vez.** Las páginas se pintan a la resolución del documento y se escalan al ancho del contenedor. `content` y `config` quedan fijados al llamar a `createLayout`; para mostrar otra cosa, crea otro componente. Para una vista previa en directo, compila en el [Web Worker](#ejecutar-la-composición-en-un-web-worker) y pinta con `renderPageToCanvas`, como en el ejemplo de React de esa sección.
- **Primero, las fuentes y las imágenes.** Carga las fuentes web del documento antes de que se monte el componente, y registra sus imágenes con `registerResourceImage`. Si el Markdown contiene un `$`, el componente arranca por su cuenta el [motor de fórmulas](/es/docs/configuration-lists-math#arrancar-el-motor-de-fórmulas).
- **React se queda fuera de la entrada principal.** `postext` nunca importa React; solo lo hace `postext/react`. `createLayout` se sigue exportando desde `postext` para que el código existente siga funcionando, pero está obsoleto: carga `postext/react` cuando lo llamas, y el componente queda en suspenso hasta que llega (React lo vuelve a renderizar por sí solo). Impórtalo desde `postext/react`.
- **El componente obsoleto queda en suspenso.** Hasta que llega `postext/react`, el `createLayout` de `postext` necesita una raíz concurrente (`createRoot`) o un límite `<Suspense>` por encima. En una raíz antigua de `ReactDOM.render`, o en `renderToString`, sin ese límite, React da un error. `react` sigue siendo una dependencia de pares (*peer dependency*) obligatoria, para que los empaquetadores puedan resolver esa importación diferida.

### Resolver valores por defecto

Las funciones de resolución rellenan los valores por defecto de los objetos de configuración parciales. Son útiles cuando necesitas una configuración completa para examinarla o compararla:

```ts
import { resolvePageConfig, resolveBodyTextConfig } from 'postext';

const fullPage = resolvePageConfig({ sizePreset: '21x28' });
// => { sizePreset: '21x28', width: { value: 21, unit: 'cm' }, height: { value: 28, unit: 'cm' },
//      margins: { top: { value: 2, unit: 'cm' }, ... }, dpi: 300, cutLines: { enabled: false, ... }, ... }

const fullBody = resolveBodyTextConfig({ fontFamily: 'Inter' });
// => { fontFamily: 'Inter', fontSize: { value: 8, unit: 'pt' }, lineHeight: { value: 1.5, unit: 'em' }, ... }
```

Funciones de resolución disponibles, una por sección de primer nivel: `resolvePageConfig`, `resolveLayoutConfig`, `resolveBodyTextConfig`, `resolveHeadingsConfig`, `resolveHeadingStylesConfig`, `resolveTocConfig`, `resolvePartsConfig`, `resolveUnorderedListsConfig`, `resolveOrderedListsConfig`, `resolveMathConfig`, `resolveTableStyleConfig`, `resolveCaptionStyleConfig`, `resolveDiagramStyleConfig`, `resolveParagraphStylesConfig`, `resolveCalloutStylesConfig`, `resolveHeaderFooterConfig`, `resolveDebugConfig`, `resolveHtmlViewerConfig`, `resolvePdfGenerationConfig`, además de `resolveDesignSlot` para una sola zona de diseño. Las paletas de colores se aplican por separado con `applyPaletteToConfig(config)`, `applyPaletteToResolvedConfig(resolved, palette)` y `resolveColorValue(value, palette, fallback)`; consulta [Paleta de colores](/es/docs/configuration-fonts-colors-viewers#paleta-de-colores).

Las funciones cuyos valores por defecto se heredan de otra sección reciben esa sección, ya resuelta, como argumento adicional. `resolveUnorderedListsConfig` y `resolveOrderedListsConfig` reciben el texto base resuelto, porque las listas heredan de él los valores por defecto de `fontFamily` y `color`; `resolveCalloutStylesConfig` recibe el texto base, los encabezados y las listas no ordenadas ya resueltos (véase el ejemplo en [Estilos de recuadro](/es/docs/configuration-callouts#estilos-de-recuadro)), y `resolveHeadingStylesConfig`, la página, el texto base y las dos secciones de listas resueltas. Consulta las declaraciones de tipos del paquete para ver la firma exacta de cada una:

```ts
import { resolveBodyTextConfig, resolveUnorderedListsConfig } from 'postext';

const body = resolveBodyTextConfig({ fontFamily: 'Inter' });
const lists = resolveUnorderedListsConfig({ bulletChar: '—' }, body);
// => lists.fontFamily === 'Inter' (heredado)
```

También se exportan los conjuntos de valores por defecto estáticos, los que se usan cuando no hay herencia: `DEFAULT_PAGE_CONFIG`, `DEFAULT_CUT_LINES`, `DEFAULT_PAGE_NUMBERING`, `PAGE_SIZE_PRESETS`, `DEFAULT_LAYOUT_CONFIG`, `DEFAULT_COLUMN_RULE`, `DEFAULT_COLUMN_BALANCING`, `DEFAULT_BODY_TEXT_CONFIG`, `DEFAULT_HYPHENATION_CONFIG`, `DEFAULT_HEADINGS_CONFIG`, `DEFAULT_UNORDERED_LISTS_STATIC`, `DEFAULT_ORDERED_LISTS_STATIC`, `DEFAULT_PARAGRAPH_STYLES`, `DEFAULT_CALLOUT_STYLES`, `DEFAULT_CALLOUT_STYLE_STATIC`, `DEFAULT_PARTS_CONFIG`, `DEFAULT_HEADING_STYLES`, `DEFAULT_TOC_CONFIG`, `DEFAULT_MATH_CONFIG`, `DEFAULT_DIAGRAM_STYLE_CONFIG`, `DEFAULT_DEBUG_CONFIG`, `DEFAULT_HTML_VIEWER_CONFIG`, `DEFAULT_PDF_GENERATION_CONFIG`, `DEFAULT_COLOR_PALETTE`, `DEFAULT_MAIN_COLOR`, `DEFAULT_MAIN_COLOR_ID`, `DEFAULT_MAIN_COLOR_NAME`, `DEFAULT_MAIN_COLOR_HEX`, además de los valores por defecto de los elementos de cabecera y pie (`DEFAULT_HEADER_FOOTER_SLOT`, `DEFAULT_HEADER_SLOT`, `DEFAULT_FOOTER_SLOT`, `DEFAULT_TEXT_ELEMENT`, `DEFAULT_RULE_ELEMENT`, `DEFAULT_BOX_ELEMENT`) y de `defaultResourceTypes(locale)`, que depende del idioma (véase [Tipos de recurso](/es/docs/configuration-resources#tipos-de-recurso)).

### Eliminar valores por defecto

Cuando guardes la configuración (por ejemplo, en localStorage o en un archivo), usa `stripConfigDefaults` para eliminar los valores que coinciden con los predeterminados. Así, las configuraciones guardadas son mínimas: solo contienen los cambios hechos a propósito.

```ts
import { stripConfigDefaults } from 'postext';

const minimal = stripConfigDefaults(fullConfig);
// Solo permanecen las propiedades que difieren de los valores por defecto
```

También hay funciones de limpieza individuales, una por cada función de resolución: `stripPageDefaults`, `stripLayoutDefaults`, `stripBodyTextDefaults`, `stripHeadingsDefaults`, `stripHeadingStylesDefaults`, `stripTocDefaults`, `stripPartsDefaults`, `stripUnorderedListsDefaults`, `stripOrderedListsDefaults`, `stripMathDefaults`, `stripTableStyleDefaults`, `stripCaptionStyleDefaults`, `stripDiagramStyleDefaults`, `stripParagraphStylesDefaults`, `stripCalloutStylesDefaults`, `stripHeaderFooterDefaults`, `stripDesignSlotDefaults`, `stripDebugDefaults`, `stripHtmlViewerDefaults`, `stripPdfGenerationDefaults`.

Algunos valores por defecto dependen del resto de la configuración: el equilibrado de columnas está desactivado en una retícula de caracteres y en el texto vertical; `bodyText.avoidWidows` está desactivado en una retícula de caracteres (y `bodyText.avoidOrphans` también, en la región `japan`), y las notas al pie, los pies de los recursos y el índice analítico dependen del idioma del documento. `stripConfigDefaults` compara cada valor con el valor por defecto de la configuración que recibe, de modo que `headings.balancing.enabled: true` se conserva donde el equilibrado está desactivado por defecto, y `false` se elimina en ese caso. Del mismo modo, `bodyText.avoidWidows: true` se conserva en una retícula de caracteres. Una función de limpieza llamada por separado recibe ese contexto como argumentos: `stripHeadingsDefaults(headings, balancingOnByDefault(config))`, `stripIndexDefaults(index, locale)`, `stripCaptionStyleDefaults(captionStyle, locale)`, `stripFootnotesDefaults(footnotes, locale, writingMode)`, `stripBodyTextDefaults(bodyText, locale, avoidWidowsByDefault(config), avoidOrphansByDefault(config))`.

Un valor que significa «nada» se conserva siempre que «nada» no sea el valor por defecto. Un estilo de encabezado toma la cabecera y el pie del documento si no fija los suyos, así que un estilo que los vacía (`footer: { elements: [] }` en una cubierta) conserva la zona vacía, y sus `margins`, `layout` y `bodyStyle` se conservan aunque estén vacíos. Un nivel de encabezado que se ha devuelto a su valor por defecto, cuando los valores generales de los encabezados son otros, conserva ese valor. `calloutStyles: []` y `chipStyles: []` siguen siendo listas vacías: si se omitieran, volvería el estilo integrado. En todos los casos, `resolveAllConfig(stripConfigDefaults(config))` se resuelve igual que `resolveAllConfig(config)`.

### Analizar el Markdown

El motor pone a tu disposición su tokenizador de Markdown y su lector de frontmatter. Úsalos para examinar un documento antes de maquetarlo, o para dar a otras herramientas la misma estructura de bloques que ve Postext:

```ts
import { parseMarkdown, extractFrontmatter } from 'postext';

const source = '---\ntitle: Capítulo uno\n---\n\n# Apertura\n\nLa historia empieza aquí.';

const { metadata, content } = extractFrontmatter(source);
// metadata.title === 'Capítulo uno'

const blocks = parseMarkdown(content);
// => [ { type: 'heading', level: 1, text: 'Apertura', … },
//      { type: 'paragraph', text: 'La historia empieza aquí.', … } ]
```

Consulta la página [Formato del documento](/es/docs/document-format) para ver la lista completa de construcciones de Markdown que reconoce Postext.

### Mapa de origen de un documento compuesto

`sourceAt(doc, pageIndex, x, y, options?)` devuelve lo que muestra un punto de una página, empezando por el elemento más interior, cada uno con su `id` estable, su `source` (un rango del Markdown, un puntero JSON de la configuración, un atributo del bloque de página o un recurso) y su `rect`. `elementsForSource(doc, start, end, options?)` devuelve en qué se ha convertido un rango del Markdown, página a página, y `findElement(doc, id)` vuelve a encontrar un elemento después de una nueva maquetación. Estas funciones leen lo que la maquetación dejó registrado en el VDT y no maquetan nada. `composedPagePaintKey(page)` indica si una página compuesta pinta lo mismo que antes. Los tipos de origen, los ids y cómo se vuelve a maquetar una página compuesta solo donde ha cambiado se explican en [Páginas compuestas › Mapa de origen](/es/docs/composed-pages#mapa-de-origen).

### Cargar las fuentes antes de componer

La maquetación mide el texto con los estilos de fuente que tiene el conjunto de fuentes en el momento en que se ejecuta. `prepareFonts` carga antes de la primera compilación todos los estilos que piden una configuración y su texto: el texto base, los encabezados, las listas, los títulos y el contenido de los recuadros, las tablas, los textos de diseño, los titulillos, el índice, el código y la rotulación de los cómics, en cada peso e inclinación que fija la configuración (los cuatro de la familia del texto base, porque `**` y `*` componen en ella la negrita y la cursiva). Cada estilo se carga para los caracteres que compone el documento, de modo que una familia servida en tramos de `unicode-range` (latín extendido, griego, árabe, los tramos CJK de Google Fonts y de Fontsource) trae los archivos que necesita el texto.

```ts
import { prepareFonts, buildDocument, buildDocumentWithFonts } from 'postext';

// Los archivos del anfitrión: el contrato del proveedor de fuentes del PDF, así que una misma función sirve a los dos.
async function resolve(family: string, weight: number, style: 'normal' | 'italic') {
  const id = family.toLowerCase().replace(/\s+/g, '-');
  return `https://cdn.jsdelivr.net/npm/@fontsource/${id}@5/files/${id}-latin-${weight}-${style}.woff2`;
}

const report = await prepareFonts(content, config, { resolve });
// report.loaded, report.missing, report.synthesized: { family, weight, style }[]
const doc = buildDocument(content, config);

// O en una sola llamada: preparar, componer, cargar las caras que usaron las páginas y no estaban, y volver a componer.
const same = await buildDocumentWithFonts(content, config, { resolve });
```

- **Los estilos que declara la página** (una regla `@font-face`, un `FontFace` ya añadido) se cargan a través del conjunto de fuentes (`document.fonts.load`, o `self.fonts` en un worker). **Los que no declara** se piden a `resolve(family, weight, style, { text, codePoints })`, que responde con un archivo (bytes o una URL), con varios archivos (los tramos de un estilo), con `{ source, unicodeRange, weight, style }` para un tramo o un intervalo variable, o con `null`. El motor los añade como `FontFace` cuando han terminado de cargarse todos, en el orden de la configuración y de cada respuesta (latin, luego latin-ext y luego greek, si la función de resolución responde así), de modo que el conjunto de fuentes queda igual sea cual sea el orden en que lleguen los archivos. También los registra en el registro de fuentes que leen las [imágenes SVG](/es/docs/configuration-resources#fuentes-en-el-texto-de-los-svg) y los workers de composición. Una función de resolución puede declarar el estilo por su cuenta (añadiendo una hoja de estilos) y responder `null`.
- **El informe** enumera en `loaded` los estilos que cubre un estilo cargado (o una familia instalada), en `missing` los que siguen faltando y en `synthesized` los que el navegador sintetizaría a partir de otro peso o de otra inclinación; `added` cuenta los `FontFace` añadidos a partir de los archivos de la función de resolución. `timeoutMs` (10 000 por defecto) limita la espera; un estilo que para entonces siga cargándose cuenta como faltante. Donde no hay conjunto de fuentes (Node), `prepareFonts` no hace nada y da todos los estilos por cargados.
- **`buildDocumentWithFonts(content, config, options)`** prepara las fuentes, compila con `buildDocumentAsync`, lee los estilos en los que las páginas han compuesto realmente texto, carga los que el conjunto de fuentes no podía proporcionar (un peso que solo revelan las páginas se pide a `resolve` aunque otro peso de la familia pudiera sustituirlo) y vuelve a compilar (como mucho, dos compilaciones más). `withLoadedFonts(build, options)` hace lo mismo alrededor de cualquier función de compilación, para un libro que se compila capítulo a capítulo o para un paquete (`buildBundle`) que devuelve varios documentos. `options.onFonts` recibe el informe final.
- **Después de la compilación**, todos los estilos con los que se ha compuesto el texto y que el conjunto de fuentes no ha podido proporcionar aparecen en `doc.contentWarnings` como `fontFallback` (véase [Avisos del documento](#avisos-del-documento)).

**Estilos de cifras.** Un estilo con [`figureStyle`](/es/docs/configuration-fonts-colors-viewers#estilos-de-cifras) compone su texto en una familia con funciones: el nombre de la familia base seguido de sus funciones OpenType tras `@` (`EB Garamond@onum`). A `prepareFonts` y a `resolve` se les pide la familia base, y el motor declara los estilos de la familia con funciones a partir de los mismos archivos, con el descriptor `featureSettings`. El `FontPayload` de un worker de maquetación admite un `featureSettings` opcional para esa fuente, con `family` igual a la familia con funciones y el búfer del archivo de la familia base. `configFeatureFamilies(config)` enumera las familias con funciones en las que una configuración compone texto. Un anfitrión que compone texto en fuentes de las que no tiene archivos nombra con `setFigureStyleFamilies((family) => boolean)` las familias que pueden tomar funciones; las demás conservan sus propias cifras. `baseFontFamily` y `featureFamilyParts` descomponen ese nombre, `withFigureStyle(fontFamily, figureStyle)` lo construye y `freezeFontFeatures(bytes, features)` devuelve una copia de un archivo TrueType u OpenType cuyo `cmap` lleva los caracteres a los glifos que dan las sustituciones simples de las funciones, para un canvas que no aplica funciones (Skia en Node).

Los estilos que llegan más tarde se tienen en cuenta automáticamente. Para cada conjunto de fuentes, el motor anota qué estilos de cada familia estaban cargados la última vez que lo comprobó; cada compilación lo vuelve a comprobar al empezar (solo si el conjunto ha crecido o menguado, si está cargando o si ha terminado de cargar un estilo) y descarta lo medido en las familias cuyos estilos han cambiado. `watchFonts(fontSet)` hace lo mismo a medida que se cargan los estilos, como mucho una vez por fotograma de animación, por muchos tramos que lleguen de golpe, y `onFontsChanged(listener)` comunica a la aplicación qué familias han cambiado, para que vuelva a maquetar las páginas:

```ts
import { watchFonts, onFontsChanged } from 'postext';

const stop = watchFonts();                         // document.fonts por defecto
const off = onFontsChanged((families) => relayout());
```

`prepareFonts` empieza a vigilar el conjunto en el que carga las fuentes (`watch: false` lo desactiva).

### Caché de medidas

La medición del texto es la parte más costosa de la maquetación. Dos tipos de caché la abaratan:

- **Una caché de bloques propia.** `createMeasurementCache()` devuelve una `MeasurementCache` que recuerda cada párrafo medido, con una clave formada por su texto, sus fuentes, su ancho, sus opciones de corte de líneas y el diccionario de separación silábica activo. Pásala como tercer argumento de `buildDocument` (o de `buildDocumentAsync`) para reutilizar las mediciones entre las pasadas de colocación de una compilación y entre compilaciones: así, un editor que vuelve a maquetar el documento en cada pulsación solo mide los párrafos que han cambiado. Sin ella, cada pasada vuelve a medir todos los bloques. Un párrafo leído de la caché es idéntico a uno medido de nuevo, así que una compilación con caché corta todas las líneas igual que una sin caché; en postext 1.4.1, un párrafo guardado en caché perdía la marca de que su última línea era demasiado corta, y el estrechamiento de las líneas cortas y el equilibrado de columnas podían cortarlo de otra manera. La caché lleva la generación de medición con la que se llenó: cuando llegan o desaparecen estilos de una familia, su siguiente consulta descarta los bloques compuestos con esa familia, así que una caché que se conserva mientras cargan las fuentes nunca devuelve líneas medidas con la fuente de reserva.
- **Cachés globales de anchos.** Los anchos de las palabras se guardan, por cadena de fuente, en un estado de módulo que comparten todas las compilaciones de la página, y pretext tiene su propia caché. El motor descarta los anchos de una familia cuando cambian sus estilos (al empezar una compilación, desde `watchFonts`, desde `prepareFonts` y desde `loadBundleFonts`); la caché de pretext no tiene índice por familia y se vacía entera.

```ts
import { buildDocument, createMeasurementCache, evictFontFamilies, clearMeasurementCache } from 'postext';

const cache = createMeasurementCache();
let doc = buildDocument(content, config, cache);

// Se añadió a document.fonts una cara de "EB Garamond": el siguiente build la ve,
// con la misma caché, y vuelve a medir esa familia.
doc = buildDocument(content, config, cache);

// Un anfitrión que cambia caras que el motor no puede ver (un conjunto de fuentes propio) lo avisa:
evictFontFamilies(['EB Garamond']);   // los anchos y los bloques en caché de esa familia
clearMeasurementCache();              // todas las familias
```

Para las aplicaciones que miden el texto fragmento a fragmento, `cachedMeasureBlock(text, font, maxWidthPx, lineHeightPx, options, cache)` y `cachedMeasureRichBlock(spans, normalFont, boldFont, italicFont, boldItalicFont, maxWidthPx, lineHeightPx, options, cache)` reciben los argumentos de `measureBlock` y de `measureRichBlock` y, al final, la caché.

### El corte de líneas (WebAssembly)

Los párrafos se cortan en líneas con Knuth–Plass. Desde postext 1.33, el motor lo ejecuta con un algoritmo de corte escrito en Rust y compilado a WebAssembly (30 KB, incluido en el paquete). Elige los mismos cortes que la versión en TypeScript, con la misma aritmética y en el mismo orden, y un libro entero se maqueta alrededor de un 15 % más rápido. No hay que configurar nada:

- En un worker, en Node y en Bun, el módulo se compila en el primer párrafo.
- En el hilo principal de una página, donde el navegador solo compila un módulo de este tamaño de forma asíncrona, se compila en segundo plano, y mientras tanto responde la versión en TypeScript. `await initLineBreaker()` antes de la primera maquetación hace que actúe desde el primer párrafo; devuelve `false` donde no hay WebAssembly.
- Donde no hay WebAssembly, o una política de seguridad de contenidos lo rechaza (`script-src` sin `'wasm-unsafe-eval'`), la versión en TypeScript responde en todos los párrafos.

Las dos versiones eligen los mismos cortes, así que la que responda nunca cambia la maquetación. `useWasmLineBreaker(false)` obliga a usar la versión en TypeScript, para comparar las dos.

```ts
import { initLineBreaker, buildDocument } from 'postext';

await initLineBreaker(); // opcional: la primera maquetación ya lo usa
const doc = buildDocument({ markdown }, config);
```


### Estado global compartido en una página

Parte del estado de Postext está en variables de módulo. Todo lo que importa `postext` en el mismo contexto de JavaScript (*realm*) lo comparte: una página y sus scripts comparten una copia, mientras que cada iframe y cada worker tienen la suya. Con un solo documento por página no se nota. Con varios documentos en la misma página (dos vistas previas en directo, una galería de ejemplos), sí:

- **Imágenes de los recursos.** `registerResourceImage(fileId, image)` llena un único registro indexado por `fileId`, que leen `renderPage` y `renderPageToCanvas`. Dos documentos que registran `figure.svg` comparten esa entrada: gana el último registro, para los dos. Pon a los ids de archivo un prefijo distinto en cada documento, y llama a `unregisterResourceImage(fileId)` o a `clearResourceImages()` cuando un documento desaparezca. Las imágenes rasterizadas que guarda en caché el backend de canvas usan la misma clave y se descartan junto con la imagen.
- **Mediciones del texto.** Los anchos medidos se guardan en caché por cadena de fuente y texto en todo el contexto. Cuando llegan o desaparecen estilos de una familia, el motor descarta los anchos de esa familia para todos los documentos (véase [Cargar las fuentes antes de componer](#cargar-las-fuentes-antes-de-componer)); `clearMeasurementCache()` los descarta todos.
- **Configuraciones resueltas.** Cada objeto de configuración se resuelve una vez, y el resultado se guarda en caché asociado a ese objeto. Cada compilación compara primero el objeto con el texto que tenía cuando se resolvió (un `JSON.stringify`, unos 0,1 ms para una configuración de libro de 55 KB y 1,5 ms para una de 240 KB), así que una configuración modificada directamente, a cualquier profundidad (`config.bodyText.fontSize = …`, un color de la paleta), se vuelve a resolver. `invalidateConfig(config)` descarta la resolución manualmente. `stableStringify` y `hashString` dan una clave de contenido que no depende del orden de las claves, para las aplicaciones que guardan en caché las maquetaciones según su configuración.
- **Idioma de la separación silábica.** Cada compilación fija el idioma de separación silábica de todo el proceso en el `bodyText.hyphenation.locale` de su documento. Las funciones exportadas `hyphenateText(text)` y `layoutDesignSlot` usan el idioma de la última compilación, salvo que les pases uno: llama a `hyphenateText(text, 'es')`.
- **Motor de fórmulas.** Hay un único motor MathJax y una única caché de fórmulas renderizadas por contexto; `initMathEngine()` lo arranca para todos.
- **Algoritmo de corte de líneas.** Hay una única versión WebAssembly del algoritmo de corte de líneas por contexto, que se compila una sola vez; `useWasmLineBreaker(false)` la desactiva para todos.

La forma más sencilla de aislarlos es usar un contexto por documento: un iframe por cada ejemplo en directo (una inserción de CodePen lo es), o un [worker de composición](#ejecutar-la-composición-en-un-web-worker) por documento para las mediciones y la separación silábica (las imágenes se siguen registrando en la página).

### Documentos de Word (`postext/word`)

El punto de entrada `postext/word` lee y escribe documentos de Word (`.docx`) sin DOM. Sobre él se construyen la importación y la exportación de Word del Sandbox y los comandos `import-docx` y `docx` de la línea de comandos (véase [Línea de comandos › docx e import-docx](/es/docs/command-line#docx-e-import-docx)).

```ts
import { readDocx, parseTemplate, emptyTemplate, analyzeDocx, wordToPostext, postextToDocx } from 'postext/word';

const word = readDocx(bytes);                                    // un Uint8Array o un ArrayBuffer
const template = parseTemplate(word.embeddedTemplate) ?? emptyTemplate();
const report = analyzeDocx(word, template, config);              // report.verdict, report.findings
const { chapters, pictures, tables } = wordToPostext(word, {
  template, config, chapters: 'split', existingIds: new Set(), untitledChapter: 'Untitled',
});

const docx = postextToDocx(chapters, { template, config, book: chapters.length > 1, title: 'Field notes' });
```

- **`readDocx(bytes)`** lee el archivo y obtiene un modelo de Word: sus estilos, párrafos, notas e imágenes, el `title` del documento y la plantilla de importación que lleva una exportación de Postext (`embeddedTemplate`). Un archivo que no es un documento de Word lanza un `DocxReadError`.
- **`wordToPostext(word, settings)`** convierte el modelo en capítulos (`{ title, markdown }`), imágenes y tablas. La plantilla asigna cada estilo de Word a un encabezado, un estilo de párrafo, un recuadro, una cita o un pie de la configuración. `chapters: 'split'` abre un capítulo en cada encabezado de nivel 1, y `'single'` deja uno solo. Las imágenes (`id`, `media.bytes`, `caption`, `alt`) y las tablas (`id`, `model`, `caption`) las guarda la aplicación como recursos; `skippedPictures` enumera las imágenes EMF, WMF y TIFF que se han dejado fuera.
- **`analyzeDocx(word, template, config)`** es el informe de calidad que muestra el Sandbox antes de importar: los estilos en uso, cuántos párrafos tienen estilo y hallazgos como `directFormatting`, `manualHeadings` y `typedNumbering`, cada uno con un recuento y ejemplos.
- **`postextToDocx(chapters, settings)`** escribe los capítulos como un `.docx` (un `Uint8Array`) con estilos de Word para los encabezados, los párrafos, los recuadros, las citas, las listas y las notas. Lo que Word no puede expresar se conserva tal cual en los estilos *Postext Markup*, y la plantilla viaja dentro del archivo, así que el documento se vuelve a importar sin cambios. `book: true` abre cada capítulo con un párrafo `Postext Chapter`, a partir del cual la importación reconstruye los capítulos.
- **`wordStyleTracking(word, template, config)`** y **`applyStyleTracking(config, tracking)`** trasladan el espaciado entre caracteres de los estilos de Word a los estilos de la configuración que no tienen ninguno.


## Ejecutar la composición en un Web Worker

**Esta es la forma recomendada de usar Postext en el navegador.** Si vas a crear algo interactivo (una vista previa en directo, un editor, un visor que se adapta al tamaño de la ventana o un banco de pruebas al estilo del Sandbox), ejecuta el proceso de composición mediante `createLayoutWorker()`, de `postext/worker`. En el código de la interfaz, no llames a `buildDocument` directamente en el hilo principal.

Si llamas a `buildDocument` en el hilo principal, todo el proceso de composición (el análisis, la medición, la colocación y todas las repeticiones de la pasada de colocación que necesite la maquetación) se ejecuta en el hilo desde el que se invoca. Para una exportación puntual, no pasa nada. Para una interfaz interactiva, es el hilo equivocado: una maquetación de 150 ms bloquea los eventos de entrada, las pulsaciones de teclado se acumulan y el desplazamiento va a trompicones. El worker traslada cada uno de esos milisegundos a un hilo en segundo plano.

Postext incluye un punto de entrada específico para Web Worker, `postext/worker`, que saca el proceso de composición del hilo principal. Es la vía que esperamos que siga la mayoría de las integraciones: las vistas Canvas, HTML y PDF del Sandbox comparten el mismo objeto de `createLayoutWorker()` mediante un único hook, `useLayoutWorker` (`packages/postext-sandbox/src/worker/useLayoutWorker.ts`), y lo controlan con cancelación «gana la última»: una nueva pulsación de tecla interrumpe la compilación en curso antes incluso de que termine.

En resumen, la integración de referencia consiste en:

1. **Crear** un worker una vez por vista con `createLayoutWorker()`.
2. **Registrar las fuentes** una vez por familia, enviando `ArrayBuffer` transferibles mediante `registerFonts(payloads)`.
3. **Compilar** con `build(content, config, { signal })`, pasando un `AbortSignal` nuevo en cada llamada para poder cancelar las compilaciones obsoletas.
4. **Sustituir** cualquier compilación anterior abortando su señal *antes* de empezar la siguiente: es el patrón «gana la última».
5. **Liberar** el worker (`dispose`) cuando se desmonte el componente que lo tiene.

El mismo `VDTDocument` que devuelve `build(...)` sirve para todos los renderizadores posteriores: `renderPage` / `renderPageToCanvas` para el canvas, `renderToHtmlIndexed` para HTML y `renderToPdf` (de `postext-pdf`) para PDF. Compilas una vez en el worker y rasterizas en el hilo principal tantas veces como necesite la interfaz.

### Qué te aporta el worker

- **El hilo principal queda libre.** El análisis, la medición y todas las pasadas de colocación se ejecutan dentro del worker. El hilo principal solo interviene cuando recibe de vuelta el `VDTDocument` terminado.
- **Cancelación «gana la última».** `build(content, config, { signal })` pasa un `AbortSignal` al worker. Si se aborta antes de que termine, se produce un `AbortError` en el lado principal; dentro del worker, el proceso de composición lanza un `BuildCancelledError` en el siguiente punto de comprobación, que hay en cada bloque, y se detiene de inmediato.
- **Una caché de medición por worker.** El worker mantiene una única `MeasurementCache` durante toda su vida. Las compilaciones siguientes que comparten fuente, texto y ancho reutilizan las mediciones de líneas guardadas en caché: al escribir un solo carácter en un documento largo, solo se vuelven a medir los bloques cuya entrada ha cambiado de verdad.
- **Las mismas métricas que en el hilo principal.** Las fuentes se envían al worker como `ArrayBuffer` transferibles y se registran con `new FontFace(...)` en el propio `FontFaceSet` del worker. El worker mide con las mismas métricas de fuente del canvas que usaría el hilo principal, así que los cortes de línea y las alturas de las columnas son idénticos byte a byte.
- **La caché de imágenes rasterizadas de las fórmulas sobrevive a las compilaciones del worker.** El renderizador de fórmulas incluye una caché de imágenes rasterizadas con clave por contenido, además de la que usa como clave la identidad del objeto: sin ella, al copiar un `MathRender` (con clonación estructurada) a través de la frontera del worker, la caché por identidad fallaría en cada recompilación.
- **Las mismas líneas que en la página.** Un canvas creado en un worker no tiene ninguna página de la que tomar un idioma, y una fuente puede dar glifos distintos según el idioma. El motor fija el idioma del documento (`locale`) en todos los contextos con los que mide, tanto en el worker como en la página, así que `build()` devuelve las mismas líneas que da `buildDocument` en una página, en cualquier idioma ([`bodyText.shapingLanguage: 'document'`](/es/docs/configuration-text#texto-base), el valor por defecto desde postext 1.30). Con `'host'`, que conservan las configuraciones guardadas antes de la 1.30, un worker mide sin idioma y una página, con el suyo, como hasta postext 1.28.

### API pública

El cliente del worker está en el punto de entrada `postext/worker` y consta de unos pocos nombres:

- **`createLayoutWorker(opts?): LayoutWorkerHandle`**: crea un worker dedicado (o envuelve uno que le pases mediante `opts.worker`, o arranca la entrada del worker que está en `opts.url`) y devuelve un objeto tipado para controlarlo. Consulta [Cargar el worker desde una CDN](#cargar-el-worker-desde-una-cdn).
- **`LayoutWorkerHandle.registerFonts(faces: FontPayload[]): Promise<void>`**: envía al worker los bytes de las fuentes. Los búferes se transfieren, así que conserva una copia nueva en el hilo principal si tienes que volver a enviarlos más tarde.
- **`LayoutWorkerHandle.unregisterFonts(families: string[]): Promise<void>`**: descarta los estilos del worker de esas familias, para que el siguiente `registerFonts` de una familia surta efecto en lugar de compararse con el estilo que ya tiene.
- **`LayoutWorkerHandle.build(content, config?, options?): Promise<VDTDocument>`**: ejecuta el proceso de composición. `options` es `{ signal?, onProgress?, onStats?, resourcesKey?, cacheKey? }`. Abortar `signal` cancela la compilación en curso. A `onProgress({ pass, blocks, totalBlocks, pages })` se le llama a medida que avanza la colocación; `onStats({ passes, totalMs, cached?, missingFonts? })` recibe los tiempos de las pasadas de la compilación terminada. `resourcesKey` es una huella de `content.resources`: las compilaciones seguidas con la misma clave envían la lista una sola vez, y el worker la conserva. `cacheKey` es una huella de toda la compilación: el worker guarda con ella sus últimos documentos y responde desde esa caché a una compilación cuya clave tiene.
- **`LayoutWorkerHandle.warm(content, config, { cacheKey, … }): Promise<void>`**: compila en la caché de documentos del worker sin devolver el documento, para un capítulo que el lector puede abrir a continuación; el siguiente `build` con ese `cacheKey` se responde desde la caché.
- **`LayoutWorkerHandle.prepareFonts(content, config?, options?)`**: `prepareFonts` en la página y, después, el envío al worker de los estilos que ha encontrado; consulta [Cargar el worker desde una CDN](#cargar-el-worker-desde-una-cdn).
- **`LayoutWorkerHandle.dispose(): void`**: termina el worker y rechaza con `AbortError` todas las compilaciones pendientes.
- **`FontPayload`**: `{ family, weight, style, unicodeRange?, buffer: ArrayBuffer }`. `weight` es un peso CSS en forma de cadena (`'700'`, `'bold'`); `registerFonts` también lo acepta como número (`700`). El `buffer` se transfiere al worker cuando llamas a `registerFonts`.
- **`BuildCancelledError`** (reexportado desde `postext`): lo que lanza `buildDocument` internamente cuando `options.shouldCancel` devuelve `true`. Normalmente no lo verás en el hilo principal: el protocolo del worker lo convierte en un `AbortError` antes de que llegue a tu código.

El paquete también publica la ruta `postext/worker/entry`, que apunta al script compilado del worker. `createLayoutWorker()` resuelve esa URL automáticamente; solo tienes que hacer referencia a ella explícitamente cuando tu empaquetador exige escribir a mano una llamada `new Worker(new URL(...), { type: 'module' })`, o cuando sirves tú mismo la entrada (`opts.url`).

### Integración mínima

```ts
import { createLayoutWorker } from 'postext/worker';
import type { FontPayload, LayoutWorkerHandle } from 'postext/worker';
import type { PostextConfig, VDTDocument } from 'postext';

// 1. Crea el worker una única vez y conserva el handle durante toda la vida de tu viewport.
const layout: LayoutWorkerHandle = createLayoutWorker();

// 2. Registra las fuentes una vez por familia (ArrayBuffers transferibles).
//    getConfigFontFamilies(config) es un helper que lista las familias que tu config va a renderizar.
const payloads: FontPayload[] = await collectFontPayloadsForFamilies([
  'EB Garamond',
  'Open Sans',
]);
await layout.registerFonts(payloads);

// 3. Dirige los builds con cancelación last-wins: aborta el signal anterior
//    antes de iniciar uno nuevo. Un build obsoleto se descarta dentro del worker.
let pending: AbortController | null = null;

async function rebuild(
  markdown: string,
  config: PostextConfig,
): Promise<VDTDocument | null> {
  pending?.abort();
  pending = new AbortController();
  try {
    return await layout.build({ markdown }, config, { signal: pending.signal });
  } catch (err) {
    if ((err as { name?: string } | null)?.name === 'AbortError') return null;
    throw err;
  }
}

// 4. Libera (dispose) cuando el componente propietario del worker se desmonta.
//    Los builds pendientes rechazan con AbortError.
layout.dispose();
```

Dentro de un componente React, queda así:

```tsx
import { useEffect, useRef } from 'react';
import { createLayoutWorker } from 'postext/worker';
import type { LayoutWorkerHandle } from 'postext/worker';
import { renderPageToCanvas } from 'postext';
import type { PostextConfig } from 'postext';

export function CanvasPreview({
  markdown,
  config,
}: {
  markdown: string;
  config: PostextConfig;
}) {
  const canvasRef = useRef<HTMLCanvasElement | null>(null);
  const workerRef = useRef<LayoutWorkerHandle | null>(null);
  const pendingRef = useRef<AbortController | null>(null);

  // Montaje: arranca el worker y envía las fuentes una sola vez.
  useEffect(() => {
    const handle = createLayoutWorker();
    workerRef.current = handle;
    (async () => {
      const payloads = await collectFontPayloadsForFamilies(
        getConfigFontFamilies(config),
      );
      await handle.registerFonts(payloads);
    })();
    return () => {
      pendingRef.current?.abort();
      handle.dispose();
    };
  }, []); // las fuentes se registran una vez; re-regístralas solo cuando cambie el conjunto de familias

  // En cada tecla o cambio de config: supersede el build en curso y lanza uno nuevo.
  useEffect(() => {
    const handle = workerRef.current;
    if (!handle) return;
    pendingRef.current?.abort();
    const ac = new AbortController();
    pendingRef.current = ac;
    (async () => {
      try {
        const vdt = await handle.build({ markdown }, config, { signal: ac.signal });
        const canvas = canvasRef.current;
        if (!canvas || !vdt.pages[0]) return;
        renderPageToCanvas(vdt.pages[0], vdt, canvas); // rasteriza en el hilo principal
      } catch (err) {
        if ((err as { name?: string } | null)?.name !== 'AbortError') throw err;
      }
    })();
  }, [markdown, config]);

  return <canvas ref={canvasRef} />;
}
```

El patrón siempre es el mismo: **crear una vez, registrar las fuentes una vez, compilar muchas veces con un AbortSignal y liberar al desmontar.**

### Cargar el worker desde una CDN

El script de un worker tiene que proceder del mismo origen que la página, así que una copia de `postext/worker` servida desde una CDN no puede arrancar el archivo `layout.worker.js` que tiene al lado. `createLayoutWorker()` lo resuelve así:

- **esm.sh, sin opciones.** Cuando el propio `postext/worker` se ha cargado desde esm.sh (la URL de su módulo tiene la forma `https://esm.sh/postext@1.5.0/es2022/worker.mjs`), el cliente arranca la entrada correspondiente, `https://esm.sh/postext@1.5.0/worker/entry`, mediante un módulo blob de una sola línea y del mismo origen que la importa. Lo mismo ocurre con las importaciones que añaden `?deps=`, `?external=` o `?alias=`, y con la forma `https://esm.sh/*postext@1.5.0/worker`. El worker siempre recibe la compilación normal de esa versión, porque un worker no tiene un *import map* con el que resolver dependencias externas.
- **Cualquier otro servidor, con `url`.** Las demás CDN, como jsDelivr (`/+esm`) o unpkg, no se detectan. `createLayoutWorker({ url })` arranca el módulo de entrada del worker que está en `url`: directamente, si es del mismo origen, o mediante el mismo envoltorio blob, si es de otro. Ese servidor debe permitir las peticiones desde otros orígenes (CORS).
- **Con un empaquetador, no cambia nada.** Con Vite, webpack o Next.js, sigue llamando a `createLayoutWorker()` sin opciones: el empaquetador genera el worker como un fragmento más de tu aplicación.

```js
import { createLayoutWorker } from 'https://esm.sh/postext/worker';

const layout = createLayoutWorker();
const face = async (weight, style) => ({
  family: 'EB Garamond',
  weight,
  style,
  buffer: await (await fetch(`https://cdn.jsdelivr.net/npm/@fontsource/eb-garamond@5/files/eb-garamond-latin-${weight}-${style}.woff2`)).arrayBuffer(),
});
await layout.registerFonts(await Promise.all([face(400, 'normal'), face(700, 'normal'), face(400, 'italic')]));
const doc = await layout.build({ markdown }, { bodyText: { fontFamily: 'EB Garamond' } });
```

**Un worker no ve las fuentes de la página.** Tiene su propio conjunto de fuentes, que solo contiene los estilos enviados con `registerFonts` y las fuentes instaladas en el sistema. Cuando una compilación compone texto con una familia que el worker no encuentra, ese texto se mide con una fuente de reserva, así que sus cortes de línea no coincidirán con los de la página. En ese caso, el cliente muestra un aviso en la consola por cada familia (`"EB Garamond" is not available inside the layout worker…`) y enumera las familias en `BuildStats.missingFonts`, que recibe la función `onStats` de `build`. El propio documento incluye esos mismos estilos como avisos de contenido `fontFallback`.

`handle.prepareFonts(content, config, options)` ejecuta [`prepareFonts`](#cargar-las-fuentes-antes-de-componer) en la página y después envía al worker los archivos de cada estilo encontrado que esté en el registro de fuentes (los archivos de la función de resolución, los estilos de un paquete, las reglas `@font-face` de la página que se pueden leer), limitados a los tramos que contienen caracteres del documento. Cuando llegan estilos al worker, este descarta solo las mediciones de esas familias, además de su caché de documentos terminados.

Los estilos también pueden llegar al worker después de una compilación: un peso que resulta que las páginas necesitan, otro tramo `unicode-range` de un estilo, un archivo que se ha vuelto a subir con el mismo nombre de familia. La compilación siguiente mide con ellos. El canvas de un worker no lo haría por sí solo: en Chrome, resuelve una fuente la primera vez que se le asigna una forma abreviada de `font` y no vuelve a consultar el conjunto de fuentes para esa misma forma abreviada, así que el texto conservaría los anchos del estilo que respondió primero. Por eso, cuando un estilo de una familia ha llegado tarde, el worker escribe esa familia dos veces en las formas abreviadas que asigna (`Geist, Geist`): para el canvas es una lista de familias nueva, pero da la misma fuente y los mismos anchos. Los documentos que devuelve conservan las cadenas de fuente tal como las escribe el motor, y un worker que recibe sus estilos antes de su primera compilación asigna todas las formas abreviadas tal cual.

### Obtener los bytes de las fuentes (Fontsource / Google Fonts)

`registerFonts` recibe los bytes de las fuentes tal cual. El hilo principal es el sitio adecuado para obtenerlos, porque con una caché central varias instancias del worker pueden compartir los mismos bytes.

`collectFontPayloadsForFamilies`, del Sandbox (`packages/postext-sandbox/src/controls/fontLoader.ts`), es una implementación de referencia. Esto es lo que hace:

1. Consulta `https://api.fontsource.org/v1/fonts/{id-de-familia}` para saber qué pesos y estilos tiene la familia.
2. Lee los subconjuntos de la familia y su `unicode-range` en su paquete de jsDelivr (`@fontsource/{id-de-familia}@5/400.css`), una vez por familia. Los archivos se piden después a la versión exacta desde la que se sirvió esa hoja de estilos (`x-jsd-version` de jsDelivr), de modo que una familia nunca llega de dos versiones de su paquete.
3. Descarga todos los archivos de la redonda, la negrita, la cursiva y la cursiva negrita de cada familia (`files/{id-de-familia}-{subconjunto}-{peso}-{estilo}.woff2`); `collectFontPayloadsForConfig(config, markdown)` toma en su lugar los pesos y estilos que pide una configuración. Son archivos estáticos, los mismos que incrusta el PDF, así que el worker mide con lo que dibuja el PDF. Un archivo variable da otros avances entre dos de sus maestros, y una línea que se pasa de su medida por una fracción de píxel se corta en otro sitio.
4. Devuelve un `FontPayload[]` en el que `buffer` es un `ArrayBuffer` nuevo en cada llamada; esto es importante, porque `registerFonts` transfiere el búfer y deja inutilizada la copia del remitente.

Los archivos de un estilo van en el orden en que los declara un pen del Recetario (un ejemplo de CodePen): primero `latin` y al final los propios de la escritura (`arabic`, los tramos numerados de una familia china o japonesa), porque, cuando dos archivos contienen el mismo carácter, responde el que se ha añadido en último lugar. Una familia de la que Fontsource no tiene archivos se lee de la hoja de estilos CSS2 de Google, que solo devuelve WOFF2 a los User-Agent que parecen de un navegador.

Combínalo con `getConfigFontFamilies(config)` para obtener la lista de familias que va a usar realmente una `PostextConfig` concreta (texto base, encabezados, viñetas de las listas, números de las listas ordenadas).

### Cancelación cooperativa dentro del motor

Si llamas tú mismo a `buildDocument` (por ejemplo, dentro de un worker propio), el proceso de composición ofrece un hook, `shouldCancel`, que puedes usar directamente:

```ts
import { buildDocument, BuildCancelledError } from 'postext';

let superseded = false;
try {
  const vdt = buildDocument(content, config, cache, {
    shouldCancel: () => superseded,
  });
} catch (err) {
  if (err instanceof BuildCancelledError) return; // un build más nuevo tomó el relevo
  throw err;
}
```

`shouldCancel` se llama una vez por cada bloque de primer nivel durante la colocación. Este hook es cooperativo a propósito: no puede detener la llamada de maquetación del propio Pretext a mitad de una línea, pero mantiene una granularidad de cancelación lo bastante fina (milisegundos) como para que alguien que escribe deprisa nunca tenga que esperar a una compilación obsoleta.

### Exportar PDF desde el worker

El backend de PDF recibe un `VDTDocument` ya terminado y lo convierte en bytes de PDF. **No** vuelve a maquetar. Por eso, el flujo habitual para generar el PDF en el navegador encaja perfectamente con el worker: compila el VDT en el worker (fuera del hilo principal, con cancelación y reutilizando la caché) y después llama a `renderToPdf` en el hilo principal con ese mismo VDT.

```ts
import type { LayoutWorkerHandle } from 'postext/worker';
import { renderToPdf } from 'postext-pdf';
import type { PostextConfig } from 'postext';
import { createPdfFontProvider } from './pdfFontProvider';

const fontProvider = createPdfFontProvider();

export async function exportPdf(
  layout: LayoutWorkerHandle,
  markdown: string,
  config: PostextConfig,
): Promise<Uint8Array> {
  // 1. Construye el VDT en el worker — la UI se mantiene fluida durante las pasadas de composición.
  const vdt = await layout.build({ markdown }, config);

  // 2. Rasteriza a PDF en el hilo principal. renderToPdf es rápido una vez que existe el VDT
  //    porque recorre coordenadas precalculadas, no vuelve a medir texto.
  return renderToPdf(vdt, {
    fontProvider,
    // La config `pdfGeneration` de `vdt.config` se respeta automáticamente.
  });
}
```

Si ya tienes un worker para la vista previa en directo, reutilízalo para la exportación en lugar de crear otro: gracias a la caché de medición del worker, una exportación a PDF que sigue a una vista previa en pantalla prácticamente no cuesta nada.

En un libro largo, escribir el propio PDF también lleva unos segundos; `postext-pdf/worker` ejecuta ese paso en un worker propio (véase [Renderizar el PDF en un worker](/es/docs/configuration-pdf-output#renderizar-el-pdf-en-un-worker)).

### Cuándo usar el worker y cuándo no

Usa el worker para:

- **Vistas previas en directo, editores y bancos de pruebas.** Cualquier caso en el que el documento se vuelve a compilar en respuesta a lo que hace el usuario.
- **Visores HTML que se adaptan al tamaño de la ventana** y vuelven a maquetar con cada aviso de `ResizeObserver`.
- **Exportación a PDF desde el navegador** lanzada desde una interfaz que ya tiene una vista previa en directo: reutiliza el worker existente para aprovechar su caché de medición.
- **Varias pestañas de salida** que necesitan el mismo VDT (las vistas Canvas, HTML y PDF del Sandbox comparten un worker por cada vista montada).

No uses el worker para:

- **La generación en el servidor**: Node no tiene el `FontFaceSet` del navegador, y de todos modos tú controlas el hilo.
- **Exportaciones puntuales aisladas** (una herramienta de línea de comandos, un script de exportación sin interfaz, una Cloud Function), en las que no hay ninguna interfaz interactiva que bloquear. Llamar directamente a `buildDocument` es más sencillo y evita el coste de la transferencia inicial de las fuentes.
