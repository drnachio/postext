# Configuração: fontes, cores e saída


## Unidades e cores

### Dimensões

Todas as medidas físicas no Postext usam o tipo `Dimension`, um valor acompanhado de uma unidade:

```ts
interface Dimension {
  value: number;
  unit: DimensionUnit; // 'cm' | 'mm' | 'in' | 'pt' | 'px' | 'em' | 'rem'
}
```

**Unidades absolutas** (`cm`, `mm`, `in`, `pt`, `px`) são convertidas em pixels com o DPI configurado. A 300 DPI, `1 cm` equivale a cerca de 118 px.

**Unidades relativas** (`em`, `rem`) acompanham o tamanho de fonte atual. Um `em` é relativo ao tamanho de fonte do próprio elemento; `rem` é relativo ao tamanho de fonte do texto do corpo.

### Cores

As cores são guardadas com uma representação hexadecimal e um modelo de cor de destino:

```ts
interface ColorValue {
  hex: string;         // '#ff0000', 'transparent' etc.
  model: ColorModel;   // 'hex' | 'rgb' | 'cmyk' | 'hsl'
  cmyk?: CmykPercent;  // Os valores exatos de quadricromia de uma cor definida em CMYK.
  paletteId?: string;  // A entrada de colorPalette que ela segue.
}
```

O campo `model` indica o espaço de cor pretendido. Para renderização na web, o normal é `'hex'` ou `'rgb'`. Em fluxos de impressão, `'cmyk'` diz que a cor foi especificada em CMYK, e `cmyk` guarda os valores dela: uma renderização de impressão em CMYK os aplica como estão, e `hex` é a forma como aparecem na tela (veja [Cores definidas em CMYK](#cores-definidas-em-cmyk)).

Como o Postext mira uma saída de qualidade editorial, a cor padrão do texto do corpo vem com `model: 'cmyk'` (`#000000`). As cores de títulos, negrito, itálico e listas usam por padrão a **Cor principal** vinculada à paleta (`#295AA3`, `model: 'hex'`). O fundo da página e as sobreposições da interface (grade de linhas de base, marcas de corte, indicadores de depuração) usam por padrão `model: 'hex'`. Substitua `color.model` em qualquer campo se precisar de outra semântica de exportação.

### Transparência

Uma cor pode ser translúcida. `hex` aceita um canal alfa, como `#rgba` ou `#rrggbbaa`. Também aceita uma cor `rgb()` / `rgba()`, na sintaxe com vírgulas ou com espaços, com o alfa como número ou porcentagem. `transparent` é totalmente transparente:

```ts
const config: PostextConfig = {
  header: {
    elements: [{
      kind: 'box',
      id: 'veil',
      placement: {
        anchor: { to: 'bleed', edge: 'top-left' },
        size: { width: 'fill', height: { value: 40, unit: 'mm' } },
      },
      style: { backgroundColor: { hex: '#ffffffb3', model: 'hex' } }, // branco a 70 %
    }],
  },
  bodyText: { color: { hex: 'rgba(0, 0, 0, 0.85)', model: 'rgb' } },
};
```

Os três renderizadores a pintam do mesmo jeito. O canvas e o visualizador HTML tomam o valor como uma cor CSS. O renderizador de PDF aplica a opacidade da cor como um alfa constante, um `ExtGState` com `ca` para preenchimentos e `CA` para traços. Isso vale para texto, fios, boxes, preenchimentos e bordas de tabela, chips, amostras de cor e fórmulas. Uma cor translúcida se compõe sobre tudo o que foi pintado antes dela. Um boxe no cabeçalho ou no rodapé é pintado por último, por isso vela o texto que está embaixo; um boxe numa faixa de abertura é pintado primeiro, por isso tinge a página sob o texto. Quando o PDF é forçado para outro espaço de cor (`pdfGeneration.forceColorSpace` com `colorSpace: 'cmyk'` ou `'grayscale'`), a cor é convertida e seu alfa se mantém. No Sandbox, o controle deslizante de opacidade do seletor de cor grava esses valores como `#rrggbbaa`, e o seletor também lê as outras formas.


## Fontes personalizadas

O Postext resolve cada string de `fontFamily` **tanto** no catálogo do Google Fonts **quanto** na lista `customFonts` do documento. As fontes personalizadas têm prioridade quando os nomes coincidem: se você declarar `customFonts: [{ name: 'Roboto', … }]`, o Postext usa o arquivo que você enviou em vez da “Roboto” do Google Fonts. O Sandbox busca na Fontsource as famílias que o Google Fonts não tem. Ele nunca consulta a Fontsource por um nome genérico (`serif`, `system-ui`) nem por uma fonte que vem com um sistema operacional (Arial, Segoe UI, PingFang SC…): essa família é composta com o que houver no computador do leitor, o painel **Fontes** a mostra como *Não encontrada* e o PDF e as imagens SVG não têm nenhum arquivo dela para incorporar. Se o livro for composto nela, envie-a como fonte personalizada.

Use fontes personalizadas quando:

- O documento precisa de uma família tipográfica da marca ou licenciada que não está no Google Fonts.
- O ambiente não alcança as CDNs de fontes, o jsDelivr (de onde o Sandbox tira os arquivos da Fontsource) ou o Google Fonts (offline, intranet, contextos sensíveis à privacidade).
- Você precisa manter o binário da fonte privado e não enviá-lo a terceiros.

### Esquema de configuração

```ts
type CustomFontFormat = 'woff2' | 'woff' | 'ttf' | 'otf';
type CustomFontStyle = 'normal' | 'italic';

interface CustomFontVariant {
  weight: number;           // font-weight do CSS, 100..900
  style: CustomFontStyle;
  fileId: string;           // id opaco do binário num armazenamento à parte
  format: CustomFontFormat;
  fileName?: string;        // nome original do arquivo enviado (opcional, mostrado na interface)
}

interface CustomFontFamily {
  name: string;             // usado em qualquer lugar onde caiba um nome de família do Google Fonts
  variants: CustomFontVariant[];
  redistributable?: boolean; // false: usada aqui, nunca copiada para fora do livro
  fallback?: string;        // família aberta de largura parecida para as faces sem arquivo (desde o postext 1.42)
}

interface PostextConfig {
  // ...
  customFonts?: CustomFontFamily[];
}
```

O binário de cada variante **não** fica incorporado à própria configuração. A configuração guarda apenas ponteiros `fileId`; os bytes ficam num armazenamento à parte. No Sandbox, isso significa IndexedDB (armazenamento chave-valor, só no navegador, privado do documento). Quem integra o Postext em outro ambiente pode resolver `fileId` como quiser (um endpoint no servidor, o cache de um service worker, qualquer coisa), desde que os bytes cheguem à thread principal antes de `buildDocument` rodar.

### Como gerenciar fontes personalizadas no Sandbox

Abra o painel **Fontes** na barra de atividades à esquerda (entre Recursos e Design). A lista **Famílias tipográficas deste livro** mostra cada família que o design usa, com sua função e de onde vem: do Google Fonts, da Fontsource (quando o Google Fonts não tem a família), de um arquivo seu, ou de lugar nenhum (*Não encontrada*). Em **Seus arquivos de fonte**, para cada família:

1. **Adicionar família**: cria uma família vazia; renomeie-a ali mesmo.
2. **Enviar variante(s)**: escolha um peso (100–900) e um estilo (normal / itálico) e selecione um *ou vários* arquivos `.woff2`, `.woff`, `.ttf` ou `.otf`. Cada arquivo vira uma variante própria, associada ao par (peso, estilo) selecionado no momento; o nome do arquivo enviado fica registrado e aparece na linha, para você distinguir as variantes. Você pode reajustar o peso ou o estilo de uma variante nos menus suspensos a qualquer momento.
3. **Variantes duplicadas são permitidas.** Se dois arquivos caírem no mesmo par (peso, estilo), os dois são mantidos e aparece um aviso **Variante de fonte duplicada**, para você saber que deve diferenciar os ajustes das variantes extras.
4. **Excluir variante** ou **Excluir família**: remove a entrada da configuração *e* os bytes guardados no IndexedDB.

Depois que uma família é declarada, todo seletor de fonte a agrupa em **Personalizado**, acima da lista do Google Fonts. Selecioná-la liga a família a cada campo de família tipográfica em que você a aplicar.

### Uma família substituta para uma família licenciada

Um livro pode ser composto numa tipografia que o titular dos direitos não permite repassar. Marque a família com `redistributable: false` e um arquivo `.postext` deixa os arquivos dela de fora. Se você indicar em `fallback` uma família aberta de largura parecida, o arquivo que abre sem eles quebra as linhas perto de onde a tipografia real as quebra, em vez de fazer o texto transbordar dos blocos com uma fonte de reserva mais larga. As faces de que a família não tem arquivo são compostas nos cortes do `fallback` de mesmo peso e mesma inclinação, com o nome da licenciada, nas visualizações, no worker de diagramação, no PDF e na linha de comando. Uma família com arquivos fica com eles; do `fallback` ela só toma a inclinação de que não tem nenhum arquivo, um itálico por exemplo, e os pesos intermediários entre os arquivos dela são escolhidos como em qualquer família. No painel Fontes, **Família substituta** (dentro da família, acima dos arquivos) recebe o nome; vazio, a família fica como estava. O PDF de um livro composto assim incorpora a face aberta, de modo que o PDF final é feito com os arquivos licenciados. Desde o postext 1.42. Desde o postext 1.43 a família aberta também vai onde a licenciada não pode: um EPUB ou uma exportação HTML, a partir do Sandbox ou do `postext`, leva as faces da substituta com o nome da família licenciada, assim como as imagens SVG cujo texto está nessa família, de modo que o sistema de leitura compõe o livro numa face da largura para a qual as linhas foram quebradas. Os arquivos próprios da família nunca saem do livro. Uma família sem `fallback`, ou cuja substituta não tem arquivo, é citada sem arquivos, como antes; a aba EPUB do Sandbox lista as famílias compostas numa substituta.

### Comportamento na renderização

Por baixo dos panos:

- Quando `customFonts` muda, cada família declarada é registrada automaticamente como entradas `FontFace` em `document.fonts`. Assim, o visualizador HTML, a área de visualização do canvas (que mede por meio de `document.fonts`) e qualquer referência CSS direta passam a usar a fonte personalizada sem que o usuário precise abrir antes o seletor de fontes.
- O worker de layout recebe os mesmos ArrayBuffers pelo caminho já existente de transferência de fontes, de modo que a medição (`buildFontString`, pretext) funciona como com uma família do catálogo.
- Alterar ou remover uma variante descarta a fonte que o worker tinha em cache para essa família e a registra de novo na diagramação seguinte, para que as visualizações acompanhem o conjunto atual de variantes.
- **Exportação para PDF**: os binários enviados passam pelo mesmo pipeline de `PdfFontProvider`. Arquivos `.woff2` são descompactados; `.ttf` e `.otf` passam direto. `.woff` é recusado com um erro claro (o pdf-lib não consegue incorporar WOFF puro; envie de novo como `.woff2`/`.ttf`/`.otf`). OpenType com contornos CFF (`.otf` com o número mágico `OTTO`) é incorporado **sem subconjunto**, porque o gerador de subconjuntos CFF do pdf-lib percorre cada glifo no momento do `save()` e pode travar por minutos com fontes reais; abrir mão do subconjunto troca um PDF um pouco maior por tempos de renderização estáveis.

### Avisos de fontes ausentes

O painel **Verificações** do Sandbox lista, no grupo *Fontes*, três falhas específicas das fontes personalizadas (todas ativadas pela mesma opção `debug.warnings.missingFont` que já controla o aviso genérico de fonte “não carregada”):

- **Família de fontes desconhecida**: um `fontFamily` cita um nome que nem o Google Fonts nem a Fontsource têm e que não é uma família personalizada declarada no momento. O aviso também aparece de imediato quando você exclui uma família personalizada que algum campo `fontFamily` ainda cita, em vez de esperar que o DOM perceba.
- **Variante de fonte ausente**: a família existe, mas o livro pede a ela um peso e um estilo sem arquivo enviado: títulos em negrito, por exemplo, numa família que só tem a regular. O aviso lista as combinações que faltam. Uma inclinação que o `fallback` da família fornece não conta como falta.
- **Variante de fonte duplicada**: dois ou mais arquivos enviados ocupam o mesmo par (peso, estilo) dentro de uma família. Só um arquivo é usado de fato na renderização; o aviso sugere que você reajuste as demais entradas.

Clicar em qualquer um desses avisos abre o painel Fontes, para você enviar a variante que falta, adicionar a família de novo ou diferenciar as duplicadas.

Quando já existe uma diagramação, o painel também lista o aviso do motor **Fonte substituta na diagramação** (`fontFallback`): uma face sem a qual as páginas foram medidas, seja porque falta, seja porque o navegador a desenha a partir de outro peso ou de outra inclinação. Uma família que já aparece como desconhecida ou com variante ausente não é listada duas vezes. Antes da primeira diagramação, uma verificação contra `document.fonts` ocupa o lugar desse aviso.

O painel também lista **Caracteres tirados de outra fonte** (`glyphFallback`): caracteres que o texto põe numa fonte que não tem glifo para eles, uma vez por fonte, com a família genérica que os desenhou (`serif`, `sans-serif`, `monospace`) quando a verificação consegue saber.

## Estilos de algarismos

`figureStyle` pede à fonte de um estilo de texto um tipo de algarismos, por meio dos recursos OpenType da fonte: algarismos de estilo antigo no texto corrido, algarismos alinhados tabulares nas tabelas. O campo existe em `bodyText`, `paragraphStyles[]`, `headings` e `headings.levels[]`, `headingStyles[]`, `tableStyle` e `tableStyles[]` (células de cabeçalho e de corpo do mesmo jeito), `captionStyle` (rótulo e descrição, e o `captionStyle` de um tipo de recurso) e nos elementos de texto de um design (cabeços, fólios, os textos de uma página de abertura ou de uma página de parte). No Sandbox é o campo **Algarismos** do painel Design, ao lado do tipo de cada um desses estilos (**Texto do corpo → Tipo** para o corpo do texto).

Um par define uma forma e uma largura. Uma fonte sem o recurso mantém os próprios algarismos, então confira se a fonte tem `onum` ou `lnum` antes de contar com eles. Uma família da qual o host não tem arquivo, como uma fonte instalada só no sistema do leitor (o Sandbox não as baixa), não recebe nenhum estilo de algarismos: o texto mantém os algarismos dessa fonte, na própria fonte. Um livro que envia arquivos com esse nome recebe os algarismos. Os cortes que o Google Fonts e o Fontsource servem costumam deixar `onum` e `lnum` de fora (o arquivo latin da Source Serif 4 só mantém `pnum` e `tnum`); com um arquivo assim, um estilo que os pede mantém os algarismos da própria fonte. Os arquivos completos da fundição têm esses recursos: envie-os para ter algarismos de estilo antigo ou alinhados. Uma família genérica (`serif`, `sans-serif`) não recebe recursos. Um valor fora da lista é informado como valor de configuração desconhecido (`unknownConfigValue`, veja [Avisos de configuração](#avisos-de-configuração)) e lido como não definido.

```ts
const config: PostextConfig = {
  bodyText: { fontFamily: 'EB Garamond', figureStyle: 'oldstyle' },
  tableStyle: { figureStyle: 'lining-tabular' },
  paragraphStyles: [{ id: 'timetable', figureStyle: 'lining-tabular' }],
  headings: { figureStyle: 'lining' },
};
```

O texto compõe anos e números de página em algarismos de estilo antigo, e o mesmo fazem as legendas e as listas, que recebem a família do corpo do texto. As células de todas as tabelas e os parágrafos do estilo `timetable` alinham os dígitos em algarismos alinhados tabulares. Todos os níveis de título compõem algarismos alinhados na família dos títulos.

### Que algarismos cada estilo recebe

- Um estilo que recebe a família de outro recebe também os algarismos dele. Os estilos de parágrafo, as tabelas, as legendas, as listas e o conteúdo dos boxes recebem a família do corpo do texto quando não nomeiam outra, então `bodyText.figureStyle` chega a todos eles.
- Um estilo que nomeia a própria `fontFamily` compõe os algarismos padrão dessa fonte, a menos que também defina `figureStyle`.
- Um nível de título sem `figureStyle` próprio recebe `headings.figureStyle`, também na própria `fontFamily` quando nomeia uma. O `figureStyle` de um estilo de título vale para a família do nível em que o estilo é usado.
- Um elemento de texto de um design nomeia a própria família (`'EB Garamond'` por padrão), então os algarismos do corpo do texto não chegam a um fólio: defina nele `figureStyle: 'oldstyle'` para combinar com um texto em algarismos de estilo antigo.
- `'default'` compõe os algarismos da própria fonte e anula os herdados: `paragraphStyles: [{ id: 'plain', figureStyle: 'default' }]` tira desse estilo os algarismos de estilo antigo do corpo do texto.

### Os algarismos em cada saída

O texto é medido com os recursos, então as linhas quebram nas mesmas larguras na visualização do Canvas, no HTML, no PDF e no EPUB, em layout fixo e refluível.

- **Visualização do Canvas e worker de layout**: o navegador declara de novo os arquivos da família base com um nome de família com recursos e o descritor `featureSettings` de `FontFace`. O nome é a família seguida dos recursos depois de `@` (`EB Garamond@onum`, `EB Garamond@lnum+tnum`) e aparece nas strings de fonte e em alguns avisos.
- **HTML e EPUB** (layout fixo e refluível): a família base, com `font-variant-numeric` (`oldstyle-nums`, `lining-nums tabular-nums`).
- **PDF**: incorpora os arquivos da família base e compõe o texto com os recursos.
- **Linha de comando**: o Skia, o canvas com que o `postext` desenha, não aplica recursos. A linha de comando registra uma cópia da fonte cujo `cmap` leva cada caractere que os recursos substituem, os dígitos, ao glifo que eles escolhem. Só as substituições simples são consideradas; uma fonte que chega aos algarismos por substituições contextuais mantém ali os próprios algarismos.

## Paleta de cores

A propriedade `colorPalette` de `PostextConfig` permite definir um conjunto reutilizável de cores com nome e referenciá-las a partir de qualquer `ColorValue` da configuração. É o equivalente, no Postext, às propriedades personalizadas do CSS ou ao painel de amostras do InDesign: você muda a entrada da paleta uma vez, e todas as cores que apontam para ela se atualizam no documento inteiro.

```ts
interface ColorPaletteEntry {
  id: string;       // identificador estável, referenciado por ColorValue.paletteId
  name: string;     // rótulo legível mostrado nas interfaces do Sandbox
  value: ColorValue;
}
```

### A paleta padrão

O Postext vem com uma paleta padrão de uma única entrada, chamada **Cor principal** (`id: 'main-color'`, hex `#295AA3`). Vários valores padrão (a cor dos títulos, a cor de negrito/itálico do corpo, a cor de `:ref`, as cores dos marcadores e dos números de lista) referenciam essa entrada por meio de `paletteId: 'main-color'`, de modo que mudar essa única amostra retinge todas as partes do documento que a usam.

Você pode inspecionar a paleta padrão, cloná-la ou comparar com ela por meio de três exportações:

```ts
import {
  DEFAULT_COLOR_PALETTE,
  cloneDefaultColorPalette,
  isDefaultColorPalette,
} from 'postext';

// Instantâneo somente leitura da paleta que vem com o pacote.
DEFAULT_COLOR_PALETTE;
// => [{ id: 'main-color', name: 'Main Color', value: { hex: '#295AA3', model: 'hex' } }]

// Cópia independente: altere esta, não DEFAULT_COLOR_PALETTE.
const palette = cloneDefaultColorPalette();

// Detecta se o usuário personalizou a paleta de alguma forma.
isDefaultColorPalette(palette); // true
```

A paleta fica no nível superior da configuração:

```ts
const config: PostextConfig = {
  colorPalette: [
    { id: 'ink',    name: 'Ink',    value: { hex: '#0a0a0a', model: 'cmyk' } },
    { id: 'accent', name: 'Accent', value: { hex: '#b8860b', model: 'hex' } },
  ],
  bodyText: { color: { hex: '#000000', model: 'cmyk', paletteId: 'ink' } },
  headings: { color: { hex: '#000000', model: 'hex', paletteId: 'accent' } },
};
```

### Como referenciar uma entrada da paleta

Qualquer `ColorValue` da configuração pode levar um campo opcional `paletteId` que aponta para uma entrada de `colorPalette`: fundo da página, cores do texto do corpo (incluída a cor de `:ref`), cores dos títulos, fios entre colunas, cores de listas, cores de tabelas, legendas, chips e boxes (caixa, faixa, ícone, marcador, rótulo, título, corpo), cores das marcas de corte e da grade de linhas de base, indicadores de depuração e todas as cores de um design: os cabeços, as aberturas de título e os designs na coluna, os designs e cabeços dos estilos de título, as páginas de parte e as linhas de parte do sumário (texto, fio, preenchimento e borda da caixa, contorno, capitular). Quando presente, o `hex` / `model` da entrada da paleta prevalece sobre o `hex` / `model` de reserva guardado ao lado. O valor de reserva embutido só é usado se a paleta não existir, estiver vazia ou não contiver aquele id, o que é útil ao distribuir uma configuração que será lida por uma ferramenta que não entende paletas.

**Mudou no postext 1.5.** Até o postext 1.4, a paleta chegava só a uma lista fixa de ajustes: as cores dos designs (cabeços, aberturas, estilos de título, partes, linhas do sumário), `bodyText.referenceColor`, as cores dos rótulos dos boxes e as cores de negrito / itálico do corpo dos boxes mantinham o `hex` guardado ao lado do `paletteId`. Um documento cujo valor guardado difere da entrada da paleta (todos os editados no Sandbox depois que a entrada mudou, e cada `:ref` quando a Cor principal não é `#295AA3`) agora imprime a cor da paleta, como o vínculo indica. Para manter uma cor como estava, remova o `paletteId` dela.

### Como as paletas são aplicadas

`buildDocument` aplica a paleta em dois momentos, para que as cores referenciadas funcionem tanto nos valores que você escreveu quanto nos valores padrão preenchidos depois:

1. `applyPaletteToConfig(config)`: resolve cada `ColorValue` da configuração bruta do usuário que traga um `paletteId`. Útil quando você quer inspecionar o que o motor vai de fato receber.
2. `applyPaletteToResolvedConfig(resolved, palette)`: roda *depois* que os valores padrão são resolvidos e reescreve os padrões vinculados à paleta (cor dos títulos, cor de negrito/itálico do corpo, cor de `:ref`, cores de listas, as cores dos designs padrão) para que acompanhem a paleta ativa.

As duas percorrem a configuração inteira, de modo que nenhuma cor vinculada à paleta fica para trás. A maioria das cores do fluxo de texto (texto do corpo, títulos, listas, tabelas, legendas, chips, a caixa, o título e o corpo do boxe) sai como valores simples. Todas as outras (as cores dos designs, a cor de `:ref`, os rótulos dos boxes) recebem o `hex` / `model` da paleta e **mantêm o `paletteId`**. É esse vínculo que o atributo `palette` de uma parte e o `palette` próprio de um estilo de título substituem nas suas páginas (veja [Partes](/pt/docs/configuration-styles#partes)), por isso ele precisa sobreviver. `htmlViewer.overrides` fica como foi escrito: o visualizador HTML o mescla primeiro, e uma paleta que ele traga se aplica então a tudo, incluídos os designs.

Raramente você vai precisar chamá-las diretamente, mas as duas são exportadas para que você possa inspecioná-las ou reutilizá-las:

```ts
import {
  applyPaletteToConfig,
  applyPaletteToResolvedConfig,
  resolveColorValue,
} from 'postext';

const flat = applyPaletteToConfig(config);
// Cada ColorValue com paletteId na configuração bruta agora leva o
// hex/model da entrada da paleta (uma cor de design mantém seu paletteId).

// `applyPaletteToResolvedConfig` normalmente fica a cargo de buildDocument; use-a
// diretamente se você montar um ResolvedConfig por conta própria e quiser a paleta aplicada.
```

`resolveColorValue(value, palette, fallback)` é a variante para um único valor, prática quando você compõe configurações de forma imperativa e precisa resolver uma cor por vez.

### Como editar a paleta

Uma cor cujo `paletteId` não indica nenhuma entrada imprime o `hex` / `model` guardado, que pode ser mais antigo que a cor que a entrada lhe dava. Por isso, antes de remover uma entrada, reescreva cada `ColorValue` vinculado a ela como uma cor simples com o valor atual da entrada. A seção *Paleta* do Sandbox (**Design → Cores**) faz isso quando você exclui uma entrada, esteja a cor onde estiver (incluídos os designs e os rótulos dos boxes), e a confirmação lista cada ajuste que usa a entrada: pelo nome, ou pelo caminho na configuração (`header.elements[2].color`).

## Visualizador Canvas

## Geração de PDF (configuração)

A propriedade `pdfGeneration` controla como o renderizador de PDF gera o documento final. Esses ajustes são lidos pelo pacote `postext-pdf` no momento da exportação; os visualizadores de canvas e HTML os ignoram.

`buildDocument` os leva na VDT, como `doc.config.pdfGeneration`, e `renderToPdf` toma cada ajuste do primeiro lugar que o fornece:

1. as opções passadas a ele (`outlines`, `accessible`, `colorSpace`);
2. o `pdfGeneration` do primeiro documento que renderiza (num livro, os ajustes do primeiro capítulo valem para o arquivo inteiro);
3. os valores padrão: marcadores e marcação de estrutura ligados, cor RGB.

Assim, `renderToPdf(doc, { fontProvider })` segue a configuração, e uma opção passada a `renderToPdf` prevalece apenas para aquele ajuste. `forceColorSpace` e `colorSpace` juntos equivalem à opção `colorSpace`: o `colorSpace` da configuração vale enquanto `forceColorSpace` estiver ligado, e o PDF é RGB enquanto estiver desligado. Versões anteriores do `postext-pdf` liam só as opções; uma configuração que define `pdfGeneration` agora muda o PDF de quem chama sem passar opções.

```ts
type PdfColorSpace = 'rgb' | 'cmyk' | 'grayscale';

interface PdfGenerationConfig {
  outlines?: boolean;          // Gera marcadores de PDF a partir da árvore de títulos.
  forceColorSpace?: boolean;   // Converte todas as cores para `colorSpace`.
  colorSpace?: PdfColorSpace;  // Espaço de destino usado quando `forceColorSpace` é true.
  accessible?: boolean;        // Saída marcada, orientada a PDF/UA (árvore de estrutura, texto alternativo, idioma).
}
```

## Produção gráfica (configuração)

A propriedade `print` diz como um livro vai para a gráfica: o padrão PDF/X do arquivo, o perfil de saída com que o CMYK dele é separado, como o preto é impresso e os limites do preflight. A diagramação a ignora; por isso, mudá-la nunca move uma linha. Três coisas a leem: o `postext-pdf` quando grava o arquivo, `preflightDocument` quando verifica um documento diagramado, e a simulação de impressão dos visualizadores canvas e Folio.

  renderingIntent?: 'relative' | 'perceptual';
  blackPointCompensation?: boolean;
  convertImages?: boolean;                 // Separa as imagens RGB (o PDF/X-1a sempre separa).
  inkLimit?: number;                       // Cobertura total de tinta, em porcentagem.
  black?: PrintBlackConfig;
  preflight?: PrintPreflightConfig;

  name: string;           // A descrição do perfil, ou o nome do arquivo.

  inkLimit?: number;
}

### PDF/X-1a e PDF/X-4

Os dois padrões gravam:

- a condição de saída (`GTS_PDFX`), que indica a condição de impressão e incorpora o perfil de destino;
- a identificação no dicionário Info (`GTS_PDFXVersion`, `/Trapped /False`, o título e as datas) e nos metadados XMP (`pdfxid:GTSPDFXVersion`, os ids do documento e da versão), junto com a identificação PDF/UA quando o arquivo é marcado;
- uma TrimBox e uma BleedBox em cada página (a página inteira quando não há marcas de corte);
- o `/ID` do trailer;
- cada cor em DeviceCMYK (ou cinza) passada pelo perfil, e as marcas de corte em cor de registro;
- nenhuma anotação de link: um arquivo para a gráfica não traz nenhuma dentro da caixa de sangria; por isso, os links do PDF de tela ficam de fora (os marcadores ficam).

O PDF/X-1a:2003 é PDF 1.4 sem fluxos de objetos e não tem transparências: uma cor translúcida é aplicada como sairia impressa sobre o papel, o alfa de uma imagem é achatado sobre branco, e a página em negativo de depuração fica de fora (com um aviso `pageNegativeIgnored`). O PDF/X-4 é PDF 1.6: as transparências ficam, cada página recebe um grupo de transparência que mescla em CMYK, e as imagens RGB mantidas por `convertImages: false` são marcadas como sRGB pelo `/DefaultRGB`.

Uma matriz de impressão em PDF (`svg.pdfFileId`) é incorporada como está; por isso, as cores, as fontes e as transparências dela são as do próprio arquivo; o preflight informa o que ela traz.

`preflightDocument(doc, options)` executa as verificações num documento diagramado e devolve uma lista de problemas, cada um com um `kind`, uma `severity` (`'critical'`, `'warning'` ou `'info'`), o `pageIndex` absoluto no livro, o `rect` do elemento em questão (px da página) e, quando o elemento tem, o intervalo de origem dele. Os tipos são `lowImageResolution`, `declaredPixelsMismatch`, `rgbImage`, `thinRule`, `smallProcessText`, `inkLimit`, `safeZone` e `nearTrim`. Sem um `transform`, uma cor neutra conta como uma tinta e qualquer outra como três, e a cobertura não é verificada; com um, as contagens e a cobertura são exatas. A resolução de uma imagem é calculada a partir dos pixels que o recurso dela declara, ou dos do próprio arquivo quando `imageSize(fileId)` os fornece (`bitmapInfo` sobre os bytes, ou a imagem decodificada): uma declaração que se afasta do arquivo em mais de um pixel é informada uma vez como `declaredPixelsMismatch`, um aviso quando declara mais pixels do que o arquivo tem. `placedImageResolutions(doc, { resources, imageSize })` lista cada bitmap colocado com o ppi efetivo, com o preflight ligado ou não. Os rótulos de uma figura contam como texto para `smallProcessText`, `inkLimit` e `safeZone`.

```ts
import { bitmapInfo, outputTransform, parseIccProfile, preflightDocument, resolvePrintConfig } from 'postext';
import { inspectPrintMaster } from 'postext-pdf';

const print = resolvePrintConfig(config.print);
const transform = outputTransform(parseIccProfile(fogra51Bytes), { intent: print.renderingIntent });
const issues = preflightDocument(doc, {
  print,
  transform,
  resources,                                    // tamanhos em pixels dos bitmaps
  imageSize: (fileId) => bitmapInfo(bytesOf(fileId)),  // os pixels reais dos arquivos
  imageColor: (fileId) => colourOf(fileId),     // 'rgb' | 'cmyk' | 'gray', tirado do arquivo
});
if (issues.some((i) => i.severity === 'critical')) process.exit(1);

const master = await inspectPrintMaster(masterBytes);
// => { nonEmbeddedFonts: ['Helvetica'], rgb: true, transparency: false }
```

### Simulação de impressão

Uma página do canvas pode ser pintada como vai sair impressa. `createPrintPreview(transform, print, { paper, dpi, grayscale })` monta a prova de cor em tela de uma configuração: cada pixel é separado com o perfil (cinzas só em K, como no PDF) e mostrado de volta na tela, sobre o branco do próprio papel quando `paper` é true; as áreas pretas grandes o bastante para o preto composto aparecem em preto composto. Com `grayscale`, a prova é a de uma impressão em escala de cinza: um PDF forçado a escala de cinza imprime a luminância de cada cor só em tinta preta, sem preto composto. Passe-a a `renderPageToCanvas` como `printPreview`. Para uma visão de trabalho, não para uma prova, `guides` acrescenta as linhas do refile, da sangria e da área de segurança, e `marksFor` contorna áreas de uma página (os `rect`s do preflight); o Sandbox deixa os dois de fora; por isso, a simulação dele mostra só o que é impresso. O `postext-folio` recebe o mesmo objeto como `printPreview`; com `paper: true`, dê ao livro um tom de papel neutro enquanto isso (`folio.paper.shade`), ou o papel é tingido duas vezes.

```ts
import { createPrintPreview, renderPageToCanvas } from 'postext';

const preview = createPrintPreview(transform, print, { paper: true, dpi: doc.config.page.dpi });
renderPageToCanvas(page, doc, canvas, {
  printPreview: { ...preview, guides: { safeZonePx: 59 }, marksFor: () => issues.map((i) => i.rect!).filter(Boolean) },
});
```

### Motor de cor

O gerenciamento de cor que o postext usa é exportado para suas próprias ferramentas. Ele lê perfis ICC v2 e v4 (matriz/TRC e as tabelas de consulta `mft1`, `mft2`, `mAB`, `mBA`) em TypeScript puro, sem WebAssembly.

- `parseIccProfile(bytes)` lê um perfil; `deviceChannels(profile)` dá o número de canais dele.
- `outputTransform(profile, { intent, blackPointCompensation, preserveNeutrals })` devolve `fromRgb(r, g, b)` (sRGB 0..1 → CMYK 0..1), `toLab(cmyk, paper?)` e `proof(cmyk, paper?)` (CMYK → sRGB de tela).
- `cmykToLab`, `labToCmyk`, `srgbToLab`, `labToSrgb`, `deltaE` e `totalAreaCoverage` são as conversões avulsas; `buildRgbLut` / `sampleRgbLut` criam e leem tabelas densas para o trabalho por pixel.
- `OUTPUT_PROFILES`, `outputProfileInfo(id)` e `loadOutputProfile(id, baseUrl?)` dão o catálogo; `srgbProfileBytes()` grava o perfil sRGB com que o PDF/X-4 marca o RGB; `authoredCmykColors(config)` lista as cores que uma configuração define em CMYK.

O resolvedor e o removedor seguem o padrão das outras seções: `resolvePrintConfig`, `stripPrintDefaults` e `profileInkLimit(config)` (o limite do perfil que uma configuração indica, antes de qualquer `inkLimit` que o substitua), com `DEFAULT_PRINT_CONFIG`, `DEFAULT_PRINT_BLACK_CONFIG`, `DEFAULT_PRINT_PREFLIGHT_CONFIG` e `DEFAULT_RICH_BLACK`.

### Pares aceitos

Uma adaptação mantém a paleta do original, e alguns dos seus pares ficam abaixo do limite: um tom claro atrás do texto de uma caixa, uma cor da marca num cabeço. `allow` os aceita sem desligar a verificação (desde o postext 1.52). Uma entrada nomeia a cor do texto `fg` e a do fundo `bg` (em hexadecimal, como a configuração as escreve ou como são pintadas), ou um `style`: o id de um estilo de caixa (`calloutStyles`, ou o `style` de um quadro de página composta), de parágrafo, de título, de etiqueta em linha ou de rótulo de figura. Todos os campos que a entrada dá precisam coincidir, então `{ style: 'note', fg: '#7a8a99' }` aceita esse cinza só dentro das caixas `note`. Uma entrada que não dá nenhum dos três não coincide com nada.

```ts
contrast: {
  allow: [
    { fg: '#b7820f', bg: '#ffffff', reason: 'O ocre da editora para os cabeços' },
    { style: 'nota-margem', reason: 'O original compõe as notas de margem num cinza claro' },
  ],
}
```

Um par aceito continua sendo apontado: cada achado que coincide traz `accepted` (o `reason` da entrada, com seu `fg`, seu `bg` e seu `style`), e os achados aceitos vêm depois dos outros. O Sandbox os lista em Verificações, sob Pares de contraste aceitos, com o motivo, e não os conta; `postext check` os imprime como notas, que não fazem `--strict` falhar. As mesmas cores fora do que a entrada nomeia continuam sendo um aviso.

### Tela e impressão

O Postext compõe as mesmas páginas para uma tela e para uma máquina de impressão, e uma cor não se lê do mesmo jeito nas duas.

- **Tela** é a razão de contraste do WCAG 2 entre as cores sRGB, `(L1 + 0.05) / (L2 + 0.05)` sobre as luminâncias relativas delas: o que mostram o canvas, o visualizador HTML, um EPUB e um PDF em RGB.
- **Impressão** é a mesma fórmula sobre a luminância que cada cor tem no papel. A cor é separada com o perfil de saída do trabalho (uma cor definida em CMYK mantém os valores), a separação é lida de volta pelo perfil, e a luminância dela é tomada em relação ao papel sem tinta, que é o branco de uma página impressa assim como o branco do monitor é o branco de uma tela. A tinta nunca é um preto perfeito: o preto chapado sobre branco dá cerca de 14:1 em papel couché (FOGRA39, FOGRA51), 8:1 em papel não revestido (FOGRA47, FOGRA52) e 5:1 em papel jornal (IFRA26, SNAP), onde uma tela dá 21:1. Um cinza que passa na tela pode não passar no papel: `#767676` sobre branco dá 4,54:1 na tela e cerca de 3,3:1 em papel couché.

A razão de impressão precisa da transformação do perfil de saída (`options.transform`, criada com `outputTransform`). Sem ela, só o texto vazado é verificado para impressão.

### Texto vazado

O texto claro vazado sobre um fundo de tinta entope na impressão quando é pequeno ou de traço fino: a tinta do fundo se espalha para dentro das letras, e um fundo composto de várias tintas também depende de as chapas se manterem em registro. A razão não mostra isso, já que branco sobre azul-escuro passa de 10:1. A verificação de impressão informa esse texto à parte (`reversedText`) quando ele está abaixo de `minSize`, ou abaixo de `minFineSize` quando é itálico ou tem peso igual ou menor que `lightWeight`. Cada problema diz de quantas das quatro tintas o fundo é composto.

### O que é lido

A verificação lê as linhas de cada bloco com as cores em linha (negrito, itálico, referências, chips), os marcadores de lista, as capitulares, as legendas, as notas e as células de tabela, e o texto dos espaços de design: cabeços, aberturas, designs de título, títulos de boxes. O fundo é o preenchimento mais acima sob o texto: uma caixa de design, um boxe, uma barra de legenda, uma célula de tabela, um chip ou, na falta deles, a cor da página (`page.backgroundColor`, ou o papel que a paleta de uma parte dá às páginas dela). Uma cor translúcida é mesclada com o que está sob ela. O texto sobre uma imagem fica de fora, já que o fundo dele não é uma cor só, assim como o letreiramento dos quadrinhos, as leituras em rubi e as fórmulas. As palavras dos rótulos de uma figura são lidas sobre a placa dele ou, se não houver, dentro do seu halo; os rótulos nus sobre a imagem são ignorados, como todo texto sobre uma imagem.

Numa página composta a verificação segue a ordem em que a página é pintada: os blocos por camada, com a `decoration` do modelo na camada 0. O texto de um bloco é lido sobre a caixa do próprio bloco quando o estilo dele pinta uma; senão, sobre a caixa da decoração que fica por baixo (uma imagem da decoração deixa-o de fora, como qualquer imagem); senão, sobre a cor da página. Letras brancas sobre uma aba colorida da decoração são, portanto, medidas contra essa aba. Um bloco girado ou escalado é levado à folha antes de se ler o fundo dele, e o texto da própria decoração é verificado da mesma forma. Desde o postext 1.37.

### Como executar a verificação

`contrastDocument(doc, options)` devolve os problemas de um documento diagramado, da menor razão para a maior. Cada um traz o `pageIndex` absoluto no livro, o `rect` na folha (px da página) e o intervalo de origem da primeira ocorrência, as duas cores como foram pintadas (`color`, `background`), o menor `sizePt` em que é composto, com o `weight` e o `italic`, um `role` (`'body'`, `'heading'`, `'caption'`, `'table'`, `'runningHead'`, `'design'`, `'chip'`, `'marker'` ou `'label'`, as palavras dos rótulos de uma figura), o `text` do primeiro trecho e o `count` de trechos compostos assim. Um par é informado uma vez por limiar, seja qual for o número de linhas que o usam.

- `lowContrast` acrescenta `level`, `large`, `required`, a razão em cada meio verificado (`screen`, `print`) e `failing`, os meios abaixo de `required`.
- `reversedText` acrescenta `reasons` (`'small'`, `'italic'`, `'light'`), `minimumPt` e `inks`.

As opções são `contrast` (os ajustes resolvidos, quando não são os do documento), `media` (os meios, independentemente do que define `mode`) e `transform`.

```ts
import { contrastDocument, outputTransform, parseIccProfile } from 'postext';

const transform = outputTransform(parseIccProfile(fogra51Bytes));
for (const issue of contrastDocument(doc, { transform })) {
  if (issue.kind === 'lowContrast') {
    console.log(`${issue.color} on ${issue.background}: ${issue.screen}:1, ${issue.level} asks for ${issue.required}:1`);
  }
}
```

`contrastPairs(doc, options)` devolve cada par de texto e fundo que o documento compõe, passe ou não, com a razão `screen`, a razão `print` quando o `transform` é fornecido, a razão `required` e as cores como a configuração as escreve (`textColor`, `groundColor`): o que uma ferramenta de design mostra ao lado de um campo de cor. Ele é executado independentemente do que define `enabled`.

As medidas são exportadas para suas próprias ferramentas:

- `contrastRatio(a, b)` e `relativeLuminance(color)` dão a razão e a luminância WCAG 2 de cores sRGB.
- `isLargeText(sizePt, weight)` e `contrastThreshold(level, large)` dão o limiar de um corpo e de um peso.
- `blendColors(top, under)` dá uma cor translúcida sobre outra, como `#rrggbb`.
- `printContrastRatio(a, b, context)`, `printLuminance(color, context)` e `printSeparation(color, context)` dão o mesmo no papel. O contexto leva o `transform` e, como `authored`, o resultado de `authoredCmykColors(config)`.
- `contrastMedia(doc.config, contrast)` dá os meios em que `mode` se resolve para um documento.

O resolvedor e o removedor seguem o padrão das outras seções: `resolveContrastConfig` e `stripContrastDefaults`, com `DEFAULT_CONTRAST_CONFIG`, `DEFAULT_CONTRAST_REVERSED_TEXT_CONFIG`, `CONTRAST_LEVELS` e `CONTRAST_MODES`.


## Verificação do conteúdo (configuração)

A propriedade `checks` reúne as verificações que leem a própria configuração. Hoje ela tem uma, `contentInConfig`, que avisa quando um design guarda o texto do livro. Um cabeço, o design de um título, uma página de parte e a linha de uma parte no sumário são forma: levam marcadores (`{chapterTitle}`, `{titleText}`, `{number}`) e no máximo uma ou duas palavras próprias, como *Capítulo* antes de `{chapterNumber}`. O texto que faz parte do livro vai no Markdown, onde o sumário, a busca, as traduções, o PDF marcado e o EPUB o enxergam. A diagramação não lê essa verificação; por isso, mudá-la nunca desloca uma linha.

### Como um texto de design é lido

- O texto literal dele é o `content` sem nenhum marcador (`{name}`, `{attr.key}`, `{firstMark.key}`), com os escapes `{{` e `}}` lidos como chaves e `\n` como quebra de linha.
- Um texto sem letras nem algarismos (uma fileira de pontos guia, um ornamento, um `·`) nunca é conteúdo.
- Uma palavra é o que fica entre espaços e tem uma letra ou um algarismo: um `·` ou uma `|` soltos não são palavras, e um endereço como `postext.dev` é uma.
- Primeiro saem as frases de `allow`, e também `title`, `subtitle`, `author` e `publisher` dos metadados do documento (o front matter), que um cabeço costuma repetir.
- O que sobra é conteúdo quando tem mais de `maxWords` palavras ou mais de `maxChars` letras e algarismos.

Todos os espaços de design são lidos: `header`, `footer`, o `advancedDesign.slot` de cada nível de título, o `advancedDesign.slot`, o `header` e o `footer` de cada estilo de título, `parts.design`, `parts.versoDesign`, `toc.parts.design`, e os mesmos dentro de `htmlViewer.overrides`. `configDesignSlots(config)` lista todos com seus caminhos, e `designTextLiteral(content)` devolve o texto literal de um modelo.

### O aviso

`collectConfigWarnings` (e `VDTDocument.configWarnings`) dá um aviso `contentInConfig` por configuração que guarda conteúdo: um estilo de título (com seu `id` em `ownerId`), um nível de título, o cabeçalho, o design das partes. `path` indica a configuração, `count` os textos de design afetados, `chars` as letras e algarismos deles, `elements` o caminho de cada um (os 20 primeiros) e `value` o início do primeiro (no máximo 40 caracteres). Passe os metadados do documento como segundo argumento para permitir o título e o autor; uma diagramação já faz isso sozinha.

```js
import { collectConfigWarnings } from 'postext';

collectConfigWarnings(config, { metadata: { title: 'A Year of Weather' } });
// [{ kind: 'contentInConfig', path: 'headingStyles[3]', ownerId: 'lesson-4',
//    value: 'Look at the picture and answer the questi…', used: '',
//    count: 30, chars: 1017, elements: ['headingStyles[3].header.elements[2]', …] }]
```

**Correção:** leve o texto para o Markdown, como título, boxe ou parágrafo do capítulo a que pertence, e deixe só marcadores no design. Um valor que muda a cada capítulo pode ir na linha do título e ser lido com `{attr.key}`: `# Mapas {kicker="Lição 4"}` e `{attr.kicker}` no design. Uma frase que é forma, como o nome da editora em um cabeço, vai em `allow`.

O Sandbox mostra o aviso no painel **Verificações** e traz a verificação em **Design → Avançado → Conteúdo na configuração**; `postext check` o imprime.


## Visualizador Folio (configuração)

A propriedade `folio` define como o visualizador Folio (`postext-folio`) apresenta o livro impresso em 3D: o ângulo de visão, o papel, a encadernação, a superfície onde o livro está e a luz. A diagramação a ignora, assim como as saídas de canvas, HTML e PDF. `buildDocument` leva os ajustes resolvidos na VDT como `doc.config.folio` quando a configuração define algum, de modo que um documento sem eles mantém seu hash de layout.

    type?: 'uncoated' | 'bookWove' | 'coatedMatte' | 'coatedSilk' | 'coatedGloss'

    bulk?: number;                // cm³/g; espessura em µm = gramatura × bulk

    texture?: 'auto' | 'smooth' | 'vellum' | 'wove' | 'laid' | 'linen' | 'felt';

    type?: 'hardcover' | 'paperback' | 'sewn' | 'layflat' | 'saddleStitch' | 'folded';

Uma página num formato de jornal (`page.sizePreset` `'broadsheet'`, `'berliner'`, `'tabloid'` ou `'compact'`) é mostrada como jornal quando a configuração não indica papel nem encadernação: papel `newsprint` e encadernação `folded` (desde o postext 1.18). Um papel ou uma encadernação que a configuração indique é mantido, de modo que `paper: { type: 'uncoated' }` imprime um tabloide em papel offset. Os campos de papel definidos sem tipo de papel (uma `grammage`, um `shade`) se aplicam ao papel-jornal. O resolvedor e o removedor recebem o formato como segundo argumento, e `folioForTrim(folio, sizePreset)` grava os dois valores padrão na configuração:

```ts
resolveFolioConfig({ tilt: 30 }, 'tabloid');
// => { tilt: 30, paper: { type: 'newsprint', grammage: 48, bulk: 1.5, … }, binding: { type: 'folded', coverMaterial: 'paper', … }, … }

stripFolioDefaults({ paper: { type: 'newsprint' }, binding: { type: 'folded' } }, 'tabloid');
// => undefined
```

As cores seguem os vínculos de paleta como qualquer outra cor da configuração (`paletteId`). O resolvedor e o removedor seguem o padrão das outras seções; o removedor descarta os valores de papel iguais aos do tipo de papel escolhido:

```ts
import { FOLIO_PAPER_STOCKS, DEFAULT_FOLIO_CONFIG, resolveFolioConfig, stripFolioDefaults } from 'postext';

resolveFolioConfig({ paper: { type: 'bible' } }).paper;
// => { type: 'bible', grammage: 40, bulk: 1.1, finish: 'uncoated', texture: 'vellum', textureStrength: 1, shade: { hex: '#f9f6ee', … }, showThrough: true }

stripFolioDefaults({ paper: { type: 'bible', grammage: 40 } });
// => { paper: { type: 'bible' } }
```

No Sandbox, esses ajustes formam o grupo **Folio** do painel Design (**Design → Folio → Visualizador Folio (3D)**), e a aba Folio os mostra à medida que você os muda, sem diagramar o livro de novo. Veja [Um livro em 3D](/pt/docs/configuration-html-folio-epub#um-livro-em-3d-postext-folio) para o próprio visualizador, e [Formato do documento › `:::paper`](/pt/docs/document-format-directives#paper) para uma sequência de páginas em outro papel.

### Linhas frouxas no seu próprio canvas

O motor exporta o destaque de linhas frouxas como dois auxiliares, para uma página que você mesmo pinta:

```ts
import { buildDocument, renderPageToCanvas, drawLooseLines, findLooseLines } from 'postext';

const doc = buildDocument(content, config);
const canvas = document.querySelector('canvas')!;
renderPageToCanvas(doc.pages[0], doc, canvas, { scale: 0.5 });
drawLooseLines(canvas.getContext('2d')!, doc.pages[0], doc, { threshold: 2.5 });

// As mesmas linhas como dados: um relatório, uma sobreposição SVG, uma contagem por página.
for (const { ratio, line, block } of findLooseLines(doc, { threshold: 2.5 })) {
  console.log(`page ${block.pageIndex + 1}: ${ratio.toFixed(2)}× — ${line.text}`);
}
```

- **`findLooseLines(doc, { threshold?, pageIndex? })`** devolve, em ordem de leitura, cada linha justificada cujo espaçamento entre palavras passa de `threshold`: `{ block, line, ratio, x, y, width, height }`. `ratio` é `lineWordSpacing(line)`: o espaçamento tal como `minWordSpacing` e `maxWordSpacing` o restringem (`justifiedSpaceLimitRatio` quando a linha contém espaços de outro estilo, senão `justifiedSpaceRatio`), de modo que uma linha composta no limite com um espaço em negrito não é sinalizada com um `threshold` igual a `maxWordSpacing`. O retângulo, em pixels da página, é a faixa que o destaque cobre: a largura inteira do bloco ao longo da linha. São as linhas que o Sandbox destaca e sinaliza como `looseLine` no painel **Verificações**.
- **`drawLooseLines(ctx, page, doc, { threshold?, color? })`** preenche essas faixas em uma página e devolve as linhas que pintou. Ele desenha em pixels da página sob a transformação atual do contexto; por isso, chame-o logo depois de `renderPage` ou `renderPageToCanvas` no mesmo canvas: os dois deixam o contexto na escala da página. `color` é qualquer estilo de preenchimento de canvas.
- **Valores padrão.** Os dois auxiliares usam o limiar padrão (3) e a cor padrão (`#ff000040`), não o `debug.looseLineHighlight` do documento: essa configuração pertence ao Sandbox. Para seguir uma configuração, passe `resolveDebugConfig(config.debug).looseLineHighlight.threshold` e `.color.hex`.

### Avisos

### Avisos de configuração

Estes erros na própria configuração nunca passam em silêncio, e nenhuma opção os oculta, exceto a que o último item cita. O motor não falha em nenhum deles; ele substitui o valor, ou ignora a configuração, e avisa:

- **Formato de numeração desconhecido**: um `numberFormat` de lista numerada, um `page.pageNumbering.format` ou o `counterFormat` de um tipo de recurso que não é nenhuma das [grafias de formato de numeração](/pt/docs/configuration-page-layout#grafias-dos-formatos-de-numeração). A numeração sai em decimal.
- **Pilha de fontes em uma família**: um `fontFamily` (ou qualquer `…FontFamily`) que contém uma pilha de fontes CSS. O texto é composto na primeira família da pilha (veja [Uma família por `fontFamily`](/pt/docs/configuration-text#uma-família-por-fontfamily)).
- **Coluna lateral sem espaço**: um `sideColumnPercent` de um layout `'oneAndHalf'` (o do documento, ou o do `layout` próprio de um estilo de título) que deixaria uma das colunas com menos de 1% da largura do conteúdo, ou que não é um número. As colunas são cortadas no valor mais próximo que as duas aceitam, e `used` informa qual é (`sideColumnPercentClamped`; veja o [layout `'oneAndHalf'`](/pt/docs/configuration-page-layout#tipos-de-layout)).
- **Número de colunas fora do intervalo**: um `columnCount` de um layout `'multiple'` (o do documento, ou o do `layout` próprio de um estilo de título) que não é um número inteiro de 3 a 8. A página é dividida no número válido mais próximo (3 para um valor que não é número), e `used` informa qual é (`columnCountClamped`; veja o [layout `'multiple'`](/pt/docs/configuration-page-layout#tipos-de-layout)).
- **Grade de caracteres grande demais**: uma `cjk.grid` com mais caracteres por linha ou linhas por página do que as margens permitem. A grade é montada com o máximo que cabe, e `used` informa esse número (`cjkGridClamped`; veja [Grade de caracteres](/pt/docs/configuration-east-asian#grade-de-caracteres)).
- **Configuração de título desconhecida**: uma chave que `headings`, `headings.balancing`, um nível de título, um estilo de título ou um estilo de parágrafo não tem: um `letterSpacng` com erro de digitação, um `tracking` emprestado de outra ferramenta, um `level` em um estilo de título, um `fontStyle: 'italic'` em um estilo de parágrafo (que usa `italic: true`). Uma parada de tabulação é verificada da mesma forma (um `leaders` em vez de `leader`), assim como uma capitular, `lineNumbers`, `canvasViewer`, `checks`, `codeStyle` e as configurações de quadrinhos. O motor a ignora (até o postext 1.4, fazia isso sem dizer nada). `value` é a chave, `used` fica vazio e `suggestion` indica a configuração mais próxima, quando há uma a uma ou duas letras de distância ou que difere só em maiúsculas e minúsculas (`unknownConfigKey`).
- **Valor de configuração desconhecido**: uma configuração que aceita uma entre poucas palavras contendo outra, como `direction: 'right'` (ela aceita `auto`, `ltr` ou `rtl`). O motor lê o valor padrão no lugar, e `used` informa no que ele resultou: para `direction`, a direção do idioma do documento (`unknownConfigValue`). Um `align` de uma parada de tabulação que não é nenhuma das suas quatro palavras é lido como `'start'`, e uma `position` que não é um comprimento, `'end'` nem uma porcentagem deixa a parada de fora (`used` é `'none'`). As palavras das configurações de quadrinhos também são verificadas ([Quadrinhos › Avisos de quadrinhos](/pt/docs/comics#avisos-de-quadrinhos)): `used` é o valor em que a configuração se resolveu (o padrão próprio de um estilo de balão, no caso de um estilo embutido), e `suggestion` indica a palavra mais próxima do valor, quando há uma próxima. O `level` e o `mode` da verificação de contraste são verificados da mesma forma: `used` é `'AA'` ou `'auto'`. `canvasViewer.pageGap` e `canvasViewer.rowGap` são verificados do mesmo modo: `used` é o inteiro de 0 a 200 em que o valor foi lido (desde o postext 1.43). O mesmo vale para `print.standard`, `print.outputProfile` e `print.renderingIntent` (`used` é o que o padrão deu) e para um `maxWords` ou `maxChars` de `checks.contentInConfig` que não seja um inteiro igual ou maior que 0.
- **Números de linha em texto vertical**: `lineNumbers.enabled: true` num documento composto na vertical (`layout.writingMode: 'vertical-rl'`). Páginas verticais não recebem números de linha, e `used` é `false` (`lineNumbersUnsupported`; veja [Numeração de linhas](/pt/docs/configuration-notes-references#numeração-de-linhas)).
- **Contorno de texto na escrita vertical** — o `defaultPlacement.wrap` de um tipo de recurso num documento composto na vertical. Páginas verticais não compõem texto ao lado de uma figura, e `used` é `none` (`wrapUnsupported`; veja [Formato do documento › Contorno de texto](/pt/docs/document-format-resources#contorno-de-texto)). Um `wrap` que não indica um lado é um valor de configuração desconhecido.
- **Estilo de boxe baseado em outro** — um estilo de boxe cujo `extends` não indica nenhum estilo de `calloutStyles` (`calloutStyleExtendsUnknown`, com o id mais próximo em `suggestion`), ou cuja cadeia de `extends` volta a ele (`calloutStyleExtendsCycle`, `value` o círculo `a → b → a`). O estilo fica sozinho, com os valores padrão no que deixa sem valor (veja [Estilos baseados em outro](/pt/docs/configuration-callouts#estilos-baseados-em-outro)).
- **Modelos de página e estilos de rótulo** — um problema em `pageTemplates` ou `labelStyles`: um id ou nome repetido, `extends`, âncoras ou blocos encadeados que formam um círculo, um estilo, bloco ou modelo que não existe, um mínimo maior que o máximo, um estilo de rótulo de uma âncora que `labelStyles` não tem (verificado quando os recursos são passados: `collectConfigWarnings(config, { resources })`). O `path` deles é um ponteiro JSON (`/pageTemplates/3/frames/2/style`); cada tipo aparece com a causa e a solução em [Avisos dos modelos de página](/pt/docs/configuration-composed-pages#avisos-dos-modelos-de-página).
- **Conteúdo em um design** — um elemento de texto de design cujo texto, além dos marcadores, é mais longo que um rótulo curto: o texto do livro guardado na configuração. Um aviso por configuração (um estilo de título, o cabeçalho, o design das partes), com o caminho de cada texto (`contentInConfig`; veja [Verificação do conteúdo](#verificação-do-conteúdo-configuração)). Ao contrário dos outros, pode ser desligado: `checks.contentInConfig.enabled: false`.

O Sandbox os lista no painel **Verificações** com o caminho da configuração. No código, `buildDocument` os coloca no documento como `configWarnings` (ausente quando a configuração está limpa), e `collectConfigWarnings(config)` os devolve sem diagramar nada:

```js
import { buildDocument, collectConfigWarnings } from 'postext';

// JavaScript puro: em TypeScript, 'roman' nem passa na verificação de tipos.
const config = { bodyText: { fontFamily: 'EB Garamond, serif' }, orderedLists: { numberFormat: 'roman' } };
const doc = buildDocument({ markdown }, config);
doc.configWarnings;
// [{ kind: 'fontFamilyStack', path: 'bodyText.fontFamily', value: 'EB Garamond, serif', used: 'EB Garamond' },
//  { kind: 'unknownNumberFormat', path: 'orderedLists.numberFormat', value: 'roman', used: 'arabic' }]
collectConfigWarnings(config); // a mesma lista
```

Toda configuração parcial aninhada também é verificada: estilos de título, as listas dentro das partes, `htmlViewer.overrides`, elementos de design.

`formatWarning` (veja [Avisos no documento](/pt/docs/configuration-programmatic-usage#avisos-no-documento)) também os descreve, com o caminho da configuração na frente (`bodyText.fontFamily: font stack "EB Garamond, serif" — set in "EB Garamond"`, `headingStyles[0].letterSpacng: unknown setting "letterSpacng" — ignored (did you mean "letterSpacing"?)`), de modo que um aplicativo hospedeiro pode registrar em um único laço as três listas que uma compilação devolve.
