# Ús programàtic: HTML, Folio, EPUB i SCORM


## Integrar el visor HTML

El visor HTML és el renderitzador de Postext pensat per a la pantalla. En lloc de convertir les pàgines en un mapa de bits, genera nodes del DOM amb posició absoluta, i la seva geometria surt del mateix procés de composició que la sortida impresa. És l'opció adequada quan vols al navegador una tipografia llegible, seleccionable i que s'adapti als canvis de mida (una aplicació de lectura, una previsualització dins d'un producte o una documentació incrustada) sense haver d'afegir un visor de PDF.

Les peces clau de l'API pública:

- **`buildDocument(content, config, cache?)`**: executa tot el procés de composició i retorna un `VDTDocument`.
- **`renderToHtmlIndexed(doc, options)`**: converteix el VDT en una única cadena HTML, amb un desglossament per pàgina i per bloc. Aquest desglossament permet actualitzar el DOM amb poc cost quan entre dos renderitzats només han canviat alguns blocs.
- **`resolveHtmlViewerConfig(partial)`**: completa els valors per defecte del visor HTML (`maxCharsPerLine`, `columnGap`, `optimalLineBreaking`).
- **`buildFontString` + `measureGlyphWidth` + `dimensionToPx`**: funcions bàsiques de mesura per calcular l'amplada real de la columna en píxels a partir d'un nombre de caràcters objectiu.
- **`createMeasurementCache` / `clearMeasurementCache`**: memòries cau intercanviables per reutilitzar mesures d'una composició a la següent.
- **`prepareFonts` / `buildDocumentWithFonts` / `watchFonts` / `onFontsChanged`**: carreguen les cares del document abans de compondre i tornen a compondre quan n'arriben de noves (vegeu [Carregar les fonts abans de compondre](/ca/docs/configuration-programmatic-usage#carregar-les-fonts-abans-de-compondre)).

### Exemple en directe: una cadena HTML

Tot el procés en JavaScript pla, abans de la integració amb React que trobaràs més avall: construir el document, passar el `VDTDocument` a `renderToHtml` i bolcar la cadena en un contenidor. `mode: 'single'` apila les pàgines en vertical, i `background` els dona color, perquè per defecte les pàgines són transparents. El pen també imprimeix el marcatge generat, perquè vegis les línies amb posició absoluta que genera el renderitzador: el navegador les pinta, però no les torna a compondre mai.

### Integració mínima

El fragment següent és la integració útil més curta: construeix el document a la mida actual de la vista, el renderitza en un contenidor i el torna a compondre quan canvia la mida.

```tsx
import { useEffect, useRef } from 'react';
import {
  buildDocument,
  renderToHtmlIndexed,
  resolveHtmlViewerConfig,
  buildFontString,
  measureGlyphWidth,
  dimensionToPx,
  createMeasurementCache,
  watchFonts,
  onFontsChanged,
} from 'postext';
import type { PostextConfig, MeasurementCache } from 'postext';

// DPI adequat per a pantalla: a 144 DPI una mida de cos de 8pt resol a 16 px.
const HTML_DPI = 144;
const PADDING_PX = 24;

// Mostra de prosa que serveix per mesurar l'amplada objectiu de columna. Les fonts
// proporcionals fan poc fiable "N × amplada mitjana", així que mesurem una
// cadena representativa.
const SAMPLE =
  'The quick brown fox jumps over the lazy dog. Sphinx of black quartz, judge my vow.';

function sampleForChars(n: number): string {
  let s = SAMPLE;
  while (s.length < n) s += ' ' + SAMPLE;
  return s.slice(0, n);
}

export function PostextHtmlViewer({
  markdown,
  config,
  mode = 'multi',
}: {
  markdown: string;
  config: PostextConfig;
  mode?: 'single' | 'multi';
}) {
  const hostRef = useRef<HTMLDivElement | null>(null);
  const cacheRef = useRef<MeasurementCache>(createMeasurementCache());

  useEffect(() => {
    const host = hostRef.current;
    if (!host) return;

    const relayout = () => {
      const rect = host.getBoundingClientRect();
      if (rect.width === 0 || rect.height === 0) return;

      const viewer = resolveHtmlViewerConfig(config.htmlViewer);
      const fontFamily = config.bodyText?.fontFamily ?? 'EB Garamond';
      const fontWeight = config.bodyText?.fontWeight ?? 400;
      const fontSize = config.bodyText?.fontSize ?? { value: 8, unit: 'pt' as const };
      const fontSizePx = dimensionToPx(fontSize, HTML_DPI);

      // Mesura l'amplada *real* de columna per a N caràcters de prosa del cos.
      const targetColumnPx = measureGlyphWidth(
        sampleForChars(viewer.maxCharsPerLine),
        buildFontString(fontFamily, fontSizePx, String(fontWeight), 'normal'),
      );

      const inner = Math.max(rect.width - PADDING_PX * 2, 100);
      let columnWidthPx: number;
      if (mode === 'single') {
        columnWidthPx = Math.min(targetColumnPx, inner);
      } else {
        // Hi encabeix tantes columnes com es pugui a l'amplada objectiu.
        const count = Math.max(
          1,
          Math.floor((inner + viewer.columnGap) / (targetColumnPx + viewer.columnGap)),
        );
        columnWidthPx = (inner - viewer.columnGap * (count - 1)) / count;
      }
      columnWidthPx = Math.max(Math.floor(columnWidthPx), 80);

      // El mode single fa servir una pàgina molt alta; el mode multi fa servir l'alçada
      // de la vista, de manera que cada "pàgina" VDT es converteix en una columna.
      const pageHeightPx =
        mode === 'single' ? Math.max(rect.height * 20, 200_000) : Math.max(rect.height - PADDING_PX * 2, 400);

      const override: PostextConfig = {
        ...config,
        page: {
          ...config.page,
          dpi: HTML_DPI,
          width: { value: columnWidthPx, unit: 'px' },
          height: { value: pageHeightPx, unit: 'px' },
          margins: {
            top: { value: 0, unit: 'px' },
            bottom: { value: 0, unit: 'px' },
            left: { value: 0, unit: 'px' },
            right: { value: 0, unit: 'px' },
          },
        },
        layout: { ...config.layout, layoutType: 'single' },
        bodyText: {
          ...config.bodyText,
          optimalLineBreaking: viewer.optimalLineBreaking,
        },
      };

      const doc = buildDocument({ markdown }, override, cacheRef.current);
      const { html } = renderToHtmlIndexed(doc, {
        mode,
        columnGap: viewer.columnGap,
        padding: PADDING_PX,
        background: 'transparent',
      });

      host.innerHTML = html;
    };

    relayout();

    const ro = new ResizeObserver(() => relayout());
    ro.observe(host);

    // Torna a mesurar quan es carreguen les web fonts perquè les amplades de glif no
    // quedin preses a partir de les fonts de reserva.
    const stopWatching = watchFonts();
    const off = onFontsChanged(() => relayout());

    return () => {
      ro.disconnect();
      off();
      stopWatching();
    };
  }, [markdown, config, mode]);

  return <div ref={hostRef} style={{ width: '100%', height: '100%', overflow: 'auto' }} />;
}
```

Algunes notes sobre el que fa l'exemple:

- **Es mesura la columna, no s'aproxima.** Com que `maxCharsPerLine` és un *objectiu* expressat en caràcters, l'amplada real en píxels depèn de la font del text de cos. `measureGlyphWidth` en fa una mesura real amb la font triada, i així l'amplada de línia es manté coherent quan es canvia de font.
- **Es reescriu la pàgina.** El visor HTML tracta cada "pàgina" del VDT com una columna en pantalla. L'exemple substitueix `page.width` per l'amplada de columna mesurada, posa els marges a zero (el farciment queda fora de la pàgina, al `.pt-doc` que l'embolcalla) i fa servir `HTML_DPI = 144` perquè un cos de `8pt` equivalgui a `16px`.
- **Pendent de la càrrega de fonts.** `watchFonts` escolta `document.fonts` i, una vegada per fotograma, descarta les mesures de les famílies que acaben de rebre cares noves; llavors `onFontsChanged` torna a compondre la columna. Sense aquesta recomposició, el primer renderitzat fa servir les mètriques de la font de reserva i el text salta quan arriba la font real.
- **Es reutilitza la memòria cau de mesures.** Si la memòria cau es crea una sola vegada per component, els canvis de mida i d'escala de la font reutilitzen les mesures del renderitzat anterior en lloc de tornar a mesurar cada paràgraf.

### Pas següent

L'exemple de més amunt és deliberadament pla. Les integracions en producció hi solen afegir:

- **Aïllament amb Shadow DOM**: renderitza a `host.attachShadow({ mode: 'open' })` perquè cap CSS de la pàgina exterior s'escoli al visor.
- **Actualització incremental**: `renderToHtmlIndexed` retorna `pages[i].blocks`, cadascun amb un `id` estable i l'HTML extern del bloc. Quan entre dos renderitzats només canvien uns quants blocs, pots substituir aquests embolcalls al mateix lloc en lloc de reconstruir tot l'`innerHTML`.
- **Capes superposades**: un SVG amb posició absoluta sobre cada `.pt-page` per a cursors, seleccions o la retícula de base.
- **Enllaços**: les paraules d'un enllaç Markdown s'embolcallen en `<a href="…" rel="noopener noreferrer">`, que agafa el color del text i no se subratlla; consulta [Format del document › Enllaços](/ca/docs/document-format-inline#enllaços). En un visor que funcioni com a editor, intercepta els clics als `a[href]` que no comencin per `#` i obre'ls en una pestanya nova (les àncores de `:ref` enllacen dins del document).
- **Imatges a una sola tinta**: amb `diagramStyle.singleInk` actiu, els `<img>` SVG porten un filtre CSS, tret que passis `singleInk: false` per a URL que ja estan recolorides; consulta [Tinta única en canvas i en HTML](/ca/docs/configuration-resources#tinta-única-en-canvas-i-en-html).
- **Pàgines compostes i de còmic sobre un full imprès**: en una pàgina tan ampla com la pantalla i tan alta com el desplaçament, un marc ancorat al peu d'una pàgina composta (`::::page{template}`) quedaria al peu del desplaçament. Passa `composedViewerLeaf: { width, height, margins? }` (la mida i els marges de la pàgina impresa) a la configuració que maquetes, i cada pàgina composta es maqueta en una pàgina d'aquesta mida, amb la seva geometria d'impremta, perquè l'escalis a la pantalla (des de postext 1.47); `comics.viewerLeaf` fa el mateix amb les pàgines de còmic, escalades a `fitWidth` px (vegeu [Còmics](/ca/docs/configuration-comics)). Totes dues són per a amfitrions: les posa el visor HTML del Sandbox i no es desen mai amb un document.

El component `HtmlPreview` del Sandbox (`packages/postext-sandbox/src/viewport/HtmlPreview/index.tsx`) implementa tot això amb la mateixa API que es mostra aquí i et pot servir de referència. A més, envia cada composició a un worker de composició compartit (consulta [Executar la composició en un Web Worker](/ca/docs/configuration-programmatic-usage#executar-la-composició-en-un-web-worker)) perquè les edicions en directe i els canvis de mida no bloquegin mai el fil principal: quan vulguis treure la composició del fil principal, substitueix la crida directa `buildDocument(...)` del fragment anterior per `layoutWorker.build(...)`.

La pàgina transparent és important en un lloc web amb tema fosc: una previsualització sense `background` mostra text negre sobre el fons fosc del lloc. Passa `renderToHtml(doc, { background: '#ffffff' })`, o dona al document un `page.backgroundColor`.

**Els estils de text de la pàgina amfitriona queden fora.** Cada línia es compon amb les amplades que va mesurar el motor; per tant, si la sortida heretés de la pàgina que la conté un `letter-spacing`, un `word-spacing`, un `text-transform` o un `font-variant`, els trams de glifs s'eixamplarien i les línies es muntarien les unes sobre les altres. Per això l'arrel `.pt-doc` restableix les propietats de text heretables (espaiat entre lletres i entre paraules, majúscules i minúscules, sagnat, espais en blanc, estil, variant, pes, amplada, trets i *kerning* de la font, interlineat, alineació, ombra i èmfasi del text, guionets, direcció, mode d'escriptura, traç i farciment del text i l'engrandiment automàtic del text en mòbils) abans de les seves declaracions de maquetació, de manera que la sortida es veu igual dins d'una *shadow root* o sota un element amb estils. La llista s'exporta com a `HTML_TEXT_RESET`, una cadena de declaracions CSS: una aplicació amfitriona que munta l'`innerHtml` de les pàgines (de `renderToHtmlIndexed`) en contenidors propis l'ha d'aplicar a l'arrel d'aquests contenidors. Fins a postext 1.4 l'arrel no restablia res; el remei era un embolcall amb `all: initial`.


## Un llibre en 3D (`postext-folio`)

`postext-folio` mostra en pantalla un document compost com si fos un llibre imprès obert sobre una taula: dobles pàgines que respecten la regla de la pàgina senar (recto) i fulls que el lector passa amb els botons ‹ ›, amb les fletxes del teclat, lliscant el dit, fent clic en una pàgina o agafant-la per la vora i arrossegant-la. Cada full es corba en three.js segons el paper i projecta una ombra real sobre les pàgines de sota. El canvas WebGL dibuixa el llibre tant quan està quiet com quan es passa la pàgina, de manera que una pàgina no canvia mai d'aspecte en quedar-se quieta. És el visor de les receptes del Receptari i de la pestanya **Folio** del Sandbox.

```bash
npm install postext postext-folio three
```

```ts
import { buildDocument } from 'postext';
import { createFolioFromDocument } from 'postext-folio';

const doc = buildDocument({ markdown }, config);
const book = createFolioFromDocument(document.getElementById('book')!, doc, {
  onChange: ({ pages }) => console.log('pàgines a la vista', pages),
});

// Després d'una edició: el mateix visor, a la mateixa pàgina.
book.setDocument(buildDocument({ markdown: edited }, config));
```

- **Les pàgines es pinten a mesura que calen.** `createFolioFromDocument` pinta cada pàgina amb `renderPageToCanvas` exactament als píxels de dispositiu de l'espai que ocupa (llavors WebGL la mostra tèxel a píxel, tan nítida com a la previsualització en canvas), i només pinta les dobles pàgines properes a la que està oberta (`window`, tres a cada costat per defecte). Les pàgines que surten d'aquesta finestra s'alliberen, de manera que un llibre de mil pàgines ocupa la memòria d'unes poques. Si se salta a una pàgina llunyana, primer es pinta aquella doble pàgina. Fins a deu pàgines de distància, els fulls passen un a un; més enllà, el bloc de pàgines intermedi s'aixeca d'una sola peça, tan gruixut com aquestes pàgines (la suma dels gruixos de cada full), i es diposita a l'altre costat. `setDocument` conserva la pintura de cada pàgina que no canvia en la nova composició (`{ repaint: true }` les torna a pintar totes, per exemple quan acaba d'arribar una imatge).
- **El document defineix el llibre.** La primera pàgina s'obre sola a la dreta quan és una pàgina senar (`pageIndexOffset` parell); un llibre enquadernat per la dreta (`page.binding: 'right'`, o un document vertical) apareix en mirall i passa les pàgines cap a l'esquerra; les pàgines en blanc agafen el color de fons de la pàgina, i l'amplada de tall de la pàgina (`pageWidthMm`) determina l'escala del gruix del paper i de les tapes. Un capítol compost amb una `continuation` suma les altres pàgines del llibre (`pageIndexOffset` abans, `bookPageCount` després) al gruix dels dos blocs de pàgines sense dibuixar-les (`extraPages`).
- **El document defineix l'aspecte.** El paper, l'enquadernació, la taula i la llum surten de la [configuració `folio`](/ca/docs/configuration-fonts-colors-viewers#visor-folio-configuració) del document (`doc.config.folio`). Una pàgina composta dins d'una tanda `:::paper` té el seu propi paper (`VDTPage.paper`), i el full es dibuixa amb el color, la superfície, el gruix i la rigidesa d'aquell paper. Amb `binding.cover: 'pages'`, la primera pàgina és la tapa davantera i l'última, si és una pàgina parella, la tapa del darrere (`covers`). Un format de diari (`'broadsheet'`, `'berliner'`, `'tabloid'`, `'compact'`) que no indica ni paper ni enquadernació apareix com a paper de diari doblegat, fins i tot quan l'aplicació amfitriona passa el seu propi `folio`.
- **El contenidor defineix la mida.** El llibre l'ocupa sencer, amb els botons i el comptador de pàgines als marges, així que dona-li una alçada; quan canvia de mida, les pàgines es tornen a pintar a la mida nova. Per sota de 560 px d'amplada mostra una sola pàgina cada vegada (`mode: 'auto'`; `'single'` i `'double'` forcen un mode o l'altre): el llom va per la vora interior de la pàgina i el full gira al seu voltant; arrossegar cap al llom avança, lliscar en sentit contrari retrocedeix, i un toc passa la pàgina.
- **Què fa el punter.** `interaction` (i, més endavant, `setInteraction`) determina què fan el botó esquerre, un dit o un llapis sobre el llibre: `'hand'` (per defecte) agafa les pàgines i les passa, `'orbit'` gira la vista com quan s'arrossega amb el botó dret (per a trackpads i tauletes), i `'select'` deixa el punter a l'aplicació amfitriona, per exemple per seleccionar text. `pageAt(event)` diu quina pàgina hi ha sota el punter i en quin punt (`{ page, x, y }`, en fraccions de la pàgina des de la cantonada superior esquerra), sobre el llibre tal com es veu, inclinat o girat; `pointOnScreen(point)` fa el camí invers, per dibuixar un cursor o una selecció sobre la pàgina. `refreshPage(src)` torna a mostrar el canvas d'una pàgina que l'aplicació amfitriona ha tornat a pintar. El Sandbox els fa servir tots per seleccionar text i seguir el cursor de l'editor sobre les pàgines en 3D.
- **Una lupa per a la lletra petita.** Amb `interaction: 'magnify'`, una lupa rodona amb un anell negre segueix el punter per damunt del llibre (amb el dit, la lupa queda per sobre del dit mentre toques la pantalla). Mostra el llibre com el veu l'ull del lector, il·luminat i corbat tal com és, amb més augment al centre i una corba cap a l'anell. La roda del ratolí, `+` i `−` canvien l'augment (`setMagnification(zoom)`, d'1,5 a 10; per defecte, la pàgina es veu a uns 5,5 px CSS per mil·límetre) i Esc la treu; `magnifier: { zoom, diameter }` fixa tots dos valors des del principi. `createFolioFromDocument` torna a pintar les pàgines que hi ha sota la lupa amb prou nitidesa per al centre, de manera que es pot llegir el text de cos d'un diari; `createFolio` obté aquestes pintures de `detail: { paint(index, deviceWidth), release() }`. El Sandbox la posa al botó **Lupa (M)**. La lupa també selecciona text: sobre les pàgines el cursor és el de text, `pageAt` retorna el punt sota el centre de la lupa (damunt del dit en una pantalla tàctil) i al Sandbox un clic hi col·loca el cursor d'edició i un arrossegament selecciona.
- **El lector pot fer la volta al llibre.** Arrossegant amb el botó dret, la vista gira al voltant del llibre (fins a 70° des de la vertical), també mentre passen fulls; `resetView()` la torna suaument als valors `tilt` i `yaw` de la configuració, i `getView()` dona la vista actual (`{ tilt, yaw }`, en graus) per desar-la en aquests paràmetres. El Sandbox els ofereix en dos botons, **Restablir la vista** i **Desar com a vista per defecte**.
- **Els vídeos es reprodueixen a les pàgines.** Un clic a la imatge de portada d'un vídeo el reprodueix a la mateixa pàgina, en qualsevol mode d'`interaction`, i el vídeo continua mentre el full passa; un altre clic el posa en pausa, i s'atura quan el llibre queda quiet en una doble pàgina on ja no apareix. Un vídeo amb `player.autoplay` s'engega sol la primera vegada que es mostra la seva doble pàgina; si a més es pot reproduir alhora que d'altres (`player.exclusive: false`), s'engega sense so cada vegada que es mostra la doble pàgina i s'atura quan es passa; n'hi pot haver diversos reproduint-se alhora. Opcions `videos`, `videoUrl` i `onVideo`, i `stopVideo()` al visor; vegeu [Format del document › Vídeos a les pàgines de Folio](/ca/docs/document-format-resources#vídeos-a-les-pàgines-de-folio).
- **Primer, les fonts i les imatges.** Com amb `renderPage`, abans de pintar les pàgines les fonts del document han d'estar carregades a `document.fonts` i les imatges dels recursos, registrades amb `registerResourceImage`.
- **Accessible.** El visor és un grup que pot rebre el focus i respon a ←/→ (invertides en un llibre enquadernat per la dreta), Re Pàg/Av Pàg, Inici i Fi; els botons i el comptador de pàgines tenen etiqueta accessible (`labels` les tradueix), i cada canvas de pàgina porta un text `alt` (`alt: (index) => …`).
- **Sense WebGL2**, o quan el lector demana menys moviment, les dobles pàgines simplement canvien. Un llibre en WebGL pesa massa per a un mòbil (una textura per cada cara de pàgina): el Sandbox ofereix la pestanya Folio només on hi ha WebGL2 i el costat curt de la pantalla mesura almenys 600 px. `canFlip()` indica si en aquell entorn els fulls passaran en 3D: cal WebGL2 i que no s'hagi demanat menys moviment.

## Llibres EPUB (`postext-epub`)

`postext-epub` escriu un llibre maquetat en un fitxer EPUB 3.3, al navegador o a Node, sense servidor. Llegeix els mateixos documents per capítol que `renderToPdf` rep per a un llibre, de manera que els números de pàgina, les notes, les citacions, les referències creuades, l'índex general i l'índex analític ja arriben resolts, i retorna el fitxer en bytes. És l'escriptor que fa servir la pestanya **EPUB 3** del Sandbox.

```bash
npm install postext postext-epub
```

`postext` és una dependència *peer*, com a `postext-pdf`: actualitza tots dos paquets alhora i, si els carregues des d'un CDN, fixa'ls a la mateixa versió.

Al llibre de maquetació fluida es converteix en una secció amb els marcs en l'ordre del Markdown: cada marc és un bloc amb el seu estil de requadre, sense la decoració, i els rètols de cada figura s'enumeren després de la imatge: vegeu [Fora del paper](/ca/docs/composed-pages#fora-del-paper-html-epub-i-pdf-etiquetat).

### Escriure un llibre

```ts
import { openBundle, buildBundle } from 'postext';
import { renderToEpub } from 'postext-epub';

const bundle = await openBundle(fileBytes);
const docs = buildBundle(bundle); // un VDTDocument per capítol, en l'ordre del llibre

const bytes = await renderToEpub(docs, {
  layout: 'reflowable',
  metadata: { title: 'Llanterna', creators: ['Ada Lovelace'], language: 'ca' },
  fonts: bundle.fonts.map((f) => ({ family: f.family, weight: f.weight, style: f.style, bytes: new Uint8Array(f.bytes), format: f.format })),
  resourceBytes: (fileId) => {
    const data = bundle.files.get(fileId);
    return data ? { bytes: data, mediaType: '' } : undefined;
  },
  onWarning: (w) => console.warn(w),
});
```

Un document sol és un llibre d'un capítol: `renderToEpub([doc], options)`.

- **`renderToEpub(docs, options): Promise<Uint8Array>`** escriu el fitxer. `options` és `{ layout, metadata, fonts?, svgFonts?, resourceBytes?, cover?, onProgress?, onWarning?, signal?, kindlePanelView? }`.
- **`metadata`**: `title` i `language` (una etiqueta BCP 47) són obligatoris; `subtitle`, `creators`, `identifier`, `date`, `publisher`, `rights`, `description` i `modified` són opcionals. Un ISBN sense prefix passa a `urn:isbn:…`. Sense `identifier`, el llibre rep un `urn:uuid:` derivat del títol, els autors i la llengua, de manera que una versió nova del mateix llibre conserva el lloc a la biblioteca del lector. Passa també `modified` per obtenir un fitxer idèntic byte a byte.
- **`fonts`**: les variants que s'incrusten, `{ family, weight, style, bytes, format, unicodeRange? }`, amb `format` un de `woff2`, `woff`, `ttf`, `otf`. Cada variant es converteix en un fitxer i una regla `@font-face`; diversos fitxers amb el seu `unicodeRange` formen una sola variant (els trams de Google Fonts). Si les pàgines fan servir una família, un pes o un estil sense variant incrustada, se'n dona un avís `missingFont`, i els sistemes de lectura la substitueixen per una de pròpia. Incrusta només les fonts amb una llicència que ho permeti: una variant amb `redistributable: false` no s'escriu mai al fitxer (el llibre es pot compondre amb aquesta variant, però el fitxer de la font en queda fora, també de les imatges SVG). En lloc seu, una aplicació amfitriona pot donar les cares de la família oberta amb el nom de la família amb llicència (són cares corrents), que és el que fan el Sandbox i `postext` amb una família que indica un `fallback` (des de postext 1.43).
- **`resourceBytes(fileId)`**: les imatges que col·loquen les pàgines, de manera síncrona o asíncrona, com a `{ bytes, mediaType }`; un `mediaType` buit es llegeix dels bytes. Dona els mapes de bits tal com estan desats i els SVG en codi font, no el màster PDF d'impremta (`svg.pdfFileId`). Cada imatge es desa una sola vegada. En un llibre a una tinta (`diagramStyle.singleInk`), els SVG es recoloren dins del fitxer. Cada SVG porta incrustades les variants que fa servir el seu text, perquè el sistema de lectura el mostra com una imatge que no veu les fonts del llibre (consulta [Fonts al text dels SVG](/ca/docs/configuration-resources#fonts-al-text-dels-svg)): primer les de `fonts` (els trams que contenen els caràcters de l'SVG) i després les de **`svgFonts.provider`**, per a les famílies que el text del llibre no fa servir. Les famílies amb variants marcades amb `redistributable: false`, i les que indiqui `svgFonts.withhold(family)`, en queden fora, i Postext en dona un avís `fontWithheld` per a cadascuna; una família sense variant genera un avís `svgFontUnavailable`, i les variants que superen `svgFonts.maxBytes` (2 MiB), un avís `svgFontsTooLarge`. `svgFonts.inline: false`, `diagramStyle.inlineFonts: false` i el `svg.inlineFonts: false` d'un recurs conserven els bytes tal com es donen. Una imatge sense bytes genera un avís `missingImage` i queda com un marc buit. `svgFonts.standIn(family)` (des de postext 1.43) indica una família oberta per substituir-ne una de retinguda: es demana a `svgFonts.provider` la cara d'aquella família amb el mateix pes i la mateixa inclinació, que entra a la imatge amb el nom de la família retinguda; si no la té, la família queda fora i se'n dona un avís.
- **`cover`**: `{ bytes, mediaType, alt?, showsFirstPage? }`, una imatge JPEG, PNG, WebP o SVG. Aleshores el llibre s'obre amb un document de coberta que la conté, i és la `cover-image` del paquet (la miniatura en una biblioteca). Sense coberta, la maquetació fixa marca la primera pàgina com a coberta i el llibre de maquetació fluida no té imatge de coberta. `showsFirstPage: true` indica que la imatge és una captura de la primera pàgina impresa: aleshores la maquetació fixa la fa servir només com a `cover-image` i s'obre en aquesta pàgina, que si no es veuria dues vegades; el llibre de maquetació fluida s'obre amb el document de coberta, com abans.
- **`kindlePanelView`**: en una maquetació fixa amb pàgines de còmic, hi afegeix Kindle Panel View, una zona de toc damunt de cada vinyeta que la mostra ampliada, amb les metadades que demana Kindle. Cada zona conté una còpia del còmic de la seva pàgina, de manera que cada pàgina creix una còpia per vinyeta; reserva-ho per als llibres destinats a Kindle. Per defecte, `false`. La navegació per regions, que pot fer servir qualsevol sistema de lectura, s'escriu en tots dos casos (vegeu [Sortida dels còmics](/ca/docs/comics#sortida-dels-còmics)).
- **`onProgress({ phase, done, total })`**: `resources` (lletres i imatges), `documents` (pàgines en la maquetació fixa, capítols en la fluida) i després `package`. **`signal`** interromp entre passos.
- **`readEpub(bytes)`** llegeix un fitxer per a un visor, sense `DOMParser`: maquetació, metadades, sentit de lectura, cada fitxer pel seu camí, el manifest, l'spine, l'índex, la llista de pàgines, el *viewport* de la maquetació fixa i la coberta. El lector del Sandbox s'hi basa.

Les dues maquetacions porten les metadades d'EPUB Accessibility 1.1 (modes d'accés, prestacions com l'índex i els números de pàgina impresos, riscos i un resum) i no declaren conformitat amb WCAG per defecte. La llista completa d'opcions i les limitacions són al [README del paquet](https://www.npmjs.com/package/postext-epub).

### Comprovar un fitxer amb EPUBCheck

[W3C EPUBCheck](https://www.w3.org/publishing/epubcheck/) és el validador de referència d'EPUB; les botigues de llibres electrònics hi passen els fitxers que reben. Amb l'eina instal·lada (`brew install epubcheck`, o la versió Java), `epubcheck llibre.epub` enumera errors, avisos i notes d'ús; les notes d'ús que deixa la sortida de Postext (`CSS-028`, `OBS-001`, `HTM_062`) són només informatives. Al repositori de Postext, `pnpm --filter postext-epub epubcheck` comprova els llibres de mostra de les proves; `node packages/postext-epub/scripts/epubcheck.mjs llibre.postext --layout both` maqueta un fitxer `.postext` o una carpeta de preset i en comprova les dues maquetacions, i `pnpm --filter postext-epub validate` recorre tota la matriu de llibres (la guia, els presets de mostra i llibres en xinès, en àrab i del Receptari), que passen tots sense errors ni avisos.

## Paquets SCORM (`postext-scorm`)

`postext-scorm` escriu un llibre, o els capítols i les seccions que se n'escullin, com un paquet SCORM: el zip que un sistema de gestió de l'aprenentatge (Moodle, Canvas, Blackboard, SCORM Cloud i la majoria dels altres) importa com un curs. El contingut és el de l'escriptor d'EPUB, pàgines fixes o text fluid, en forma de pàgines HTML5; cada part que segueix l'LMS porta al voltant un petit reproductor, i els exercicis que conté envien a l'LMS la puntuació, si s'ha completat i si s'ha aprovat. És l'escriptor que fa servir la pestanya **SCORM** del Sandbox.

```bash
npm install postext postext-epub postext-scorm
```

`postext` i `postext-epub` són dependències *peer*: actualitza tots tres paquets alhora.

### Escriure un paquet

```ts
import { openBundle, buildBundle } from 'postext';
import { renderToScorm, scormTree, scormOrganization, treeLeaves } from 'postext-scorm';

const bundle = await openBundle(fileBytes);
const docs = buildBundle(bundle);

// L'esquema del llibre: els capítols i els seus encapçalaments fins al tercer nivell.
const tree = scormTree(bundle.chapters.map((c) => ({ markdown: c.markdown, title: c.title })));
// El capítol 1 sencer i dues seccions del capítol 2.
const picked = new Set([tree[0]!, tree[1]!.children[0]!, tree[1]!.children[2]!].flatMap(treeLeaves).map((n) => n.id));

const zip = await renderToScorm(docs, {
  version: '1.2',
  layout: 'fixed',
  items: scormOrganization(tree, picked),
  metadata: { title: 'Llanterna', language: 'ca' },
  fonts, resourceBytes, // com a renderToEpub
});
```

- **`renderToScorm(docs, options): Promise<Uint8Array>`** escriu el zip. `docs` són els documents per capítol que rep `renderToEpub`. `options` és `{ version, layout, items?, metadata, fonts?, svgFonts?, resourceBytes?, cover?, passingScore?, onProgress?, onWarning?, signal? }`; `metadata`, `fonts`, `svgFonts`, `resourceBytes` i `cover` són els de l'escriptor d'EPUB.
- **`version`**: `'1.2'` o `'2004'` (SCORM 2004, 4a edició). Tots els LMS accepten SCORM 1.2. SCORM 2004 separa la compleció de l'èxit, dona una puntuació escalada i desa fins a 64.000 caràcters de respostes, mentre que SCORM 1.2 en desa 4.096; tria'l quan l'LMS l'accepti i això importi.
- **`layout`**: `'fixed'`, cada pàgina impresa ajustada a la finestra, o `'reflowable'`, el text recompost per a la finestra, com a [Maquetació fixa i maquetació fluida](#maquetació-fixa-i-maquetació-fluida).
- **`items`**: l'organització que mostra l'LMS, un arbre de `{ title, doc?, range?, children? }`. Un element amb `children` els agrupa; un element sense és un SCO, una part que l'LMS obre, segueix i qualifica per separat: el capítol `doc` sencer o el tram `range` (`{ start, end? }`, posicions al Markdown del capítol tal com és escrit, amb el front matter inclòs). Sense `items`, cada capítol és un SCO.
- **`scormTree(chapters, config?)`** enumera els capítols i els seus encapçalaments dels nivells 1 a 3, cadascun amb el tram que representa: des de la seva línia fins al següent encapçalament del seu nivell o superior. El primer encapçalament dins d'un capítol o d'un altre encapçalament s'emporta també el text que el precedeix, de manera que el títol i els paràgrafs inicials d'un capítol van amb la primera secció. **`scormOrganization(tree, picked)`** converteix un conjunt d'ids de fulles triades en `items`: un node triat sencer és un SCO; un de triat en part agrupa els elements dels seus fills. `treeLeaves(node)` i `pickState(node, picked)` (`'all'`, `'some'`, `'none'`) ajuden a fer un arbre amb caselles.
- **`passingScore`**: el percentatge de respostes qualificades correctes amb què s'aprova, per damunt del `exercises.digital.passingScore` dels documents. `0` o cap valor: ni aprovat ni suspès.

Un SCO de maquetació fixa conté totes les pàgines impreses que toca la seva part, de manera que una pàgina que comparteixen dues parts apareix a totes dues. Un SCO de maquetació fluida conté exactament el text de la seva part, tallat pels encapçalaments. Els enllaços de les pàgines d'un SCO a les d'un altre es treuen, perquè un LMS segueix un SCO pel que obre. El reproductor mostra un document cada vegada, amb ← i → (o Re Pàg i Av Pàg a les pàgines fixes), l'índex de l'SCO i la posició; un llibre enquadernat per la dreta passa les pàgines cap a l'esquerra.

### Què arriba a l'LMS

El reproductor busca l'API de l'LMS tal com demana SCORM (`API` a SCORM 1.2, `API_1484_11` a SCORM 2004, pujant per la cadena de finestres pare i després a la finestra que l'ha obert) i hi envia:

- **Puntuació.** Un exercici compta la seva última comprovació: les respostes qualificades correctes sobre el total de respostes qualificades, la puntuació que mostra la seva barra. La puntuació d'un SCO és la suma de les respostes correctes sobre la suma de les respostes qualificades dels seus exercicis, de manera que un mot encreuat de vint caselles pesa més que un vertader o fals; un exercici que no s'ha comprovat mai no suma cap resposta correcta. SCORM 1.2 la rep com a percentatge (`cmi.core.score.raw`, de 0 a 100); SCORM 2004, com a fracció (`cmi.score.scaled`), amb les respostes com a `raw` i `max`. Un exercici pertany a la part on és el seu bloc: només aquest SCO el compta, encara que la seva pàgina aparegui també en un SCO veí.
- **Compleció.** Un SCO queda completat quan s'han mostrat totes les seves pàgines o documents i s'han comprovat tots els exercicis que compta (o ja no els queden comprovacions). Fins aleshores és incomplet, i l'LMS guarda el punt de lectura per a la visita següent.
- **Èxit.** Amb una nota per aprovar, un SCO completat queda aprovat o suspès segons aquesta nota. El manifest la porta (`adlcp:masteryscore` a SCORM 1.2, un objectiu principal amb `minNormalizedMeasure` a SCORM 2004), i el reproductor pren el valor que li torna l'LMS, de manera que, si l'LMS en fixa una de pròpia, mana la de l'LMS.
- **Interaccions.** Cada comprovació escriu l'exercici com una interacció: un identificador tret de la seva àncora o del seu número, un tipus d'interacció segons el tipus d'exercici (`true-false`, `choice`, `fill-in`, `other`), la resposta del lector, la correcta, el resultat i un pes segons les seves respostes qualificades; SCORM 2004 hi afegeix una descripció i desa una interacció per exercici, i SCORM 1.2 n'afegeix una per comprovació.
- **Agregació.** SCORM 2004 pondera al manifest la mesura de cada SCO per les seves respostes qualificades, de manera que la puntuació del curs és el total de respostes correctes sobre el total de respostes qualificades. SCORM 1.2 no té agregació pròpia: decideix el mètode de qualificació de l'LMS (Moodle ofereix la més alta, la mitjana o la suma de les puntuacions dels SCO).
- **Respostes.** Van a `cmi.suspend_data` amb les comprovacions i els reinicis gastats, de manera que els límits d'un intent ([Avaluació](/ca/docs/configuration-exercises#avaluació)) es mantenen entre visites i dispositius. Si passen dels 4.096 caràcters de SCORM 1.2, els comptadors continuen arribant a l'LMS i les respostes es queden al navegador del lector.

Obert fora d'un LMS (la pàgina d'inici sola, o el paquet en un servidor web), el reproductor no troba cap API: el llibre es llegeix igual i els exercicis desen les respostes al navegador, com en un llibre HTML o EPUB.

### Comprovar un paquet

Les proves validen amb `xmllint` els manifests de totes dues versions contra els esquemes d'IMS i ADL. Per provar un paquet, importa el zip en un LMS (l'activitat SCORM de Moodle accepta totes dues versions) o a [SCORM Cloud](https://cloud.scorm.com/). També serveix un substitut local: [scorm-again](https://github.com/jcputney/scorm-again) ofereix les API de SCORM 1.2 i 2004 en una pàgina que emmarca la pàgina d'inici, i rebutja els valors que el model de dades no admet.
