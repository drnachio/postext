# Configuration : utilisation programmatique


## Utilisation programmatique

> **Voie recommandée : utilisez le Web Worker.** Dans un navigateur, mettez en page par `createLayoutWorker()` de `postext/worker` plutôt qu’en appelant `buildDocument` sur le thread principal. Le worker garde la page réactive pendant la mise en page, conserve les mesures du texte d’une mise en page à l’autre et annule celle qui est en cours quand une plus récente commence : une frappe n’attend jamais la mise en page d’un texte plus ancien. La recette est dans [Mise en page dans un Web Worker](#mise-en-page-dans-un-web-worker). Le reste de cette section (`buildDocument` en direct, résolveurs, fonctions de nettoyage, caches) reste valable : le worker prend les mêmes entrées et rend les mêmes sorties. N’appelez `buildDocument` sur le thread principal que pour un export ponctuel, le rendu côté serveur (Node) ou les tests.

### Construire un document

La fonction `buildDocument` exécute toute la chaîne de mise en page et renvoie un arbre de document virtuel (VDT) avec les coordonnées précises de chaque élément. C’est le point d’entrée de plus bas niveau ; le code d’interface doit lui préférer l’[enveloppe Web Worker](#mise-en-page-dans-un-web-worker), qui appelle `buildDocument` dans un thread de worker dédié avec les mêmes arguments.

```ts
import { buildDocument } from 'postext';

const content = {
  markdown: '# Chapter One\n\nThe story begins here...',
};

const config = {
  page: { sizePreset: '17x24' },
  layout: { layoutType: 'double' },
  bodyText: { fontFamily: 'EB Garamond', fontSize: { value: 9, unit: 'pt' } }, // 9 pt overrides the 8 pt default
};

// Build the layout — produces a VDT with one entry per page in `vdt.pages`
const vdt = buildDocument(content, config);
console.log(`Document has ${vdt.pages.length} pages`);
```

### Avertissements dans le document

`buildDocument` ne s’arrête pas sur une référence erronée ou sur un style inconnu : il applique une solution de repli et consigne ce qu’il a fait dans `doc.contentWarnings`. Les encadrés que la mise en page a dû forcer se trouvent dans `doc.warnings`, qui garde la forme qu’il avait dans postext 1.4 : chaque entrée y est un `calloutOverflow` avec ses `pageIndex`, `columnIndex` et `overflowPx`. Chaque champ est absent lorsqu’il n’y a rien à signaler. Chaque entrée a un `kind`. Les avertissements de contenu indiquent la position dans la source de l’élément de syntaxe concerné (`sourceStart` / `sourceEnd`, des positions dans le Markdown que vous avez passé, en-tête YAML compris) et, lorsque cet élément est tombé sur une page, son `pageIndex`.

Les types propres à une fonctionnalité sont décrits avec elle : la bande dessinée (`comicPanelCount`, `comicBalloonOverflow`…) sur la page [Bande dessinée](/fr/docs/comics), les vidéos (`videoWithoutUrl`, `videoUrlInvalid`, `videoWithoutPoster`) dans [Ressources](/fr/docs/document-format-resources), les citations et l’index (`unknownCitationKey`, `referencesUnreadable`, `indexMark`…) dans [Notes et références](/fr/docs/document-format-notes-references), le texte chinois, japonais et arabe (`cjkLooseLine`, `rubyExceedsLeading`, `arabicMarksExceedLeading`…) sur les pages de ces écritures, et ceux de l’algorithme de coupure des lignes (`raggedLine`, `unbreakableWordOverflow`, `wordDividedByCharacter`, `wordDividedBySyllable`) dans [Justification](/fr/docs/justification).

Les avertissements qui concernent une ressource (son style de tableau, sa grille, une référence dans sa légende, sa note ou ses cellules) pointent sur la première insertion ou la première référence de la ressource dans le texte, et chacun n’est listé qu’une fois par ressource. Seules les ressources que le document utilise sont vérifiées : un chapitre d’un livre signale les tableaux qu’il cite, pas tous les tableaux du livre.

```ts
import { buildDocument, formatWarning } from 'postext';

const doc = buildDocument({ markdown: 'See :ref{id="fig-map"}.\n\n:::sidebar\nNotes.' }, config);
for (const w of [...(doc.warnings ?? []), ...(doc.contentWarnings ?? []), ...(doc.configWarnings ?? [])]) console.warn(formatWarning(w));
// Unknown resource id "fig-map" in :ref — it prints "?" (or its text= label), with no number or link (page 1, offset 4)
// Unknown directive ":::sidebar" — the line is set as text (page 1, offset 25)

// Narrow on `kind` to read the fields of a kind.
const missing = (doc.contentWarnings ?? []).flatMap((w) => (w.kind === 'unknownResourceId' ? [w.resourceId] : []));
```

`formatWarning(w)` renvoie une description d’une ligne en anglais. Un hôte qui localise ses messages s’appuie plutôt sur `kind`, en gardant une branche par défaut, car des versions mineures peuvent ajouter des types. `collectContentWarnings(markdown, config, resources)` renvoie les avertissements de contenu sans rien mettre en page (la liste qu’ajoute la construction, sans `pageIndex`), pour un éditeur qui vérifie le texte pendant la saisie. `collectHeadingDesignCuts(doc)` cherche dans une mise en page terminée les maquettes de titre dont le texte dépasse le pied de leur page ou de leur colonne (`kind: 'headingDesignCut'` ; voir [Hauteur réservée](/fr/docs/configuration-headings#hauteur-réservée)), ce que la mise en page elle-même ne signale pas, et `formatWarning` décrit aussi ses résultats. Le panneau **Vérifications** du Sandbox les liste tous.

Les moteurs de rendu signalent ce qu’ils ne peuvent pas peindre comme demandé par une option `onWarning` : `renderPageToCanvas`, `renderPage` et `renderToCanvas` (`RenderPageOptions`), `renderToHtml` et `renderToHtmlIndexed` (`RenderHtmlOptions`), et `renderToPdf` (`RenderToPdfOptions`, aussi par le worker PDF). Le principal type d’avertissement de rendu est `missingImage` : une image (une figure, l’image d’une cellule de tableau, une icône d’encadré, une image de maquette) qui n’a rien à dessiner est peinte comme un espace réservé neutre et signalée, une fois par `fileId` et par appel de rendu, avec son `pageIndex`, le `resourceId` quand le code de peinture le connaît (figures et images de cellule) et, dans le PDF, le `documentIndex` d’un rendu de plusieurs documents. « Rien à dessiner » signifie : aucun `registerResourceImage` pour le `fileId` dans le canvas, aucune URL renvoyée par `resourceImageUrl` en HTML, et aucun octet fourni par `resourceBytes` (ou des octets qui ne se décodent pas) dans le PDF. Une ressource bitmap ou SVG qui n’indique aucun `fileId` n’a rien à demander : elle est dessinée comme un espace réservé, sans signalement. Deux autres types viennent des hôtes qui incorporent des polices dans des images SVG (`registerSvgImage`, `registerBundleImages`, `bundleImageUrl`, `renderToHtml` avec `inlineSvgFonts`, postext-epub ; voir [Polices du texte SVG](/fr/docs/configuration-resources#polices-du-texte-svg)), avec le `fileId` et le `resourceId` de l’image : `svgFontUnavailable` (`family`, `weight`, `style`), une famille qu’utilise son texte mais qu’aucune police disponible ne permet d’incorporer, l’image composant alors ce texte dans une police de repli ; et `svgFontsTooLarge` (`bytes`, `maxBytes`), des polices au-delà du plafond de taille, dont aucune n’est incorporée. Les avertissements de rendu ne sont pas stockés dans le VDT : ce qu’un hôte peut fournir change après la mise en page.

```ts
import { buildDocument, renderPage, type RenderWarning, type Resource } from 'postext';

const map: Resource = {
  id: 'fig-map', typeId: 'figure', kind: 'bitmap', caption: 'The route.', createdAt: 0, updatedAt: 0,
  bitmap: { fileId: 'map-file', format: 'png', width: 1200, height: 800 },
};
const doc = buildDocument({ markdown: 'See :ref{id="fig-map"}.', resources: [map] }, config);

const warnings: RenderWarning[] = [];
const canvas = renderPage(doc.pages[0], doc, { onWarning: (w) => warnings.push(w) });
// Until 'map-file' is registered with registerResourceImage:
// [{ kind: 'missingImage', fileId: 'map-file', resourceId: 'fig-map', pageIndex: 0 }]
```

### Rendre une page en bitmap

Chaque page peut être rastérisée indépendamment. Utilisez `renderPage(page, doc)` pour obtenir un `HTMLCanvasElement` pour un numéro de page donné : le canvas est un bitmap aux dimensions exactes de la page en pixels (à la résolution configurée), que vous pouvez afficher, exporter ou passer à n’importe quelle chaîne de traitement d’images :

```ts
import { buildDocument, renderPage } from 'postext';

const vdt = buildDocument(content, config);

// Render page 3 (zero-indexed) to a bitmap canvas
const pageNumber = 2;
const page = vdt.pages[pageNumber];
if (!page) throw new Error(`Page ${pageNumber} does not exist`);

const canvas = renderPage(page, vdt);
// canvas.width / canvas.height are the page bitmap size in pixels

// Show it in the DOM
document.body.appendChild(canvas);

// …or export it as a PNG data URL
const pngDataUrl = canvas.toDataURL('image/png');

// …or get a Blob for download / upload
canvas.toBlob((blob) => {
  if (blob) saveAs(blob, `page-${pageNumber + 1}.png`);
}, 'image/png');

// …or grab raw RGBA pixels
const ctx = canvas.getContext('2d')!;
const imageData = ctx.getImageData(0, 0, canvas.width, canvas.height);
```

Si vous préférez dessiner dans un canvas que vous possédez déjà (par exemple un canvas attaché au DOM avec une mise en page précise), utilisez `renderPageToCanvas(page, doc, canvas)` : il redimensionne le canvas que vous lui passez et y peint, au lieu d’en créer un nouveau.

Pour rendre toutes les pages, parcourez `vdt.pages` :

```ts
const bitmaps = vdt.pages.map((page) => renderPage(page, vdt));
```

### React

`postext/react` exporte `createLayout(content, config?)` : un composant qui met le document en page une seule fois, au montage, et affiche chaque page sous forme de `<canvas>` dans une `<div>`.

```tsx
import { createLayout } from 'postext/react';

const Article = createLayout(
  { markdown: '# Hello\n\nThe first paragraph of the article.' },
  { page: { sizePreset: '17x24' } },
);

export function ArticlePage() {
  return <Article className="pages" style={{ maxWidth: 480 }} />;
}
```

- **Sur le thread principal, une seule fois.** Les pages sont peintes à la résolution du document et mises à l’échelle à la largeur du conteneur. `content` et `config` sont fixés au moment où vous appelez `createLayout` ; créez un autre composant pour afficher autre chose. Pour un aperçu en direct, construisez dans le [Web Worker](#mise-en-page-dans-un-web-worker) et peignez avec `renderPageToCanvas`, comme dans l’exemple React de cette section.
- **Les polices et les images d’abord.** Chargez les polices web du document avant le montage du composant, et enregistrez ses images avec `registerResourceImage`. Lorsque le Markdown contient un `$`, le composant démarre lui-même le [moteur mathématique](/fr/docs/configuration-lists-math#démarrer-le-moteur-mathématique).
- **React reste hors du point d’entrée principal.** `postext` n’importe jamais React ; seul `postext/react` le fait. `createLayout` est toujours exporté depuis `postext` pour que le code existant continue de fonctionner, mais il est déprécié : il charge `postext/react` quand vous l’appelez, et le composant se suspend jusqu’à son arrivée (React le rend de nouveau de lui-même). Importez-le depuis `postext/react`.
- **Le composant déprécié se suspend.** Tant que `postext/react` n’est pas arrivé, le `createLayout` de `postext` a besoin d’une racine concurrente (`createRoot`) ou d’une frontière `<Suspense>` au-dessus de lui. Dans une racine `ReactDOM.render` historique, ou dans `renderToString`, sans frontière, React signale une erreur à la place. `react` reste une dépendance pair obligatoire, afin que les bundlers puissent résoudre cet import différé.

### Résoudre les valeurs par défaut

Les fonctions de résolution complètent les objets de configuration partiels avec les valeurs par défaut. C’est utile lorsque vous avez besoin d’une configuration complète pour l’inspecter ou la comparer :

```ts
import { resolvePageConfig, resolveBodyTextConfig } from 'postext';

const fullPage = resolvePageConfig({ sizePreset: '21x28' });
// => { sizePreset: '21x28', width: { value: 21, unit: 'cm' }, height: { value: 28, unit: 'cm' },
//      margins: { top: { value: 2, unit: 'cm' }, ... }, dpi: 300, cutLines: { enabled: false, ... }, ... }

const fullBody = resolveBodyTextConfig({ fontFamily: 'Inter' });
// => { fontFamily: 'Inter', fontSize: { value: 8, unit: 'pt' }, lineHeight: { value: 1.5, unit: 'em' }, ... }
```

Résolveurs disponibles, un par section de premier niveau : `resolvePageConfig`, `resolveLayoutConfig`, `resolveBodyTextConfig`, `resolveHeadingsConfig`, `resolveHeadingStylesConfig`, `resolveTocConfig`, `resolvePartsConfig`, `resolveUnorderedListsConfig`, `resolveOrderedListsConfig`, `resolveMathConfig`, `resolveTableStyleConfig`, `resolveCaptionStyleConfig`, `resolveDiagramStyleConfig`, `resolveParagraphStylesConfig`, `resolveCalloutStylesConfig`, `resolveHeaderFooterConfig`, `resolveDebugConfig`, `resolveHtmlViewerConfig`, `resolvePdfGenerationConfig`, plus `resolveDesignSlot` pour une seule zone de maquette. Les palettes de couleurs s’appliquent séparément par `applyPaletteToConfig(config)`, `applyPaletteToResolvedConfig(resolved, palette)` et `resolveColorValue(value, palette, fallback)` : voir [Palette de couleurs](/fr/docs/configuration-fonts-colors-viewers#palette-de-couleurs).

Les résolveurs dont les valeurs par défaut découlent d’une autre section prennent cette section, déjà résolue, comme argument supplémentaire. `resolveUnorderedListsConfig` et `resolveOrderedListsConfig` prennent le texte courant résolu, car les valeurs par défaut des listes pour `fontFamily` et `color` en découlent ; `resolveCalloutStylesConfig` prend le texte courant, les titres et les listes à puces résolus (voir l’exemple dans [Styles d’encadré](/fr/docs/configuration-callouts#styles-dencadré)), et `resolveHeadingStylesConfig` la page, le texte courant et les deux sections de listes résolus. Consultez les déclarations de types du paquet npm pour la signature exacte de chacun :

```ts
import { resolveBodyTextConfig, resolveUnorderedListsConfig } from 'postext';

const body = resolveBodyTextConfig({ fontFamily: 'Inter' });
const lists = resolveUnorderedListsConfig({ bulletChar: '—' }, body);
// => lists.fontFamily === 'Inter' (inherited)
```

Les jeux de valeurs par défaut statiques (les valeurs utilisées quand aucune cascade n’intervient) sont aussi exportés : `DEFAULT_PAGE_CONFIG`, `DEFAULT_CUT_LINES`, `DEFAULT_PAGE_NUMBERING`, `PAGE_SIZE_PRESETS`, `DEFAULT_LAYOUT_CONFIG`, `DEFAULT_COLUMN_RULE`, `DEFAULT_COLUMN_BALANCING`, `DEFAULT_BODY_TEXT_CONFIG`, `DEFAULT_HYPHENATION_CONFIG`, `DEFAULT_HEADINGS_CONFIG`, `DEFAULT_UNORDERED_LISTS_STATIC`, `DEFAULT_ORDERED_LISTS_STATIC`, `DEFAULT_PARAGRAPH_STYLES`, `DEFAULT_CALLOUT_STYLES`, `DEFAULT_CALLOUT_STYLE_STATIC`, `DEFAULT_PARTS_CONFIG`, `DEFAULT_HEADING_STYLES`, `DEFAULT_TOC_CONFIG`, `DEFAULT_MATH_CONFIG`, `DEFAULT_DIAGRAM_STYLE_CONFIG`, `DEFAULT_DEBUG_CONFIG`, `DEFAULT_HTML_VIEWER_CONFIG`, `DEFAULT_PDF_GENERATION_CONFIG`, `DEFAULT_COLOR_PALETTE`, `DEFAULT_MAIN_COLOR`, `DEFAULT_MAIN_COLOR_ID`, `DEFAULT_MAIN_COLOR_NAME`, `DEFAULT_MAIN_COLOR_HEX`, plus les valeurs par défaut des éléments d’en-tête et de pied de page (`DEFAULT_HEADER_FOOTER_SLOT`, `DEFAULT_HEADER_SLOT`, `DEFAULT_FOOTER_SLOT`, `DEFAULT_TEXT_ELEMENT`, `DEFAULT_RULE_ELEMENT`, `DEFAULT_BOX_ELEMENT`) et `defaultResourceTypes(locale)`, qui dépend de la langue (voir [Types de ressources](/fr/docs/configuration-resources#types-de-ressources)).

### Élaguer les valeurs par défaut

Lorsque vous enregistrez une configuration (par exemple dans localStorage ou dans un fichier), utilisez `stripConfigDefaults` pour retirer les valeurs égales aux valeurs par défaut. Les configurations stockées restent ainsi minimales, seules les modifications voulues étant enregistrées :

```ts
import { stripConfigDefaults } from 'postext';

const minimal = stripConfigDefaults(fullConfig);
// Only properties that differ from defaults remain
```

Des fonctions d’élagage individuelles existent aussi, une par résolveur : `stripPageDefaults`, `stripLayoutDefaults`, `stripBodyTextDefaults`, `stripHeadingsDefaults`, `stripHeadingStylesDefaults`, `stripTocDefaults`, `stripPartsDefaults`, `stripUnorderedListsDefaults`, `stripOrderedListsDefaults`, `stripMathDefaults`, `stripTableStyleDefaults`, `stripCaptionStyleDefaults`, `stripDiagramStyleDefaults`, `stripParagraphStylesDefaults`, `stripCalloutStylesDefaults`, `stripHeaderFooterDefaults`, `stripDesignSlotDefaults`, `stripDebugDefaults`, `stripHtmlViewerDefaults`, `stripPdfGenerationDefaults`.

Certaines valeurs par défaut dépendent du reste de la configuration : l’équilibrage des colonnes est désactivé sur une grille de caractères et en texte vertical, `bodyText.avoidWidows` est désactivé sur une grille de caractères (et `bodyText.avoidOrphans` aussi dans la région `japan`), et les notes de bas de page, les légendes et l’index suivent la langue du document. `stripConfigDefaults` compare chaque valeur à la valeur par défaut de la configuration qu’on lui donne : `headings.balancing.enabled: true` est donc conservé là où l’équilibrage est désactivé par défaut, et `false` y est supprimé. `bodyText.avoidWidows: true` est conservé de la même façon sur une grille de caractères. Une fonction d’élagage appelée seule reçoit ce contexte en arguments : `stripHeadingsDefaults(headings, balancingOnByDefault(config))`, `stripIndexDefaults(index, locale)`, `stripCaptionStyleDefaults(captionStyle, locale)`, `stripFootnotesDefaults(footnotes, locale, writingMode)`, `stripBodyTextDefaults(bodyText, locale, avoidWidowsByDefault(config), avoidOrphansByDefault(config))`.

Une valeur qui signifie « rien » est conservée partout où « rien » n’est pas la valeur par défaut. Un style de titre reprend l’en-tête et le pied de page du document lorsqu’il n’en définit pas : un style qui les vide (`footer: { elements: [] }` sur une couverture) garde donc la zone vide, et ses `margins`, `layout` et `bodyStyle` sont conservés même vides. Un niveau de titre ramené à sa valeur par défaut alors que les valeurs communes à tous les titres diffèrent garde sa valeur. `calloutStyles: []` et `chipStyles: []` restent des listes vides : omis, le style intégré reviendrait. Dans tous les cas, `resolveAllConfig(stripConfigDefaults(config))` donne la même résolution que `resolveAllConfig(config)`.

### Analyse

Le moteur expose son analyseur Markdown et son lecteur d’en-tête YAML. Utilisez-les pour inspecter un document avant de le construire, ou pour alimenter d’autres outils avec la même structure de blocs que celle que voit Postext :

```ts
import { parseMarkdown, extractFrontmatter } from 'postext';

const source = '---\ntitle: Chapter One\n---\n\n# Opening\n\nThe story begins here.';

const { metadata, content } = extractFrontmatter(source);
// metadata.title === 'Chapter One'

const blocks = parseMarkdown(content);
// => [ { type: 'heading', level: 1, text: 'Opening', … },
//      { type: 'paragraph', text: 'The story begins here.', … } ]
```

Voir la page [Format du document](/fr/docs/document-format) pour la liste complète des éléments de syntaxe Markdown que Postext reconnaît.

### Carte des sources d’un document mis en page

`sourceAt(doc, pageIndex, x, y, options?)` renvoie ce que montre un point d’une page, de l’intérieur vers l’extérieur, chaque élément avec son `id` stable, sa `source` (un passage du Markdown, un pointeur JSON de la configuration, un attribut du délimiteur de page ou une ressource) et son `rect`. `elementsForSource(doc, start, end, options?)` renvoie ce qu’est devenu un passage du Markdown, page par page, et `findElement(doc, id)` retrouve un élément après une nouvelle mise en page. Ces fonctions lisent ce que la mise en page a inscrit dans le VDT et ne mettent rien en page. `composedPagePaintKey(page)` indique si une page composée peint ce qu’elle a peint auparavant. Les types de source, les identifiants et la façon dont une page composée n’est remise en page que là où elle a changé sont décrits dans [Pages composées › Carte des sources](/fr/docs/composed-pages#carte-des-sources).

### Charger les polices avant la mise en page

La mise en page mesure le texte avec les polices dont dispose le jeu de polices au moment où elle s’exécute. `prepareFonts` charge, avant la première construction, toutes les polices que demandent une configuration et son texte : le texte courant, les titres, les listes, les titres et le corps des encadrés, les tableaux, les textes de maquette, les titres courants, la table des matières, le code et le lettrage de bande dessinée, dans chaque graisse et chaque inclinaison que définit la configuration (les quatre de la famille du texte courant, puisque `**` et `*` y composent le gras et l’italique). Chaque police est chargée pour les caractères que le document compose : une famille servie en tranches `unicode-range` (latin étendu, grec, arabe, les tranches CJK de Google Fonts et de Fontsource) apporte donc les fichiers dont le texte a besoin.

```ts
import { prepareFonts, buildDocument, buildDocumentWithFonts } from 'postext';

// The host's files: the PDF font provider's contract, so one function serves both.
async function resolve(family: string, weight: number, style: 'normal' | 'italic') {
  const id = family.toLowerCase().replace(/\s+/g, '-');
  return `https://cdn.jsdelivr.net/npm/@fontsource/${id}@5/files/${id}-latin-${weight}-${style}.woff2`;
}

const report = await prepareFonts(content, config, { resolve });
// report.loaded, report.missing, report.synthesized: { family, weight, style }[]
const doc = buildDocument(content, config);

// Or in one call: prepare, build, load any face the pages used that was not there, build again.
const same = await buildDocumentWithFonts(content, config, { resolve });
```

- **Les polices que la page déclare** (une règle `@font-face`, une `FontFace` déjà ajoutée) sont chargées par le jeu de polices (`document.fonts.load`, ou `self.fonts` dans un worker). **Celles qu’elle ne déclare pas** sont demandées à `resolve(family, weight, style, { text, codePoints })`, qui répond par un fichier (des octets, ou une URL), par plusieurs fichiers (les tranches d’une police), par `{ source, unicodeRange, weight, style }` pour une tranche ou une plage variable, ou par `null`. Le moteur les ajoute comme `FontFace` une fois que toutes sont chargées, dans l’ordre de la configuration et de chaque réponse (latin, puis latin-ext, puis greek quand le résolveur répond ainsi) : le jeu de polices est donc le même quel que soit l’ordre d’arrivée des fichiers. Il les enregistre aussi dans le registre de polices que lisent les [images SVG](/fr/docs/configuration-resources#polices-du-texte-svg) et les workers de mise en page. Un résolveur peut déclarer la police lui-même (en ajoutant une feuille de style) et répondre `null`.
- **Le rapport** liste dans `loaded` les polices couvertes par une police chargée (ou par une famille installée), dans `missing` celles qui manquent encore, et dans `synthesized` celles que le navigateur dessinerait à partir d’une autre graisse ou inclinaison ; `added` compte les `FontFace` ajoutées à partir des fichiers du résolveur. `timeoutMs` (10 000 par défaut) borne l’attente ; une police encore en cours de chargement compte alors comme manquante. Là où il n’y a pas de jeu de polices (Node), `prepareFonts` ne fait rien et signale toutes les polices comme chargées.
- **`buildDocumentWithFonts(content, config, options)`** prépare, construit avec `buildDocumentAsync`, lit les polices dans lesquelles les pages composent réellement du texte, charge celles que le jeu de polices n’a pas pu fournir (une graisse que seules les pages révèlent est demandée à `resolve` même si une autre graisse de la famille pourrait la remplacer), puis reconstruit (deux constructions supplémentaires au plus). `withLoadedFonts(build, options)` fait de même autour de n’importe quelle fonction de construction, pour un livre construit chapitre par chapitre ou pour un paquet (`buildBundle`) qui renvoie plusieurs documents. `options.onFonts` reçoit le rapport final.
- **Après la construction**, chaque police dans laquelle le texte a été composé et que le jeu de polices n’a pas pu fournir figure dans `doc.contentWarnings` sous la forme `fontFallback` (voir [Avertissements dans le document](#avertissements-dans-le-document)).

**Styles de chiffres.** Un style doté d’un [`figureStyle`](/fr/docs/configuration-fonts-colors-viewers#styles-de-chiffres) compose son texte dans une famille à fonctionnalités : le nom de la famille de base suivi de ses fonctionnalités OpenType après `@` (`EB Garamond@onum`). `prepareFonts` et `resolve` reçoivent la demande de la famille de base, et le moteur déclare les fontes de la famille à fonctionnalités à partir des mêmes fichiers, avec le descripteur `featureSettings`. Le `FontPayload` d’un worker de mise en page accepte un `featureSettings` facultatif pour une telle fonte, avec la famille à fonctionnalités pour `family` et le fichier de la famille de base pour tampon. `configFeatureFamilies(config)` liste les familles à fonctionnalités dans lesquelles une configuration compose du texte. Un hôte qui compose du texte dans des polices dont il n’a pas les fichiers nomme avec `setFigureStyleFamilies((family) => boolean)` les familles qui peuvent prendre des fonctionnalités ; les autres gardent leurs propres chiffres. `baseFontFamily` et `featureFamilyParts` décomposent un tel nom, `withFigureStyle(fontFamily, figureStyle)` le construit, et `freezeFontFeatures(bytes, features)` renvoie une copie d’un fichier TrueType ou OpenType dont la `cmap` envoie les caractères vers les glyphes que donnent les substitutions simples des fonctionnalités, pour un canvas qui n’applique aucune fonctionnalité (Skia sous Node).

Les polices qui arrivent plus tard sont prises en compte d’elles-mêmes. Le moteur garde, pour chaque jeu de polices, la liste des polices de chaque famille qui étaient chargées lors de sa dernière vérification ; une construction vérifie de nouveau à son début (seulement si le jeu a grandi ou diminué, est en cours de chargement ou vient de finir de charger une police) et abandonne ce qui a été mesuré dans les familles dont les polices ont changé. `watchFonts(fontSet)` fait de même au fil du chargement des polices, au plus une fois par image d’animation quel que soit le nombre de tranches qu’apporte une rafale, et `onFontsChanged(listener)` indique à l’hôte quelles familles ont changé, pour qu’il puisse refaire la mise en page :

```ts
import { watchFonts, onFontsChanged } from 'postext';

const stop = watchFonts();                         // document.fonts by default
const off = onFontsChanged((families) => relayout());
```

`prepareFonts` lance la surveillance sur le jeu dans lequel il charge les polices (`watch: false` la laisse désactivée).

### Cache de mesures

La mesure du texte est l’étape coûteuse de la mise en page. Deux sortes de cache la gardent bon marché :

- **Un cache de blocs qui vous appartient.** `createMeasurementCache()` renvoie un `MeasurementCache` qui mémorise chaque paragraphe mesuré, indexé par son texte, ses polices, sa largeur, ses options de coupure des lignes et le dictionnaire de césure actif. Passez-le comme troisième argument de `buildDocument` (ou de `buildDocumentAsync`) pour réutiliser les mesures entre les passes de placement d’une construction et d’une construction à l’autre : un éditeur qui met le document en page à chaque frappe ne mesure alors que les paragraphes qui ont changé. Sans lui, chaque passe mesure de nouveau chaque bloc. Un paragraphe lu dans le cache est identique à un paragraphe mesuré à neuf : une construction avec cache compose donc chaque ligne comme une construction sans cache ; dans postext 1.4.1, un paragraphe en cache perdait la marque de sa ligne creuse, et le resserrement des lignes creuses ainsi que l’équilibrage des colonnes pouvaient alors le couper autrement. Le cache garde la génération de mesure sous laquelle il a été rempli : lorsque des polices d’une famille arrivent ou disparaissent, sa consultation suivante abandonne les blocs composés dans cette famille. Un cache conservé pendant des chargements de polices ne sert donc jamais de lignes mesurées avec une police de repli.
- **Les caches globaux de largeurs.** Les largeurs de mots sont mises en cache par chaîne de police dans un état de module que partagent toutes les constructions de la page, et pretext tient son propre cache. Le moteur abandonne les largeurs d’une famille lorsque ses polices changent (au début d’une construction, depuis `watchFonts`, depuis `prepareFonts` et `loadBundleFonts`) ; le cache de pretext n’a pas d’index par famille et il est vidé en entier.

```ts
import { buildDocument, createMeasurementCache, evictFontFamilies, clearMeasurementCache } from 'postext';

const cache = createMeasurementCache();
let doc = buildDocument(content, config, cache);

// A face of "EB Garamond" was added to document.fonts: the next build sees it,
// with the same cache, and measures that family again.
doc = buildDocument(content, config, cache);

// A host that changes faces the engine cannot see (a font set of its own) says so:
evictFontFamilies(['EB Garamond']);   // that family's widths and cached blocks
clearMeasurementCache();              // every family
```

Pour les applications qui mesurent le texte morceau par morceau, `cachedMeasureBlock(text, font, maxWidthPx, lineHeightPx, options, cache)` et `cachedMeasureRichBlock(spans, normalFont, boldFont, italicFont, boldItalicFont, maxWidthPx, lineHeightPx, options, cache)` prennent les arguments de `measureBlock` et de `measureRichBlock`, plus le cache, en dernier.

### Le module de coupure des lignes (WebAssembly)

Les paragraphes sont coupés en lignes par Knuth–Plass. Depuis postext 1.33, le moteur l’exécute dans un module de coupure des lignes écrit en Rust et compilé en WebAssembly (30 Ko, inclus dans le paquet npm). Il choisit les mêmes coupures que le module TypeScript, avec la même arithmétique dans le même ordre, et un livre entier se met en page environ 15 % plus vite. Rien n’est à configurer :

- Dans un worker, dans Node et dans Bun, le module est compilé au premier paragraphe.
- Sur le thread principal d’une page, où un navigateur ne compile un module de cette taille que de façon asynchrone, il se compile en arrière-plan et le module TypeScript répond en attendant. `await initLineBreaker()` avant la première mise en page le met au travail dès le premier paragraphe ; la promesse se résout à `false` là où WebAssembly n’est pas disponible.
- Là où WebAssembly manque, ou là où une Content Security Policy le refuse (`script-src` sans `'wasm-unsafe-eval'`), le module TypeScript répond pour chaque paragraphe.

Les deux choisissent les mêmes coupures : le module qui a répondu ne change donc jamais une mise en page. `useWasmLineBreaker(false)` garde le module TypeScript, pour comparer les deux.

```ts
import { initLineBreaker, buildDocument } from 'postext';

await initLineBreaker(); // optional: the first layout already uses it
const doc = buildDocument({ markdown }, config);
```


### État global partagé dans une page

Une partie de l’état de Postext vit dans des variables de niveau module. Tout ce qui importe `postext` dans le même domaine d’exécution JavaScript (realm) le partage : une page et ses scripts partagent une copie, tandis que chaque iframe et chaque worker a la sienne. Avec un seul document par page, on ne s’en aperçoit jamais. Avec plusieurs documents dans une page (deux aperçus en direct, une galerie d’exemples), on s’en aperçoit :

- **Images de ressources.** `registerResourceImage(fileId, image)` remplit un registre unique indexé par `fileId`, que lisent `renderPage` et `renderPageToCanvas`. Deux documents qui enregistrent tous deux `figure.svg` partagent cette entrée : le dernier enregistrement l’emporte, pour les deux. Donnez aux identifiants de fichier un préfixe propre à chaque document, et appelez `unregisterResourceImage(fileId)` ou `clearResourceImages()` quand un document disparaît. Les rastérisations que le moteur de rendu canvas met en cache sont indexées de la même façon et abandonnées avec l’image.
- **Mesures de texte.** Les largeurs mesurées sont mises en cache par chaîne de police et par texte pour tout le domaine d’exécution. Lorsque des polices d’une famille arrivent ou disparaissent, le moteur abandonne les largeurs de cette famille pour tous les documents (voir [Charger les polices avant la mise en page](#charger-les-polices-avant-la-mise-en-page)) ; `clearMeasurementCache()` les abandonne toutes.
- **Configurations résolues.** Chaque objet de configuration est résolu une fois et le résultat est mis en cache pour cet objet. Chaque construction compare d’abord l’objet au texte qu’il avait lors de sa résolution (un `JSON.stringify`, environ 0,1 ms pour une configuration de livre de 55 Ko et 1,5 ms pour une configuration de 240 Ko) : une configuration modifiée sur place, à n’importe quelle profondeur (`config.bodyText.fontSize = …`, une couleur de palette), est donc résolue de nouveau. `invalidateConfig(config)` abandonne la résolution à la main. `stableStringify` et `hashString` donnent une clé de contenu indépendante de l’ordre des clés, pour les hôtes qui mettent en cache des mises en page par configuration.
- **Langue de césure.** Chaque construction règle la langue de césure globale du processus sur le `bodyText.hyphenation.locale` de son document. Les fonctions exportées `hyphenateText(text)` et `layoutDesignSlot` utilisent la langue de la dernière construction, sauf si vous en passez une : appelez `hyphenateText(text, 'es')`.
- **Moteur mathématique.** Il y a un seul moteur MathJax et un seul cache de formules rendues pour le domaine d’exécution ; `initMathEngine()` le démarre pour tout le monde.
- **Module de coupure des lignes.** Il y a un seul module WebAssembly de coupure des lignes pour le domaine d’exécution, compilé une fois ; `useWasmLineBreaker(false)` le désactive pour tout le monde.

L’isolation la plus simple consiste à donner un domaine d’exécution à chaque document : une iframe pour chaque exemple en direct (une intégration CodePen en est une), ou un [worker de mise en page](#mise-en-page-dans-un-web-worker) par document pour les mesures et la césure (les images restent enregistrées sur la page).

### Documents Word (`postext/word`)

Le sous-chemin `postext/word` lit et écrit des documents Word (`.docx`) sans DOM. L’importation et l’exportation Word du Sandbox, ainsi que les commandes `import-docx` et `docx` de la ligne de commande, reposent sur lui (voir [Ligne de commande › docx et import-docx](/fr/docs/command-line#docx-et-import-docx)).

```ts
import { readDocx, parseTemplate, emptyTemplate, analyzeDocx, wordToPostext, postextToDocx } from 'postext/word';

const word = readDocx(bytes);                                    // a Uint8Array or an ArrayBuffer
const template = parseTemplate(word.embeddedTemplate) ?? emptyTemplate();
const report = analyzeDocx(word, template, config);              // report.verdict, report.findings
const { chapters, pictures, tables } = wordToPostext(word, {
  template, config, chapters: 'split', existingIds: new Set(), untitledChapter: 'Untitled',
});

const docx = postextToDocx(chapters, { template, config, book: chapters.length > 1, title: 'Field notes' });
```

- **`readDocx(bytes)`** lit le fichier et en tire un modèle Word : ses styles, ses paragraphes, ses notes et ses images, le `title` du document et le modèle d’importation que contient une exportation Postext (`embeddedTemplate`). Un fichier qui n’est pas un document Word lève une `DocxReadError`.
- **`wordToPostext(word, settings)`** transforme le modèle en chapitres (`{ title, markdown }`), images et tableaux. Le modèle d’importation fait correspondre chaque style Word à un titre, un style de paragraphe, un encadré, une citation ou une légende de la configuration. `chapters: 'split'` ouvre un chapitre à chaque titre de niveau 1, `'single'` en garde un seul. L’hôte range comme ressources les images (`id`, `media.bytes`, `caption`, `alt`) et les tableaux (`id`, `model`, `caption`) ; `skippedPictures` nomme les images EMF, WMF et TIFF laissées de côté.
- **`analyzeDocx(word, template, config)`** est le rapport de qualité que montre le Sandbox avant une importation : les styles utilisés, le nombre de paragraphes stylés et des constats comme `directFormatting`, `manualHeadings` et `typedNumbering`, chacun avec un nombre et des exemples.
- **`postextToDocx(chapters, settings)`** écrit des chapitres en `.docx` (un `Uint8Array`) avec des styles Word pour les titres, les paragraphes, les encadrés, les citations, les listes et les notes. Ce que Word ne sait pas exprimer reste tel quel dans les styles *Postext Markup*, et le modèle d’importation va dans le fichier : le document se réimporte donc sans changement. `book: true` ouvre chaque chapitre par un paragraphe `Postext Chapter`, à partir duquel l’importation reconstruit les chapitres.
- **`wordStyleTracking(word, template, config)`** et **`applyStyleTracking(config, tracking)`** reportent l’espacement des caractères des styles Word sur les styles de la configuration qui n’en définissent aucun.


## Mise en page dans un Web Worker

**C’est la façon recommandée d’utiliser Postext dans le navigateur.** Si vous construisez quoi que ce soit d’interactif (un aperçu en direct, un éditeur, une visionneuse qui suit le redimensionnement, un espace d’essai comme le Sandbox), pilotez la chaîne par `createLayoutWorker()` de `postext/worker`. N’appelez pas `buildDocument` directement sur le thread principal pour du code d’interface.

Appeler `buildDocument` sur le thread principal exécute toute la chaîne (analyse, mesure, placement et chaque nouvelle exécution de la passe de placement dont la mise en page a besoin) sur le thread qui l’a appelée. Pour un export ponctuel, cela convient. Pour une interface interactive, c’est le mauvais thread : une mise en page de 150 ms bloque les événements d’entrée, les frappes s’accumulent et le défilement saccade. Le worker déplace chacune de ces millisecondes vers un thread d’arrière-plan.

Postext fournit un point d’entrée Web Worker dédié, `postext/worker`, qui sort la chaîne du thread principal. C’est la voie que nous attendons de la majorité des intégrations : les vues Canvas, HTML et PDF du Sandbox partagent toutes le même handle `createLayoutWorker()` par un unique hook `useLayoutWorker` (`packages/postext-sandbox/src/worker/useLayoutWorker.ts`) et le pilotent avec une annulation où la dernière demande l’emporte : une nouvelle frappe interrompt la construction en cours avant même qu’elle se termine.

D’un coup d’œil, l’intégration de référence se présente ainsi :

1. **Créez** un worker une fois par vue avec `createLayoutWorker()`.
2. **Enregistrez les polices** une fois par famille en postant des `ArrayBuffer` transférables par `registerFonts(payloads)`.
3. **Construisez** avec `build(content, config, { signal })`, en passant un nouvel `AbortSignal` à chaque appel pour pouvoir annuler les constructions périmées.
4. **Remplacez** toute construction précédente en interrompant son signal *avant* de lancer la suivante : c’est le modèle « la dernière l’emporte ».
5. **Libérez** le worker lorsque le composant qui le possède est démonté.

Le même `VDTDocument` que renvoie `build(...)` alimente tous les moteurs de rendu en aval : `renderPage`/`renderPageToCanvas` pour le canvas, `renderToHtmlIndexed` pour le HTML et `renderToPdf` (de `postext-pdf`) pour le PDF. Vous construisez une fois dans le worker et vous rastérisez sur le thread principal autant de fois que l’interface en a besoin.

### Ce que le worker vous apporte

- **Le thread principal reste libre.** L’analyse, la mesure et chaque passe de placement s’exécutent toutes dans le worker. Le thread principal n’est sollicité que lorsque le `VDTDocument` terminé lui est renvoyé.
- **Annulation où la dernière demande l’emporte.** `build(content, config, { signal })` transmet un `AbortSignal` au worker. Une interruption avant la fin lève une `AbortError` côté principal ; dans le worker, la chaîne lève une `BuildCancelledError` au point de contrôle d’annulation suivant (il y en a un par bloc) et s’arrête immédiatement.
- **Cache de mesures par worker.** Le worker garde un seul `MeasurementCache` pendant toute sa durée de vie. Les constructions suivantes qui partagent police, texte et largeur réutilisent les mesures de lignes en cache : taper un seul caractère dans un long document ne remesure que les blocs dont l’entrée a réellement changé.
- **Des métriques identiques à celles du thread principal.** Les polices sont envoyées dans le worker sous forme d’`ArrayBuffer` transférables et enregistrées par `new FontFace(...)` dans le propre `FontFaceSet` du worker. Le worker mesure avec les mêmes métriques de police canvas que celles qu’utiliserait le thread principal : les coupures de ligne et les hauteurs de colonne sont donc identiques à l’octet près.
- **Le cache de rastérisation des formules survit aux constructions du worker.** Le moteur de rendu mathématique fournit un cache de rastérisation indexé par contenu à côté de celui indexé par identité : sans lui, le clonage structuré d’un `MathRender` à travers la frontière du worker manquerait le cache par identité à chaque reconstruction.
- **Les mêmes lignes que sur la page.** Un canvas créé dans un worker n’a pas de page dont tirer une langue, et une police répond avec d’autres glyphes selon la langue. Le moteur fixe la langue du document (`locale`) sur chaque contexte avec lequel il mesure, dans le worker comme sur la page : `build()` renvoie donc les lignes que `buildDocument` donne sur une page, dans n’importe quelle langue ([`bodyText.shapingLanguage: 'document'`](/fr/docs/configuration-text#texte-courant), la valeur par défaut depuis postext 1.30). Avec `'host'`, que garde une configuration enregistrée avant 1.30, un worker mesure sans langue et une page avec la sienne, comme jusqu’à postext 1.28.

### API publique

Le client du worker se trouve dans le sous-chemin `postext/worker` et tient en quelques noms :

- **`createLayoutWorker(opts?): LayoutWorkerHandle`** : lance un worker dédié (ou enveloppe celui que vous passez par `opts.worker`, ou démarre le point d’entrée du worker situé à `opts.url`) et renvoie un handle typé. Voir [Charger le worker depuis un CDN](#charger-le-worker-depuis-un-cdn).
- **`LayoutWorkerHandle.registerFonts(faces: FontPayload[]): Promise<void>`** : envoie les octets des polices dans le worker. Les buffers sont transférés : gardez une copie neuve sur le thread principal si vous devez les renvoyer plus tard.
- **`LayoutWorkerHandle.unregisterFonts(families: string[]): Promise<void>`** : retire du worker les polices de ces familles, pour que le prochain `registerFonts` d’une famille prenne effet au lieu d’être rapproché de la police qu’il détient déjà.
- **`LayoutWorkerHandle.build(content, config?, options?): Promise<VDTDocument>`** : exécute la chaîne. `options` vaut `{ signal?, onProgress?, onStats?, resourcesKey?, cacheKey? }`. Interrompre `signal` annule la construction en cours. `onProgress({ pass, blocks, totalBlocks, pages })` est appelé à mesure que le placement avance ; `onStats({ passes, totalMs, cached?, missingFonts? })` reçoit les temps des passes de la construction terminée. `resourcesKey` est une empreinte de `content.resources` : des constructions successives avec la même clé n’envoient la liste qu’une fois, et le worker la garde. `cacheKey` est une empreinte de toute la construction : le worker garde ses derniers documents sous cette clé et répond depuis ce cache à une construction dont il détient la clé.
- **`LayoutWorkerHandle.warm(content, config, { cacheKey, … }): Promise<void>`** : construit dans le cache de documents du worker sans renvoyer le document, pour un chapitre que le lecteur ouvrira peut-être ensuite ; le prochain `build` avec ce `cacheKey` est servi depuis le cache.
- **`LayoutWorkerHandle.prepareFonts(content, config?, options?)`** : `prepareFonts` sur la page, puis les polices trouvées envoyées au worker ; voir [Charger le worker depuis un CDN](#charger-le-worker-depuis-un-cdn).
- **`LayoutWorkerHandle.dispose(): void`** : termine le worker et rejette toute construction en attente avec `AbortError`.
- **`FontPayload`** : `{ family, weight, style, unicodeRange?, buffer: ArrayBuffer }`. `weight` est une chaîne de graisse CSS (`'700'`, `'bold'`) ; `registerFonts` l’accepte aussi sous forme de nombre (`700`). Le `buffer` est transféré au worker lorsque vous appelez `registerFonts`.
- **`BuildCancelledError`** (réexportée depuis `postext`) : ce que `buildDocument` lève en interne lorsque `options.shouldCancel` renvoie `true`. Vous ne la voyez généralement pas sur le thread principal : le protocole du worker la convertit en `AbortError` avant qu’elle n’atteigne votre code.

Le paquet npm publie aussi un chemin `postext/worker/entry` qui pointe vers le script compilé du worker. `createLayoutWorker()` résout cette URL automatiquement ; vous n’avez besoin de la référencer explicitement que si votre bundler exige un appel `new Worker(new URL(...), { type: 'module' })` construit à la main, ou si vous servez le point d’entrée vous-même (`opts.url`).

### Intégration minimale

```ts
import { createLayoutWorker } from 'postext/worker';
import type { FontPayload, LayoutWorkerHandle } from 'postext/worker';
import type { PostextConfig, VDTDocument } from 'postext';

// 1. Create the worker once and keep the handle for the lifetime of your viewport.
const layout: LayoutWorkerHandle = createLayoutWorker();

// 2. Register fonts once per family (transferable ArrayBuffers).
//    getConfigFontFamilies(config) is a helper that lists the families your config will render.
const payloads: FontPayload[] = await collectFontPayloadsForFamilies([
  'EB Garamond',
  'Open Sans',
]);
await layout.registerFonts(payloads);

// 3. Drive builds with last-wins cancellation: abort the previous signal
//    before starting a new build. A stale build is thrown away inside the worker.
let pending: AbortController | null = null;

async function rebuild(
  markdown: string,
  config: PostextConfig,
): Promise<VDTDocument | null> {
  pending?.abort();
  pending = new AbortController();
  try {
    return await layout.build({ markdown }, config, { signal: pending.signal });
  } catch (err) {
    if ((err as { name?: string } | null)?.name === 'AbortError') return null;
    throw err;
  }
}

// 4. Dispose when the component that owns the worker unmounts.
//    Pending builds reject with AbortError.
layout.dispose();
```

Enveloppé dans un composant React, cela donne :

```tsx
import { useEffect, useRef } from 'react';
import { createLayoutWorker } from 'postext/worker';
import type { LayoutWorkerHandle } from 'postext/worker';
import { renderPageToCanvas } from 'postext';
import type { PostextConfig } from 'postext';

export function CanvasPreview({
  markdown,
  config,
}: {
  markdown: string;
  config: PostextConfig;
}) {
  const canvasRef = useRef<HTMLCanvasElement | null>(null);
  const workerRef = useRef<LayoutWorkerHandle | null>(null);
  const pendingRef = useRef<AbortController | null>(null);

  // Mount: spin up the worker and ship the fonts once.
  useEffect(() => {
    const handle = createLayoutWorker();
    workerRef.current = handle;
    (async () => {
      const payloads = await collectFontPayloadsForFamilies(
        getConfigFontFamilies(config),
      );
      await handle.registerFonts(payloads);
    })();
    return () => {
      pendingRef.current?.abort();
      handle.dispose();
    };
  }, []); // fonts registered once; re-register only when the family set changes

  // Every keystroke or config change: supersede the in-flight build and kick a new one.
  useEffect(() => {
    const handle = workerRef.current;
    if (!handle) return;
    pendingRef.current?.abort();
    const ac = new AbortController();
    pendingRef.current = ac;
    (async () => {
      try {
        const vdt = await handle.build({ markdown }, config, { signal: ac.signal });
        const canvas = canvasRef.current;
        if (!canvas || !vdt.pages[0]) return;
        renderPageToCanvas(vdt.pages[0], vdt, canvas); // rasterise on the main thread
      } catch (err) {
        if ((err as { name?: string } | null)?.name !== 'AbortError') throw err;
      }
    })();
  }, [markdown, config]);

  return <canvas ref={canvasRef} />;
}
```

Le schéma est toujours le même : **créer une fois, enregistrer les polices une fois, construire avec un AbortSignal autant de fois que nécessaire, libérer au démontage.**

### Charger le worker depuis un CDN

Un script de worker doit provenir de l’origine de la page : une copie de `postext/worker` servie par un CDN ne peut donc pas démarrer le fichier `layout.worker.js` placé à côté d’elle. `createLayoutWorker()` s’en charge :

- **esm.sh, sans option.** Lorsque `postext/worker` a lui-même été chargé depuis esm.sh (l’URL de son module ressemble à `https://esm.sh/postext@1.5.0/es2022/worker.mjs`), le client démarre le `https://esm.sh/postext@1.5.0/worker/entry` correspondant par un module blob d’une ligne, de même origine, qui l’importe. Il en va de même pour les imports qui ajoutent `?deps=`, `?external=` ou `?alias=`, et pour la forme `https://esm.sh/*postext@1.5.0/worker`. Le worker reçoit toujours le build simple de cette version, car un worker n’a pas d’import map pour résoudre des dépendances externes.
- **Tout autre serveur, avec `url`.** Les autres CDN, comme jsDelivr (`/+esm`) ou unpkg, ne sont pas détectés. `createLayoutWorker({ url })` démarre le module d’entrée du worker situé à `url` : directement pour une URL de même origine, par la même enveloppe blob pour une URL d’une autre origine. Ce serveur doit autoriser les requêtes cross-origin (CORS).
- **Les bundlers ne changent rien.** Avec Vite, webpack ou Next.js, continuez d’appeler `createLayoutWorker()` sans option : ils émettent le worker comme un chunk de votre application.

```js
import { createLayoutWorker } from 'https://esm.sh/postext/worker';

const layout = createLayoutWorker();
const face = async (weight, style) => ({
  family: 'EB Garamond',
  weight,
  style,
  buffer: await (await fetch(`https://cdn.jsdelivr.net/npm/@fontsource/eb-garamond@5/files/eb-garamond-latin-${weight}-${style}.woff2`)).arrayBuffer(),
});
await layout.registerFonts(await Promise.all([face(400, 'normal'), face(700, 'normal'), face(400, 'italic')]));
const doc = await layout.build({ markdown }, { bodyText: { fontFamily: 'EB Garamond' } });
```

**Un worker ne voit pas les polices de la page.** Il a son propre jeu de polices, qui ne contient que les polices envoyées par `registerFonts` et les polices installées sur le système. Lorsqu’une construction compose du texte dans une famille que le worker ne trouve pas, ce texte est mesuré avec une police de repli, et ses coupures de ligne ne correspondront pas à celles de la page. Le client affiche alors un avertissement dans la console par famille (`"EB Garamond" is not available inside the layout worker…`) et liste les familles dans `BuildStats.missingFonts`, que reçoit le callback `onStats` de `build`. Le document lui-même signale les mêmes polices sous forme d’avertissements de contenu `fontFallback`.

`handle.prepareFonts(content, config, options)` exécute [`prepareFonts`](#charger-les-polices-avant-la-mise-en-page) sur la page, puis envoie au worker les fichiers de chaque police trouvée que contient le registre de polices (les fichiers du résolveur, les polices d’un paquet, les règles `@font-face` lisibles de la page), en se limitant aux tranches qui contiennent les caractères du document. Lorsque des polices arrivent dans le worker, il abandonne uniquement les mesures de ces familles, ainsi que son cache de documents terminés.

Des polices peuvent aussi atteindre le worker après une construction : une graisse dont les pages se révèlent avoir besoin, une autre tranche `unicode-range` d’une police, un fichier téléversé de nouveau sous le même nom de famille. La construction suivante mesure avec elles. Le canvas d’un worker ne le ferait pas de lui-même : dans Chrome, il résout une police la première fois qu’une notation abrégée de police est définie et ne consulte plus le jeu de polices pour cette notation : le texte garderait donc les largeurs de la police qui a répondu en premier. Le worker répète donc le nom d’une famille dans les notations abrégées qu’il définit, dès qu’une police de cette famille est arrivée en retard (`Geist, Geist`) : une autre liste de familles pour le canvas, la même police et les mêmes largeurs. Les documents qu’il renvoie gardent les chaînes de police telles que le moteur les écrit, et un worker qui a reçu ses polices avant sa première construction définit chaque notation abrégée telle qu’elle est écrite.

### Collecte des polices (Fontsource / Google Fonts)

`registerFonts` prend des octets de police bruts. Le thread principal est le bon endroit pour les récupérer, car un cache central permet à plusieurs instances de worker de partager les mêmes octets.

Le `collectFontPayloadsForFamilies` du Sandbox (`packages/postext-sandbox/src/controls/fonts/fontLoader.ts`) sert d’implémentation de référence. Il :

1. Interroge `https://api.fontsource.org/v1/fonts/{family-id}` pour connaître les graisses et les styles de la famille.
2. Lit les sous-ensembles de la famille et leur `unicode-range` dans son paquet sur jsDelivr (`@fontsource/{family-id}@5/400.css`), une fois par famille. Les fichiers sont ensuite demandés à la version exacte depuis laquelle cette feuille de style a été servie (le `x-jsd-version` de jsDelivr) : une famille n’arrive donc jamais de deux versions de son paquet.
3. Télécharge chaque fichier du romain, du gras et de leurs italiques pour chaque famille (`files/{family-id}-{subset}-{weight}-{style}.woff2`) ; `collectFontPayloadsForConfig(config, markdown)` prend plutôt les graisses et les styles que demande une configuration. Ce sont des fichiers statiques, ceux que le PDF incorpore : le worker mesure donc avec ce que dessine le PDF. Un fichier variable donne d’autres chasses entre deux de ses masters, et une ligne à une fraction de pixel de sa justification se coupe ailleurs.
4. Renvoie un `FontPayload[]` dont le `buffer` est un `ArrayBuffer` neuf à chaque appel. C’est important, car `registerFonts` transfère le buffer et laisse la copie de l’expéditeur détachée.

Les fichiers d’une police s’ajoutent dans l’ordre où un pen du livre de recettes (un exemple CodePen) les déclare, `latin` en premier et les fichiers propres à l’écriture en dernier (`arabic`, les tranches numérotées d’une famille chinoise ou japonaise), car le fichier ajouté en dernier répond pour un caractère que deux fichiers contiennent. Une famille pour laquelle Fontsource n’a pas de fichiers est lue dans la feuille de style CSS2 de Google, qui ne renvoie du WOFF2 qu’aux chaînes User-Agent de type navigateur.

Associez-le à `getConfigFontFamilies(config)` pour obtenir la liste des familles qu’une `PostextConfig` donnée rendra réellement (texte courant, titres, puces de liste, numéros de liste ordonnée).

### Annulation coopérative dans le moteur

Si vous pilotez `buildDocument` vous-même (par exemple dans un worker personnalisé), la chaîne expose un hook `shouldCancel` que vous pouvez utiliser directement :

```ts
import { buildDocument, BuildCancelledError } from 'postext';

let superseded = false;
try {
  const vdt = buildDocument(content, config, cache, {
    shouldCancel: () => superseded,
  });
} catch (err) {
  if (err instanceof BuildCancelledError) return; // a newer build took over
  throw err;
}
```

`shouldCancel` est appelé une fois par bloc de premier niveau pendant le placement. Le hook est volontairement coopératif : il ne peut pas arrêter l’appel de mise en page de pretext au milieu d’une ligne, mais il garde une granularité d’annulation assez fine (quelques millisecondes) pour qu’un utilisateur qui tape vite n’attende jamais une construction périmée.

### Piloter l’export PDF depuis le worker

Le moteur de rendu PDF prend un `VDTDocument` prêt et le transforme en octets PDF. Il ne relance **pas** la mise en page. Le flux PDF de référence dans le navigateur s’associe donc proprement au worker : construisez le VDT dans le worker (hors du thread principal, annulable, avec réutilisation du cache), puis appelez `renderToPdf` sur le thread principal avec ce même VDT.

```ts
import type { LayoutWorkerHandle } from 'postext/worker';
import { renderToPdf } from 'postext-pdf';
import type { PostextConfig } from 'postext';
import { createPdfFontProvider } from './pdfFontProvider';

const fontProvider = createPdfFontProvider();

export async function exportPdf(
  layout: LayoutWorkerHandle,
  markdown: string,
  config: PostextConfig,
): Promise<Uint8Array> {
  // 1. Build the VDT in the worker — UI stays responsive during the layout passes.
  const vdt = await layout.build({ markdown }, config);

  // 2. Rasterise to PDF on the main thread. renderToPdf is fast once the VDT exists
  //    because it is walking precomputed coordinates, not remeasuring text.
  return renderToPdf(vdt, {
    fontProvider,
    // pdfGeneration config on `vdt.config` is honoured automatically.
  });
}
```

Si vous gérez déjà un handle de worker pour l’aperçu en direct, réutilisez-le pour l’export au lieu de lancer un second worker : grâce au cache de mesures du worker, un export PDF qui suit un aperçu à l’écran ne coûte presque rien.

Pour un long livre, l’écriture du PDF lui-même prend aussi quelques secondes ; `postext-pdf/worker` exécute cette étape dans un worker à part (voir [Rendre le PDF dans un worker](/fr/docs/configuration-pdf-output#rendre-le-pdf-dans-un-worker)).

### Quand utiliser le worker, et quand s’en passer

Utilisez le worker pour :

- **Les aperçus en direct, les éditeurs et les espaces d’essai.** Tout ce qui reconstruit le document en réponse à une saisie de l’utilisateur.
- **Les visionneuses HTML qui suivent le redimensionnement** et relancent la mise en page à chaque tick de `ResizeObserver`.
- **L’export PDF dans le navigateur** déclenché depuis une interface qui a déjà un aperçu en direct : réutilisez le handle de worker existant pour que l’export profite du cache de mesures.
- **Plusieurs onglets de sortie** qui ont tous besoin du même VDT (les vues Canvas / HTML / PDF du Sandbox partagent un handle de worker par montage de vue).

Passez-vous du worker pour :

- **La génération côté serveur** : Node n’a pas de `FontFaceSet` de navigateur, et vous contrôlez de toute façon le thread.
- **Les exports ponctuels isolés** (une CLI, un script d’export sans interface, une Cloud Function) où aucune interface interactive ne risque d’être bloquée. Appeler `buildDocument` directement est plus simple et évite le coût du transfert initial des polices.
