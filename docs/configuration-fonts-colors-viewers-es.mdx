# Configuración: fuentes, colores y salida


## Unidades y colores

### Dimensiones

En Postext, todas las medidas físicas usan el tipo `Dimension`, un valor acompañado de una unidad:

```ts
interface Dimension {
  value: number;
  unit: DimensionUnit; // 'cm' | 'mm' | 'in' | 'pt' | 'px' | 'em' | 'rem'
}
```

**Unidades absolutas** (`cm`, `mm`, `in`, `pt`, `px`): se convierten en píxeles según la resolución (DPI) configurada. A 300 DPI, `1 cm` equivale aproximadamente a 118 px.

**Unidades relativas** (`em`, `rem`): cambian con el cuerpo de la letra. Un `em` es relativo al cuerpo del propio elemento, y `rem`, al cuerpo del texto base.

### Colores

Los colores se guardan con una representación hexadecimal y un modelo de color de destino:

```ts
interface ColorValue {
  hex: string;         // '#ff0000', 'transparent', etc.
  model: ColorModel;   // 'hex' | 'rgb' | 'cmyk' | 'hsl'
  cmyk?: CmykPercent;  // Los valores de cuatricromía exactos de un color definido en CMYK.
  paletteId?: string;  // La entrada de colorPalette que sigue.
}
```

El campo `model` indica el espacio de color previsto. Para la web, lo habitual es `'hex'` o `'rgb'`. En los flujos de impresión, `'cmyk'` indica que el color se definió en CMYK, y `cmyk` guarda sus valores: una salida CMYK para imprenta los usa tal cual, y `hex` es su representación en pantalla (véase [Colores definidos en CMYK](#colores-definidos-en-cmyk)).

Como Postext busca una salida de calidad editorial, el color por defecto del texto base viene con `model: 'cmyk'` (`#000000`). Los colores de los encabezados, las negritas, las cursivas y las listas toman por defecto el **Color principal** vinculado a la paleta (`#295AA3`, `model: 'hex'`). El fondo de la página y las ayudas visuales (la rejilla base, las marcas de corte, los indicadores de depuración) usan `model: 'hex'` por defecto. Cambia el `color.model` de cualquier campo si necesitas que se exporte de otra forma.

### Transparencia

Un color puede ser translúcido. `hex` admite un canal alfa, como `#rgba` o `#rrggbbaa`. También admite un color `rgb()` / `rgba()`, con la sintaxis de comas o la de espacios, y el alfa como número o como porcentaje. `transparent` es del todo transparente:

```ts
const config: PostextConfig = {
  header: {
    elements: [{
      kind: 'box',
      id: 'velo',
      placement: {
        anchor: { to: 'bleed', edge: 'top-left' },
        size: { width: 'fill', height: { value: 40, unit: 'mm' } },
      },
      style: { backgroundColor: { hex: '#ffffffb3', model: 'hex' } }, // blanco al 70 %
    }],
  },
  bodyText: { color: { hex: 'rgba(0, 0, 0, 0.85)', model: 'rgb' } },
};
```

Los tres backends lo pintan del mismo modo. El canvas y el visor HTML toman el valor como un color CSS. El backend de PDF aplica la opacidad del color como un alfa constante: un `ExtGState` con `ca` para los rellenos y `CA` para los trazos. Esto abarca el texto, los filetes, las cajas, los rellenos y los bordes de las tablas, los chips, las muestras de color y las fórmulas. Un color translúcido se superpone a lo que se haya pintado antes. Una caja de la cabecera o del pie se pinta la última, así que vela el texto que tiene debajo; una caja de una banda de apertura se pinta la primera, así que colorea la página por debajo del texto. Cuando se fuerza el PDF a otro espacio de color (`pdfGeneration.forceColorSpace` con `colorSpace: 'cmyk'` o `'grayscale'`), el color se convierte y conserva su alfa. En el Sandbox, el deslizador de opacidad del selector de color escribe estos valores como `#rrggbbaa`, y el selector también lee las demás formas.


## Fuentes personalizadas

Postext busca cada `fontFamily` **tanto** en el catálogo de Google Fonts **como** en la lista `customFonts` del documento. Si coinciden los nombres, tienen prioridad las fuentes personalizadas: si declaras `customFonts: [{ name: 'Roboto', … }]`, Postext usa tu archivo en lugar de la «Roboto» de Google Fonts. El Sandbox toma de Fontsource las familias que Google Fonts no tiene. Nunca consulta Fontsource por un nombre genérico (`serif`, `system-ui`) ni por una fuente que trae un sistema operativo (Arial, Segoe UI, PingFang SC…): esa familia se compone con lo que tenga el equipo del lector, el panel **Fuentes** la muestra como *No encontrada* y el PDF y las imágenes SVG no tienen ningún archivo suyo que incrustar. Si el libro se compone con ella, súbela como fuente personalizada.

Usa fuentes personalizadas cuando:

- El documento necesita un tipo de letra corporativo o con licencia que no está en Google Fonts.
- El entorno no tiene acceso a las CDN de fuentes, a jsDelivr (de donde el Sandbox toma los archivos de Fontsource) ni a Google Fonts (sin conexión, en una intranet, por motivos de privacidad).
- Tienes que mantener privado el archivo de la fuente, sin subirlo a ningún servicio externo.

### Esquema de configuración

```ts
type CustomFontFormat = 'woff2' | 'woff' | 'ttf' | 'otf';
type CustomFontStyle = 'normal' | 'italic';

interface CustomFontVariant {
  weight: number;           // CSS font-weight, 100..900
  style: CustomFontStyle;
  fileId: string;           // id opaco del binario en almacenamiento externo
  format: CustomFontFormat;
  fileName?: string;        // nombre original del archivo (se muestra en la UI)
}

interface CustomFontFamily {
  name: string;             // se usa donde encajaría un nombre de Google Font
  variants: CustomFontVariant[];
  redistributable?: boolean; // false: se usa aquí, nunca se copia fuera del libro
  fallback?: string;        // familia abierta de ancho parecido para las caras sin archivo (desde postext 1.42)
}

interface PostextConfig {
  // ...
  customFonts?: CustomFontFamily[];
}
```

El archivo de cada estilo **no** se incluye en la propia configuración. La configuración solo guarda referencias `fileId`; los bytes se guardan aparte. En el Sandbox, eso significa IndexedDB (un almacén clave-valor del navegador, privado del documento). Quien integre Postext en otra aplicación puede resolver `fileId` como prefiera (un servicio del servidor, la caché de un service worker, lo que sea), siempre que los bytes lleguen al hilo principal antes de que se ejecute `buildDocument`.

### Gestionar fuentes personalizadas en el Sandbox

Abre el panel **Fuentes** desde la barra de actividades de la izquierda (entre Recursos y Diseño). Su lista **Tipos de letra de este libro** muestra todas las familias que usa el diseño, con su función y su origen: Google Fonts, Fontsource (para las familias que Google Fonts no tiene), un archivo propio o ninguno (*No encontrada*). En **Tus archivos de fuente**, para cada familia:

1. **Añadir familia de fuentes**: crea una familia vacía; cámbiale el nombre en el propio campo.
2. **Subir archivo**: elige un peso (100–900) y un estilo (normal / cursiva) y selecciona uno *o varios* archivos `.woff2`, `.woff`, `.ttf` u `.otf`. Cada archivo se convierte en un estilo propio, asociado a la combinación de peso y estilo seleccionada; el nombre del archivo subido se guarda y aparece en la fila, para que puedas distinguir los estilos. Puedes cambiar en cualquier momento el peso o el estilo de cada uno desde sus desplegables.
3. **Se admiten estilos duplicados.** Si dos archivos corresponden a la misma combinación de peso y estilo, se conservan los dos y aparece el aviso **Variante de fuente duplicada**, para que sepas que debes cambiar los ajustes de los sobrantes.
4. **Eliminar variante** o **Eliminar familia**: elimina la entrada de la configuración *y* los bytes guardados en IndexedDB.

Una vez declarada la familia, todos los selectores de fuente la agrupan en **Personalizadas**, encima de la lista de Google Fonts. Al elegirla, la familia se asigna a cada campo `fontFamily` en el que la apliques.

### Una familia de sustitución para una fuente no redistribuible

Un libro puede componerse con una fuente que su propietario no puede distribuir. Marca la familia con `redistributable: false`, y los archivos `.postext` la dejarán fuera. Indica en `fallback` una familia abierta de ancho parecido, y un archivo que se abra sin esos archivos seguirá cortando sus líneas cerca de donde las corta la fuente real, en lugar de desbordar sus marcos con una fuente de reserva más ancha. Los estilos de los que la familia no tiene archivo se componen con los de la familia de reserva del mismo peso e inclinación, con el nombre de la familia con licencia, en las vistas previas, en el worker de maquetación, en el PDF y en la línea de comandos. Una familia con archivos los conserva y solo toma de la familia de reserva la inclinación de la que no tiene archivo (por ejemplo, una cursiva); los pesos intermedios entre sus archivos se eligen como en cualquier otra familia. En el panel Fuentes, **Familia de sustitución** (dentro de la familia, encima de sus archivos) recibe el nombre; si el campo está vacío, la familia queda como estaba. El PDF de un libro compuesto así incrusta la fuente abierta, así que el PDF definitivo debe generarse con los archivos con licencia. Desde postext 1.42. Desde postext 1.43, la fuente abierta también va a donde no puede ir la que tiene licencia: un EPUB o una exportación HTML, tanto desde el Sandbox como desde `postext`, incluyen los estilos de la familia de reserva con el nombre de la familia con licencia, igual que las imágenes SVG cuyo texto se compone con esa familia, de modo que el sistema de lectura compone el libro con una fuente del ancho para el que se cortaron sus líneas. Los archivos propios de la familia nunca salen del libro. Una familia sin `fallback`, o cuya familia de reserva no tiene archivo, se indica sin archivos, como antes; la pestaña EPUB del Sandbox enumera las familias que se han compuesto con una familia de reserva.

### Comportamiento de renderizado

Por dentro:

- Cuando cambia `customFonts`, todas las familias declaradas se registran automáticamente como entradas `FontFace` en `document.fonts`, de modo que el visor HTML, la vista Canvas (que mide mediante `document.fonts`) y cualquier referencia CSS directa usan el estilo personalizado sin necesidad de abrir antes el selector de fuentes.
- El worker de maquetación recibe los mismos `ArrayBuffer` por el canal habitual de transferencia de fuentes, así que la medición (`buildFontString`, pretext) funciona igual que con una familia del catálogo.
- Al cambiar o eliminar un estilo, el worker descarta el estilo que tenía guardado en caché para esa familia y lo vuelve a registrar en la siguiente compilación, de modo que las vistas previas siguen sincronizadas con los estilos actuales.
- **Exportación a PDF**: los archivos subidos pasan por el mismo `PdfFontProvider`. Los `.woff2` se descomprimen; los `.ttf` y `.otf` se usan tal cual. Los `.woff` se rechazan con un mensaje de error claro (pdf-lib no puede incrustar WOFF directamente; vuelve a subirlo como `.woff2`, `.ttf` u `.otf`). Las OpenType con contornos CFF (un `.otf` cuya firma es `OTTO`) se incrustan **sin crear un subconjunto**, porque el generador de subconjuntos CFF de pdf-lib recorre todos los glifos al llamar a `save()` y puede quedarse bloqueado varios minutos con fuentes reales; prescindir del subconjunto da un PDF algo más grande a cambio de tiempos de generación estables.

### Avisos de fuentes faltantes

El panel **Revisión** del Sandbox muestra, en su grupo *Fuentes*, tres problemas propios de las fuentes personalizadas (todos se activan con el mismo interruptor, `debug.warnings.missingFont`, que ya controla el aviso general de fuente «no cargada»):

- **Familia de fuentes desconocida**: un `fontFamily` remite a un nombre que no tienen ni Google Fonts ni Fontsource y que no es una familia personalizada declarada. También aparece de inmediato si eliminas una familia personalizada a la que todavía remite algún campo `fontFamily`, sin esperar a que lo detecte el DOM.
- **Falta una variante de la fuente**: la familia existe, pero el libro le pide un peso y un estilo de los que no hay archivo: encabezados en negrita, por ejemplo, en una familia que solo tiene la redonda. El aviso enumera las combinaciones que faltan. Una inclinación que pone el `fallback` de la familia no cuenta como falta.
- **Variante de fuente duplicada**: dos o más archivos subidos corresponden a la misma combinación de peso y estilo dentro de una familia. Al dibujar solo se usa uno; el aviso te recuerda que cambies los ajustes de los demás.

Al hacer clic en cualquiera de estos avisos se abre el panel **Fuentes**, para que subas el estilo que falta, vuelvas a añadir la familia o distingas los duplicados.

Cuando ya hay una maquetación, el panel muestra también el aviso del motor **Fuente sustituida en la composición** (`fontFallback`): un estilo con el que no se han podido medir las páginas, bien porque falta, bien porque el navegador lo dibuja a partir de otro peso o de otra inclinación. Una familia que ya aparece como desconocida o con un estilo que falta no se muestra dos veces. Antes de la primera maquetación, se hace en su lugar una comprobación con `document.fonts`.

El panel también muestra **Caracteres tomados de otra fuente** (`glyphFallback`): caracteres que el texto pone en una fuente que no tiene glifo para ellos, una vez por fuente, con la familia genérica que los dibujó (`serif`, `sans-serif`, `monospace`) cuando la comprobación puede saberlo.

## Estilos de cifras

`figureStyle` pide a la fuente de un estilo de texto un juego de cifras concreto, con las funciones OpenType de la fuente: cifras elzevirianas en el texto corrido, cifras alineadas tabulares en las tablas. El campo está en `bodyText`, `paragraphStyles[]`, `headings` y `headings.levels[]`, `headingStyles[]`, `tableStyle` y `tableStyles[]` (celdas de cabecera y de cuerpo por igual), `captionStyle` (etiqueta y descripción, y el `captionStyle` de un tipo de recurso) y los elementos de texto de un diseño (cabeceras, folios, los textos de una portadilla o de una página de parte). En el Sandbox es el campo **Cifras** del panel Diseño, junto a la letra de cada uno de esos estilos (**Texto base → Letra** para el cuerpo).

Un par fija una forma y un ancho. Una fuente que no tiene la función conserva sus propias cifras, así que comprueba que la fuente tiene `onum` o `lnum` antes de contar con ellas. Una familia de la que el anfitrión no tiene archivo, como una fuente instalada solo en el sistema del lector (el Sandbox no las descarga), no toma ningún estilo de cifras: su texto conserva las cifras propias de esa fuente, en la propia fuente. Un libro que sube archivos con ese nombre sí obtiene las cifras. Los cortes que sirven Google Fonts y Fontsource suelen dejar fuera `onum` y `lnum` (el archivo latin de Source Serif 4 solo conserva `pnum` y `tnum`); con un archivo así, un estilo que las pide conserva las cifras propias de la fuente. Los archivos completos de la fundición las tienen: súbelos para obtener cifras elzevirianas o alineadas. Una familia genérica (`serif`, `sans-serif`) no toma funciones. Un valor que no está en la lista se notifica como valor de ajuste desconocido (`unknownConfigValue`, véase [Avisos de configuración](#avisos-de-configuración)) y se lee como si no estuviera.

```ts
const config: PostextConfig = {
  bodyText: { fontFamily: 'EB Garamond', figureStyle: 'oldstyle' },
  tableStyle: { figureStyle: 'lining-tabular' },
  paragraphStyles: [{ id: 'timetable', figureStyle: 'lining-tabular' }],
  headings: { figureStyle: 'lining' },
};
```

El texto compone los años y los números de página con cifras elzevirianas, y lo mismo hacen los pies y las listas, que toman la familia del cuerpo. Las celdas de todas las tablas y los párrafos del estilo `timetable` alinean sus dígitos con cifras alineadas tabulares. Todos los niveles de encabezado ponen cifras alineadas en la familia de los encabezados.

### Qué cifras toma cada estilo

- Un estilo que toma la familia de otro toma también sus cifras. Los estilos de párrafo, las tablas, los pies, las listas y el cuerpo de los recuadros toman la familia del cuerpo cuando no nombran otra, así que `bodyText.figureStyle` llega a todos ellos.
- Un estilo que nombra su propio `fontFamily` pone las cifras por defecto de esa fuente, salvo que también fije `figureStyle`.
- Un nivel de encabezado sin `figureStyle` propio toma `headings.figureStyle`, también en su propio `fontFamily` cuando nombra uno. El `figureStyle` de un estilo de encabezado se aplica a la familia del nivel en el que se usa el estilo.
- Un elemento de texto de un diseño nombra su propia familia (`'EB Garamond'` por defecto), así que las cifras del cuerpo no llegan a un folio: ponle `figureStyle: 'oldstyle'` para que case con un texto en cifras elzevirianas.
- `'default'` pone las cifras propias de la fuente y anula las heredadas: `paragraphStyles: [{ id: 'plain', figureStyle: 'default' }]` quita a ese estilo las cifras elzevirianas del cuerpo.

### Las cifras en cada salida

El texto se mide con las funciones, de modo que sus líneas cortan en los mismos anchos en la vista previa del Canvas, el HTML, el PDF y el EPUB, en maquetación fija y en maquetación fluida.

- **Vista previa del Canvas y worker de maquetación**: el navegador declara otra vez los archivos de la familia base con un nombre de familia con funciones y el descriptor `featureSettings` de `FontFace`. El nombre es la familia seguida de sus funciones tras `@` (`EB Garamond@onum`, `EB Garamond@lnum+tnum`), y aparece en las cadenas de fuente y en algunos avisos.
- **HTML y EPUB** (maquetación fija y fluida): la familia base, con `font-variant-numeric` (`oldstyle-nums`, `lining-nums tabular-nums`).
- **PDF**: incrusta los archivos de la familia base y compone el texto con las funciones.
- **Línea de comandos**: Skia, el canvas con el que dibuja `postext`, no aplica funciones. La línea de comandos registra una copia de la fuente cuyo `cmap` lleva cada carácter que sustituyen las funciones, los dígitos, al glifo que eligen. Solo se toman las sustituciones simples; una fuente que llega a sus cifras con sustituciones contextuales conserva ahí sus propias cifras.

## Paleta de colores

La propiedad `colorPalette` de `PostextConfig` permite definir un conjunto reutilizable de colores con nombre y remitir a ellos desde cualquier `ColorValue` de la configuración. Es el equivalente en Postext de las propiedades personalizadas de CSS o del panel de muestras de InDesign: si cambias una entrada de la paleta, se actualizan en todo el documento todos los colores que remiten a ella.

```ts
interface ColorPaletteEntry {
  id: string;       // identificador estable — referenciado por ColorValue.paletteId
  name: string;     // etiqueta legible que se muestra en las UIs del sandbox
  value: ColorValue;
}
```

### La paleta por defecto

Postext incluye una paleta por defecto con una sola entrada, llamada **Color principal** (`id: 'main-color'`, hex `#295AA3`). Varios valores por defecto (el color de los encabezados, el de las negritas y las cursivas del texto base, el de los `:ref` y el de las viñetas y los números de las listas) remiten a esa entrada mediante `paletteId: 'main-color'`, así que, al cambiar esa única muestra, cambia el color de todas las partes del documento que la usan.

Puedes examinar, copiar o comparar la paleta por defecto mediante tres exportaciones:

```ts
import {
  DEFAULT_COLOR_PALETTE,
  cloneDefaultColorPalette,
  isDefaultColorPalette,
} from 'postext';

// Snapshot de solo lectura de la paleta publicada.
DEFAULT_COLOR_PALETTE;
// => [{ id: 'main-color', name: 'Main Color', value: { hex: '#295AA3', model: 'hex' } }]

// Copia independiente — muta esta, no DEFAULT_COLOR_PALETTE.
const palette = cloneDefaultColorPalette();

// Comprueba si el usuario ha personalizado la paleta.
isDefaultColorPalette(palette); // true
```

La paleta está en el nivel superior de la configuración:

```ts
const config: PostextConfig = {
  colorPalette: [
    { id: 'tinta',  name: 'Tinta',  value: { hex: '#0a0a0a', model: 'cmyk' } },
    { id: 'acento', name: 'Acento', value: { hex: '#b8860b', model: 'hex' } },
  ],
  bodyText: { color: { hex: '#000000', model: 'cmyk', paletteId: 'tinta' } },
  headings: { color: { hex: '#000000', model: 'hex', paletteId: 'acento' } },
};
```

### Referenciar una entrada de la paleta

Cualquier `ColorValue` de la configuración puede tener un campo opcional `paletteId` que remite a una entrada de `colorPalette`: el fondo de la página, los colores del texto base (incluido el de los `:ref`), los colores de los encabezados, los filetes entre columnas, los colores de las listas, los de las tablas, los pies, los chips y los recuadros (caja, franja, icono, marcador, etiqueta, título y contenido), el color de las marcas de corte y de la rejilla base, los indicadores de depuración y todos los colores de un diseño: los titulillos, las aperturas y los diseños en columna de los encabezados, los diseños y los titulillos de los estilos de encabezado, las páginas de parte y las filas de parte del índice (texto, filete, relleno y borde de caja, contorno, capitular). Cuando existe, el `hex` / `model` de la entrada de la paleta tiene prioridad sobre el `hex` / `model` guardados como valor de reserva. Ese valor de reserva solo se usa si la paleta falta, está vacía o no contiene ese id, lo que resulta útil al distribuir una configuración que leerá una herramienta que no entiende las paletas.

**Cambio en postext 1.5.** Hasta postext 1.4, la paleta solo llegaba a una lista fija de ajustes. Los demás (los colores de los diseños: titulillos, aperturas, estilos de encabezado, partes, filas del índice; `bodyText.referenceColor`; los colores de las etiquetas de los recuadros y los de las negritas y cursivas de su contenido) conservaban el `hex` guardado junto a su `paletteId`. Un documento cuyo valor guardado no coincide con la entrada de la paleta (todos los editados en el Sandbox después de cambiar la entrada, y todos los `:ref` cuando el color principal no es `#295AA3`) imprime ahora el color de la paleta, como indica el vínculo. Para conservar un color tal como estaba, quita su `paletteId`.

### Cómo se aplican las paletas

`buildDocument` aplica la paleta en dos momentos, para que los colores vinculados funcionen tanto en los valores que hayas indicado tú como en los valores por defecto que se completan después:

1. `applyPaletteToConfig(config)`: resuelve todos los `ColorValue` de la configuración original del usuario que tienen un `paletteId`. Es útil si quieres ver lo que recibirá realmente el motor.
2. `applyPaletteToResolvedConfig(resolved, palette)`: se ejecuta *después* de resolver los valores por defecto y reescribe los valores por defecto vinculados a la paleta (el color de los encabezados, el de las negritas y cursivas del texto base, el de los `:ref`, los de las listas, los colores de los diseños por defecto) para que coincidan con la paleta activa.

Las dos recorren toda la configuración, así que no se queda atrás ningún color vinculado a la paleta. La mayoría de los colores del flujo de texto (texto base, encabezados, listas, tablas, pies, chips, y la caja, el título y el contenido de los recuadros) quedan como valores sin vínculo. Todos los demás (los colores de los diseños, el de los `:ref`, las etiquetas de los recuadros) toman el `hex` / `model` de la paleta y **conservan su `paletteId`**. Ese vínculo es lo que sustituyen en sus páginas el atributo `palette` de una parte y el `palette` de un estilo de encabezado (véase [Partes](/es/docs/configuration-styles#partes)), así que debe mantenerse. `htmlViewer.overrides` se deja tal como está: el visor HTML lo combina primero, y la paleta que contenga se aplica entonces a todo, incluidos los diseños.

Rara vez tendrás que llamarlas tú, pero las dos se exportan para que puedas examinarlas o reutilizarlas:

```ts
import {
  applyPaletteToConfig,
  applyPaletteToResolvedConfig,
  resolveColorValue,
} from 'postext';

const flat = applyPaletteToConfig(config);
// Cada ColorValue con paletteId en el config original lleva ahora el
// hex/model de la entrada de la paleta (un color de diseño conserva su paletteId).

// `applyPaletteToResolvedConfig` normalmente lo gestiona buildDocument; úsalo
// directamente si construyes un ResolvedConfig a mano y quieres aplicar la paleta.
```

`resolveColorValue(value, palette, fallback)` es la versión para un solo valor, práctica cuando construyes configuraciones por código y necesitas resolver los colores de uno en uno.

### Editar la paleta

Un color cuyo `paletteId` no corresponde a ninguna entrada imprime el `hex` / `model` que tiene guardado, que puede ser anterior al color que le daba la entrada. Por eso, antes de eliminar una entrada, conviene reescribir todos los `ColorValue` vinculados a ella como colores sin vínculo, con el valor actual de la entrada. La sección *Paleta* del Sandbox (**Diseño → Colores**) lo hace al eliminar una entrada, esté donde esté el color (incluidos los diseños y las etiquetas de los recuadros), y su confirmación enumera todos los ajustes que usan la entrada: por su nombre o por su ruta en la configuración (`header.elements[2].color`).

## Visor Canvas

La propiedad `canvasViewer` fija el espacio entre las páginas en la pestaña Canvas del Sandbox (desde postext 1.43). ## Generación de PDF (configuración)

La propiedad `pdfGeneration` controla cómo genera el documento final el backend de PDF. Estos ajustes los usa el paquete `postext-pdf` al exportar; el canvas y el visor HTML los ignoran.

`buildDocument` los incluye en el VDT, como `doc.config.pdfGeneration`, y `renderToPdf` toma cada ajuste del primer sitio en el que lo encuentra:

1. sus propias opciones (`outlines`, `accessible`, `colorSpace`);
2. el `pdfGeneration` del primer documento que recibe (en un libro, los ajustes del primer capítulo valen para todo el archivo);
3. los valores por defecto: marcadores y etiquetado activados, color RGB.

Así, `renderToPdf(doc, { fontProvider })` sigue la configuración, y una opción que se pasa a `renderToPdf` solo tiene prioridad en ese ajuste. `forceColorSpace` y `colorSpace` equivalen, juntos, a la opción `colorSpace`: el `colorSpace` de la configuración se aplica mientras `forceColorSpace` está activado, y si está desactivado, el PDF sale en RGB. Las versiones anteriores de `postext-pdf` solo leían las opciones; ahora, una configuración que fija `pdfGeneration` cambia el PDF de quien llama a la función sin opciones.

```ts
type PdfColorSpace = 'rgb' | 'cmyk' | 'grayscale';

interface PdfGenerationConfig {
  outlines?: boolean;          // Emitir marcadores PDF desde el árbol de encabezados.
  forceColorSpace?: boolean;   // Convertir todos los colores a `colorSpace`.
  colorSpace?: PdfColorSpace;  // Espacio destino cuando `forceColorSpace` es true.
  accessible?: boolean;        // Salida etiquetada orientada a PDF/UA (árbol de estructura, texto alternativo, idioma).
}
```

## Producción para imprenta (configuración)

La propiedad `print` indica cómo va un libro a la imprenta: la norma PDF/X del archivo, el perfil de salida con el que se separa su CMYK, cómo se imprime el negro y los umbrales de la verificación previa (preflight). La maquetación no la tiene en cuenta, así que cambiarla nunca desplaza ninguna línea. La leen tres componentes: `postext-pdf`, al escribir el archivo; `preflightDocument`, al revisar un documento ya maquetado, y la vista previa de impresión de los visores Canvas y Folio.

### PDF/X-1a y PDF/X-4

Las dos normas escriben:

- el *output intent* (`GTS_PDFX`), que indica la condición de impresión e incrusta el perfil de destino;
- la identificación en el diccionario Info (`GTS_PDFXVersion`, `/Trapped /False`, el título y las fechas) y en los metadatos XMP (`pdfxid:GTSPDFXVersion`, los ids del documento y de la versión), unida a la identificación PDF/UA cuando el archivo está etiquetado;
- una TrimBox y una BleedBox en cada página (la página entera cuando no hay marcas de corte);
- el `/ID` del trailer;
- todos los colores en DeviceCMYK (o en gris), separados con el perfil, y las marcas de corte en color de registro;
- ninguna anotación de enlace: un archivo para imprenta no lleva ninguna dentro de su caja de sangrado, así que se omiten los enlaces del PDF de pantalla (los marcadores se conservan).

PDF/X-1a:2003 es PDF 1.4 sin flujos de objetos y no admite transparencias: un color translúcido se convierte en el color que daría impreso sobre el papel, el canal alfa de una imagen se acopla sobre blanco y se omite el negativo de página de depuración (con un aviso `pageNegativeIgnored`). PDF/X-4 es PDF 1.6: se mantienen las transparencias, cada página recibe un grupo de transparencia que se funde en CMYK y las imágenes RGB que se conservan con `convertImages: false` se etiquetan como sRGB mediante `/DefaultRGB`.

Un original de imprenta en PDF (`svg.pdfFileId`) se incrusta tal cual, así que sus colores, sus fuentes y sus transparencias son los suyos; la verificación previa informa de lo que aporta.

`preflightDocument(doc, options)` ejecuta las comprobaciones sobre un documento maquetado y devuelve una lista de incidencias, cada una con un `kind`, una `severity` (`'critical'`, `'warning'` o `'info'`), el `pageIndex` absoluto en el libro, el `rect` afectado (en píxeles de página) y, cuando el elemento lo tiene, su rango en el texto de origen. Los tipos son `lowImageResolution`, `declaredPixelsMismatch`, `rgbImage`, `thinRule`, `smallProcessText`, `inkLimit`, `safeZone` y `nearTrim`. Sin un `transform`, un color neutro cuenta como una tinta y cualquier otro como tres, y no se comprueba la cobertura; con él, los recuentos y la cobertura son exactos. La resolución de una imagen se calcula a partir de los píxeles que declara su recurso o, cuando `imageSize(fileId)` los proporciona (`bitmapInfo` sobre los bytes, o la imagen decodificada), de los del propio archivo: una declaración que difiere del archivo en más de un píxel se notifica una vez como `declaredPixelsMismatch`, con nivel de aviso cuando declara más píxeles de los que tiene el archivo. `placedImageResolutions(doc, { resources, imageSize })` enumera todos los mapas de bits colocados con su resolución efectiva en ppp, esté activada o no la verificación previa. Los rótulos de una figura cuentan como texto para `smallProcessText`, `inkLimit` y `safeZone`.

```ts
import { bitmapInfo, outputTransform, parseIccProfile, preflightDocument, resolvePrintConfig } from 'postext';
import { inspectPrintMaster } from 'postext-pdf';

const print = resolvePrintConfig(config.print);
const transform = outputTransform(parseIccProfile(fogra51Bytes), { intent: print.renderingIntent });
const issues = preflightDocument(doc, {
  print,
  transform,
  resources,                                    // tamaños en píxeles de los mapas de bits
  imageSize: (fileId) => bitmapInfo(bytesOf(fileId)),  // los píxeles reales de los archivos
  imageColor: (fileId) => colourOf(fileId),     // 'rgb' | 'cmyk' | 'gray', según el archivo
});
if (issues.some((i) => i.severity === 'critical')) process.exit(1);

const master = await inspectPrintMaster(masterBytes);
// => { nonEmbeddedFonts: ['Helvetica'], rgb: true, transparency: false }
```

### Simulación de impresión

Una página de canvas se puede pintar tal como se imprimirá. `createPrintPreview(transform, print, { paper, dpi, grayscale })` crea la prueba en pantalla de una configuración de impresión: cada píxel se separa con el perfil (los neutros, solo en K, como en el PDF) y se vuelve a mostrar en pantalla, sobre el blanco del propio papel cuando `paper` es `true`; las masas negras lo bastante grandes para el negro enriquecido se ven como negro enriquecido. Con `grayscale`, la prueba es la de una impresión en escala de grises: un PDF forzado a escala de grises imprime la luminancia de cada color solo con tinta negra, sin negro enriquecido. Pásalo a `renderPageToCanvas` como `printPreview`. Para una vista de trabajo, y no para una prueba, `guides` añade las líneas del corte, del sangrado y de la zona segura, y `marksFor` recuadra zonas de una página (los `rect` de la verificación previa); el Sandbox prescinde de ambas, así que su vista previa solo muestra lo impreso. `postext-folio` acepta el mismo objeto como `printPreview`; con `paper: true`, da mientras tanto al libro un tono de papel neutro (`folio.paper.shade`), o el papel se teñirá dos veces.

```ts
import { createPrintPreview, renderPageToCanvas } from 'postext';

const preview = createPrintPreview(transform, print, { paper: true, dpi: doc.config.page.dpi });
renderPageToCanvas(page, doc, canvas, {
  printPreview: { ...preview, guides: { safeZonePx: 59 }, marksFor: () => issues.map((i) => i.rect!).filter(Boolean) },
});
```

### Motor de color

La gestión del color de postext se exporta para que puedas usarla en tus propias herramientas. Lee perfiles ICC v2 y v4 (matriz/TRC y las tablas de consulta `mft1`, `mft2`, `mAB` y `mBA`) en TypeScript puro, sin WebAssembly.

- `parseIccProfile(bytes)` lee un perfil; `deviceChannels(profile)` da su número de canales.
- `outputTransform(profile, { intent, blackPointCompensation, preserveNeutrals })` devuelve `fromRgb(r, g, b)` (sRGB 0..1 → CMYK 0..1), `toLab(cmyk, paper?)` y `proof(cmyk, paper?)` (CMYK → sRGB de pantalla).
- `cmykToLab`, `labToCmyk`, `srgbToLab`, `labToSrgb`, `deltaE` y `totalAreaCoverage` son las conversiones individuales; `buildRgbLut` / `sampleRgbLut` crean y leen tablas de consulta densas para trabajar píxel a píxel.
- `OUTPUT_PROFILES`, `outputProfileInfo(id)` y `loadOutputProfile(id, baseUrl?)` dan el catálogo; `srgbProfileBytes()` escribe el perfil sRGB con el que PDF/X-4 etiqueta el RGB; `authoredCmykColors(config)` enumera los colores que una configuración define en CMYK.

Las funciones de resolución y de limpieza siguen el mismo patrón que en las demás secciones: `resolvePrintConfig`, `stripPrintDefaults` y `profileInkLimit(config)` (el límite del perfil que indica una configuración, antes de que lo sustituya `inkLimit`), con `DEFAULT_PRINT_CONFIG`, `DEFAULT_PRINT_BLACK_CONFIG`, `DEFAULT_PRINT_PREFLIGHT_CONFIG` y `DEFAULT_RICH_BLACK`.

### Pares aceptados

Una adaptación conserva la paleta del original, y algunos de sus pares quedan bajo el umbral: un tinte claro detrás del texto de un recuadro, un color de marca en un titulillo. `allow` los acepta sin apagar la comprobación (desde postext 1.52). Una entrada nombra el color del texto `fg` y el del fondo `bg` (en hexadecimal, tal como los escribe la configuración o como se pintan), o un `style`: el id de un estilo de recuadro (`calloutStyles`, o el `style` de un marco de página compuesta), de párrafo, de título, de etiqueta en línea o de rótulo de figura. Todos los campos que da una entrada tienen que coincidir, así que `{ style: 'note', fg: '#7a8a99' }` acepta ese gris solo dentro de los recuadros `note`. Una entrada que no da ninguno de los tres no coincide con nada.

```ts
contrast: {
  allow: [
    { fg: '#b7820f', bg: '#ffffff', reason: 'El ocre de la editorial para los titulillos' },
    { style: 'nota-margen', reason: 'El original compone sus notas al margen en un gris claro' },
  ],
}
```

Un par aceptado se sigue señalando: cada hallazgo que coincide lleva `accepted` (el `reason` de la entrada, con su `fg`, su `bg` y su `style`), y los hallazgos aceptados van después de los demás. El Sandbox los muestra en Comprobaciones, bajo Pares de contraste aceptados, con el motivo, y no los cuenta; `postext check` los imprime como notas, que no hacen fallar `--strict`. Los mismos colores fuera de lo que nombra la entrada siguen siendo un aviso.

### Pantalla e imprenta

Postext compone las mismas páginas para la pantalla y para la imprenta, y un color no se lee igual en una y en otra.

- **Pantalla** es la ratio de contraste de WCAG 2 entre los colores sRGB, `(L1 + 0.05) / (L2 + 0.05)`, calculada con sus luminancias relativas: lo que muestran el canvas, el visor HTML, un EPUB y un PDF en RGB.
- **Imprenta** es la misma fórmula, calculada con la luminancia que tiene cada color sobre el papel. El color se separa con el perfil de salida del trabajo (uno definido en CMYK conserva sus valores), la separación se vuelve a leer a través del perfil y su luminancia se toma respecto al papel sin imprimir, que es el blanco de una página impresa igual que el blanco del monitor es el de una pantalla. La tinta nunca da un negro perfecto: un negro sólido sobre blanco da unos 14:1 en papel estucado (FOGRA39, FOGRA51), 8:1 en papel sin estucar (FOGRA47, FOGRA52) y 5:1 en papel prensa (IFRA26, SNAP), cuando una pantalla da 21:1. Un gris que pasa en pantalla puede no pasar en papel: `#767676` sobre blanco da 4,54:1 en pantalla y unos 3,3:1 en papel estucado.

La ratio de imprenta necesita el `transform` del perfil de salida (`options.transform`, creado con `outputTransform`). Sin él, en la impresión solo se comprueba el texto calado.

### Texto calado

El texto claro calado sobre un fondo entintado se empasta en la máquina cuando es pequeño o de trazo fino: la tinta del fondo invade las letras, y un fondo formado por varias tintas depende además de que las planchas no pierdan el registro. La ratio no lo refleja, porque un blanco sobre azul oscuro supera 10:1. La comprobación de impresión notifica ese texto aparte (`reversedText`) cuando queda por debajo de `minSize`, o por debajo de `minFineSize` si es cursiva o tiene un peso de `lightWeight` o menos. Cada incidencia indica cuántas de las cuatro tintas forman el fondo.

### Qué se lee

La comprobación lee las líneas de cada bloque con sus colores en línea (negrita, cursiva, referencias, chips), los marcadores de lista, las capitulares, los pies, las notas y las celdas de tabla, y el texto de las zonas de diseño: titulillos, aperturas, diseños de encabezado, títulos de recuadro. El fondo es el relleno superior que hay bajo el texto: una caja de diseño, un recuadro, una barra de pie, una celda de tabla, un chip o, si no hay ninguno, el color de la página (`page.backgroundColor`, o el papel que la paleta de una parte da a sus páginas). Un color translúcido se mezcla con lo que tiene debajo. Se omite el texto sobre una imagen, porque su fondo no es de un solo color, y también la rotulación de los cómics, las lecturas ruby y las fórmulas. Las palabras de los rótulos de una figura se leen sobre su placa o, si tienen halo, dentro de él; los rótulos que van directamente sobre la imagen se omiten, como cualquier texto sobre una imagen.

En una página compuesta, la comprobación sigue el orden en que se pinta la página: los marcos por capas, con la `decoration` de la plantilla en la capa 0. El texto de un marco se lee sobre la caja del propio marco cuando su estilo la pinta; si no, sobre la caja de la decoración que tiene debajo (el texto sobre una imagen de la decoración se omite, como sobre cualquier imagen), y si no, sobre el color de la página. Así, unas letras blancas sobre una pestaña de color de la decoración se miden contra esa pestaña. Un marco girado o escalado se coloca en la hoja antes de leer su fondo, y el texto de la propia decoración se comprueba del mismo modo. Desde postext 1.37.

### Ejecutar la comprobación

`contrastDocument(doc, options)` devuelve las incidencias de un documento maquetado, empezando por la ratio más baja. Cada una lleva el `pageIndex` absoluto en el libro, el `rect` en la hoja (en píxeles de página) y el rango en el texto de origen de su primera aparición, los dos colores tal como se pintan (`color`, `background`), el menor `sizePt` con que se compone, con su `weight` y su `italic`, un `role` (`'body'`, `'heading'`, `'caption'`, `'table'`, `'runningHead'`, `'design'`, `'chip'`, `'marker'` o `'label'`, las palabras de los rótulos de una figura), el `text` del primer tramo y el `count` de tramos compuestos así. Cada par se notifica una vez por umbral, por muchas líneas que lo usen.

- `lowContrast` añade `level`, `large`, `required`, la ratio en cada medio comprobado (`screen`, `print`) y `failing`, los medios que quedan por debajo de `required`.
- `reversedText` añade `reasons` (`'small'`, `'italic'`, `'light'`), `minimumPt` e `inks`.

Las opciones son `contrast` (los ajustes resueltos, cuando no son los del documento), `media` (los medios, diga lo que diga `mode`) y `transform`.

```ts
import { contrastDocument, outputTransform, parseIccProfile } from 'postext';

const transform = outputTransform(parseIccProfile(fogra51Bytes));
for (const issue of contrastDocument(doc, { transform })) {
  if (issue.kind === 'lowContrast') {
    console.log(`${issue.color} on ${issue.background}: ${issue.screen}:1, ${issue.level} asks for ${issue.required}:1`);
  }
}
```

`contrastPairs(doc, options)` devuelve todos los pares de texto y fondo del documento, cumplan o no, con su ratio `screen`, su ratio `print` cuando se proporciona el `transform`, la ratio `required` y los colores tal como los escribe la configuración (`textColor`, `groundColor`): lo que una herramienta de diseño muestra junto a un campo de color. Se ejecuta diga lo que diga `enabled`.

Las medidas se exportan para tus propias herramientas:

- `contrastRatio(a, b)` y `relativeLuminance(color)` dan la ratio y la luminancia de WCAG 2 de colores sRGB.
- `isLargeText(sizePt, weight)` y `contrastThreshold(level, large)` dan el umbral que corresponde a un cuerpo y un peso.
- `blendColors(top, under)` da un color translúcido sobre otro, como `#rrggbb`.
- `printContrastRatio(a, b, context)`, `printLuminance(color, context)` y `printSeparation(color, context)` dan lo mismo sobre el papel. El contexto lleva el `transform` y, como `authored`, el resultado de `authoredCmykColors(config)`.
- `contrastMedia(doc.config, contrast)` da los medios en que se resuelve `mode` para un documento.

Las funciones de resolución y de limpieza siguen el mismo patrón que en las demás secciones: `resolveContrastConfig` y `stripContrastDefaults`, con `DEFAULT_CONTRAST_CONFIG`, `DEFAULT_CONTRAST_REVERSED_TEXT_CONFIG`, `CONTRAST_LEVELS` y `CONTRAST_MODES`.


## Comprobación del contenido (configuración)

La propiedad `checks` reúne las comprobaciones que revisan la propia configuración. Por ahora tiene una, `contentInConfig`, que avisa cuando un diseño contiene texto del libro. Un titulillo, el diseño de un encabezado, una página de parte y la fila de una parte en el índice son forma: llevan marcadores (`{chapterTitle}`, `{titleText}`, `{number}`) y, como mucho, una o dos palabras propias, como *Capítulo* delante de `{chapterNumber}`. El texto que forma parte del libro va en el Markdown, donde lo ven el índice, la búsqueda, las traducciones, el PDF etiquetado y el EPUB. La maquetación no tiene en cuenta esta comprobación, así que cambiarla nunca desplaza ninguna línea.

### Cómo se lee un texto de diseño

- Su texto literal es su `content` sin ninguno de sus marcadores (`{name}`, `{attr.key}`, `{firstMark.key}`), con los escapes `{{` y `}}` leídos como llaves y `\n` como salto de línea.
- Un texto sin letras ni cifras (una fila de puntos conductores, un adorno, un `·`) nunca cuenta como contenido.
- Una palabra es lo que hay entre espacios y contiene una letra o una cifra: un `·` o una `|` sueltos no son palabras, y una dirección como `postext.dev` es una sola.
- Primero se descuentan las frases de `allow`, y también el `title`, el `subtitle`, el `author` y el `publisher` de los metadatos del documento (su *front matter*), que un titulillo suele repetir.
- Lo que queda es contenido cuando tiene más de `maxWords` palabras o más de `maxChars` letras y cifras.

Se revisan todas las zonas de diseño: `header`, `footer`, el `advancedDesign.slot` de cada nivel de encabezado, el `advancedDesign.slot`, el `header` y el `footer` de cada estilo de encabezado, `parts.design`, `parts.versoDesign`, `toc.parts.design`, y lo mismo dentro de `htmlViewer.overrides`. `configDesignSlots(config)` las enumera con sus rutas, y `designTextLiteral(content)` devuelve el texto literal de una plantilla.

### El aviso

`collectConfigWarnings` (y `VDTDocument.configWarnings`) da un aviso `contentInConfig` por cada ajuste que guarda contenido: un estilo de encabezado (con su `id` en `ownerId`), un nivel de encabezado, la cabecera, el diseño de una parte. `path` indica el ajuste; `count`, los textos de diseño afectados; `chars`, sus letras y cifras; `elements`, la ruta de cada uno (los 20 primeros), y `value`, el principio del primer texto (40 caracteres como máximo). Pasa los metadatos del documento como segundo argumento para que se admitan su título y su autor; una compilación lo hace por sí sola.

```js
import { collectConfigWarnings } from 'postext';

collectConfigWarnings(config, { metadata: { title: 'A Year of Weather' } });
// [{ kind: 'contentInConfig', path: 'headingStyles[3]', ownerId: 'lesson-4',
//    value: 'Look at the picture and answer the questi…', used: '',
//    count: 30, chars: 1017, elements: ['headingStyles[3].header.elements[2]', …] }]
```

**Solución:** pasa el texto al Markdown, como encabezado, recuadro o párrafo del capítulo al que pertenece, y deja solo marcadores en el diseño. Un valor que cambia en cada capítulo puede ir en la línea del encabezado y leerse con `{attr.key}`: `# Mapas {kicker="Lección 4"}` y `{attr.kicker}` en el diseño. Una frase que forma parte de la forma, como el nombre de la editorial en un titulillo, va en `allow`.

El Sandbox muestra el aviso en el panel **Revisión** y ofrece la comprobación en **Diseño → Avanzado → Contenido en la configuración**; `postext check` lo imprime.


## Visor Folio (configuración)

La propiedad `folio` determina cómo presenta el visor Folio (`postext-folio`) el libro impreso en 3D: el ángulo de la vista, el papel, la encuadernación, la superficie sobre la que descansa el libro y la luz. La maquetación no la tiene en cuenta, ni tampoco las salidas de canvas, HTML y PDF. `buildDocument` incluye los ajustes resueltos en el VDT, como `doc.config.folio`, cuando la configuración fija alguno, de modo que un documento sin ellos conserva el hash de su maquetación.

Una página con formato de periódico (`page.sizePreset` `'broadsheet'`, `'berliner'`, `'tabloid'` o `'compact'`) se muestra como un periódico cuando la configuración no indica papel ni encuadernación: papel `newsprint` y encuadernación `folded` (desde postext 1.18). El papel o la encuadernación que indique la configuración se respetan, así que `paper: { type: 'uncoated' }` imprime un tabloide en papel offset. Los campos del papel que se fijan sin indicar el tipo (un `grammage`, un `shade`) se aplican al papel prensa. Las funciones de resolución y de limpieza reciben el formato como segundo argumento, y `folioForTrim(folio, sizePreset)` escribe esos dos valores por defecto en la configuración:

```ts
resolveFolioConfig({ tilt: 30 }, 'tabloid');
// => { tilt: 30, paper: { type: 'newsprint', grammage: 48, bulk: 1.5, … }, binding: { type: 'folded', coverMaterial: 'paper', … }, … }

stripFolioDefaults({ paper: { type: 'newsprint' }, binding: { type: 'folded' } }, 'tabloid');
// => undefined
```

Los colores siguen los vínculos con la paleta como cualquier otro color de la configuración (`paletteId`). Las funciones de resolución y de limpieza siguen el mismo patrón que en las demás secciones; la de limpieza quita los valores del papel que coinciden con los del tipo elegido:

```ts
import { FOLIO_PAPER_STOCKS, DEFAULT_FOLIO_CONFIG, resolveFolioConfig, stripFolioDefaults } from 'postext';

resolveFolioConfig({ paper: { type: 'bible' } }).paper;
// => { type: 'bible', grammage: 40, bulk: 1.1, finish: 'uncoated', texture: 'vellum', textureStrength: 1, shade: { hex: '#f9f6ee', … }, showThrough: true }

stripFolioDefaults({ paper: { type: 'bible', grammage: 40 } });
// => { paper: { type: 'bible' } }
```

En el Sandbox, estos ajustes forman el grupo **Folio** del panel Diseño (**Diseño → Folio → Visor Folio (3D)**), y la pestaña Folio los refleja a medida que los cambias, sin volver a maquetar el libro. El visor en sí se describe en [Un libro en 3D](/es/docs/configuration-html-folio-epub#un-libro-en-3d-postext-folio), y una serie de páginas en otro papel, en [Formato del documento › `:::paper`](/es/docs/document-format-directives#paper).

### Líneas flojas en tu propio canvas

El motor exporta el resaltado de líneas flojas como dos funciones auxiliares, para una página que pintas tú:

```ts
import { buildDocument, renderPageToCanvas, drawLooseLines, findLooseLines } from 'postext';

const doc = buildDocument(content, config);
const canvas = document.querySelector('canvas')!;
renderPageToCanvas(doc.pages[0], doc, canvas, { scale: 0.5 });
drawLooseLines(canvas.getContext('2d')!, doc.pages[0], doc, { threshold: 2.5 });

// Las mismas líneas como datos: un informe, una capa SVG, un recuento por página.
for (const { ratio, line, block } of findLooseLines(doc, { threshold: 2.5 })) {
  console.log(`página ${block.pageIndex + 1}: ${ratio.toFixed(2)}× — ${line.text}`);
}
```

- **`findLooseLines(doc, { threshold?, pageIndex? })`** devuelve, en orden de lectura, todas las líneas justificadas cuyo espaciado entre palabras supera `threshold`: `{ block, line, ratio, x, y, width, height }`. `ratio` es `lineWordSpacing(line)`: el espaciado tal como lo acotan `minWordSpacing` y `maxWordSpacing` (`justifiedSpaceLimitRatio` cuando la línea contiene espacios de otro estilo de fuente y, si no, `justifiedSpaceRatio`), así que una línea compuesta en el límite que contiene un espacio en negrita no se notifica con un umbral igual a `maxWordSpacing`. El rectángulo, en píxeles de página, es la franja que cubre el resaltado: todo el ancho del bloque a la altura de la línea. Son las líneas que el Sandbox resalta y que su panel Revisión notifica como `looseLine`.
- **`drawLooseLines(ctx, page, doc, { threshold?, color? })`** rellena esas franjas en una página y devuelve las líneas que ha pintado. Dibuja en píxeles de página con la transformación actual del contexto, así que llámala justo después de `renderPage` o `renderPageToCanvas` sobre el mismo canvas: ambas dejan el contexto escalado a la página. `color` es cualquier estilo de relleno del canvas.
- **Valores por defecto.** Las dos funciones usan el umbral (3) y el color (`#ff000040`) por defecto, no el `debug.looseLineHighlight` del documento: ese ajuste es del Sandbox. Para seguir una configuración, pasa `resolveDebugConfig(config.debug).looseLineHighlight.threshold` y `.color.hex`.

Estos interruptores solo filtran el panel del Sandbox. ### Avisos de configuración

Estos errores de la propia configuración nunca pasan inadvertidos, y ningún interruptor los oculta salvo el que indica el último punto. El motor no falla por ninguno de ellos: sustituye el valor, o prescinde del ajuste, y lo notifica:

- **Formato de numeración desconocido**: un `numberFormat` de lista numerada, un `page.pageNumbering.format` o el `counterFormat` de un tipo de recurso que no corresponde a ninguna de las [grafías de los formatos de numeración](/es/docs/configuration-page-layout#grafías-de-los-formatos-de-numeración). Se numera en decimal.
- **Lista de fuentes en una familia**: un `fontFamily` (o cualquier `…FontFamily`) que contiene una lista de fuentes CSS. El texto se compone con la primera familia de la lista (véase [Una sola familia por `fontFamily`](/es/docs/configuration-text#una-sola-familia-por-fontfamily)).
- **Columna lateral sin sitio**: un `sideColumnPercent` de una disposición `'oneAndHalf'` (la del documento, o el `layout` propio de un estilo de encabezado) que dejaría alguna de las columnas por debajo del 1 % del ancho del área de contenido, o que no es un número. Las columnas se ajustan al valor más cercano que admiten las dos, y `used` lo indica (`sideColumnPercentClamped`; véase la [disposición `'oneAndHalf'`](/es/docs/configuration-page-layout#tipos-de-disposición)).
- **Número de columnas fuera de rango**: un `columnCount` de una disposición `'multiple'` (la del documento, o el `layout` propio de un estilo de encabezado) que no es un número entero de 3 a 8. La página se divide en el número válido más cercano (3 si el valor no es un número), y `used` lo indica (`columnCountClamped`; véase la [disposición `'multiple'`](/es/docs/configuration-page-layout#tipos-de-disposición)).
- **Retícula de caracteres demasiado grande**: un `cjk.grid` con más caracteres por línea o más líneas por página de los que caben entre los márgenes. La retícula se compone con el máximo que cabe, y `used` indica el número (`cjkGridClamped`; véase [Retícula de caracteres](/es/docs/configuration-east-asian#retícula-de-caracteres)).
- **Ajuste de encabezado desconocido**: una clave que no existe en `headings`, `headings.balancing`, un nivel de encabezado, un estilo de encabezado o un estilo de párrafo: un `letterSpacng` mal escrito, un `tracking` tomado de otra herramienta, un `level` en un estilo de encabezado, un `fontStyle: 'italic'` en un estilo de párrafo (que usa `italic: true`). Una tabulación se comprueba del mismo modo (un `leaders` en lugar de `leader`), y también una capitular, `lineNumbers`, `canvasViewer`, `checks`, `codeStyle` y los ajustes de cómic. El motor la ignora (hasta postext 1.4 lo hacía sin avisar). `value` es la clave, `used` queda vacío y `suggestion` indica el ajuste al que más se parece, cuando solo difiere en una o dos letras o en las mayúsculas (`unknownConfigKey`).
- **Valor de ajuste desconocido**: un ajuste que admite unas pocas palabras contiene otra, como `direction: 'right'` (admite `auto`, `ltr` o `rtl`). El motor lee en su lugar el valor por defecto, y `used` indica en qué se ha traducido: para `direction`, la dirección del idioma del documento (`unknownConfigValue`). Un `align` de tabulación que no es ninguna de sus cuatro palabras se lee como `'start'`, y una `position` que no es una longitud, `'end'` ni un porcentaje descarta la tabulación (`used` es `'none'`). También se comprueban las palabras de los ajustes de cómic ([Cómics › Avisos de cómic](/es/docs/comics#avisos-de-cómic)): `used` es el valor que ha tomado el ajuste (el valor por defecto del propio estilo de bocadillo, en un estilo integrado), y `suggestion` indica la palabra a la que más se parece el valor, cuando hay alguna parecida. El `level` y el `mode` de la comprobación del contraste se comprueban del mismo modo: `used` es `'AA'` o `'auto'`. `canvasViewer.pageGap` y `canvasViewer.rowGap` también se comprueban así: `used` es el número entero de 0 a 200 con el que se ha leído el valor (desde postext 1.43). También `print.standard`, `print.outputProfile` y `print.renderingIntent` (`used` es lo que dio el valor por defecto), y un `maxWords` o `maxChars` de `checks.contentInConfig` que no sea un número entero igual o mayor que 0.
- **Números de línea en texto vertical**: `lineNumbers.enabled: true` en un documento compuesto en vertical (`layout.writingMode: 'vertical-rl'`). Las páginas verticales no llevan números de línea, y `used` es `false` (`lineNumbersUnsupported`; véase [Numeración de líneas](/es/docs/configuration-notes-references#numeración-de-líneas)).
- **Texto alrededor de figuras en escritura vertical**: el `defaultPlacement.wrap` de un tipo de recurso en un documento compuesto en vertical. Las páginas verticales no componen texto al lado de una figura, y `used` es `none` (`wrapUnsupported`; véase [Formato del documento › Ajuste del texto](/es/docs/document-format-resources#ajuste-del-texto)). Un `wrap` que no indica ningún lado es un valor de ajuste desconocido.
- **Estilo de recuadro basado en otro**: un estilo de recuadro cuyo `extends` no remite a ningún estilo de `calloutStyles` (`calloutStyleExtendsUnknown`, con el id más parecido en `suggestion`), o cuya cadena de `extends` vuelve a él (`calloutStyleExtendsCycle`, con el bucle `a → b → a` en `value`). El estilo queda aislado, con los valores integrados en lo que no fija (véase [Estilos basados en otro](/es/docs/configuration-callouts#estilos-basados-en-otro)).
- **Plantillas de página y estilos de rótulo**: un problema en `pageTemplates` o `labelStyles`: un id o un nombre repetido, `extends`, anclajes o marcos encadenados que forman un bucle, un estilo, un marco o una plantilla que no existe, un mínimo mayor que su máximo, o un estilo de rótulo de un anclaje que no está en `labelStyles` (esto se comprueba cuando se pasan los recursos: `collectConfigWarnings(config, { resources })`). Su `path` es un puntero JSON (`/pageTemplates/3/frames/2/style`); cada tipo aparece con su causa y su solución en [Avisos de las plantillas de página](/es/docs/configuration-composed-pages#avisos-de-las-plantillas-de-página).
- **Contenido en un diseño**: un elemento de texto de diseño cuyo texto, sin contar los marcadores, es más largo que una etiqueta breve: el texto del libro guardado en la configuración. Un aviso por ajuste (un estilo de encabezado, la cabecera, el diseño de una parte), con la ruta de cada texto (`contentInConfig`; véase [Comprobación del contenido](#comprobación-del-contenido-configuración)). A diferencia de los demás, se puede desactivar: `checks.contentInConfig.enabled: false`.

El Sandbox los muestra en el panel **Revisión** con la ruta del ajuste. En el código, `buildDocument` los deja en el documento como `configWarnings` (que no aparece cuando la configuración no tiene errores), y `collectConfigWarnings(config)` los devuelve sin maquetar nada:

```js
import { buildDocument, collectConfigWarnings } from 'postext';

// JavaScript sin tipos: en TypeScript, 'roman' ni siquiera pasa la comprobación de tipos.
const config = { bodyText: { fontFamily: 'EB Garamond, serif' }, orderedLists: { numberFormat: 'roman' } };
const doc = buildDocument({ markdown }, config);
doc.configWarnings;
// [{ kind: 'fontFamilyStack', path: 'bodyText.fontFamily', value: 'EB Garamond, serif', used: 'EB Garamond' },
//  { kind: 'unknownNumberFormat', path: 'orderedLists.numberFormat', value: 'roman', used: 'arabic' }]
collectConfigWarnings(config); // la misma lista
```

También se revisan todas las configuraciones parciales anidadas: los estilos de encabezado, las listas dentro de las partes, `htmlViewer.overrides`, los elementos de diseño.

`formatWarning` (véase [Avisos del documento](/es/docs/configuration-programmatic-usage#avisos-del-documento)) también los describe, con la ruta del ajuste delante (`bodyText.fontFamily: font stack "EB Garamond, serif" — set in "EB Garamond"`, `headingStyles[0].letterSpacng: unknown setting "letterSpacng" — ignored (did you mean "letterSpacing"?)`), de modo que una aplicación anfitriona puede registrar con un solo bucle las tres listas que devuelve una compilación.
