# Utilisation programmatique : HTML, Folio, EPUB et SCORM


## Intégrer la visionneuse HTML

La visionneuse HTML est le moteur de rendu de Postext conçu d’abord pour l’écran. Au lieu de rastériser les pages en image bitmap, elle produit des nœuds DOM positionnés en absolu, dont la géométrie vient du même pipeline que la sortie imprimée. C’est donc le bon choix quand vous voulez, dans un navigateur, une typographie lisible, sélectionnable et qui suit le redimensionnement (une application de lecture, un aperçu intégré à un produit, une documentation embarquée) sans charger de visionneuse PDF.

Les pièces essentielles de l’API publique :

- **`buildDocument(content, config, cache?)`** : exécute tout le pipeline de mise en page et renvoie un `VDTDocument`.
- **`renderToHtmlIndexed(doc, options)`** : transforme le VDT en une seule chaîne HTML accompagnée d’un découpage par page et par bloc. Ce découpage permet de patcher le DOM à peu de frais quand seuls quelques blocs ont changé d’un rendu à l’autre.
- **`resolveHtmlViewerConfig(partial)`** : complète la configuration avec les valeurs par défaut de la visionneuse HTML (`maxCharsPerLine`, `columnGap`, `optimalLineBreaking`).
- **`buildFontString` + `measureGlyphWidth` + `dimensionToPx`** : primitives de mesure qui servent à déduire une largeur de colonne réelle, en pixels, d’un nombre de caractères visé.
- **`createMeasurementCache` / `clearMeasurementCache`** : caches interchangeables qui permettent de réutiliser les mesures d’une mise en page à l’autre.
- **`prepareFonts` / `buildDocumentWithFonts` / `watchFonts` / `onFontsChanged`** : chargent les fontes du document avant la mise en page et relancent la mise en page quand des fontes arrivent (voir [Charger les polices avant la mise en page](/fr/docs/configuration-programmatic-usage#charger-les-polices-avant-la-mise-en-page)).

### Exemple en direct : une chaîne HTML

L’aller-retour complet en JavaScript simple, avant l’intégration React plus bas : construisez le document, passez le `VDTDocument` à `renderToHtml` et déposez la chaîne dans un conteneur. `mode: 'single'` empile les pages verticalement ; `background` leur donne une couleur, car les pages sont transparentes par défaut. L’exemple CodePen affiche aussi le balisage généré : vous y voyez les lignes positionnées en absolu que produit le moteur de rendu, que le navigateur peint sans jamais les recomposer.

### Intégration minimale

L’extrait ci-dessous est l’intégration utile la plus courte : construire le document à la taille actuelle de la fenêtre, le rendre dans un conteneur et recommencer à chaque redimensionnement.

```tsx
import { useEffect, useRef } from 'react';
import {
  buildDocument,
  renderToHtmlIndexed,
  resolveHtmlViewerConfig,
  buildFontString,
  measureGlyphWidth,
  dimensionToPx,
  createMeasurementCache,
  watchFonts,
  onFontsChanged,
} from 'postext';
import type { PostextConfig, MeasurementCache } from 'postext';

// Screen-friendly DPI: at 144 DPI, an 8pt body size resolves to 16 px.
const HTML_DPI = 144;
const PADDING_PX = 24;

// Prose sample used to measure the target column width. Proportional fonts
// make "N × average width" unreliable, so we measure a representative string.
const SAMPLE =
  'The quick brown fox jumps over the lazy dog. Sphinx of black quartz, judge my vow.';

function sampleForChars(n: number): string {
  let s = SAMPLE;
  while (s.length < n) s += ' ' + SAMPLE;
  return s.slice(0, n);
}

export function PostextHtmlViewer({
  markdown,
  config,
  mode = 'multi',
}: {
  markdown: string;
  config: PostextConfig;
  mode?: 'single' | 'multi';
}) {
  const hostRef = useRef<HTMLDivElement | null>(null);
  const cacheRef = useRef<MeasurementCache>(createMeasurementCache());

  useEffect(() => {
    const host = hostRef.current;
    if (!host) return;

    const relayout = () => {
      const rect = host.getBoundingClientRect();
      if (rect.width === 0 || rect.height === 0) return;

      const viewer = resolveHtmlViewerConfig(config.htmlViewer);
      const fontFamily = config.bodyText?.fontFamily ?? 'EB Garamond';
      const fontWeight = config.bodyText?.fontWeight ?? 400;
      const fontSize = config.bodyText?.fontSize ?? { value: 8, unit: 'pt' as const };
      const fontSizePx = dimensionToPx(fontSize, HTML_DPI);

      // Measure the *actual* column width for N characters of body prose.
      const targetColumnPx = measureGlyphWidth(
        sampleForChars(viewer.maxCharsPerLine),
        buildFontString(fontFamily, fontSizePx, String(fontWeight), 'normal'),
      );

      const inner = Math.max(rect.width - PADDING_PX * 2, 100);
      let columnWidthPx: number;
      if (mode === 'single') {
        columnWidthPx = Math.min(targetColumnPx, inner);
      } else {
        // Fit as many columns as we can at the target width.
        const count = Math.max(
          1,
          Math.floor((inner + viewer.columnGap) / (targetColumnPx + viewer.columnGap)),
        );
        columnWidthPx = (inner - viewer.columnGap * (count - 1)) / count;
      }
      columnWidthPx = Math.max(Math.floor(columnWidthPx), 80);

      // Single mode uses one very tall page; multi mode uses the viewport
      // height so each VDT "page" becomes one column.
      const pageHeightPx =
        mode === 'single' ? Math.max(rect.height * 20, 200_000) : Math.max(rect.height - PADDING_PX * 2, 400);

      const override: PostextConfig = {
        ...config,
        page: {
          ...config.page,
          dpi: HTML_DPI,
          width: { value: columnWidthPx, unit: 'px' },
          height: { value: pageHeightPx, unit: 'px' },
          margins: {
            top: { value: 0, unit: 'px' },
            bottom: { value: 0, unit: 'px' },
            left: { value: 0, unit: 'px' },
            right: { value: 0, unit: 'px' },
          },
        },
        layout: { ...config.layout, layoutType: 'single' },
        bodyText: {
          ...config.bodyText,
          optimalLineBreaking: viewer.optimalLineBreaking,
        },
      };

      const doc = buildDocument({ markdown }, override, cacheRef.current);
      const { html } = renderToHtmlIndexed(doc, {
        mode,
        columnGap: viewer.columnGap,
        padding: PADDING_PX,
        background: 'transparent',
      });

      host.innerHTML = html;
    };

    relayout();

    const ro = new ResizeObserver(() => relayout());
    ro.observe(host);

    // Re-measure when web fonts land so glyph widths aren't taken from fallbacks.
    const stopWatching = watchFonts();
    const off = onFontsChanged(() => relayout());

    return () => {
      ro.disconnect();
      off();
      stopWatching();
    };
  }, [markdown, config, mode]);

  return <div ref={hostRef} style={{ width: '100%', height: '100%', overflow: 'auto' }} />;
}
```

Quelques remarques sur ce que fait cet exemple :

- **Mesurer la colonne plutôt que l’estimer.** Comme `maxCharsPerLine` est une *cible* exprimée en caractères, la largeur réelle en pixels dépend de la police du texte courant. `measureGlyphWidth` donne une vraie mesure dans la police choisie, ce qui garde la longueur de ligne constante quand on change de police.
- **Réécrire la page.** La visionneuse HTML traite chaque « page » du VDT comme une colonne à l’écran. L’exemple remplace `page.width` par la largeur de colonne mesurée, met les marges à zéro (la marge intérieure se trouve hors de la page, dans le div `.pt-doc` qui l’enveloppe) et utilise `HTML_DPI = 144` pour qu’un texte courant de `8pt` donne `16px`.
- **Tenir compte du chargement des polices.** `watchFonts` écoute `document.fonts` et, une fois par image, oublie ce qui a été mesuré dans les familles dont des fontes sont arrivées ; `onFontsChanged` relance ensuite la mise en page de la colonne. Sans cette relance, le premier rendu utilise les métriques d’une police de secours et saute quand la vraie police arrive.
- **Réutiliser le cache de mesures.** Créer le cache une seule fois par composant permet aux redimensionnements et aux changements d’échelle de police de reprendre les mesures du rendu précédent au lieu de remesurer chaque paragraphe.

### Aller plus loin

L’exemple ci-dessus est volontairement dépouillé. Les intégrations en production ajoutent en général :

- **L’isolation par Shadow DOM** : rendre dans `host.attachShadow({ mode: 'open' })` pour qu’aucune règle CSS de la page extérieure ne déborde sur la visionneuse.
- **Le patch incrémental** : `renderToHtmlIndexed` renvoie `pages[i].blocks`, chacun avec un `id` stable et le HTML extérieur du bloc. Quand seuls quelques blocs diffèrent entre deux rendus, vous pouvez remplacer ces enveloppes de blocs sur place au lieu de reconstruire `innerHTML`.
- **Les calques** : superposer un SVG positionné en absolu sur chaque `.pt-page` pour les curseurs, les sélections ou les grilles de ligne de base.
- **Les liens** : les mots d’un lien Markdown sont enveloppés dans `<a href="…" rel="noopener noreferrer">`, qui prend la couleur du texte et n’est pas souligné ; voir [Format du document › Liens](/fr/docs/document-format-inline#liens). Dans une visionneuse de type éditeur, interceptez les clics sur les `a[href]` qui ne commencent pas par `#` et ouvrez-les dans un nouvel onglet (les ancres de `:ref` renvoient à l’intérieur du document).
- **Les exercices interactifs** : le HTML d’un document qui contient des blocs `:::exercise` porte leurs données dans un `<script type="application/json" class="pt-exercises">`, mais aucun code pour y répondre : c’est la page qui l’affiche qui ajoute les commandes. Une fois le balisage en place, appelez `attachExercises(root, options?)` de `postext` sur l’élément (ou la racine fantôme) qui le contient, et appelez la fonction qu’il renvoie avant de remplacer ce balisage. `attachExercises` place sur les pages les champs de saisie, les choix à cocher et la barre des boutons « Vérifier », « Voir la solution » et « Recommencer », et ajoute sa propre feuille de style. `storageKey` nomme le livre et le chapitre sous lesquels les réponses sont conservées, `store` les garde ailleurs que dans `localStorage` (tout objet doté de `getItem`, `setItem` et `removeItem`), et `onResult(result)` reçoit chaque vérification, chaque recommencement et chaque solution affichée, avec le score (`right` sur `total`) et chaque réponse notée. Un hôte qui remplace les blocs un à un à partir de `renderToHtmlIndexed` passe les `exercises` de l’index dans `data`. `EXERCISE_SCRIPT` est le même code sous forme de script autonome, pour un fichier HTML sans page hôte qui l’appelle. Voir [Exercices en HTML et EPUB](/fr/docs/exercises#exercices-en-html-et-epub).
- **Les images à encre unique** : avec `diagramStyle.singleInk` activé, les `<img>` SVG reçoivent un filtre CSS, sauf si vous passez `singleInk: false` pour des URL déjà recolorées ; voir [Encre unique sur le canvas et en HTML](/fr/docs/configuration-resources#encre-unique-sur-le-canvas-et-en-html).
- **Pages composées et pages de bande dessinée sur une feuille imprimée** : sur une page large comme l'écran et haute comme le défilement, un cadre ancré au pied d'une page composée (`::::page{template}`) se retrouverait au pied du défilement. Passez `composedViewerLeaf: { width, height, margins? }` (le format et les marges de la page imprimée) dans la configuration que vous mettez en page : chaque page composée est alors mise en page sur une page de ce format, avec sa géométrie d'impression, et vous la mettez à l'échelle de l'écran (depuis postext 1.47) ; `comics.viewerLeaf` fait de même pour les pages de bande dessinée, mises à l'échelle à `fitWidth` px (voir [Bande dessinée](/fr/docs/configuration-comics)). Les deux sont destinés aux hôtes : le visualiseur HTML du Sandbox les fixe, et ils ne sont jamais enregistrés avec un document.

Le composant `HtmlPreview` du Sandbox (`packages/postext-sandbox/src/viewport/HtmlPreview/index.tsx`) met tout cela en œuvre sur la même API que ci-dessus et peut servir de référence. Il fait aussi passer chaque construction par un worker de mise en page partagé (voir [Exécuter la mise en page dans un Web Worker](/fr/docs/configuration-programmatic-usage#mise-en-page-dans-un-web-worker)), pour que les modifications en direct et les redimensionnements ne bloquent jamais le thread principal : remplacez l’appel direct `buildDocument(...)` de l’extrait ci-dessus par `layoutWorker.build(...)` quand vous êtes prêt à sortir la mise en page du thread principal.

La page transparente compte sur un site sombre : un aperçu sans `background` affiche du texte noir sur le fond sombre du site. Passez `renderToHtml(doc, { background: '#ffffff' })`, ou donnez au document une `page.backgroundColor`.

**Les styles de texte de la page hôte restent dehors.** Chaque ligne est composée aux largeurs que le moteur a mesurées : un `letter-spacing`, un `word-spacing`, un `text-transform` ou un `font-variant` que la sortie hériterait de la page environnante élargirait les suites de glyphes et ferait se chevaucher les lignes. La racine `.pt-doc` réinitialise donc les propriétés de texte héritées (espacement des lettres et des mots, casse, retrait, espaces blancs, style, variante, graisse et chasse de la police, fonctionnalités OpenType et crénage, hauteur de ligne, alignement, ombre et emphase du texte, césure, direction, mode d’écriture, contour et remplissage du texte, agrandissement automatique du texte sur mobile) avant ses propres déclarations de mise en page : la sortie a ainsi le même aspect dans une racine fantôme (shadow root) ou sous un élément stylé. Cette liste est exportée sous le nom `HTML_TEXT_RESET`, une chaîne de déclarations CSS : un hôte qui monte le `innerHtml` des pages (issu de `renderToHtmlIndexed`) dans ses propres conteneurs l’applique à leur racine. Jusqu’à postext 1.4, la racine ne réinitialisait rien ; le contournement consistait à l’envelopper dans un élément avec `all: initial`.


## Un livre en 3D (`postext-folio`)

`postext-folio` présente à l’écran un document mis en page comme un livre imprimé ouvert sur un bureau : des doubles pages selon la règle du recto, et des feuillets que le lecteur tourne avec les boutons ‹ ›, les flèches du clavier, un balayage, un clic sur une page, ou en saisissant une page par son bord pour la faire passer de l’autre côté. Chaque feuillet se courbe dans three.js selon son papier et projette une ombre réelle sur les pages qu’il recouvre. Le canvas WebGL dessine le livre de la même façon, immobile ou en train de tourner ses pages : une page ne change donc jamais d’aspect en se posant. C’est la visionneuse qu’utilisent les recettes du livre de recettes et l’onglet **Folio** du Sandbox.

```bash
npm install postext postext-folio three
```

```ts
import { buildDocument } from 'postext';
import { createFolioFromDocument } from 'postext-folio';

const doc = buildDocument({ markdown }, config);
const book = createFolioFromDocument(document.getElementById('book')!, doc, {
  onChange: ({ pages }) => console.log('showing pages', pages),
});

// After an edit: the same viewer, on the same page.
book.setDocument(buildDocument({ markdown: edited }, config));
```

- **Les pages sont peintes au fur et à mesure.** `createFolioFromDocument` peint chaque page avec `renderPageToCanvas` exactement aux pixels physiques d’un emplacement de page (WebGL l’affiche alors texel pour pixel, aussi net que l’aperçu canvas), et seulement les doubles pages autour de celle qui est ouverte (`window`, trois de chaque côté par défaut). Les pages qui sortent de cette fenêtre sont libérées : un livre de mille pages ne coûte ainsi que la mémoire de quelques-unes. Un saut vers une page lointaine peint d’abord cette double page. Jusqu’à dix pages d’écart, les feuillets tournent un par un ; au-delà, le bloc de pages intermédiaire se soulève d’un seul tenant, aussi épais que ces pages (leurs épaisseurs additionnées), et se pose de l’autre côté. `setDocument` conserve la peinture de chaque page qui reste identique dans la nouvelle mise en page (`{ repaint: true }` les repeint toutes, après l’arrivée d’une image).
- **Le document définit le livre.** Sa première page s’ouvre seule à droite quand c’est un recto (`pageIndexOffset` pair), un livre relié à droite (`page.binding: 'right'`, ou un document vertical) est disposé en miroir et tourne vers la gauche, les pages blanches prennent la couleur de fond de la page, et la largeur rognée de la page (`pageWidthMm`) met à l’échelle l’épaisseur du papier et les plats. Un chapitre mis en page avec une `continuation` compte les autres pages du livre (`pageIndexOffset` avant lui, `bookPageCount` après lui) dans l’épaisseur des deux blocs de pages, sans les dessiner (`extraPages`).
- **Le document définit l’aspect.** Le papier, la reliure, le bureau et l’éclairage sont les [réglages `folio`](/fr/docs/configuration-fonts-colors-viewers#visionneuse-folio-configuration) du document (`doc.config.folio`). Une page composée dans une suite `:::paper` a son propre papier (`VDTPage.paper`), et son feuillet est dessiné avec la couleur, la surface, l’épaisseur et la rigidité de ce papier. Avec `binding.cover: 'pages'`, la première page est le plat avant et la dernière, quand c’est un verso, le plat arrière (`covers`). Un format de journal (`'broadsheet'`, `'berliner'`, `'tabloid'`, `'compact'`) dont les réglages n’indiquent ni papier ni reliure se présente comme du papier journal plié, y compris quand l’hôte passe son propre `folio`.
- **Le conteneur définit la taille.** Le livre le remplit, avec les boutons et le nombre de pages dans les marges : donnez donc une hauteur au conteneur ; un redimensionnement repeint les pages à la nouvelle taille. Sous 560 px de large, il affiche une page à la fois (`mode: 'auto'` ; `'single'` et `'double'` imposent l’un ou l’autre) : le dos longe le bord intérieur de la page et le feuillet tourne autour de lui ; faire glisser vers le dos tourne la page en avant, un balayage dans l’autre sens revient en arrière, un tapotement tourne la page.
- **Ce que fait le pointeur.** `interaction` (puis `setInteraction`) définit ce que font sur le livre le bouton gauche, un doigt ou un stylet : `'hand'` (la valeur par défaut) saisit et tourne les pages, `'orbit'` fait pivoter la vue comme un glissement du bouton droit (pour les pavés tactiles et les tablettes), `'select'` laisse le pointeur à l’hôte, pour sélectionner du texte par exemple. `pageAt(event)` donne la page sous un pointeur et l’endroit visé (`{ page, x, y }`, en fractions de la page depuis son coin supérieur gauche), sur le livre tel qu’on le voit, incliné ou pivoté ; `pointOnScreen(point)` fait le chemin inverse, pour dessiner un curseur ou une sélection sur la page. `refreshPage(src)` réaffiche un canvas de page que l’hôte a redessiné sur place. Le Sandbox les utilise tous pour sélectionner du texte et suivre le curseur de l’éditeur sur les pages en 3D.
- **Une loupe pour les petits caractères.** `interaction: 'magnify'` tient une loupe ronde cerclée de noir au-dessus du livre, là où se trouve le pointeur (un doigt la tient au-dessus de lui tant qu’il touche l’écran). Elle montre le livre tel que le voit l’œil du lecteur, éclairé et courbé comme il est posé, grossi au maximum au centre et s’incurvant vers le bord. La molette, `+` et `−` changent le grossissement (`setMagnification(zoom)`, de 1,5 à 10 ; la valeur par défaut montre la page à environ 5,5 px CSS par millimètre) et Échap range la loupe ; `magnifier: { zoom, diameter }` règle les deux dès le départ. `createFolioFromDocument` repeint les pages sous la loupe, assez nettes pour son centre : le texte courant d’un journal reste ainsi lisible ; `createFolio` prend ces peintures dans `detail: { paint(index, deviceWidth), release() }`. Le Sandbox la place sur le bouton **Loupe** (M). La loupe sélectionne aussi du texte : au-dessus des pages, le curseur est un curseur de texte, `pageAt` renvoie le point situé sous le centre de la loupe (au-dessus du doigt sur un écran tactile) et, dans le Sandbox, un clic à cet endroit place le curseur et un glissement sélectionne.
- **Le lecteur peut en faire le tour.** Un glissement du bouton droit fait tourner la vue autour du livre (jusqu’à 70° de la verticale), y compris pendant que des feuillets tournent ; `resetView()` la ramène en douceur aux valeurs `tilt` et `yaw` des réglages, et `getView()` donne la vue telle qu’on la voit à cet instant (`{ tilt, yaw }`, en degrés) pour l’enregistrer dans ces réglages. Le Sandbox les place sur deux boutons, **Réinitialiser la vue** et **Enregistrer comme vue par défaut**.
- **Les vidéos se lisent sur les pages.** Un clic sur l’affiche d’une vidéo la lit sur la page, dans tous les modes d’`interaction`, et elle continue pendant que son feuillet tourne ; un autre clic la met en pause, et elle s’arrête quand le livre s’immobilise sur une double page qui ne la montre pas. Une vidéo avec `player.autoplay` démarre d’elle-même la première fois que sa double page s’affiche ; une vidéo qui se lit aussi en même temps que les autres (`player.exclusive: false`) démarre, sans le son, à chaque fois et s’arrête quand on tourne la double page, plusieurs à la fois. Options `videos`, `videoUrl` et `onVideo`, et `stopVideo()` sur la visionneuse ; voir [Format du document › Vidéos sur les pages de Folio](/fr/docs/document-format-resources#les-vidéos-sur-les-pages-de-folio).
- **D’abord les polices et les images.** Comme pour `renderPage`, les fontes qu’utilise le document doivent être chargées dans `document.fonts` et ses images de ressources enregistrées avec `registerResourceImage` avant que les pages ne soient peintes.
- **Accessible.** La visionneuse est un groupe focalisable qui répond à ←/→ (inversées pour un livre relié à droite), Page précédente/suivante, Début et Fin ; ses boutons et son nombre de pages sont étiquetés (`labels` les traduit), et chaque canvas de page a un texte `alt` (`alt: (index) => …`).
- **Sans WebGL2**, ou quand le lecteur demande des animations réduites, les doubles pages changent simplement. Les livres WebGL sont lourds pour un téléphone (une texture par face de page) : le Sandbox ne propose son onglet Folio que là où WebGL2 est disponible et où le petit côté de l’écran mesure au moins 600 px. `canFlip()` indique si les feuillets tourneront en 3D à cet endroit : WebGL2, et pas d’animations réduites.

## Livres EPUB (`postext-epub`)

`postext-epub` écrit un livre mis en page sous forme de fichier EPUB 3.3, dans le navigateur ou sous Node, sans serveur. Il lit les mêmes documents de chapitres que `renderToPdf` reçoit pour un livre : les numéros de page, les notes, les citations, les renvois, la table des matières et l’index arrivent donc résolus. Il renvoie le fichier sous forme d’octets. C’est lui qui écrit les fichiers de l’onglet **EPUB 3** du Sandbox.

```bash
npm install postext postext-epub
```

`postext` est une dépendance pair (peer dependency), comme pour `postext-pdf` : mettez les deux à jour ensemble et, sur un CDN, épinglez-les à la même version.

### Écrire un livre

```ts
import { openBundle, buildBundle } from 'postext';
import { renderToEpub } from 'postext-epub';

const bundle = await openBundle(fileBytes);
const docs = buildBundle(bundle); // one VDTDocument per chapter, in book order

const bytes = await renderToEpub(docs, {
  layout: 'reflowable',
  metadata: { title: 'Lantern', creators: ['Ada Lovelace'], language: 'en' },
  fonts: bundle.fonts.map((f) => ({ family: f.family, weight: f.weight, style: f.style, bytes: new Uint8Array(f.bytes), format: f.format })),
  resourceBytes: (fileId) => {
    const data = bundle.files.get(fileId);
    return data ? { bytes: data, mediaType: '' } : undefined;
  },
  onWarning: (w) => console.warn(w),
});
```

Un document seul est un livre d’un chapitre : `renderToEpub([doc], options)`.

- **`renderToEpub(docs, options): Promise<Uint8Array>`** écrit le fichier. `options` vaut `{ layout, metadata, fonts?, svgFonts?, resourceBytes?, cover?, onProgress?, onWarning?, signal?, kindlePanelView? }`.
- **`metadata`** : `title` et `language` (une étiquette BCP 47) sont obligatoires ; `subtitle`, `creators`, `identifier`, `date`, `publisher`, `rights`, `description` et `modified` sont facultatifs. Un ISBN seul devient `urn:isbn:…`. Sans `identifier`, le livre reçoit un `urn:uuid:` dérivé de son titre, de ses auteurs et de sa langue : une nouvelle version du même livre garde ainsi sa place dans la bibliothèque d’un lecteur. Passez aussi `modified` pour obtenir une sortie identique à l’octet près.
- **`fonts`** : les fontes à incorporer, `{ family, weight, style, bytes, format, unicodeRange? }`, `format` valant `woff2`, `woff`, `ttf` ou `otf`. Chaque fonte devient un fichier et une règle `@font-face` ; plusieurs fichiers avec leur `unicodeRange` forment une seule fonte (les tranches de Google Fonts). Une famille, une graisse ou un style que les pages utilisent sans fonte incorporée est signalé par `missingFont`, et les systèmes de lecture y substituent les leurs. N’incorporez que des polices dont la licence le permet : une fonte marquée `redistributable: false` n’est jamais écrite dans le fichier (le livre peut être composé avec elle, mais son fichier reste dehors, y compris des images SVG). Un hôte peut fournir à la place les fontes de la famille libre sous le nom de la famille sous licence (ce sont des fontes ordinaires), ce que font le Sandbox et `postext` pour une famille qui indique un `fallback` (depuis postext 1.43).
- **`resourceBytes(fileId)`** : les images que placent les pages, de façon synchrone ou asynchrone, sous la forme `{ bytes, mediaType }` ; un `mediaType` vide est déduit des octets. Fournissez les bitmaps tels qu’ils sont stockés et les SVG sous forme de source, pas l’original d’impression PDF (`svg.pdfFileId`). Chaque image est stockée une seule fois. Un livre à encre unique (`diagramStyle.singleInk`) voit ses SVG recolorés dans le fichier. Un SVG reçoit, incorporées en lui, les fontes qu’utilise son texte, puisqu’un système de lecture l’affiche comme une image qui ne voit pas les polices du livre (voir [Polices dans le texte SVG](/fr/docs/configuration-resources#polices-du-texte-svg)) : depuis `fonts` (les tranches qui contiennent ses caractères), puis depuis **`svgFonts.provider`** pour une famille que le texte du livre n’utilise pas. Les familles des fontes marquées `redistributable: false`, et celles que désigne `svgFonts.withhold(family)`, restent dehors et sont signalées une fois chacune par `fontWithheld` ; une famille sans fonte est signalée par `svgFontUnavailable`, des fontes au-delà de `svgFonts.maxBytes` (2 Mio) par `svgFontsTooLarge`. `svgFonts.inline: false`, `diagramStyle.inlineFonts: false` et le `svg.inlineFonts: false` d’une ressource gardent les octets tels quels. Une image sans octets est signalée par `missingImage` et laissée comme un cadre vide. `svgFonts.standIn(family)` (depuis postext 1.43) désigne une famille libre pour remplacer l’une d’elles : `svgFonts.provider` doit alors fournir la fonte de cette famille de même graisse et de même inclinaison, qui entre dans l’image sous le nom de la famille écartée ; s’il n’en a pas, la famille reste dehors et l’absence est signalée.
- **`cover`** : `{ bytes, mediaType, alt?, showsFirstPage? }`, une image JPEG, PNG, WebP ou SVG. Le livre s’ouvre alors sur un document de couverture qui la contient, et elle devient le `cover-image` du paquet (la vignette dans une bibliothèque). Sans elle, la mise en page fixe désigne sa première page comme couverture, et le livre recomposable n’a pas d’image de couverture. `showsFirstPage: true` indique que l’image est une capture de la première page imprimée : la mise en page fixe ne l’utilise alors que comme `cover-image` et s’ouvre sur cette page, qui serait sinon montrée deux fois ; le livre recomposable s’ouvre sur le document de couverture comme avant.
- **`kindlePanelView`** : pour une mise en page fixe avec des pages de bande dessinée, ajoute Kindle Panel View, une zone à toucher sur chaque case qui la montre agrandie, avec les métadonnées que demande Kindle. Chaque zone contient une copie de la bande dessinée de sa page : chaque page grossit donc d’une copie par case ; réservez-le aux livres destinés à Kindle. Valeur par défaut `false`. La navigation par régions, que tout système de lecture peut utiliser, est écrite dans tous les cas (voir [Sorties de la bande dessinée](/fr/docs/comics#sorties-de-la-bande-dessinée)).
- **`onProgress({ phase, done, total })`** : `resources` (polices et images), `documents` (pages pour une mise en page fixe, chapitres pour une recomposable), puis `package`. **`signal`** interrompt le travail entre deux étapes.
- **`readEpub(bytes)`** relit un fichier pour une visionneuse, sans `DOMParser` : mise en page, métadonnées, sens de lecture, chaque fichier par chemin, le manifeste, la séquence de lecture (spine), la table des matières, la liste des pages, la zone d’affichage de la mise en page fixe et la couverture. Le lecteur du Sandbox repose sur elle.

Les deux rendus contiennent les métadonnées EPUB Accessibility 1.1 (modes d’accès, fonctions comme la table des matières et les numéros de pages imprimées, risques et un résumé) et ne revendiquent par défaut aucune conformité WCAG. La liste complète des options et les limites se trouvent dans le [README du paquet](https://www.npmjs.com/package/postext-epub).

### Vérifier un fichier avec EPUBCheck

[W3C EPUBCheck](https://www.w3.org/publishing/epubcheck/) est le validateur de référence pour EPUB ; les librairies numériques vérifient avec lui les fichiers qu’elles reçoivent. Une fois installé (`brew install epubcheck`, ou la version Java), `epubcheck book.epub` liste les erreurs, les avertissements et les remarques d’usage ; les remarques d’usage que déclenche la sortie de Postext (`CSS-028`, `OBS-001`, `HTM_062`) sont informatives. Dans le dépôt de Postext, `pnpm --filter postext-epub epubcheck` vérifie les livres d’exemple de la suite de tests, `node packages/postext-epub/scripts/epubcheck.mjs book.postext --layout both` met en page un fichier `.postext` ou un dossier de préréglage et vérifie les deux rendus, et `pnpm --filter postext-epub validate` exécute toute la matrice de livres (le guide, les préréglages vitrines, les livres chinois, arabes et ceux du livre de recettes), qui passent tous sans erreur ni avertissement.

## Paquets SCORM (`postext-scorm`)

`postext-scorm` écrit un livre, ou les chapitres et sections qu’on y choisit, sous forme de paquet SCORM : le zip qu’un système de gestion de l’apprentissage (Moodle, Canvas, Blackboard, SCORM Cloud et la plupart des autres) importe comme un cours. Le contenu est celui qu’écrit `postext-epub`, pages fixes ou texte recomposable, sous forme de pages HTML5 ; chaque partie que suit le LMS s’affiche dans une petite visionneuse, et les exercices qu’elle contient envoient au LMS leur score, leur achèvement et leur réussite ou leur échec. C’est lui qui écrit le paquet de l’onglet **SCORM** du Sandbox.

```bash
npm install postext postext-epub postext-scorm
```

`postext` et `postext-epub` sont des dépendances pair (peer dependencies) : mettez les trois paquets à jour ensemble.

### Écrire un paquet

```ts
import { openBundle, buildBundle } from 'postext';
import { renderToScorm, scormTree, scormOrganization, treeLeaves } from 'postext-scorm';

const bundle = await openBundle(fileBytes);
const docs = buildBundle(bundle);

// The book's spine: chapters and their headings down to the third level.
const tree = scormTree(bundle.chapters.map((c) => ({ markdown: c.markdown, title: c.title })));
// Chapter 1 whole, and two sections of chapter 2.
const picked = new Set([tree[0]!, tree[1]!.children[0]!, tree[1]!.children[2]!].flatMap(treeLeaves).map((n) => n.id));

const zip = await renderToScorm(docs, {
  version: '1.2',
  layout: 'fixed',
  items: scormOrganization(tree, picked),
  metadata: { title: 'Lantern', language: 'en' },
  fonts, resourceBytes, // as for renderToEpub
});
```

- **`renderToScorm(docs, options): Promise<Uint8Array>`** écrit le zip. `docs` sont les documents de chapitres que reçoit `renderToEpub`. `options` vaut `{ version, layout, items?, metadata, fonts?, svgFonts?, resourceBytes?, cover?, passingScore?, onProgress?, onWarning?, signal? }` ; `metadata`, `fonts`, `svgFonts`, `resourceBytes` et `cover` sont ceux de `renderToEpub`.
- **`version`** : `'1.2'` ou `'2004'` (SCORM 2004 4e édition). Tous les LMS acceptent SCORM 1.2. SCORM 2004 sépare l’achèvement et la réussite, donne un score normalisé et garde jusqu’à 64 000 caractères de réponses enregistrées, là où SCORM 1.2 en garde 4 096 ; choisissez-le quand le LMS l’accepte et que ces différences comptent.
- **`layout`** : `'fixed'`, chaque page imprimée ajustée à la fenêtre, ou `'reflowable'`, le texte recomposé pour la fenêtre, comme dans [Mise en page fixe et recomposable](#mise-en-page-fixe-et-recomposable).
- **`items`** : l’organisation que montre le LMS, un arbre de `{ title, doc?, range?, children? }`. Un élément avec `children` les regroupe ; un élément sans enfants est un SCO, une partie que le LMS lance, suit et note à part : le chapitre `doc` entier, ou sa `range` (`{ start, end? }`, des positions dans le Markdown du chapitre tel qu’il est écrit, en-tête YAML compris). Sans `items`, chaque chapitre est un SCO.
- **`scormTree(chapters, config?)`** liste les chapitres et leurs titres de niveaux 1 à 3, chacun avec l’étendue qu’il représente : de sa ligne jusqu’au titre suivant de même niveau ou de niveau supérieur. Le premier titre sous un chapitre ou sous un titre prend aussi le texte qui le précède : le titre d’un chapitre et ses paragraphes d’ouverture vont ainsi avec sa première section. **`scormOrganization(tree, picked)`** transforme un ensemble d’identifiants de feuilles choisies en `items` : un nœud choisi en entier donne un SCO, un nœud choisi en partie regroupe les éléments de ses enfants. `treeLeaves(node)` et `pickState(node, picked)` (`'all'`, `'some'`, `'none'`) servent à construire un arbre à cases à cocher.
- **`passingScore`** : le pourcentage de réponses notées justes qui donne la réussite, par-dessus le `exercises.digital.passingScore` des documents. `0` ou absent : ni réussite ni échec.

Un SCO à mise en page fixe contient toutes les pages imprimées que touche sa partie : une page que partagent deux parties apparaît donc dans les deux. Un SCO recomposable contient exactement le texte de sa partie, coupé à ses titres. Les liens des pages d’un SCO vers celles d’un autre sont retirés, puisqu’un LMS suit un SCO d’après ce qu’il ouvre. La visionneuse montre un document à la fois, avec ← et → (ou Page précédente et Page suivante sur les pages fixes), le sommaire du SCO et la position ; un livre relié à droite tourne ses pages vers la gauche.

### Ce qui parvient au LMS

La visionneuse trouve l’API du LMS comme le demande SCORM (`API` pour SCORM 1.2, `API_1484_11` pour SCORM 2004, en remontant la chaîne des fenêtres parentes, puis dans la fenêtre qui l’a ouverte) et transmet :

- **Score.** Un exercice compte sa dernière vérification : ses réponses notées justes sur l’ensemble de ses réponses notées, le score qu’affiche sa barre. Le score d’un SCO est la somme des réponses justes divisée par la somme des réponses notées de ses exercices : des mots croisés de vingt cases pèsent ainsi plus qu’un vrai ou faux ; un exercice jamais vérifié ne compte aucune réponse juste. SCORM 1.2 le reçoit en pourcentage (`cmi.core.score.raw`, de 0 à 100) ; SCORM 2004 en fraction (`cmi.score.scaled`), avec les réponses en `raw` et `max`. Un exercice appartient à la partie où se trouve son délimiteur : seul ce SCO le compte, même là où sa page apparaît aussi dans un SCO voisin.
- **Achèvement.** Un SCO est terminé une fois que toutes ses pages ou tous ses documents ont été montrés et que chaque exercice qu’il compte a été vérifié (ou n’a plus de vérifications). Jusque-là, il est incomplet, et le LMS garde la position du lecteur pour la visite suivante.
- **Réussite.** Avec un seuil de réussite, un SCO terminé est réussi ou échoué par rapport à ce seuil. Le manifeste le contient (`adlcp:masteryscore` en SCORM 1.2, un objectif principal avec `minNormalizedMeasure` en SCORM 2004), et la visionneuse prend la valeur que lui renvoie le LMS : un LMS qui fixe son propre seuil l’emporte.
- **Interactions.** Chaque vérification écrit l’exercice sous forme d’interaction : un identifiant tiré de son ancre ou de son numéro, un type tiré de son genre (`true-false`, `choice`, `fill-in`, `other`), la réponse du lecteur, la bonne réponse, le résultat et une pondération égale à ses réponses notées ; SCORM 2004 ajoute une description et garde une interaction par exercice, SCORM 1.2 en ajoute une à chaque vérification.
- **Agrégation.** SCORM 2004 pondère dans le manifeste la mesure de chaque SCO par ses réponses notées : le score du cours est l’ensemble des réponses justes sur l’ensemble des réponses notées. SCORM 1.2 n’a pas d’agrégation propre : c’est la méthode d’évaluation du LMS qui décide (Moodle propose le score le plus haut, la moyenne ou la somme des scores des SCO).
- **Réponses.** Elles vont dans `cmi.suspend_data` avec les vérifications et les recommencements utilisés : les limites d’une tentative ([Évaluation](/fr/docs/configuration-exercises#évaluation)) tiennent ainsi d’une visite et d’un appareil à l’autre. Au-delà des 4 096 caractères de SCORM 1.2, les compteurs vont toujours au LMS et les réponses restent dans le navigateur du lecteur.

Hors d’un LMS (la page de lancement seule, ou le paquet sur un serveur web), la visionneuse ne trouve aucune API : le livre se lit de la même façon et les exercices gardent leurs réponses dans le navigateur, comme ceux d’un livre HTML ou EPUB.

### Vérifier un paquet

La suite de tests valide les manifestes des deux versions par rapport aux schémas IMS et ADL avec `xmllint`. Pour essayer un paquet, importez le zip dans un LMS (l’activité SCORM de Moodle accepte les deux versions) ou dans [SCORM Cloud](https://cloud.scorm.com/). Un substitut local fonctionne aussi : [scorm-again](https://github.com/jcputney/scorm-again) fournit les API SCORM 1.2 et 2004 dans une page qui affiche la page de lancement dans un cadre, et refuse toute valeur que le modèle de données n’autorise pas.
