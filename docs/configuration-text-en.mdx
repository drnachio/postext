      <td><code>shapingLanguage</code></td>
      <td><code>'document' | 'host'</code></td>
      <td><code>'document'</code></td>
      <td>The language the text is shaped in: measured, painted and embedded. A font answers with other glyphs under a language (OpenType <code>locl</code>): Noto Serif SC sets its digits differently in Chinese, a face with a Catalan form draws <code>l·l</code> differently, and one with the Turkish rule keeps <code>fi</code> apart. <code>'document'</code> (the default since postext 1.30): the document's own (<code>locale</code>, else the hyphenation language; a document that names none is English, <code>en-US</code>, and one whose <code>locale</code> is not a language tag is shaped in no language), and a run's own where it names one (<code>:ltr[…]&#123;lang=en&#125;</code>). The layout sets it on every context it measures with, so a document breaks its lines the same on a page in any language and in a layout worker; the canvas paints in it, the HTML viewer and the EPUB declare it on the document and on each page, and the PDF shapes with the OpenType language system of the language. Since postext 1.30 the text is measured under it as it is painted. A string has one width whatever was measured before it: Chrome keeps the words it has shaped, and Noto Serif SC sets <code>2026</code> 2.20 em wide in a string with no character past U+00FF and 2.23 em in a string that has one, so the two kinds of string are measured on separate contexts. A right-to-left word is measured right to left in any face. A word the line breaker may cut (at a syllable or a hyphen) is measured whole and set whole where it stays on one line, on the canvas, in the HTML viewer and in the PDF, in any paragraph (since postext 1.31: up to 1.30.1 a paragraph without formatting measured each piece of such a word by itself, so what a face draws across a hyphenation point, the <code>ff</code> of <code>of·fice</code> in EB Garamond or the wide Catalan dot of Crimson Pro in <code>l·l</code>, showed in a word of a paragraph with an italic in it and not in the same word of a plain paragraph). Under <code>'host'</code> a paragraph without formatting still measures each piece of such a word by itself. When a word is broken at a line end, each part is measured as it is painted: the part that opens the next line as a text of its own, and the first part of a Catalan <code>col·lecció</code> as <code>col-</code>. A design text (a running head, an opener, a heading design) is measured run by run, each run in the direction it is painted in. The PDF shapes word by word as the browser's canvas does (a word ends at a space, a tab, U+3000 or U+200B, and before a Han character), sets one at a time the Chinese and Japanese characters that the layout measured one at a time, and takes each character from the font file the browser took it from when the font provider says which (see <a href="/en/docs/configuration-pdf-output#chinese-japanese-and-korean-fonts">Chinese, Japanese and Korean fonts</a>). <code>'host'</code>: as up to postext 1.28, the layout measures in the language of the page that hosts it (none in a worker) and the canvas paints in that same language; the HTML viewer declares the language of a Chinese, Japanese, Korean or right-to-left document. A document with <code>'host'</code> keeps the widths and the PDF it had; in a paragraph with formatting its canvas and its HTML viewer also set whole a word that stays on one line (up to postext 1.29.2 they painted it piece by piece). Under <code>'host'</code>, the part of a broken word that opens the next line is measured as the whole word minus its first part, so a face whose form for the language needs the letters on both sides of the break (the Catalan <code>l·l</code> of Crimson Pro, a wide dot set only between two <code>l</code>) leaves a gap after the rest of the word, a third of an em in that face, on a page in that language. The default was <code>'document'</code> in postext 1.29.0 alone, whose canvas and PDF did not follow the measure, <code>'host'</code> in 1.29.1 and 1.29.2, and <code>'document'</code> again from 1.30.0. A configuration stored before <code>configVersion</code> 14 that does not name the setting has <code>'host'</code> written out (<code>pinLegacyShapingLanguage</code>), so a stored document keeps its lines; one that names a value keeps it. A browser whose canvas has no <code>lang</code> (Chrome before 136, and Firefox and Safari where it is missing) is given no language and keeps the forms it always measured, and the command line always lays out with <code>'host'</code> (see <a href="/en/docs/command-line#differences-from-the-sandbox">Differences from the Sandbox</a>).</td>

### Drop caps

A body paragraph can open with a drop cap: its first letter set large beside its first lines, which are shortened by the letter's width and a gap and set like any other lines (broken by Knuth–Plass, justified, hyphenated). A paragraph style gives one to the first paragraph of each `:::paragraphs` group in the style (every paragraph with `each: true`, for a catalogue of entries); a heading level or a heading style gives one to the first body paragraph after the heading (see the `dropCap` field of [Per-level overrides](/en/docs/configuration-headings#per-level-overrides), [Paragraph styles](/en/docs/configuration-styles#paragraph-styles) and [Heading styles](/en/docs/configuration-styles#heading-styles)). The paragraph after the heading is found by looking past container fences, directives, boxes taken out of the flow and floated figures, as `indentAfterHeading` does; a paragraph inside a box, a list item, a quotation, a poem or a note never takes one. In the text, `{dropcap}`, `{dropcap=false}` and `{dropcap=N}` on a heading line or a `:::paragraphs` fence turn it on, off, or set its lines for that chapter or group (see [Document format › Drop caps](/en/docs/document-format#drop-caps)). Since postext 1.23.

A frame of a composed page is not a box: it is running text, and its paragraphs take drop caps as the flow's do, from a `:::paragraphs` group, a paragraph style, or a heading level after a heading in the same frame (a heading the template sends to a frame of its own, `takes: 'h1'`, gives its level's drop cap to the paragraph that follows it in the Markdown when that paragraph opens the flow frame's text, since postext 1.39). A group that asks for a drop cap inside a `:::callout` box is set without one and raises a `dropCap` warning (`inBox`). Since postext 1.38. A paragraph that opens with a drop cap is never cut before the initial's last line, in a chain of frames (`next`) or in a frame that goes on to another page, just as in the flow: it moves on whole, and is cut there only when it opens a frame too short for those lines, with a `dropCap` warning (`split`). Since postext 1.39.

headings: {

How the letter is set:

- **Size.** Both cap heights, the text's and the initial's, are measured from their faces (the ink of an `H`; of the initial itself in Chinese or Japanese text), and a face that gives no ink metrics counts its capitals as 0.72 of its size. The default size suits any pair of faces, so a per-face correction is not needed. A design text's `dropCap` keeps its fixed 0.72 (see [Text elements](/en/docs/configuration-headers-footers#text-elements)).
- **The letter and its word.** The initial takes whole grapheme clusters. The rest of the first word goes on after it with no space; a one-letter word (*A*, *Y*) keeps its word space at the start of the first line. The paragraph's own first-line indent is dropped. Copying, search, the source map and the Sandbox's caret read the paragraph as written: the block's plain text includes the letter, the first line's `plainStart` counts past it, and `VDTBlock.dropCap` holds its range and geometry on the fragment with the first line.
- **A raised initial** (`lines: 1` with a larger `fontSize`, or `sink` under `lines`) rises above the first line, and the paragraph keeps that rise clear above it, in whole grid lines, so it does not overprint the text above.
- **Breaking.** The paragraph never breaks before line `sink`: it moves on whole to the next column or page instead, unless it is alone in an empty column that cannot hold those lines, where it breaks all the same and raises a `dropCap` warning. A heading kept with its text keeps those lines under it. The part that goes on in the next column carries no initial and full-width lines; broken again for a column of another width, the first lines keep their indent. Column balancing may set the paragraph loose or tight like any other, and never adds space between the shortened lines.
- **Scripts.** The lines are shortened on the start side: the left in Latin text, the right in Arabic and Hebrew. A letter that joins the next one (Arabic, Syriac, N'Ko) is not set apart, and the paragraph raises a `dropCap` warning; horizontal Chinese and Japanese take a one-character initial (首字下沉). Vertical text takes none (warning). A paragraph that opens with no letter or digit (a reference, a formula, a note mark) takes none either (warning).
- **Outputs.** The canvas, the HTML viewer and fixed EPUB paint the initial beside the lines; the HTML writes it right before the first line's text with nothing between, so a screen reader reads the word whole. In a tagged PDF the initial is part of the paragraph's `P`, and with the rest of its word a `Span` whose `/ActualText` is the word: text extraction reads *Long before*, never *L ong before*. A reflowable EPUB sets it as a CSS `initial-letter` (lines, sink), floated where the reading system does not support it.

The settings are checked with the rest of the configuration (see [Configuration warnings](/en/docs/configuration-fonts-colors-viewers#configuration-warnings)): an unknown key in a drop cap or its lead-in is reported as `unknownConfigKey`, a `punctuation` or `shortParagraph` that is not one of its values, or a `lines`, `sink` or `characters` that is not a whole number of 1 or more, as `unknownConfigValue`, and the default is used. Drop caps are off by default, so no stored document changes.

### One family per `fontFamily`

`fontFamily` — here and in every other font-family field (`headings.fontFamily`, `tableStyle.bodyFontFamily`, `separatorFontFamily`, a chip style's or a design element's `fontFamily`…) — names **one** family. The canvas, the HTML output and the PDF must set the same face, and the PDF embeds one font per family with no fallback chain, so there is nothing for a CSS font stack to fall back to. A stack is set in its first family and reported as a [configuration warning](/en/docs/configuration-fonts-colors-viewers#configuration-warnings):

```ts
bodyText: { fontFamily: "'EB Garamond', Georgia, serif" } // set in EB Garamond
```

Load that family before laying out (see [Custom fonts](/en/docs/configuration-fonts-colors-viewers#custom-fonts) and the font provider under [Generating PDFs](/en/docs/configuration-pdf-output#generating-pdfs)); if it is missing, the browser measures with its default font, whatever the rest of the stack says. A comma inside quotes is part of a name (`'"Foo, Bar"'` is one family).
