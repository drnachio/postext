# プログラムからの利用：PDFファイル


## PDFの生成

PDFの出力は別パッケージ（**`postext-pdf`**）が受け持ちます。Webだけで使う組み込みが`pdf-lib`と`@pdf-lib/fontkit`のコストを負わずに済むようにするためです。PDFバックエンドはテキストを計測し直しません。`renderToCanvas`や`renderToHtml`に渡すのとまったく同じ`VDTDocument`を受け取り、そのピクセル単位の座標をPDFのポイントに変換します。そのため3つの出力は、改行位置、段の高さ、リソースの配置が必ず一致します。

> **ブラウザーでは、VDTを[Web Worker](/ja/docs/configuration-programmatic-usage#web-workerでレイアウトを実行する)で構築してください。**`renderToPdf`自体はVDTができていれば高速で、時間がかかるのはVDTを生成したレイアウトのパイプラインのほうです。このパイプラインをワーカーで動かせばUIの応答性が保たれ、PDFの書き出しで、ライブプレビューがすでに温めた計測キャッシュを再利用できます。推奨する流れは[ワーカーからのPDF書き出し](/ja/docs/configuration-programmatic-usage#ワーカーからのpdf書き出し)を参照してください。以下のメインスレッドの例は、各引数が何を意味するかを示すリファレンスです。UIのコードでは、まずワーカーでVDTを構築し、`renderToPdf`だけを直接呼び出してください。

### インストール

```bash
npm install postext postext-pdf
```

`postext`は`postext-pdf`のピア依存関係（peer dependency）です。`postext-pdf`の各リリースには、同時にリリースされた`postext`か、同じメジャーバージョンのそれより新しいものが必要です（ピア依存の範囲はそのバージョンに`^`を付けたもので、1.5.0なら`^1.5.0`）。そのリリースで`postext`に追加されたヘルパーをインポートしているためです。2つは一緒にアップグレードし、CDNでは同じバージョンに固定してください。

### 公開API

このパッケージは、エントリーポイントを1つと、いくつかの型を公開しています。

- **`renderToPdf(doc, options): Promise<Uint8Array>`** — `VDTDocument`（または本の章を並べたその配列）を受け取り、PDFの生のバイト列を返します。
- **`PdfFontProvider`** — `renderToPdf`が新しいファミリー・ウェイト・スタイルの組み合わせを埋め込む必要があるときに、フォントのバイト列を要求するために使うコールバックのシグネチャ`(family, weight, style, request?) => Promise<Uint8Array | Uint8Array[]>`です。`request.codePoints`には、ページがそのフェイスで組む文字が入ります。返すのは1つのファイルか、合わせて1つのフェイスになる複数のファイルです（[中国語・日本語・韓国語のフォント](#中国語日本語韓国語のフォント)を参照）。
- **`declaredFontFile(bytes, { unicodeRange?, order? }): PdfFontFile`** — ページでの宣言のしかたを記録したフェイスのファイルです。記録するのは、`@font-face`規則の`unicode-range`と、宣言順での位置です。`PdfFontFile`は、この2つの省略可能なプロパティを加えた`Uint8Array`です（[中国語・日本語・韓国語のフォント](#中国語日本語韓国語のフォント)を参照。postext-pdf 1.30以降）。
- **`RenderToPdfOptions`** — `{ fontProvider, forms?, resourceBytes?, previewBytes?, outlines?, accessible?, colorSpace?, pageNegative?, characterGrid?, baselineGrid?, onProgress?, onWarning?, rasterizeSvg?, harfbuzzWasm?, print?, outputProfile?, profileBaseUrl?, date? }`。`forms`は、フォームフィールドでの数値の書き方（通貨、その位置、区切り記号）と、値を表示するフェイス（`font`）を指定します（[フォームフィールド](#フォームフィールド)を参照）。`outlines`、`accessible`、`colorSpace`は、省略するとドキュメントの`pdfGeneration`の値になります（[PDF生成（設定）](/ja/docs/configuration-fonts-colors-viewers#pdf生成設定)を参照）。`resourceBytes`は[リソースのバイト列と印刷用マスター](#リソースのバイト列と印刷用マスター)で、`onWarning`は[プロバイダーに要求されるフェイス](#プロバイダーに要求されるフェイス)と[文書の中の警告](/ja/docs/configuration-programmatic-usage#文書の中の警告)で説明します。`characterGrid: true`は、`cjk.grid.show`が画面に描くグリッドを印刷します。指定しなければPDFには含まれません（[文字グリッド](/ja/docs/configuration-east-asian#文字グリッド)を参照）。`harfbuzzWasm`は、右から左に書く文字や連結する文字を含むドキュメントのために、HarfBuzzの`harfbuzz.wasm`をどこから読み込むかを指定します（ページからの相対URL、またはファイルのバイト列）。省略すると、postext-pdfのモジュールの隣にあるコピー、次にjsDelivrとesm.shにある同じharfbuzzjsのリリースを使います。`print`は印刷出力の設定（PDF/X規格、出力プロファイル、黒の扱い、プリフライト）を受け取り、省略時は文書の`print`を使います。PDF/X規格、または`colorSpace: 'cmyk'`を指定すると、すべての色がICC出力プロファイルで分版されます。プロファイルのバイト列は`outputProfile`で渡し、省略時は`profileBaseUrl`（既定はnpm CDN上のpostextの`icc/`フォルダー）から取得します。`date`（`Date`、ミリ秒の時刻、または日付の文字列。`createBundle`の`mtime`と同じ型）は、ファイルの作成日と更新日になります。PDF/XではXMPパケットの日付にもなり、文書IDもここから求めます。同じ文書を同じ`date`で2回書き出すと、バイト列は一致します。省略時は呼び出した時刻が入ります。無効な日付はエラーになります。
- **`PdfWarning`** — `onWarning`で報告される致命的でない問題です。`kind`で絞り込みます。`'fontFallback'`（`PdfFontFallbackWarning`）はフェイスがファミリーの別のカットで組まれたこと、`'missingGlyph'`（`PdfMissingGlyphWarning`）はフェイスのどのファイルにもグリフがない文字、`'variableFontDefaultInstance'`（`PdfVariableFontWarning`）は可変フォントが既定のインスタンス以外のウェイトで要求されたこと、`'cffEmbeddedWhole'`（`PdfCffEmbeddedWholeWarning`）は2 MBを超えるCFFフェイスが丸ごと埋め込まれたこと、`'complexShapingUnavailable'`（`PdfComplexShapingWarning`）はHarfBuzzを読み込めず（`reason`に探した場所が並びます）、右から左に書く文字や連結する文字がHarfBuzzなしで描かれたため、アラビア文字の記号の位置がずれることを示します。`'outputProfileUnavailable'`（`PdfPrintWarning`）は、CMYKでの描画で出力プロファイルを読み込めず、単純な計算式で変換したこと、`'pageNegativeIgnored'`（`PdfPrintWarning`）は、PDF/X-1aのファイルでページのネガ反転を省いたことを示します。`'spotTintsExhausted'`（`PdfPrintWarning`）は、レンダリングが特色の濃度を区別するコード（約2,500万）を使い切り、残りをプロセスカラーで刷ったことを示します。`'spotInkRenamed'`（`PdfPrintWarning`）は、インキの版を別の名前で書き出したことを示します（[特色](#特色)を参照）。`'imageProfileUnavailable'`（`PdfPrintWarning`）は、RGB 画像に割り当てたプロファイルを読み込めず、画像自身のプロファイルを使ったことを示します。`'pictureOriginalUnreadable'`（`PdfPrintWarning`）は、TIFF または Photoshop の原本を復号できず、プレビュー（`previewBytes`）から、またはプレースホルダーとして印刷したことを示します。`'plateMixesApproximated'`と`'artworkOffPlates'`（`PdfPrintWarning`）は、少数の版で刷るジョブ（`print.plates`）がコードを使い切って残りの色をすでにコード化した最も近い掛け合わせで刷ったこと、または配置したPDFページや復号できない画像がそれ自身のインキのまま置かれたことを示します。`'missingImage'`は、バイト列のない画像がプレースホルダーとして描かれたことを示します（これは渡した`onWarning`にだけ報告されます。それがないとき、フォントの警告は`console.warn`に出ます）。
- **`inspectPrintMaster(bytes): Promise<PrintMasterReport>`** — PDFの印刷用マスターの1ページ目を読み、埋め込まずに使っているフォント（`nonEmbeddedFonts`）、RGBで描いているか（`rgb`）、透明効果を使っているか（`transparency`）を報告します。[プリフライト](/ja/docs/configuration-pdf-output#プリフライト)が使います。
- **`inspectPrintPdf(bytes): Promise<PrintPdfReport>`** — 完成したPDFを、印刷所のプリフライトと同じように全ページ読み直します。バージョンとページ数、PDF/Xの識別と出力インテント（そのプロファイルが埋め込まれているか）、仕上がりサイズと最小の塗り足し、仕上がりサイズが異なるページ、TrimBoxのないページ、ページボックスが4つの数値でないページ（`malformedBoxPages`。ボックスがないものとして読みます）、フォント（`fonts`：名前、埋め込みの有無、種類。埋め込みと非埋め込みの両方で使われたフォントは、それぞれ1回ずつ挙がります）、描画に使う色（CMYK、グレー、名前付きの特色、レジストレーション、そしてプロファイルのない`deviceRgb`とプロファイル付きの`iccRgb`に分けたRGB。どちらも`vector`の描画と`images`に分けます）、透明、オーバープリント、注釈、インタラクティブフォーム、タグ付きかどうかを報告します。ページのほかに、注釈の外観、フォームのフィールドと既定のリソース、パターン、Type 3グリフ、インライン画像も読みます。読むのは設定が求めた内容ではなく、ファイルに書かれている内容です。画像の解像度、総インキ量、細すぎる線、トラッピングは読みません。ページの走査は`inspectPrintMaster`と共通で、`inspectPrintMaster`はシェーディング、パターン、Type 3グリフ内のRGBも報告します。
- **`decompressWoff2(bytes): Uint8Array`** — WOFF2ファイルを、`pdf-lib`がそのまま埋め込める形式であるTTFのバイト列に変換するヘルパーです。
- **`createPdfWorker(options?)`**（`postext-pdf/worker`から） — 同じ描画をWeb Workerで行います。[ワーカーでPDFを描画する](#ワーカーでpdfを描画する)を参照してください。

### 最小限の例

```ts
import { buildDocument } from 'postext';
import { renderToPdf } from 'postext-pdf';

const vdt = buildDocument(
  { markdown: '# Chapter One\n\nThe story begins here…' },
  {
    page: { sizePreset: '17x24' },
    layout: { layoutType: 'double' },
    bodyText: { fontFamily: 'EB Garamond', fontSize: { value: 9, unit: 'pt' } }, // 9 pt overrides the 8 pt default
  },
);

const pdfBytes = await renderToPdf(vdt, {
  fontProvider: async (family, weight, style) => {
    // Return TTF bytes for this family/weight/style.
    // See the "Font provider" section below for a real implementation.
    const res = await fetch(`/fonts/${family}-${weight}${style === 'italic' ? 'i' : ''}.ttf`);
    return new Uint8Array(await res.arrayBuffer());
  },
});

// `pdfBytes` is a Uint8Array — save, download, or stream it.
const blob = new Blob([pdfBytes], { type: 'application/pdf' });
const url = URL.createObjectURL(blob);
window.open(url);
```

### なぜフォントプロバイダーが必要か

`pdf-lib`はPDFに実際のフォントファイルを埋め込みます。描画時にはブラウザーにインストールされたフォントを使えず、画面上の計測のためだけに読み込んだフォントも、それだけでは自己完結したPDFを作るのに足りません。`renderToPdf`はページを走査して、ページが描くすべてのフェイス（`family|weight|style`の組み合わせごとに1つ。[プロバイダーに要求されるフェイス](#プロバイダーに要求されるフェイス)を参照）を集め、固有の組み合わせごとに1回プロバイダーを呼び出します。プロバイダーは**TTFまたはOTF**のバイト列を`Uint8Array`で返します。複数のファイルで提供されるフェイスなら、そのリストを返します（[中国語・日本語・韓国語のフォント](#中国語日本語韓国語のフォント)を参照）。`pdf-lib`はTrueTypeのアウトラインをサブセット化し、CFF（`.otf`）ファイルは丸ごと埋め込みます。CFFのフェイスはCFFとして宣言されます。CFFプログラムを`FontFile3`（`CIDFontType0C`）に収めた`CIDFontType0`フォントで、`pdffonts`では`CID Type 0C`と表示され、印刷のプリフライトもこの形を前提にしています。CIDキー方式のCFFフェイス（Source Han、Noto CJKの`.otf`ファイル）は、TrueTypeとしての宣言のままです。グリフの番号付けが、テキストの書かれている番号付けと一致しないためです。印刷には、これらのファミリーのTrueType版を使ってください。ファミリーにない太字の代わりにレギュラーのカットを返す場合のように、プロバイダーが同じファイルを返したフェイスどうしは、埋め込みフォントを1つ共有します。SVGの図を画像として描くときのその図のテキストのフェイスのように、最終的にどのページの描画にも使われないフェイスはファイルに含まれません。

**可変フォント1つではなく、ウェイトごとの静的フォントを使ってください**。Google Fontsは多くの場合、ファミリーごとにウェイト軸全体を覆う可変WOFF2を1つ配信しています。`pdf-lib`は可変フォントのファイルから既定のインスタンスしか埋め込めないため、太字の段落がレギュラーのウェイトで描かれてしまいます。Fontsourceはウェイトごとの静的WOFF2ファイルを公開しており、この問題をきれいに解決できます。Sandboxが使っているのもこの方法です。既定のインスタンス以外のウェイトで要求された可変フォントのファイルは、`variableFontDefaultInstance`警告として報告されます。

**テキストのどの語も、レイアウトが置いた位置に描かれます**。段落、リスト項目、引用、囲みなど流し込まれるテキストでは、各語がVDTの計測した位置から始まるので、ブラウザーの幅と埋め込んだフェイスの幅の差が行に沿って積み重なることはありません。インライン書式のない行は、語と語の間でペンを動かす1つのテキストオブジェクトとして描かれます。両端そろえの行、中央そろえの行、書式を含む行は語ごとに描かれます。フェイスにグリフのない文字は、ブラウザーが別のフォントで計測し、PDFではフェイスの欠落グリフの箱として描かれますが、後に続く語を動かすことはなく、フェイスごとに1回`missingGlyph`警告として報告されます。狭いノーブレークスペースや数字幅スペースのようにフェイスにないスペースは、ブラウザーが与えた幅をとり、単語結合子（word joiner）やゼロ幅スペースのような不可視の文字は描かれません。フェイスにないノーブレークハイフン（U+2011）は、ブラウザーの表示と同じく、フェイスのハイフン（U+2010）で描かれ、それもなければハイフンマイナスで描かれます。Open SansやOutfitなどは、その両方を持っていません。どちらの場合も欠落グリフには数えません。例外が2つあります。右から左に書く文字を含む行は、従来どおり1つのランとして描かれます（[言語と文字体系](/ja/docs/configuration-language#言語と文字体系)を参照）。デザインが配置するテキスト（柱、フッター、章扉、囲みのタイトルなどのデザイン要素）は、埋め込んだフェイス自身の幅で組まれるため、そこでフェイスにないグリフがあると、行の残りが動きます。

### プロバイダーに要求されるフェイス

`renderToPdf`はページを描くときと同じ順にたどり、実際に描かれるフェイスだけをプロバイダーに要求します。

- 1行でも組むブロックのレギュラーのフェイスと、実際に太字、イタリック、太字イタリックで組まれる各ランのフェイス
- チップのラン、リストのマーカー、デザインのスロット（柱、ノンブル、章扉と部扉の帯）のテキスト
- すべてのリソースのキャプション、注記、表のセルのテキスト
- SVGの図を埋め込むときに、その`<text>`が指定するフェイス。プロバイダーがまったく提供できないファミリーは、SVGの`font-family`リストの次のファミリーに引き継がれます

そのため、どこでもイタリックにしない見出しのファミリーのイタリックが要求されることはなく、注記のない図に注記のフェイスが必要になることもありません。

プロバイダーがフェイスを拒否しても、描画は続きます。同じファミリーの別のフェイスが代わりに埋め込まれ、`PdfWarning`が報告されます。代わりになるのは最初に読み込めたフェイスで、9つの標準ウェイト（100〜900）をCSSのフォントマッチングと同じ順に試します。これはプレビューでブラウザーが表示するフェイスでもあります。

1. まず同じスタイル。400〜500のウェイトでは、500までのウェイトを先に試し、次に軽いウェイトを近いものから順に、その後600以上の重いウェイトを試します。400未満のウェイトでは、軽いウェイトを近いものから先に試し、次に重いウェイトを試します。500を超えるウェイトでは、重いウェイトを先に試し、次に軽いウェイトを試します。
2. 次にもう一方のスタイル（正体ならイタリック、イタリックなら正体）を、要求されたウェイトとほかのウェイトについて、同じ順で試します。

したがって、イタリックのないファミリーはイタリックのランを正体で組み、400と700だけのファミリーは600を700で組み、カットが1つしかないファミリーはすべてをそのカットで組みます。プロバイダーへの要求はこの順に1フェイスずつ行い、同じフェイスを2度要求することはないので、何にも使われないフェイスが埋め込まれることはありません。プロバイダーがまったく提供できないファミリーについては、描画が失敗するまでにこの18のフェイスすべてが要求されます。

```ts
const bytes = await renderToPdf(doc, {
  fontProvider,
  onWarning: (w) => {
    // { kind: 'fontFallback', family: 'Oswald', weight: 700, style: 'italic',
    //   fallback: { weight: 700, style: 'normal' }, reason: '…', message: '…' }
    console.info(w.message);
  },
});
```

`onWarning`がないと、メッセージは`console.warn`に出ます。テキストの位置はVDTから来ており、ブラウザーが持っていたフェイスで計測されたものなので、幅の異なる代替フェイスでは詰まって見えたり、ゆるく見えたりすることがあります。直すには本来のフェイスを提供してください。描画が失敗する（`postext-pdf: failed to load font(s): …`）のは、プロバイダーがあるファミリーのどのフェイスも、標準ウェイトで正体・イタリックのいずれでも提供できない場合だけです。

### ブラウザー向けフォントプロバイダー（Fontsource + WOFF2）

Sandboxには`createPdfFontProvider()`（`packages/postext-sandbox/src/viewport/pdf/pdfFontProvider.ts`）があり、どのブラウザーアプリにもコピーして使えます。要点は次のとおりです。

```ts
import type { PdfFontProvider } from 'postext-pdf';
import { decompressWoff2 } from 'postext-pdf';

const bytesCache = new Map<string, Promise<Uint8Array>>();

function fontsourceId(family: string): string {
  return family.toLowerCase().replace(/\s+/g, '-');
}

function fontsourceWoff2Url(
  family: string,
  weight: number,
  style: 'normal' | 'italic',
): string {
  const id = fontsourceId(family);
  return `https://cdn.jsdelivr.net/npm/@fontsource/${id}@5/files/${id}-latin-${weight}-${style}.woff2`;
}

export function createPdfFontProvider(): PdfFontProvider {
  return async (family, weight, style) => {
    const key = `${family}|${weight}|${style}`;
    const cached = bytesCache.get(key);
    if (cached) return cached;

    const promise = (async (): Promise<Uint8Array> => {
      const url = fontsourceWoff2Url(family, weight, style);
      const res = await fetch(url, { mode: 'cors' });
      if (!res.ok) throw new Error(`font fetch failed: ${res.status} ${url}`);
      // pdf-lib needs TTF bytes, so decompress the WOFF2 wrapper client-side.
      return decompressWoff2(new Uint8Array(await res.arrayBuffer()));
    })();

    bytesCache.set(key, promise);
    return promise;
  };
}
```

本番用の実装では、さらに次のことも行ってください。

- **利用できるウェイトを問い合わせ**（`https://api.fontsource.org/v1/fonts/{id}`を使用）、要求されたウェイトを、ファミリーが実際に提供する最も近いウェイトに合わせます。こうすれば、`{400, 700}`しかないファミリーに`weight: 600`を要求しても成功します。
- **イタリックから正体にフォールバックします**。要求されたウェイトにイタリックのカットがないファミリーでも、描画全体を失敗させずに済みます。
- **描画をまたいでキャッシュを再利用します**（`bytesCache`は呼び出しごとではなく、モジュールスコープに置きます）。こうすれば、設定を変えた後のPDFの再生成には実質的にコストがかかりません。

### 中国語・日本語・韓国語のフォント

CJKのフェイスは小さな1つのファイルでは提供されません。FontsourceはNoto Serif SCを1ウェイトあたり約100のファイルで配信しており、各ファイルは文字の一部を収め、ファミリーのスタイルシート（`@fontsource/noto-serif-sc/400.css`）でその`unicode-range`とともに宣言されています。ブラウザーは、ページのテキストが使うファイルをダウンロードします。上のプロバイダーが取得する`latin`ファイルには漢字がまったく含まれず、名前付きのサブセットも不完全です。Noto Serif SCの`chinese-simplified`には釵がなく、Noto Serif TCの`chinese-traditional`には全角の約物（），！？：；が1つもありません。

そこで、プロバイダーは1つのフェイスに対して複数のファイルを返せるようになっています。`renderToPdf`は、ページがそのフェイスで組む文字（`request.codePoints`）をプロバイダーに渡します。これは描画を始める前にすべての章から集めたものです。プロバイダーは、それらの文字を収めるファイルを、ブラウザーが参照するのと同じ順で返します。各ファイルはそれぞれ独立したサブセットとして埋め込まれ、各文字は、その文字のグリフを持つ最初のファイルから描かれます。60のスライスを使う章には、60の小さなサブセットが埋め込まれます。SVGの図のテキストなどのために同じフェイスが再び要求されるときは、それまでのファイルにない文字だけが要求されます。`Uint8Array`を1つ返すプロバイダーは従来どおり動作します。Sandboxのプロバイダーは、そのウェイトとスタイルのFontsourceのスタイルシートを読み、範囲がテキストの文字を含むファイルを取得します。その中核部分は次のとおりです。

```ts
import type { PdfFontProvider } from 'postext-pdf';
import { decompressWoff2 } from 'postext-pdf';

type Slice = { url: string; ranges: Array<[number, number]> };

async function fontsourceSlices(family: string, weight: number, style: 'normal' | 'italic'): Promise<Slice[]> {
  const id = family.toLowerCase().replace(/\s+/g, '-');
  const cssUrl = `https://cdn.jsdelivr.net/npm/@fontsource/${id}@5/${weight}${style === 'italic' ? '-italic' : ''}.css`;
  const css = await (await fetch(cssUrl)).text();
  return [...css.matchAll(/@font-face\s*{([^}]*)}/g)].map(([, rule]) => ({
    url: new URL(/url\(\.?\/?([^)]+\.woff2)\)/.exec(rule)![1], cssUrl).href,
    ranges: /unicode-range:\s*([^;]+);/.exec(rule)![1].split(',').map((part) => {
      const [lo, hi = lo] = part.trim().slice(2).split('-');
      return [parseInt(lo, 16), parseInt(hi, 16)] as [number, number];
    }),
  }));
}

export const sliceFontProvider: PdfFontProvider = async (family, weight, style, request) => {
  // Where ranges overlap, the browser tries the last rule first.
  const slices = (await fontsourceSlices(family, weight, style)).reverse();
  const picked = new Set<Slice>();
  for (const cp of request?.codePoints ?? []) {
    const slice = slices.find((s) => s.ranges.some(([lo, hi]) => cp >= lo && cp <= hi));
    if (slice) picked.add(slice);
  }
  if (picked.size === 0) picked.add(slices[0]!);
  return Promise.all(slices.filter((s) => picked.has(s)).map(async (s) =>
    decompressWoff2(new Uint8Array(await (await fetch(s.url)).arrayBuffer()))));
};
```

ラテン文字のファミリーも同じコードで扱えます。英語のテキストには`latin`ファイルだけが、チェコ語には`latin`と`latin-ext`が使われます。

ブラウザーは、グリフを持つ最初のファイルを使うわけではありません。`unicode-range`にその文字が入っているファイルのうち、最後に宣言されたものでその文字を組みます。そしてファミリーのファイルには重なりがあります。FontsourceはNoto Serif JPのASCII文字を、`latin`ファイルにも番号付きのスライスにも入れています。別々のファイルで組んだ2つの文字の間にはカーニングがかからないので、どのファイルを使うかで幅が決まります。Chrome 154は、スライスを`latin`の後に宣言した場合、`Shift_JIS`を幅4.25emで組みます。`latin`ファイルだけでは`t_`と`_J`にカーニングがかかり、幅は4.32emです。postext-pdf 1.30以降、プロバイダーは、ページが各ファイルをどう宣言したかを伝えられます。`declaredFontFile(bytes, { unicodeRange, order })`は同じバイト列を返し、そこに、そのファイルの規則の`unicode-range`（CSSの書き方のまま）と、フェイスの規則全体の中でのその規則の位置を記録します。位置は宣言順に大きくなる数であれば何でもよく、最も大きいものが最後に宣言されたファイルです。

```ts
import { declaredFontFile } from 'postext-pdf';

declaredFontFile(bytes, { unicodeRange: 'U+0000-00FF,U+0131,U+0152-0153', order: 0 });
```

フェイスのファイルが範囲を持っている場合、文書自身の言語で組む文書（[`bodyText.shapingLanguage: 'document'`](/ja/docs/configuration-text#本文)、既定値）では、各文字は、範囲にその文字が入っていてグリフも持つファイルのうち、最後に宣言されたものから描かれます。ブラウザーが`@font-face`規則の中から選ぶのと同じです。文字とその結合記号は1つのファイルにまとめます。どの範囲にも入らない文字は、グリフを持つ最初のファイルから描かれます。この情報のないファイルと、`'host'`の文書のすべてのファイルは、従来どおり渡された順に読まれます。そのため、ファイルの情報を伝えるプロバイダーも、最後に宣言されたファイルを先頭に並べます。こうして情報を伝えたフェイスは、まだ要求されていなかったすべての文字について、もう一度要求されます。後に宣言されたファイルがその文字を持っているかもしれないからです。Sandboxのプロバイダーは、ファイルの情報を伝えます。

フェイスのどのファイルにもグリフのない文字は、フォントの`.notdef`グリフ（多くのフォントでは空の四角）で描かれ、`renderToPdf`はページを描き終えた後に、フェイスごとに1回それを報告します。

```ts
// { kind: 'missingGlyph', family: 'Noto Serif TC', weight: 400, style: 'normal',
//   characters: ['，', '！', '？'], message: '…' }
```

Sandboxは、これと以下の2つの警告を、PDFを生成するたびに**検査**パネルに一覧表示します。本、その設定、リソースが変わると、次のPDFで置き換わるまで、それらは以前のPDFによるものとして示されます。別の本を開くと消えます。

- **太字にはウェイトごとの静的ファイルが必要です**。FontsourceはNoto Serif SCとTCの各ウェイトを別々の静的ファイルとして配信しているので、Sandboxでは太字が使えます。Google Fontsのファイル（`NotoSerifSC[wght].ttf`、25 MB）は可変フォントです。pdf-libはその既定のインスタンスを埋め込むため、700のフェイスは400で印刷され、`renderToPdf`はそれを`variableFontDefaultInstance`として報告します。バンドルでは、fontToolsでウェイトごとに静的インスタンスを1つ切り出し（`fonttools varLib.instancer NotoSerifSC[wght].ttf wght=700`）、`pyftsubset`で本の文字だけにサブセット化してください。
- **TrueType版を使ってください**。Source Han SerifとNoto Serif CJKの`.otf`ファイルはCFFアウトラインで、postext-pdfはこれを丸ごと、1ウェイトあたり8〜25 MB埋め込みます。2 MBを超えるCFFフェイスは`cffEmbeddedWhole`として報告されます。TrueType版（Google Fonts、Fontsource）は、使われたグリフだけにサブセット化されます。日本語では、Noto Serif JPとNoto Sans JP（Google Fonts、またはFontsourceの番号付きスライス）、Shippori Mincho、Zen Old Mincho、BIZ UDMinchoはTrueTypeで提供されています。Source Han Serif JPと、Noto Serif CJKの`JP`の`.otf`ファイルはCFFです。
- **汎CJKフェイスの日本語字形**。漢字、約物、引用符の同じコードポイントでも、日本と中国では字形が異なることがあり、汎CJKフェイス（Source Han、Noto CJK）は両方を持っています。PDFは、日本語のドキュメント（`locale: 'ja'`）と、どのドキュメントでも日本語のアイソレート（`:ltr[…]{lang=ja}`）を、OpenTypeの言語システム`JAN `でシェーピングします。そのため、フェイスの`locl`機能によって、CanvasとHTMLが`lang`を通じて表示するのと同じ日本語の字形が印刷されます。日本語の本の中にある別の言語のアイソレートは、その言語の字形（`'host'`では、中国語はフォントの既定の字形）でシェーピングされ、その`/Lang`を持つ`Span`としてタグ付けされます。[`bodyText.shapingLanguage: 'document'`](/ja/docs/configuration-text#本文)（postext 1.30以降の既定値）では、どのドキュメントもどのアイソレートも、レイアウトが計測したとおり、それぞれの言語でシェーピングされます（簡体字中国語は`ZHS`）。`'host'`では、中国語などのドキュメントは、従来どおりフォントの既定の字形でシェーピングされます。Noto Serif JPのように日本語用に作られたフェイスは既定の字形が日本語のものですが、それでも日本語のテキストの“ ”は`JAN `の字形で組まれます。

あるファミリーに欠けている文字を、別のファミリーから借りることはありません。Noto Serif TCはNoto Serif SCから借りません。収録範囲の問題は、フォントファイルを作る段階で解決しておいてください。红楼梦のショーケースは、TCのサブセットに欠けているグリフをSCのフェイスからコピーしています。

### サーバー側のフォントプロバイダー（Node、ローカルファイル）

Nodeでは、WOFF2の手順を丸ごと省き、ディスクからTTF/OTFファイルを読み込めます。

```ts
import { readFile } from 'node:fs/promises';
import { join } from 'node:path';
import type { PdfFontProvider } from 'postext-pdf';

const FONT_DIR = '/path/to/fonts';

function filename(family: string, weight: number, style: 'normal' | 'italic'): string {
  const slug = family.replace(/\s+/g, '');
  const styleSuffix = style === 'italic' ? 'Italic' : '';
  const weightName =
    weight >= 700 ? 'Bold'
    : weight >= 600 ? 'SemiBold'
    : weight >= 500 ? 'Medium'
    : weight >= 300 ? 'Light'
    : 'Regular';
  return `${slug}-${weightName}${styleSuffix}.ttf`;
}

export const localFontProvider: PdfFontProvider = async (family, weight, style) => {
  const buf = await readFile(join(FONT_DIR, filename(family, weight, style)));
  return new Uint8Array(buf);
};
```

### リソースのバイト列と印刷用マスター

`resourceBytes(fileId)`は画像の生のバイト列を返し、バックエンドはその形式を判別します。

- PNG、JPEG、GIF、WebPは画像として埋め込まれます
- SVGのマークアップはベクターのパスとして描かれ、その`text`は文書に埋め込んだフォントで実際のテキストとして組まれます。ベクターのサブセットにない機能を使っている場合は、ブラウザーで600 dpiでラスタライズされます。`@font-face`規則だけを含む`<style>`（作者が埋め込んだフェイス）は読み飛ばされ、図はベクターのままです（postext-pdf 1.25以降）。それ以外のスタイルシートがあると図はラスターになり、そのラスターは、文字が指定するフェイスを`fontProvider`から得て埋め込んでから作られます（`diagramStyle.inlineFonts`またはリソースの`svg.inlineFonts`が`false`の場合を除きます）
- TIFFとPhotoshopのドキュメント（PSD、PSB）は、それ自身のピクセルから印刷されます。グレー、RGB、CMYKの8ビットまたは16ビットで、持っているICCプロファイルと解像度を使います。CMYKのものはインキをそのまま保ち、グレーとRGBは`print.imageColor`に従います。Photoshopのドキュメントは、「互換性を優先」で保存される統合画像から読みます。JPEG圧縮のTIFFは読めません
- PDFは最初のページがそのまま、フォームXObjectとして埋め込まれます

各画像は、何回描かれてもファイルには1回だけ格納されます。ベクターのパスとして描かれるSVGは、すべてのページが描画するフォームXObjectになるので、30ページのドキュメントで、ページデザインにある枠やロゴは、30回ではなく1回だけ書き込まれます。ページが1つ増えるごとに増えるのは数百バイトです。postext-pdf 1.4までは、各ページがパスのコピーをそれぞれ持っていました。

SVGの図は、`svg.pdfFileId`で**印刷用マスター**を指定できます。同じ図の1ページのPDFで、通常はSVGの書き出し元になった原本です。`renderToPdf`はまず`resourceBytes`にマスターのidを問い合わせます。そして、図として、表のセルの画像（`TableCell.image`）として、デザインの画像として、囲みのアイコン（その`marker`も）として、SVGが描かれるすべての場所で、フォント、グラデーション、色空間を保ったまま、そのページをSVGの代わりに埋め込みます。VDTはそれぞれの使用箇所でマスターのidを保持しているので（図のリソースには`svg.pdfFileId`、セルの画像とデザインの画像ブロックには`pdfFileId`）、本ではどの章にもマスターが使われます。CanvasとHTMLのバックエンドは引き続きSVGを描きます。SVG自身のバイト列が代わりに使われるのは、マスターがない場合、マスターがPDFでない場合、単色インキが有効な場合（`diagramStyle.singleInk`はSVGのマークアップだけを色替えします）の3つです。

```ts
const resources: Resource[] = [{
  id: 'map', typeId: 'figure', kind: 'svg', createdAt: 0, updatedAt: 0,
  svg: { fileId: 'map.svg', width: 800, height: 600, pdfFileId: 'map.pdf' },
}];
const files = new Map([['map.svg', svgBytes], ['map.pdf', masterPdfBytes]]);
const pdf = await renderToPdf(buildDocument({ markdown, resources }, config), {
  fontProvider,
  resourceBytes: (fileId) => files.get(fileId),
});
```

ホストは、`bundleResourceBytes`のように、SVG自身のidに対してマスターのバイト列を返すこともできます。どちらの方法でも動作します。

ブラウザーはTIFFやPhotoshopのドキュメントを表示できないので、それから作ったビットマップのリソースは2つのファイルを持ちます。`bitmap.fileId`はPNGのプレビューで、Canvas、HTML、EPUBはこれを表示します。`bitmap.printFileId`（`printFormat: 'tiff' | 'psd'`付き）は原本です。ホストは、`bundleResourceBytes`やSandboxのように、`bitmap.fileId`に対して原本のバイト列を返し、PDFはそこから印刷します。プレビューも`previewBytes`として渡します（バンドルなら`bundlePreviewBytes`）。原本を復号できないときはプレビューから印刷して`pictureOriginalUnreadable`警告を出し、プレビューがなければプレースホルダーになります。`postext`の`decodePrintRaster(bytes)`と`rasterToRgba(raster)`は原本を読み、プレビューを作ります。Sandboxはファイルを読み込むときにプレビューを作り、バンドルは原本をプレビューの隣に`resources/<名前>.tif`または`.psd`として格納します。

Adobe Illustratorで「PDF互換ファイルを作成」を有効にして保存したファイルはPDFなので、ほかのPDFと同じように印刷用マスターにできます（`.ai`）。そのスウォッチはそれ自身の版です。プリフライトは、インキ表が名前を変えるもの、本のどの色にも定義されていないもの、そして独自の版で刷る作業（`print.plates`）では作業で刷らないものを一覧にします。配置したファイルはそのまま印刷されるためです。

### PDFの縦組み

縦組みのページ（`layout.writingMode: 'vertical-rl'`）は、Canvasが描くのと同じく90度回転した座標系を通して描かれ、テキストは縦方向に組まれます。

- **正立する文字**は、同じ埋め込みファイルから作る2つ目のType0フォントで表示されます。CIDFont、幅、ToUnicodeマップは同じで、`Encoding /Identity-V`（縦組みモード）を使います。ひと続きの文字は1つのテキストオブジェクトになり、そのグリフは自ら1 emずつ下へ進むので（`DW2 [880 −1000]`）、PDFビューアーでは縦の1行を1行として選択・抽出できます。グリフはOpenTypeの`vert`と`fwid`でシェーピングされ、括弧、引用符、中国大陸式の読点、三点リーダー、ダッシュが縦組み用の字形になります。そのままで正立する文字は横組み用のグリフのままです。フォントのどの部分も2回埋め込まれることはありません。
- **ラテン文字の単語と長い数字**は横組み用のフォントで横倒しに組まれ、**1マスに収める数字**は正立し、1字幅より広いときは横方向に詰めて1字幅に収めます。フォントに縦組み用の字形がない記号は、Canvasと同じく回転または移動されます。
- **トラッキング**は文字間に`TJ`の数値として書き込まれ、縦組みモードではペンを下へ移動させます。
- **縦組みの各行**には、そのテキストの`/ActualText`が付くので、コピーやテキスト抽出では書かれたとおりに読み取られます。`pdftotext`とpdf.jsは、行を上から下へ、右から左へと読みます。pdf.jsは1マスに収めた数字の位置で新しい行を始めます。
- **リンク、しおり、移動先**は用紙上の座標に対応付けられます。縦組みの行の上にあるリンクは縦長の細い矩形になり、しおりは見出しの行の上端でページを開きます。
- **タグ付きPDF**は、`Document`要素で組み方向を宣言します（Layout属性の`WritingMode /TbRl`。すべての要素がこれを継承します）。縦組みの章はPDF/UA-1の検証（veraPDF）に合格します。
- **ビューアー**：Acrobat、Preview、Chrome（PDFium）、pdf.js、Popplerは縦組み用のフォントを表示できます。右綴じの本（`page.binding`）は、見開きを右から左に並べるようビューアーにも求めます（`/Direction /R2L`、`/PageLayout /TwoPageRight`）。AcrobatとFoxitはこれに従いますが、Chromeは従いません。

Noto Serif TC（本で使う文字だけ、TrueType）で組んだ43ページの章は約820 KBで、その大半を2つのフォントサブセットが占めます。

### フォームフィールド

`field`属性を持つチップは、入力できるフォームフィールド（AcroForm）になります。チップはほかのチップと同じように組まれ、ボックスを描きます。外観と最小幅（`minWidth`）はスタイルで決まり、チップの語がフィールドの初期値になります。PDFではボックスの上に対話型のフィールドが置かれます。同じ名前を2回使うと、ウィジェットを2つ持つ1つのフィールドになります。

```md
数量 :chip[ ]{style="field" field="pos.a.qty" kind="number"}
単価 :chip[120]{style="field" field="pos.a.price" format="currency"}
小計 :chip[ ]{style="field" field="pos.a.total" format="currency" calc="product(pos.a.qty, pos.a.price)"}
サービス :chip[ ]{style="box" field="pkg.a" kind="checkbox" on="1"}
注文合計 :chip[ ]{style="field" field="order.total" format="currency" calc="sum(pos.a.total, product(pkg.a, 161.75))"}
サイズ :chip[M]{style="field" field="size" kind="choice" options="S|M|L"}
```

- `kind`：`text`（既定）、`number`、`checkbox`、`choice`（選択肢は`options`に`|`区切りで書きます）。`kind`がなく`format`か`calc`を持つチップは数値フィールドになります。
- `on`（チェックボックス）：チェックボックスのオン状態の名前です。チェックが入っているとき、スクリプトはこの値を読みます。`on="1"`にすると、チェックの入ったボックスは計算で1と数えられるので、`product(pkg.a, 161.75)`はチェックが入ったときに固定の価格を加えます。既定は`Yes`で、計算では0と数えられます。
- `format`：`currency`、`decimal`（小数2桁）、`integer`。Acrobatの`AFNumber_Format`と`AFNumber_Keystroke`で書かれ、区切り記号は文書の言語に従います（ドイツ語なら`1.234,56`）。`RenderToPdfOptions.forms.separatorStyle`で別の書き方を指定することもできます。通貨は`forms.currency`（既定は`€`）で、`forms.currencyBefore`が`false`でなければ数値の前に付きます。初期値も書式を適用して描かれます。
- `calc`：`sum(…)`、`product(…)`、`min(…)`、`max(…)`、`avg(…)`。引数には、名前で指すほかのフィールド、数値（小数点はピリオド。例：`161.75`）、入れ子の計算を書けます（例：`sum(pos.a.total, pos.b.total, product(pkg.a, 161.75))`）。フィールドだけを使う計算は`AFSimple_Calculate`として書かれます。数値や入れ子の計算を含むものは、専用の短いCalculateスクリプトになります。このスクリプトも各フィールドを同じように読み（値に`AFMakeNumber`を適用し、数値でないものは0と数えます）、結果を小数6桁に丸めます。計算されるフィールドは読み取り専用になり、計算順序は、入れ子の計算の中も含め、読み取るすべてのフィールドに合わせて決まります。次の場合は`formField`警告が出ます。未知のフィールドを読む計算（0と数えます）、循環、2種類のフィールドに使われた名前、`on`の値が数値でないチェックボックスを含む計算（常に0と数えます）です。
- `readonly`、`required`、`multiline`、`tooltip`：名前のとおりです。

フィールドは、値と入力された文字を、チップのフェイス（`forms.font: 'chip'`、既定）か、`forms.font`で指定した文書のフォントのフェイス（`{ family, weight?, style? }`。ほかのフェイスと同じく`fontProvider`に要求されます）で表示します。このフェイスはサブセットではなく**丸ごと**埋め込まれます。サブセットには、あとから入力される文字のグリフがないためです。使うフィールドがいくつあっても埋め込みは1回だけで、フォームの既定リソース（`/DR`）と各フィールドの既定の外観（`/DA`）で名前が参照され、初期値もこのフェイスで描かれます。丸ごと埋め込んだフェイスは、ページの本文が使うサブセットとは別に、ファイル全体がPDFに入ります（ラテン文字の本文用フェイスで通常50〜300 KB、CJKのフェイスでは数MB）。プロバイダーはTrueType、OpenType、WOFF2（埋め込み前に展開されます）のどれで返してもかまいません。フェイスを丸ごと埋め込めない場合、フィールドは`formField`警告とともにHelveticaで表示されます。該当するのは、ライセンスが埋め込みを禁じている場合（OS/2の`fsType`が制限付きまたはビットマップのみ）、プロバイダーが複数のファイルに分けて返す場合（分割されたフェイス）、形式がWOFFかコレクションの場合です。`forms.font: 'helvetica'`にすると、何も埋め込まずにHelveticaを使います。ビューアーによっては（macOSのプレビューなど）、入力中の文字を独自のフォントで描きますが、値は変わりません。

Acrobat、Foxit、pdf.js（Firefox）をはじめ、多くのビューアーがこれらのスクリプトを実行します。印刷用の規格（PDF/X）では対話型フィールドを使えないため、値はテキストとして描かれます。数値フィールドの値は、フォームでの表示と同じく、書式を適用し、スタイルの`paddingX`の内側でボックスの末尾にそろえて、チップの色で描かれます。

canvasも数値フィールドを同じように描くので、プレビューはPDFと一致します。`renderPageToCanvas`（または`renderPage`、`renderToCanvas`）に、`renderToPdf`と同じ`forms`オプションを渡してください。どちらでも、区切り記号は既定で文書の`locale`（なければハイフネーションの言語）から決まります。数値の書き方を決めるルールは1つで、postextはほかの出力形式のためにそれをエクスポートしています。`formNumberStyle(forms, lang)`はオプションを解決し、`formatFieldNumber(value, format, style)`は値に書式を適用し（数値でないテキストにはundefinedを返します）、`numberFieldText(field, words, style)`は描かれた数値フィールドに表示される文字列を返します。ディスプレイリストでは、フィールドはチップのランに載ります（`inline.field`。レイアウトの`sizePx`と`padPx`を含みます）。

本はこれらのオプションを設定に持てます。`pdfGeneration.forms`は同じフィールド（`currency`、`currencyBefore`、`separatorStyle`、`font`）を取ります。`renderToPdf`とcanvasは、各フィールドをまず自身の`forms`オプションから、次に最初の文書の`pdfGeneration.forms`から、最後に既定値から取ります。組版は変わらず、フィールドの書き方と描き方だけが変わります。Sandboxでは、PDFセクションの**フォームフィールド**グループです。

```ts
pdfGeneration: {
  forms: { currency: 'USD', currencyBefore: true, separatorStyle: 0, font: { family: 'Lora', weight: 400 } },
}
```

**ブラウザーで esm.sh から読み込む場合**は `https://esm.sh/postext-pdf?bundle` をインポートしてください。esm.sh の既定ビルドでは pdf-lib の注釈クラスが別モジュールに分かれ、pdf-lib は各フィールドのウィジェットを受け付けません。PDF に枠は残りますが、書式・計算・属性が失われ、フィールドごとに `formField` 警告が出ます。`?bundle` は pdf-lib を一つのモジュールにまとめ、`postext` は外に残してページと共有します。バンドラー（Vite、webpack、Next.js）と Node には影響しません。

IDMLの書き出しは、同じフィールドをInDesignのフォームフィールドとして書き出します（[プログラムからの利用 › InDesignパッケージ](/ja/docs/configuration-programmatic-usage#indesignパッケージpostext-idml)を参照）。

### PDFのリンク

Markdownのリンク（[文書形式 › リンク](/ja/docs/document-format-inline#リンク)を参照）の語は、URIリンク注釈になります。行ごとに、リンクされた語のひと続きにつき1つです。各注釈は行の矩形を覆い、枠線はありません。アクセシブルな描画では、ひと続きごとに`Link`要素になり、その`/Contents`はそのテキストです。リンクになるのは、絶対URLの`http:`、`https:`、`mailto:`、`tel:`、`ftp:`のターゲットだけです。相対URLはPDFの中では基準となるURLを持たないためです。印字可能なASCII以外の文字はパーセントエンコードされます。`:ref`による参照と目次の行は、ドキュメント内へのリンクのままです。

### 完全なブラウザーの例：構築、描画、ダウンロード

すべてを組み合わせて、VDTを構築し、PDFに描画し、ブラウザーからダウンロードを開始します。

```tsx
import { buildDocument, createMeasurementCache } from 'postext';
import { renderToPdf } from 'postext-pdf';
import { createPdfFontProvider } from './pdfFontProvider';

const fontProvider = createPdfFontProvider();

export async function downloadPdf(markdown: string, config: PostextConfig) {
  const cache = createMeasurementCache();
  const vdt = buildDocument({ markdown }, config, cache);

  const bytes = await renderToPdf(vdt, { fontProvider });

  const blob = new Blob([bytes.slice().buffer], { type: 'application/pdf' });
  const url = URL.createObjectURL(blob);
  const a = document.createElement('a');
  a.href = url;
  a.download = 'document.pdf';
  document.body.appendChild(a);
  a.click();
  a.remove();
  setTimeout(() => URL.revokeObjectURL(url), 1000);
}
```

**重要**：Webフォントを参照する設定では、`buildDocument`の*前*に`ensureConfigFontsLoaded(config)`（または同等の処理）を呼び出してください。レイアウトは、そのファミリーについてブラウザーがその時点で持っているフォントメトリクスで計測されます。本来のフォントがまだ届いていなければ、VDTは代替フォントで計測され、PDFはCanvasやHTMLの出力と一致しません。Sandboxは描画のたびに、その前にこれを明示的に行っています（`packages/postext-sandbox/src/viewport/pdf/PdfViewport.tsx`を参照）。

### ワーカーでPDFを描画する

`postext-pdf/worker`は、`renderToPdf`をメインスレッドの外に移します。ワーカーはテキスト、ベクターの図、構造ツリー、ファイルそのものを書き出します。Webページ側でしかできない処理が2つあり、ワーカーはそれらをメインスレッドに依頼します。フォントの取得と、`<img>`を通じたSVGのラスタライズです。数百ページの本では、描画にかかる数秒のあいだページが固まってしまうのを防げます。数ページなら、`renderToPdf`を直接呼び出すほうが簡単です。

```ts
import { createPdfWorker } from 'postext-pdf/worker';

const pdfWorker = createPdfWorker();
const bytes = await pdfWorker.render(docs, {
  fontProvider,                                     // runs on this thread
  resourceBytes: new Map([['map.svg', svgBytes]]),  // a Map; its buffers move to the worker
  onProgress: ({ phase, pages, totalPages }) => showProgress(phase, pages, totalPages),
  onWarning: (w) => console.info(w.message),
});
pdfWorker.dispose();
```

- `render(docs, options)`は、1つのドキュメント、または本の章のドキュメントの配列を受け取ります。オプションは`renderToPdf`のものですが、違いが2つあります。`resourceBytes`（と`previewBytes`）は`Map<string, Uint8Array>`で、そのバッファーは転送されるため、手元に残すバイト列はコピーを渡してください。`rasterizeSvg`は、指定した場合はメインスレッドで実行されます。指定しなければ、ページ自身の`Image`とcanvasが処理します。
- 1つのハンドルが描画するドキュメントは一度に1つです。`dispose()`はワーカーを終了し、保留中の描画をすべて`AbortError`（`DOMException`）で拒否（reject）します。これはキャンセルとして扱ってください。`dispose()`のあとにプロバイダーが返したフォントや画像は破棄されます。
- `inspect(bytes)`は完成したPDFをワーカー上で読み直し（`inspectPrintPdf`）、そのレポートで解決します。バイト列をPDFとして読めないときは`undefined`です。バイト列はコピーされるので、手元のものはそのまま使えます。呼ばない限り何も読みません。
- `createPdfWorker({ worker })`は、自分で作成した`Worker`を受け取ります。ワーカーのURLを制御するビルドツール向けです。そのワーカーでは`postext-pdf/worker/entry`を実行する必要があります。

**CDNから使う場合**。既定では、ワーカーのスクリプトはパッケージ自身のURL（`new URL('./pdf.worker.js', import.meta.url)`）から読み込まれます。別のオリジンのページでは、これを起動できないことがあります。`esm.sh`からインポートすると、`createPdfWorker()`は`Failed to construct 'Worker': Script at 'https://esm.sh/postext-pdf@…/pdf.worker.js' cannot be accessed from origin …`を投げます。代わりに、エントリーをインポートする同一オリジンのモジュールワーカーを起動してください（バージョンを固定する場合は、両方のURLで同じバージョンに固定します）。

```js
import { createPdfWorker } from 'https://esm.sh/postext-pdf/worker';

const entry = URL.createObjectURL(new Blob(
  ["import 'https://esm.sh/postext-pdf/worker/entry';"],
  { type: 'text/javascript' },
));
const pdfWorker = createPdfWorker({ worker: new Worker(entry, { type: 'module' }) });
```

`postext/worker`のレイアウトワーカーには、このラッパーは要りません。`createLayoutWorker()`は、オプションなしではesm.shから、ほかのサーバーからは`url`オプションで、自分のエントリーを起動します（[CDNからワーカーを読み込む](/ja/docs/configuration-programmatic-usage#cdnからワーカーを読み込む)を参照）。

### 印刷入稿用のPDF

本番の印刷ワークフローでは、描画の前に次の設定を調整してください。

- **`page.cutLines.enabled: true`** — 仕上がり線の外側に塗り足し領域とトンボを加え、各ページにTrimBoxとBleedBoxを設定します。[トンボ](/ja/docs/configuration-page-layout#トンボ)を参照してください。
- **`print: { standard: 'pdfx4', outputProfile: 'fogra51' }`**（または`'pdfx1a'`） — 印刷所が確認する出力インテント、識別情報、ボックスを備えたPDF/Xファイルを書き出します。すべての色とRGBの画像はICCプロファイルで分版され、K 100%はオーバープリントになり、大きな黒い面はリッチブラックで刷られます。[印刷出力（設定）](/ja/docs/configuration-fonts-colors-viewers#印刷出力設定)を参照してください。
- **`colorSpace: 'cmyk'`**（または`pdfGeneration: { forceColorSpace: true, colorSpace: 'cmyk' }`） — PDF/Xの識別情報なしで、同じ分版を行います（トンボは常にレジストレーションカラーです）。PDFの印刷用マスターはそのまま埋め込まれます。
- **`page.dpi: 300`** — レイアウトの1インチあたりのpx数です。自身の解像度を持たないビットマップは、原寸ではこの解像度で印刷されます。印刷サイズで300 ppiに満たない画像は、[プリフライト](/ja/docs/configuration-pdf-output#プリフライト)が報告します。
- **`ColorValue.cmyk`** — CMYKで指定した色は、その値のまま印刷されます。
- **`{ pageNegative: true }`**（`RenderToPdfOptions`のオプション） — Differenceブレンドモードで仕上がり領域を反転します（トンボは反転しません）。明るい地に暗い文字の組版を、プリフライトで確認するのに便利です。
- **`print.dieLine`** — 抜き加工のある本の抜き型の線を、印刷機がインキを付けない専用の版に描きます（既定の名前は`Die`。PDF/X-1a以外ではオプションコンテンツグループに入ります）。[PDFでの抜き型の線](/ja/docs/special-inks-die-cuts#pdfでの抜き型の線)を参照してください。

### 特色

特色（Pantone、コーポレートインキ、ニスなど）は専用の版で刷られます。`model: 'spot'` の色は `ColorValue.spot` にインキを持ちます。`name` は印刷所が使う版の名前、`cmyk` は100 %のインキの見え方（インキがない環境でPDFが代わりに使う値）、`tint` はパーセントでの網点濃度（既定は100）、`overprint` はニスのように下の色をノックアウトせずオーバープリントさせ、`finish` は特殊インキが何であるか（メタリック、箔、蛍光、不透明ホワイト、ニス）を示します。`hex` は画面上の表示色です。それぞれの加工がどう刷られ、どう表示されるかは[特殊インキと抜き加工](/ja/docs/special-inks-die-cuts#加工)で説明しています。

CMYKまたはPDF/XのPDFでは、各インキがその名前の `Separation` 色空間として書き出され、そのインキの色はそれぞれの濃度で塗られます。同じ `name` の色は同じ版を共有します。2色刷り（墨と特色1色）、一部の要素だけ特色を使うプロセス印刷、選んだ部分へのオーバープリントのニスといった一般的な仕事に対応します。`diagramStyle.singleInk` に特色を使うと、SVG図版はその版の濃淡で刷られます。RGBのPDFと画面では `hex` で塗られます。

**SVG内の特色。** [単色刷りの仕組み](/ja/docs/configuration-resources#単色刷りの仕組み)を参照してください。

```ts
colorPalette: [
  { id: 'brand', name: 'Brand', value: { hex: '#1f3f99', model: 'spot', spot: { name: 'PANTONE 286 C', cmyk: { c: 100, m: 66, y: 0, k: 2 } } } },
  { id: 'brand-40', name: 'Brand 40 %', value: { hex: '#a5b6dd', model: 'spot', spot: { name: 'PANTONE 286 C', cmyk: { c: 100, m: 66, y: 0, k: 2 }, tint: 40 } } },
  { id: 'varnish', name: 'Varnish', value: { hex: '#f4f4ee', model: 'spot', spot: { name: 'Varnish', cmyk: { c: 0, m: 0, y: 10, k: 0 }, finish: { kind: 'varnish', sheen: 'gloss' } } } },
],
diagramStyle: { singleInk: true, inkColor: { hex: '#1f3f99', model: 'spot', paletteId: 'brand' } },
```

プリフライトは特色を1インキとして数え、総インキ量の上限から除外し、作業で使う特色を一覧にします（`spotInks`）。SVG画像が名前で指定するインキも含みます。また、次の場合に警告します。同じインキが異なる値で2回定義されているとき（`spotInkConflict`。PDFは最初の定義を使います）、SVGが指定するインキをパレットの色も `cmyk` を持つインキ表のエントリーも定義していないとき（`spotInkUndefined`。そのインキは専用の版に刷られ、SVGの色のCMYKが代替値になります。版は名前ごとに1つです）、PDFが版名を書き換える必要があるとき（`spotInkName`。下記参照）、2つの版名が大文字小文字やスペースの違いしかないとき（`spotInkSimilar`。`PANTONE 185 C` と `Pantone  185 C` は2つの版になります）。`preflightDocument` は、SVGがどのインキを指定しているかを `svgInks(fileId)` から知ります。これは `svgSpotInks(markup)` がファイル内で見つけた名前を返す関数で、Sandboxの**検査**パネルと `postext check` が渡します。

**版名。** 名前は入力したとおりに書き出されます。アクセント、記号、`#` はUTF-8でPDFに入り（`Rojo Médica` は `/Rojo#20M#C3#A9dica`）、Acrobat、RIP、印刷所のプリフライトもそのように読みます。版が持てない名前は、別の名前で書き出されます。`All`、`None`、`Cyan`、`Magenta`、`Yellow`、`Black`（大文字小文字を問わず）には後ろに ink という語が付き（`All ink`）、制御文字は取り除かれ、UTF-8で127バイトを超える名前は文字の境目で切られて短いハッシュで終わります。そのため、先頭が同じ2つの長い名前も2つの版のままです。プリフライトの `spotInkName` は理由（`problem`：`reserved`、`process`、`control`、`tooLong`）とPDFが書き出す名前（`written`）を示し、レンダリングは名前を変えるたびに `onWarning` で知らせます（`spotInkRenamed`）。名前を自分で決めるには、インキ表でそのインキに `pdfName` を指定します。

**1色に1インキ。** 印刷用のレンダリングは色を画面上のhexで識別するため、印刷値を指定する2つの色（2つのインキ、またはインキとCMYKで定義した色）は同じhexを共有できません。共有している場合、後の色は1段階離れた最も近い空きhexへ移され（画面上では見分けられません）、それぞれが自分の版で刷られます。特色と同じhexを持つ通常の画面色（`model: 'hex'`）はその特色として刷られます。明示するには、パレットのエントリーにリンクしてください。移された色は画面上でも変わります。1つのチャンネルで1段階（1/255）、まず青のチャンネルから、すべての出力（Canvas、HTML、EPUB、RGBのPDF）で変わります。目で見分けられる差よりはるかに小さく、印刷用のレンダリングが塗られたhexからインキを読み取るための代償です。保存された設定は変わりません。

#### インキ表

`print.inks` は、色、SVG、読み込んだファイルがどう呼んでいても、作業のインキをどのように印刷所へ渡すかを指定します。表にないインキは、その色の定義どおりに刷られます。

```ts
interface PrintInk {
  name: string;                    // spot.nameまたはSVGが呼ぶインキ名。
  aliases?: string[];              // 同じインキの別名。この版で刷られる。
  pdfName?: string;                // PDF内の版名。既定はname。
  output?: 'spot' | 'process';     // 'process'はインキを代替値からCMYKで刷る。
  cmyk?: CmykPercent;              // 100 %での代替値。色側の値より優先。
  overprint?: boolean;             // 色側の値より優先。
  finish?: InkFinish;              // メタリック、箔、蛍光、白、ニス。色側の値より優先。
}
```

名前と別名は、大文字小文字と連続するスペースを区別せずに照合されます。インキを使う色がいくつあっても、名前の変更は1行で済みます。別名は、デザイナーのスウォッチ、SVG（`data-spot`、`icc-named-color`）、以前のパレットが同じインキに付けていた名前を1つの版にまとめます。`output: 'process'` は、印刷機にそのインキのユニットがないとき、すべての濃度を含めてインキをCMYKで刷ります。`finish` は、名前がどこから来たものでも（`Gold`という名前を使うSVGや読み込んだファイルも含めて）そのインキを特殊インキにします。

Sandboxでは、この表は**デザイン › 書き出し › 印刷の準備 › インキ表**にあります。インキごとにカードが1枚あり、**インキ名**、**別名**、**PDFでの版名**、**刷り方**、**代替CMYK**、**オーバープリント**、**加工**、**光沢**を設定します。**色が使っているインキ**には、本の色が使っていて表にないインキが並び、それぞれのボタンで表に加えられます。

```ts
print: {
  standard: 'pdfx4',
  inks: [
    { name: 'Azul corporativo', pdfName: 'PANTONE 286 C', aliases: ['Pantone 286C', 'Azul'] },
    { name: 'Varnish', output: 'process' },
  ],
},
```

#### 2色刷り

`print.plates` は作業で刷る版を指定し、それ以外の版には何も刷りません。墨と特色1色、特色2色、墨1色だけの本などです。プロセスの版は `Cyan`、`Magenta`、`Yellow`、`Black` です。特色の版は、PDFでの名前か、インキ表の名前または別名で指定します。

```ts
interface PrintPlatesConfig {
  inks?: string[];                                // 版。空なら、通常どおりすべての版。
  images?: string[];                              // 画像を刷る版。1つか2つ。
  curves?: Record<string, Array<[number, number]>>; // 画像の版のカーブ。[階調, インキ]（%）。
}
```

- 作業で刷るインキの色や、作業で刷るチャンネルだけを使うCMYKの色は、そのまま使われます。
- それ以外の色は射影されます。出力プロファイルを通した見え方が最も近い、1版または2版の掛け合わせで刷られます。2つのインキの掛け合わせはPDFでは `DeviceN` 色空間になり、グレーは `Black` だけに残ります。リッチブラックは、作業でプロセス4色をすべて刷る場合を除いて使われません。
- 画像は、1版ならモノトーン、2版ならダブルトーンで刷られます。各ピクセルの階調（明度）が各版のカーブを通ります。`images` の既定は `Black` で、作業で墨を刷らない場合は最初の版です。モノトーンのカーブは直線です。ダブルトーンは最初の版をシャドウに、2番目の版を中間調に置きます。`curves` はどちらのカーブも置き換えます。

```ts
print: {
  standard: 'pdfx4',
  plates: {
    inks: ['Black', 'PANTONE 286 C'],
    images: ['Black', 'PANTONE 286 C'],
    curves: { 'PANTONE 286 C': [[0, 0], [50, 35], [100, 70]] },
  },
},
```

プリフライトはジョブの版と、射影で動く色をひとつずつ一覧にします。ジョブで刷らない特色やCMYKの色は、掛け合わせがΔE 6以内に収まれば情報、それを超えるとき、または出力プロファイルを読み込む前は警告です（`offPlateInk`、`offPlateCmyk`）。ΔE 6を超えて離れる画面の色も警告です（`offPlateColor`）。どの色にもインキ表のどのエントリーにも定義されていない特色の版は警告で、黒として刷られ、校正でも黒で表示されます。このようなジョブでは図の印刷用原稿は使わず、そのSVGを版の上に組みます。配置したPDFページや復号できない画像はそれ自身のインキを保ち、レンダリングが警告します（`artworkOffPlates`）。Sandboxでは版を「印刷の準備 → 版」で設定します。そのプレビューと印刷プレビューは本で定めた色を表示し、版で刷った色は表示しません。PDFを確認してください。印刷用に検査が使われているインキを一覧にします。

### 画像の色

画像は、それが作られたときの色から分版されます。`print.imageColor`は、画像のピクセルの読み方を指定します。

```ts
interface PrintImageColorConfig {
  embeddedProfile?: 'use' | 'ignore';                  // A picture's own ICC profile. Default 'ignore'.
  assignedRgbProfile?: { name: string; fileId: string }; // Read every RGB picture through this .icc instead.
  grayDotGain?: 'profile' | 'none' | number;           // Greyscale pictures on black. Default 'none'.
  cmykProfile?: 'convert' | 'keep';                    // A CMYK picture of another press. Default 'keep'.
}
```

既定値では、画像は以前のバージョンと同じように印刷されます。RGB 画像はすべて sRGB として読み込まれ（`'ignore'`）、グレースケール画像はほかの画像と同様に分版され（`'none'`）、CMYK 画像は値をそのまま保ちます（`'keep'`）。以下の各動作は、それぞれのフィールドで有効になります。

- **画像自身のプロファイル。** プロファイルを埋め込んだPNG（`iCCP`）やJPEG（`ICC_PROFILE`）は、そのプロファイルを通して読みます。そのため、Adobe RGBやDisplay P3の写真は、sRGBとしてではなく見えるとおりに分版されます。プロファイルのない画像やsRGBのプロファイルを持つ画像は、これまでどおりsRGBとして読みます。`'ignore'`はすべての画像をsRGBとして読みます。
- **割り当てたプロファイル。** `assignedRgbProfile`は保存済みの`.icc`を指定し、RGBの画像は何を埋め込んでいてもすべてそれを通して読みます。たとえば、プロファイルが失われた一連の写真に使います。そのバイト列は`resourceBytes`から渡します。渡されなければ画像自身のプロファイルを使い、`imageProfileUnavailable`の警告を出します。
- **RIPに任せる。** PDF/X-4で`convertImages: false`のとき、sRGB以外のプロファイルを持つ画像は元の色のまま書き出され、そのプロファイルで`ICCBased`としてタグ付けされ、印刷所のRIPが変換します。
- **グレースケール。** グレースケールの画像（グレーのPNGやJPEG、またはグレーのプロファイルを持つ画像）は墨インキだけで刷られ、4色グレーにはなりません。その階調は、画像自身のプロファイルを通して（なければ画面に表示されるとおりに）読まれ、印刷機に合わせられます。`'profile'`は出力プロファイルの黒を通します。そのドットゲインは印刷条件にすでに含まれています。数値は50 %の網点での印刷機のドットゲイン（パーセント、通常は10–30）で、代わりにそれを補正します。`'none'`はこれまでどおり値をそのまま書き出します。

```ts
print: {
  standard: 'pdfx4',
  imageColor: { grayDotGain: 20 },
},
```

- **別の印刷機のCMYK画像。** 画像自身のプロファイルが別の印刷条件であるCMYKの画像（FOGRA向けの本に入った、SWOPや新聞用紙向けに分版された写真など）は、出力の印刷条件に合わせて分版し直されます（`cmykProfile: 'convert'`）。墨だけの部分は墨だけのまま残ります。TIFFやPhotoshopの画像はピクセルから分版し直します。CMYKのJPEGはピクセルをデコードしないので、PDF/X-4では画像自身のプロファイルで`ICCBased`としてタグ付けされ、RIPが変換します。そのようなタグを許さないPDF/X-1aでは、そのまま渡されます。その場合、ホストが画像のプロファイル（`imageProfile`）を渡していれば、プリフライトが警告します（`cmykImageForeign`）。PDF/X-4で`convertImages: false`のときは、TIFFやPhotoshopの画像も同じようにタグ付けされます。`'keep'`は、すべてのCMYKの画像の値をそのまま刷ります。

**1枚の画像だけの設定。** リソースの`printColor`は、本の`print.imageColor`と同じフィールドを受け取り、その画像だけに適用します。たとえば、プロファイルを無視すべき写真、割り当てたプロファイルを通して読む写真、ドットゲインの異なるグレーの画像です。Sandboxでは、画像のカードで、画像自身のプロファイルを通して読むかどうか（「印刷時の色」）、グレーを印刷機にどう合わせるか（「印刷時のグレー」）、画像に割り当てるプロファイル（「割り当てプロファイル」、`.icc`ファイル）を指定します。バンドルは、本と画像に割り当てたプロファイルを`profiles/`フォルダーに収めます。本全体の設定は「印刷の準備 → 画像」にあります。

```ts
{ id: 'archive-photo', kind: 'bitmap', bitmap: { fileId: 'photo.jpg', format: 'jpeg', width: 2400, height: 1600 },
  printColor: { embeddedProfile: 'ignore' } }
```


### CMYKで指定した色

CMYKで書いた色は、その値をそのまま保ちます。印刷用の描画では`ColorValue.cmyk`（%）がそのまま使われ、`hex`は画面での表示になります。CMYKで指定したパレットの項目は、それに連動するすべての色に適用されます。

```ts
colorPalette: [
  { id: 'brand', name: 'Brand', value: { hex: '#00a0e3', model: 'cmyk', cmyk: { c: 100, m: 0, y: 0, k: 0 } } },
],
```

### オーバープリントする色

印刷用の描画では、どの色もオーバープリントにできます。`ColorValue`に`overprint: true`を指定すると、その色で描くもの（文字、罫線、ボックス、地色）はすべて、下にあるものをノックアウトせず、その上に重ねて刷られます。プロセスカラーは分版されるとおりに、オーバープリントのグラフィックステートの下で書き出されます。特色は、同じインキを別の色がノックアウトしている場所でも、そのインキの版でオーバープリントします。オーバープリントするK 100%の黒は黒の扱いを保ち、大きな面は引き続きリッチブラックになります（`black.richBlack`）。RGBのPDFと画面はこれを無視します。パレットの項目に指定すると、それにリンクするすべての色が、その濃度も含めてオーバープリントします。リンクした色は項目の設定に従い、独自の設定は持ちません。部やセクションのパレットもこの設定を保つので、部の色の文字もオーバープリントします。

```ts
colorPalette: [
  { id: 'title', name: 'Title', value: { hex: '#c00020', model: 'cmyk', cmyk: { c: 0, m: 100, y: 80, k: 10 }, overprint: true } },
],
```

印刷用の描画は、レイアウトが塗るhexで色を見分けます。そのため、オーバープリントする色がノックアウトする色とhexを共有することはありません。一致した場合は、特色と同じように、オーバープリントする側が1段階（1つのチャンネルで1/255）ずれます。オーバープリントする項目の部の色も、同じようにして本のノックアウトする色から離れます。オーバープリントしてインキを載せない色（紙の白、0%のインキ）は、印刷すると消えてしまいます。プリフライトはこれを重大として報告します（`overprintWhite`）。使えるコード（約2,500万）より多くの異なる色を含む描画では、残りの色をノックアウトし、警告を出します（`overprintsExhausted`）。Sandboxでは、カラーピッカーの「印刷時にオーバープリント」スイッチで設定します。

`preflightDocument(doc, options)`は組み上がった文書を検査し、問題の一覧を返します。各問題には、`kind`、`severity`（`'critical'`、`'warning'`、`'info'`）、本全体での`pageIndex`、問題のある`rect`（ページのpx）と、要素にあればそのソースの範囲が付きます。`kind`は`lowImageResolution`、`declaredPixelsMismatch`、`rgbImage`、`thinRule`、`smallProcessText`、`inkLimit`、`safeZone`、`nearTrim`です。`transform`を渡さないときは、無彩色を1色、それ以外の色を3色と数え、インキ量は検査しません。渡すと、色数もインキ量も正確に求めます。画像の解像度は、リソースが宣言するピクセル数から求めます。`imageSize(fileId)`がファイル自体のピクセル数を返すとき（バイト列に対する`bitmapInfo`、またはデコードした画像）は、そちらを使います。宣言がファイルと1ピクセルより大きく食い違うと`declaredPixelsMismatch`として1回報告され、ファイルにあるより多いピクセル数を宣言している場合は警告になります。`placedImageResolutions(doc, { resources, imageSize })`は、プリフライトの有効・無効にかかわらず、配置したすべてのビットマップをその実効ppiとともに一覧にします。図のラベルは、`smallProcessText`、`inkLimit`、`safeZone`では文字として数えます。

```ts
import { bitmapInfo, outputTransform, parseIccProfile, preflightDocument, resolvePrintConfig } from 'postext';
import { inspectPrintMaster } from 'postext-pdf';

const print = resolvePrintConfig(config.print);
const transform = outputTransform(parseIccProfile(fogra51Bytes), { intent: print.renderingIntent });
const issues = preflightDocument(doc, {
  print,
  transform,
  resources,                                    // pixel sizes of the bitmaps
  imageSize: (fileId) => bitmapInfo(bytesOf(fileId)),  // the files' real pixels
  imageColor: (fileId) => colourOf(fileId),     // 'rgb' | 'cmyk' | 'gray', from the file
});
if (issues.some((i) => i.severity === 'critical')) process.exit(1);

const master = await inspectPrintMaster(masterBytes);
// => { nonEmbeddedFonts: ['Helvetica'], rgb: true, transparency: false }
```

### リファレンス実装

Sandboxの`PdfViewport`コンポーネント（`packages/postext-sandbox/src/viewport/pdf/PdfViewport.tsx`）は、上の要素を組み合わせて、再計算、ダウンロード、印刷のボタンを備えたライブプレビューにしたもので、ブラウザー内でPDFを扱う組み込みの出発点に適しています。VDTは共有のレイアウトワーカーで構築するので（[Web Workerでレイアウトを実行する](/ja/docs/configuration-programmatic-usage#web-workerでレイアウトを実行する)を参照）、**再計算**をクリックしても、パイプラインの実行中にUIが固まりません。メインスレッドが受け持つのは`renderToPdf`だけです（VDTができていれば、これは高速です）。
